## 1. 저희 회신 — 기다리신 것 둘

### A1. `NOT_ATTEMPTED` — **값을 하나 늘려 주세요**(1번 안)

문구만 중립화하는 2번 안은 **더 나쁩니다.**

지금 `NOT_ATTEMPTED` 하나에 두 상황이 겹쳐 있습니다.

| 상황 | 학생에게 | 지금 |
|---|---|---|
| 마감 전이라 아직 안 냈다 | **정상.** 아직 시간이 있다 | `NOT_ATTEMPTED` |
| 마감이 지나도록 안 냈다 | **놓쳤다.** 매니저에게 알려야 한다 | `NOT_ATTEMPTED` |

문구를 *"아직 응시 기록이 없습니다"* 로 중립화하면 두 상황이 **같은 말을 듣습니다.**
그러면 **정말 놓친 학생에게서 경고가 사라집니다** — 지금 화면은 그 학생에게
*"사정이 있었다면 매니저에게 알려 주세요"* 를 붙이고 있는데, 그 문장이 마감 전
학생에게도 나가면 안 되고 반대로 놓친 학생에게서 빠져도 안 됩니다.

**값이 갈리면 화면이 갈립니다.** 분기 하나 느는 비용이 경고를 잃는 것보다 쌉니다.

```
NOT_STARTED     제출 마감 전 · 응시 기록 없음   →  "아직 시작하지 않았어요"
NOT_ATTEMPTED   마감이 지났고 응시 기록 없음    →  "이 회차는 응시하지 않았어요"
```

**이름은 제안일 뿐이니 편하신 쪽으로 하셔도 됩니다.** 저희는 값 집합이 갈리기만
하면 됩니다.

> 참고로 **홈은 이미 이 둘을 갈라서 줍니다** — 6차가 `SUBMISSION_REQUIRED`(할 일)로
> 오고 마감이 지나면 `SUBMISSION_MISSED`(놓침)로 옵니다. 리포트만 한 값으로 뭉쳐
> 있어서 같은 회차를 두 화면이 다르게 말합니다.

### A2. 5차 개인 응시 창 — **지금은 고치지 마세요**

**고치면 어긋난 곳이 하나 더 늡니다.**

지금 5차 데이터를 뜯어보면 이렇습니다.

```
회차 응시 창   08-11 ~ 08-14
개인 응시 창   07-31 ~ 08-03      ← trainee01: 제출 07-30 · 분석 완료 07-31
```

**개인 창은 틀린 값이 아닙니다.** "분석 완료 + 24시간" 규칙대로 정확히 계산된
값입니다. 어긋난 것은 **회차 일정만 나중에 8월로 옮겨졌다**는 것이고, 제출·분석
시각은 7월 그대로 남아 있습니다.

그래서 개인 창만 8월로 밀면 **"분석이 끝나고 11일 뒤에 열리는 응시권"** 이 되어
24시간 규칙이 깨집니다. 지금은 어긋난 데가 한 군데인데 두 군데가 됩니다.

제대로 맞추려면 제출·분석 시각까지 함께 옮겨야 하는데 5차 데이터를 다시 만드는
일이고, R4 수정으로 **5차는 이미 `past`로 내려가 화면 영향이 없습니다.**

### 🔴 다만 이것은 시드만의 문제가 아닙니다

**회차 일정을 나중에 바꾸면 개인 창이 따라가지 않는다** — 이것이 5차에서 일어난
일이고, 사람이 조심해서 막을 수 있는 것이 아닙니다.

**그리고 곧 겪으실 수 있습니다.** R3(24차 §6)에서 6차 제출 마감을 8/23 이후로
미루는 안을 검토 중이신데, **그때 이미 제출한 9팀의 개인 창이 어떻게 되는지**가
같은 문제입니다.

```
지금       6차 제출 마감 08-21 · 회차 응시 창 08-21 ~ 08-24
미루면     제출 마감 08-2X   · 회차 응시 창은?  · 이미 제출한 9팀의 개인 창은?
```

**회차 일정을 옮기실 때 개인 수행 행도 함께 옮겨 주세요.** 마감을 미루기로
정하시면 그때 어떻게 처리하실지만 알려 주시면 저희도 화면을 맞추겠습니다.

## 2. 🟡 R1 — 두 응시 창이 어긋날 때 어느 쪽이 이기나요

응답에 응시 창이 **두 개** 옵니다.

```
roundAssessmentOpenAt · roundAssessmentDueAt    회차 응시 창 (운영자가 정한 일정)
assessmentOpenAt      · assessmentCloseAt       개인 응시 창 (분석 완료 + 24시간)
```

**둘이 어긋날 수 있는데 어느 쪽이 이기는지가 스펙에 없습니다.**

### 언제 어긋나나

학생이 **회차 마감 직전에 제출**하면 개인 창이 회차 창 밖으로 나갑니다.

```
회차 창    ~ 08-24 00:00
분석 완료    08-23 23:00   →   개인 창 ~ 08-24 23:00     ← 회차보다 23시간 뒤
```

반대 방향은 5차에서 이미 보셨습니다 — 개인 창이 회차 창보다 **앞서 닫힌** 경우입니다.

### 화면이 무엇을 못 하나

**저희 화면은 `representativeStatus`를 믿고 그리므로 지금 당장 틀리지는 않습니다.**
서버가 판정한 대로 따라갑니다.

문제는 그 판정을 **서버 안에서 무엇이 정하는지 저희가 모른다**는 것입니다. 지금은
남은 시간 안내(*"응시 창 마감까지 N시간"*)에 어느 값을 써야 하는지 정할 근거가
없어서, `verifyClosesAt` 하나만 쓰고 있습니다. 두 값이 갈리면 **화면이 말하는
마감과 서버가 막는 시점이 달라집니다.**

### 요청

**규칙 한 줄만 알려 주세요.** 스펙 설명에 적어 주시면 제일 좋습니다.

- **개인 창이 이긴다** → 분석이 끝났으면 회차가 닫혀도 24시간은 보장된다
- **회차 창이 이긴다** → 회차가 닫히면 개인 창이 남아 있어도 끝난다
- **둘의 교집합** → 둘 다 열려 있을 때만 응시 가능

저희가 기대하는 것은 **"둘의 교집합"** 입니다(가장 좁은 것이 이긴다). 다만 그러면
마감 직전 제출자가 24시간을 못 받는데, 그것이 의도인지 아닌지는 기획 판단이라
저희가 정할 수 없습니다.

> 무엇으로 정하시든 **`representativeStatus`가 그 규칙을 반영하고 있으면** 화면은
> 지금 그대로 둡니다. 남은 시간 문구에 쓸 값만 알려 주시면 됩니다.

## 3. 🟡 R2 — `api:check` error 1건

```
❌ [nullable] 설명에는 null이라 적혀 있는데 타입이 null을 허용하지 않는다 — 1건
     · TraineeRosterResponse.rounds
```

설명문에는 `null`이 될 수 있다고 적혀 있는데 타입이 `null`을 안 받습니다.

**optional보다 나쁩니다** — 컴파일러가 null 검사를 요구하지 않는데 런타임에 null이
옵니다. 그러면 화면이 `rounds.map(...)`을 그대로 쓰다가 터집니다.

### 저희 CI를 막습니다

`api:check`가 error를 내면 종료코드 1이라 **스펙을 커밋하면 `develop`이 빨개집니다.**
19차 R1·23차 R1과 같은 자리입니다.

교육생 화면은 이 스키마를 쓰지 않지만(오퍼레이터 명단입니다), **스펙은 하나라
저희 쪽 전체가 막힙니다.**

### 요청

다른 필드에 이미 적용하신 것과 같은 방식이면 됩니다.

```java
@Schema(nullable = true)
List<...> rounds;
```

설명문이 사실이라면 위처럼, **실제로는 항상 온다면 설명문을 고쳐** 주셔도 됩니다.
둘 중 무엇이 사실인지만 맞으면 됩니다.

## 4. 24차 반영 확인 ✅

스펙을 다시 받아(`sha256 5bf74d88…` · 오퍼레이션 122 · 스키마 277) 대조하고,
**실계정으로 응답까지 확인**했습니다.

| 24차 요청 | 결과 |
|---|---|
| **R4** 회차 유실 | ✅ **이미 배포됐습니다.** `current: 6차` · 합계 6개로 `/reports`와 일치 |
| **R1** `retryState` | ✅ **이미 배포됐습니다.** 2차가 `PENDING → NONE`, 모순 0건 |
| **R5** 정렬 | ✅ **이미 배포됐습니다.** `past: 5·4·3·2·1` 최신순 |
| **R6** 옛 축 서술 | 전부 시드 — 그대로 두겠습니다 |
| **R2** `explain` | ✅ `s058` 계정으로 확인 — 3차에서 **대상 개념에만** `explain` 2줄, 4차는 `PENDING`이라 차단 |
| **R3** 마감 vs 재개 | ⏳ 운영 판단 대기 중 |
| **`upcoming`에 `OPEN` 가능** | ✅ 스키마 설명 확인. 저희 화면은 `roundStatus`로 분기하지 않아 그대로 동작합니다 |

**"다음 배포"라고 하셨는데 셋 다 지금 나옵니다.** 저희 쪽 홈이 바로 달라졌습니다.

```
코드를 제출할 차례예요 · 8일 남음 · 제출 마감 08-21
미니프로젝트 6차 이해도 확인 · C반 1팀 · 교안 Spring 백엔드 설계
```

### 회신을 받고 화면을 고친 것

**공개 범위가 매니저 소관이라는 답**(24차 회신 §2)에 따라 두 곳을 바로잡았습니다.

- *"자세한 해설은 다시 보기를 마치면 열려요"* → **"매니저가 공개하면 열려요"**
- *"다시 보기를 마쳤어요 · 자세한 해설이 열렸습니다"* → 뒷문장을 지웠습니다
  (1차처럼 마쳐도 안 열리는 회차가 있어 거짓이 됩니다)

그리고 **잠금 안내를 개념마다 반복하던 것을 리포트 머리로 올렸습니다.**
`disclosureScope`가 리포트 단위 값이라 개념마다 자물쇠를 그리면 같은 말이 세 번
반복되고 *"이 개념만 잠겼나"* 로 읽힙니다.

**특히 도움이 된 것 하나.** R4의 원인을 *"뷰는 맞는데 서비스가 응답을 만들면서
버리고 있었다"* 까지 짚어 주신 것입니다. 저희가 세운 가설(반마다 회차 배정이 다르다)이
왜 틀렸는지도 함께 알려 주셔서, `trainee-draft`가 6차를 보여준 이유가 반이 아니라
**경쟁할 OPEN 회차가 없어서**였다는 것까지 정리됐습니다.
`조회된 회차 = current + upcoming + past` 라는 불변식을 세우신 것도, 앞으로 같은
유실이 안 생긴다는 뜻이라 신뢰가 됩니다.

## 5. 저희 쪽 상태

```
TR-01 홈       ✅ 실서버 연동 완료
TR-02 제출     ✅ 실서버 연동 완료 — 제출 버튼만 막아 둠(24차 R3 대기)
TR-04 리포트   ✅ 실서버 연동 완료
TR-03 세션     ⏳ API 8개 사용 불가 — 목 유지
```

**교육생 4화면 중 3개가 실서버에 붙었습니다.** 남은 것은 세션(TR-03)뿐이고,
23차에 8/14 목표라고 알려 주신 것을 기다리고 있습니다.

**저희가 지금 못 밟는 경로는 하나입니다** — ZIP 실제 업로드입니다. 제출 API 2개가
`사용 불가`라 멱등키와 50MB 상한을 한 번도 실제로 태워 보지 못했습니다.
24차 R3이 정해지면 그때 확인하겠습니다.

R2(`api:check` error)만 저희 CI를 막고 있고, 나머지는 확인만 주시면 됩니다.
