## 1. 결정 — 공개 기본값

> **공개 기본값을 우선 '공개'로 설정했습니다.**

**이게 무엇에 대한 결정인가** — 매니저가 자기 반 교육생에게 *그 학생 본인의 리포트를
열어 줄지*를 정하는 권한이다. 기획의 **GOV-03(열람 범위 통제)** 이 그것이고,
`PUT /reports/{reportId}/disclosure`가 그 API다. 교육생은 검증 세션을 마쳐도 매니저가
열어 주기 전에는 자기 리포트를 못 본다.

### ⚠️ 기획 원안과 세 군데가 다르다

원안은 `SC-M03-measurement-plan.md`(회차 설정 모달 · GOV-03)와 `SC-T05-result-report.md`에 있다.

| | 기획 원안 | 새 결정 |
|---|---|---|
| **① 기본값** | **비공개** — *"미지정·조회 실패 시 기본 비공개(안전)"* | **공개** |
| **② 범위를 누가 정하나** | 매니저가 **비공개/요약/전체 3단 라디오**로 고름 | 공개 여부만 매니저 · **요약/전체는 통과 여부로 자동** |
| **③ 설정 단위** | **회차(체크포인트)** — `PATCH /checkpoints/{id}/disclosure` (D121) | *"교육생 **개인별**로 활성화"* |

**②가 가장 큰 변화다.** 원안은 매니저가 *얼마나 보여줄지*를 골랐는데, 새 규칙은
매니저가 *열지 말지*만 정하고 범위는 서버가 판정한다. 매니저 설정 UI가 라디오 3개에서
토글 하나로 준다.

**③은 API가 이미 개인별이다.** `reportId` 단위이고 리포트 1건 = 교육생 1명 × 1회차다.
다만 원안이 *"일괄 공개 = 검토 없이 노출 = 유해"*(D121)라며 벌크 설정 페이지를 명시적으로
배제했던 항목이라, 개인별로 가면 매니저가 학생 수만큼 눌러야 한다 — **그 부담이 §4의
"자동 공개" 논의가 나온 진짜 배경으로 보인다.**

**①은 ③과 묶여 있다.** 개인별인데 기본이 공개면 매니저가 아무것도 안 해도 전원이 본다 —
원안이 기본 비공개로 둔 이유가 정확히 그걸 막는 것이었다. 16차 요청서 Q2로 물어 뒀다.

## 3. `SUMMARY` vs `FULL` — 통과 여부로 갈리고, 재시험으로 승격된다

**기준은 도달 2단이다** — 재시험 대상(불합격)을 가르는 선과 같다.

```
합격 (2단 이상)  ─────────────────────────────→ FULL
불합격 (0·1단)   → SUMMARY ──재시험 완료──→ FULL
                    └ 교안 위치 + 다시 보기 버튼
```

| | FULL(전체) | SUMMARY(일부) |
|---|---|---|
| 개념 도달 단계 | ⭕ | ⭕ |
| 서술 | ⭕ | ⭕ |
| 교안 위치 | — | ⭕ |
| 다시 보기 활성화 | — | ⭕ |
| 해설 | ⭕ | ❌ |
| 문답 원문 | ⭕ | ❌ |

> **못 한 쪽에 다시 보기와 교안 위치가 붙고, 잘한 쪽에 해설과 문답 원문이 붙는다.**
> 통과하지 못한 개념은 *답을 먼저 보여주지 않고 다시 풀게* 하는 구조다 —
> `SUMMARY`에서 해설·문답 원문이 빠지는 것은 누락이 아니라 **의도**다.
>
> **그래서 `SUMMARY`는 재시험 전의 임시 상태다.** 재시험을 마치면 그 개념도 FULL이 된다
> — 지금 화면이 이미 그렇게 동작한다(`retryState PENDING`이면 해설 잠금, `DONE`이면 열림).

### 문항 없음 — 제3의 자리

개념 3개가 고정인데 그중 하나가 **그 학생 코드에 없으면 문항이 안 만들어진다**(`unasked`).
서버는 이것을 `0단`과 엄격히 구분한다 — *"`level0`과 `unasked`를 합치면 안 된다."*

| | 도달 단계 | 재시험 | 리포트 표시 |
|---|---|---|---|
| 합격 | 2~4단 | ❌ | FULL |
| 불합격 | 0·1단 | ⭕ | SUMMARY → 재시험 후 FULL |
| **문항 없음** | **없음** | **❌ 대상 아님** | **표시만** — *"코드에 이 개념이 없어 묻지 못했습니다 — 못한 것이 아닙니다"* |

**교육생에게도 보여준다**(확인받음). 안 보여주면 개념 3개 중 2개만 뜨는 이유를 학생이 알 수 없다.
매니저·오퍼레이터 화면은 이미 해치 무늬와 범례까지 만들어 두고 같은 문구를 쓴다.

## 4. 리포트가 열리는 시점

```
검증 세션 종료 → 리포트 생성 → 리포트 발행 → 매니저가 공개 활성화 → 교육생이 조회
                                              └ 이게 없으면 영원히 못 본다
```

- 리포트가 생성·발행돼도 **매니저의 공개 활성화 없이는 교육생 조회가 절대 불가**.
- 매니저가 개인별로 열어 주지 않는 한, **모든 교육생은 일괄 공개 시점에 동시에** 보게 된다.
- 즉 **검증 세션을 일찍 봤든 늦게 봤든 조회 시점은 같다.**

### "프로젝트 종료 기간"이 나왔던 이유 — 그리고 접는 이유

**전제한 사고:** 매니저가 공개 활성화를 깜빡하면 교육생이 **무기한** 리포트를 못 본다.

그래서 코드 제출 마감 시점에 **일괄 자동 공개**를 걸려고 했다. 그런데 생성·발행에 시간이 걸려서
**마감 시점에 공개해도 리포트가 아직 만들어지는 중이라 안 보이는** 경우가 생긴다.
그 틈을 메우려고 나온 것이 `시작 기간 - 코드제출 마감 기간 - 프로젝트 종료 기간` 3단 일정이었다.

**결론(둘 중 하나로 간다):**

1. 그냥 **코드 제출 시점 자동 공개**로 두고, 늦게 낸 사람은 리포트를 조금 늦게 보는 것으로 감수
2. **자동 공개를 아예 안 걸고 매니저가 수동으로 공개** — *"지금 상황에선 이게 베스트"*

> ⏳ **미결.** 2번이 현재 유력하지만 확정이 아니다. 1번을 고르면 프로젝트에 종료 기간 필드가
> 필요 없어지므로, **일정 필드 설계가 이 결정에 걸려 있다.**

## 4-2. 재시험 리포트 — 한 회차에 하나, 안에서 병기 (제안)

*"재시험 결과의 리포트도 교육생이 볼 수 있어야 한다"* 인데 **원점수는 안 바뀐다.**
그럼 한 회차에 리포트가 둘인지 하나 안에 병기인지가 갈리는데, **병기를 권한다.**

| | 근거 |
|---|---|
| ① | **원점수가 정본이다.** 문서를 둘로 쪼개면 "어느 게 진짜냐"가 볼 때마다 생긴다 |
| ② | 재시험은 **불합격 개념만** 본다 — 떼어 놓으면 개념 하나짜리 반쪽 문서가 되고 맥락이 없다 |
| ③ | 좌측 레일이 **회차** 목록이다. `미프 3차`가 둘 생기면 회차 축이 시도 축으로 바뀐다 |
| ④ | 매니저 공개 설정이 **2배**가 된다 — 개인별로 여는 구조라 부담이 이미 크다 |
| ⑤ | 화면이 이미 그 구조다 — 개념 카드에 `comparedReach {before, after}` 자리가 있다 |

**다만 서버는 두 시도를 다 갖고 있어야 한다** — 문답 원문이 2세트다. 개념별로
`attempts: [{ seq, reachedLevel, qa[] }]` 형태로 오면 화면이 병기든 분리든 나중에 고를 수 있다.

## 5. 지금 코드와의 차이

| | 지금 (`src/features/trainee/report/`) | 바뀌어야 하는 것 |
|---|---|---|
| 공개 상태 | `PENDING_VISIBILITY` 하나로 뭉뚱그림 | `NOT_CONFIGURED` / `WITHHELD` / `RELEASED` |
| 공개 범위 | **없다** — 항상 전량을 그린다 | `SUMMARY` / `FULL` 분기 |
| 도달 단계 | `LadderLevel = 1\|2\|3\|4` | **`0` 추가** (`--color-reach-0`은 이미 있다) |
| 문항 없음 | **없다** | 개념이 3개 미만으로 올 수 있다 — 제3의 표시 |
| 통과 여부 | **없다** | 2단 기준. 범위·재시험 대상을 같이 정한다 |
| 해설 잠금 | `retryState`가 정한다(`explain`은 다시 보기 완료 후 열림) | ⭕ **방향은 맞다** — 다만 SUMMARY면 `explain`이 **아예 안 온다** |
| 문답 원문 | `qa[]`를 항상 준다 | SUMMARY면 **안 온다** · FULL이면 재시험분까지 2세트 |
| 교안 위치 | `curriculumRef?` — 선택 | SUMMARY에서 **필수** |
| 다시 보기 | `isRetryTarget` 플래그를 목이 임의로 정함 | **도달 2단 미만** — 파생값이라 서버가 준다 |
| 재시험 횟수 | 제한 없음 | **1회만** — 마치면 버튼이 사라진다 |

**타입 구조가 한 겹 바뀐다.** 지금 `RoundReport`는 발행 상태 6종의 유니온이고 `PublishedReport`
안에서 `retryState`가 갈리는데, 여기에 **공개 범위라는 두 번째 축**이 생긴다. `ConceptReport`의
`explain`·`qa`가 **범위에 따라 아예 없는 필드**가 되므로 옵셔널이 아니라 유니온으로 가르는 편이
맞다 — 그래야 SUMMARY 화면이 `qa`를 그릴 수 없다는 걸 컴파일러가 막는다.

## 6. 막힘 — 붙일 API가 없다

리포트 4개가 **전부 `x-readiness: unavailable`** 이다(2026-08-12 `api:pull` 기준).

| readiness | 엔드포인트 | |
|---|---|---|
| `unavailable` | `GET /api/v0/reports` | 내 리포트 전량 |
| `unavailable` | `GET /api/v0/reports/{reportId}` | 단건 |
| `unavailable` | `GET /api/v0/reports/{reportId}/disclosure` | 공개 상태 조회 |
| `unavailable` | `PUT /api/v0/reports/{reportId}/disclosure` | 공개 범위 설정 |

**공개 정책이 정해졌는데 그 정책을 읽고 쓰는 API 2개가 아직 닫혀 있다.** 함수가 생성되지 않으므로
(`src/api/PENDING.md`) 이 화면은 목으로 계속 돈다. 백엔드가 `available`로 바꾸면
`npm run api:gen`만 다시 돌리면 된다.

**백엔드에 물을 것** — 전부 [16차 요청서](../backend/backend-api-requests-16.md) R4·Q2로 나갔다.

- `release_status`와 `SUMMARY`/`FULL`이 **같은 응답에 오는가** — disclosure 조회를 따로 해야 하나
- §1의 세 갈래(기본값 · 범위 판정 주체 · 설정 단위) 확정
- 통과 여부를 **판정해서 주는가**(`FULL`/`SUMMARY` 자체를 주는가), 아니면 단계 숫자만 주고
  화면이 가르는가 — **서버가 줘야 한다**(api-boundary §2, 매니저 화면과 갈리면 안 된다)
- `SUMMARY`면 `explanation`·`qa`를 **아예 빼 주는가** — 기획도 *"비공개 회차는 잠금 플래그만
  반환하고 본문은 전송하지 않는다. 클라이언트에 숨기는 방식 금지"* 로 같은 요구를 한다
