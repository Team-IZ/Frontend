# 백엔드 API — 39차 요청 · 보낸 관찰 신호가 돌아오지 않습니다

> **37차에서 `POST /activity`를 붙였습니다.** 창 이탈·연결 끊김·첫 타이핑 지연이
> `204`로 접수됩니다.
>
> 🔴 **그런데 그 값을 다시 볼 수 있는 곳이 없습니다.** 저희가 확인할 수 있는 것은
> `204`까지이고, **매니저 화면에도 그 숫자가 오지 않습니다.** 지금 구조로는 신호를
> 아무리 정확히 보내도 아무도 못 봅니다.
>
> 규정이 응시 중 이탈을 금지하고 있으니, 그것을 **집행할 수 있는 경로**까지 이어져야
> 의미가 있다고 봅니다.

---

## 0. 한눈에

| | 무엇 | 우선순위 |
|---|---|---|
| **R1** | 보낸 관찰 신호를 **되읽을 수 있는 곳이 없습니다** — 저장되는지도 확인 못 합니다 | 🔴 |
| **R2** | `voidEvidence`에 **이탈·연결 끊김·첫 타이핑이 빠져 있습니다** | 🔴 |
| **R3** | `PATCH /assessment-attempts/{attemptId}/validity`가 **`사용 불가`입니다** | 🔴 집행 경로 |
| **R4** | `Reference`의 `path`·`lineStart`·`lineEnd`가 **필수인데 `null`로 옵니다** | 🟡 |
| **R5** | `PROBLEM_ALREADY_CLOSED`가 **아직 안 온 문제에도** 옵니다 — 급하지 않습니다 | 🟢 |
| **정정** | **37차 R4는 저희 오해였습니다** — 서버 데이터가 아니라 저희가 스펙을 잘못 읽었습니다 | ℹ️ |

배포본 스펙(오퍼레이션 146개)에서 확인했습니다.

## 1. 지금 사슬이 어디서 끊기나

```
학생이 창을 떠남
   ↓
POST /assessment-sessions/{id}/activity   ✅ 204 (붙였고 동작합니다)
   ↓
서버 저장 (window_leave_count · connection_loss_count …)   ❓ 확인할 방법이 없습니다
   ↓
매니저가 봄                                                🔴 오는 필드가 없습니다
   ↓
PATCH /assessment-attempts/{id}/validity                   🔴 사용 불가
```

**저희 쪽은 끝났습니다.** 아래 셋은 실측으로 확인했습니다.

| 신호 | 언제 | 결과 |
|---|---|---|
| `awaySeconds` | 창을 떠났다 돌아온 순간 | ✅ 204 |
| `disconnectedSeconds` | 재연결된 순간 | ✅ 204 |
| `firstKeystrokeDelayMs` | 질문을 보고 첫 글자를 칠 때 | ✅ 204 |

경계도 스펙대로입니다 — 끝난 세션은 `409`를 무시하고, 빈 본문은 아예 안 보내고,
범위(`0~86400`)를 넘는 값은 잘라서 보냅니다.

> ℹ️ **한 가지는 저희도 확인 못 했습니다.** 실제로 다른 앱으로 전환하는 동작은 자동화
> (Playwright)로 재현되지 않습니다 — `visibilitychange`·`blur`·`focus`가 **하나도 뜨지
> 않습니다**(직접 계측). 이벤트를 직접 발생시켜 저희 처리 경로가 도는 것까지는
> 확인했고, 실제 창 전환은 사람이 손으로 봐야 합니다.

## 2. 🔴 R1 — 저장됐는지 확인할 방법이 없습니다

전체 스펙에서 이 값을 돌려주는 조회를 찾지 못했습니다.

```
window_leave_count · connection_loss_count · *_away_count · *_first_keystroke_delay_ms
  → 이 값을 담아 주는 응답 스키마가 없습니다
```

`SessionActivityRequest`(보내는 쪽)에만 존재하고 받는 쪽이 없습니다. 그래서 **저희는
신호가 쌓이고 있는지 아닌지를 알 수 없습니다** — `204`는 "요청을 받았다"까지만
말해 줍니다.

### 부탁드리는 것

계정 하나로 이탈을 몇 번 만든 뒤 **DB 값을 한 번 확인해 주시겠습니까.** 그것만
알려 주셔도 저희 쪽 구현이 맞는지 확정됩니다.

> 저희가 태운 계정으로 확인하실 수 있습니다 — `s020@techbridge.kr`(창 이탈·연결
> 끊김·첫 타이핑을 모두 보냈습니다) · `s022@nextcode.ac.kr`.

조회 경로를 새로 열어 주실 필요는 없습니다. **R2가 되면 매니저 화면에서 자연히
보이므로** 그쪽이 본류입니다.

---

## 3. 🔴 R2 — `voidEvidence`에 관찰 신호가 없습니다

무효 응시 브리프의 `voidEvidence`가 *"시스템이 본 것"* 이라고 되어 있어 여기 있을
줄 알았는데, 담긴 값이 넷뿐입니다.

| 지금 있는 것 | 뜻 |
|---|---|
| `unanswered` | 문제 단위 무응답 수 |
| `totalQuestions` | 그 회차 문제 수 |
| `copied` | 답변이 질문 문장과 완전 일치 |
| `durationMin` | 세션 시작~종료 분 |

**이탈 횟수·연결 끊김·첫 타이핑 지연이 빠져 있습니다.** 그런데 `POST /activity` 설명은
이 경로가 없으면 *"무효 응시 판정과 매니저 브리프의 「어느 답변이 의심스러운가」가 빈
값으로 돌아간다"* 고 적고 있습니다 — 그 "어느 답변이 의심스러운가"가 들어갈 자리가
지금 응답에 없습니다.

### 부탁드리는 것

`VoidEvidenceResponse`에 세 값을 더해 주세요.

```
windowLeaveCount      창을 떠난 횟수
connectionLossCount   연결이 끊긴 횟수
firstKeystrokeDelayMs 답변별(또는 최솟값) 첫 타이핑 지연
```

**화면은 그대로 그리기만 합니다.** 스펙이 *"관찰이지 판정이 아닙니다"* 라고 못박아
두었고 저희도 그 전제로 만듭니다 — 숫자를 보여주되 "이 학생은 부정행위"라고 화면이
말하지 않습니다.

## 4. 🔴 R3 — 무효 처리 경로가 닫혀 있습니다

```
PATCH /api/v0/assessment-attempts/{attemptId}/validity   ⚠️ 사용 불가
```

매니저가 무효를 확정하거나 되돌리는 **유일한 경로**입니다. 이것이 없으면 신호를 모아
보여줘도 매니저가 할 수 있는 일이 없습니다.

**저희 쪽 자리는 이미 있습니다** — 면담 케이스 응답이 `attemptId`·`voidReviewPending`·
`voidConfirmed`를 주고 있고, 저희 매니저 화면 타입에도 들어와 있습니다. 열어 주시면
버튼을 붙입니다.

**언제쯤 열릴지만 알려 주세요.** 그 전까지는 저희도 무효 확인 UI를 만들지 않겠습니다 —
누르면 안 되는 버튼을 먼저 만들면 학생·매니저 모두에게 고장으로 보입니다.

## 5. 🟡 R4 — `Reference` 필드가 비어서 옵니다

실제 응시 중인 계정(`trainee01@example.com`)의 문제 1에서 받은 값입니다.

```json
{"type":"CURRICULUM_EVIDENCE","path":null,"lineStart":null,"lineEnd":null,"axisCode":null}
{"type":"CALLER","path":"…/CohortController.java","lineStart":1,"lineEnd":1,"axisCode":null}
{"type":"CALLER","path":"…/EnrollmentController.java","lineStart":1,"lineEnd":1,"axisCode":null}
{"type":"CALLER","path":"…/EnrollmentResponse.java","lineStart":1,"lineEnd":1,"axisCode":null}
```

두 가지를 여쭙습니다.

**① `CURRICULUM_EVIDENCE`는 필드가 전부 `null`입니다** — 스키마에서는 `path`·`lineStart`·
`lineEnd`가 **필수**인데 실제로는 비어 옵니다. 스키마를 `nullable`로 고치실지, 값을
채우실지 알려 주세요. 저희는 지금 **`path`가 없는 참조를 버리고** 있습니다.

**② `CALLER`의 줄 범위가 `1~1`입니다** — 다른 파일을 가리키면서 1번 줄이라 실제 위치가
아닌 것으로 보입니다. 그대로 그리면 `CohortController.java:1`이 되어 없는 곳을
가리키므로, 지금은 **구간이 한 줄뿐이면 위치를 빼고 파일 이름만** 보여줍니다.

호출부의 실제 줄 범위를 주실 수 있으면 그 자리로 데려가겠습니다. 어려우면 지금처럼
파일 이름만 두어도 됩니다 — **알려만 주세요.**

---

## 6. 🟢 R5 — 같은 코드가 서로 다른 두 상황을 가리킵니다

문제 번호를 바꿔 가며 불러 봤습니다(진행 중 커서는 1번).

| 요청 | 응답 |
|---|---|
| 이미 끝난 문제 | `409 PROBLEM_ALREADY_CLOSED` |
| **아직 안 온 문제(2·3)** | **`409 PROBLEM_ALREADY_CLOSED`** ← 같은 코드 |
| 범위 밖(0·99) | `400 VALIDATION_FAILED` |

**지금 저희가 곤란하지는 않습니다.** 어느 쪽이든 화면이 하는 일이 같아서(서버에 커서를
다시 물어 따라간다) 그대로 동작합니다.

다만 *"이미 끝난 문제는 다시 열 수 없습니다"* 라는 메시지가 **아직 시작도 안 한 문제**에
붙는 것이라, 로그를 보실 때 오해하실 수 있어 적어 둡니다. 앞으로 화면이 두 경우를 다르게
말해야 할 일이 생기면 그때 코드를 나눠 주시면 됩니다 — **지금은 요청이 아니라 관찰입니다.**

## 7. ℹ️ 정정 — 37차 R4는 저희 오해였습니다

37차에서 *"코드 스니펫과 줄 번호가 서로 안 맞습니다"* 라고 보냈는데, **스펙을 다시 읽어
보니 저희가 틀렸습니다.**

| 필드 | 스펙 원문 | 저희가 읽은 것 |
|---|---|---|
| `snippet` | **문제를 낸 파일 전체** | 〃 |
| `lineStart` | **강조할 구간 시작(파일 기준 절대 줄 번호)** | 🔴 스니펫이 시작하는 줄 |

`lineStart`를 스니펫의 첫 줄 번호로 오해해서, 파일 첫 줄에 `48`을 붙이고 있었습니다.
실제 파일이 243줄이라 **모든 줄이 47칸 밀렸습니다.** 저희 버그이고 고쳤습니다.

시드 데이터(4줄짜리)에서는 우연히 티가 나지 않아 서버 문제로 오인했습니다. **실제 응시
계정을 보고서야 드러났습니다** — 번거롭게 해 드려 죄송합니다.

**37차 R4는 없던 것으로 봐 주세요.** 남는 것은 위 R4(`Reference` 필드)뿐입니다.
