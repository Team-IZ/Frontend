# 도메인 계층 · 엔티티 관계 (백엔드 ERD 근거)

> 명세(ORG-01·02·03) + 실무 구조(반·다수 프로젝트·프로젝트별 팀 재편성) 반영.
> 목적: 백엔드가 이 문서로 ERD를, 프론트가 SC-M02(기수·반·팀·프로젝트 관리)를 설계.
> ⚠️ 명세와 다른 점은 §4에 별도 표기(보완 제안).

---

## 1. 전체 그림

```
기관 Organization ─────────────── 테넌트(슈퍼어드민이 생성)
 └─ 기수 Cohort (7기, 8기)         ── 총괄 매니저(ORG_MANAGE)가 생성(ORG-01), 기간·단계
     └─ 반 Class (A반, B반)         ── 안정적 그룹. 교육생 소속. 담당 매니저(N:M)
         ├─ 교육생 Trainee           ── 반에 소속(enrollment)
         └─ 프로젝트 Project          ── 반에서 진행, 여러 개(개인/팀), 시간순 반복
             └─ 팀 Team              ── 팀 프로젝트일 때만. 프로젝트마다 새로 편성
                 └─ 팀원 TeamMembership ── 그 프로젝트의 교육생들(from/to 이력)

매니저 Manager ──< ManagerAssignment(N:M) >── 반 Class
```

## 2. 엔티티별 존재 이유 (아래→위)

각 엔티티에 3문: **① 왜 따로 존재하나(안 나누면 뭐가 깨지나) ② 관계 ③ 카디널리티.**

### 교육생 Trainee
- ① 측정·채점·리포트의 대상. 개인 단위 데이터(점수·세션·시그널)가 여기 붙음.
- ② 하나의 **반**에 소속(enrollment). 여러 **팀**(프로젝트별)에 참여.
- ③ 반 1 : 교육생 N.

### 반 Class (신규)
- ① **안정적 소속 그룹.** 학생이 "어디 소속인지", 매니저가 "무엇을 담당하는지"의 기준. 이게 없으면 대형 기수(100명)에서 담당·조회 범위를 나눌 단위가 없어 매니저가 전체를 다 봐야 함.
- ② **기수**에 속함. **교육생**을 담고, **매니저**가 담당(N:M), **프로젝트**가 여기서 진행.
- ③ 기수 1 : 반 N. (소규모 기수는 반 1개=전체로 흡수 → 분기 없음.)

### 기수 Cohort
- ① **함께 시작하는 코호트 단위(7기).** 측정 회차(체크포인트)·벤치마크·통계의 기준 모집단. 회차 평균·히트맵이 전부 기수 단위.
- ② **기관**에 속함. **반**을 담음. 매니저가 생성(ORG-01).
- ③ 기관 1 : 기수 N.

### 프로젝트 Project
- ① **측정 대상 산출물의 맥락.** 교육생이 제출하는 코드가 "어느 프로젝트의 것인지". 요구사항·레포·추출범위가 여기 붙음(ORG-03).
- ② **반**에서 진행. 유형 **개인/팀**. 팀 유형이면 **팀**을 가짐.
- ③ 반 1 : 프로젝트 N(시간순 여러 개). 개인 프로젝트는 팀 없이 교육생별 제출.

### 팀 Team
- ① **한 프로젝트의 협업 단위.** 기여 편차(ENG-03)·팀 분석(DASH-13)의 대상. 프로젝트마다 편성이 달라지므로 **프로젝트에 종속**.
- ② **프로젝트**에 속함. **교육생**을 **TeamMembership**(from/to 이력)으로 담음.
- ③ 프로젝트 1 : 팀 N(팀 프로젝트). 다음 프로젝트 = 새 팀.

### 매니저 Manager (권한 계층: 총괄 / 담당 — 역할 하나, 권한 묶음 둘)
- ① 교육 운영자. 담당 범위 내 학생을 측정·개입·리포트.
- ② **기관** 소속 계정. **반**을 담당(ManagerAssignment, N:M). 그만둬도 **삭제 금지 — soft-delete(status=INACTIVE)**로 이름·이메일 보존(과거 기수에 담당 이름이 남아야 하므로).
- ③ 기관 1 : 매니저 N. 매니저 N : 반 M(한 매니저가 여러 반, 한 반에 여러 매니저).
- ④ **권한 계층(D63) — 별도 역할 아님, 매니저 역할 안의 권한 묶음 차이:**
  - **총괄 매니저** = `ORG_MANAGE`(+`COHORT_MANAGE`·`MANAGER_ASSIGN`) 보유 → 기수 개설·반 구성·**다른 매니저 초대·배정**·명단. 기관 전체 범위. 슈퍼어드민이 초대하는 **첫 매니저**가 이 권한 보유(부트스트랩).
  - **담당 매니저** = `ORG_MANAGE` 미보유, 배정 기수 한정으로 `ASSESSMENT_RUN`·`SCORE_REVIEW`·`INTERVENTION_MANAGE`·`REPORT_VIEW`·`APPEAL_REVIEW`.
  - 소규모 기관: 한 사람이 총괄 권한 묶음 전체 보유(개설도 운영도 겸직). 규모 있으면 총괄 1~소수 + 담당 다수.
  - **닭-달걀 해소:** 슈퍼어드민 → 기관 + 첫 총괄 매니저 → 총괄이 기수·매니저 세팅 → 담당이 기수 운영. 역할명 하드코딩 금지·권한 플래그로 관리(AUTH-09·AUTH-11). 순수 운영 관리자(직무 분리)는 엔터프라이즈 후속 시 권한→역할 승격.

### ManagerAssignment (조인 · 이력형)
- ① 매니저↔반 담당을 **기간형 이력**으로: `assigned_at` / `unassigned_at`(nullable). 배정을 **삭제하지 않고 마감**하므로, 매니저가 그만둬도 **과거 기수엔 담당 이름이 남고 이후 기수엔 안 나옴**(1·2기엔 남고 3기엔 없음). 반이 기수에 종속되므로 **기수 단위 담당이 자동 스코프**됨. (확장 대비 — 담당 단위 반→기수 변경 시 조인만 교체.)
- ② 매니저 ↔ 반. 필드: assigned_at, unassigned_at.
- ③ N:M(시점별).

## 3. "안정 vs 유동" 분리가 핵심

| 안정적(오래 유지) | 유동적(자주 바뀜) |
|---|---|
| 기관·기수·반·교육생 소속·매니저 담당 | 프로젝트·팀·팀 편성 |

**팀을 프로젝트 밑에 둔 이유:** 팀이 매 프로젝트마다 달라지므로, 팀을 기수 밑 고정으로 두면 프로젝트마다 팀을 지웠다 다시 만드는 억지가 됨. 프로젝트 밑에 두면 "새 프로젝트 = 새 팀"이 자연스럽고, 과거 프로젝트의 팀 편성·기여 데이터가 그대로 보존됨(회차 독립성 B2와도 정합).

### 이력 보존 원칙 (덮어쓰지 말고 기간으로 쌓는다)
**소속·담당·편성은 현재값을 덮어쓰지 않고 `from/to` 기간으로 쌓고, 계정은 삭제 대신 soft-delete한다.** 그래야 과거 시점의 사실("1기 담당은 누구였나", "그때 팀은 어떻게 짜였나")이 이후 변경·퇴사에도 보존된다.

| 무엇 | 이력 방식 |
|---|---|
| 매니저 담당 | `ManagerAssignment.assigned_at/unassigned_at` + 매니저 soft-delete |
| 팀 편성 | `TeamMembership.from_at/to_at` (명세 ORG-02) |
| 교육생 반 소속 | 이동 가능하면 `from_at/to_at`(대개 안정, 기본은 단일 소속) |
| 최종 리포트의 담당자·점수 | 생성 시 **스냅샷**으로 고정(원본 변경 무관) |

근거: 이건 새 규칙이 아니라 명세에 이미 깔린 패턴 — TeamMembership from/to(ORG-02), due_at 스냅샷(DASH-04), before/after 불변(GOV-01), soft-delete·보존기간(SYS-01).

## 4. 명세와 다른 점 (보완 제안 — 백엔드 전달)

| 명세(ORG-02·03) | 실무 반영(이 문서) | 이유 |
|---|---|---|
| 팀이 **기수** 소속, 재배정 이력(from/to) | 팀이 **프로젝트** 소속, 프로젝트마다 편성 | 프로젝트마다 팀이 달라짐 |
| 팀·프로젝트가 기수 아래 평면 | 기수 **> 반 >** (교육생·프로젝트) | 반이라는 안정적 그룹이 실제로 존재 |
| 프로젝트 1개 뉘앙스 | 반당 프로젝트 **N개**(개인/팀 혼재) | 기간 내 여러 프로젝트 반복 |
| 매니저 "담당 기수"(DASH-01) | 매니저 담당 **반**(N:M) | 담당 단위가 반. 반 없으면 기수=반 1개로 흡수 |

**⚠️ 트랙(Track) 재조정 필요:** 명세가 DASH-15·16·17에서 **트랙**을 그룹 축으로 씀(예: "코드스쿨 A트랙"). 트랙이 (a)반과 같은 것인지, (b)커리큘럼 트랙(AI/백엔드 등)으로 반과 직교하는지 확인 필요. 확인 후 반=트랙으로 합치거나 별도 축으로 유지.

## 5. 측정과의 연결 (참고)

- **체크포인트(회차)는 기수 단위**(PLAN-01). 매 회차, 교육생이 **현재 프로젝트**의 코드를 제출(Submission) → 검증 세션 → 채점.
- 한 교육생의 회차별 제출물은 서로 다른 프로젝트일 수 있음(시간순). 회차 측정은 **매 회차 독립**(신규 커밋 스냅샷, B2).
- 기여 편차(ENG-03)·팀 분석은 **그 프로젝트의 팀** 안에서 계산.
- 코호트 통계(히트맵·벤치마크)는 **기수**(필요시 반) 단위 집계.

## 6. 이 구조가 닿는 화면

- **SC-S01(슈퍼어드민):** 기관까지. 기수 수는 지표로만.
- **SC-M02 기수 구성(매니저):** 기수 생성 → **반** 구성 → 교육생 배정(안정적 구조). D18로 프로젝트·팀 분리.
- **SC-M13 프로젝트·팀(매니저):** **프로젝트**(개인/팀·기간) 생성 → 팀 프로젝트면 **팀** 편성(레포 팀별), 개인 프로젝트는 **학생별 레포**(반복 운영). D18.
- **SC-M04·M05·M06:** 반·팀·기수 단위 분석·조회.
