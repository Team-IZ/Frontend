## 1. 조회 흐름

```
useManagerCohort()      GET /members/me/enrollments        ─┐ cohortId가 정해져야
                                                            │ 아래 둘이 시작한다
useTraineeDetail()      GET .../trainees/{id}              ─┤ 병렬 — 헤더·회차 격자
useTraineeTimeline()    GET .../trainees/{id}/timeline     ─┘ 이력(커서, size=100)

「자세히」를 펼칠 때만
useTraineeEvaluation()  GET /projects/{pid}/evaluations/{uid}   채점 근거(축별 note)
```

**둘을 하나의 로딩으로 묶지 않는다**(async-states §2-1) — 격자가 먼저 오면 먼저
그린다. 셋째는 회차마다 `projectId`가 달라 **쿼리 키가 회차별로 갈리고**, 펼친 것만
나간다(회차 6개를 미리 받으면 안 볼 것까지 6콜).

**권한 없음은 서버가 판정한다** — 담당 밖 교육생은 404(`MANAGER_SCOPE_NOT_FOUND`).
화면이 id 목록으로 가르지 않는다. ⚠ 다만 **그 404가 지금 무응답**이라(32차 R1)
카드가 뜰 일이 없고 요청 예산을 다 쓴 뒤 실패로 떨어진다.

## 4. 실측 · 판정 · 고침

### 4-1. 🔴 타임라인이 **13~17초**다. `size`가 무시된다

```
size=100   13474ms   14512B   회차 5 · 이벤트 15 · hasNext=false
size=20    15014ms   14512B   회차 5 · 이벤트 15
size=5     12374ms   14512B   회차 5 · 이벤트 15   ← 5를 줘도 15건이 온다

── 같은 교육생 대조군 ──
상세        2822ms    6601B
채점 근거   1546~2088ms
```

**`size`를 5로 줘도 응답이 바이트까지 같다**(14512B). 커서 페이징이라 적혀 있는데
페이지 크기가 안 걸린다 — 그래서 화면이 조절할 수단이 없다.

이벤트 15건에 13초면 **행 수 때문이 아니다.** 같은 교육생의 상세가 2.8초이므로
교육생 조회 자체가 느린 것도 아니다. → §5

> MG-05 명부(7초)와 함께 **매니저 화면에서 가장 느린 둘**이다.

### 4-2. ✅ 조회를 나눈 설계가 실제로 값을 한다

```
[201ms]    격자=있음  이력=없음(스피너)
[12000ms]  격자=있음  이력=있음
본문 높이 790 고정
```

**격자가 200ms에 먼저 그려진다.** 둘을 하나의 로딩으로 묶었으면 화면 전체가 12초
비었을 것이다(async-states §2-1). 레이아웃 시프트도 없다.

### 4-3. ⓘ `published=true`인데 `note`가 0건 — **미응시라 정상이다**

```
5차   reportPublished: true   resultStatus: NOT_ATTENDED   steps=[] · note 0건
4차   reportPublished: true   resultStatus: AVAILABLE      L3에 note 있음
```

「발행됐는데 근거가 없다」로 적을 뻔했다. **응시를 안 한 회차**라 채점할 단계 자체가
없고(`steps: []`), 그래서 근거도 없다. 화면은 그 회차를 **격자에서 이미 제외**한다
(`attended = !!attemptId`) — 펼칠 일이 없다.

> 화면의 「발행 전에는 근거가 없다」 안내는 `reportPublished=false`일 때만 뜬다.
> 이 경우와 안 겹친다.

### 4-4. ✅ 채점 근거가 축별로 정확히 붙는다

개념 이름으로 맞추는 방식이 실제로 맞는지 전수로 확인했다.

```
4차   타임라인 ["JPA 엔티티 관계 설정","계층 분리와 의존성 방향","예외 처리와 롤백 전략"]
      채점     ["JPA 엔티티 관계 설정","계층 분리와 의존성 방향","예외 처리와 롤백 전략"]  전부 맞음
5차   〃 전부 맞음
```

렌더도 맞다.

```
2단  JPA 엔티티 관계 설정   자력
     L3  트랜잭션 경계 설정에서 선택 이유까지 설명했지만, 어떤 상황에서
         이 방식이 깨지는지는 답하지 못했습니다.
1단  예외 처리와 롤백 전략   자력
     L2  무엇을 하는지까지는 설명했지만, 왜 그 구조를 선택했는지에서 막혔습니다.
```

### 4-5. ✅ 이벤트 필터 5종이 정확하다

```
전체 15건 = 이해도 확인 5 + 다시 보기 4 + 리포트 4 + 면담 2
aria-pressed 반영 · 전체로 복귀됨
```

「다시 보기 4건」이 `REVIEW`·`REVIEW_CLOSED` 둘을 한 칸에 담은 결과다(설계대로).

## 하드닝 2차 — 조합 전수 320/320 (2026-08-17)

### 컨트롤을 셌다

```
필터 칩 5 × 회차 접힘 2⁶ = 320        ← 회차 수는 사람마다 다르다(임윤슬 5 · 백하은 6)
「자세히」 5                            ← 답한 문항이 있는 이해도 확인 행에만 붙는다
```

**요청이 하나도 안 나가는 화면 안 계산이라** 320을 다 도는 데 25초면 된다. MG-05처럼
API로 미리 거를 수 없는 대신(서버가 관여하지 않으므로) 화면에서 곱해 도는 값이 싸다.

### 320 조합 — 문제 0 · 요청 0

조합마다 넷을 봤다.

```
① 보인 이벤트 수 = 펼친 회차들의 이벤트 수 합
② 필터 밖 종류가 새지 않는가
③ 헤더 「N건」이 접힘에 흔들리지 않는가      ← 접어도 전체 건수는 그대로여야 한다
④ 접힌 회차에 이벤트가 DOM에 남지 않는가
```

부분합도 맞다 — **백하은(이벤트 18건)**으로 재 보면

```
이해도 확인 6 + 다시 보기 4 + 리포트 6 + 면담 2 = 18 = 전체
```

유형이 빠짐없이 갈린다(어느 이벤트도 두 번 세거나 빠지지 않는다).

### 오판 하나 — 라벨이 겹쳤다

첫 스윕이 **「리포트 필터인데 다시 보기가 샌다」를 62건** 뱉었다. 리포트 행 문구가
이렇다.

```
리포트 발행 · 다시 보기 3건 지정
              ~~~~~~~~~
```

내 판정기가 **먼저 만난 것으로 종류를 정해서** 리포트를 REVIEW로 읽은 것이다. 화면은
멀쩡했다. `screen-hardening.md` §「버튼 이름이 겹치면 어느 것을 눌렀는지 남긴다」와 같은
종류 — **겹치면 가장 구체적인 것부터** 봐야 한다(`리포트 발행`을 먼저 검사).

## 고친 것 (하드닝 2차)

### 1. 🔴 필터에 걸린 것이 없으면 회차 껍데기만 남았다

면담이 없는 교육생에게 `면담` 칩을 누르면 이렇게 됐다.

```
전   이력  면담 0건   [전체][이해도 확인][다시 보기][리포트][면담]
     6차 · 5팀 · 08.16 – 08.16
     5차 · 5팀 · 07.31 – 08.01  미응시
     … 회차 줄 6개, 그 아래 전부 빈 칸
```

「면담 0건」이라는 **작은 회색 글씨 하나**가 유일한 설명이라 고장으로 읽힌다. 아무것도
안 들어 있는 회차 줄은 정보가 아니므로, 그 자리에 이유를 적는다.

```
후   면담 기록이 없어요
     이 교육생에게는 아직 없습니다. 위에서 **전체**를 누르면 다른 기록을 볼 수 있어요.
```

되돌리는 버튼은 두지 않는다 — 칩이 바로 위에 있고 어느 것이 눌렸는지 보인다(규칙 F).

### 2. 스피너 둘 → 스켈레톤 둘

`머리 34 + mb 16 · 격자 183.6 + mb 16 · 이력 머리 30 · 회차 줄 38.6 · 이벤트 줄 47`을
재서 박았다. 공용으로 올리지 않는다 — 쓰는 곳이 여기뿐이다(D14).

### 3. 이력 스켈레톤의 회차 수를 **상세에서 받는다**

두 조회는 따로 온다(실측 격자 5.6초 → 이력 9.1초). 그 사이에는 **회차 수를 이미 안다.**
6으로 박아 뒀더니 회차가 5인 교육생에서 34px 어긋났다 — `detail.data.rounds.length`를
넘긴다. 백하은(6회차)에서 스켈레톤 6줄 = 실제 6줄로 확인했다.

## 실측 (하드닝 2차)

```
상세                1.49 / 1.30초      ← 1차 대비 크게 줄었다
타임라인 size=100   4.70 / 5.11초      ← 1차 13~17초
```

### 🔴 1차의 「`size`가 무시된다」는 틀렸다 — **스펙에 이미 적혀 있었다**

```
size=1     회차 1 · 이벤트 3    hasNext=true
size=5     회차 5 · 이벤트 15   hasNext=true
size=20    회차 6 · 이벤트 18   hasNext=false
size=100   회차 6 · 이벤트 18   hasNext=false
```

1차에는 **이벤트가 18건뿐이라 20과 100이 같은 결과**였고, 그것을 「무시된다」로 읽었다.
1까지 내려 보고서야 갈렸다 — `hasNext`도 정확히 온다.

**그런데 실측이 필요하지도 않았다.** 스펙이 이미 이렇게 적고 있다.

```
| size | 선택 | int | **회차** 수(이벤트 수가 아니다). 기본 20, 최대 100 |
⚠️ **`size`는 회차 수다.** 회차 중간이 잘리면 화면이 그 회차를 반쪽만 그리므로
```

즉 1차의 「무시된다」는 관측 실패가 아니라 **스펙을 안 읽은 것**이고, 2차에 「실측으로
확정」이라고 쓴 것도 틀렸다 — 확정할 것이 없었다. `screen-hardening.md` §「스펙이
사실인지 확인한다」는 스펙을 의심하라는 말이지 **안 읽어도 된다는 말이 아니다.**

화면은 `size: 100`을 보내는데 기수 회차가 6이라 늘 전량이다(맞는 선택).

### 🔴 없는 교육생 id — 404 분기가 한 번도 안 걸린다

```
0초 ──────────────── 75초 ────────────
스켈레톤 그대로       「교육생 정보를 불러오지 못했습니다」
```

화면은 404 `MANAGER_SCOPE_NOT_FOUND`를 받으면 「담당하는 반의 교육생만 볼 수 있습니다」로
가르도록 **이미 되어 있는데**, 응답 자체가 안 와서 그 길로 못 간다. 29차 R1 → 30차 R1 →
32차 R12 → 33차 R1로 이어지는 **프록시의 404 처리**와 같은 뿌리라 새 요청이 아니라
사례로만 34차 §11에 붙였다.

**담당 밖의 실재하는 교육생으로는 못 재 봤다** — 매니저 토큰으로는 담당 반 밖 교육생의
id를 얻을 방법이 없다(그게 스코프의 목적이다).
