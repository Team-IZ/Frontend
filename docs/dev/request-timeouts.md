# 응답이 안 올 때 — 요청 예산과 흰 화면

> **이 백엔드는 「없는 것」을 물으면 404가 아니라 무응답이고, 잠들어 있으면 전 경로가
> 침묵한다.** 그동안 화면이 무엇을 해야 하는지가 여기 있다 — 얼마나 기다리고, 언제
> 끊고, 무엇을 그리고, 재시도를 주는지.
>
> **같은 일이 또 생기면 7절부터 본다.**
>
> 버그 제보 하나("로그인 화면이 오래 흰색이다")로 시작해 통신 계층까지 간 기록이라
> 진단 과정을 그대로 남겼다 — 원인이 세 겹이었고 세 층을 다 고쳤다(2026-08-14~15).
>
> 4절의 기능 인벤토리는 이 주제와 별개다(발표용으로 뽑은 것) — 옮길 곳이 정해지면
> 그때 뺀다.

## 1. 진단 — 흰 화면의 정체

### 추적 경로

```
/shared/login 진입
  → useSession() → GET /api/v0/members/me
  → 응답이 오지 않음
  → isPending 이 영원히 참
  → LoginScreen: if (sessionLoading) return null    ← 이것이 흰 화면이다
```

`return null`은 **의도된 코드**였다. 주석이 이유를 적어 뒀다 — *"로그인 폼을 먼저
보여주면 쿠키가 살아 있는 사용자에게 화면이 깜빡였다가 사라진다."*

**의도는 맞지만 대가를 안 봤다.** 깜빡임을 막으려고 **완전한 백지**를 택했고, 그 백지에
상한이 없었다.

### 왜 끝나지 않나 — 타임아웃이 0개였다

- `fetch`는 **기본 타임아웃이 없다.** 브라우저는 서버가 답할 때까지 안 끊는다
- React Query의 `retry`는 **실패한 뒤** 도는 것이라 **응답이 없으면 실행되지 않는다**
- `src/api/_contract` 전체에 `AbortSignal.timeout` 사용처 **0건**

### 측정 — 서버가 잠들어 있었다

```
GET  /api/v0/members/me       60초 ×3   응답 없음 (status 000 · TTFB 0)
GET  /v3/api-docs             20초      응답 없음
GET  /                        20초      응답 없음
POST /api/v0/auth/login  {}   20초      응답 없음   ← 형식 오류라 즉답 가능한 요청
POST /api/v0/auth/refresh     20초      응답 없음

── 끊지 않고 150초까지 기다림 ──
GET  /v3/api-docs             200 · 13.5초          ← 깨어났다
```

**TCP는 0.05초에 붙는다.** 네트워크가 아니라 애플리케이션이 응답을 시작하지 못한
상태였고, **죽은 것도 아니었다** — 충분히 기다리니 200이 왔다.

> 스웨거 문서까지 안 온다는 것이 판정 근거였다. 우리 코드가 부르는 경로가 아니므로
> **앱 문제일 수 없다.**

### 같은 버그가 한 곳 더 있었다

`RequireRole`도 `if (isLoading) return null`이었다 — **보호 화면 전부가 같은 흰 화면**이다.
제보는 로그인 화면 하나였지만 고칠 자리는 둘이었다.

## 2. 수정 — 7파일

| 파일 | 무엇 |
|---|---|
| `_contract/client.ts` | **요청 예산 90초** · 업로드(multipart)만 180초. 401 재발급 재시도 경로에도 같이 걸린다 |
| `_contract/errors.ts` | `TIMEOUT` 코드 신설 + `isTimeout`. `TimeoutError`와 `AbortError`를 갈라, **화면 이동으로 취소된 요청**이 실패로 뜨지 않게 한다 |
| `main.tsx` | **예산 초과는 재시도하지 않는다** |
| `lib/errorCopy.ts` | 예산 초과 문구를 오프라인과 분리 |
| `check-error-copy.mts` | 위 판정을 CI가 지킨다 |
| `LoginScreen.tsx` | `null` → 로딩 표시 |
| `RequireRole.tsx` | 같은 것 (보호 화면 전체) |

### 값을 10초에서 90초로 뒤집었다 — 이 세션에서 가장 중요한 판단

처음엔 **10초**를 제안했다. 근거는 정상 응답 실측 1.9초였고, 5배 여유면 충분해 보였다.

그런데 `components/common/Loading.tsx`에 **이미 결정이 박혀 있었다.**

> *"**끊지 않는 이유** — 서버가 잠들어 있으면 깨어나는 데 **최대 76초**가 걸린다
> (App Runner). 30초에 끊으면 정상적으로 깨어나는 중인 요청을 죽인다."*

**10초는 콜드스타트를 통째로 못 넘긴다.** 그 값으로 갔으면 아침 첫 접속자는 영원히
로그인할 수 없고, 증상만 "흰 화면"에서 "즉시 실패"로 바뀌었을 것이다.

그래서 목적을 다시 세웠다 — **대기를 짧게 만드는 것이 아니라 끝나기는 하게 만드는 것.**
그날 실측(150초를 기다리니 13.5초에 200)이 그 76초를 뒷받침했다.

> 남의 코드에 적힌 "왜 안 했나"를 안 읽었으면 **멀쩡한 결정을 되돌릴 뻔했다.**

### 왜 예산 초과는 재시도하지 않나

기존 정책은 `status: 0`(네트워크 실패)을 **3회** 재시도한다 — 오프라인은 즉시 실패라
3회가 4초로 끝나기 때문이다.

**예산 초과도 `status: 0`이다.** 같은 규칙을 쓰면 90초 × 4 = **6분**을 기다린다.
상태가 같다고 같은 정책을 쓰면 안 되는 자리였다.

### 왜 문구를 갈랐나

예산 초과에 *"인터넷 연결을 확인해 주세요"* 가 나가면 **사용자가 멀쩡한 자기 와이파이를
고치러 간다.** 연결은 됐고 안 답한 것은 서버다.

```ts
assert.doesNotMatch(timeout.description, /인터넷/)  // 가드가 막는다
```

### 업로드만 180초인 이유

파일은 서버가 받아서 파싱까지 한다. 조회와 같은 예산이면 **멀쩡한 업로드가 죽는다.**
`FormData`를 본문으로 주면 `Request`가 `multipart/…`를 직접 붙이므로, 호출부가
따로 알려줄 필요 없이 **본문이 파일이면 예산이 저절로 길어진다.**

## 3. 27차 요청서

`docs/dev/backend/backend-api-requests-27.md`

| | 무엇 |
|---|---|
| **R1** 🚨 | 잠든 인스턴스가 **전 경로에 침묵**한다 — 죽은 것과 구분되지 않는다 |
| **R2** 🔴 | **`503` + `Retry-After` 하나면** 화면이 추측을 멈춘다 |
| **R3** 🟠 | 비로그인 첫 진입이 왕복 2회(`/me` 401 → `refresh` 401)라 콜드스타트를 두 번 기다린다 |
| **R4** 🟡 | 확인 — 배포 중에도 기존 인스턴스가 응답하나 |

**같은 증상의 다섯 번째**다(18차 R1·R7 · 21차 · 25차 R4 · 27차 R1). 앞의 넷은 "특정
상황에서 상태코드 대신 침묵"이었고 이번은 **"특정 시간대에 전부 침묵"** 이다 — 원인은
달라도 화면에서 보이는 모습은 같다.

R2가 오면 로딩 문구에서 **「~일 수 있습니다」의 추측을 뗄 수 있다**는 것을 요청 근거로 썼다.

## 4. 곁들여 — 프로젝트 기능 인벤토리

발표·포트폴리오용으로 전체 기능을 뽑아 **세 층**으로 갈랐다.

```
① 겉으로 보이는 기능        검증 세션 · 히트맵 · 면담 브리프 · 재응시 파이프라인 …
② 그것을 구현하기 위한 기능   코드 생성 파이프라인 · 토큰 재발급 · 에러 문구 단일 원천 …
③ 구현의 프로세스           백엔드 요청서 27차 · CI 재현 · mock-first
```

③은 **기능이 아니라 일하는 방식**이라 기능 목록에서 뺐다.

### 압축본 (10줄)

1. 회원가입·로그인·초대 기반 계정 활성화 & 약관·개인정보 동의(대상별 필수/선택 차등)
2. JWT 인증 — 액세스 토큰 메모리 · 리프레시 httpOnly 쿠키 · 401 자동 재발급·재시도
3. 역할 기반 접근 제어(4종) 라우트 가드 & 시큐어코딩 대응(마스킹·권한 통제·업로드 검증)
4. **OpenAPI 코드 생성 파이프라인 자체 제작**(pull → check → gen) + 스펙 품질 검사기
5. **CI 가드 13종 & Git 훅 4종** — 생성물·문서 드리프트, WCAG 대비 자동 계산, `.env` 차단
6. 검증 세션 — 4단계 계단형 문답 · 힌트 지급 · 이중 타이머 · 창 이탈·오프라인 대응
7. 히트맵 3단 드릴다운 · 집단 미달 자동 판정 · 리포트 발행/인쇄/CSV · 사용량·비용 집계
8. CSV 명단 일괄 등록·드라이런 검증·초대 발송(행별 부분 성공) & 파일 업로드
9. 서버 상태 관리(TanStack Query) & 비동기 상태 표준화(스켈레톤·빈 상태 3종·문구 단일 매핑)
10. 디자인 시스템(토큰 + 공용 컴포넌트 33종) · WCAG 2.1 AA · Vercel 배포

## 5. 검증 — 배포 후 실제로 돌렸다

### 백엔드 (깨어 있을 때)

```
/members/me    401 · 0.50s / 0.52s / 0.73s
/auth/refresh  403 · 0.72s
/auth/login {} 400 · 0.85s
/cohorts/{없는 id}  401 · 0.70s
```

**서버가 느린 것이 아니다.** 깨어 있으면 1초 안에 온다 — 문제는 잠든 동안의 침묵이고,
그 구간이 사용자에게 그대로 노출된다(아침 첫 접속·시연 직전).

### 화면

| 단계 | 결과 |
|---|---|
| `/shared/login` 진입 직후 | 접근성 트리에 `status "로그인 상태를 확인하는 중"` — **흰 화면이 사라졌다** |
| ~2.5초 | 로그인 폼 정상 |
| 오퍼레이터 로그인 | `/operator/dashboard` 이동 · 헤더 `김도현` · `기수 9기` |
| 대시보드 | 스켈레톤 → 실데이터(198명·9반 · 미니프로젝트 6개 · 반 비교 기준선) |

콘솔 에러 2건은 **비로그인 상태의 `/me` 401 → `refresh` 401**이라 설계대로다.

### 정적 검사

`typecheck` · `lint` · `check:error-copy` · `check:async` · `check:design` · `format` 전부 통과.

## 6. 남은 것

- **90초 예산이 실제로 끊는 장면은 못 봤다.** 서버가 건강해 재현할 상황이 없다 —
  콜드스타트를 다시 만나면 그때 확인한다
- 27차 R2가 반영되면 **로딩 문구에서 추측을 뺀다**
- 이 세션 변경분은 **아직 커밋하지 않았다**

## 7. 다음에 같은 일이 생기면

1. **화면 코드부터 의심하지 말고 왕복을 재라.** `curl`로 `total`·`ttfb`를 찍으면
   "느리다"와 "안 온다"가 한 번에 갈린다 — `status=000`에 `ttfb=0`이면 응답이 없는 것이다
2. **우리 코드가 안 부르는 경로**(스웨거 문서·루트)를 같이 재라. 그게 안 오면 앱 문제가 아니다
3. **끊기 전에 충분히 기다려 봐라.** 20초에 끊었을 때는 "죽었다"였고 150초를 기다리니
   "깨어나는 중"이었다 — 두 판정은 요청서 내용이 완전히 달라진다
4. **고치기 전에 "왜 안 했나"가 적혀 있는지 찾아라.** 이번엔 `Loading.tsx` 주석 한 문단이
   타임아웃 값을 9배 바꿨다
