# MG-05 교육생 명부 — 상황 전수

> **절차는 [screen-hardening.md](../screen-hardening.md).**
>
> 공통 축(헤더·스코프·기수 이름·빵부스러기)은
> [mg-03-situations.md](mg-03-situations.md)에서 한 번 쟀다 — 여기서 다시 재지 않고
> **이 화면 고유의 것**만 본다.
>
> **쓰기가 없는 첫 화면이다.** 대신 **페이지네이션과 필터 조합**이 있어 축이 가장 넓고,
> 그 조합에서만 나는 사고(2쪽에서 검색, 필터 바꿔도 쪽 유지 등)가 여기 있다.

---

## 1. 조회 흐름

```
useManagerCohort()      GET /members/me/enrollments    ─┐ cohortId가 정해져야
                                                        │ 아래 둘이 시작한다
useRoster()             GET /cohorts/{id}/trainees     ─┤ 병렬
useManagedClassrooms()  GET /cohorts/{id}/classrooms   ─┘

MG-03과 달리 회차를 먼저 안 받는다 — `assessmentRoundId`를 **생략하면 서버가
「이번 회차」를 골라** 응답으로 알려주고, 회차 드롭다운도 그 응답의 `rounds[]`가 채운다.
그래서 **왕복이 하나 적다**(32차 R2로 면담에도 같은 규칙을 요청했다).
```

**검색·필터·정렬·페이지를 전부 서버가 한다.** 화면은 조건을 만들어 보내기만 한다 —
페이지네이션이 붙은 순간 화면 정렬은 「이 쪽 안에서만 맞는 정렬」이 되기 때문이다.

`listQueryOptions`(=`keepPreviousData`)를 쓴다 — 조건이 바뀌어도 표가 사라지지 않고,
옛 값을 그리는 동안 `staleProps`로 그 사실을 숨기지 않는다.

## 2. 축

```
A. 스코프
  A1 담당 기수 1개    A2 여러 개    A3 0개    A4 조회 실패

B. 회차 (rounds[])
  B1 여럿 · 서버가 「이번 회차」를 고름     B2 회차 0개
  B3 고른 회차에 지표 없음(전원 미응시)     B4 회차마다 문항 수가 다름

C. 목록
  C1 여러 쪽(26명 · 20/쪽)   C2 한 쪽    C3 0건(필터)    C4 0건(모집단)
  C5 조회 실패               C6 옛 값 유지 중(isPlaceholderData)

D. 행의 값
  D1 도달 3칸 정상            D2 `reachLevel: null`(문항 없음/무응답)
  D3 `conceptResultItems: []`  D4 파싱 불가 문자열
  D5 `lowStageConceptCount: null` → `—`
  D6 분모가 사람마다 다름(2·3·0)  D7 우수 누적 배열
  D8 배지 8종 · 모르는 코드    D9 `className: null`(반 미배정)
  D10 `INACTIVE` + 사유·시각   D11 `INVITED`(초대 대기)

E. 조작
  E1 회차 변경      E2 검색(한글 조합)   E3 반 필터   E4 계정 필터
  E5 정렬 4종       E6 페이지 이동       E7 조건 바꾼 뒤 쪽 유지 여부
  E8 행 클릭 → 상세  E9 이름 링크(키보드)

F. 값의 빈 구석
  F1 `terminalAt: null`인데 배지가 NOT_ATTENDED
  F2 `inactivatedReason: null`인데 INACTIVE
  F3 이름·이메일이 아주 길 때
```

**조합 수** — 4 × 4 × 6 × 11 × 9 × 3 = **28,512**. 2단계에서 갈리는 지점만 추린다.

## 4. 실측 · 판정 · 고침

### 4-1. 🔴 명부 조회가 **7초**다 — 같은 매니저의 다른 조회보다 5배

```
size=20 · 회차 생략        7774ms   29450B   rows=20
size=1  · 회차 생략        7865ms    2922B   rows=1     ← 크기와 무관
size=20 · 회차 지정(6차)   6862ms   29450B
size=1  · 회차 지정(6차)   7154ms    2922B
size=20 · 회차 지정(3차)   7339ms   31353B
검색으로 1건               2621ms    2921B   rows=1     ← 여기만 빠르다

── 대조군 (같은 매니저 · 같은 시각) ──
면담 목록                  1449ms
반 목록                    1516ms
내 소속                    1149ms
```

**변수를 바꿔도 안 줄어든다.**

| 바꾼 것 | 결과 |
|---|---|
| `size` 20 → 1 (응답 29KB → 2.9KB) | **7.8초 그대로** — 크기도 직렬화도 아니다 |
| 회차 생략 → 지정 | 그대로 — 「이번 회차 고르기」가 원인이 아니다 |
| 회차 3차 ↔ 6차 | 그대로 |
| **`query=노주안`(1건으로 좁힘)** | **2.6초** — 여기서만 5초가 빠진다 |

`size=1`은 안 줄고 **검색은 주는 것**이 갈림길이다. `size`는 *자르는* 것이라 집계는
26명분을 다 돌고, 검색은 *모집단을 줄이는* 것이라 그만큼 준다 — **행마다 도는 계산이
있다**는 뜻으로 읽힌다(회차 지표·우수 누적·위험 판정이 행당 붙는다).

브라우저 실측도 같다 — 사이드바 클릭 후 **11초에 첫 행**(MG-03은 6초).

**화면이 줄일 수 없다.** 페이지 크기를 줄여도 그대로고, 지표를 빼고 부를 방법이 없다.
→ §5

### 4-2. ⓘ `RECENT_ENROLLED`가 `NAME`과 결과가 같다 — **시드 탓이다**

```
NAME             노주안 · 문유진 · 백서준 · 백은우 · 백하은
RECENT_ENROLLED  노주안 · 문유진 · 백서준 · 백은우 · 백하은   ← 같다
RISK             노주안 · 백하은 · 이준서 · 정가온 · 문유진
EXCELLENCE       유시우 · 윤다인 · 유예서 · 노주안 · 손지안
```

「정렬이 안 먹는다」로 적을 뻔했다. **담당 반 26명의 `joinedAt`이 전부
`2026-03-01T15:00:00Z`로 같다**(실측) — 동점이라 2차 기준(이름)으로 떨어진 것이고
서버가 맞다. 나머지 둘은 확실히 다르게 온다.

> 하드닝 §「안 맞는다고 쓰기 전에 부분합으로 한 번 더 센다」와 같은 종류다.

### 4-3. ✅ 페이지네이션·조건 변경이 정상이다

| 조작 | 결과 |
|---|---|
| 1쪽 → 2쪽 | `26명 중 21–26` · 6행. **푸터가 앞서지 않는다** |
| **2쪽에서 검색** | `1명 중 1–1` · 페이저 1쪽만. **없는 3쪽을 조회하지 않는다**(조건이 바뀌면 `page: 0`) |
| 검색 지우기 | `26명 중 1–20`으로 복귀 |

### 4-4. ⓘ 빵부스러기가 **두 단계로 채워진다**

```
[101ms]    교육생 › 담당 반          ← 기수 자리가 아직 없다
[2000ms]   교육생 › 9기 › 담당 반
```

MG-03에서 고친 `filter(Boolean).join(' › ')` 덕에 **`› ›`(빈 구분자)는 안 난다.**
대신 조각이 중간에 끼어들며 가로로 밀린다 — 헤더 한 줄 안이라 CLS에는 안 잡히고,
「없는 것을 그리지 않는다」는 규칙과도 맞아 **그대로 둔다.**

## 하드닝 2차 — 조합 전수 192/192 (2026-08-17)

1차는 축을 하나씩만 훑었다. 이번엔 **네 축을 곱한 전 조합**을 API와 화면 양쪽으로 돌았다.

### 컨트롤을 세는 데 두 번 틀렸다

```
회차 6 × 반 2 × 계정 4 × 정렬 4 = 192      ← 맞게 센 값
```

**① 포트를 틀렸다.** 이 워크트리는 `5175`인데 `5173`(다른 체크아웃)을 열고 정렬 선택지를
읽었다. `이름·반·우수 누적·2단 이하`가 나왔고 소스에는 그런 항목이 없어 「라우트가 다른
화면을 가리킨다」로 갈 뻔했다. `ps`로 vite가 어느 디렉터리에서 도는지 보고 잡았다.

> 여러 세션이 같은 레포를 나눠 쓰면 **포트가 곧 워크트리**다. 화면이 소스와 다르면
> 먼저 포트를 의심한다.

**② `:visible`이 통하지 않는다.** 하드닝 문서가 「선택지는 열어서 DOM에서 읽는다
(`:visible` 필수)」라고 하는데, **base-ui Select는 닫힌 팝오버를 그대로 둔다** —
`data-closed`만 붙고 `offsetParent`는 살아 있다.

```
[data-slot="select-content"]  open=null closed=""  offsetParent=true  ← 닫혔는데 "보인다"
```

그래서 축을 이어 세면 앞 축이 누적돼 `6 · 8 · 12 · 16`(합 9216)이 나온다. 실제 손잡이는
**`[data-open]`**이다. 덤으로 `document.body.click()`은 팝오버를 **안 닫는다** —
base-ui는 `pointerdown`을 본다(트리거 재클릭 · Escape · 옵션 클릭 · 바깥 `pointerdown`은
넷 다 닫힌다. 실측).

### API 192 — 검산 9종 전부 통과

계정/반 필터 밖 행 · 내역 합 = `cohortTotal` · `totalPages` = `ceil(total/20)` ·
행 ≤ `size` · 1쪽이면 행 = total · 보낸 회차로 답하는가 · 이름 정렬 · `2단 미만` 분자 ≤ 분모 ·
`conceptResultItems` 파싱. **실패 0.**

### 화면 192 — 조합당 요청 1건

`요청 1건 × 144 · 2건 × 36 · 3건 × 6 · 4건 × 5` (여러 축을 한 번에 바꾼 조합이 2건 이상).
**중복 조회가 없다.**

### 4. 🔴 결과가 0건일 때 조건을 바꾸면 로딩 표시가 없었다

`StaleBlock`을 표 갈래에만 걸었더니, 0건인 조건에서 다른 조건으로 바꿀 때 **6.6초 동안
「조건에 맞는 교육생이 없습니다」가 그대로** 있었다(조회를 3초 늦춰 재현).

```
전   0.1초 빈 상태 … 6.6초 빈 상태 → 갑자기 3행
후   0.2초 덮개 ✅ … 6.9초 → 5행
```

0건도 **옛 조건의 결과**다. 규칙 E가 "표를 비우지 말라"고 하는 것과 같은 이유로 여기도
덮어야 한다. 이 버그는 **스윕이 0행 조합을 지날 때마다 즉시 「도착」으로 읽히면서** 드러났다
— 측정이 안 맞아서 코드를 다시 본 것이 잡은 경로다.

### 5. 🔴 푸터가 실재하지 않는 범위를 5초 보여줬다

1쪽 → 2쪽을 누르면 그 사이에 **`26명 중 21–40`**이 떴다. 화면이 든 `page`는 벌써 1인데
`rows`는 아직 옛 20행이라 `1×20+1 – 1×20+20`을 센 값이다. 26명짜리 목록에 40번은 없다.

**행과 같은 응답에서 세면 그 틈이 없다** — 서버가 `page`를 주므로 `RosterView.page`로
옮겼다. 덮개 안이라 흐리게 보이긴 했지만, 없는 숫자는 흐려도 없는 숫자다.

```
후   26명 중 1–20 · 20행(덮개)  →  26명 중 21–26 · 6행
```

## 실측 (하드닝 2차)

```
명부 1쪽(20행)    5.3 / 5.7초      ← 1차 7.8초 · 34차 R6 재측정 6.36초
명부 2쪽(6행)     3.4 / 3.5초
검색 1건          2.1 / 2.1초
반 목록           1.5 / 1.5초

→ 고정 2.5초 + 행당 약 145ms
```

### ⚠ 한글은 **아직 제대로 안 쟀다** — 내가 틀린 방법으로 쟀다

처음에 「자모 7타 → 요청 1건」이라고 적었는데 **거짓이다.** `pressSequentially('이준서')`는
**완성된 음절 셋**을 넣지 조합 버퍼를 안 거친다 — `screen-hardening.md` §「한글 입력은
조합 중을 따로 본다」가 정확히 이것을 경고한다.

```
✗ 내가 한 것    pressSequentially('이준서')       완성 음절 3타
○ 해야 할 것    Input.imeSetComposition          ㅇ→이→잊→이ㅈ→이주→…  조합 9타
```

디바운스가 요청 수를 줄이는 것은 확인됐지만(요청 1건), **조합 중 리렌더로 자모가 확정
문자로 남는지**(`ㅇㅣㅈㅜㄴㅅㅓ이준서`)는 못 봤다. 그 둘은 다른 것이다 — 문서가
「검색 버튼을 다는 것으로는 안 고쳐진다. 조합 깨짐은 요청이 아니라 리렌더 때문이다」라고
적어 둔 그대로다.

**규칙 K 미검증으로 남긴다.** 코드상으로는 `useDebounced`가 입력값과 조회값을 갈라 두어
안전해 보이지만, **「안전해 보인다」는 측정이 아니다.**
