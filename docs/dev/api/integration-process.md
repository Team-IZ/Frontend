# 목으로 만든 화면을 실서버에 붙이는 법 — 작업 절차

> **이 문서의 목적:** 교육생 3화면(TR-01·02·04)을 실서버에 붙이면서 **실제로 밟은 순서와
> 내린 판단**을 남긴다. 다음 도메인(매니저·오퍼레이터)이 같은 길을 다시 찾지 않도록.
>
> [api-usage.md](api-usage.md)가 *"API를 어떻게 쓰나"*, [api-process.md](api-process.md)가
> *"생성기가 어떻게 도나"* 라면, 이 문서는 **"목을 어떻게 걷어내나"** 다.
>
> **원칙 하나로 줄이면 이것이다 — 서버가 판정하고, 화면은 그 코드를 문장으로 옮긴다.**
> 화면이 다시 판단하기 시작하면 같은 규칙이 두 곳에 생기고, 규칙이 바뀔 때 반드시
> 한쪽만 바뀐다.

---

## 0. 전체 그림

```
① 스펙 받기        api:pull → api:check → api:gen
② 화면 읽기        목이 무엇을 가정했나
③ 대조표 만들기    목 계약  vs  서버 응답
④ 어댑터 쓰기      _/api/{api.ts, types.ts}
⑤ 목 걷어내기      mockDb·types·api·?state= 삭제
⑥ 실계정 확인      브라우저로 하나씩 눌러본다
⑦ 어긋난 것 정리   요청서 → 회신 → 재확인
```

**③이 이 작업의 전부다.** 코드를 쓰는 시간보다 *"목이 지어낸 것과 서버가 실제로 주는 것이
어디서 갈리나"* 를 가리는 시간이 훨씬 길다. 거기를 대충 넘기면 ④~⑥에서 세 배로 돌아온다.

---

## 1. 스펙 받기

```bash
npm run api:pull     # 배포된 스웨거를 받아 api/openapi.json에 쓴다
npm run api:check    # 생성해도 되는 품질인가 (error면 종료코드 1 → CI가 막는다)
npm run api:gen      # src/api/** 를 통째로 다시 만든다
npm run typecheck    # ⚠️ npx tsc --noEmit 아니다 (§6 함정 참고)
```

### `api:check`가 error를 내면 멈춘다

**error는 "이 상태로 생성하면 타입이 거짓말을 한다"는 뜻**이라 그냥 넘기면 안 된다.
다만 **백엔드 문제인지 우리 검사기 오탐인지 먼저 가른다.**

실제로 이 작업에서 나온 것 둘:

| 잡힌 것 | 진단 |
|---|---|
| `SubmissionContent`에 `required` 없음 | ✅ 진짜 — 백엔드가 `oneOf`로 갈라 해결 |
| `TraineeTimelineEvent.type`이 null이 아닌데 설명에 null | ❌ **오탐** — 설명문이 *옆 필드*를 가리켰다 |

**오탐이면 검사기를 고친다.** 백엔드에 "설명문을 고쳐 달라"고 하면 정확한 문서를
검사기에 맞춰 왜곡시키는 것이다. 같은 유형이 두 번 나오면 그건 검사기가 부족하다는
신호다(실제로 그랬다 → `scripts/api-check.mjs`의 `REFERS_SIBLINGS`).

### 스펙이 바뀌면 컴파일이 깨지는 것이 정상이다

`uploads.ts`처럼 **손으로 쓰는 계약**은 응답 타입을 스펙에서 직접 뽑는다.

```ts
type SubmitZipResponse = operations['submitZip']['responses'][202]['content']['application/json']
```

실제로 백엔드가 성공 코드를 `200 → 202`, `201 → 202`로 정정했을 때 **여기서 컴파일이
깨져서 알았다.** 이게 목적이다 — 스펙과 어긋난 채로 굳지 않는다.

---

## 2. 화면 읽기 — 목이 무엇을 가정했나

**코드부터 읽는다.** 목업 HTML이나 기획 문서는 낡았을 수 있다.

읽어야 할 것:

```
{screen}/types.ts      목이 정의한 계약 — 여기가 대조의 왼쪽
{screen}/api.ts        목 호출부 (지울 것)
{screen}/mockDb.ts     목 데이터 (지울 것)
{screen}/labels.ts     서버 코드 → 문장 표 (대부분 살아남는다)
{screen}/*Screen.tsx   상태별 분기 — 몇 종인지 센다
```

**`labels.ts`는 대체로 살아남는다.** 거기 있는 것은 *"이 코드를 사람 말로 어떻게
옮기나"* 라 서버가 바뀌어도 유효하다. 반대로 `types.ts`는 대부분 갈아엎게 된다.

## 3. 대조표 만들기 — **여기가 핵심이다**

목 계약과 서버 응답을 나란히 놓고 **한 필드씩** 본다. 세 부류로 갈린다.

### ① 이름까지 같다 — 그대로 산다

TR-02 상태 6종(`DRAFT`·`ANALYZING`·`READY`·`LOCKED`·`ANALYSIS_FAILED`·`SUBMISSION_CLOSED`)이
글자까지 같이 왔다. 우리가 요청서로 그 이름을 제안했기 때문이다.

> **목을 만들 때 지은 이름을 요청서에 그대로 쓰면** 이런 일이 생긴다. 화면 분기가
> 통째로 산다.

### ② 서버 모양이 더 낫다 — 서버를 따른다

TR-01은 목이 상태를 8종 union으로 좁혀 뒀는데, 서버는 평평한 `current` +
`representativeStatus` + `warningCodes[]`를 준다.

**서버 쪽이 표현력이 넓다.** 배열이라 *"마감도 지났고 분석도 실패했다"* 를 동시에 말할
수 있는데, union이던 시절엔 둘 중 하나를 골라야 했다.

### ③ 목이 지어낸 축이다 — **버린다**

TR-04에서 둘이 나왔다.

| 목이 가정한 것 | 서버 실제 |
|---|---|
| 개념마다 공개 범위(`scope`) | **리포트 하나**에 `disclosureScope` |
| 재시험 문답 2벌(`attempts[]`) | 문답 한 벌 + **전후 도달 단계**(`comparedReach`) |

**서버에 그런 축이 아예 없다.** 목을 만들 때 "이렇게 오겠지" 하고 지어낸 것이다.

이걸 놓치면 화면이 이상해진다 — 개념마다 자물쇠를 그리면 같은 말이 세 번 반복되고
*"이 개념만 잠겼나"* 로 읽힌다. 리포트 단위 값이면 **머리에 한 번** 말해야 한다.

## 4. 어댑터 쓰기 — `_/api/`

```
{screen}/_/api/types.ts    화면이 읽을 모양
{screen}/_/api/api.ts      생성 훅 + 변환
```

### 기본은 생성 훅이다

```ts
export function useHome() {
  const query = useGetMyAssessmentRounds()          // ⭕ 생성 훅
  const data = useMemo(() => query.data ? toHomeView(query.data) : undefined, [query.data])
  return { ...query, data }
}
```

호출 함수를 직접 쓰고 `useQuery`를 손으로 짜면 **쿼리 키와 `queryFn`이 두 벌**이 되고,
키가 한 글자만 달라도 캐시가 갈린다. 같은 데이터를 두 번 받고 무효화가 한쪽만 맞는다 —
조용히 틀리는 종류다.

### 어댑터가 하는 일은 넷뿐이다

1. **구획 합치기** — 반은 `membership`(기수 스코프), 팀은 `current`(회차 스코프)라
   `A반 3팀`을 여기서 만든다. 화면이 두 곳을 뒤지게 두지 않는다
2. **필드 추리기** — 44필드 중 화면이 읽는 것만. 안 그러면 카드 컴포넌트가 응답 구조를 안다
3. **`null` 기본값** — 합성 카드에서는 식별·일정이 전부 null이라 한 곳에서 정한다
4. **경계 접기** — 두 값 중 하나를 고르는 규칙이 있으면 여기서 한 번 접는다

네 번째의 실례가 **응시 창 교집합**이다.

```ts
assessmentCloseAt: earlier(c.assessmentCloseAt, c.roundAssessmentDueAt)
```

개인 창(분석 완료 + 24시간)과 회차 창(운영자 일정)이 둘 다 열려 있어야 응시할 수 있다.
카운트다운이 늦은 쪽을 가리키면 **화면이 말하는 마감과 서버가 막는 시점이 갈린다.**

### 판정은 어댑터가 하지 않는다

**상태를 다시 계산하지 않는다.** 서버가 `representativeStatus`·`defaultActionCode`·
`canSubmit`까지 보고 정한 값이라, 화면이 조합하면 그 규칙이 두 곳에 생긴다.

예외는 **서버가 자기모순일 때의 방어**뿐이고, 그때는 주석에 근거와 요청 차수를 남긴다.

```ts
// 🔴 retryState: PENDING인데 재시험 대상이 0개인 회차가 있다(24차 R1).
//    그대로 그리면 "다시 볼 문제가 0개 있어요" 아래에 아무것도 없다.
{report.retryState === 'PENDING' && retryCount > 0 && ( … )}
```

## 5. 목 걷어내기

```bash
rm {screen}/mockDb.ts {screen}/api.ts {screen}/types.ts
```

그리고 **`?state=` dev 오버라이드를 지운다.** 상태는 이제 서버가 정하므로 눌러서
재현할 수 없다. `TraineeCaseIndex`의 케이스 링크도 같이 지운다 — 남겨 두면 404로
안내하는 표가 된다.

> **삭제 후 화면이 빈 채로 뜨면** `rm -rf node_modules/.vite` 후 dev 서버 재시작.
> 지워진 모듈을 캐시가 붙들고 있다.

## 6. 실계정으로 확인 — **여기까지 해야 끝이다**

`typecheck`가 통과했다고 끝이 아니다. **브라우저로 하나씩 눌러본다.**

### 검사 명령을 정확히 쓴다

```bash
npm run typecheck     # ⭕ tsc -b — 프로젝트 참조를 따라 실제로 검사한다
npx tsc --noEmit      # ❌ 루트 tsconfig(files: [])를 읽어 아무것도 검사하지 않는다
```

**이 세션에서 한동안 후자를 썼고, 그동안 진짜 에러가 조용히 통과했다.**

### 눌러보면 코드로는 안 보이는 것이 나온다

실제로 나온 것:

- **두 화면이 같은 실패를 다르게 말했다.** ZIP으로 낸 학생에게 홈은 *"저장소 주소와
  브랜치를 확인해 주세요"* 라고 했다. `analysisFailureCode`를 받아만 두고 안 썼고,
  안내가 GitHub 전제로 하드코딩돼 있었다
- **경계 문구가 자기모순이었다.** 50MB를 1바이트 넘긴 파일이 반올림돼
  *"50MB — 50MB를 넘어 제출할 수 없어요"* 로 나왔다 (→ 올림으로)
- **카드가 아예 안 그려졌다.** ZIP 제출은 `content`가 없어서 "제출한 내용"이 통째로 빠졌다

### 커버리지를 센다

```
TR-01 카드 상태  2 / 10      ← 실제로 눈으로 본 것
TR-02 상태       2 / 6
TR-04 상태       4 / 7
```

**대부분을 못 본 채로 끝난다.** 제출 API가 막혀 있어 정상 흐름을 한 바퀴 돌릴 수 없으면,
앞 상태들은 백엔드가 데이터로 만들어 줘야 한다. 그 요청도 작업의 일부다
([trainee-state-matrix.md](../screens/trainee-state-matrix.md)처럼 표로 관리한다).

## 7. 지켜야 할 선 — `사용 가능`인 것만 호출한다

스펙의 `x-readiness`가 `available`이 아니면 **호출하지 않는다.**

```
available    → 붙인다
unavailable  → 화면은 만들되 그 경로를 막고, 사유를 화면에 띄운다
```

ZIP 제출이 실제로 그랬다. 서버가 안 받는데 버튼을 열어 두면 **누른 사람이 원인 모를
실패를 본다** — 파일을 고르는 데 들인 수고가 통째로 버려진다.

막을 때는 **상수 하나로** 막고, 열릴 때 그 한 줄만 지우면 되게 둔다.

```ts
const ZIP_SUBMIT_OPEN = false   // POST /submissions/zip이 unavailable (8/23 재개 예정)
```

> 생성기도 같은 기준이라, `unavailable`이면 **훅과 타입이 아예 안 만들어진다.**
> 붙여 뒀던 API가 내려가면 컴파일이 깨져서 알게 된다(실제로 겪었다).

## 8. 어긋난 것은 요청서로

붙이다 보면 **스펙만 읽을 때는 안 보이던 것**이 나온다. 실제 응답을 화면에 그리는
순간 드러난다.

| 유형 | 실례 |
|---|---|
| 값이 규칙과 안 맞는다 | `level`이 전부 0인데 서술은 2·3단 도달을 말한다 |
| 두 필드가 반대를 말한다 | 창이 닫혔는데 기본 행동이 "이어서 응시" |
| 두 API가 다른 답을 준다 | 같은 회차를 홈은 `미응시`, 리포트는 `발행 전` |
| 스키마엔 있는데 안 온다 | `fileName`·`fileSize`가 실응답에 없다 |

### 요청서 쓰는 법

- **실응답을 붙인다.** "이럴 것 같다"가 아니라 받은 JSON 그대로
- **화면이 어떻게 되는지 쓴다.** 백엔드가 우선순위를 정할 수 있게
- **우리가 뭘 해뒀는지 밝힌다.** 임시 방어를 해뒀으면 그것도 적는다
- **단정하지 않는다.** 근거가 약하면 *"둘 중 어느 쪽인가요"* 로 묻는다
  (실제로 대조군이 성립하지 않는 걸 뒤늦게 발견해 정정한 적 있다 — 반이 달랐다)

회신이 오면 **스펙을 다시 받고 실계정으로 재확인한다.** "반영했다"는 말과 실제
배포가 다를 수 있다 — 반대로 *"다음 배포"* 라고 한 것이 이미 나와 있던 적도 있다.

## 9. 완료 판정

```
✅ npm run verify:ci 전 단계 통과   (커밋된 상태만으로 CI를 재현한다)
✅ 목 파일이 남아 있지 않다          mockDb·api·types·?state=
✅ 호출하는 오퍼레이션이 전부 available
✅ 실계정으로 최소 한 상태는 눈으로 확인
✅ 못 본 상태를 표로 남겼다
```

**`verify:ci`는 커밋된 상태를 임시 워크트리에서 검사한다.** 작업 트리에만 있는 수정은
반영되지 않으니, 실패하면 먼저 *"커밋했나"* 를 본다.

## 10. 다음 도메인에 적용할 때

매니저·오퍼레이터도 같은 순서다. 다만 교육생과 다른 점이 있다.

- **화면이 더 많다** — 도메인 하나에 7개쯤 된다. 화면 단위로 브랜치를 나누지 말고
  **서로 응답을 참조하는 것끼리 묶는다**(제출 화면이 홈의 `projectId`를 쓴 것처럼)
- **쓰기(POST·PATCH)가 많다** — 조회만 있던 교육생과 달리 무효화 대상을 정해야 한다.
  `{tag}Keys.all`로 도메인 전체를 날릴지, 특정 키만 날릴지
- **권한 스코프가 있다** — 매니저는 담당 반만 본다. 빈 결과와 권한 없음이 다르게 와야
  하는데(`404 MANAGER_SCOPE_NOT_FOUND`), 그 구분을 화면이 아는지 확인한다
