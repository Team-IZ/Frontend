## 1. 🔴 R1 — TR-01 홈: 진행 중 회차 상태

**이 화면이 교육생 루프의 관문입니다.** 나머지 세 화면은 전부 여기서 링크로 들어갑니다.

### 핵심 요청 — **상태를 서버가 하나로 판정해 주세요**

화면이 *제출했나 · 분석 끝났나 · 응시했나 · 마감 지났나* 를 조합해서 상태를 유추하지
않게 해 주세요. 조합하면 같은 판정 규칙이 화면과 서버 양쪽에 생기고, 규칙이 바뀔 때
반드시 한쪽만 바뀝니다.

```jsonc
// GET /api/v0/members/me/home  (이름은 제안입니다)
{
  "scope": { "cohortName": "7기", "classroomName": "A반", "teamName": "3팀" },
  "currentRound": {                      // 진행 중인 회차가 없으면 null
    "projectId": "…",
    "roundLabel": "미프 3차",            // 운영자가 붙인 이름 그대로
    "curriculumName": "AI_LLMOps",
    "status": "NOT_SUBMITTED",           // ★ 아래 8종
    // 상태별로 필요한 값만 (아래 표)
    "submissionDueAt": "2026-08-13T14:16:00Z"
  },
  "upcomingRound": { "roundLabel": "미프 4차", "submissionDueAt": "…", "verifyOpensAt": "…", "verifyClosesAt": "…" },
  "pastRounds": [ { "reportId": "…", "roundLabel": "미프 2차", "attended": true, "retryState": "DONE" } ]
}
```

### 상태 8종과 각 상태가 필요한 값

| status | 뜻 | 같이 필요한 값 |
|---|---|---|
| `NOT_SUBMITTED` | 미제출(기한 내) | `submissionDueAt` |
| `ANALYZING` | 제출 완료·분석 중 | — (남은 시간을 화면에 안 씁니다) |
| `ANALYSIS_FAILED` | 분석 실패 | `submissionDueAt` · `failureReason`(사용자에게 보일 사유) |
| `READY_TO_VERIFY` | 응시 가능 | `verifyClosesAt` ← **분석 완료 + 24h** |
| `VERIFY_DONE` | 응시 완료·리포트 대기 | `verifiedAt` · `reportAfter`(발행 예정) |
| `RETRY_AVAILABLE` | 다시 보기 대상 | `retryDueAt` · `retryConcepts[]`(개념명) · `reportId` |
| `SUBMISSION_CLOSED` | 제출 마감 지남 → 미제출 확정 | `submissionDueAt` |
| `VERIFICATION_CLOSED` | 응시 창 마감 → 미응시 확정 | `verifyClosedAt` |

> **왜 상태마다 필드가 다른가** — 화면이 상태별로 완전히 다른 카드를 그립니다. 전부
> optional로 주시면 *"`ANALYZING`인데 `verifyClosesAt`이 있으면 무슨 뜻인가"* 를 화면이
> 매번 판단하게 됩니다. 한 응답에 필요한 것만 담아 주시면 그 판단이 사라집니다.
>
> 한 응답 안에서 필드가 갈리는 게 어려우시면 **전부 nullable로 주시고 `status`만
> 정확하면 됩니다** — 그 경우 저희가 흡수합니다. **중요한 것은 `status`를 서버가
> 정하는 것 하나입니다.**

### 조회 시점

화면은 **폴링하지 않습니다.** 진입할 때 한 번, 그리고 응시 창 마감 시각이 지나는
순간에 한 번 더 부릅니다. 분석 완료 알림이 필요하면 그건 별도 논의 대상입니다.

## 2. 🔴 R2 — TR-02 제출

### ① 제출 현황 조회

```jsonc
// GET /api/v0/projects/{projectId}/my-submission
{
  "roundLabel": "미프 3차",
  "submissionDueAt": "…",
  "status": "READY",              // 아래 6종
  "submittedAt": "…",             // 제출 후
  "analyzedAt": "…",              // 분석 후
  "verifyClosesAt": "…",          // READY
  "failureReason": "…",           // ANALYSIS_FAILED
  "content": { "repoUrl": "…", "branch": "main",
               "lastCommit": { "sha": "a3f9c21", "message": "…", "at": "…" } }
}
```

| status | 뜻 |
|---|---|
| `DRAFT` | 아직 제출 안 함 → 폼 |
| `ANALYZING` | 제출됨·분석 중 |
| `READY` | 분석 완료 → **아직 다시 제출할 수 있음** |
| `LOCKED` | **세션을 시작해서 잠김** — 다시 제출 불가 |
| `ANALYSIS_FAILED` | 분석 실패 → 폼을 이전 값으로 채워 다시 제출 |
| `SUBMISSION_CLOSED` | 마감 지남 |

> **`LOCKED`가 중요합니다.** 질문이 제출된 코드로 만들어지므로, 세션을 시작한 뒤
> 코드가 바뀌면 질문과 답이 어긋납니다. 화면이 그 사실을 문구로 설명하고 있어서
> **`READY`와 `LOCKED`를 서버가 갈라 주셔야 합니다.**

### ② 제출

방식이 둘입니다.

```
POST /api/v0/projects/{projectId}/submissions
  · GitHub — { repoUrl, branch }   (branch 비우면 기본 브랜치)
  · ZIP    — multipart/form-data   (file)
```

> **제출·분석 단위가 팀입니다.** 검증 질문을 **팀 코드 전체**로 만든다고 확인받았습니다 —
> 개인 기여분을 갈라내지 않으므로 **커밋 이메일 검증(옛 AUTH-07)이 필요 없습니다.**
> 기획 문서(SC-T02)에는 아직 그 단계가 3단계 중 1단계로 남아 있는데, 근거가 사라졌으니
> **같이 정리되는 것으로 이해하고 화면에서 뺐습니다.** 아니면 알려 주세요.
>
> 그러면 같은 팀 4~5명이 **같은 코드로 각자 세션**을 봅니다. 팀원끼리 비슷한 질문을 받게
> 되는데, 그게 의도인지만 확인 부탁드립니다(같은 질문을 공유하면 먼저 본 사람이 알려줄 수
> 있어 측정이 오염됩니다 — 질문을 학생마다 다르게 생성하시는지).

**ZIP은 50MB를 상한으로 화면에서 먼저 막고 있습니다.** 서버 상한이 다르면 알려
주세요 — 화면 상한을 그 값에 맞추겠습니다. 같은 값이어야 "올린 뒤에 거절"이 안 됩니다.

> multipart는 저희 코드 생성기가 건너뛰고 손으로 씁니다(기존 CSV 업로드와 같은 방식)
> — 스펙에 정의만 있으면 됩니다.

### ③ 저장소 사전 확인

```
POST /api/v0/submissions/repository-checks  { repoUrl }
  → 200 { ok: true }
  → 4xx REPO_NOT_FOUND
```

**제출 버튼을 누르기 전에 막으려는 것입니다.** 저장소를 못 여는 걸 제출 후 분석
실패로 알게 되면, 학생은 마감 시간을 이미 쓴 뒤입니다. 비공개·조직 밖 저장소는
ZIP으로 유도하는 안내가 이 응답에 붙습니다.

이 API가 부담스러우시면 **제출 시점에 동기로 검증**해 주셔도 됩니다 — 그 경우
`POST /submissions`가 `REPO_NOT_FOUND`를 즉시 내면 화면이 같은 안내를 띄웁니다.

## 3. 🔴 R3 — TR-03 검증 세션

> 2026-08-11 논의 + 이후 확인으로 **규칙이 확정됐습니다.** 아래가 저희가 이해한 모델이니
> **틀린 곳이 있으면 잡아 주세요.** 화면은 이 규칙대로 고칩니다.

### 구조 — 세션 1 : 개념 3 : 단계 4 : 시도 3

```
세션(sessionId)
 └ 개념(문제) 3개 고정          예) REST 설계 · 예외처리 · DTO 분리
    └ 단계 4개 (L1~L4)          질문 하나가 단계 하나
       └ 시도 최대 3회           답변 + 힌트1 후 답변 + 힌트2 후 답변
```

| | |
|---|---|
| 개념 | 테스트당 **3개 고정** |
| 단계 | **1단** 코드이해 · **2단** 설계논리 · **3단** 대안비교 · **4단** 반례대응 |
| 점수 | 시도마다 **0~5점**, **3점 미만 실패** |
| 힌트 | **3점 미만일 때 제공** · 질문당 **최대 2개** |
| 단계 종료 | 힌트 2개를 쓰고도 3점 미만 → **그 개념 종료, 다음 개념으로** |
| 시간 | **세션 1시간 · 문제(개념)당 20분** |
| 재시험 | **불합격 개념만**(도달 2단 미만) · **L1부터 4단계 전부** · **1회만** |

**한 단계에서 최대 3번 답합니다.** 힌트 2개가 그 사이에 낍니다.

```
질문(L4) → 답변① 1점  미달 → 힌트1
         → 답변② 1점  미달 → 힌트2
         → 답변③ 2점  미달 → 이 개념 종료, 다음 개념으로
                    3점↑ → L4 통과
```

### ★ 도달 단계 = 마지막으로 통과한 단계

| | 통과 | 실패한 단계 | 도달 |
|---|---|---|---|
| A문제 | L3까지 | L4 | **3단** |
| B문제 | L2까지 | L3 | **2단** |
| C문제 | L1까지 | L2 | **1단** |
| — | 없음 | L1 | **0단** |

> *"2단에서 종료되면 1단으로 취급"* 은 별도 보정 규칙이 아니라 위 정의에서 자동으로 나오는
> 결과로 이해했습니다. **서버가 이 값을 확정해서 주세요** — 화면이 계산하면 리포트·매니저
> 화면과 갈립니다.

**`0단`과 `문항 없음`을 구분해 주세요.** 이미 `GET /reports/class-diagnosis`가 그렇게 하고
있습니다(*"`level0`과 `unasked`를 합치면 안 된다"*). 교육생 리포트에도 **문항 없음을
그대로 보여줍니다** — 개념 3개 중 2개만 뜨는 이유를 학생이 알아야 하기 때문입니다.

### ★ 힌트가 나오는 길이 **둘**입니다

| | 언제 | 지금 화면 |
|---|---|---|
| **① 학생이 요청** | [다시 설명해 주세요] 버튼 | ⭕ 이미 있습니다 |
| **② 점수 미달로 지급** | 채점 결과가 3점 미만 | ❌ **없습니다 — 새로 붙습니다** |

②가 새로 생기는 것이고 ①은 그대로 남습니다. 그래서 힌트는 **요청 API**와 **제출
응답** 양쪽에서 올 수 있어야 합니다.

```jsonc
// POST /api/v0/sessions/{sessionId}/answers   { answer }
{
  "score": 2,                    // 0~5
  "outcome": "SAME_QUESTION",    // 아래
  "hint": { "text": "…", "remaining": 0 },   // ② score < 3 이고 남았을 때만
  "nextQuestion": { … }          // outcome이 NEXT_QUESTION·NEXT_CONCEPT일 때
}

// POST /api/v0/sessions/{sessionId}/hints    ← ① 학생이 버튼을 눌렀을 때
{ "text": "…", "remaining": 1 }
```

> **`remaining`을 서버가 세 주세요.** 화면이 세면 두 경로(요청·지급)의 합산 규칙이
> 화면에 생깁니다. 남은 개수가 0이면 화면이 버튼을 감춥니다.

**⚠️ 확인 — 질문당 2개가 두 경로의 합산인가요?** 버튼으로 1개를 받은 학생이 미달로
1개를 더 받으면 거기서 끝인지(합산 2), 아니면 경로별로 각각 2개인지에 따라 화면의
남은 횟수 표시가 달라집니다. **합산 2개로 이해하고 있습니다.**

| outcome | 뜻 | 화면 |
|---|---|---|
| `SAME_QUESTION` | 미달 · 힌트 주고 같은 질문 재시도 | 힌트 버블 + 입력 유지 |
| `NEXT_QUESTION` | 통과 · 같은 개념의 다음 단계 | 새 질문 |
| `NEXT_CONCEPT` | 이 개념 종료(통과 또는 힌트 소진) | 전환 화면 → 다음 개념 |
| `COMPLETED` | 3개념 전부 끝 | 종료 화면 |

> **`SAME_QUESTION`과 `NEXT_CONCEPT`를 서버가 갈라 주셔야 합니다.** "힌트 2개를 다
> 썼는데도 미달"인지를 화면이 세면, 힌트 지급 규칙이 두 곳에 생깁니다.

### 문제(개념) 조회

```jsonc
// GET /api/v0/projects/{projectId}/session  또는 POST /sessions (시작과 동시에)
{
  "sessionId": "…",
  "mode": "FIRST",               // FIRST | RETRY
  "concepts": [{
    "conceptId": "…",
    "name": "HITL Trigger 조건",
    "file": "nodes.py",
    "code": [{ "line": 12, "text": "def should_trigger_hitl(...)" }],   // 근거 코드 조각
    "callers": { "label": "이 함수를 쓰는 곳", "ref": "graph.py:41", "snippet": "…" },
    "firstQuestion": { "text": "…", "ref": "nodes.py:12–20", "level": 1 }
  }]
}
```

**`ref`가 필수입니다** — 화면 왼쪽이 코드를 고정으로 띄우고 질문이 가리키는 줄을
하이라이트합니다. 형식은 `파일:줄` 또는 `파일:시작–끝`, 여러 줄은 쉼표로 주시면 됩니다
(`nodes.py:14, 17`) — 지금 목이 그 형식으로 파싱하고 있습니다.

### 시간 — 두 상한을 서버가 갖고 판정해 주세요

**세션 1시간 · 문제(개념)당 20분**으로 이해했습니다. 3 × 20 = 60이라 두 상한이 맞물립니다.

시간초과는 **그 시도의 실패**로 처리하고, 그 시점의 마지막 통과 단계가 도달 단계가 됩니다
(예시의 B문제가 *"L3에서 2점, 2점, 시간초과로 실패"* → 도달 2단).

**남은 시간을 응답에 실어 주세요** — 화면이 자체 시계로 세면 서버와 어긋나서, 화면은
"아직 10초 남음"인데 서버가 이미 마감 처리하는 구간이 생깁니다.

```jsonc
{ "conceptDeadlineAt": "…", "sessionDeadlineAt": "…" }
```

### 재시험(다시 보기)

| | |
|---|---|
| 대상 | **도달 2단 미만**(0·1단) 개념만 |
| 범위 | 그 개념을 **L1부터 4단계 전부** 다시 |
| 횟수 | **1회만** |
| 결과 | 원점수를 **바꾸지 않습니다** — 위험자·집단미달·기수비교는 첫 응시 기준 |
| 문항 없음 | **대상 아님** |

> ⚠️ **지금 화면은 "막혔던 질문 하나만 다시"로 되어 있어 고쳐야 합니다.** 저희 쪽 작업입니다.

### 확인이 필요한 것

1. **힌트 2개가 요청·지급 두 경로의 합산인가요?** 버튼으로 1개 받고 미달로 1개 더 받으면
   거기서 끝인지. **합산 2개로 이해하고 있습니다.**
2. **문제당 20분이 이월되나요?** 15분에 끝내면 남은 5분이 다음 문제로 가는지, 각 20분
   독립인지. **독립으로 이해하고 있습니다.**
3. **첫 시도에서 시간초과면** 그 시도만 실패인가요, 그 개념이 바로 종료인가요?
4. **4단을 통과하면** 거기서 개념이 끝나나요(질문 4개를 다 쓴 것이므로)?
5. **재시험에도 힌트가 있나요?** 지금 화면은 다시 보기에 힌트를 안 줍니다.
6. **재시험의 시간 규칙** — 개념 1개만 보면 20분인가요?

## 4. 🟠 R4 — TR-04 리포트: `unavailable` 해제

스펙에 이미 있으나 넷 다 `x-readiness: unavailable`이라 호출 함수가 생성되지 않습니다.

| | 엔드포인트 |
|---|---|
| | `GET /api/v0/reports` — 내 리포트 전량 |
| | `GET /api/v0/reports/{reportId}` — 단건 |
| | `GET /api/v0/reports/{reportId}/disclosure` — 공개 상태 |
| | `PUT /api/v0/reports/{reportId}/disclosure` — 공개 범위 설정 |

### 공개 정책(저희 이해)

| `release_status` | 교육생이 보는 것 |
|---|---|
| `NOT_CONFIGURED` | 못 봄(발행 전) |
| `WITHHELD` | 못 봄(비공개) |
| `RELEASED` | 봄 — `SUMMARY` / `FULL`이 갈림 |

**`SUMMARY`/`FULL`은 개념별이고 기준은 도달 2단입니다** — 재시험 대상을 가르는 선과 같습니다.

```
합격 (2단 이상)  ─────────────────────────────→ FULL
불합격 (0·1단)   → SUMMARY ──재시험 완료──→ FULL
```

| | FULL | SUMMARY |
|---|---|---|
| 개념 도달 단계 · 서술 | ⭕ | ⭕ |
| 교안 위치 · 다시 보기 | — | ⭕ |
| 해설 · 문답 원문 | ⭕ | ❌ |

> **`SUMMARY`는 재시험 전의 임시 상태로 이해했습니다.** 재시험을 마치면 그 개념도 FULL이
> 되어 해설이 열립니다 — *"재시험이면 그냥 FULL"* 로 확인받았습니다.

### 문항 없음 — 제3의 값

개념 3개 중 하나가 그 학생 코드에 없으면 문항이 안 만들어집니다(`unasked`).
`GET /reports/class-diagnosis`가 이미 `level0`과 엄격히 구분하고 있으니, **교육생 리포트에도
같은 구분으로 주세요.** 화면에 *"코드에 이 개념이 없어 묻지 못했습니다 — 못한 것이 아닙니다"*
로 그립니다. **재시험 대상은 아닙니다.**

### 재시험 결과 — 한 회차에 리포트 하나, 안에서 병기

*"재시험 결과의 리포트도 교육생이 볼 수 있어야 한다"* 이고 **원점수는 안 바뀝니다.**
저희는 **문서를 쪼개지 않고 한 리포트 안에 병기**하려 합니다 — 재시험은 불합격 개념만 보므로
따로 떼면 개념 하나짜리 반쪽 문서가 되고, 회차 목록에 같은 회차가 둘 생기며, 매니저의 개인별
공개 설정이 2배가 되기 때문입니다.

**그래서 개념마다 시도를 배열로 주시면 좋겠습니다.**

```jsonc
"attempts": [
  { "seq": 1, "reachedLevel": 1, "qa": [ … ] },   // 첫 응시 — 이게 정본
  { "seq": 2, "reachedLevel": 3, "qa": [ … ] }    // 재시험 — 기록
]
```

이 모양이면 화면이 병기로 그리다가 나중에 분리로 바꿔도 서버가 안 바뀝니다.

### 요청

1. **`release_status`와 `SUMMARY`/`FULL`을 리포트 응답에 같이 주세요.** disclosure를
   따로 조회해야 하면 화면이 두 번 부르고, 그 사이 상태가 갈릴 수 있습니다.
2. **`FULL`/`SUMMARY` 판정 자체를 주세요** — 단계 숫자만 주시고 화면이 가르면, 매니저
   화면과 기준이 갈립니다.
3. **`SUMMARY`면 `explanation`·`qa`를 아예 빼 주세요.** null로 오면 "없는 것"과 "안
   준 것"이 구분되지 않습니다. 빼 주시면 화면이 그릴 수 없다는 것을 타입이 보장합니다.
   > 기획도 같은 요구입니다 — *"비공개 회차는 잠금 플래그만 반환하고 본문은 전송하지
   > 않는다. 공개 필터는 서버측, **클라이언트에 숨기는 방식 금지**"*. 안 보이게 하는
   > 것과 안 보내는 것은 다릅니다.

리포트 본문에 필요한 값은 이렇습니다.

```jsonc
{
  "reportId": "…", "roundLabel": "미프 3차", "publishedAt": "…", "curriculumName": "AI_LLMOps",
  "releaseStatus": "RELEASED",
  "concepts": [{
    "name": "HITL Trigger 조건",
    "asked": true,                 // false면 문항 없음 — 아래 값들이 전부 빠진다
    "reachedLevel": 1,             // 0~4 · 마지막으로 통과한 단계
    "scope": "SUMMARY",            // 개념별 · 2단 미만이면 SUMMARY
    "retryTarget": true,           // reachedLevel < 2 && 재시험 미사용
    "narrative": "이 함수가 무엇을 하는지는 설명했어요. 다만 …",
    "curriculumRef": { "chapter": "3장", "pages": "36~46쪽", "title": "사람 확인이 필요한 순간" },
    "explanation": ["…"],          // FULL일 때만
    "attempts": [                  // FULL일 때만 · 재시험을 봤으면 2건
      { "seq": 1, "reachedLevel": 1, "qa": [{ "level": 1, "question": "…", "answer": "…", "score": 4 }] }
    ]
  }],
  "retry": { "used": false, "dueAt": "…" }   // 1회만 가능
}
```

> **`narrative`(서술)는 서버가 문장으로 주시는 것으로 이해했습니다.** 화면이 단계
> 숫자로 문장을 만들지 않습니다 — 개념마다 막힌 지점이 달라 숫자로는 못 씁니다.

## 5. 🟡 확인 2건

### Q1 — `findMyEnrollments`에 팀이 없습니다

```jsonc
// GET /members/me/enrollments 현재 응답
{ "enrollments": [{ "cohortId": "…", "cohortName": "7기",
                    "classroom": { "classroomId": "…", "name": "A반" } }] }
```

화면은 **`A반 3팀`** 으로 표시합니다(제출이 팀 단위라 팀이 소속의 일부입니다).
팀을 여기에 얹어 주시거나, R1의 홈 응답 `scope`에 담아 주시면 됩니다 — **둘 중
어느 쪽이든 좋습니다.**

### Q2 — 리포트 공개: **기획 원안(GOV-03)과 세 군데가 다릅니다**

주신 내용을 *"매니저가 자기 반 교육생에게 리포트를 열어 줄지 정한다"* 로 이해했습니다.
그 자체는 기획의 **GOV-03(열람 범위 통제)** 과 같습니다. 다만 **세부가 셋 다릅니다** —
어느 쪽으로 갈지 정해 주시면 화면을 맞추겠습니다.

| | 기획 원안 | 주신 내용 |
|---|---|---|
| **① 기본값** | **비공개**(안전 기본값·미지정도 비공개) | **공개** |
| **② 범위를 누가 정하나** | 매니저가 **비공개/요약/전체 3단 라디오**로 고름 | 공개 여부만 매니저 · **요약/전체는 도달 2단으로 자동** |
| **③ 설정 단위** | **회차(체크포인트)** 단위 — `PATCH /checkpoints/{id}/disclosure` | *"교육생 **개인별**로 활성화"* |

**②가 가장 큰 변화입니다.** 원안은 매니저가 *얼마나 보여줄지*를 고르는데, 새 규칙은
매니저가 *열지 말지*만 정하고 범위는 서버가 판정합니다. 이쪽이 매니저 설정 UI를
라디오 3개에서 토글 하나로 줄여 주므로 **저희는 새 규칙이 낫다고 봅니다** — 다만
기획 문서(SC-M03 §3 회차 설정 모달)가 아직 라디오 3단이라 같이 정리돼야 합니다.

**③은 API가 이미 개인별입니다.** `PUT /reports/{reportId}/disclosure`가 리포트 1건
단위이고, 리포트 1건 = 교육생 1명 × 1회차이므로 개인별입니다. 기획은 회차 단위였습니다
— **API 쪽(개인별)로 확정된 것으로 이해해도 될까요?** 그렇다면 매니저 화면에 회차
단위 일괄 설정이 필요할 텐데, 원안이 *"일괄 공개 = 검토 없이 노출 = 유해"*(D121)라며
벌크 페이지를 명시적으로 배제했던 항목이라 확인이 필요합니다.

**①은 ③과 묶여 있습니다.** 개인별인데 기본이 공개라면, 매니저가 아무것도 안 해도
전원이 보게 됩니다 — 원안이 기본 비공개로 둔 이유가 *"검토 없이 노출되는 것을 막는다"*
였습니다. 정책이 바뀐 것이면 그대로 따르겠습니다. **확인만 부탁드립니다.**

### 덧 — "프로젝트 종료 기간"

자동 공개 타이밍 문제 때문에 나온 것으로 이해했습니다. **자동 공개를 걸지 않고 매니저
수동 공개로 가면 그 필드가 필요 없어집니다.** 원안도 같은 이유로 일괄 공개를 배제했으니
(D121) 수동 쪽이 기획과 정합적입니다. 정해지면 알려 주세요 — 일정 관련 화면이 같이
정리됩니다.

## 6. 우선순위 제안

교육생 루프 순서대로 나오면 **화면을 한 개씩 실서버로 넘길 수 있습니다.**

```
R1 홈  →  R2 제출  →  R3 세션  →  R4 리포트
```

**R1이 없으면 나머지 셋에 들어갈 길이 없습니다**(전부 홈에서 링크로 진입합니다).
R1 하나만 먼저 주셔도 홈은 그 시점에 실서버로 넘어갑니다.

세 화면 모두 목으로 완성돼 있어서, **응답만 오면 붙이는 데 화면당 하루가 안 걸립니다.**
지금 개발 중이시라면 위 모양에서 어긋나는 부분을 미리 알려 주세요 — 저희가 맞추겠습니다.
