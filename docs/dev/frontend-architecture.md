# 프론트엔드 구조 설계

> 두 명이 영역을 나눠 병렬로 개발하기 위한 폴더·레이어 규칙. 결정 배경은 `decision-log.md`.
> **설계 원칙: 폴더 구조가 곧 작업 분할선이 되어야 한다.** 두 사람이 같은 파일을 건드리면 폴더가 잘못 잡힌 것이다.

## 지금 어디까지 와 있나

이 문서는 **합의된 규칙**이고, 코드는 아직 전부 들어오지 않았다. 규칙을 먼저 확정해야 두 사람이 같은 자리에 코드를 놓는다.

| | 상태 |
| --- | --- |
| 디자인 토큰 · 가드 · 토큰 문서 | **머지됨** — `docs/dev/design-system.html` |
| 이 문서의 폴더·레이어 규칙 | **합의됨** |
| 레이어 경계 린트 규칙 | **적용됨** — 위반하면 `npm run lint` 실패 |
| 셸 2종 · 라우터 · 첫 화면 | 검토 중 — 아래 구조와 §5는 **그 설계**다 |

즉 **폴더가 아직 비어 있는 것이 정상**이다. 파일을 만들 때 이 규칙대로 놓으면 되고, 린트가 어긋난 위치를 바로 잡아준다.

## 2. 폴더 구조

```
src/
├─ app/                  앱 진입·라우팅·전역 프로바이더
│  └─ routes.tsx         각 feature의 라우트를 합치기만 한다
│                        (전역 프로바이더가 둘 이상 되면 providers.tsx를 만든다.
│                         지금은 RouterProvider 하나뿐이라 main.tsx에 있다)
│
├─ shells/               레이아웃 셸 — 4역할 공용, ConsoleShell 하나뿐이다
│  ├─ ConsoleShell.tsx   Header + Sidebar + content, role prop으로 조립
│  ├─ Header.tsx         브랜드 + 스코프 선택기 + 사용자
│  ├─ Sidebar.tsx        좌측 메뉴 — role별 항목은 sidebarConfig.ts가 갖는다
│  └─ sidebarConfig.ts   역할별 사이드바 항목 · Role 타입
│                        (역할별 래퍼 파일을 따로 두지 않는다 — 넷 다 "어떤
│                         사이드바를 넣을까"만 다른 얇은 래퍼였다. AU 화면은
│                         로그인 전이라 셸이 없다)
│
├─ components/
│  ├─ ui/                shadcn 프리미티브 — CLI가 쓰는 고정 경로
│  └─ common/             팀 공용 조합 (도메인을 모른다, 예: Wordmark)
│
├─ features/             도메인별 — ★ 작업 분할선
│  └─ {역할}/{화면}/     docs/plan/v2/wireframe/{역할}/{화면}.html과 1:1
│     ├─ {X}Screen.tsx   화면 컴포넌트만
│     ├─ {X}Screen.route.tsx  그 화면의 `route` export(§4) — 도메인 routes.tsx는 없다
│     └─ components/     그 도메인에서만 쓰는 조각
│
├─ api/                  HTTP 클라이언트 · 공통 응답 타입
├─ mocks/                MSW 핸들러
├─ stores/               Zustand (2개)
└─ lib/                  utils (`cn` 등)
```

### 왜 `shells/`를 따로 두나

와이어 22개를 실측하면 **가장 많이 반복되는 것이 컴포넌트가 아니라 셸**이다.

| 요소 | 등장 화면 수 |
| --- | --- |
| `app`(레이아웃 골격) | 13 |
| `nav` / `content` | 12 |
| `topbar` | 11 |
| `phead`(페이지 헤더) · `cohortsel`(기수 선택기) | 10 |

두 사람이 각자 셸을 만들면 **가장 크고 가장 많이 쓰이는 것을 두 벌 갖게 된다.** 그래서 셸은 분할 전에 하나로 확정한다. 도메인을 모르는 순수 UI(`components/ui`)도 아니고 한 도메인의 것(`features/*`)도 아니라서 별도 위치에 둔다. 이름은 명세서가 쓰는 어휘("앱 셸 5종")를 따랐다.

## 3. 레이어 경계 — 아래층은 위층을 모른다

```
features/*  ──▶  components/common  ──▶  components/ui  ──▶  lib
    │
    └──────────▶  shells/
```

| 규칙 | 뜻 |
| --- | --- |
| `components/ui`는 **도메인을 모른다** | `기수`·`교육생` 같은 말이 들어가면 잘못된 위치 |
| `components/common`도 **도메인을 모른다** | 알아야 하면 `features/*`로 내린다 |
| `shells/`는 라우팅·권한을 알아도 되나 **특정 화면은 모른다** | |
| **`features/A`는 `features/B`를 import하지 않는다** | ★ 이 규칙이 작업 분할을 성립시킨다 |

교차 참조가 필요해지면 둘 중 하나다 — 공통 부분을 `components/common`으로 올리거나, 애초에 한 도메인이었던 것이다.

**이 경계는 문서가 아니라 린터가 지킨다.** `.oxlintrc.json`의 `overrides`에 `no-restricted-imports`로 걸려 있어 위반 시 `npm run lint`가 실패한다(에디터에도 즉시 표시된다).

```
src/features/**          →  @/features/*/*  import 금지
src/components/**, lib/  →  @/features/*, @/stores/*  import 금지
```

## 4. 라우팅 — 충돌 지점을 없앤다

각 화면이 자기 라우트를 **옆 파일**(`{X}Screen.route.tsx`)에 `route` export로
갖는다. 도메인 단위 `routes.tsx`도, 화면 파일 안에 같이 두는 것도 아니다.

```tsx
// features/manager/curriculum/CurriculumScreen.tsx — 컴포넌트만
export default function CurriculumScreen() { ... }

// features/manager/curriculum/CurriculumScreen.route.tsx — 그 옆에
import CurriculumScreen from './CurriculumScreen'
export const route: RouteObject = { path: '/manager/curriculum', element: <CurriculumScreen /> }
```

두 가지를 다 시도했다가 이 형태로 왔다.

- **도메인당 `routes.tsx` 하나** — 화면 폴더에 화면이 2개면(면담 목록+브리프,
  프로젝트 목록+상세 등) 그 파일을 나눠 가져야 했다. 애초에 화면마다 폴더를
  쪼갠 이유(작업이 겹치지 않게)가 여기서 다시 깨진다.
- **화면 파일 안에 `route`를 같이 export** — 컴포넌트 export와 값 export가
  한 파일에 있으면 React Fast Refresh가 그 파일에 상태 보존 핫리로드를 못
  한다(`react/only-export-components`). 화면이 폼·타이머처럼 실제 상태를
  갖기 시작하면, 저장할 때마다 그 상태가 날아가는 게 반복적으로 걸린다.

옆 파일로 쪼개면 둘 다 안 생긴다 — 화면마다 파일이 여전히 독립적이고
(공유하는 파일이 없다), `{X}Screen.tsx`는 컴포넌트만 export해서 Fast
Refresh가 정상 동작한다.

`app/routes.tsx`는 이 파일들을 손으로 import하지 않는다.
`import.meta.glob('/src/features/**/*.route.tsx', { eager: true })`로 폴더를
훑어 `route`만 모은다 — Vite 빌드타임에 정적으로 분석되는 네이티브 기능이라
런타임 매직이 아니다. **새 화면을 추가해도 `app/routes.tsx`는 한 글자도 안
바뀐다.**

> **한 단계 더 모으지 않는다.** "역할 폴더마다 routes.ts로 한 번 더 모아서
> 루트는 그것만 5개 import하면 어떤가"는 성능상 이득이 없다(어차피
> `eager: true`라 전부 같은 번들에 정적으로 들어간다 — 모으는 단계가 하나
> 늘어도 앱 부팅 시 배열 20여 개를 도는 마이크로초 단위 차이일 뿐이다).
> 오히려 그 역할 폴더 `routes.ts` 하나를 여러 화면 담당자가 같이 고쳐야 해서
> **원래 없애려던 충돌이 다시 생긴다.** 파일 수가 늘어나는 게 이 구조의
> 목적이다 — 루트에서 한 단계로 바로 모은다.

**미등록 경로는 로그인으로 조용히 보내지 않는다.** 그러면 "라우트를 등록하지 않은 것"과 "코드가 틀린 것"을 구분할 수 없다. 등록되지 않은 경로는 URL을 유지한 채 원인을 알려준다. 인증이 붙으면 미로그인 사용자용 리다이렉트로 바뀐다.

## 5. 무엇을 언제 만드나 — 빈도 기준

### 측정 대상은 "확정된 화면"만

와이어 22개 중 **분석·진단 / 개입 관리 / 리포트는 임시 화면**이고 나중에 전면 재작성된다. 상태·case 매핑용 `cases.html`과 뷰어 `index.html`도 제품 화면이 아니다. 이들을 빼면 **확정 화면은 17개**다.

```
확정  로그인 · 비밀번호 재설정 · 매니저 회원가입 · 교육생 계정 활성화
     플랫폼 콘솔 · 운영 관리(기수/반/명단·반 배정)
     대시보드 · 교안 · 프로젝트 워크스페이스 · 교육생 리스트·상세 · 온보딩
     교육생 홈·제출·검증 세션·결과 리포트
임시  분석·진단 · 개입 관리 · 리포트
```

**버릴 화면의 빈도로 공용 컴포넌트를 정하면 안 된다.** 실제로 대상을 좁히자 순위가 바뀌었다.

| 요소 | 22화면 기준 | **확정 17화면** | 해석 |
| --- | --- | --- | --- |
| `badge` | 8 (36%) | **8 (47%)** | 임시 화면엔 하나도 없었다 → 중요도 상승 |
| `tabs` | 6 (27%) | **4 (24%)** | 일부가 임시 화면에 있었다 → 1티어에서 제외 |
| `split`(인증 셸) | 7 (32%) | **7 (41%)** | 상승 |

아래 표는 확정 17화면 기준이다.

### 지금 만든다 (7화면 이상)

| 것 | 확정 화면 수 | 근거 |
| --- | --- | --- |
| **매니저 셸**(`app`·`nav`·`content`·`topbar`·`phead`·`cohortsel`) | 7~9 / 17 | 최대 충돌 지점 |
| **인증 셸**(`split`·`brand`·`formside`·`form`) | 4~7 / 17 | 로그인 화면에 이미 있음 — 뽑기만 하면 된다 |
| **Button** | 10 / 17 | 빈도 1위 |
| **Badge** | 8 / 17 | variant가 토큰 문서에 확정돼 있다 |
| **Card** | 6 / 17 | 단순 |
| **표 레이아웃** | 5 / 17 | ↓ |

**표는 배치만 만든다.** 헤더(제목+총개수 / +추가) · 툴바(검색·필터·정렬 좌측) · 푸터(범위개수 좌 + 페이저 중앙) — 이 4단 배치는 팀 규약에 이미 확정돼 있어 추측이 아니다. **컬럼 정의·데이터 바인딩 API는 만들지 않는다.**

### 이름만 합의 (4~5화면)

Tabs · Search · Select · Input/Field · Link — 어디에 둘지와 이름만 정한다. 필요한 사람이 만들고 나중에 통합한다.

### 매니저 셸의 nav는 데이터로 둔다

nav 8항목 중 **셋(분석·진단 / 개입 / 리포트)이 임시 화면**이다. 셸이 항목을 하드코딩하면 그 화면을 갈아엎을 때 셸까지 건드려야 한다. nav 항목은 **배열 하나**로 두고 셸은 그것을 렌더하기만 한다 — 와이어도 이미 그렇게 되어 있다.

```js
// 와이어의 방식. 임시 화면 항목은 교체 시 이 배열만 고치면 된다.
var NAV = [["▦","대시보드",""],["⚙","운영 관리","총괄"], … ]
```

### 안 만든다

3화면 이하 프리미티브, props 시그니처 선확정, 원시 팔레트 레이어.

> **경계:** 와이어에서 확정할 수 있는 것은 **무엇이 존재하고 몇 곳에서 쓰이는가**이고, 확정할 수 없는 것은 **props 시그니처·상태 관리·합성 방식**이다. 전자는 오늘 정하고 후자는 만들면서 정한다.

## 6. 작업 분할 (2인 기준)

폴더가 곧 분할선이다.

| | 담당 폴더 |
| --- | --- |
| A | `features/{cohort,curriculum,project}` — 매니저 라인 |
| B | `features/{auth,trainee}` — 인증·교육생 라인 |

`shells/`·`components/`·`app/`은 **분할 전에 확정**하고, 이후 변경은 서로에게 알린다.

## 7. 새 컴포넌트를 만들 때

둘이 나눠 개발하면 각자 컴포넌트를 만들게 된다. 공용을 미리 다 만드는 것보다 **만드는 방법을 통일하는 것**이 현실적이다.

1. **먼저 `components/ui`에 있는지 본다.** 있으면 그걸 쓴다.
2. **없으면 `features/{내 도메인}/components`에 만든다.** 처음부터 공용으로 올리지 않는다.
3. **다른 도메인에서도 같은 게 필요해지면** 그때 `components/common`으로 올린다.
4. 색·반경·글자 크기는 **토큰만** 쓴다. 하드코딩은 `npm run check:design`이 막는다.
5. 크기·간격에 임의값(`h-[46px]`)을 쓰는 것은 막지 않는다. 다만 **같은 값이 3번 반복되면 토큰으로 승격**한다.

3번이 핵심이다. 처음부터 공용으로 만들면 **한 곳의 사정에 맞춘 것이 공용이 된다.**

## 8. 실행 순서

앞이 뒤의 전제가 되도록 배열했다.

| # | 파트 | 이유 |
| --- | --- | --- |
| 1 | 폴더 골격 + 레이어 규칙 + 라우터 | 이후 모든 코드가 놓일 자리 |
| 2 | 셸 2종(매니저·인증) | 최다 반복, 최대 충돌 |
| 3 | 프리미티브(Button·Badge·Card) + 표 배치 | 빈도 상위 |
| 4 | MSW 목 경계 | 둘 다 같은 가짜 API에 붙는다 |
| 5 | 반복 크기값 토큰화 | 화면이 몇 개 생긴 뒤 재측정 |

1~4가 끝나면 분할해서 병렬로 갈 수 있다.
