## 1. 🔴 R1 — 허용한다고 말하는 수단을 실제로는 못 씁니다

`GET /api/v0/assessment-rounds` 실응답입니다.

```json
"availableSubmissionMethods": ["GITHUB_URL", "ZIP_WITH_GITLOG"]
```

그런데 GitHub URL을 받는 API는 `사용 불가`입니다.

```
POST /api/v0/submissions        x-readiness: unavailable
POST /api/v0/submissions/zip    x-readiness: available
```

### 왜 이게 조용히 안 끝나는가

저희는 **"지금은 ZIP만"을 화면에 하드코딩하지 않았습니다.** 그 배열이 허용 수단을
알려주는 필드니까, 그것만 보고 탭을 열고 잠그도록 만들었습니다 — 나중에 GitHub이
열리면 화면을 한 글자도 안 고치고 따라가려고요.

그래서 배열만 믿으면 화면이 **GitHub 탭을 열고, 그 탭이 선택된 채로 그 아래에 ZIP
드롭존을 띄웁니다** — 저장소 입력칸 자체가 없으니까요. 학생 입장에서는 고를 수는
있는데 낼 수는 없는 탭입니다.

**지금은 저희가 막아 뒀습니다.** 배열과 별개로 *"그 API가 실제로 있는지"* 를 화면이
AND로 묶어서, `POST /submissions`가 열릴 때까지 탭을 잠급니다. 다만 이건 **서버 말과
화면이 어긋난 상태를 코드로 덮은 것**이라, 오래 두고 싶지 않습니다.

`availableSubmissionMethods`의 뜻이 *"기관 정책이 허용한 수단"* 이라면 지금 값은
맞습니다. 하지만 **화면이 "낼 수 있다"의 근거로 쓸 필드로는 틀립니다.**

### 요청 — 둘 중 하나만 골라 주시면 됩니다

1. **`POST /submissions`를 `available`로** 열어 주신다 → 저희가 막아 둔 한 줄을 지우고
   저장소 입력 폼을 붙입니다
2. **`GITHUB_URL`을 배열에서 빼신다** → 막아 둔 한 줄도 필요 없어집니다. 나중에 열릴 때
   배열에 다시 넣어 주시면 화면이 자동으로 따라갑니다

**어느 쪽이든 저희는 따라갑니다 — 일정만 알려 주세요.** 곧 여실 계획이면 1번을
기다리고, 아니면 2번으로 정리하는 게 깔끔합니다.

> 만약 이 배열이 *"실제 호출 가능"* 이 아니라 *"기관이 정책상 허용"* 을 뜻하는
> 거라면, **호출 가능한 수단을 알려주는 필드를 하나 따로** 주셔도 됩니다. 다만
> 필드 두 개를 화면이 AND로 묶어야 해서, 값을 빼는 쪽이 단순합니다.

## 2. 🔴 R2 — 리포트 `level`과 `said`가 서로 다른 말을 합니다

`GET /api/v0/reports/e5425bbb-7d00-5d88-af76-9469f74c7f77` 실응답입니다.

```json
{
  "status": "PUBLISHED",
  "completionStatus": "FULL",
  "expectedConceptCount": 3,
  "missingConceptCount": 0,
  "concepts": [
    { "name": "예외 처리와 롤백 전략", "asked": true, "level": 0,
      "said": "…실패 조건까지 짚었지만, 같은 요구사항을 다른 방법으로 구현하는 대안은 제시하지 못했습니다.",
      "isRetryTarget": false },
    { "name": "API 응답 계약 설계", "asked": true, "level": 0,
      "said": "…선택 이유까지 설명했지만, 어떤 상황에서 이 방식이 깨지는지는 답하지 못했습니다.",
      "isRetryTarget": true },
    { "name": "영속성 매핑과 지연 로딩", "asked": true, "level": 0,
      "said": "…선택 이유까지 설명했지만, 어떤 상황에서 이 방식이 깨지는지는 답하지 못했습니다.",
      "isRetryTarget": true }
  ]
}
```

### 두 필드가 반대를 말합니다

확정된 채점 모델(2026-08-11)에서 단계는 이렇습니다.

| 단계 | 무엇을 묻나 |
|---|---|
| 1단 | 코드 이해 |
| 2단 | 설계 논리 (왜 이렇게 했나) |
| 3단 | 대안 비교 (다른 방법은?) |
| 4단 | 반례 대응 (언제 깨지나) |

`said` 문장을 그 표에 대보면:

- *"실패 조건까지 짚었지만 **대안은 제시하지 못했습니다**"* → **2단 통과 · 3단 실패**
- *"선택 이유까지 설명했지만 **어떤 상황에서 깨지는지는 답하지 못했습니다**"* → **3단 통과 · 4단 실패**

즉 `said`는 **2단·3단 도달**을 말하는데 `level`은 **전부 `0`** 입니다.

### 화면이 어떻게 되나

`level: 0`은 저희 화면에서 **"1단조차 통과하지 못함"** 이고, 가장 무거운 문구가 붙습니다.

```
0단  →  "설명이 코드에 닿지 않았어요"
```

그 바로 옆에 *"실패 조건까지 짚었지만…"* 이라는 칭찬 섞인 문장이 놓입니다.
**학생이 읽으면 리포트가 자기 모순을 일으킵니다** — 하나도 못 했다면서 뭘 했다고
설명합니다. 그래서 이 값으로는 TR-04를 붙일 수 없습니다.

### 요청

**어느 쪽이 정본인지** 알려 주세요.

- `level`이 아직 계산되지 않아 `0`으로 나가는 것이라면 → 계산해서 채워 주세요
- 시드 데이터만 그런 것이고 실제 세션을 거치면 정상이라면 → **그렇다고만 알려 주시면**
  저희는 이 값을 신뢰하고 붙이겠습니다 (R8의 테스트 계정이 있으면 저희가 직접 확인합니다)

### 그리고 `level`의 계약이 스펙에 없습니다

```
ConceptReportResponse.level  =>  integer     (설명 없음 · minimum/maximum 없음)
```

**저희는 `0`~`4`로 이해하고 있습니다**(0단 = L1조차 실패, 4단 = 반례 대응까지 통과).
그게 맞으면 `@Schema(minimum = "0", maximum = "4", description = "…")`로 못박아 주세요.
지금은 `-1`이나 `7`이 와도 스펙상 합법이라, 화면이 그걸 그리게 됩니다.

또 `level`이 **required가 아닙니다**(`required: ["asked","isRetryTarget","name","problemId"]`).
`asked: false`(문항 없음)일 때 키가 빠지는 것이라면 맞습니다 — **그 뜻이면 그대로
두시고**, 확인만 부탁드립니다. `asked: true`인데도 빠질 수 있다면 그건 어떤 경우인지
알려 주세요.

## 3. 🔴 R3 — `isRetryTarget`이 `level`과 맞지 않습니다

위 응답에서 세 개념이 **모두 `level: 0`** 인데 재시험 대상은 갈립니다.

| 개념 | `level` | `isRetryTarget` |
|---|---|---|
| 예외 처리와 롤백 전략 | 0 | **`false`** |
| API 응답 계약 설계 | 0 | `true` |
| 영속성 매핑과 지연 로딩 | 0 | `true` |

확정 규칙은 **"불합격(2단 미만) 개념만 재시험"** 입니다. `level: 0`은 전부 2단 미만이니
셋 다 `true`여야 합니다.

`said` 기준으로 보면 오히려 맞아떨어집니다 — 1번은 2단을 통과했으니 대상이 아니고,
2·3번은… 3단 통과라 이것도 대상이 아니어야 합니다. **어느 기준으로도 이 조합은
설명되지 않습니다.**

R2와 같은 원인일 가능성이 높아서 따로 요청하지는 않습니다. **R2를 보실 때 같이
확인만** 부탁드립니다. `isRetryTarget`이 `level`에서 파생되는 값인지, 별도로
저장되는 값인지도 알려 주시면 저희가 화면에서 무엇을 신뢰할지 정할 수 있습니다.

## 4. 🟡 R4 — ZIP으로 낸 학생은 자기가 뭘 냈는지 못 봅니다

`MySubmissionResponse.content`가 **GitHub 제출에서만** 옵니다(스펙 명시).
ZIP 제출이면 실응답이 이렇습니다.

```json
{
  "status": "LOCKED",
  "method": "ZIP_WITH_GITLOG",
  "submittedAt": "2026-07-30T16:59:00Z",
  "submissionId": "f92c9054-…"
}
```

`content`가 없으니 저장소·브랜치·커밋 행이 전부 빠지고, **"제출한 내용" 카드에 채울
것이 없습니다.** 지금은 `method`와 `submittedAt`으로 두 줄만 그리도록 화면을
고쳤습니다 — 카드가 아예 안 뜨던 것보다는 낫지만, 학생이 확인하고 싶은 건
**"내가 올린 그 파일이 맞나"** 입니다.

### 요청

ZIP 제출일 때 `content`에 **파일 이름과 크기**를 넣어 주세요.

```json
"content": { "fileName": "team3-miniproject.zip", "fileSize": 12873421 }
```

`repoUrl`·`branch`와 배타적이어도 됩니다(둘 중 한쪽만 채워짐). 커밋 정보는
git log를 파싱하시는 것 같으니 **`lastCommit`도 ZIP에서 채울 수 있으면** 같이
주시면 좋겠습니다 — 그러면 "제출한 내용" 카드가 두 수단에서 같은 모양이 됩니다.

> 급하지 않습니다. 없어도 화면은 서고, 들어오면 행이 늘어날 뿐입니다.

## 5. 🟡 R5 — `reviewStatus` 실측값 · 19차 R3 후속

19차에서 값 집합을 물었고, 저희가 `NOT_ASSIGNED` · `PENDING` · `COMPLETED` 정도로
추측했습니다. **실제로는 다릅니다.**

| 어디 | 실제 값 |
|---|---|
| `PastRoundResponse.reviewStatus` | `COMPLETED` (3건) · **`SESSION_READY`** (1건) |
| `CurrentRoundResponse.reviewStatus` | **`null`** |

`SESSION_READY`는 저희가 예상하지 못한 값이고, `null`도 옵니다.
`completedReviewCount`와 짝지어 보면 이렇게 읽힙니다.

```
COMPLETED     + count 1  →  다시 보기를 마쳤다
SESSION_READY + count 0  →  다시 볼 수 있는 상태인데 아직 안 했다
null                     →  해당 없음 (현재 회차 · 재시험 대상 아님)
```

**이 읽기가 맞나요?** 그리고 **값 집합 전체**를 알려 주세요 — 위 셋 말고 무엇이 더
있는지(진행 중을 뜻하는 값이 따로 있는지). 확정되면 `@Schema`로 못박아 주시면
enum으로 받겠습니다. 지금은 `string`이라 화면이 오타를 잡지 못합니다.

## 6. 🟡 R6 — 창이 닫혔는데 "이어서 응시"라고 합니다

`trainee01`의 현재 회차 실응답입니다.

```json
"representativeStatus":  "ASSESSMENT_WINDOW_CLOSED",
"defaultActionCode":     "RESUME_ASSESSMENT",
"initialSessionStatus":  "IN_PROGRESS",
"warningCodes":          ["ASSESSMENT_WINDOW_CLOSED"]
```

**응시 창이 닫혔는데 기본 행동이 "이어서 응시"** 입니다. 저희 화면은
`representativeStatus`를 우선해서 CTA를 비활성화하고 `blockedReason`을 띄우고
있습니다 — 그래서 지금 화면은 정상입니다.

다만 두 필드가 반대를 말하면, 나중에 어느 쪽이든 하나가 바뀔 때 화면이 조용히
틀립니다. 그리고 `initialSessionStatus: IN_PROGRESS`가 같이 있어서 **"창이 닫힌
시점에 세션이 열려 있던 상태로 남았다"** 로 읽히는데, 그게 맞나요?

### 요청

**창이 닫힌 회차에서 `defaultActionCode`가 무엇이어야 하는지** 정해 주세요.
저희 생각은 `NONE`(또는 그에 해당하는 값)입니다 — 할 수 있는 행동이 없으니까요.
`RESUME_ASSESSMENT`가 의도된 것이면 **화면이 우선순위를 어떻게 매겨야 하는지**
(어느 필드가 정본인지) 알려 주시면 그대로 따르겠습니다.

> 참고로 저희는 **닫힌 창에 이어하기 버튼을 두지 않습니다.** 세션은 한 번에
> 끝내는 것이 원칙이고, `ASSESSMENT_IN_PROGRESS`는 네트워크 장애로 남은 흔적으로
> 보고 있습니다(카드는 그리되 CTA는 안 엽니다).

## 7. 🟡 R7 — 세션 API 9개 · TR-03만 목으로 남습니다

`사용 불가`인 것들입니다.

GET   /assessment-sessions/{sessionId}/problems/{problemNo}

POST  /assessment-sessions/{sessionId}/hints

17차 Q5에 *"활성화는 배포 일정"* 이라고 답해 주셨습니다. **일정이 잡히면 알려
주세요.** 그때까지 TR-03은 목으로 둡니다 — 화면은 확정 채점 모델(개념 3 × 단계 4 ×
시도 3 · 힌트 2)로 이미 완성돼 있어서, **열리면 `_/api/` 어댑터만 바꿔 붙입니다.**

교육생 4화면 중 **TR-01·TR-02는 붙었고, TR-04는 R2가 풀리면 바로 붙습니다.**
TR-03만 이것들을 기다립니다.

## 8. 🟢 R8 — 테스트 데이터 요청 · 제출 전 상태 계정

**저희 손으로 확인할 수 없는 것이 셋 남았습니다.**

| 항목 | 왜 못 하나 |
|---|---|
| ZIP 업로드 → 접수 → 재조회 | `DRAFT` 회차가 실제로 있어야 합니다 |
| GitHub 탭 잠금 표시 | 제출 폼이 `DRAFT`·`ANALYSIS_FAILED`에서만 뜹니다 |
| 50MB 초과 차단 | 같은 이유 (폼 안에서만 탈 수 있습니다) |

저희 dev 계정에 교육생은 `trainee01` 하나뿐이고, 그 계정의 현재 회차는
`LOCKED`(이해도 확인을 시작해서 잠김)입니다. **제출 화면이 폼을 그리는 경로에
들어갈 방법이 없습니다.** 목을 지웠으니 화면에서 상태를 강제할 수단도 없습니다.

### 요청

**현재 회차가 `DRAFT`(아직 제출 안 함)인 교육생 계정을 하나** 만들어 주세요.

## 9. 🟢 R9 — enum 인라인 1건 잔여

19차 R2를 대부분 반영해 주셔서 **7건 → 1건**입니다.

```
2회 — PENDING | UNVERIFIED | VERIFIED
```

`SubmissionMethod`·`TraineeReleaseStatus` 등은 `$ref`로 잘 빠졌습니다.
**이것 하나만 남았습니다** — 커밋 검증 상태로 보이는데, Java enum이 있으면 같은
방식으로 내보내 주시면 됩니다.

급하지 않습니다. `api:check`가 warn으로만 잡고 생성은 정상입니다.

## 10. 19차 반영 확인 ✅

| 19차 요청 | 결과 |
|---|---|
| **R1** `nullable` 2건 | ✅ 반영. `api:check` **error 2건 → 0건**. 스펙을 커밋하고 연동을 시작했습니다 |
| **R2** enum 인라인 | ✅ 7건 → 1건 (§9) |
| **R3** `reviewStatus` 값 집합 | 🔶 필드는 살아 있지만 아직 `string`입니다 — 실측값을 §5에 정리했습니다 |
| **Q1** `PARTIAL` vs `asked:false` | ⏳ 회신을 아직 못 받았습니다 |

### Q1을 다시 한 번 올립니다

**생성이 실패한 개념도 `asked: false`로 오나요?**

그렇다면 화면이 장애를 *"이 개념은 묻지 않았어요 — 못한 것이 아니에요"* 라고
말하게 됩니다. **학생이 손해를 본 상황에서 괜찮다고 안심시키는** 것이라 그대로
두기 어렵습니다.

이번 실응답은 `completionStatus: FULL` · `missingConceptCount: 0`이라 이 경우가
아니었습니다. **`missingConceptCount`로 갈리는 것이면 그렇다고만** 알려 주시면
그걸로 판정하겠습니다.

그리고 **`PARTIAL`로 끝난 리포트가 나중에 다시 채워질 수 있는지**(기술적 가능성만)
도 함께 부탁드립니다.

## 11. 저희 쪽 상태

```
TR-01 홈       ✅ 실서버 연동 완료
TR-02 제출     ✅ 실서버 연동 완료 (R1·R4·R8이 남은 확인 항목)
TR-04 리포트   ⏳ API는 available — R2가 풀리면 붙입니다
TR-03 세션     ⏳ API 사용 불가 — 목 유지 (R7)
```

`api:check` **error 0건 · warn 6건**(§9의 1건 + 일반 에러코드 5건)으로,
생성·커밋·CI가 모두 통과합니다. **바뀌는 것은 `features/trainee/*/_/api/` 안쪽뿐이고
화면 컴포넌트는 그대로입니다.**

가장 급한 것은 **R2(리포트가 자기 모순을 일으킵니다)** 입니다 — 이것만 TR-04를
막고 있습니다. **R1**은 저희가 임시로 막아 둬서 화면이 지금 틀리지는 않지만, 서버 말과
화면이 어긋난 상태라 오래 두고 싶지 않습니다. **R8(테스트 계정)** 은 만들어 주시는
비용이 가장 작으면서 저희가 못 밟은 경로 셋을 한 번에 열어 줍니다.

나머지는 붙이면서 병행할 수 있습니다.
