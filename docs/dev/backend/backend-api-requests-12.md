## 1. 🔴 R1 — `roundNo`가 요청과 응답에서 다른 뜻입니다

### 관측

`GET /cohorts/{id}/analytics/risk-trainees`를 파라미터 없이 부른 응답입니다.

```
rounds[0]  roundNo = 1   미니프로젝트 6차
rounds[1]  roundNo = 1   미니프로젝트 5차
rounds[2]  roundNo = 1   미니프로젝트 4차
rounds[3]  roundNo = 1   미니프로젝트 3차
rounds[4]  roundNo = 1   미니프로젝트 2차
rounds[5]  roundNo = 1   미니프로젝트 1차
```

**여섯 개가 전부 `1`입니다.** 프로젝트마다 응시 회차가 하나씩이라 **프로젝트 안에서 매긴 번호**로 보입니다.

그런데 **같은 이름의 요청 파라미터는 기수 순번으로 해석됩니다.**

```
?fromRoundNo=2&toRoundNo=4  →  미프 2차 · 3차 · 4차
?fromRoundNo=1&toRoundNo=2  →  미프 1차 · 2차
?fromRoundNo=5&toRoundNo=6  →  미프 5차 · 6차
```

**요청은 `기수의 N번째 회차`, 응답은 `프로젝트의 N번째 응시`** 입니다. 이름이 같아서 처음에는 같은 축인 줄 알았습니다.

### 저희를 문 자리

격자의 **열 키**로 `roundNo`를 썼더니 여섯 열이 전부 같은 키가 됐습니다. React가 행을 뭉개면서 **중복 키 경고 45건**이 떴고, 값이 엉뚱한 열에 들어갔습니다.

지금은 경계에서 두 체계를 잇고 있습니다 — 열 번호는 **정렬 후 자리**로 새로 매기고, 셀은 `assessmentRoundId`로 잇습니다. 돌아가지만 **서버가 준 번호를 못 쓰고 화면이 다시 세는 상태**입니다.

### 요청

**요청 파라미터를 응답 필드와 같은 축으로 맞춰 주세요.** 셋 중 하나면 됩니다.

| | 방식 |
|---|---|
| **ⓐ** | 응답 `rounds[]`에 **기수 순번**을 별도 필드로 추가 (예: `cohortRoundNo`) |
| **ⓑ** | 요청 파라미터 이름을 바꿔 축이 다름을 드러낸다 (예: `fromCohortRoundNo`) |
| **ⓒ** | 응답 `roundNo`를 기수 순번으로 바꾼다 |

**ⓐ를 권합니다.** 두 축이 실제로 둘 다 있는 값이라(한 프로젝트에 응시가 여러 번 생길 수 있다면 프로젝트 안 번호도 필요합니다) 이름을 갈라 두는 편이 정확합니다. ⓒ는 지금 값을 쓰는 다른 화면이 있으면 깨집니다.

> `totalRegisteredRoundCount: 6`은 기수 기준이라 이미 그쪽 축입니다 — 응답 안에서도 두 축이 섞여 있습니다.

## 2. 🟠 R2 — `sameCurriculumOnly=true`면 결과가 사라집니다

```
GET /cohorts/{id}/analytics/cohort-comparison                        → concepts 7건
GET /cohorts/{id}/analytics/cohort-comparison?sameCurriculumOnly=true → concepts 0건
```

9기 ↔ 8기 비교입니다. 기본값(`false`)으로는 7건이 나오고 **모든 행의 교안 버전이 `v1 · 그대로`** 인데, `true`로 켜면 **0건**이 됩니다.

같은 교안 같은 버전인데 "같은 교안만"이 걸러내는 것으로 보입니다 — 판정 기준이 저희가 이해한 것과 다른 것 같습니다.

### 화면 쪽 사정

이 표의 부제가 **`같은 교안 · 같은 개념만`** 입니다(정의서 §5). 즉 화면은 그 조건이 **항상 켜진 것**으로 설명하고 있는데, 실제로 켜면 빈 표가 됩니다.

### 요청

`sameCurriculumOnly`의 **판정 기준**을 알려 주세요. 그리고 위가 의도된 동작이 아니라면 고쳐 주세요.

- 같은 `materialId`인지, 같은 `versionId`인지
- 같은 회차에 쓰였는지까지 보는지

기준이 정해지면 화면이 그 옵션을 켤지, 부제 문구를 바꿀지 정하겠습니다. **지금은 기본값으로 두고 부제를 유지**하고 있습니다.

## 3. 🟡 Q1 — `cohort-comparison`의 `cohortId` 위치

설명문에는 이렇게 적혀 있습니다.

> `cohortId (쿼리, 필수): 기준 기수 ID`

실제 스펙은 **경로 파라미터**입니다(`/cohorts/{cohortId}/analytics/cohort-comparison`). 쿼리로 보내면 400입니다.

같은 오퍼레이션의 `findComparableCohorts`(`/curricula/comparable-cohorts`)는 진짜로 쿼리라, 둘을 나란히 보다가 헷갈렸습니다. **설명문만 고쳐 주시면 됩니다.**

## 5. OP-02 검증 결과 — 두 탭 다 붙었습니다

브라우저에서 눌러 확인했습니다.

| | 결과 |
|---|---|
| 회차 흐름 격자 | ✅ 6열 × 반 8행 · 기수 기준선 · `집계 전`/`시작 전` 구분 · 채점 제외 3종 |
| 부호 색 | ✅ `comparisonToCohort`를 그대로 씁니다 — **화면이 비교하지 않습니다** |
| 정렬 4종 | ✅ `RECENT_ROUND_WORST` · `WORSE_ROUND_COUNT` · `EXCLUSION_COUNT` · `NAME` |
| 회차 범위 | ✅ `fromRoundNo`/`toRoundNo` (R1의 축 문제만 빼면) |
| 팀 계층 | ✅ 기준선이 **그 반**으로 바뀌고 범례도 따라갑니다 |
| 기수 간 비교 | ✅ 개념 7건 · 출처 · 교안 버전 · 변화 판정 |

### 🟢 임계값 하나를 걷어냈습니다

기수 간 비교의 `나아짐/비슷/나빠짐`을 한때 화면이 `|차이| <= 0.2`로 갈랐습니다. **그 숫자가 어느 문서에도 없어서** 화면이 기준을 만드는 상태였는데, 서버가 `changeThreshold`를 갖고 `change.direction`으로 판정까지 해 주어서 그 자리를 없앴습니다. 감사합니다.

### 팀 계층 규칙은 서버 쪽이 맞습니다

`TEAM_LEVEL_PROJECT_REQUIRED`·`TEAM_LEVEL_SINGLE_CLASSROOM_REQUIRED`로 막아 주시는 것을 처음에는 제약으로 봤는데, **팀은 회차마다 다시 짜일 수 있어** 회차를 가로질러 같은 팀으로 추적하는 것이 성립하지 않더군요. 화면을 그 규칙에 맞춰 **툴바에 회차 단일 선택**을 넣었습니다.
