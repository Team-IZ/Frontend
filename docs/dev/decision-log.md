## D1 · 개발 착수: `feature/setup` 브랜치 + `docs/` 재편(plan/screen · handbook)

- **배경:** 목업(화면정의 v8) 단계가 끝나고 프론트엔드 개발이 시작됨. 목업 작업은 `planning` 브랜치에 쌓였고 기본 브랜치 `main`은 아직 Vite 스타터(hello-world). 산출물이 `docs/` 루트에 평평하게 섞여 있어(화면정의 + 방법론 + 구버전 v7 + 프로세스 문서) 개발 브랜치에 그대로 들고 가면 스펙과 잡문서가 구분되지 않음.
- **선택지:** (a) `planning`에서 그대로 개발 계속 (b) `main`에서 `feature/setup` 분기 후 필요한 문서만 이관 (c) 문서는 `planning`에만 두고 개발 브랜치는 순수 코드.
- **판단:** (b). `main`에서 `feature/setup`을 파고, **개발 레퍼런스가 되는 문서만** 이관하며 동시에 폴더를 재편한다.
  - `docs/plan/screen/definition/` — 화면정의 명세 전부(SC-\*, 번호문서, `_parking-lot`) + `_source/`(design-tokens · component-contract). **평면 유지**.
  - `docs/plan/screen/wireframe/` — 와이어프레임 HTML 23개.
  - `docs/handbook/` — 팀 협업 규약.
  - **제외:** 구버전 `docs/screens/`(v7) · `docs/superpowers/`(스펙 제작 프로세스 문서) · 루트 PNG 48장(작업 중 스크린샷) · 기획 단계 방법론·회고 문서. 전부 `planning` 브랜치에 보존.
- **근거·출처:** ① 명세서를 평면으로 유지한 이유 = SC↔번호문서↔`_source` 상호링크 34건이 전부 **같은 폴더 상대링크**라, 하위 폴더로 쪼개면 전량 깨짐(이관 전 grep 검증). ② 와이어를 별도 폴더로 뺀 것은 안전 = 마크다운 링크로 참조되는 곳이 0건(코드스팬 언급뿐). ③ 방법론·회고 문서를 뺀 이유 = 제품 스펙이 아니라 기획 단계 산출물이라 개발 브랜치에 두면 신입이 스펙으로 오독함.
- **경로 갱신 원칙:** **실제 파일을 가리키는 포인터만** 새 경로로 치환. **당시 결정의 기록은 원문 보존** — 화면정의 로그 D4의 "`docs/screen-def-v8/` 신규, 예전 `docs/screens/` 미참조"는 그대로 둔다. 히스토리를 새 경로로 덮어쓰면 결정 기록이 위조되므로.
- **목적·효과:** 개발자가 `docs/plan/screen/`만 보면 "무엇을 만드는가"가, `docs/handbook/`만 보면 "어떻게 일하는가"가 나온다.
- **후속:** 목업 배포(gh-pages, `team-iz.github.io/Frontend/`)와 `planning` 브랜치는 목업 아카이브로 유지하다 폐기. 폐기 전 태그로 박제 권장.

## D2 · 팀 Git 규약: 문서에 적을 것과 기계가 막을 것을 분리

- **배경:** 팀이 정한 Git/PR 규약 원문을 어디에 넣을지(md냐 커밋 시 실행되는 스킬이냐) 질문받음. 원문은 커밋 형식·체크리스트·브랜치 전략·PR 규칙·이슈 기준·충돌·커뮤니케이션이 한 덩어리로 섞여 있었음.
- **선택지:** (a) 원문 그대로 md 한 장 (b) 원문 그대로 AI 작업규약에 삽입 (c) **강제 수단별로 쪼개 배치**.
- **판단:** (c). 규칙을 주제가 아니라 **"무엇이 이걸 강제하는가"**로 나눈다.
  - **기계** — `.env` 금지=`.gitignore` · 커밋 메시지 형식=`commit-msg` 훅 · `console.log`=oxlint · 빌드=GitHub Actions · 직접 push=브랜치 보호 · PR 형식=템플릿
  - **핸드북 `docs/handbook/git-convention.md`** — 사람 판단 영역만(브랜치 전략·작업 흐름·이슈 등록 기준·충돌 예절·리뷰 SLA).
- **근거:** ① 원문 체크리스트 6개 중 5개가 기계로 검증 가능 — "console.log 제거" 체크박스보다 린트 룰 한 줄이 정확하고, 사람이 체크하는 항목은 바쁠 때 가장 먼저 생략된다. ② 원문이 같은 규칙을 **3번 중복** 기재했고 이미 드리프트 시작(`1인 승인` vs `1인 리뷰`, 체크박스 누락 2건) — 규약이 3개면 지켜지는 건 0개라 단일 원천으로 통합.
- **폐기:** "로컬에서 정상 동작 확인" 체크 항목 — 검증 기준이 없어 체크박스로 무의미.
- **발견한 충돌:** 규약 전체가 `develop` 통합 브랜치를 전제하는데 레포에 `develop`가 없었음 → 생성 + 브랜치 보호를 세팅 범위에 편입.
- **목적·효과:** 사람은 판단이 필요한 것만 읽고, 나머지는 커밋·PR 시점에 자동으로 막힌다.

## D3 · 규약 자동화: git 네이티브 훅 + 브랜치별 이슈 번호 자동 부착

- **배경:** [[D2]]에서 "문서에 적으면 무시된다 → 기계가 막아야 한다"고 판단한 것의 구현. 추가로 "커밋마다 이슈 번호를 사람이 타이핑해야 하나"라는 문제 제기.
- **선택지(훅 설치):** (a) husky 도입 (b) **git 네이티브 `core.hooksPath`** (c) 각자 `.git/hooks`에 수동 복사.
- **판단:** (b). `.githooks/`를 레포에 커밋하고 `core.hooksPath`로 가리킨다. husky는 이 정도 검사에 npm 의존성 하나를 더 얹는 것이라 불필요. `package.json`의 `prepare` 스크립트가 `npm install` 시 자동 설정하므로 팀원은 클론 후 별도 조치가 없다. (c)는 버전 관리가 안 되어 사람마다 규칙이 갈린다.
- **선택지(이슈 번호):** (a) 매번 손으로 입력 (b) 브랜치명에 번호를 넣어 파싱(`feature/3-setup`) (c) **`git config branch.<name>.issue`에 1회 등록 → `prepare-commit-msg`가 자동 부착**.
- **판단:** (c). (b)는 규약의 브랜치 네이밍(`feature/login-api`)을 바꿔야 하고, (a)는 누락이 반복된다. (c)는 브랜치 생성 시 한 번만 등록하면 이후 커밋 전부에 `(#N)`이 붙고, 이미 번호가 있으면 존중한다.
- **차단 범위:** 되돌리기 비싼 것만 막는다 — `main`·`develop` 직접 커밋, `.env` 스테이징(`.env.example`류는 허용), **AI 공동저자 trailer**(`Co-Authored-By`·`Generated with`·🤖 — 커밋 저자는 사람). 이슈 미연결은 **경고만** 하고 통과시킨다(오타·포맷팅은 이슈 없이 커밋하는 것이 규약 §3).
- **길이 규칙 해석:** 50자 상한은 **`(#N)`을 제외한 설명** 기준. 훅이 자동 부착하는 메타데이터까지 세면 사용자가 쓴 적 없는 글자로 커밋이 거부되기 때문.
- **검증:** `.githooks/test-hooks.sh` 자체 검사 18케이스(정상 7 · 위반 11) **전량 통과**. 이슈 자동 부착·중복 방지·`.env` 차단은 실제 실행으로 확인.
- **한계(명시):** 로컬 훅은 `--no-verify`로 우회된다. **최종 방어선은 GitHub 브랜치 보호 규칙**이며 이는 레포 설정 사항이라 훅으로 대체 불가.
- **AI 서명 소급 안 함:** 기존 히스토리에 5건 이상 유입됐으나 이미 push된 커밋의 재작성 비용이 크고 다른 브랜치·gh-pages까지 물려 있어 앞으로만 차단.

## D4 · default 브랜치를 `develop`으로 변경

- **배경:** 규약은 "모든 기능은 develop으로 머지"인데 GitHub default가 `main`이었음.
- **판단:** default = `develop`.
- **근거:** ① **`closes #N` 자동 닫힘은 default 브랜치로 머지될 때만 작동한다.** default가 main이면 feature→develop 머지로 이슈가 안 닫혀 승격 전까지 계속 열려 있음 — 규약과 GitHub 동작이 어긋남. ② New PR 기본 base가 develop이 되어 실수로 main에 PR을 넣는 사고가 준다. ③ `main`의 역할이 "프로덕션 릴리스 전용"으로 명확해진다.
- **필수 동반 조치:** default를 옮겼으므로 **`main`·`develop` 둘 다** 브랜치 보호를 건다. 안 그러면 develop이 무방비가 된다.
- **연결:** `docs/handbook/issue-and-branch-online.md` §4·부록.

## D5 · 세팅 1차: 되돌리기 비싼 것부터 (strict · 포매터 · alias · CI)

- **배경:** "팀 협업을 위해 세팅 단계에서 뭘 해야 하나" 질문. 목적은 도구를 채우는 게 아니라 **자유도를 미리 줄이는 것** — 4명이 4가지 방언으로 쓰기 시작하면 되돌릴 수 없다. 판단 기준은 하나: **"나중에 하면 비싼가"**(Type-1/Type-2, 화면정의 로그 D5와 동일 프레임).
- **한 것 (Type-1 — 코드 쌓이기 전에만 쌈):**
  - **`strict: true`**(app·node 양쪽). 지금 켜서 **에러 0건**, 코드가 쌓인 뒤면 수백 건. 실측 확인 후 적용.
  - **Prettier** — 없으면 매 PR이 공백 diff 전쟁이 되어 리뷰가 로직을 못 본다. 설정은 **기존 코드 스타일에 맞춤**(`semi:false`·`singleQuote`) — 포매터 도입으로 생기는 리포맷 diff를 최소화하기 위함.
  - **`@/` path alias**(vite `resolve.alias` + tsconfig `paths` 쌍) — `../../../` 방지. tsc·vite 양쪽에서 실제 import로 해석 검증.
  - **`.editorconfig`** — prettier를 안 돌리는 에디터·비JS 파일 대비.
- **한 것 (Type-2지만 매일 아픈 것):** CI(GitHub Actions) · Node 22 고정(`.nvmrc`+`engines`) · README를 Vite 템플릿 원문에서 팀 온보딩용으로 교체 · PR 템플릿.
- **포매터 적용 범위 — 마크다운 전면 제외:** prettier가 표 셀을 **글자 수 기준**으로 패딩하는데 한글은 표시 폭이 2배라, 스펙 문서 30여 개의 표가 오히려 어긋난다(README에서 실제로 재현·확인). 렌더 결과는 어차피 같으므로 **`**/*.md` 전체 제외**. 포매터는 코드·설정에만 건다.
- **`baseUrl` 제거:** TypeScript 6에서 deprecated(TS5101). `paths`만으로 tsconfig 위치 기준 해석되므로 `ignoreDeprecations`로 덮지 않고 제거하는 쪽을 택함.
- **CI 3단계(format:check · lint · build):** `build`가 `tsc -b && vite build`라 타입 검사를 포함 → typecheck를 따로 돌리지 않는다(중복 제거). **로컬에서 CI와 동일 명령을 전수 실행해 3단계 전부 종료코드 0 확인** 후 커밋.
- **안 한 것 (명시):**
  - **`.env.example`** — 환경변수가 아직 0개. 빈 파일은 "나중을 위한 스캐폴딩"이므로 MSW/API가 붙는 단계에서 첫 변수와 함께 만든다.
  - **Storybook** — 컴포넌트 소비자가 여러 팀이 될 때. 3~4명 규모에 와이어프레임이 이미 스펙 역할을 하므로 유지비만 남는다.
  - **Vitest·E2E** — 테스트할 로직이 아직 없다. 첫 실제 로직(RBAC 게이트·기수 스코프 전파)에서 도입.
  - **폴더 레이어 경계(ui/common/features)** — 빈 디렉터리를 미리 파는 건 스캐폴딩. 실제 컴포넌트가 생기는 디자인 시스템 작업에서 규칙과 함께 확정.
- **이슈 분리:** `#3 [Chore] Project Settings` = `src/`를 건드리지 않는 레포·협업 인프라까지. 디자인 시스템(토큰→Tailwind `@theme`·컴포넌트 3계층·variant 어휘·a11y·RBAC 프리미티브)은 **첫 실제 코드**라 리뷰 포인트가 완전히 달라 별도 이슈로 분리(규약 §4 "1 PR = 1 기능", 파일 10개 이내).
- **연결:** [[D1]] 개발 착수 · [[D2]] 규약 배치 원칙 · [[D3]] 훅 자동화 · `docs/plan/screen/definition/07-frontend-setup-plan.md` 0단계.

## D6 · 리뷰 승인을 강제하지 않는다 (의도적 이탈)

- **배경:** ruleset을 점검하다 규약(§2·§4 "최소 1인 리뷰")과 실제 설정(`required_approving_review_count: 0`)이 어긋난 것을 발견. 규약대로 1로 켤지 물음.
- **판단:** **켜지 않는다. 대신 문서에서 "1인 리뷰" 문구를 걷어내고 이탈임을 명시한다.**
- **근거:** 프론트 인원이 **2명**이라 승인 필수는 곧 "매 PR이 상대 1명에게 병목"이다. 지금은 일정이 빠듯해 그 대기 비용이 리뷰로 얻는 것보다 크다는 판단.
- **대신 하는 것:** 리뷰가 필요한 변경(공용 기반·설계 결정·남의 영역)은 **머지 전에 말로 요청**한다. 규칙이 아니라 판단으로 가져간다.
- **되돌리는 조건:** 인원이 늘거나 일정에 여유가 생기면 승인 1인을 다시 켠다.
- **왜 문구를 지웠나:** 지켜지지 않는 규약을 문서에 남겨두면 **나머지 규약의 신뢰도까지 같이 떨어진다**([[D2]] "규약이 3개면 지켜지는 건 0개"와 같은 이유). 정석이 아님을 아는 상태로 내린 결정이라는 사실 자체를 기록해 둔다 — 몰라서 빠진 것과 알고 뺀 것은 다르다.
- **함께 확인된 것:** ruleset에 `required_status_checks`가 없어 **CI가 빨개도 머지되던 상태**였다. 이건 이탈이 아니라 누락이므로 `verify` 체크를 필수로 걸었다.

## D7 · `.gitattributes`로 줄바꿈을 저장소 차원에서 고정

- **배경:** "`.gitattributes`가 없어 Windows·Mac 사용자가 같은 파일을 저장만 해도 전체가 바뀐 것처럼 보인다"는 지적을 받고 검증.
- **검증 결과:** 지적은 타당하다. 다만 현재 추적 파일 중 **CRLF는 0개**(전부 LF)이고 `core.autocrlf`는 미설정 상태였다.
- **판단:** 지금 넣는다. `* text=auto eol=lf` + 바이너리 확장자 명시.
- **근거:** ① `core.autocrlf`는 **사람마다 다른 로컬 설정**이라 신뢰할 수 없다 — Windows Git 설치 옵션에 따라 갈린다. 저장소 차원 보증은 `.gitattributes`뿐. ② 이미 넣은 `.editorconfig`·`.vscode`의 `eol=lf`는 **에디터** 설정이라 git의 체크아웃/커밋 변환은 막지 못한다. ③ **타이밍:** 지금은 정규화할 파일이 0개라 비용이 파일 1개지만, Windows 팀원이 CRLF를 커밋한 뒤에는 **전 파일을 건드리는 정규화 커밋**이 필요해진다 — 정확히 지적이 우려한 "왜 파일 전체를 고쳤지?" 상황이 된다.
- **검증:** `git add --renormalize .` 결과 변경 0건(공짜 시점 확인). `git check-attr`로 텍스트 파일은 `text=auto eol=lf`, PNG는 `binary set`으로 변환 차단됨을 확인.

## D8 · 이슈·PR 제목은 `[Tag] Title Case`, 커밋은 소문자 명령형

- **배경:** 이슈 제목 컨벤션 요청 — `[Chore] Project Settings`처럼 **의미 있는 단어는 대문자로 시작**하고, 관사·등위접속사·짧은 전치사 같은 무의미한 단어는 소문자.
- **판단:** 요청대로 Title Case. **더해서 PR 제목도 같은 규칙으로 통일**한다(기존 규약은 `[feat] add login page UI` 소문자였음).
- **근거:** 이슈와 PR은 **둘 다 GitHub UI에서 사람이 읽는 제목**이라 다른 규칙을 쓸 이유가 없었다. 반면 커밋 메시지는 소문자 명령형을 유지한다 — git 전통이고 훅이 이미 그렇게 검사하며, 로그를 기계로 훑는 대상이라 성격이 다르다. 경계를 "누가 읽는가"로 그었다.
- **어휘:** 태그는 커밋 type과 동일 — `[Feat]` `[Fix]` `[Refactor]` `[Style]` `[Docs]` `[Chore]` `[Remove]`.
- **강제 수단:** **훅으로 막을 수 없다**(제목은 GitHub 쪽). 이슈 제목을 검사하는 Action은 2명 팀에 잔소리 비용이 더 크다고 보고 만들지 않았다. 대신 **이슈 템플릿의 `title:` 기본값**(`[Fix] `·`[Feat] `)으로 형태를 미리 보여주는 방식을 택했다 — 빈칸보다 강하고 봇 코멘트보다 조용하다.
- **적용:** 템플릿 2개 기본 제목, PR 템플릿 주석, 규약 §3·§4, 이미 올라간 PR #4 제목.
- **부수 발견:** 이 레포는 옛 Projects(classic)가 붙어 있어 `gh pr edit`·`gh issue view`가 GraphQL 에러를 낸다. 제목 수정은 REST(`gh api -X PATCH`)로 우회했다.

## D9 · 디자인 토큰: 1레이어(의미론) + 가드, 컴포넌트는 미룸

- **배경:** 참고용으로 사내 다른 프로젝트(React Native 기반)의 디자인 시스템을 검토. 2레이어(원시 팔레트 → 시맨틱)를 쓸지, 컴포넌트를 먼저 만들지 판단 요청.
- **핵심 비대칭(사용자 지적):** 그 시스템은 **화면 5개를 만든 뒤 추출한 결과물**이다("값은 실화면의 실측 사용 빈도에서 도출"). 우리는 화면이 0개다. 같은 산출물을 시작점으로 복제하면 **추측을 시스템처럼 포장**하게 된다. → 베낄 것은 그들의 *산출물*이 아니라 *방법*(만들고 → 재고 → 뽑고 → 왜인지 적는다).

### 판단 기준
**"화면을 만들어봐야 알 수 있는가?"** — 그렇다면 지금 정하지 않는다. 색은 컴포넌트 구조와 독립적이므로(Button을 어떻게 쪼개든 primary는 `#3a4db8`) 토큰은 지금 확정, 컴포넌트 API는 미룸.

### 레이어 = 1개 (원시 팔레트 층 없음)
검토한 측면과 우선순위: ① 가역성 ② 테마 확장 ③ 디자인 소스 정합 ④ 강제 가능성 ⑤ 인지 부하 ⑥ SOLID ⑦ 변경 전파.

- **① 가역성이 결정적 — 한 방향 문이 아니다.** `@theme` 안에서 `--color-primary: var(--color-blue-600)` 형태의 참조가 동작함을 **빌드로 확인**했다. 나중에 원시 층을 끼워도 컴포넌트(`bg-primary`)는 변경 0건. 되돌릴 수 있으면 "지금 필요한 만큼만" 짓는 게 옳다.
- **② 테마 확장 요구 없음** — 플랫폼 콘솔 설정 탭은 상태·AI예산·보존기간·공개범위뿐이고 **기관별 브랜딩 항목이 없다**. 다크 모드도 스펙에 없다(교육생 세션의 다크 코드패널은 컴포넌트 색이지 테마가 아님). 2레이어의 최강 논거가 해당 없음.
- **③ 디자인 소스 정합** — 우리 SSOT는 역할당 값이 1개로 저작됐다. 원시 팔레트를 만들면 **디자인에 없는 구조를 발명**하는 것. 그쪽은 반대로 디자인 원본에 번호 스케일이 있어 2레이어가 원본을 반영한 것이다.
- **④ 강제 가능성** — 2레이어는 "컴포넌트는 시맨틱만 참조" 규율이 있어야 성립하는데, **참고 프로젝트조차 "가능하면 시맨틱을 먼저"라는 연성 규칙**이라 이미 새고 있다. 강제 못 하는 레이어는 무너지고, 무너진 2레이어는 1레이어보다 나쁘다(개념 2개·규율 0).
- **⑥ SOLID** — DIP(구체 대신 추상 의존) 이득은 컴포넌트가 hex 대신 `bg-primary`를 쓰는 시점에 **이미 달성**된다. 원시 층의 추가 이득은 SRP/OCP인데, 그건 **팔레트가 의미와 독립적으로 변할 때**만 값어치가 있다 — 전담 디자이너가 팔레트를 따로 관리하지 않는 우리 구조에선 발생하지 않는다.
- **전환 트리거를 `index.css` 주석에 명시:** ①다크모드·기관 브랜딩 요구 ②같은 계열 명도 단계 5개 초과(현재 최대 primary 4) ③디자이너의 독립 팔레트 관리.

### 이름 = 역할 기준 (실측)
`text-text-2` 같은 중복을 없애고 역할을 드러냄. 와이어 측정: `--c-text-3` **614회**(47%가 xs·11px 동반 → 캡션·메타), `--c-text-2` **280회**(19% → 보조 본문). → `fg` / `fg-muted` / `fg-subtle`, `bg` → `canvas`. **SSOT 문서도 같이 갱신**했다(코드와 문서가 갈리는 것보다 낫다).

### 간격 의도 레이어는 만들지 않음
참고 프로젝트의 간격 의도 레이어(화면 패딩·요소 간격에 이름을 붙인 것)는 실화면 빈도에서 도출된 것. 우리 와이어는 **지배적 패딩값이 없다**(sp-3/4/5/6 = 27·19·11·3회) → 만들면 존재하지 않는 일관성을 발명하게 된다. Tailwind 기본 스케일을 그대로 쓰고 **컨테이너 폭만** 토큰화(`--container-page`, 와이어 10회 일관).

### 가드 = 코드로 (참고 프로젝트에서 가져온 것)
그 프로젝트의 토큰 검사 스크립트는 **컴포넌트 29개에 하드코딩 hex 0건**이라는 결과로 실효성이 입증됐다. 이걸 본떠 `scripts/check-design.mjs`를 만들되 **bash가 아니라 Node**로 썼다 — `.gitattributes`로 Windows 호환을 챙겨놓고 bash 스크립트를 두면 앞뒤가 안 맞는다.
- 검사 ①하드코딩 hex(토큰 정의 파일만 예외) ②대비 AA 16쌍.
- **가드가 즉시 결함을 잡았다:** `fg-subtle #6b7280`은 흰 배경에서 4.83:1로 통과하지만 **실제 페이지 배경(`canvas` #f4f5f7)에서 4.43:1로 미달**이었다. 수동 검산이 놓친 것을 잡아 `#686f7d`(4.63:1)로 교정. 가드를 만든 이유가 그대로 증명됨.
- CI 3단계 → 4단계(design 추가). 위반 시 종료코드 1, 정상 0을 실제로 확인.

### 컴포넌트를 지금 만들지 않음
3번 반복되기 전엔 추출하지 않는다. 첫 화면에서 뽑은 Button은 두 번째 화면에서 반드시 틀린다. 순서를 이렇게 잡았다:
```
① 토큰 + 가드(이 결정)  → ② 화면 1개를 추상화 없이 끝까지 → ③ 두 번째 화면(중복 노출)
→ ④ 추출  ← 여기서부터 2명 병렬
```
②의 첫 화면은 **교육생 리스트** — 173줄로 가장 단순한데 반복 패턴(표·툴바·페이저·배지·빈상태)을 다 품어 추출 수확이 가장 크다. **병렬 시점이 "공용 컴포넌트 완성 후"가 아니라 "④ 추출 후"로 바뀐다.**

### 그 외 버린 것
TS 객체 토큰(RN은 CSS가 없어 불가피했던 것 — 우리가 하면 토큰이 두 곳에 생겨 drift), `AppText` 강제 래퍼(웹은 CSS 상속이 함), 학습용 장문 주석, 컴포넌트 29개 선제작.

## D10 · 디자인 시스템 카탈로그 페이지 — 그리고 그것이 드러낸 결함 3건

- **배경:** "만든 것을 한 화면에서 다 보고 싶다"는 요청. Storybook은 [[D9]]에서 규모에 안 맞아 제외했다.
- **형태를 두 번 바꿨다.** 처음에 앱 라우트(`/dev/design-system`)로 만들었으나, **정적 HTML이어야 한다**는 지적을 받고 생성물로 바꿨다. 이유가 타당했다 — ① 앱 코드는 검수 후 커밋해야 하는데 문서는 먼저 공유하고 싶었고, ② 팀원이 문서를 보려고 개발 서버를 띄워야 하는 것은 문턱이 높다. 지금은 `npm run doc:design`이 `docs/dev/design-system.html`을 만들고, 브라우저로 바로 열린다(외부 자원 참조 0건 확인).
- **핵심 판단 — 토큰 값을 문서에 적지 않는다.** 값을 하드코딩하면 토큰이 바뀔 때 문서가 조용히 거짓말을 하게 된다. 생성 시점에 `src/index.css`에서 읽어 이름·값 모두 `@theme` 하나에서만 나오게 했다. 가드가 하드코딩 hex를 막는 것과 같은 원칙이다.
- **드리프트를 CI가 막는다.** `--check`는 생성 결과가 커밋된 파일과 다르면 실패한다. 토큰만 고치고 문서를 다시 만들지 않는 것은 반드시 일어나므로 사람에게 맡기지 않는다(토큰 한 글자를 바꿔 종료 코드 1을 실측).
- **만들면서 결함 3건이 드러났다.** 카탈로그가 없었으면 전부 조용히 남았을 것들이다.

### ① Tailwind가 토큰을 `@layer` 안에 넣는다
최상위 `cssRules`만 훑으면 토큰이 **0개** 잡힌다. `:root, :host` 규칙이 `CSSLayerBlockRule` 안에 있어서다. 중첩 규칙까지 내려가도록 고쳤다. 빌드는 통과하므로 렌더해보기 전에는 알 수 없는 종류의 결함이었다.

### ② 문서에 적은 예시 코드가 빌드 CSS에 실렸다
카탈로그에 `--color-blue-600`이 떠서 추적하니, 값이 내가 쓴 hex가 아니라 **Tailwind 기본 팔레트의 oklch 값**이었다. 원인은 `docs/dev/decision-log.md`에 남긴 원시 팔레트 예시 한 줄 — Tailwind v4는 기본적으로 **프로젝트 전체**를 훑어 클래스 후보를 찾으므로 문서의 텍스트까지 스캔 대상이 된다.
- **조치:** 문서를 고치지 않고 **스캔 범위를 좁혔다**(`@import 'tailwindcss' source(none)` + `@source '.'`). 문서는 앞으로도 늘어나므로 원인 쪽을 막는 것이 맞다.
- **효과:** 빌드 CSS 19,666 → **17,265 bytes**. 문서에서 끌려오던 것이 그만큼 있었다.
- 주석을 고치다 같은 함정에 두 번 빠졌다("기본 팔레트 이름을 적지 말 것"이라고 쓰면서 그 이름을 적었다). 스캐너는 주석·문서를 가리지 않는다.

### ③ 정의했는데 방출되지 않는 토큰이 있었다
`success`·`neutral-soft`·`primary-border` 등 5개가 아직 어느 화면도 쓰지 않아 CSS에 실리지 않았다. 카탈로그가 "있는 토큰"이 아니라 "쓰인 토큰"만 보여주면, 새로 합류한 사람이 `success`를 못 찾고 임의 색을 만든다.
- **조치:** `@theme static`으로 전량 방출. 비용은 **175 bytes**로, 발견 가능성이 그 값어치보다 크다.

- **부수 효과:** 문서가 세는 색 개수와 가드가 세는 개수가 일치해 서로를 교차 검증한다. 분류에 안 잡힌 토큰은 "그 외"로 떨어져 눈에 띈다.
- **참고:** ①③은 실행 중 스타일시트를 파싱하던 시절의 결함이다. 정적 생성으로 바꾸면서 `@layer` 문제는 사라졌고(CSS 원본을 직접 읽는다), 미방출 토큰 문제도 사라졌다(`@theme static`은 유지 — 유틸리티 클래스 자체는 여전히 사용된 것만 생성된다). 그러나 ②(문서가 CSS를 오염시킴)는 형태와 무관하게 남는 문제였고 그대로 유효하다.

## D11 · 문서를 협업 자료로 — 정보를 세 층으로 나눈다

- **배경:** 팀원이 이 페이지를 보고 코드를 짤 것이므로 "어떤 경우에 쓰는지"와 "왜 그렇게 정했는지"가 필요하다. 다만 다 펼치면 훑어보기가 안 되고, 다 숨기면 아무도 근거를 안 읽는다.
- **판단 — 읽는 목적이 다르면 층을 나눈다.**

| 층 | 무엇 | 언제 읽나 | 수단 |
|---|---|---|---|
| 1 | 토큰 이름·값 | 무엇이 있는지 훑을 때 | 항상 보임 |
| 2 | 언제 쓰나 + 실제 예 | 코딩하다 잠깐 확인할 때 | 호버·포커스 |
| 3 | 왜 이렇게 정했나 | 합류했거나 규칙을 바꾸려 할 때 | 클릭(`<details>`) |

- **2층을 호버로 한 이유:** 코딩 중 확인은 빈도가 높고 짧다. 클릭이면 흐름이 끊긴다. 단 **호버 전용은 접근성 실패**이므로 카드를 `tabIndex=0`으로 두고 `group-focus`에도 같은 규칙을 걸었다(키보드로 Tab 이동 시 동일하게 열림을 실측 확인). 팝오버는 절대 위치로 겹쳐 띄운다 — 카드가 커지면 격자가 흔들린다.
- **3층을 `<details>`로 한 이유:** 네이티브라 키보드·스크린리더가 기본 동작하고, 접혀 있어도 내용이 문서에 있어 검색·인쇄에 걸린다. 상태 관리 코드도, JavaScript도 필요 없다 — 정적 HTML로 옮기면서 이 선택이 더 값어치를 했다.
- **설명을 `scripts/design-doc-content.mjs`로 분리:** 값은 `@theme`에서 읽고, 설명은 이 파일에서만 온다. **값을 두 곳에 적으면 한쪽이 반드시 낡는다**는 [[D10]]의 원칙을 설명에도 적용했다.
- **문서 구멍이 드러나게 했다:** 설명이 없는 토큰은 팝오버가 없어 눈에 띈다. 현재 우리가 정의한 31개는 전부 설명이 있고, 없는 것은 Tailwind 기본 `white` 하나다.
- **값이 조정된 토큰(4개)에 표시(✎)를 붙였다.** SSOT와 다른 값을 쓰는 이유를 카드에서 바로 알 수 있어야, 팀원이 SSOT 문서를 보고 "왜 다르지"라고 혼란스러워하지 않는다.

### 가드에 예외 표시를 추가했다

문서는 **"이렇게 쓰지 마라"를 보여주려고 그 나쁜 예를 적어야 한다.** 실제로 카탈로그의 금지 예시와 옛 SSOT 값 인용이 가드에 걸렸다.

- **판단:** 예시를 흐리게 쓰는 대신 줄 단위 예외 표시(`design-token-allow`)를 뒀다. 문서에서 반복될 상황이고, 예외 수단이 없으면 사람들이 **규칙 자체를 약화시키는 쪽**으로 간다.
- **표시가 눈에 보이고 grep으로 셀 수 있게** 했다 — 현재 5건(금지 예시 2, 옛 값 인용 3). 이 수가 늘어나면 규칙이 현실과 안 맞는다는 신호다.

## D12 · 셸·라우터 검토 — 참조 구현이 되기 전에 감사한다

- **배경:** 이 코드가 팀의 참조 구현이 된다(팀원이 다르게 짜오면 여기 맞추기로 함). 새 컴포넌트를 얹기 전에 기존 코드를 먼저 감사했다.

### 검토에서 잡은 결함 2건

| # | 무엇 | 왜 문제인가 |
|---|---|---|
| 1 | 미등록 경로 화면이 전역 `location.pathname`을 읽음 | 라우터 상태가 아니라 화면 안에서 경로가 바뀌어도 갱신되지 않는다. **실측 확인** — 주소는 `/second-missing`인데 화면은 `/first-missing`을 계속 보여줬다. `useLocation()`으로 교체 |
