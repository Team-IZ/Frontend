# OP-01 대시보드 — 일어날 수 있는 모든 상황

> **이 화면을 고치기 전에 이 문서를 본다.** 무엇이 일어날 수 있고, 지금 그중 무엇이
> 처리돼 있고, 무엇이 안 돼 있나.
>
> 화면의 설계 근거는 [op-01-dashboard.md](op-01-dashboard.md), 비동기 상태 표준은
> [async-states.md](../async-states.md)가 갖는다. 여기는 **상황 목록과 실측 결과**다.
>
> **이 문서를 만든 절차는 [screen-hardening.md](../screen-hardening.md)에 있다** —
> 다른 화면도 그대로 따라 하면 된다.
>
> 실측 — 2026-08-11 · 운영 계정 · 9기(RUNNING) · 10기(PLANNED) · 실서버.

---

## 0. 왜 이 문서가 필요한가

이 화면은 **조회 하나가 아니다.** 기수를 먼저 묻고, 그다음 셋을 병렬로 부르고, 그중 하나는
안에서 또 둘을 순차로 부른다. 조회 다섯이 각자 성공·실패·지연하므로 **조합이 곱해진다.**

```
useCohortId()        GET /cohorts                     ─┐ 이게 끝나야
                                                       │ 나머지가 시작한다
useDashboard(cohortId)                                ─┘
  ├─ risk      GET /cohorts/{id}/analytics/risk-trainees
  ├─ todos     GET /cohorts/{id}/analytics/actions
  └─ pipeline  GET /cohorts/{id}/projects            ─┐ 순차
               GET /projects/{pid}/class-progress    ─┘
```

한 화면이 **다섯 응답 × (성공/실패/느림) × 데이터 상태**를 견뎌야 한다. 아래는 그것을
축으로 나눈 것이다.

---

## 1. 상황 축 — 무엇이 달라질 수 있나

### 축 A. 기수 스코프

| 값 | 언제 | 지금 화면 |
|---|---|---|
| A1 · 기수가 정해짐 | 정상 | 조회 나감 |
| A2 · 기수 조회 중 | 진입 직후 1.2초 | 제목 + 블록 셋의 스켈레톤 |
| A3 · 기수가 하나도 없음 | 신규 기관 | 「없는 것」 유형 2 |
| A4 · 기수 조회 실패 | 네트워크·5xx | **A3과 같은 문구를 쓴다** ⚠ |
| A5 · 진행 중 기수 없음(전부 PLANNED/CLOSED) | 기수 사이 | 목록 첫 기수를 씀 |

### 축 B. 회차(프로젝트) 상태

| 값 | 언제 | 파이프라인 블록 |
|---|---|---|
| B1 · RUNNING 하나 있음 | 정상 | 그 회차 |
| B2 · RUNNING 없고 PLANNED 있음 | 회차 사이 | 가장 이른 예정 회차 |
| B3 · 전부 CLOSED | 기수 종료 | 마지막 회차 |
| B4 · 회차가 0개 | 기수 막 생성 | ✅ `pending` — 「아직 회차가 없습니다」 |
| B5 · RUNNING이 둘 이상 | 일정 겹침 | `find` 첫 번째 — 무엇을 고른 건지 화면에 안 나옴 |

### 축 C. 집계 상태

| 값 | 언제 | 반 비교 블록 |
|---|---|---|
| C1 · AGGREGATED 회차 있음 | 정상 | 그 회차 기준으로 그림 |
| C2 · 전부 NOT_STARTED | 기수 시작 전 | ✅ `pending` — 「아직 집계된 회차가 없습니다」 |
| C3 · 최신은 미집계, 이전은 집계됨 | 상시 | 이전 기준 + "N차는 미발행" |
| C4 · `riskRate`가 `null` | 집계 전 셀 | `0%`로 그림 ⚠ (0과 없음이 섞임) |

### 축 D. 파이프라인 진행

| 값 | 화면 |
|---|---|
| D1 · 제출 0 | 뒤 단계 `—` · "아직 들어온 제출이 없습니다" |
| D2 · 제출 일부 | `N명 미제출` 중립색 |
| D3 · 마감 지남 + 미제출 있음 | `N명 미제출` **danger** |
| D4 · 분석 실패 팀 있음 | 그 단계 보조줄 + 현황 링크 |
| D5 · 마감(`submissionDueAt`)이 `null` | `stamp` 호출 안 함 — 조건 분기 있음 |
| D6 · 리포트 발행됨 | 마지막 단계 표시 |

### 축 E. 조치 필요

| 값 | 화면 |
|---|---|
| E1 · 0건 | 빈 상태 |
| E2 · 1~4건 | 각 줄 · 유형별 아이콘 |
| E3 · 미배정만 | danger 톤 하나 |
| E4 · 다음 회차 미시작 | 개념 공백 문구가 갈림(`upcomingRoundLabel`) |

**조합 수** — A(5) × B(5) × C(4) × D(6) × E(4) = 2,400. 전부 볼 수는 없으므로 아래
2절에서 **실제로 갈리는 지점**만 추린다.

## 2. 실측 — 지금 실제로 어떤가

### 2-1. ✅ 로딩이 8초였다 — 블록별로 갈랐다

실측(9기, 실서버, 로컬 dev):

```
 1,169ms  GET /cohorts                     ← 이게 끝나야 아래가 시작
 2,016ms  GET .../analytics/risk-trainees  ─┐
 2,105ms  GET .../analytics/actions         │ 병렬
 5,227ms  GET .../projects                 ─┘  ← 느리다
 1,678ms  GET /projects/{id}/class-progress    ← projects 뒤에 순차
────────
 ≈ 8.1초  화면 전체가 스피너 하나
```

세 가지가 겹쳐 있다.

| | 무엇 | 왜 아픈가 |
|---|---|---|
| ① | `/projects`가 **5초** | 파이프라인 블록 하나가 전체를 8초로 만든다 |
| ② | 기수 조회가 **직렬** | 대시보드 조회가 1.2초 뒤에야 시작한다 |
| ③ | 블록 셋이 **한 쿼리** | 1.5초에 온 조치 필요를 6.6초 더 기다린다 |

**③이 가장 아깝다.** 블록별로 실패는 갈라 놨는데(`Block<T>`) **도착은 안 갈라져 있다** —
`Promise.all`이 셋을 묶어 놔서 가장 느린 하나에 맞춰진다. 화면은 이미 블록마다 독립적으로
그릴 수 있게 돼 있으므로, 쿼리를 셋으로 나누면 **조치 필요가 1.5초에 뜬다.**

### 2-2. 🔴 인원이 화면마다 다르다

같은 9기를 세 곳이 다르게 센다.

| 화면 | 값 | 출처 |
|---|---|---|
| 대시보드 머리글 | **196명** | `risk.cohortSummary.traineeCount` |
| 파이프라인 분모 | **208명** | `class-progress.summary.targetTraineeCount` |
| 운영 관리 · 명단 | **224명** | `trainees.cohortTotal` |

**한 화면 안에서도 갈린다** — 머리글이 `196명`인데 바로 아래 파이프라인이 `0/208`이다.
셋 다 뜻이 다를 수는 있지만(등록 / 이번 회차 대상 / 명부 전체), **화면이 그 차이를 한
글자도 설명하지 않는다.** 사용자는 셋 중 무엇이 맞는지 알 수 없다.

> 이건 프론트가 혼자 못 고친다 — **백엔드에 정의를 물어야 한다**(OP 화면 전수 점검이 끝나면 요청서로 나간다).
> 정의가 오면 화면이 라벨로 구분해 쓴다(`196명 등록` · `대상 208명`). **답 전까지 손대지 않는다** —
> 모르는 채 하나로 맞추면 셋 중 둘은 확실히 틀린다.

### 2-3. ✅ 「아직」을 「실패」로 그렸다 (C2 · B4)

10기(PLANNED)에 실제로 물어본 결과:

```
projects        6개 (전부 PLANNED)
risk-trainees   200 · rounds 6개 전부 NOT_STARTED · classes 0 · traineeCount 0
actions         200 · actionCount 0
```

이때 화면은 이렇게 된다.

| 블록 | 지금 문구 | 사실 |
|---|---|---|
| 반 비교 | **"반별 위험 비율을 불러오지 못했습니다" + 다시 시도** | 조회는 200이다. 집계된 회차가 아직 없을 뿐 |
| 머리글 | `0명 · 0반` | 반이 아직 안 만들어진 것 |

**조회는 성공했는데 실패라고 말한다.** 「다시 시도」를 눌러도 회차가 돌기 전에는 영영
같다 — async-states §3-2가 금지한 그 버튼이다. 회차가 0개인 기수(B4)도 같은 경로다.

`toCompare`가 `null`을 돌려주는 것은 **의도된 판단**이었지만(0%를 사실로 그리지 않으려고),
`{ ok: false }`로 떨어뜨리는 순간 그 의도가 "실패"로 바뀌었다.

**고침 — `Block<T>`에 세 번째 상태를 넣었다.**

```ts
type Block<T> =
  | { state: 'ok'; value: T }
  | { state: 'pending'; reason: string }   // 기다리면 채워진다 · 재시도 없음
  | { state: 'failed'; error: unknown }
```

실측(회차 0개 + 집계 회차 없음을 응답 가로채기로 재현):

```
전  ⚠ 이번 회차 진행 상황을 불러오지 못했습니다   [다시 시도]
    ⚠ 반별 위험 비율을 불러오지 못했습니다        [다시 시도]

후  · 아직 회차가 없습니다 — 프로젝트를 만들면 이번 회차 진행이 여기에 보입니다
    · 아직 집계된 회차가 없습니다 — 회차가 끝나고 집계되면 반별 위험 비율이 여기에 쌓입니다
```

**경고 아이콘도 재시도 버튼도 없다.** 눌러도 회차가 돌기 전엔 영영 같기 때문이다.

### 2-4. ✅ 실패 원인을 버렸다

```ts
async function block<T>(load: () => Promise<T>): Promise<Block<T>> {
  try { return { ok: true, value: await load() } }
  catch { return { ok: false } }          // ← 에러가 여기서 사라진다
}
```

`catch`가 원인을 통째로 버려서 **권한 없음·서버 오류·오프라인이 전부 같은 문구**가 됐다.
`errorCopy`가 이 화면에서만 못 쓰이던 이유다.

**고침 — `failed`가 `error`를 들고 있고 `BlockBody`가 `errorCopy`를 부른다.** 실측(조치
필요 500 · 반 비교 403을 동시에 주입):

```
조치 필요   ⚠ 조치 항목을 불러오지 못했습니다        [다시 시도]     ← 500, 재시도가 의미 있다
반 비교     ⚠ 반별 위험 비율을 볼 수 있는 권한이 없습니다            ← 403, 버튼 없음
이번 회차   (정상 렌더)                                            ← 남의 실패에 안 휩쓸린다
```

### 2-5. ✅ 블록 하나를 재시도하면 다섯이 다시 나갔다

「다시 시도」가 `page.refetch()`를 불러서 쿼리가 하나라 **조회 다섯이 전부 다시** 나갔다.
조치 필요만 실패했는데 잘 뜬 파이프라인까지 사라졌다 다시 왔다.

**2-1의 쿼리 분리가 이것도 같이 고쳤다** — `page.retry.todos()`가 그 블록만 다시 부른다.
버튼이 `page.fetching.todos` 동안 `불러오는 중…`으로 잠겨 연타도 막힌다(U2도 같이 해소).

### 2-6. ✅ `riskRate: null`을 `0%`로 그렸다

```ts
const toPercent = (rate) => (rate == null ? 0 : Math.round(rate * 100))
```

실제 응답에 `riskRate: null`이 온다(집계 전 셀). 이걸 `0`으로 만들면 **"위험자 0%"라는
사실을 주장**하는데 실제로는 아직 안 센 것이다.

**고침 — 파생값이 아니라 원인이 되는 값으로 판정한다.** `riskRate`가 `null`인 것은
`eligibleCount`(채점된 사람)가 0일 때이므로, `graded > 0`으로 갈랐다. 안 센 반은
막대를 안 그리고 `— 집계 전`으로 쓴다(이 레포가 이미 6곳에서 쓰는 「없음」 표기).

### 2-7. ✅ 회차 선택 근거가 화면에 없었다 (B5)

`RUNNING`이 둘 이상이면 `find`가 첫 번째를 집는데, **화면은 그것을 골랐다고 말하지 않았다.**

**고침 — 자명하지 않을 때만 밝힌다.** `RoundPipeline.pick`이 `RUNNING`/`PLANNED`/`CLOSED`를
들고 오고, 진행 중인 회차를 고른 것이 아닐 때만 머리줄에 `· 다음 예정 회차` ·
`· 마지막으로 끝난 회차`가 붙는다.

**선택기(사용자가 고르게)를 두지 않는다** — 이 화면의 규칙이 *"여기서 처리하지 않는다,
요약과 링크만"* 이고 선택기는 그 규칙을 깬다. 그리고 진행 중인 회차가 하나면 그게 이번
회차인 것은 자명해서, 정상 케이스에 설명을 붙이면 잔소리가 된다.

### 2-9. ✅ 화면이 다섯 번 움직였다 (레이아웃 시프트)

쿼리를 블록별로 나눈 직후(§2-1) 새로 생긴 문제다. 블록이 각자 도착하는데 **자리를 안 잡고
있어서** 도착할 때마다 아래를 밀어냈다.

```
전   1,413ms  [45, 45, 45]   ← 회색 막대 하나
     4,867ms  [45,260, 45]   ← 조치 필요 도착 · 아래 198px 밀림
     8,692ms  [80,260,325]   ← 이번 회차 도착 · 전체 18px 밀림
     CLS 0.0445 · 이동 3회 · 마지막 이동이 8.7초
```

**8.7초가 가장 나빴다.** 3.9초에 조치 필요를 읽기 시작했는데 5초 뒤에 위에서 뭐가 자라며
읽던 줄이 밀린다 — 읽는 중에 움직이는 것은 다 로딩되고 나서 움직이는 것보다 훨씬 거슬린다.

**고침 두 가지.**

**① 상류를 기다리는 것을 실패로 그렸다.** 기수가 정해지기 전에는 세 조회가 `enabled: false`라
`isFetching`이 거짓이고 그래서 `isLoading`도 거짓이다 — 그걸로 갈랐더니 **진입 직후 1.3초
동안 블록 셋이 전부 «불러오지 못했습니다»** 였다. `isLoading`이 아니라 **값이 있나**로
판정하도록 바꿨다.

**② 블록마다 자기 모양의 스켈레톤**(`BlockSkeleton`). 회색 막대 하나가 아니라 파이프라인은
4단계, 조치 필요는 4행, 반 비교는 반 수만큼 — 높이는 실제 블록에서 재서 박았다
(65px/행 · 31px/행).

```
후   1,673ms  [77,262,298]   ← 올 것과 같은 자리
     7,312ms  [77,260,325]
     CLS 0 · 이동 0회
```

남은 오차는 반 비교의 **한 행**(기본 8행 vs 실제 9반)뿐이고, 그 블록이 맨 아래라 아무것도
밀지 않는다 — 반 수가 그 블록과 **같은 응답**에서 오므로 첫 진입에는 알 수 없다.

**순서를 바꾸는 선택지는 버렸다** — 늦는 블록을 아래로 내리면 정보 위계가 응답 속도에
끌려간다. 조치 필요가 주인공인 것이 이 화면의 설계다.

### 2-10. ✅ 자정을 넘기면 마감 판정이 하루 틀렸다 (T1)

`getToday()`가 마운트 시점에 고정돼, 켜 둔 채 자정을 넘기면 `overdue`가 어제 기준이었다.

**고침 — 이 화면만 `refetchOnWindowFocus`.** 타이머를 두지 않은 이유는 두 가지다.

- **날짜만 고치면 더 헷갈린다** — "날짜는 맞는데 데이터는 어제 것"이 된다. 탭에 돌아왔을 때
  **둘을 같이** 새로 읽는 것이 맞다.
- 보지 않는 탭에서 도는 폴링은 서버만 때린다.

전역 기본값은 `false`이고 그게 맞다(폼을 만지다 돌아오면 입력이 흔들린다) — **이 화면은
조작이 없는 지표판**이라 예외가 성립한다.

### 2-11. ✅ 나가는 길이 데이터보다 먼저 있었다

반 비교 머리줄의 `분석에서 보기 ↗`가 **조회 중·집계 전·실패에도** 떠 있었다. 아무것도 없는
화면에서 그것을 누르면 또 아무것도 없는 화면으로 간다.

이 화면의 규칙이 *"나가는 길은 전부 **데이터에 붙어 있다**"* 인데(OP-01 §5), 이 링크만
**자리에 붙어** 있었다 — 다른 두 블록은 이미 값이 있을 때만 링크를 그리고 있었다.

**고침** — `link={compare ? {...} : undefined}`. 실측: 로딩 중 0개 · 집계 전 0개 ·
정상일 때만 뜬다.

### 2-12. 🔴 로그인부터 대시보드까지 **13.5초** — 4단 직렬 (플로우 관찰)

상태별로는 다 맞았는데(스켈레톤 정상 · CLS 0 · 예외 0) **클릭 순간부터 프레임 단위로**
따라가니 다른 것이 보였다.

```
auth/login          39 →  2144  (2.1초)
members/me        2147 →  3438  (1.3초)   ← 로그인이 끝나야 시작
cohorts           3586 →  5210  (1.6초)   ← me가 끝나야 시작
analytics/*       5234 →  8034  (2.8초)   ─┐ 여기부터는 병렬
projects          5234 → 11266  (6.0초)   ─┘
class-progress   11268 → 13474  (2.2초)   ← projects가 끝나야 시작
──────────────────────────────────────────
                          13.5초
```

화면이 채워지는 순서는 이랬다.

```
   41ms  스켈레톤 셋 (정상)
 5.5초   헤더에 «기수 9기» · 빵부스러기 «› 9기»
 9.0초   조치 필요 · 반 비교
13.0초   이번 회차(파이프라인)
```

**직렬 세 곳이 각각 다른 문제다.**

| | 무엇 | 누구 몫 |
|---|---|---|
| ① | `login` → `me` (1.3초) | **auth 도메인** — 아래 참고 |
| ② | `me` → `cohorts` (1.6초) | ①이 풀리면 같이 당겨진다 |
| ③ | `projects` → `class-progress` (6+2.2초) | **백엔드** — `projects/current` 신설 요청 대상 |

#### ① `members/me`를 기다릴 이유가 있나 — auth 도메인에 확인할 것

`RequireRole`이 *"세션 확인 중엔 아무것도 그리지 않는다"* 로 되어 있어(깜빡임 방지 —
판단 자체는 맞다), **`/members/me` 응답 전에는 대시보드가 마운트되지 않는다.** 그래서
`cohorts` 조회가 1.3초 뒤에야 시작한다.

그런데 **로그인 응답에 이미 다 있다.**

```
login 응답  memberId · email · name · role · organizationId · redirectPath
me 응답     memberId · email · name · role · organizationId · status · emailDomain
                                                              ~~~~~~~~~~~~~~~~~~~~
                                                              me가 더 주는 것은 이 둘뿐
```

대시보드는 `status`·`emailDomain`을 쓰지 않는다. **로그인 직후 그 값들을 세션에 미리
심으면 `me`를 기다릴 필요가 없다**(또는 병렬로 부른다).

⚠ **`features/auth`는 다른 레포(`IZ-frontend`)가 맡는 영역이라 여기서 고치지 않는다.**
전 화면 첫 진입에 1.3초씩 붙는 문제이므로 그쪽에 알린다.

### 2-13. ✅ 헤더가 「기수 7기」라고 거짓말했다 (플로우 관찰)

진입 직후 헤더 스위처가 **`기수 7기`** 로 뜬 뒤 잠시 후 `9기`로 바뀌었다.
`ConsoleShell`의 자리표시자(`PLACEHOLDER_COHORT = '7기'`)가 기본값이라, 화면이
`cohort={cohortName}`으로 `undefined`를 넘기는 동안 그 값이 그려진 것이다.

**오퍼레이터 5화면 전부 그랬다.**

**고침 — `cohort={cohortName ?? ''}`.** `''`가 이미 「스코프 자리를 그리지 않는다」의
계약값이라(prop 주석) **공용 파일은 건드리지 않았다.** 모르면 안 그리는 편이 틀린 기수를
말하는 것보다 낫다.

> 남은 것 — 칩이 **없다가 생긴다**(5.5초). 헤더 안 가로 이동이라 CLS에는 안 잡히지만,
> 자리를 잡아 두는 편이 더 낫다. 공용 셸 수정이라 저쪽과 조율이 필요하다.

### 2-14. ✅ 블록이 **랜덤하게** 「불러오지 못했습니다」가 됐다 (플로우 관찰)

새로고침할 때마다 「이번 회차」·「반 비교」 중 아무거나 실패했다. **재현이 확률이라
«안 뜨네»가 증명이 못 됐다** — 코드에서 원인 후보를 찾아 막아야 했다.

**원인 — CORS 프리플라이트가 502.** 브라우저는 `Authorization`이 붙은 요청 앞에 `OPTIONS`를
먼저 보내는데, 조회 셋을 동시에 쏘면 **프리플라이트 셋도 동시에** 나가고 프록시가 둘을
죽인다(3회 반복 모두 `502/502/200`). 프리플라이트가 죽으면 브라우저는 **본 요청을 아예
보내지 않는다** — `net::ERR_FAILED`다.

**두 번 헛짚었다.**

| 가설 | 왜 틀렸나 |
|---|---|
| App Runner가 자고 있다 | 로그상 그 시각 `RUNNING` · 에러 없음 |
| 502를 재시도로 잡으면 된다 | `net::ERR_FAILED`는 **`status: 0`** 이라 `status >= 500`에 안 걸린다 |

**고침 — 네트워크 실패도 재시도 + 흔들림.**

```ts
retry: (count, error) =>
  isApiError(error) && (error.status >= 500 || error.isNetwork) && count < 3,
retryDelay: (count) => 400 * 2 ** count + Math.random() * 400,
```

**흔들림이 핵심이다** — 동시에 죽은 요청들이 같은 순간에 재시도하면 또 겹친다.

실측: 재시도 전 3/4 실패 → **후 4/4 정상.** 네트워크 로그에 `ERR_FAILED → 재요청 → 200`이
그대로 찍힌다.

> ⚠ **증상 완화다.** 실패할 때마다 최대 4초가 더 붙는다. 근본은 프록시 쪽이라
> **요청서로 나간다**(OP 전수 점검이 끝나면) — 프리플라이트를 Lambda까지 태우지 않으면
> 동시 호출이 절반이 된다.
>
> `main.tsx`는 **저쪽 레포와 공유하는 파일**이다. 다만 같은 프록시를 쓰므로 auth·슈퍼어드민도
> 같은 실패를 맞고 있었을 것이다 — 알리고 넣었다.

### 2-8. ✅ 잘 돼 있어 건드리지 않는 것

- **블록 단위 실패 격리**(`Block<T>` · `BlockBody`) — 하나가 죽어도 나머지를 그린다
- **제목 줄이 조회를 안 기다린다** — 도착해도 페이지가 안 밀린다(4단계에서 고침)
- **마감이 판별선** — 같은 `19명 미제출`을 마감 전/후로 색이 갈린다
- **UTC 마감을 로컬로 파싱** — `split('T')`였으면 KST 23:59가 14:59로 보였다
- **분석 실패는 팀 수** — 단위가 명→팀→명으로 튀지 않게 단계 밖으로 내림
- **없음과 0** — 제출 전 뒤 단계를 `—`로
