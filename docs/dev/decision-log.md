# 개발 결정 기록

> 프론트엔드 **개발** 과정의 결정과 그 목적·근거. 팀에 "왜 이렇게 했는가"를 그대로 전달하기 위한 문서.
> 새 결정이 나올 때마다 아래에 append.
>
> **화면 설계 결정은 여기가 아니다** — `docs/plan/screen/definition/01-decision-log.md`(기획 단계, D1~D131)에 있다.
> 그쪽을 가리킬 때는 번호가 겹치므로 **"화면정의 로그 D4"**처럼 출처를 명시한다.
>
> **한 화면을 만들며 내린 결정도 여기가 아니다** — 화면 문서가 갖는다(`op-01-dashboard.md` ·
> `op-06-admin.md` · `mg-04-brief.md` …). 여기 남는 것은 **여러 화면에 걸치는
> 것**(구조·규약·도구)뿐이다.

## 어디에 적는가 — 판정 기준

**한 화면·한 기능의 구현 세부는 이 파일에 적지 않는다.** 여기 남길지 아닌지는 한 가지로 가른다:

> **"이 화면을 안 만드는 사람도 읽어야 하는가?"** — 아니면 같은 폴더의 그 화면 문서로.

| | 여기(decision-log) | 화면 문서(`op-*.md` · `mg-*.md`) |
|---|---|---|
| 무엇 | 구조·규약·도구·공용 컴포넌트·여러 화면에 걸치는 패턴 | 그 화면의 레이아웃·컬럼·모달·목 데이터·정의서와 다르게 정한 것·그 화면에서만 난 버그 |
| 번호 | `D1`, `D2` … | 화면코드 + 일련번호 — `OP06-1` · `MG04-1` |
| 예 | D9 토큰 · D15 레이어 린트 · D23 세션 격리 · D24 공용 Checkbox | OP06-3 명단 헤더 수 · MG08-6 독촉 모달 · MG02-1 히트맵 목 설계 |

- 한 화면 결정이 3개를 넘으면 그 시점에 `docs/dev/<화면코드>-<이름>.md`를 만들어 옮긴다(기존 `op-01-dashboard.md`·`op-06-admin.md`와 같은 자리·같은 형식). 같은 화면 문서가 이미 있으면 새로 만들지 말고 거기 합친다.
- **번호는 문서마다 따로, 1부터.** 코드 주석에서 가리킬 때는 `OP06-3`처럼 접두어까지 쓴다 — 접두어가 곧 어느 문서인지다.
- 화면 문서 목록은 [README.md](README.md)에 있다.

## D1 · 개발 착수: `feature/setup` 브랜치 + `docs/` 재편(plan/screen · handbook)

- **배경:** 목업(화면정의 v8) 단계가 끝나고 프론트엔드 개발이 시작됨. 목업 작업은 `planning` 브랜치에 쌓였고 기본 브랜치 `main`은 아직 Vite 스타터(hello-world). 산출물이 `docs/` 루트에 평평하게 섞여 있어(화면정의 + 방법론 + 구버전 v7 + 프로세스 문서) 개발 브랜치에 그대로 들고 가면 스펙과 잡문서가 구분되지 않음.
- **선택지:** (a) `planning`에서 그대로 개발 계속 (b) `main`에서 `feature/setup` 분기 후 필요한 문서만 이관 (c) 문서는 `planning`에만 두고 개발 브랜치는 순수 코드.
- **판단:** (b). `main`에서 `feature/setup`을 파고, **개발 레퍼런스가 되는 문서만** 이관하며 동시에 폴더를 재편한다.
  - `docs/plan/screen/definition/` — 화면정의 명세 전부(SC-\*, 번호문서, `_parking-lot`) + `_source/`(design-tokens · component-contract). **평면 유지**.
  - `docs/plan/screen/wireframe/` — 와이어프레임 HTML 23개.
  - `docs/handbook/` — 팀 협업 규약.
  - **제외:** 구버전 `docs/screens/`(v7) · `docs/superpowers/`(스펙 제작 프로세스 문서) · 루트 PNG 48장(작업 중 스크린샷) · 기획 단계 방법론·회고 문서. 전부 `planning` 브랜치에 보존.
- **근거·출처:** ① 명세서를 평면으로 유지한 이유 = SC↔번호문서↔`_source` 상호링크 34건이 전부 **같은 폴더 상대링크**라, 하위 폴더로 쪼개면 전량 깨짐(이관 전 grep 검증). ② 와이어를 별도 폴더로 뺀 것은 안전 = 마크다운 링크로 참조되는 곳이 0건(코드스팬 언급뿐). ③ 방법론·회고 문서를 뺀 이유 = 제품 스펙이 아니라 기획 단계 산출물이라 개발 브랜치에 두면 신입이 스펙으로 오독함.
- **경로 갱신 원칙:** **실제 파일을 가리키는 포인터만** 새 경로로 치환. **당시 결정의 기록은 원문 보존** — 화면정의 로그 D4의 "`docs/screen-def-v8/` 신규, 예전 `docs/screens/` 미참조"는 그대로 둔다. 히스토리를 새 경로로 덮어쓰면 결정 기록이 위조되므로.
- **목적·효과:** 개발자가 `docs/plan/screen/`만 보면 "무엇을 만드는가"가, `docs/handbook/`만 보면 "어떻게 일하는가"가 나온다.
- **후속:** 목업 배포(gh-pages, `team-iz.github.io/Frontend/`)와 `planning` 브랜치는 목업 아카이브로 유지하다 폐기. 폐기 전 태그로 박제 권장.

## D2 · 팀 Git 규약: 문서에 적을 것과 기계가 막을 것을 분리

- **배경:** 팀이 정한 Git/PR 규약 원문을 어디에 넣을지(md냐 커밋 시 실행되는 스킬이냐) 질문받음. 원문은 커밋 형식·체크리스트·브랜치 전략·PR 규칙·이슈 기준·충돌·커뮤니케이션이 한 덩어리로 섞여 있었음.
- **선택지:** (a) 원문 그대로 md 한 장 (b) 원문 그대로 AI 작업규약에 삽입 (c) **강제 수단별로 쪼개 배치**.
- **판단:** (c). 규칙을 주제가 아니라 **"무엇이 이걸 강제하는가"**로 나눈다.
  - **기계** — `.env` 금지=`.gitignore` · 커밋 메시지 형식=`commit-msg` 훅 · `console.log`=oxlint · 빌드=GitHub Actions · 직접 push=브랜치 보호 · PR 형식=템플릿
  - **핸드북 `docs/handbook/git-convention.md`** — 사람 판단 영역만(브랜치 전략·작업 흐름·이슈 등록 기준·충돌 예절·리뷰 SLA).
- **근거:** ① 원문 체크리스트 6개 중 5개가 기계로 검증 가능 — "console.log 제거" 체크박스보다 린트 룰 한 줄이 정확하고, 사람이 체크하는 항목은 바쁠 때 가장 먼저 생략된다. ② 원문이 같은 규칙을 **3번 중복** 기재했고 이미 드리프트 시작(`1인 승인` vs `1인 리뷰`, 체크박스 누락 2건) — 규약이 3개면 지켜지는 건 0개라 단일 원천으로 통합.
- **폐기:** "로컬에서 정상 동작 확인" 체크 항목 — 검증 기준이 없어 체크박스로 무의미.
- **발견한 충돌:** 규약 전체가 `develop` 통합 브랜치를 전제하는데 레포에 `develop`가 없었음 → 생성 + 브랜치 보호를 세팅 범위에 편입.
- **목적·효과:** 사람은 판단이 필요한 것만 읽고, 나머지는 커밋·PR 시점에 자동으로 막힌다.

## D3 · 규약 자동화: git 네이티브 훅 + 브랜치별 이슈 번호 자동 부착

- **배경:** [[D2]]에서 "문서에 적으면 무시된다 → 기계가 막아야 한다"고 판단한 것의 구현. 추가로 "커밋마다 이슈 번호를 사람이 타이핑해야 하나"라는 문제 제기.
- **선택지(훅 설치):** (a) husky 도입 (b) **git 네이티브 `core.hooksPath`** (c) 각자 `.git/hooks`에 수동 복사.
- **판단:** (b). `.githooks/`를 레포에 커밋하고 `core.hooksPath`로 가리킨다. husky는 이 정도 검사에 npm 의존성 하나를 더 얹는 것이라 불필요. `package.json`의 `prepare` 스크립트가 `npm install` 시 자동 설정하므로 팀원은 클론 후 별도 조치가 없다. (c)는 버전 관리가 안 되어 사람마다 규칙이 갈린다.
- **선택지(이슈 번호):** (a) 매번 손으로 입력 (b) 브랜치명에 번호를 넣어 파싱(`feature/3-setup`) (c) **`git config branch.<name>.issue`에 1회 등록 → `prepare-commit-msg`가 자동 부착**.
- **판단:** (c). (b)는 규약의 브랜치 네이밍(`feature/login-api`)을 바꿔야 하고, (a)는 누락이 반복된다. (c)는 브랜치 생성 시 한 번만 등록하면 이후 커밋 전부에 `(#N)`이 붙고, 이미 번호가 있으면 존중한다.
- **차단 범위:** 되돌리기 비싼 것만 막는다 — `main`·`develop` 직접 커밋, `.env` 스테이징(`.env.example`류는 허용), **AI 공동저자 trailer**(`Co-Authored-By`·`Generated with`·🤖 — 커밋 저자는 사람). 이슈 미연결은 **경고만** 하고 통과시킨다(오타·포맷팅은 이슈 없이 커밋하는 것이 규약 §3).
- **길이 규칙 해석:** 50자 상한은 **`(#N)`을 제외한 설명** 기준. 훅이 자동 부착하는 메타데이터까지 세면 사용자가 쓴 적 없는 글자로 커밋이 거부되기 때문.
- **검증:** `.githooks/test-hooks.sh` 자체 검사 18케이스(정상 7 · 위반 11) **전량 통과**. 이슈 자동 부착·중복 방지·`.env` 차단은 실제 실행으로 확인.
- **한계(명시):** 로컬 훅은 `--no-verify`로 우회된다. **최종 방어선은 GitHub 브랜치 보호 규칙**이며 이는 레포 설정 사항이라 훅으로 대체 불가.
- **AI 서명 소급 안 함:** 기존 히스토리에 5건 이상 유입됐으나 이미 push된 커밋의 재작성 비용이 크고 다른 브랜치·gh-pages까지 물려 있어 앞으로만 차단.

## D4 · default 브랜치를 `develop`으로 변경

- **배경:** 규약은 "모든 기능은 develop으로 머지"인데 GitHub default가 `main`이었음.
- **판단:** default = `develop`.
- **근거:** ① **`closes #N` 자동 닫힘은 default 브랜치로 머지될 때만 작동한다.** default가 main이면 feature→develop 머지로 이슈가 안 닫혀 승격 전까지 계속 열려 있음 — 규약과 GitHub 동작이 어긋남. ② New PR 기본 base가 develop이 되어 실수로 main에 PR을 넣는 사고가 준다. ③ `main`의 역할이 "프로덕션 릴리스 전용"으로 명확해진다.
- **필수 동반 조치:** default를 옮겼으므로 **`main`·`develop` 둘 다** 브랜치 보호를 건다. 안 그러면 develop이 무방비가 된다.
- **연결:** `docs/handbook/issue-and-branch-online.md` §4·부록.

## D5 · 세팅 1차: 되돌리기 비싼 것부터 (strict · 포매터 · alias · CI)

- **배경:** "팀 협업을 위해 세팅 단계에서 뭘 해야 하나" 질문. 목적은 도구를 채우는 게 아니라 **자유도를 미리 줄이는 것** — 4명이 4가지 방언으로 쓰기 시작하면 되돌릴 수 없다. 판단 기준은 하나: **"나중에 하면 비싼가"**(Type-1/Type-2, 화면정의 로그 D5와 동일 프레임).
- **한 것 (Type-1 — 코드 쌓이기 전에만 쌈):**
  - **`strict: true`**(app·node 양쪽). 지금 켜서 **에러 0건**, 코드가 쌓인 뒤면 수백 건. 실측 확인 후 적용.
  - **Prettier** — 없으면 매 PR이 공백 diff 전쟁이 되어 리뷰가 로직을 못 본다. 설정은 **기존 코드 스타일에 맞춤**(`semi:false`·`singleQuote`) — 포매터 도입으로 생기는 리포맷 diff를 최소화하기 위함.
  - **`@/` path alias**(vite `resolve.alias` + tsconfig `paths` 쌍) — `../../../` 방지. tsc·vite 양쪽에서 실제 import로 해석 검증.
  - **`.editorconfig`** — prettier를 안 돌리는 에디터·비JS 파일 대비.
- **한 것 (Type-2지만 매일 아픈 것):** CI(GitHub Actions) · Node 22 고정(`.nvmrc`+`engines`) · README를 Vite 템플릿 원문에서 팀 온보딩용으로 교체 · PR 템플릿.
- **포매터 적용 범위 — 마크다운 전면 제외:** prettier가 표 셀을 **글자 수 기준**으로 패딩하는데 한글은 표시 폭이 2배라, 스펙 문서 30여 개의 표가 오히려 어긋난다(README에서 실제로 재현·확인). 렌더 결과는 어차피 같으므로 **`**/*.md` 전체 제외**. 포매터는 코드·설정에만 건다.
- **`baseUrl` 제거:** TypeScript 6에서 deprecated(TS5101). `paths`만으로 tsconfig 위치 기준 해석되므로 `ignoreDeprecations`로 덮지 않고 제거하는 쪽을 택함.
- **CI 3단계(format:check · lint · build):** `build`가 `tsc -b && vite build`라 타입 검사를 포함 → typecheck를 따로 돌리지 않는다(중복 제거). **로컬에서 CI와 동일 명령을 전수 실행해 3단계 전부 종료코드 0 확인** 후 커밋.
- **안 한 것 (명시):**
  - **`.env.example`** — 환경변수가 아직 0개. 빈 파일은 "나중을 위한 스캐폴딩"이므로 MSW/API가 붙는 단계에서 첫 변수와 함께 만든다.
  - **Storybook** — 컴포넌트 소비자가 여러 팀이 될 때. 3~4명 규모에 와이어프레임이 이미 스펙 역할을 하므로 유지비만 남는다.
  - **Vitest·E2E** — 테스트할 로직이 아직 없다. 첫 실제 로직(RBAC 게이트·기수 스코프 전파)에서 도입.
  - **폴더 레이어 경계(ui/common/features)** — 빈 디렉터리를 미리 파는 건 스캐폴딩. 실제 컴포넌트가 생기는 디자인 시스템 작업에서 규칙과 함께 확정.
- **이슈 분리:** `#3 [Chore] Project Settings` = `src/`를 건드리지 않는 레포·협업 인프라까지. 디자인 시스템(토큰→Tailwind `@theme`·컴포넌트 3계층·variant 어휘·a11y·RBAC 프리미티브)은 **첫 실제 코드**라 리뷰 포인트가 완전히 달라 별도 이슈로 분리(규약 §4 "1 PR = 1 기능", 파일 10개 이내).
- **연결:** [[D1]] 개발 착수 · [[D2]] 규약 배치 원칙 · [[D3]] 훅 자동화 · `docs/plan/screen/definition/07-frontend-setup-plan.md` 0단계.

## D6 · 리뷰 승인을 강제하지 않는다 (의도적 이탈)

- **배경:** ruleset을 점검하다 규약(§2·§4 "최소 1인 리뷰")과 실제 설정(`required_approving_review_count: 0`)이 어긋난 것을 발견. 규약대로 1로 켤지 물음.
- **판단:** **켜지 않는다. 대신 문서에서 "1인 리뷰" 문구를 걷어내고 이탈임을 명시한다.**
- **근거:** 프론트 인원이 **2명**이라 승인 필수는 곧 "매 PR이 상대 1명에게 병목"이다. 지금은 일정이 빠듯해 그 대기 비용이 리뷰로 얻는 것보다 크다는 판단.
- **대신 하는 것:** 리뷰가 필요한 변경(공용 기반·설계 결정·남의 영역)은 **머지 전에 말로 요청**한다. 규칙이 아니라 판단으로 가져간다.
- **되돌리는 조건:** 인원이 늘거나 일정에 여유가 생기면 승인 1인을 다시 켠다.
- **왜 문구를 지웠나:** 지켜지지 않는 규약을 문서에 남겨두면 **나머지 규약의 신뢰도까지 같이 떨어진다**([[D2]] "규약이 3개면 지켜지는 건 0개"와 같은 이유). 정석이 아님을 아는 상태로 내린 결정이라는 사실 자체를 기록해 둔다 — 몰라서 빠진 것과 알고 뺀 것은 다르다.
- **함께 확인된 것:** ruleset에 `required_status_checks`가 없어 **CI가 빨개도 머지되던 상태**였다. 이건 이탈이 아니라 누락이므로 `verify` 체크를 필수로 걸었다.

## D7 · `.gitattributes`로 줄바꿈을 저장소 차원에서 고정

- **배경:** "`.gitattributes`가 없어 Windows·Mac 사용자가 같은 파일을 저장만 해도 전체가 바뀐 것처럼 보인다"는 지적을 받고 검증.
- **검증 결과:** 지적은 타당하다. 다만 현재 추적 파일 중 **CRLF는 0개**(전부 LF)이고 `core.autocrlf`는 미설정 상태였다.
- **판단:** 지금 넣는다. `* text=auto eol=lf` + 바이너리 확장자 명시.
- **근거:** ① `core.autocrlf`는 **사람마다 다른 로컬 설정**이라 신뢰할 수 없다 — Windows Git 설치 옵션에 따라 갈린다. 저장소 차원 보증은 `.gitattributes`뿐. ② 이미 넣은 `.editorconfig`·`.vscode`의 `eol=lf`는 **에디터** 설정이라 git의 체크아웃/커밋 변환은 막지 못한다. ③ **타이밍:** 지금은 정규화할 파일이 0개라 비용이 파일 1개지만, Windows 팀원이 CRLF를 커밋한 뒤에는 **전 파일을 건드리는 정규화 커밋**이 필요해진다 — 정확히 지적이 우려한 "왜 파일 전체를 고쳤지?" 상황이 된다.
- **검증:** `git add --renormalize .` 결과 변경 0건(공짜 시점 확인). `git check-attr`로 텍스트 파일은 `text=auto eol=lf`, PNG는 `binary set`으로 변환 차단됨을 확인.

## D8 · 이슈·PR 제목은 `[Tag] Title Case`, 커밋은 소문자 명령형

- **배경:** 이슈 제목 컨벤션 요청 — `[Chore] Project Settings`처럼 **의미 있는 단어는 대문자로 시작**하고, 관사·등위접속사·짧은 전치사 같은 무의미한 단어는 소문자.
- **판단:** 요청대로 Title Case. **더해서 PR 제목도 같은 규칙으로 통일**한다(기존 규약은 `[feat] add login page UI` 소문자였음).
- **근거:** 이슈와 PR은 **둘 다 GitHub UI에서 사람이 읽는 제목**이라 다른 규칙을 쓸 이유가 없었다. 반면 커밋 메시지는 소문자 명령형을 유지한다 — git 전통이고 훅이 이미 그렇게 검사하며, 로그를 기계로 훑는 대상이라 성격이 다르다. 경계를 "누가 읽는가"로 그었다.
- **어휘:** 태그는 커밋 type과 동일 — `[Feat]` `[Fix]` `[Refactor]` `[Style]` `[Docs]` `[Chore]` `[Remove]`.
- **강제 수단:** **훅으로 막을 수 없다**(제목은 GitHub 쪽). 이슈 제목을 검사하는 Action은 2명 팀에 잔소리 비용이 더 크다고 보고 만들지 않았다. 대신 **이슈 템플릿의 `title:` 기본값**(`[Fix] `·`[Feat] `)으로 형태를 미리 보여주는 방식을 택했다 — 빈칸보다 강하고 봇 코멘트보다 조용하다.
- **적용:** 템플릿 2개 기본 제목, PR 템플릿 주석, 규약 §3·§4, 이미 올라간 PR #4 제목.
- **부수 발견:** 이 레포는 옛 Projects(classic)가 붙어 있어 `gh pr edit`·`gh issue view`가 GraphQL 에러를 낸다. 제목 수정은 REST(`gh api -X PATCH`)로 우회했다.

## D9 · 디자인 토큰: 1레이어(의미론) + 가드, 컴포넌트는 미룸

- **배경:** 참고용으로 사내 다른 프로젝트(React Native 기반)의 디자인 시스템을 검토. 2레이어(원시 팔레트 → 시맨틱)를 쓸지, 컴포넌트를 먼저 만들지 판단 요청.
- **핵심 비대칭(사용자 지적):** 그 시스템은 **화면 5개를 만든 뒤 추출한 결과물**이다("값은 실화면의 실측 사용 빈도에서 도출"). 우리는 화면이 0개다. 같은 산출물을 시작점으로 복제하면 **추측을 시스템처럼 포장**하게 된다. → 베낄 것은 그들의 *산출물*이 아니라 *방법*(만들고 → 재고 → 뽑고 → 왜인지 적는다).

### 판단 기준
**"화면을 만들어봐야 알 수 있는가?"** — 그렇다면 지금 정하지 않는다. 색은 컴포넌트 구조와 독립적이므로(Button을 어떻게 쪼개든 primary는 `#3a4db8`) 토큰은 지금 확정, 컴포넌트 API는 미룸.

### 레이어 = 1개 (원시 팔레트 층 없음)
검토한 측면과 우선순위: ① 가역성 ② 테마 확장 ③ 디자인 소스 정합 ④ 강제 가능성 ⑤ 인지 부하 ⑥ SOLID ⑦ 변경 전파.

- **① 가역성이 결정적 — 한 방향 문이 아니다.** `@theme` 안에서 `--color-primary: var(--color-blue-600)` 형태의 참조가 동작함을 **빌드로 확인**했다. 나중에 원시 층을 끼워도 컴포넌트(`bg-primary`)는 변경 0건. 되돌릴 수 있으면 "지금 필요한 만큼만" 짓는 게 옳다.
- **② 테마 확장 요구 없음** — 플랫폼 콘솔 설정 탭은 상태·AI예산·보존기간·공개범위뿐이고 **기관별 브랜딩 항목이 없다**. 다크 모드도 스펙에 없다(교육생 세션의 다크 코드패널은 컴포넌트 색이지 테마가 아님). 2레이어의 최강 논거가 해당 없음.
- **③ 디자인 소스 정합** — 우리 SSOT는 역할당 값이 1개로 저작됐다. 원시 팔레트를 만들면 **디자인에 없는 구조를 발명**하는 것. 그쪽은 반대로 디자인 원본에 번호 스케일이 있어 2레이어가 원본을 반영한 것이다.
- **④ 강제 가능성** — 2레이어는 "컴포넌트는 시맨틱만 참조" 규율이 있어야 성립하는데, **참고 프로젝트조차 "가능하면 시맨틱을 먼저"라는 연성 규칙**이라 이미 새고 있다. 강제 못 하는 레이어는 무너지고, 무너진 2레이어는 1레이어보다 나쁘다(개념 2개·규율 0).
- **⑥ SOLID** — DIP(구체 대신 추상 의존) 이득은 컴포넌트가 hex 대신 `bg-primary`를 쓰는 시점에 **이미 달성**된다. 원시 층의 추가 이득은 SRP/OCP인데, 그건 **팔레트가 의미와 독립적으로 변할 때**만 값어치가 있다 — 전담 디자이너가 팔레트를 따로 관리하지 않는 우리 구조에선 발생하지 않는다.
- **전환 트리거를 `index.css` 주석에 명시:** ①다크모드·기관 브랜딩 요구 ②같은 계열 명도 단계 5개 초과(현재 최대 primary 4) ③디자이너의 독립 팔레트 관리.

### 이름 = 역할 기준 (실측)
`text-text-2` 같은 중복을 없애고 역할을 드러냄. 와이어 측정: `--c-text-3` **614회**(47%가 xs·11px 동반 → 캡션·메타), `--c-text-2` **280회**(19% → 보조 본문). → `fg` / `fg-muted` / `fg-subtle`, `bg` → `canvas`. **SSOT 문서도 같이 갱신**했다(코드와 문서가 갈리는 것보다 낫다).

### 간격 의도 레이어는 만들지 않음
참고 프로젝트의 간격 의도 레이어(화면 패딩·요소 간격에 이름을 붙인 것)는 실화면 빈도에서 도출된 것. 우리 와이어는 **지배적 패딩값이 없다**(sp-3/4/5/6 = 27·19·11·3회) → 만들면 존재하지 않는 일관성을 발명하게 된다. Tailwind 기본 스케일을 그대로 쓰고 **컨테이너 폭만** 토큰화(`--container-page`, 와이어 10회 일관).

### 가드 = 코드로 (참고 프로젝트에서 가져온 것)
그 프로젝트의 토큰 검사 스크립트는 **컴포넌트 29개에 하드코딩 hex 0건**이라는 결과로 실효성이 입증됐다. 이걸 본떠 `scripts/check-design.mjs`를 만들되 **bash가 아니라 Node**로 썼다 — `.gitattributes`로 Windows 호환을 챙겨놓고 bash 스크립트를 두면 앞뒤가 안 맞는다.
- 검사 ①하드코딩 hex(토큰 정의 파일만 예외) ②대비 AA 16쌍.
- **가드가 즉시 결함을 잡았다:** `fg-subtle #6b7280`은 흰 배경에서 4.83:1로 통과하지만 **실제 페이지 배경(`canvas` #f4f5f7)에서 4.43:1로 미달**이었다. 수동 검산이 놓친 것을 잡아 `#686f7d`(4.63:1)로 교정. 가드를 만든 이유가 그대로 증명됨.
- CI 3단계 → 4단계(design 추가). 위반 시 종료코드 1, 정상 0을 실제로 확인.

### 컴포넌트를 지금 만들지 않음
3번 반복되기 전엔 추출하지 않는다. 첫 화면에서 뽑은 Button은 두 번째 화면에서 반드시 틀린다. 순서를 이렇게 잡았다:
```
① 토큰 + 가드(이 결정)  → ② 화면 1개를 추상화 없이 끝까지 → ③ 두 번째 화면(중복 노출)
→ ④ 추출  ← 여기서부터 2명 병렬
```
②의 첫 화면은 **교육생 리스트** — 173줄로 가장 단순한데 반복 패턴(표·툴바·페이저·배지·빈상태)을 다 품어 추출 수확이 가장 크다. **병렬 시점이 "공용 컴포넌트 완성 후"가 아니라 "④ 추출 후"로 바뀐다.**

### 그 외 버린 것
TS 객체 토큰(RN은 CSS가 없어 불가피했던 것 — 우리가 하면 토큰이 두 곳에 생겨 drift), `AppText` 강제 래퍼(웹은 CSS 상속이 함), 학습용 장문 주석, 컴포넌트 29개 선제작.

## D10 · 디자인 시스템 카탈로그 페이지 — 그리고 그것이 드러낸 결함 3건

- **배경:** "만든 것을 한 화면에서 다 보고 싶다"는 요청. Storybook은 [[D9]]에서 규모에 안 맞아 제외했다.
- **형태를 두 번 바꿨다.** 처음에 앱 라우트(`/dev/design-system`)로 만들었으나, **정적 HTML이어야 한다**는 지적을 받고 생성물로 바꿨다. 이유가 타당했다 — ① 앱 코드는 검수 후 커밋해야 하는데 문서는 먼저 공유하고 싶었고, ② 팀원이 문서를 보려고 개발 서버를 띄워야 하는 것은 문턱이 높다. 지금은 `npm run doc:design`이 `docs/dev/design-system.html`을 만들고, 브라우저로 바로 열린다(외부 자원 참조 0건 확인).
- **핵심 판단 — 토큰 값을 문서에 적지 않는다.** 값을 하드코딩하면 토큰이 바뀔 때 문서가 조용히 거짓말을 하게 된다. 생성 시점에 `src/index.css`에서 읽어 이름·값 모두 `@theme` 하나에서만 나오게 했다. 가드가 하드코딩 hex를 막는 것과 같은 원칙이다.
- **드리프트를 CI가 막는다.** `--check`는 생성 결과가 커밋된 파일과 다르면 실패한다. 토큰만 고치고 문서를 다시 만들지 않는 것은 반드시 일어나므로 사람에게 맡기지 않는다(토큰 한 글자를 바꿔 종료 코드 1을 실측).
- **만들면서 결함 3건이 드러났다.** 카탈로그가 없었으면 전부 조용히 남았을 것들이다.

### ① Tailwind가 토큰을 `@layer` 안에 넣는다
최상위 `cssRules`만 훑으면 토큰이 **0개** 잡힌다. `:root, :host` 규칙이 `CSSLayerBlockRule` 안에 있어서다. 중첩 규칙까지 내려가도록 고쳤다. 빌드는 통과하므로 렌더해보기 전에는 알 수 없는 종류의 결함이었다.

### ② 문서에 적은 예시 코드가 빌드 CSS에 실렸다
카탈로그에 `--color-blue-600`이 떠서 추적하니, 값이 내가 쓴 hex가 아니라 **Tailwind 기본 팔레트의 oklch 값**이었다. 원인은 `docs/dev/decision-log.md`에 남긴 원시 팔레트 예시 한 줄 — Tailwind v4는 기본적으로 **프로젝트 전체**를 훑어 클래스 후보를 찾으므로 문서의 텍스트까지 스캔 대상이 된다.
- **조치:** 문서를 고치지 않고 **스캔 범위를 좁혔다**(`@import 'tailwindcss' source(none)` + `@source '.'`). 문서는 앞으로도 늘어나므로 원인 쪽을 막는 것이 맞다.
- **효과:** 빌드 CSS 19,666 → **17,265 bytes**. 문서에서 끌려오던 것이 그만큼 있었다.
- 주석을 고치다 같은 함정에 두 번 빠졌다("기본 팔레트 이름을 적지 말 것"이라고 쓰면서 그 이름을 적었다). 스캐너는 주석·문서를 가리지 않는다.

### ③ 정의했는데 방출되지 않는 토큰이 있었다
`success`·`neutral-soft`·`primary-border` 등 5개가 아직 어느 화면도 쓰지 않아 CSS에 실리지 않았다. 카탈로그가 "있는 토큰"이 아니라 "쓰인 토큰"만 보여주면, 새로 합류한 사람이 `success`를 못 찾고 임의 색을 만든다.
- **조치:** `@theme static`으로 전량 방출. 비용은 **175 bytes**로, 발견 가능성이 그 값어치보다 크다.

- **부수 효과:** 문서가 세는 색 개수와 가드가 세는 개수가 일치해 서로를 교차 검증한다. 분류에 안 잡힌 토큰은 "그 외"로 떨어져 눈에 띈다.
- **참고:** ①③은 실행 중 스타일시트를 파싱하던 시절의 결함이다. 정적 생성으로 바꾸면서 `@layer` 문제는 사라졌고(CSS 원본을 직접 읽는다), 미방출 토큰 문제도 사라졌다(`@theme static`은 유지 — 유틸리티 클래스 자체는 여전히 사용된 것만 생성된다). 그러나 ②(문서가 CSS를 오염시킴)는 형태와 무관하게 남는 문제였고 그대로 유효하다.

## D11 · 문서를 협업 자료로 — 정보를 세 층으로 나눈다

- **배경:** 팀원이 이 페이지를 보고 코드를 짤 것이므로 "어떤 경우에 쓰는지"와 "왜 그렇게 정했는지"가 필요하다. 다만 다 펼치면 훑어보기가 안 되고, 다 숨기면 아무도 근거를 안 읽는다.
- **판단 — 읽는 목적이 다르면 층을 나눈다.**

| 층 | 무엇 | 언제 읽나 | 수단 |
|---|---|---|---|
| 1 | 토큰 이름·값 | 무엇이 있는지 훑을 때 | 항상 보임 |
| 2 | 언제 쓰나 + 실제 예 | 코딩하다 잠깐 확인할 때 | 호버·포커스 |
| 3 | 왜 이렇게 정했나 | 합류했거나 규칙을 바꾸려 할 때 | 클릭(`<details>`) |

- **2층을 호버로 한 이유:** 코딩 중 확인은 빈도가 높고 짧다. 클릭이면 흐름이 끊긴다. 단 **호버 전용은 접근성 실패**이므로 카드를 `tabIndex=0`으로 두고 `group-focus`에도 같은 규칙을 걸었다(키보드로 Tab 이동 시 동일하게 열림을 실측 확인). 팝오버는 절대 위치로 겹쳐 띄운다 — 카드가 커지면 격자가 흔들린다.
- **3층을 `<details>`로 한 이유:** 네이티브라 키보드·스크린리더가 기본 동작하고, 접혀 있어도 내용이 문서에 있어 검색·인쇄에 걸린다. 상태 관리 코드도, JavaScript도 필요 없다 — 정적 HTML로 옮기면서 이 선택이 더 값어치를 했다.
- **설명을 `scripts/design-doc-content.mjs`로 분리:** 값은 `@theme`에서 읽고, 설명은 이 파일에서만 온다. **값을 두 곳에 적으면 한쪽이 반드시 낡는다**는 [[D10]]의 원칙을 설명에도 적용했다.
- **문서 구멍이 드러나게 했다:** 설명이 없는 토큰은 팝오버가 없어 눈에 띈다. 현재 우리가 정의한 31개는 전부 설명이 있고, 없는 것은 Tailwind 기본 `white` 하나다.
- **값이 조정된 토큰(4개)에 표시(✎)를 붙였다.** SSOT와 다른 값을 쓰는 이유를 카드에서 바로 알 수 있어야, 팀원이 SSOT 문서를 보고 "왜 다르지"라고 혼란스러워하지 않는다.

### 가드에 예외 표시를 추가했다

문서는 **"이렇게 쓰지 마라"를 보여주려고 그 나쁜 예를 적어야 한다.** 실제로 카탈로그의 금지 예시와 옛 SSOT 값 인용이 가드에 걸렸다.

- **판단:** 예시를 흐리게 쓰는 대신 줄 단위 예외 표시(`design-token-allow`)를 뒀다. 문서에서 반복될 상황이고, 예외 수단이 없으면 사람들이 **규칙 자체를 약화시키는 쪽**으로 간다.
- **표시가 눈에 보이고 grep으로 셀 수 있게** 했다 — 현재 5건(금지 예시 2, 옛 값 인용 3). 이 수가 늘어나면 규칙이 현실과 안 맞는다는 신호다.

## D13 · 프리미티브를 전부 Base UI 위에 — 손수 구현 폐기

- **배경:** shadcn CLI(`base-nova` 스타일)로 뽑은 Base UI 포트와 손수 만든 버전을 나란히 두고 비교했다. 가르려던 것은 "Base UI로 우리 디자인을 그대로 재현할 수 있는가"와 "손수 만든 게 나은 지점은 어딘가".
- **1차 판단(기각):** APG 명세가 있는 위젯만 Base UI로 — Dialog·Tabs. Button·Badge·Card는 포커스·포털·키보드 관리가 필요 없어 이득이 없다고 봤다. 실제로 Base UI 프리미티브 위에 같은 cva를 얹었더니 픽셀 단위로 동일했다.
- **최종 판단(뒤집음):** **여섯 개 전부 Base UI 위에.** 손수 버전은 폐기했다.
  - 지금 안 쓰인다고 앞으로도 안 쓰이는 게 아니다 — Button에 아이콘·로딩이 붙거나 "버튼처럼 보이는 링크"가 필요해지는 건 시간 문제다. Base UI Button의 `render`(다른 요소로 렌더)·`focusableWhenDisabled`(비활성도 탭으로 닿게)는 그때 새 컴포넌트 없이 확장된다. Badge도 `useRender`로 같은 이점.
  - **"지금 필요 없다"(YAGNI)보다 "기반을 하나로 통일해 나중에 갈아끼우지 않는다"를 우선했다** — 프리미티브 레벨이라 화면 결정보다 되돌리기 비용이 크다.
  - 픽셀까지 같았다는 실측은 여전히 유효하다. "이득이 없다"가 아니라 "당장의 이득은 없지만 나중 확장 비용이 더 크다"로 결론이 바뀐 것이다.
- **CLI 결과물을 그대로 커밋하지 않는다 — 3단계를 거친다.** ① cva를 우리 토큰으로 교체(`rounded-lg/xl`은 우리 스케일에 없는 값이다) ② 안 쓰는 variant·size 전량 삭제 ③ 파일명·export 정규화. 안 거치면 "variant를 임의로 늘리지 않는다"는 자체 규율이 CLI 한 번에 무너진다.
- **export 규약:** 서브컴포넌트가 없는 단일 요소(Button·Badge)는 `export default` + named 둘 다. 컴파운드(Card·Dialog·Table·Tabs)는 named만 — 서브컴포넌트가 여럿이라 default가 애초에 불가능하다.
- **문서와 대조해 기본값에서 되돌린 것 2건.** Button의 `border border-transparent`(문서의 `.btn`은 `border: 0`이고 ghost만 1px), Badge의 `h-5` 고정 높이(`.bdg`는 높이를 정하지 않는다 — 고정하면 글자가 커질 때 잘린다). **"Base UI 위에"가 "shadcn 기본값대로"를 뜻하지는 않는다.**
- **shadcn 토큰층이 우리 토큰을 덮고 있었다.** `@theme static` 뒤에 `@theme inline`이 붙으면서 같은 이름을 뒤엣것이 이겼다. 빌드 산출물로 실측하니 `bg-primary`가 `#3a4db8`이 아니라 거의 검정, `rounded-md`가 10px이 아니라 8px, body 배경이 canvas가 아니라 흰색이었다. 겹치는 이름을 `@theme inline`에서 빼고 `:root`의 shadcn 변수를 전부 `var()`로 우리 토큰에 연결했다 — **값을 두 곳에 적으면 한쪽이 반드시 낡는다**는 [[D10]]의 원칙을 토큰 이름에도 적용한 것이다.
  > CSS 커스텀 프로퍼티 충돌은 **타입 검사도 린트도 못 잡는다.** 빌드 산출물을 열어보기 전까지 아무도 모른다.
- **미착수:** 아이콘 전용 버튼 사이즈(Dialog 닫기 버튼이 `size="sm"` + `p-1.5`로 정사각형을 흉내내는 중 — 실제 공백이지만 사용처가 한 곳뿐이라 둘째가 생길 때), 기수/프로젝트 전환 팝업(Select가 아니라 Menu Button 패턴이라 별개).

## D14 · 중복 프리미티브를 지금 통합하지 않는다 — 세 번째 등장까지

- **배경:** 인증 화면이 합류하면서 같은 역할의 조각이 두 벌이 됐다.

  | 인증 쪽 | 공용 쪽 | 겹치는 것 |
  |---|---|---|
  | `features/auth/components/PrimaryButton` | `components/ui/Button` | 주 액션 버튼 |
  | `features/auth/components/BrandPanel` + `AuthForm` | (셸 없음) | 인증 화면 2단 레이아웃 |
  | `features/auth/components/TextField` · `PasswordField` | (없음) | 입력 필드 |

- **판단: 지금 통합하지 않는다.** 사용처가 인증 화면 3개뿐이라, 지금 올리면 **인증 화면 사정에 맞춘 것이 공용이 된다.** 이건 `frontend-architecture.md`가 경계한 그 함정이다 — "처음부터 공용으로 만들면 한 곳의 사정에 맞춘 것이 공용이 된다."
- **다시 볼 시점:** 같은 조각이 **두 번째 도메인에서 필요해질 때**(세 번째 등장). 그때는 두 도메인이 실제로 공유하는 부분이 무엇인지 눈으로 보인다. 지금은 추측해야 한다.
  > 한 번은 만들고, 두 번은 기록하고, **세 번째에 올린다.** 두 번째에 올리면 공통점이 아니라 우연의 일치를 공용으로 만든다.
- **이슈로 두지 않고 여기 적는 이유:** "언제 끝난 것인가"를 판정할 수 없기 때문이다. 완료 조건을 쓸 수 없는 것은 이슈가 아니라 결정이다. 이슈로 두면 아무도 못 닫는 채 목록에 남아, 진짜 열린 작업이 안 보이게 된다.
- **중복이 생긴 진짜 원인은 규칙 부재가 아니다.** 규칙(`빈도 5회 이상만 공용으로`)은 이미 있었고 문서에도 적혀 있었다. 두 사람이 각자 만든 이유는 **만들기 전에 볼 곳을 몰랐기** 때문이다. 2인 팀에서 이걸 막는 것은 린터가 아니라 화면 착수 전 **"이 화면에 뭐가 필요한가"를 맞춰보는 5분**이다 — "이 두 파일이 같은 것"은 기계가 판정할 수 없다.

## D15 · 레이어 경계 린트가 절반만 지켜지고 있었다

- **배경:** 인증 화면을 계층 구조로 옮기며 import 방식을 정하다가, 규칙을 실제로 돌려보고 발견했다.
- **결함:** `@/features/*/*` 는 glob의 `*`가 `/`를 넘지 않아 **딱 두 단계만** 잡는다.

  | import | 고치기 전 | 후 |
  |---|---|---|
  | `@/features/{남}/AuthContext` | 막힘 | 막힘 |
  | `@/features/{남}/components/TextField` | **통과** | 막힘 |

  하필 통과하던 쪽이 **남의 도메인 컴포넌트 가져다 쓰기** — 교차 참조의 제일 흔한 형태다. 규칙은 있는데 정작 막아야 할 것을 안 막고 있었다.
- **고침:** 패턴에 `@/features/*/**` 를 더했다. feature가 늘어도 이 줄은 그대로다.
- **feature 안은 상대경로로 참조한다.** 이 규칙이 자기 자신도 막기 때문이기도 하지만, 그것과 별개로 폴더째 옮길 때 내부 import를 다시 쓰지 않아도 된다. 실제로 인증 화면을 옮기며 절대경로로 쓰인 import를 13개 파일에서 다시 썼다. `@/` 로 시작하면 그것만으로 "내 모듈 밖"이 드러나는 이점도 있다.
  > **규칙이 있다는 것과 규칙이 작동한다는 것은 다르다.** 검사 규칙도 코드다 — 통과하는 것만 보지 말고, **막아야 할 것을 넣어서 실제로 막히는지** 확인해야 한다. 이 결함은 규칙을 도입한 날부터 있었지만, 아무도 위반 코드를 넣어본 적이 없어 드러나지 않았다.

## D17 · 역할별 셸 4개를 `ConsoleShell(role)` 하나로 — 짜고 나서 SOLID·YAGNI 위반을 발견

- **배경:** v2는 역할 4개(슈퍼어드민·오퍼레이터·매니저·교육생)마다 메뉴·스코프가 다르다(`docs/plan/v2/17-ia-menu-tree.md`). 처음엔 v1의 `ManagerShell` 패턴을 그대로 늘려 `SuperAdminShell`·`OperatorShell`·`ManagerShell`·`TraineeShell` 4개 파일을 만들었다 — 각자 공용 프레임에 자기 역할의 사이드바 배열만 주입하는 얇은 래퍼.
- **문제 제기(사용자):** "통일된 거 하려고 ConsoleShell 만든 거 아니야? 넷 다 내용만 다를 텐데 왜 뷰를 하나하나 들어가서 고쳐야 돼?" — 스코프 라벨 하나 바꾸는 데도 파일 4개를 돌아다녀야 했다.
- **판단:** 4개 파일을 지우고 `ConsoleShell`이 `role: Role` 하나를 받아 사이드바(`SIDEBAR_BY_ROLE[role]`)·스코프(`COHORT_SCOPED_ROLES.includes(role)`) 둘 다 내부에서 결정하게 합쳤다. 역할별 래퍼는 "어떤 사이드바를 넣을까"만 다른 얇은 함수였다 — 동작이 아니라 **파라미터**만 다른데 파일을 따로 둔 것.
- **근거:** 이건 개방-폐쇄나 단일 책임과 무관한, 그냥 파라미터화 누락이었다(SOLID). "역할별로 다른 컴포넌트가 필요할 수도 있으니 미리 나눠 둔다"는 근거도 없었다(YAGNI) — 넷 다 지금도 앞으로도 프레임은 완전히 같다.
- **재발 방지:** 이 세션에서 "코드 짜기 전에 기존 구조 파악 + 계획부터"를 원칙으로 명시적으로 받았다. 여러 유사 파일을 만들기 전에 "이게 진짜 행동이 다른가, 파라미터만 다른가"를 먼저 묻는다.

## D18 · 손으로 만들지 않는다 — 있는 컴포넌트·토큰부터 확인

- **배경:** `ConsoleShell`의 상단바(`Header`)를 처음 만들 때 브랜드 로고·기수 선택기·사용자 아바타를 전부 `<div>`/`<span>`/`<button>`으로 손으로 그렸다. 나브 구분선 색도 임의 클래스(`border-nav-active`)를 새로 붙였다.
- **문제 제기(사용자):** "쉘 구분선이 너무 하얘" → 확인해보니 목업 값(`--c-nav-2`)과 다른 색을 썼다. 이어서 "만들 때는 항상 디자인 시스템·컴포넌트 있는 거 다 참고해서 해."
- **판단·조치:**

  | 손으로 만든 것 | 교체 |
  |---|---|
  | 브랜드 로고 `<div>` | `components/common/Wordmark`(인증 화면 `BrandPanel`과 같은 로고 — `features-v1/auth`에서 공용 위치로 승격) |
  | 기수 선택기 `<button>+▾` | `components/ui/Select`(`component-page-map.md`가 이미 이 자리를 select로 매핑해 둠) |
  | 사용자 이니셜 원 | `components/ui/Avatar` + `AvatarFallback` |
  | 나브 색 임의 클래스 | `index.css`에 이미 배선된 shadcn 표준 `--sidebar-*` 토큰(`bg-sidebar` · `text-sidebar-foreground` · `bg-sidebar-accent` · `border-sidebar-border`) |
  | nav 아이콘 유니코드 글리프(▦▨✎) | `lucide-react`(다른 shadcn 프리미티브가 이미 쓰는 라이브러리) |

- **예외 1건 — 토큰이 틀렸다:** `--sidebar-accent-foreground`가 `--color-nav-fg`(흐린 회색)로 매핑돼 있는데, 목업의 선택 항목 글자는 흰색이다. 토큰을 그대로 썼으면 대비가 떨어졌다 — 이 한 곳만 `text-white`를 직접 쓰고 이유를 주석에 남겼다.
  > **"있는 걸 써라"가 "토큰이 항상 맞다"는 뜻은 아니다** — 확인하고 어긋나면 근거를 남기고 벗어난다.

## D19 · 셸 프레임 버그 2건 — 스크롤과 반응형 폭

- **배경:** `ConsoleShell` 초안이 렌더는 됐지만 실사용 조건에서 두 가지가 깨져 있었다.
- **① 고정 높이(진짜 버그):** `min-h-svh`(최소 높이)를 썼더니, 콘텐츠가 길어지면 문서 전체가 늘어나 헤더·사이드바까지 스크롤에 밀려 올라갔다. 목업은 `.app{height:var(--screen-h)}` + `.content{overflow:hidden}` — 콘텐츠 영역 **안에서만** 스크롤되는 구조다. `h-svh`(고정 높이) + `overflow-hidden`으로 바꾸고, 3000px짜리 테스트 콘텐츠를 넣어 헤더·사이드바가 고정된 채 본문만 스크롤되는 것을 스크린샷으로 확인했다.
- **② 반응형 폭(재현 환경 문제였다):** 사용자가 "헤더 width가 고정 아니냐"고 반복 지적. 코드상 `<header>`는 이미 `flex`/`w-full` 계열이라 뷰포트 폭을 따라가야 했는데, 확인해보니 **재시작 전 죽은 dev 서버 포트(5174)에 열린 탭**을 보고 있었던 것으로 드러났다 — 살아있는 포트(5173)에서는 1100~1920px 전 구간에서 헤더 폭 = 뷰포트 폭이 실측(`getBoundingClientRect`)으로 일치했다. 그래도 `<header>`에 `w-full`을 명시로 박아 애매함 자체를 없앴다.
  > ②는 코드 값이 아니라 **사용자가 실제로 보고 있는 화면을 먼저 재현**하고 나서야 원인이 갈렸다. 코드만 계속 고치는 쪽으로 갔으면 시간을 낭비했을 것이다.

## D20 · 라우팅 방식을 세 번 갈아엎었다 — 도메인 파일 → 화면 파일 겸용 → 화면별 sibling 파일

- **배경:** v1 라우팅 관례(§4, 도메인마다 `routes.tsx` 하나 + `app/routes.tsx`가 손으로 import)를 v2 화면 25개로 그대로 확장하려 했다.
- **1차 — 도메인당 `routes.tsx`.** `app/routes.tsx`가 18개 도메인을 손으로 import + spread하게 됐다. "import가 너무 많다"는 지적에 `import.meta.glob('/src/features/**/routes.tsx')`로 폴더를 훑도록 바꿔, 새 도메인 추가 시 루트 파일이 안 바뀌게 했다.
- **2차 — 화면 파일이 `route`를 겸해서 export.** "폴더마다 routes.tsx를 계속 남겨야 하냐"는 재지적에, `routes.tsx` 자체를 없애고 `{X}Screen.tsx`가 컴포넌트와 `route` export를 같이 갖게 했다. 폴더 하나에 화면이 2개면(면담 목록+브리프 등) 파일을 나눠 가져야 하는 문제는 풀렸지만, 대신 `react/only-export-components` 경고가 화면 25개 전부에서 떴다 — React Fast Refresh가 그 파일에 상태 보존 핫리로드를 못 해 준다.
- **판정 질문(사용자):** "그런 상태가 뭔데, 예를 들어줘." → 폼 입력값·70분 세션 타이머·에디터 내용처럼 개발 중 저장할 때마다 날아가는 구체 사례로 답했다. 비용이 실제로 있다는 데 동의한 뒤 분리를 결정했다.
- **3차(최종) — 화면 파일 옆에 `{X}Screen.route.tsx`를 따로 둔다.** 컴포넌트 파일은 컴포넌트만 export(Fast Refresh 정상), 라우트는 화면마다 독립된 sibling 파일(공유 파일 없음 — 충돌 재발 안 함). `app/routes.tsx`는 glob 패턴만 `*.route.tsx`로 바꿔 계속 자동 수집한다.
- **기각한 대안 — 역할 폴더 단위로 한 번 더 모으기:** "그게 성능상 낫냐"는 질문에 추측으로 답하지 않고 확인했다 — `eager: true`라 glob 단계 수와 무관하게 25개 화면이 전부 같은 번들에 정적으로 들어간다(빌드 산출물의 JS 청크가 1개인 것으로 확인). 중간 집계 파일을 두면 그 파일을 여러 화면 담당자가 같이 고쳐야 해서, 애초에 화면마다 파일을 쪼갠 이유(작업 겹침 방지)가 다시 깨진다. 성능 이득 0 + 충돌 재발이라 기각했다.
  > **파일 구조를 "성능 때문"이라는 이유로 합치기 전에, 무엇이 실제로 정적 번들되는지부터 확인한다.** `eager: true` 하나가 이 질문의 답을 완전히 바꾼다 — 확인 없이 짐작으로 구조를 결정하지 않는다.

## D21 · 셸을 목업과 토큰 단위로 대조 — `--sp-N`의 N은 Tailwind의 N이 아니다

- **배경:** 오퍼레이터 화면 착수 전에 셸을 점검하다가, `01-design-checklist.md`의 「반영 완료」 표가 `ConsoleShell.tsx`에 본문 폭 상한(`mx-auto max-w-7xl`)이 있다고 적어 뒀는데 **실제 코드에는 없었다**(`grep`로 확인). 같은 표의 `TraineeShell.tsx` 행도 존재하지 않는 파일을 가리키고 있었다. 문서의 "반영 완료"를 믿고 화면을 그리기 시작했으면 25화면이 1920에서 조용히 H8을 어겼다.
- **고친 것 3건:**

  | | 목업 | 코드(전) | 코드(후) |
  |---|---|---|---|
  | 본문 폭 상한 | `.content > *{max-width:--w-app}` 1280 | **없음** | `<div class="mx-auto max-w-7xl">` |
  | 본문 좌우 여백 | `.content{padding:--sp-6}` **32px** | `p-6` **24px** | `p-8` 32px |
  | 나브 그룹 구분선 간격 | `.nav .grp{margin-top:--sp-2}` **8px** | `mt-3 pt-3` **12px** | `mt-2 pt-2` 8px |

- **★ 근본 원인 — 목업 간격 토큰의 번호가 Tailwind 번호와 다르다.**

  | 목업 | px | Tailwind 클래스 | 같은 번호를 쓰면 |
  |---|---|---|---|
  | `--sp-1` ~ `--sp-4` | 4·8·12·16 | `1`~`4` | 일치 |
  | **`--sp-5`** | **24** | **`6`** | `p-5`는 20px — **4px 부족** |
  | **`--sp-6`** | **32** | **`8`** | `p-6`은 24px — **8px 부족** |
  | **`--sp-8`** | **48** | **`12`** | `p-8`은 32px — **16px 부족** |

  **오퍼레이터 목업 5장에서만 이 구간이 78회 쓰인다**(sp-5 52 · sp-6 14 · sp-8 12). 목업의 숫자를 그대로 Tailwind 클래스 번호로 옮기는 순간 전부 좁아진다. `p-6` 사고가 정확히 이것이었다.

- **대조해서 이상 없던 것:** `--fs-*`(12·13·14·16·20·26)와 `--r-*`(6·10·14)는 `index.css`의 `--text-*`·`--radius-*`와 **값이 전부 같다.** 타이포·라운드는 목업 이름을 그대로 믿어도 된다 — **어긋나는 축은 간격 하나뿐**이다.

- **검증:** 1920에서 목업(`zoom` 환산)과 앱을 나란히 실측 — 나브 184 / 패딩 32 / 본문 1280 / 좌우 여백 226~228 대 228로 일치. 1440·1512·1728에서도 가로 스크롤 없음.

- **혼선 하나를 같이 기록한다 — 목업은 반응형이 아니다.** `.viewport{width:1920px; zoom:.6625}`라 **창을 어떻게 놓든 항상 1920 레이아웃을 축소해 보여준다.** 실제 앱은 창 폭을 따라가므로 1550px 창에서는 좌우 여백이 43px(패딩 32 + 남는 11)이 정상이고, 목업의 226px와 다른 것이 **버그가 아니다.** 목업과 눈으로 비교할 때는 브라우저를 1920으로 맞추거나 축소해서 본다.

- **재발 방지:** 목업 값을 코드로 옮길 때는 **토큰 이름이 아니라 px 값**을 기준으로 옮긴다. 그리고 문서의 「반영 완료」류 표는 **믿지 말고 `grep`으로 확인한다** — 이 표가 실제로 틀려 있었다.

## D22 · 표 컬럼 폭 — 목업 px을 베끼지 않고 측정해서 시스템으로 만든다

- **배경:** OP-03 프로젝트 목록을 그리려고 목업 컬럼 폭(`.c-nm 112` 등)을 옮기려다, 그 값들이 **실제로는 적용조차 안 되고 있다**는 것을 렌더 실측으로 발견했다.

  | | 선언 | **실제 렌더** |
  |---|---|---|
  | `operator/projects` — 6열 **전부** 폭 지정 | 112·64·180·230·124·108 (합 818) | **175·100·281·359·194·169** |
  | `manager/trainees` — 흡수 열 1개 비움 | 150·124·92·112·(없음)·124 | **선언대로** |

  `table-layout:fixed`는 **모든 열에 폭을 주면 남는 폭을 전 열에 비례 분배한다.** 체크리스트가 이미 *"마지막 열에만 폭을 주지 않는다"* 고 적어 뒀는데 이 목업이 그것을 어겼다 — 462px가 흩어져 선언값이 전부 무의미해졌다. **이미 구현된 MG-05는 규칙을 지키고 있다.**

- **또 하나 — 같은 뜻의 열이 목업마다 다르다.** `.c-nm`(주 식별자)이 **112 / 150 / 264** 세 종류였다. 체크리스트의 *"같은 뜻의 열은 어느 표에서나 같은 폭"* 이 목업에서 안 지켜지고 있었다.

- **기존 `--col-*` 11개도 시스템이 아니었다.** 8px 격자(업계 표준 8pt grid) 위에 있는 것이 **11개 중 4개**뿐이다(`chk 40 · act 96 · period 168 · name 200`). 나머지(92·108·110·116·124·132·196)는 눈대중으로 나온 값이라 근거를 댈 수 없다.

- **판단: 목업 px을 베끼지 않는다. 실제 콘텐츠를 재서 정하고, 새 CSS 토큰은 만들지 않는다.**

  실측(앱 실제 폰트, 셀 좌우 패딩 32px 포함) → 8배수 올림:

  | 뜻 | 최장 내용 | 필요폭 | 채택 | Tailwind |
  |---|---|---|---|---|
  | 짧은 라벨 | `미프` | 56 | **56** | `w-14` |
  | 상태 배지 | `준비 중` + 점 | 90 | **96** | `w-24` |
  | 날짜 | `07-21 18:00` + `5일 남음` | 104 | **128** | `w-32` |
  | 주 식별자 | `미프 5차` + 하위설명 | 160 | **160** | `w-40` |
  | 부 식별자 | `Kubernetes 기초 v1` | 136 | **160** | `w-40` |
  | **흡수 열** | 칩 3개 / `⚠ 미확정 · 후보 8건에서 3건`(176) | — | **미지정** | — |

- **왜 새 토큰을 안 만드나:** Tailwind 폭 유틸리티가 **이미 8px 격자 시스템**이다. 우리에게 없던 것은 값이 아니라 *"어떤 뜻에 어떤 폭"* 이라는 **매핑**이고, 그것은 CSS 변수가 아니라 이 표가 담는다. 토큰을 새로 정의하면 Tailwind 스케일과 `--col-*` 두 벌을 유지하게 된다.

- **경계:** **레이아웃 수치는 우리가 정하고, 문구·상태 이름·케이스 표는 목업이 계약이다.** 00-index가 *"목업이 단일 원천"* 이라고 한 것은 **케이스 표**를 가리킨 것이지 px을 가리킨 것이 아니다. 문구는 계정 열거 방지 같은 보안 규칙이 실려 있어 바꾸면 규칙이 깨진다(D21과 같은 결).

## D23 · 여러 세션이 한 폴더를 공유해 작업이 두 번 사라졌다 — 격리로 풀고, 훅은 보조로 둔다

- **배경:** 터미널 두 개(OP-04 · OP-06)가 같은 레포 폴더에서 동시에 작업하다가, 한쪽의 git 명령이 **다른 쪽의 미커밋 파일을 두 번 날렸다.** 두 번째에는 OP-06 화면 13개가 사라졌다.

### 원인 — reflog에 그대로 남아 있다

추측이 아니라 `.git`의 기록으로 갈렸다.

```
HEAD reflog   2cf9676 → 2cf9676  22:58  reset: moving to HEAD
              2cf9676 → 2cf9676  23:17  reset: moving to HEAD
stash reflog  23:10  WIP on feature/op-03-project-list          ← untracked까지 치움(부모 3개)
.git/AUTO_MERGE  23:17                                          ← 머지하다 끊은 흔적
```

**커밋 해시가 안 움직이고(`2cf9676 → 2cf9676`) 워킹트리만 버려진 것**이 reset 계열이 돌았다는 뜻이다. 그 stash 하나에는 **두 사람 작업이 같이 들어가 있었다** — `admin/` 36개 + `projects/` 6개. 한쪽이 자기 작업을 정리하려던 명령이 남의 폴더까지 쓸어 담은 것이다.

> **reflog 문구만으로 어느 명령인지는 안 갈린다.** 임시 저장소에서 확인해 보니
> `git reset --hard`와 `git merge --abort`가 **똑같이 `reset: moving to HEAD`를 남긴다.**
> 23:17 것은 `.git/AUTO_MERGE`와 시각이 같아 머지 중단 쪽이고, 22:58 것은 그 흔적이 없다 —
> **다른 파일과 대조해야 갈린다.** 처음엔 둘 다 `reset --hard`로 단정했다가 검증에서 고쳤다.

### 왜 이런 일이 가능한가 — 세션 격리가 애초에 없다

터미널·에디터·AI 세션을 여럿 띄워도 **디렉터리 한 벌, `.git` 한 벌을 물리적으로 같이 쓴다.** git에는 "이 세션이 만든 파일"이라는 개념이 없어서, 파괴적 명령은 **경로를 안 주면 워킹트리 전체**에 걸린다.

| git이 아는 저장 지점 | 보호받나 |
|---|---|
| 커밋 | ⭕ reflog가 지킨다 |
| index(`git add`) | 🔺 `clean`엔 안 지워짐 · 되돌리기엔 날아가되 **dangling blob으로 건진다** |
| stash | ⭕ (단 버리면 끝) |
| **untracked 새 파일** | ❌ **git이 존재를 모른다** |

사라진 것은 전부 마지막 칸이었다. **새 화면을 만드는 작업은 구조적으로 가장 약한 상태로 오래 머문다** — 파일을 20개 만들 때까지 커밋할 것이 없기 때문이다.

### 조치 ① 규약 — `git-convention.md` §5

**폴더 분리(`git worktree`)를 동시 작업의 기본으로 올렸다.** 원래 §5는 worktree를 *"정말 필요하면"* 이라는 최후 수단으로 적어 뒀는데 순서가 반대다 — 금지 목록은 실수를 **줄이고**, 격리는 사고를 **불가능하게** 한다.

`.git`을 공유하므로 커밋·브랜치·stash가 한 곳에 모이고, 별도 clone과 달리 서로의 브랜치가 보인다. **이 레포는 이미 목업 작업에 worktree를 쓰고 있어서**(`git worktree list`) 새로 배울 것도 없었다.

### 조치 ② 훅 — 만들었지만 🔺로 표기했다

git에는 `pre-stash`·`pre-reset` 훅이 없다. 그래서 Claude Code의 `PreToolUse`로 명령 실행 **전에** 문자열을 검사하는 `.claude/guard-worktree.sh`를 뒀다.

**만들고 나서 실제로 돌려 봤고, 그 결과를 표에 정직하게 적었다**([[D15]] — *"규칙이 있다는 것과 규칙이 작동한다는 것은 다르다"*).

| 검증 결과 | |
|---|---|
| 의도한 7개 | **전부 차단됨** ⭕ |
| **같은 파괴력인데 통과** | stash 버리기(`drop`·`clear`) · 강제 체크아웃(`-f`) · `checkout <브랜치> -- <경로>` · `reset --merge` · `rm -rf <소스폴더>` · `git -C <경로>` 우회 |
| **우회가 쉽다** | 공백을 둘 넣거나 따옴표를 끼우면 통과 |
| **오탐** | 명령문에 **단어가 들어가기만 해도** 막는다 — 문서를 `grep`하는 것, 금지 문구를 파일에 쓰는 것이 전부 걸렸다. **이 D23을 작성하는 명령 자체가 세 번 막혀서 다른 도구로 우회해야 했다** |

특히 stash 버리기가 안 막히는 것이 아프다 — **이번 사고에서 stash가 유일한 복구처였다.**

- **미커밋 결함(발견 즉시 기록):** `settings.json`은 추적되는데 `guard-worktree.sh`는 **untracked였다.** 둘이 따라온다 — ① 가드 자신이 자기가 막으려는 `clean` 명령의 삭제 대상이다 ② settings.json만 push되면 팀원 쪽엔 스크립트가 없어 `sh`가 **127**을 반환하는데, 차단은 **2**일 때만 걸리므로 **조용히 전부 통과한다.** 훅이 있다고 믿는 상태가 훅이 없는 상태보다 위험하다.

### 결론 — 계층을 뒤집지 않는다

```
1  폴더 분리(worktree)   사고를 불가능하게 한다        ← 진짜 방어선
2  규약(§5)              사람이 판단한다
3  훅                    AI 세션의 실수를 알린다        ← 방어선이 아니다
4  백업 · git add        사고가 나도 복구된다
```

**훅을 정교하게 만들어도 "폴더를 공유한다"는 전제는 안 바뀐다.** 이번에 작업이 살아난 것도 훅이 아니라 4번이었다 — 세션 스크래치패드 백업과, stash에 36개가 남아 있었던 것.

- **연결:** `docs/handbook/git-convention.md` §5·§6 · [[D2]] 규약을 강제 수단별로 배치 · [[D15]] 검사 규칙도 코드다.

## D24 · 공용 Checkbox.tsx `disabled:*` 무동작 버그 수정(이슈 #113) — 원인 파일을 직접 고침

- **배경:** MG08-9에서 발견한 것 — 공용 `components/ui/Checkbox.tsx`의 `disabled:cursor-not-allowed disabled:opacity-50`·`group-has-disabled/field:opacity-50`가 처음부터 한 번도 작동한 적이 없었다. Base UI `Checkbox.Root`가 `<span role="checkbox">`로 렌더돼 네이티브 `disabled` 속성 자체가 없고 `data-disabled` 어트리뷰트로만 비활성을 표시하는데, `disabled:`·`group-has-disabled:`는 둘 다 `:disabled` 가상 클래스를 전제로 하는 선택자라 `<span>`엔 애초에 매칭될 수 없었다. MG08-9 당시엔 팀장님 소유 파일이라 그 화면(`RetrySendDialog.tsx`)에서만 우회하고 원인 파일은 안 건드렸는데, 이번에 사용자(진용)가 "내가 고쳐보자"며 직접 승인 — CLAUDE.md §7 "팀장이 만든 파일은 임의로 수정하지 않는다 · 수정이 필요해 보이면 먼저 알리고 확인받는다"의 확인 절차를 사용자 본인이 그 자리에서 충족했다.
- **판단:**
  - `disabled:*` → `data-disabled:*`, `group-has-disabled/field:` → `group-has-data-disabled/field:`로 교체. 같은 파일군의 `Switch.tsx`·`Select.tsx`·`DropdownMenu.tsx`가 이미 `data-disabled:*`를 올바르게 쓰고 있어 그 표기를 그대로 옮겼다 — 새 규칙을 만들지 않았다. `group-has-data-*`도 `Field.tsx`(`group-has-data-horizontal/field:`)·`Avatar.tsx`(`group-has-data-[size=lg]/avatar-group:`)에 이미 있는 표기와 동일하다.
  - `RetrySendDialog.tsx`의 `DISABLED_CHECKED_CLASS`(MG08-9에서 만든 로컬 우회)는 **지우지 않았다.** 공용 컴포넌트가 고쳐져도 주는 건 "흐릿한 파랑"(`data-disabled:opacity-50`, 불투명도만 낮춤)이고, 이 화면이 사용자 지시로 이미 만들어 둔 건 "뚜렷한 회색"(다른 배경·테두리·글자색)이라 서로 다른 요구다. 두 클래스가 건드리는 CSS 속성이 겹치지 않아(opacity·cursor vs border·background·text-color) 공용 클래스 위에 로컬 오버라이드가 그대로 얹힌다 — 충돌도 중복도 아니라 그대로 뒀다.
- **검산:** `/tmp` 격리 복사(레포 전체 — Checkbox가 14개 화면에서 쓰여 부분 복사로는 회귀를 못 잡는다) 후 `tsc --noEmit -p tsconfig.app.json`·`-p tsconfig.node.json` 둘 다 통과, `prettier --check` 통과. `oxlint`·`vite build`는 이 샌드박스의 알려진 네이티브 바인딩 문제로 실행 불가 — 브라우저 실측(`getComputedStyle`로 비활성 체크박스 opacity·cursor 확인)은 다음 렌더 확인 때 사용자가 직접.
- **목적·효과:** 비활성 체크박스가 이 레포 전역(14개 화면)에서 처음으로 실제로 흐려지고 커서가 `not-allowed`로 바뀐다. `RetrySendDialog.tsx`처럼 이미 우회해 둔 화면은 그대로 두되, 다른 13개 화면도 별도 조치 없이 자동으로 정상화된다.

## D25 · 회차를 바꾸면 나머지 필터(검색·상태·위험 유형·반)를 초기화한다

  요청.

  ① 위험 유형은 회차마다 구성이 아예 다르다(1차는 `관찰`뿐, 2차 이상만 `단계

  종결·제외) 분포도 회차마다 다르다 — 예: 3차만 보고 있던 "종결" 필터를 켠 채
  4차(결과 전)로 넘어가면 혼란만 커진다. ③ 이미 이 함수가 회차 전환을 "새
  맥락"으로 취급하고 있었다(되돌리기 배너를 지우는 기존 로직) — 나머지 필터도
  같은 원칙으로 맞추는 게 일관적이다. 반대로 **브리프를 열었다 같은 회차로
  돌아오는 것**은 초기화 대상이 아니다 — 그건 "새 맥락"이 아니라 "하던 일
  이어서"라 MG04-6의 세션 유지가 그대로 적용된다.

- **목적·효과:** 회차를 옮기면 항상 그 회차의 전체 목록에서 다시 시작한다 —
  이전 회차 필터가 새 회차에서 뜻밖의 빈 화면을 만드는 일이 없어진다.

## D31 · SA-02 이슈 #195 후속 — "삭제됨"→"삭제 대기" 라벨 통합 + 복구 배너 조건 버그 수정

- **D30 정정:** D30 배경 문단이 "백엔드가 보내는 문자열이 바뀌면 화면도 따라 바뀐다"고 적었는데 **틀렸다.** `org.status`는 자유 문자열이 아니라 고정 enum(`ACTIVE`/`SUSPENDED`/`DELETION_PENDING`/`DELETED`)이고, 그 값을 "삭제됨"·"삭제 대기" 같은 한글 문구로 바꾸는 건 전부 `labels.ts`의 프론트 하드코딩(`orgStatusBadge`)이다. 백엔드가 "라벨을 바꾼다"는 건 실제로는 **어떤 enum 값을 내려주는지를 바꾼다**는 뜻이 아니라(그대로 `DELETED`를 계속 보낸다), 이 상태의 의미를 프론트에 알려준 것뿐이다 — 그래서 프론트 코드 수정이 필요했다.
- **배경 — 관측 결과:** 팀장 확인 — 이 백엔드에서 관측 가능한 `org.status === 'DELETED'`는 전부 "삭제 대기(복구 가능, 파기 전)"를 뜻한다. 진짜로 파기가 끝난 기관은 어떤 조회 응답에도 나타나지 않는다(목록에도, 상세 헤더에도 뜰 방법이 없다 — 조회 대상 자체가 사라진다). 즉 화면 코드 입장에서 `DELETION_PENDING`과 `DELETED`는 **이름만 다른 같은 실제 상태**다.
- **수정 1 — `labels.ts` `orgStatusBadge()`:** `DELETED` 전용 분기(neutral "삭제됨")를 없애고 `DELETION_PENDING` 분기 조건에 `|| org.status === 'DELETED'`를 합쳐 danger "삭제 대기 · 날짜 파기"로 통일했다. 우선순위 주석의 "삭제됨 > 삭제 대기 > ..."도 "삭제 대기 > ..."로 정리하고 병합 근거를 한 줄 남겼다. 이 함수는 SA-01·SA-02 공유라 **SA-01 목록의 DELETED 기관 행 배지도 자동으로 neutral "삭제됨" → danger "삭제 대기 · 날짜 파기"로 바뀐다** — 의도된 파급 효과. `sa-01-org-list-situations.md`의 관련 서술(축 F5 근처, "`DELETED` → `삭제됨`(neutral). 정상")이 stale해져 한 줄 정정 주석만 남겼다 — 로직 변경이 아니라 공유 함수의 표시값 정정이라 **이슈 #185는 재오픈하지 않는다.**
- **수정 2 — `SettingsTab.tsx` 복구 배너 조건:** "삭제 대기 중입니다" `Alert`(파기일 안내 + 복구 버튼)가 `org.status === 'DELETION_PENDING'`으로만 열려 있었는데, 실제 관측된 삭제 대기 기관(파이널랩·(주)코딩몬스터)이 전부 `DELETED`였으므로 **이 조건이 한 번도 참이 된 적이 없었다** — 배너·복구 버튼이 지금까지 렌더된 적이 없는 결함이었다. 수정 1의 결론에 따라 조건을 이미 5개 버튼 잠금에 쓰던 `settingsLocked`(`DELETION_PENDING || DELETED`)로 넓혔다. 곁들여 `deleteLockedTitle`(기관 삭제 버튼의 비활성 사유)도 상태별로 문구를 가르던 것을 `settingsLocked` 하나로 통일했다(라벨이 이미 통합됐는데 title만 "이미 삭제된 기관입니다."로 다른 말을 하면 K2와 같은 종류의 불일치가 새로 생긴다).
- **판단 — restore를 `DELETED`에도 허용:** D29에서 "`DELETED` 상태에 `useRestoreOrganization`을 임의로 호출하지 않는다"고 보류했던 건 "즉시 파기 버그일 수 있어 상태 전이가 문서화 안 됨"이 근거였다. 그 근거가 팀장 확인으로 해소됐다(관측되는 `DELETED` == 복구 가능한 삭제 대기, D30·본 항목) — 그래서 보류를 철회한다. `handleRestore()`·복구 버튼의 `disabled={restore.isPending}` 로직은 원래도 `org.status`로 막고 있지 않았으므로(항상 시도 가능했다) **코드 변경이 필요 없었다** — 배너 자체가 안 뜨던 게 유일한 막힘이었고, 수정 2로 해소됐다.
- **검산:** `typecheck`·`build`·`lint`·`format:check`·`check:design`·`check:admin` 전부 로컬 통과. 렌더 확인(Playwright, 실제 삭제 대기 기관 (주)코딩몬스터 `ca37e470-9f49-4e9d-8784-80a19855f49e`로): 헤더·설정 탭 배지가 danger "삭제 대기 · 날짜 파기"로 노출(neutral "삭제됨" 더 이상 안 뜸) · "삭제 대기 중입니다" 배너 + 복구 버튼이 처음으로 실제 렌더됨 확인 · 복구 버튼 클릭 → 정상 동작(성공 시 배너·잠금 해제, 헤더 배지 "활성"로 복귀) · SA-01 목록에서 같은 기관 행 배지도 danger "삭제 대기"로 회귀 아닌 의도된 변화로 확인.
- **목적·효과:** SA-02 복구 플로우가 이번에 처음으로 실제 동작을 확인받았다(배너·복구 버튼 렌더 자체가 그동안 죽어 있던 코드였다). SA-01·SA-02가 이제 `DELETED`/`DELETION_PENDING`을 완전히 같은 실제 상태로 취급해 화면 두 곳의 값 체계가 진짜로 하나가 됐다.

## D35 · 새로고침 로그아웃 버그(#201) — 원인은 크로스사이트 리프레시 쿠키, 해법은 /api 동일 출처 프록시

- **배경:** "새로고침하면 로그인 화면으로 튕긴다"는 오래된 별개 이슈(`/auth/refresh` 미완성으로 2026-08-08~10 여러 세션 기록에 남아 있던 그 트랙). 이번에 백엔드가 `REFRESH_TOKEN_COOKIE_SECURE=true`·`REFRESH_TOKEN_COOKIE_SAME_SITE=None`으로 쿠키 속성을 고쳤다는 회신을 받았는데도 증상이 그대로였다. DevTools로 재확인: Application 탭엔 `refresh_token` 쿠키가 새로고침 후에도 그대로 남아 있는데(속성도 `Secure`✓·`SameSite=None` 정상), Network 탭에서 실제 `POST /auth/refresh` 요청의 요청 헤더엔 `Cookie:`가 아예 없고 `Sec-Fetch-Storage-Access: none`·`Sec-Fetch-Site: cross-site`가 찍혔다 — 쿠키가 브라우저에 저장은 되지만 **전송 시점에 차단**되고 있다는 뜻.
- **근본 원인:** `client.ts`의 `credentials: 'include'`는 처음부터 정확히 켜져 있었고 문제는 프론트 코드가 아니었다. `.env.local`의 `VITE_API_BASE`가 `https://xvdanr6m362b2ge232vdmfbrny0kwakz.lambda-url.ap-northeast-1.on.aws`(백엔드) 절대경로였고, 프론트는 로컬 `localhost:5173`·배포 Vercel 도메인에서 열린다 — `vite.config.ts`·`vercel.json` 어디에도 `/api`를 같은 출처로 우회시키는 프록시가 없어 이 요청은 **항상 진짜 크로스사이트 요청**이었다. `SameSite=None; Secure`는 크로스사이트 쿠키 전송의 필요조건일 뿐이고, 브라우저의 서드파티 쿠키 정책(Chrome 기본 정책 전환·사용자 설정·확장 프로그램)이 그 위 단계에서 쿠키 자체를 차단하면 속성이 맞아도 못 나간다 — 딱 실측된 증상과 일치.
- **판단 — 쿠키 속성을 더 만지지 않고 동일 출처화로 해결:** `Partitioned`(CHIPS) 속성 추가 같은 우회도 검토했지만, Safari는 이미 기본으로 서드파티 쿠키를 막고 Chrome도 같은 방향이라 브라우저 정책에 계속 기대는 구조는 반복해서 깨질 것으로 판단. 정공법은 `/api/*` 요청이 프론트 자기 출처로 나가고, 서버가 실제 백엔드로 중계하는 것 — 그러면 쿠키가 퍼스트파티가 되어 서드파티 쿠키 정책과 무관해진다.
- **구현:**
  1. `vite.config.ts` — `server.proxy`에 `/api` → 백엔드 Lambda URL(`changeOrigin: true`) 추가. 로컬 dev 전용.
  2. `vercel.json` — `/api/(.*)` → 백엔드 Lambda URL로 가는 rewrite를 기존 SPA fallback(`/(.*)`  → `/index.html`)보다 **먼저** 추가(먼저 매치하는 규칙이 이겨야 `/api` 요청이 `index.html`로 안 삼켜진다).
  3. `.env.local`·`.env.example`의 `VITE_API_BASE`를 절대경로에서 **빈 값(상대경로)**으로 변경 — `client.ts`의 `baseUrl: import.meta.env?.VITE_API_BASE ?? ''`가 그대로 상대경로로 떨어져 프록시를 타게 된다. `client.ts` 자체는 안 건드렸다(이미 맞게 짜여 있었다).
- **부수 효과:** 브라우저 관점에서 요청이 same-origin이 되므로 CORS 프리플라이트(OPTIONS)가 아예 안 돈다 — 2026-08-10 세션에 기록된 "GET 요청이 프리플라이트는 200인데 본요청이 Stalled로 멈춘다"던 별개 이슈도 프리플라이트 자체가 사라지면서 같이 해소될 가능성이 있다(확정 아님, 다음에 그 증상 재현되면 이 변경과 함께 재확인).
- **검산:** `npx tsc -b` 0에러·`npx prettier --check`(`vite.config.ts`·`vercel.json`·본 문서) 통과. 렌더 확인(사용자, 로컬 `npm run dev`): 로그인 → 새로고침 → 로그인 화면으로 안 튕김, Network 탭에서 `POST http://localhost:5173/api/v0/auth/refresh` 200·`Cookies` 탭에 `refresh_token` 정상 전송 확인.
- **팀장 요청 — "액세스 토큰 만료(15분?) 기다렸다가 새로고침해도 안 튕겨야 성공" 검증 방법 정리:** `accessToken`은 메모리 전용(`authStore.ts`)이라 새로고침하면 경과 시간과 무관하게 즉시 사라지고, 그 순간부터 쿠키 기반 재발급(`authMiddleware` → `refreshOnce()` → `authBridge.refresh()`)이 **무조건** 실행된다 — 로그인 직후 새로고침이든 만료 후 새로고침이든 코드 경로가 완전히 같다. 즉 위 렌더 확인이 이미 "만료 후 새로고침" 케이스를 포함해 검증한 것과 같다 — 별도로 기다릴 필요가 없다. 실제 `accessTokenExpiresIn` 값도 확인함: 문서(`openapi.json` `RefreshTokenResponse`/`LoginResponse`)의 예시(`3600000`=1시간)와 실제 `refresh` 응답 바디 값이 **`3600000`(정확히 1시간)** 로 일치 — 팀장이 말한 15분이 아니다. 사전(proactive) 갱신 타이머는 스펙 설명엔 언급되지만 현재 `client.ts`엔 미구현(401 맞았을 때만 갱신하는 사후 방식만 있음) — 별개 트랙, 이번 범위 아님.
- **목적·효과:** "새로고침하면 로그아웃된다" 버그의 진짜 원인(크로스사이트 리프레시 쿠키)을 처음으로 코드·네트워크 실측 둘 다로 확정했고, 백엔드 쿠키 속성 수정만으로는 못 넘는 구조적 문제라는 것도 함께 남긴다 — 다음에 비슷한 "쿠키는 있는데 요청엔 안 실린다" 증상이 나오면 이 항목부터 볼 것. 이슈 #201 완료 조건(새로고침해도 로그인 화면으로 안 튕김) 실측 충족.

## D36 · 서버에서 오는 필터는 메뉴가 상태를 말한다 — 공용 `FilterSelect` + 이름표를 `│`로 통일

- **배경:** 오퍼레이터 교안 필터 하나에만 「불러오는 중」이 붙어 있었고 나머지 필터는 `disabled`로 잠그기만 했다. 잠긴 필터는 **왜 잠겼는지 말할 자리가 없다** — 명부 조회가 5.4초인 MG-03에서는 그동안 회차 선택기가 흐린 채 아무 말도 안 했고, 서버 목록이 아예 실패하면 필터가 조용히 「전체」 하나로 **영구히** 쪼그라드는데 쓰는 사람이 그 사실을 모른다(로딩은 몇 초 뒤 저절로 낫지만 실패는 세션 내내 안 낫는다).
- **판단 — 트리거는 안 건드리고 메뉴에 적는다.** 버린 안 셋과 이유는 `async-states.md` §1-6에 표로 남겼다. 핵심은 역할 분리다: **트리거는 「지금 무엇이 걸려 있나」**(「반 │ 전체」는 로딩 중에도 참이라 바꿀 이유가 없다), **메뉴는 「무엇을 고를 수 있나」**(여기에 상태를 고를 수 없는 줄로 적는다). 「전체」 라벨 자체를 「불러오는 중」으로 바꾸는 안은 **선택지가 상태 메시지로 변신**해서 버렸다 — 그 항목을 누르면 「불러오는 중」을 고른 셈이 된다.
- **`components/common/FilterSelect`로 승격(D14 세 번째 등장 규칙).** 같은 모양이 매니저·오퍼레이터 네 곳에 각자 구현돼 있었다. 판정 기준은 **선택지가 `undefined`인가**다 — 빈 배열은 「없다고 확인된 것」이라 다르고, `isPending`은 `enabled:false` 구간에서 거짓이라 못 쓴다(하드닝 규칙 E). 실패면 메뉴 안에 사실과 **다시 시도** 버튼을 그린다. 현재 14개 파일이 쓴다.
- **상수 목록에는 안 쓴다.** 정렬·계정 상태처럼 코드가 갖는 선택지는 늦게 올 일이 없어서, 「불러오는 중」을 달면 그 자체가 거짓말이다.
- **표시할 필요부터 없앤다.** 매니저 담당 반은 기수당 거의 고정이라 `stores/cohortScope`가 기수를 정하는 순간 미리 받아 둔다(결과는 안 쓰고 캐시만 채운다). 다만 대시보드에 5초 이상 머물러야 효과가 있고 새로고침·딥링크로 바로 들어오면 그대로라 **둘 다 한다.**
- **이름표 구분자를 `·`에서 `│`로 통일.** 매니저 쪽만 `라벨 · 값` 문자열이었는데 **값에 점이 들어가는 이름이 실제로 있다**(`정렬 · 최근 발행 회차 나쁜 순`) — 어디까지가 이름표인지 읽을 수 없고 드롭다운 항목마다 같은 접두사가 반복됐다. `ControlLabel`(얇은 세로선)로 전부 바꿨다. 오퍼레이터 `RoundToolbar`는 범위 선택기라 `FilterSelect`로는 못 옮기고 `ControlLabel`만 적용했다.
- **검산:** `typecheck`·`lint`·`check-design` 통과. 렌더 확인(Playwright, 5175) — MG-03·MG-05·MG-07·OP-02 필터에서 로딩 줄·실패+다시 시도·프리페치 후 즉시 도착 각각 관찰.

## D41 · SPA 내비게이션 캐시 무효화 — "data 있으면 data 우선", 배경 재조회 실패로 전면 에러를 덮지 않는다 (SA-01 파일럿)

  배경 재조회가 503을 맞아 **정상 데이터를 밀어내고 전면 에러 화면으로 바뀌는** 현상.
- **원인 확인 — `@tanstack/query-core`(`src/query.ts` reducer `case 'error'`) 직접 확인.**

## D45 · D43·D44 배너 조건에서 TypeScript `possibly undefined` 21건 — `X.isError && !view`를 `!view`로 단순화해 narrowing 복구

- **배경:** 진용님이 로컬 `tsc`를 돌려 D43·D44 4개 화면에서 `TS18048 'view'(or 'data') is
  possibly 'undefined'` 21건을 발견 — `view.rows.map(...)`처럼 이미 `!view`를 걸렀다고
  믿었던 아래쪽 코드 전부.
- **원인 — `&&`의 부정은 TS가 단일 변수 사실로 못 좁힌다.** 전면 에러 조건을
  `X.isError && !view`(AND)로 바꾼 게 문제였다. `!view`(단독 부정)였던 원래 코드는
  `else` 갈래에서 `!(!view)` → `view`로 바로 좁혀지지만, `X.isError && !view`의 부정은
  드모르간으로 `!X.isError || view`(OR)가 돼 "view가 참"이라는 사실을 단독으로 못
  끌어낸다 — 실제로는 위 스켈레톤 분기(`!view && !X.isError`)와 결합하면 `view`가 항상
  참이라는 게 논리적으로 성립하지만(케이스 분석으로 확인), TS의 흐름 분석은 서로 다른
  두 삼항 조건에 걸친 논리 결합까지는 추론하지 않는다 — SAT solver가 아니라 조건 하나당
  국소적으로만 좁힌다.
- **수정 — 조건을 `!view`(또는 `!data`) 단독으로 되돌렸다.** 4개 파일 전부 동일 패턴
  (`X.isError && !view` → `!view`). 뜻은 바뀌지 않는다 — 위 스켈레톤 분기가 이미
  `!view && !X.isError`(로딩 중)를 걸러내므로, 그 분기를 통과하고 남은 `!view`는
  항상 "에러로 인해 데이터가 없는" 케이스일 수밖에 없다(케이스 분석: 스켈레톤 분기가
  거짓이려면 `view || X.isError`가 성립해야 하고, 동시에 `!view`면 `X.isError`가
  강제된다). 각 파일에 이 근거를 주석으로 남겼다.
- **검산:** `npx prettier --write` 4개 전부 통과. **`tsc -b`는 이번에도 이 세션에서 45초
  안에 못 끝냄**(증분 캐시 `node_modules/.tmp/*.tsbuildinfo`가 있어도 마찬가지) — 논리
  검증은 케이스 분석(수기)으로 하고, 실제 통과 확인은 진용님 로컬 재실행에 의존.
- **목적·효과:** "배경 재조회 실패해도 데이터 있으면 화면 유지"라는 D41 정책의 조건식을
  런타임 동작은 그대로 두면서 TypeScript strict 모드와도 맞게 고친다. 이후 같은 정책을
  다른 화면에 적용할 때 `X.isError && !view`가 아니라 **`!view`만 쓰는 것**이 맞는
  패턴이라는 걸 다음 배치를 위해 남긴다 — 스켈레톤 분기가 이미 `!view && !X.isError`
  형태로 있는 화면이라면 항상 이 단순화가 통한다.

  **(2026-08-20 후속) 진용님 로컬에서 `npx tsc -b --force`로 재검증 — 21건 전부 해소
  확인.** 증분 캐시(`.tsbuildinfo`)가 원인이었던 것으로 보임(같은 줄 번호로 반복 재현되던
  게 `--force` 한 번으로 없어짐). `typecheck`·`lint` 통과.

## D46 · SPA 내비게이션 캐시 무효화 — operator/admin 5개 탭 배치, D44가 "구조가 다르다"고 미룬 화면이 실은 같은 버그였다

- **배경:** D44가 "다음 배치로 이월"하며 근거로 든 것은 *"`X.isError ? 에러 : 표` 2단
  분기라 D43·D44의 `X.isError || Y.isError || !view` 3단 분기와 다르다 — 확인 없이 같은
  패치를 대면 스켈레톤 분기가 없을 때 잘못 건드릴 위험"*이었다(`ClassesTab.tsx`·
  `CohortsTab.tsx`·`ManagersTab.tsx`·`RosterTab.tsx`·`CurriculaTab.tsx`, 반·기수·매니저·
  명단·교안). 구조를 다시 읽어 보니 다섯 파일 전부 **스켈레톤 분기가 이미 있었다**
  (`X.isLoading ? 스켈레톤 : X.isError ? ErrorState : …`) — D44가 우려한 "스켈레톤 분기
  없음"은 사실이 아니었고, **분기 순서만 다를 뿐 결함은 D41과 완전히 같았다**: `X.isError`
  단독 조건이 참이면 `X.data`(캐시된 이전 값)가 남아 있어도 `ErrorState`가 표 전체를
  덮는다.
- **근거 — `data`는 배경 재조회 실패에도 지워지지 않는다.** 전역 `QueryClient`

  없다 — TanStack Query 기본 동작대로 배경 재조회가 실패하면 `data`는 마지막 성공 값을
  유지한 채 `error`·`isError`만 같이 켜진다. 그래서 `X.isError`만으로 가르면 데이터가
  있어도 에러 화면이 이긴다. 다섯 파일 모두 `SectionHeader`/`PageHeader`의 헤더 수·내역이
  이미 `X.data ?`로 데이터 유무를 가려 왔다(`ClassesTab.tsx`의
  `count={classes.data ? … : undefined}` 등) — "데이터 있음"의 판정 기준은 이미 화면
  안에 있었다.
- **수정 — 다섯 파일 모두 같은 두 가지를 더했다.**
  1. `X.isError` 단독 분기를 **`!X.data`**로 바꿨다 — `X.data`가 아예 없을 때(최초 진입
     실패)만 전면 `ErrorState`, 배경 재조회만 실패했으면 아래 표 분기로 그대로 넘어간다.
  2. `X.isError && X.data`일 때 표 위에 경고 배너(공용 `Alert` warning, D44가 통일한
     컴포넌트)를 얹어 "새로고침 실패, 마지막 값을 보여주는 중"임을 알린다.

  `ManagersTab.tsx`는 원래 empty 분기가 `!page.data || page.data.content.length === 0`로
  두 조건을 한 갈래에 묶어 뒀던 것도 **셋으로 갈랐다**(`!page.data` → 에러,
  `content.length === 0` → 빈 상태) — 안 갈라 두면 `!page.data`가 참인 "진짜 에러" 케이스가
  "필터에 안 걸림" 문구를 달고 나갈 뻔했다.
- **D45의 `!view` narrowing 함정은 이번엔 안 걸린다.** D45가 고친 것은 `X.isError && !view`

  처음부터 `!X.data` 단독으로 썼고(`X.isError && !view` 같은 AND 조합을 아예 안 만들었다),
  분기 아래에서 `X.data`를 직접 non-null로 참조하는 곳도 `ManagersTab.tsx`의
  `page.data.content.map(...)` 하나뿐이라 TS가 국소적으로도 문제없이 좁힌다 — 그래서 D45식

- **검산 — 이번에도 부분적.** `npx prettier --write` 5개 전부 파싱·포맷 통과(코드 파일만 —
