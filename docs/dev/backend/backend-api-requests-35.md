# 백엔드 API — 35차 요청 · 제출 파일 저장 실패와 테스트 계정 데이터

> **33차 CORS는 고쳐진 것을 확인했습니다.** 헤더가 허용 목록에 들어와 브라우저가 요청을
> 보냅니다. 감사합니다.
>
> 그래서 **처음으로 실제 ZIP을 서버까지 보내 봤고, 서버가 파일을 저장하지 못했습니다**
> (`500 ARTIFACT_STORE_FAILED`). 제출은 여전히 안 됩니다 — 막히는 자리만 브라우저에서
> 서버 안쪽으로 옮겨졌습니다.
>
> 그리고 하나 더 있습니다. **주신 테스트 계정이 하루 만에 못 쓰는 상태가 됐습니다**
> (`응시 가능` 9개 전부). 계정을 다시 달라는 요청이 아니라, **어떻게 주시면 반복해서
> 쓸 수 있는지**를 §2에 적었습니다.

## 1. 🔴 R1 — 제출 파일을 저장하지 못합니다

### 무엇을 보냈나

정상 ZIP입니다. 실제 git 저장소를 만들어 압축했습니다 — 파일 61개 · 25,743바이트.

```
POST /api/v0/submissions/zip?assessmentRoundId=<진행 중 회차>
  Authorization : Bearer …
  Idempotency-Key: …
  Content-Type  : multipart/form-data
  file          : team-project.zip (25,743 bytes)
```

### 무엇이 왔나

```json
HTTP/1.1 500
{
  "status": 500,
  "error": "INTERNAL_SERVER_ERROR",
  "code": "ARTIFACT_STORE_FAILED",
  "message": "제출 파일을 저장하지 못했습니다."
}
```

### 검증 단계는 정상입니다 — 저장 단계에서 죽습니다

같은 경로로 **일부러 깨진 파일**을 보내면 서버가 정확히 걸러 냅니다.

| 보낸 것 | 응답 | 판단 |
|---|---|---|
| 1MB 0바이트 덩어리(ZIP이 아님) | `400 ARCHIVE_INVALID` · *"빈 압축 파일입니다"* | ✅ 정확합니다 |
| 정상 git 저장소 ZIP(61개 파일) | **`500 ARTIFACT_STORE_FAILED`** | 🔴 |

**형식 검사는 통과했고 저장에서 실패했다**는 뜻으로 읽었습니다. 저희 쪽에서 손댈 수 있는
자리가 없어 보여 요청드립니다.

- 저장소(S3 등) 권한·버킷 설정을 확인해 주세요
- 재현되지 않으면 그 시각 서버 로그를 봐 주세요 (요청에 `Idempotency-Key`를 넣어 보냈습니다)

### 저희 쪽에서 한 것

제출 거절 코드 13종이 **화면에서 한 문장으로 뭉쳐 있었습니다.** 코드별로 갈랐고, **다시
눌러서 될 것인지**를 기준으로 나눴습니다.

```
ARCHIVE_INVALID            압축 파일을 열지 못했어요. 다시 압축해서 올려 주세요.   (재시도 ❌)
FILE_TOO_LARGE             파일이 너무 커요. 50MB 아래로 줄여 주세요.              (재시도 ❌)
ARTIFACT_STORE_FAILED      파일을 저장하는 중 문제가 생겼어요. 잠시 후 다시…      (재시도 ⭕)
AI_SERVER_UNAVAILABLE      분석 서버를 깨우는 중이에요. 최대 2분쯤…               (재시도 ⭕)
SUBMISSION_DEADLINE_PASSED 제출 마감이 지나 더 이상 낼 수 없어요.                 (재시도 ❌)
…
```

다시 눌러도 같게 실패하는 코드에 *"잠시 후 다시 시도해 주세요"* 를 붙이면 학생이 헛수고를
반복합니다. **`ARTIFACT_STORE_FAILED`는 재시도 가능으로 뒀습니다** — 일시적 저장 실패로
읽었기 때문입니다. 항상 실패하는 성격이면 알려 주세요, 문구를 바꾸겠습니다.

## 2. 🟡 R2 — 세션을 학생이 되어 끝까지 돌려 보려면

주신 엑셀(계정 194개)은 **잘 쓰고 있습니다.** 로그인 화면에 상태별 고르개로 붙여서
상태마다 반·팀이 겹치지 않게 10개씩 뽑아 씁니다.

**부족한 것은 계정 수가 아니라 "세션을 태울 수 있는 계정"입니다.** 저희가 하려는 것은
**응시 화면(TR-03)을 학생이 되어 처음부터 끝까지, 일어날 수 있는 상황을 전부** 밟아
보는 것입니다. 지금은 **한 번도 시작해 보지 못했습니다.**

### 왜 한 번도 못 했나

엑셀에 `응시 가능`으로 적힌 계정 **아홉을 오늘 다시 훑었더니 전부 창이 닫혀** 있었습니다.
응시 창이 분석 완료 뒤 24시간이라 그렇습니다.

```
GET /api/v0/assessment-rounds  →  current.representativeStatus

s016@algohouse.io           ASSESSMENT_WINDOW_CLOSED   NONE   문제 2개
s002@algohouse.io           ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
b150@green.com              ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
s022@nextcode.ac.kr         ASSESSMENT_WINDOW_CLOSED   NONE   문제 2개
s020@techbridge.kr          ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
s166@codeschool.kr          ASSESSMENT_WINDOW_CLOSED   NONE   문제 2개
s021@nextcode.ac.kr         ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
s027@frontier-bootcamp.com  ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
s050@devcamp.kr             ASSESSMENT_WINDOW_CLOSED   NONE   문제 3개
```

`defaultActionCode`가 전부 `NONE`이라 **누를 버튼이 없습니다.** 화면에서도 그대로 보입니다 —
`s016`으로 들어가면 홈이 *"응시 기한이 지났어요 · 응시 창은 08-17 20:44에 닫혔어요"* 입니다.

### 진행 중인 세션도 하나도 없습니다

엑셀에 `일시정지`·`중단`으로 적힌 계정도 확인했는데, **살아 있는 세션이 하나도
없었습니다.**

| 엑셀 라벨 | 확인 | 지금 상태 |
|---|---|---|
| `일시정지` | 3개 | `ASSESSMENT_COMPLETED`(리포트 대기) 2 · `ASSESSMENT_WINDOW_CLOSED` 1 |
| `중단` | 3개 | `ASSESSMENT_COMPLETED`(리포트 대기) 3 |

`중단`이 완료로 집계되는 것은 그럴 수 있다고 봅니다. 다만 **`일시정지`가 완료로 바뀐 것은
세션 60분 상한이 지나 서버가 닫은 것으로 읽었습니다.** 결과적으로 `ASSESSMENT_IN_PROGRESS`
계정이 **0개**라, 이어하기 화면도 못 보고 있습니다.

### 살아 있는 것 하나는 찾았습니다

`리포트 발행됨` 시트를 훑다가 **다시 보기 계정 하나**를 찾았습니다.

```
a037@green.com   REVIEW_REQUIRED   START_REVIEW    ← 다시 보기가 열려 있습니다
s001@stackup.co.kr · b226@green.com · s015@techbridge.kr
                 ASSESSMENT_COMPLETED  VIEW_REPORT
```

이 하나로 **다시 보기(⑬)는 저희가 오늘 확인할 수 있습니다.** 다만 이것도 한 번 쓰면
끝이라 여유분이 하나 더 있으면 좋겠습니다.

> 참고로 `미응시 확정`(`s067@codeschool-b.kr`)은 `ASSESSMENT_WINDOW_CLOSED` ·
> **`CONTACT_MANAGER`** 로 옵니다. `defaultActionCode`가 `NONE`이 아니라 매니저 연락인
> 경우를 처음 봤습니다 — 화면은 그 경우 버튼 없이 안내만 그립니다.

그리고 계정은 **쓰면 없어집니다.**

| | 무엇 | 되돌릴 수 있나 |
|---|---|---|
| **시간** | 응시 창 24시간 · 세션 60분 · 문제당 20분 | ❌ |
| **한 번 쓰면 끝** | 세션을 시작하면 그 계정은 시작 전으로 안 돌아갑니다 | ❌ |
| **들어가기만 해도** | `GET /assessment-sessions/current`가 상한 넘은 세션을 그 자리에서 닫습니다 | ❌ |

세 번째는 **의도된 설계로 이해했고 그 자체는 문제가 아닙니다**(학생이 새로고침만 해도
상한이 반영되는 것이 맞습니다). 다만 **화면을 열어 보기만 해도 계정이 줄어든다**는 뜻이라
적어 둡니다.

### 어떻게 테스트할 계획인가 — 사람 5명 × 여러 회차

**팀에서 5명이 각자 학생이 되어 돌립니다.** 한 사람이 세션 하나를 처음부터 끝까지
밟으면서 답을 일부러 다르게 냅니다.

| 사람 | 어떻게 답하나 | 보려는 것 |
|---|---|---|
| A | **다 맞게** | 통과만으로 끝까지 — 문제 전환 · 정상 종료 |
| B | **다 틀리게** | 힌트가 열리고, 다 쓰고도 미달로 문제가 닫히는 길 |
| C | **섞어서** | 실제 학생에 가장 가까운 길 |
| D | **중간에 멈춘다** | 새로고침·창 닫기 뒤 이어지는지, 시간 초과 |
| E | **다시 보기** | 리포트를 받은 뒤 재응시 경로 |

**한 사람 = 계정 하나 = 세션 하나입니다.** 세션이 끝나면 그 계정은 끝이라 다시 못 씁니다.

**그리고 이걸 한 번만 하지 않습니다.** 테스트는 원래 이렇게 돕니다.

```
1회차  돌려 본다        →  버그 10개쯤 나옵니다
2회차  고치고 다시       →  고친 게 맞나 + 고치다 깬 게 없나
3회차  또 고치고 다시    →  …
4회차  마지막 확인       →  배포 전 회귀
```

**회차마다 계정 5개가 통째로 없어집니다.** 한 번 태운 계정으로는 같은 자리를 다시 못
봅니다. 그래서 **최소 4회차 × 5명 = 20개**이고, 사람이 잘못 눌러 흐름을 놓치는 것까지
넣으면 더 됩니다. 실제로는 회차가 4번에 안 끝납니다.

> 이것이 **저희가 계정을 몇 개 달라고 말하기 어려운 이유**입니다. 정직하게 세면 30~40개인데,
> 그만큼을 매번 만들어 달라고 하는 것도 받으시는 쪽에서 그때마다 만드는 것도 서로 못 할
> 짓입니다. **그래서 아래 ①·②가 계정 수보다 중요합니다.**

### 그렇게 밟아도 못 보는 것이 남습니다

한 세션 안에서 볼 수 있는 것과, **계정을 따로 태워야 보이는 것**이 갈립니다.

| # | 상황 | 한 세션 안에서 되나 |
|---|---|---|
| ① | 시작 → 1번 문제 | ⭕ |
| ② | 통과 (`NEXT_TURN`) | ⭕ |
| ③ | 미달 → 힌트 (`RETRY_WITH_HINT`) | ⭕ |
| ④ | 힌트 소진 미달 (`PROBLEM_CLOSED`) | ⭕ |
| ⑤ | 새로고침 복원 (`turns[]`·`shownHints[]`) | ⭕ |
| ⑥ | `ANSWER_ALREADY_SUBMITTED` (같은 답 두 번) | ⭕ |
| ⑦ | 문제 전환 (`NEXT_PROBLEM`) | **문제가 2개 이상인 계정이어야** |
| ⑧ | 정상 종료 (`SESSION_ENDED`) | ⭕ (**여기서 계정이 끝납니다**) |
| ⑨ | **문제 20분 초과** — 그 문제만 접히고 커서가 다음으로 | ❌ 20분 기다리고 **세션 하나 소모** |
| ⑩ | **세션 60분 초과** — `204`로 종료 | ❌ 60분 기다리고 **세션 하나 소모** |
| ⑪ | 응시 창이 세션 도중에 닫힘 (`ASSESSMENT_WINDOW_CLOSED`) | ❌ 창 마감이 임박한 계정이 필요 |
| ⑫ | `GRADING_FAILED`(503) 재전송 | ❓ **만들 방법을 모릅니다** |
| ⑬ | 다시 보기(REVIEW) | ❌ `REVIEW_REQUIRED` 계정이 따로 |
| ⑭ | 문항이 0개인 회차 | ❌ 그런 계정이 있는지도 모릅니다 |

**⑨⑩⑪⑬⑭는 "그 상황을 미리 만들어 둔 계정"이 있어야 합니다.** 저희가 정상 흐름을
아무리 밟아도 도달할 수 없거나, 도달하는 데 한 시간씩 걸립니다.

### 필요한 것 — 우선순위 순

**① 테스트 조직의 시간 상한을 짧게·길게 조절해 주세요** 🔴

가장 크게 막는 것이 시간입니다. 값 두 개만 테스트 조직에서 다르게 주시면 됩니다.

| 값 | 지금 | 테스트에서 원하는 것 | 왜 |
|---|---|---|---|
| **응시 창** | 분석 후 24시간 | **길게** (예: 30일) | 계정이 하루 만에 죽지 않게 |
| **세션 상한** | 60분 | **짧게** (예: 3분) | ⑧을 **60분 기다리지 않고** 확인 |
| **문제 상한** | 20분 | **짧게** (예: 1분) | ⑦을 20분 기다리지 않고 확인 |

응시 창은 길게, 세션·문제 상한은 짧게 — **방향이 반대입니다.** 앞은 계정이 죽지 않게
하는 것이고 뒤는 시간 초과 분기를 몇 분 만에 보기 위한 것입니다.

셋 다 어려우면 **응시 창 하나만이라도** 늘려 주세요. 나머지는 기다리면 됩니다.

**② `응시 가능` 계정을 정기적으로 채워 주세요** 🔴

①이 안 되면 이것이 대안입니다. 셋 중 아무거나 좋습니다.

```
(a) 리셋 API        POST /dev/trainees/{id}/reset?state=ASSESSMENT_AVAILABLE
(b) 정기 재생성      매일 새벽 특정 계정 묶음을 응시 가능으로 되돌리기
(c) 수동 재생성      요청드릴 때마다 (지금 방식)
```

**(a)가 제일 좋습니다** — 저희가 필요할 때 만들 수 있어 요청 왕복이 없어집니다.

**③ 문제 수가 1개·0개인 계정** 🟡

지금 있는 계정을 세어 보니 **2개짜리 3명 · 3개짜리 6명**입니다. 전환(⑦)은 볼 수 있습니다.

없는 것은 **1개짜리와 0개짜리**입니다.

| 문제 수 | 지금 | 왜 필요한가 |
|---|---|---|
| 3 | ✅ 6명 | — |
| 2 | ✅ 3명 | — |
| **1** | ❌ | 전환 없이 바로 끝나는 길 — 화면이 "1군데"를 제대로 말하나 |
| **0** | ❌ | 문항이 하나도 안 만들어진 회차. **화면이 뭘 그려야 하는지가 가장 불확실합니다** |

`0`짜리는 있는지조차 모릅니다. 있으면 하나 알려 주세요.

**④ `GRADING_FAILED`(503)를 만들 방법** 🟡

스펙에 **같은 답을 그대로 재전송하라**고 적혀 있어 화면을 그렇게 만들었는데, **한 번도
재현하지 못해 확인을 못 했습니다.** AI 채점이 실패할 때 나오는 코드로 이해했습니다.
테스트로 강제할 수 있는 방법이 있으면 알려 주세요. 없으면 확인 못 한 채로 두겠습니다.

**⑤ 엑셀에 상태 코드 열** 🟡

지금 라벨이 한국어라 **화면 상태로 옮길 때 저희가 추측합니다.**

| 지금 | 필요한 것 |
|---|---|
| `02 응시 가능 · 아직 시작 안 함` | `representativeStatus = ASSESSMENT_AVAILABLE` |
| `응시 완료` (시트 둘에 같은 이름) | `ASSESSMENT_COMPLETED` / `REVIEW_REQUIRED`로 갈라서 |

**`응시 완료`가 시트 둘에 같은 이름으로 있습니다** — 하나는 리포트 대기고 하나는 발행됨이라
홈 카드가 다릅니다. 저희가 시트 이름으로 갈라 뒀는데, 코드 열이 있으면 추측이 사라집니다.

`representativeStatus`와 `defaultActionCode` 두 열이면 충분합니다.

엑셀에 `일시정지`·`중단`·`무효 응시` 라벨도 있는데, **세션 상태인지 홈 상태인지 확실하지
않습니다.** 코드로 적혀 있으면 이것도 풀립니다.

맞습니다. 계정마다 다른 것이 섞이면 열로 주세요.

### 그래서 정리하면 — 두 갈래로 나눠 주십시오

**갈래 A — 소모품.** 회차마다 없어지는 것이라 **①·②가 되면 이 줄은 통째로 사라집니다.**

| 무엇 | 지금 | 한 회차에 | 4회차면 |
|---|---|---|---|
| **`응시 가능` · 문제 2~3개** | **0개** | 8개 (5명 + 여유 3) | **32개** |

**갈래 B — 한 번만 있으면 되는 것.** 특정 상황을 미리 만들어 둔 계정이라, 회차마다
새로 필요한 것이 아니라 **한 번 확인하면 됩니다.**

| 무엇 | 지금 | 필요 | 왜 |
|---|---|---|---|
| **`응시 가능` · 문제 1개** | 0개 | 1개 | 전환 없이 바로 끝나는 짧은 길 |
| **`REVIEW_REQUIRED`** | **1개** ✅ | +1개 | ⑬ — `a037@green.com`이 살아 있습니다. 여유 하나만 |
| **문제 상한이 임박한 세션** | 0개 | 1개 | ⑨를 20분 안 기다리고 보려면 |
| **응시 창 마감이 임박한 계정** | 0개 | 1개 | ⑪ — 세션 도중에 창이 닫히는 길 |
| **문항 0개인 회차** | ? | 1개 | ⑭ (있으면) |

**B는 5개뿐이고 한 번이면 됩니다.** 문제는 A입니다 — 지금 방식이면 **회차마다 여덟 개씩
만들어 주셔야 하고, 저희는 그때마다 기다립니다.**

### 그래서 진짜 요청은 A를 없애는 것입니다

```
지금        회차마다 → 계정 8개 요청 → 기다림 → 태움 → 다시 요청 → …
①이 되면    응시 창이 안 닫히므로 남은 계정을 계속 씀
②가 되면    저희가 필요할 때 되돌려서 씀 — 요청 왕복이 0
```

**①이나 ② 중 하나만 되면 A(32개)가 필요 없어집니다.** 둘 다 어려우면 A를 회차마다
부탁드리게 되는데, 그건 서로 손이 많이 갑니다.

### 확인 하나 — 로그인에 Origin 검사가 있습니다

계정 상태를 한꺼번에 훑으려고 브라우저 밖(스크립트)에서 로그인했더니 이렇게 나왔습니다.

```
403 { "code": "LOGIN_ORIGIN_NOT_ALLOWED",
      "message": "허용되지 않은 클라이언트에서 요청했습니다." }
```

`Origin: http://localhost:5173`을 손으로 붙이니 통과했습니다. **문제로 보고드리는 것이
아닙니다**(브라우저에서는 정상입니다) — 서버 쪽에서 같은 걸 겪으실 때를 위해 적어 둡니다.

