## 1. 무엇을 재는가

### 제품 명제

> **AI가 대신 할 수 없는 것은 하나다. 자기 코드의 특정 지점에 대해, 그 자리에서, 왜 그렇게 됐는지 말하는 것.**

나머지는 전부 이걸 굴리는 기계다.

### 도구 성격 — 판단이 갈릴 때 여기로 돌아온다

| | |
|---|---|
| 무엇인가 | **매니징 도구(B2B LMS)** + 이해도 검증이라는 특수 기능 |
| 1순위 사용자 | **매니저** |
| 평가인가 학습인가 | **둘 다.** 평가이되 학습 지원 |
| 개인 진단인가 수업 진단인가 | 평소엔 개인, 기수 끝나면 수업(다음 기수 개선) |
| 결과물 목표 | **v1 MVP.** 현실적 구현 가능성 우선 |

## 2. Tier — 무엇이 확정이고 무엇이 검증 대기인가

### Tier 1 · 이게 틀리면 제품이 없다 — 논쟁 종결

| # | | 왜 |
|---|---|---|
| 1 | **코드 특정성** — 모든 질문은 `파일:라인`을 인용한다. 예외 없음 | AI가 못 하는 유일한 것 |
| 2 | **교안 앵커** — 미프 소재는 교안 개념 × 코드 교집합에서만 | 안 배운 걸 물으면 측정이 아니다. 난이도 통제도 여기서만 |
| 3 | **실시간성** — 창 이탈 기록 · 붙여넣기·선택 차단 · 전체화면 · 한 번에 끝냄 | 조회할 시간을 주면 1·2가 무력해진다 |
| 4 | **공통 축** — 검증 개념 3건은 **프로젝트 단위로 고정**. 반·팀·개인이 달라도 같은 3건 | 팀마다 코드·질문·꼬리질문이 전부 다르다. 이게 유일하게 남는 비교 축이다 |

### Tier 2 · 잠정 확정 — 검증 전까지 재논의 없음

계단 순서 · 축 4개 · 필수/선택 경계 · 힌트 재진술 2회 · 종료 규칙 · 3문제 · 통과식 판정

**재논의 조건은 15절에 있다.**

### Tier 3 · 파일럿까지 미룸

무효 응시 임계값 · 시간 예산 미세조정 · 우수 인원

> **가중치가 사라지고 도달 경계가 이론으로 정해져서(5-4) Tier 3이 거의 비었다.** 파일럿에서는 **분포 확인**만 한다.

## 3. 측정 구조

### 3-1. 계단 4단

| 단계 | 축 | 학생이 할 수 있는 것 | 질문 |
|---|---|---|---|
| **0** | — | 응답 없음 / 무성의 | — |
| **1** | **코드이해** | 무엇을 하고 어떻게 연결되는지 말한다 | "이 부분이 무슨 일을 하나요? 어디랑 연결되나요?" |
| **2** | **설계논리** | 왜 그렇게 했는지, 무엇을 고려했는지 말한다 | "왜 그 방식을 골랐나요? 무엇을 고려했나요?" |
| **3** | **대안비교** | 다른 방법이 있다는 것을 말한다 | "다른 방식으로 할 수도 있었을까요?" |
| **4** | **반례대응** | 언제 깨지는지 말한다 | "(상황을 던지고) 이러면 어떻게 되나요?" |

**한 턴은 한 가지만 묻는다.** 두 가지를 한 문장에 묶지 않는다.

> **근거:** 기존 L1이 `"~한 이유는 무엇인가요? 특히 …각각 어떤 목적을 가지고 있는지"`처럼 두 개를 묶어 물었고, **코드이해와 설계논리 점수가 7세션 중 5세션에서 완전히 일치**했다. 채점 근거문에서 두 축이 학생의 **같은 문장**을 인용한다. 답변이 하나면 근거도 하나고 점수도 같아진다.

### 3-2. 순서의 근거

5세션 단조 비증가 검증(평탄 2세션 제외):

| 인접 경계 | 성립 |
|---|---|
| 코드이해 ≥ 설계논리 | **4/5** |
| 설계논리 ≥ 대안비교 | **4/5** (오염 보정 후 5/5) |
| 대안비교 ≥ 반례대응 | **2/5** |

**약한 경계가 3↔4에 있다.** 그런데 **L3·L4가 선택 구간**이므로 위험 판별(L1·L2)은 가장 강한 위계 위에 있다.

**오판 비용이 큰 쪽(위험 판별)에 강한 위계를, 작은 쪽(우수 판별)에 불확실성을 배치한 구조다.**

### 3-3. 축과 루브릭

**4축 · 24칸(0~5).** 자기수정 축과 그 루브릭은 **삭제**한다.

> **삭제 근거:** 자기수정이 다른 4축과 **상관이 없다.** 실측에서 4축 평균 3.25인 세션이 자기수정 1점, 3.75인 세션이 5점이었다 — 실력이 있어도 인정 안 하고 낮아도 인정을 잘 한다. **상관 없음 = 다른 구인을 재고 있다는 뜻**이고, 정적 능력 4개와 변화 잠재력 1개를 같은 체계에 두면 범주 오류다.
>
> 그리고 측정 조건에 결함이 있었다 — 조건부(틀린 상황이 발생해야) · 유도 질문 후 자발성 판정 · **근거 있는 방어와 근거 없는 고집을 같은 1점으로** 처리.

루브릭 전문은 부록에 있다.

## 4. 세션 진행

### 4-1. 흐름

```
문제당 (3문제)

L1 코드이해   힌트 ≤2  ─ 미달 → 문제 종료 (0단)
                       └ 도달 → L2
L2 설계논리   힌트 ≤2  ─ 미달 → 문제 종료 (1단)      ← 여기까지 필수
                       └ 도달 → L3
L3 대안비교   힌트 ≤2  ─ 미달 → 문제 종료 (2단)      ← 여기부터 선택
                       └ 도달 → L4
L4 반례대응   힌트 ≤2  ─ 도달/미달 → 문제 종료 (4단/3단)
```

**힌트를 다 쓰고도 미달이면 그 문제는 끝이다.** 다음 단계를 던지지 않는다.

> **근거:** 1↔2가 **4/5로 가장 강한 위계**다. "코드가 뭐하는지 못 말하면 왜 그랬는지도 못 말한다"가 데이터에서 가장 잘 성립한다. 보험이 가장 덜 필요한 지점이다.

### 4-2. 힌트 — 재진술만

| | 내용 | 기록 |
|---|---|---|
| **1차** | 질문을 **다른 표현**으로 | 재진술1 |
| **2차** | **더 쉽게 풀어서** | 재진술2 |

**정보 추가는 0이다.** 코드 위치를 짚어주거나(`"이 파일의 이 함수를 보세요"`) 선택지를 제시하는 것은 힌트가 아니라 **답의 일부를 주는 것**이므로 하지 않는다.

**단계당 최대 2회.** 기록은 `자력 / 재진술1 / 재진술2 / 미달`.

#### 무엇을 바꾸고 무엇을 안 바꾸나

| | 바꿔도 되는 것 | 바꾸면 안 되는 것 |
|---|---|---|
| **1차** | 긴 문장 → 짧은 문장 여러 개 · 추상 표현 → 일상어 | 코드 위치 언급 추가 · 선택지 제시 |
| **2차** | **요구사항 분해** — `"A와 B를 설명하세요"` → `"먼저 A부터 설명해주세요"` | 답 방향 암시(`"~때문일까요?"`) · 새 용어·개념 도입 |

**코드에 나오는 식별자(함수명·변수명)는 그대로 둔다.** 풀어쓰면 답을 주는 것이다.

#### 판정 기준

> **재진술 후에도 정답의 집합이 같아야 한다.**

원 질문의 정답 = 재진술의 정답. **다르면 잘못된 재진술이다.**

**가장 흔한 위반은 "쉽게"를 "덜 묻는다"로 해석하는 것이다.** 질문 범위를 좁히면 쉬워지지만 **측정 대상이 바뀐다. 2차는 분해이지 축소가 아니다.**

```
재진술은 같은 질문을 다르게 말하는 것이다. 다음을 지켜라.
- 원 질문의 정답과 재진술의 정답이 같아야 한다
- 코드 위치·선택지·답의 방향을 암시하지 않는다
- 질문 범위를 좁히지 않는다 (2차는 분해이지 축소가 아니다)
- 코드에 나오는 식별자는 그대로 쓴다
```

**선택지 제공은 금지 사항이다.**

> **근거:** 실측에서 질문 안에 보기 세 개가 들어가 있었고 학생이 **"저는 3번"** 이라고 답해 **만점**을 받았다. 보기가 없던 질문을 받은 학생은 1점이었다. **같은 축인데 질문에 보기가 붙었는지에 따라 1점과 5점이 갈렸다.**
>
> → 질문 생성 프롬프트에 **"예시 보기를 제시하지 말 것"** 을 명시한다.

### 4-3. 시간

**시간은 안내만 하고 강제로 끊지 않는다.** 계단은 능력 검사(어디까지 가나)이지 속도 검사가 아니다. 시간으로 자르면 잘라낸 곳이 능력의 한계가 아니라 시간의 한계가 된다.

| 층 | 안내 예산 |
|---|---|
| L1 (코드 읽기 포함) | 6분 |
| L2 | 5분 |
| L3 | 5분 |
| L4 | 6분 |

| 학생 | 문제당 | **3문제** |
|---|---|---|
| L1 미달 | 6분 | 18분 |
| **L2 정지 (중위 예상)** | 11분 | **33분** |
| L3까지 | 16분 | 48분 |
| L4까지 | 22분 | 66분 |

**세션 하드 상한 70분** — 비용 방어용. 넘으면 완료된 문제까지 저장하고 종료.

**답변 길이는 3~5문장으로 안내한다.** 하드 제한이 아니다. 실측 답변이 대부분 그 길이였고 한 문장 답변은 1점을 받았다.

#### 왜 제한 시간이 부정행위 방어가 되지 못하나

> **"시간을 안 끊으면 나가서 AI한테 묻고 와서 쓰면 되는 것 아닌가"** — 맞는 지적이고, 그래서 **제한 시간으로는 그걸 못 막는다.**

**LLM 왕복은 20~40초다.** 질문을 옮기고 답을 받아 읽는 데까지 넉넉히 1분이다. 그걸 막으려면 턴 제한을 1분 밑으로 둬야 하는데, **그건 자기 코드를 읽고 설명을 구성하는 시간보다 짧다.** 정직한 학생만 잘린다.

| 제한 시간 | 부정행위자 | 정직한 학생 |
|---|---|---|
| 5분 | **통과** (1분이면 됨) | 대부분 통과 |
| 2분 | **통과** | 느린 학생 잘림 |
| 1분 | 빠듯하지만 **통과** | **대부분 잘림** |

**어떤 값을 골라도 정직한 학생을 먼저 자른다.** 시간 압박은 검색·교재 조회(느림)에는 통했지만 **LLM(빠름)에는 통하지 않는 옛 방어**다.

**그래서 시간이 아니라 이탈 자체를 잡는다.** 나갔다는 사실은 몇 초가 걸렸든 남는다(4-4). **시간 예산은 학생에게 페이스를 알려주는 용도로만 남긴다.**

**이탈 시간은 예산에서 빼지 않는다.** 나가 있는 동안 타이머는 계속 흐르고, 이탈 시간은 **따로도 쌓인다.** 멈춰주면 이탈이 공짜가 된다.

### 4-4. 부정 방어

**원칙: 막을 수 있는 것은 막고, 나머지는 기록해서 매니저가 본다. 자동 판정은 하지 않는다.**

#### 설계 전제 — 전체화면이 성립하려면

**세션 화면 안에 코드가 전부 있어야 한다.** 학생이 자기 코드를 다른 창에서 봐야 한다면 전체화면 강제가 측정을 방해한다 — 코드 조회가 이해도의 일부가 아니라 **탐색 부담**이 되기 때문이다.

**질문에 해당 블록(`파일:라인`)이 인용돼 있으므로 조건이 충족된다**(7-5). 전체 레포를 볼 필요가 없다.

#### 차단 3 · 기록 3

| 순위 | 방법 | 효과 | 비용 | 오탐 |
|---|---|---|---|---|
| **1** | **창 이탈 감지** (`visibilitychange`·`blur`) | **최고** | 0 | 낮음 |
| **2** | **질문 텍스트 선택 차단** (`user-select:none`) | 높음 | 0 | 없음 |
| **3** | 붙여넣기 차단 + 시도 기록 | 중 | 0 | 없음 |
| **4** | **전체화면 강제** | 중 | 낮음 | 낮음 |
| **5** | 첫 타이핑까지 지연 기록 | 조합 시 높음 | 0 | 중 |
| 6 | 타이핑 리듬 | 중 | 중 | **높음** → v2 |

#### 1 · 창 이탈 감지 — 가장 강력하다

**다른 AI에 물어보려면 반드시 창을 떠나야 한다.** 브라우저가 그걸 알려준다.

```js
document.addEventListener('visibilitychange', …)   // 탭 전환
window.addEventListener('blur', …)                 // 창 전환
```

**기록: 이탈 횟수 + 각 이탈의 지속 시간.** 알림 팝업으로 1초 blur 되는 것은 정상이고 **30초 이상 이탈**이 의미 있는 신호다.

**차단이 아니라 기록이다.** 이탈을 막으면 우회하고, 기록하면 매니저가 본다.

**이탈은 세션이 아니라 답변에 붙인다.** 세션 단위로 "이탈 3회"만 남기면 **어느 답변이 의심스러운지 알 수 없다.**

```
Q2 · L2 설계논리
  ⚠ 답변 작성 전 이탈 42초 · 복귀 후 첫 타이핑 3초 · 213자
  "…"
```

**이 한 줄이 시간 제한보다 강하다.** 제한 시간은 부정행위자를 통과시키지만(4-3), 이 기록은 **부정행위 경로를 밟았다는 사실 자체**를 남긴다 — 빨리 했든 늦게 했든.

**자동 판정은 여전히 안 한다**(아래). 플래그가 붙은 문답만 매니저 화면에 펼쳐 보여주고, 판단은 사람이 한다.

#### 2 · 질문 텍스트 선택 차단

**붙여넣기 차단의 반대편이다.** 답변 붙여넣기만 막으면 **질문을 복사해서 AI에 넣는 경로**가 열려 있다.

`user-select: none` 한 줄. 우회(스크린샷·재타이핑)는 가능하지만 마찰이 생긴다.

#### 4 · 전체화면 강제

화면 분할로 옆에 AI를 띄우는 것을 막는다. 이탈 시 경고 + 기록.

**한계:** 듀얼 모니터와 휴대폰은 못 막는다. **그래서 창 이탈 감지와 함께 써야 의미가 있다.** 전체화면만 강제하면 두 번째 모니터로 우회된다.

#### 5 · 첫 타이핑 지연 — 조합했을 때 강력하다

단독으로는 약하지만 창 이탈과 결합하면 명확한 패턴이 나온다.

```
창 이탈 40초  →  복귀  →  즉시 유창한 장문
```

**가장 전형적인 외부 조회 패턴이다.** 각 신호는 오탐이 나지만 **순서가 결합된 패턴**은 잘 나오지 않는다.

#### 배제

| | 이유 |
|---|---|
| 우클릭·개발자도구 차단 | **효과 거의 0.** 우회가 5초. 학생 불편만 |
| 웹캠 감시 | 효과는 크나 개인정보 동의·설치 부담·법적 검토. **MVP 부적합.** 이 제품은 자격시험이 아니라 학습 도구 |

**자동 부정행위 판정은 하지 않는다.** 오탐 비용이 크고 "확정은 사람이" 원칙에 걸린다. 매니저 화면에 플래그로만 띄운다.

**한계 명시:** 세션 중 다른 AI 조회를 완전히 막을 수는 없다. 실효 방어는 **코드 특정성 · 답변 단위 이탈 기록 · 꼬리질문**이다.

> **"시간 압박"을 실효 방어 목록에서 뺐다.** LLM 왕복이 1분이라 어떤 제한 시간도 부정행위자를 못 자른다(4-3). 시간을 방어로 세면 **막고 있다고 착각한 채 정직한 학생만 자르게 된다.**

**남은 방어의 성격을 정확히 말하면 "완전 차단"이 아니라 "비용 부과"다.**

| | 부정행위자가 치러야 하는 것 |
|---|---|
| 코드 특정성 | 자기 레포의 그 블록을 AI에 옮겨야 함. 붙여넣기·복사가 막혀 있어 **스크린샷 또는 재타이핑** |
| 답변 단위 이탈 기록 | 옮기러 나간 순간 **그 답변에 흔적이 남음** |
| **꼬리질문** | 같은 지점을 층마다 다시 묻는다. **매 층 나갔다 와야 하고, 이탈 기록이 층마다 쌓인다** |

**계단 구조 자체가 방어다.** 한 번 조회로 끝나는 단답형이면 이탈 1회로 끝나지만, 4층을 올라가려면 **4번 나가야 한다.** 이탈 4회 · 매번 복귀 직후 유창한 장문은 사람이 봐서 판별되는 패턴이다.

## 5. 판정

### 5-1. 통과식 — 총점을 만들지 않는다

| 층 | 방식 |
|---|---|
| **단계 진행** | **비보상 통과** — 못 넘으면 위는 의미 없음 |
| **단계 안의 질** | 루브릭 점수 (tie-break에만) |

**총합 점수제를 쓰지 않는 이유 둘.**

**① 이 구인은 보상을 허용하지 않는다.** 자기 코드가 무엇을 하는지 설명하지 못하는데 대안을 잘 알아서 총점이 높은 상태는 성립하면 안 된다. 대안 지식은 일반 지식이지 **이 코드에 대한** 이해가 아니다.

**② 총합은 결측을 0으로 만든다.** L1에서 막혀 L2~L4를 받지 않은 학생의 나머지를 0점으로 계산하면 **"못한 것"과 "안 물어본 것"이 섞인다.** 그러면 L1에서 막힌 학생이 자동으로 전원 재시험 대상이 된다. 계단에서는 **"1단에서 멈춤"이 완결된 관측값**이라 메울 빈칸이 없다.

### 5-2. 정렬 — 사전식. 가중치 없음

```
우수    도달 단계(높은 순)  →  힌트 총 횟수(적은 순)  →  루브릭 평균(높은 순) ← 내부값
위험    2단 미달 검증 개념 개수(많은 순)  →  도달 단계(낮은 순)  →  힌트 횟수(많은 순)
```

**루브릭 평균은 마지막 tie-break에만 쓰고 화면에 표시하지 않는다**(10-3). 앞의 두 키로 대부분 갈린다.

**힌트 횟수는 정렬 키일 뿐 감점이 아니다.** 힌트를 써서 도달했으면 도달이다 — 도달 단계가 먼저 걸러지고 그 안에서만 힌트가 순서를 정한다.

**화면 표기가 그대로 정렬 근거다.**

```
우수 교육생 · 김OO    4단 도달 · 힌트 0회 · 미프 3차
우수 교육생 · 이OO    3단 도달 · 힌트 1회 · 미프 3차
```

두 번째 줄을 보면 매니저가 **"이 반은 전체적으로 얕다"** 를 읽는다.

> **가중 합을 쓰지 않는 이유:** 임의 숫자에 근거가 없고, 순서 정보가 사라지며(`L1자력+L2힌트2`와 `L1힌트2+L2자력`이 같은 값), **비보상 원칙이 합산으로 무너진다.**

### 5-3. 3문제를 어떻게 합치나 — 용도마다 다르다

| 용도 | 방식 | 왜 |
|---|---|---|
| **위험 판정** | **합치지 않는다. 검증 개념 단위로 본다** | 평균 내면 보상성이 되살아난다 |
| **우수 판별** | **최저값** | 일관성이 조건 |
| **성장 추이** | 평균 | 시계열 비교용 |

**위험을 평균으로 내면 안 되는 이유**

> Service 1단 · Volume 4단 · CICD 3단 → **평균 2.7단**

괜찮아 보이지만 **이 학생은 Service를 전혀 모른다.** 한 목표에서 무너진 것을 다른 목표가 가려버린다.

**검증 개념 단위로 봐야 처방이 나온다.** "평균 2.7단"으로는 아무것도 못 하지만 **"Service에서 1단"** 이면 무엇을 다시 가르칠지가 바로 나온다.

**재시험 대상도 검증 개념 단위다.** 3문제 중 2단 이하인 검증 개념만 재시험한다.

### 5-4. 도달 경계 = 3점

**4축이 같은 척도(SOLO)로 통일되어 경계를 하나로 정할 수 있다**(부록 A).

| 점수 | | 도달 |
|---|---|---|
| 0~2 | Prestructural · Unistructural · Multistructural | **미달** |
| **3~5** | **Relational 이상** | **도달** |

**근거:** 계단의 각 단계 정의가 **"그 수준의 설명을 할 수 있다"** 이고, SOLO Relational이 **"요소들을 통합해 설명"** 이다. **Multistructural(나열)은 설명이 아니다.**

**채점 시 도달 여부와 점수를 따로 받는다.** 점수는 척도이고 도달은 판정이므로 채점기가 둘 다 출력한다. 행동 기준도 프롬프트에 함께 명시한다.

| 단계 | 도달 기준 (3점 정의와 동일) |
|---|---|
| L1 | 요소들이 **어떻게 이어지는지** 말했는가 |
| L2 | 의도와 **제약 하나**를 연결했는가 |
| L3 | 대안 **하나를 구체적으로** 말했는가 |
| L4 | **언제 문제가 되는지 조건을 특정**했는가 |

> 실측(편향된 데이터)에서 3점 이상이 71%였다. 4점 경계(29%)보다 현실적이다. **재측정에서 분포를 확인한다.**

## 6. 무엇에 대해 묻는가

### 6-1. 앵커 2층

```
검증 개념  = 무엇을 물을지   → 반 전체가 같음  (난이도·비교 가능성)
코드 지점 = 어디서 물을지   → 학생마다 다름  (개인화)
```

**두 층을 나누는 것이 핵심이다.** 검증 개념만 앵커로 쓰면 팀원 전원이 거의 같은 질문을 받는다(미프는 팀당 레포 하나일 수 있다). 같은 개념을 A는 `ingress.yaml`에서, B는 `service.yaml`에서 물으면 비교 가능성은 유지되고 개인화는 확보된다.

### 6-2. 미프 / 빅프

| | 미프 | 빅프 |
|---|---|---|
| **앵커** | **검증 개념** (교안 기반) | **본인 커밋 영역** |
| 문제 수 | 3개 | **3개** |
| 범위 | 전체 코드 | 자기 영역 |
| 성적 | 반영 | **미반영** — 성장 지표 + 팀 내부 파악 |
| 선별 | 교안 교집합 | **기존 정적 스캐너** |

**계단은 양쪽 동일하다.** 앵커만 다르다. 그래서 미프와 빅프의 도달 단계를 비교할 수 있고, 그게 성장 지표의 근거다.

### 6-3. 누가 무엇을 입력하나

**"학습목표"라는 별도 개념은 만들지 않는다.** 교안 분석 그래프가 그 자리를 대신하고, 운영자는 새로 쓰는 것이 아니라 **있는 목록에서 고른다.**

### 검증 개념 = 교안 분석이 내놓은 `teaches` 중 3건 (v1.2 정정)

**교안 분석 단계의 출력이 `질문에 사용할 teaches`다.** 화면은 그 목록에서 3개를 고르게 하는 것까지이고, 새 개념을 쓰거나 별도 분류를 만들지 않는다.

**후보를 교안 · 섹션으로 묶어 보여준다.** 합쳐서 늘어놓으면 `p.53`이 어느 교안 어느 섹션의 53쪽인지 알 수 없다. 확정한 3건은 **출처 교안과 섹션을 달고 다닌다** — 리포트의 교안 위치와 면담 브리프가 그 값을 읽는다.

**정의문을 같이 보여준다.** 이름만으로는 무엇을 묻게 될지 판단할 수 없는데, 고르는 순간 그것이 그 회차 **모든 학생의 문항**이 된다.


**교안은 프로젝트당 여러 개를 붙일 수 있다.** 한 회차가 교안 하나에만 걸치지 않는다 — LangGraph로 만들고 Streamlit으로 붙이는 미프면 두 교안이 다 재료다. 하나만 걸게 하면 **나머지 교안에서 가르친 것은 물어볼 방법이 없어진다.** `teaches` 후보는 연결한 교안 전체의 합집합이고, 확정한 3건은 **각자 출처 교안을 달고 다닌다**(7-6의 `concept`에 교안 식별자가 붙는다) — 리포트의 교안 위치와 면담 브리프가 그 값을 읽으므로 출처가 없으면 `3장 p.55`를 어느 문서에서 펼지 알 수 없다.

| 시점 | 주체 | 하는 일 | 필수 |
|---|---|---|---|
| **프로젝트 생성** | **기관 운영자** | 교안 연결(**1개 이상**) + **검증 섹션 3건 확정** | **필수** |
| 〃 | 〃 | **요구사항 붙여넣기** (교안과 별개 필드 · 8절) | 선택 |
| 체크포인트 실행 | 담당 매니저 | **없음** | — |

**매니저 선택은 폐지한다.** 이전 설계는 매니저가 체크포인트마다 검증할 3개를 골랐다.

> **폐지 근거:** 팀마다 프로젝트가 다르고, 코드 지점이 다르니 질문도 꼬리질문도 전부 다르다. **그 위에서 유일하게 공통인 축이 `teaches` 3건뿐이다.** 매니저가 반별로 다르게 고르면 그 축마저 반마다 달라져 **반끼리 비교가 불가능해진다.** 매니저도 학생 코드를 미리 보고 고르는 것이 아니라 고를 근거가 없다.

**그래서 3건은 프로젝트 단위로 고정한다.** 같은 프로젝트를 하는 모든 반·팀·개인이 같은 3개 개념으로 평가된다. 개인화는 **코드 지점**(6-1의 아래층)이 담당한다.

**`teaches` 3건과 요구사항은 완전히 별개다.**

| | 어디서 오나 | 무엇에 쓰나 |
|---|---|---|
| **`teaches` 3건** | 교안 (등록된 것) | **이해도 검증 문항 3개** |
| **요구사항** | 과제 요구사항 문서 (교안에 없음) | **구현 P/F 체크**(8절) · L3 재료 |

요구사항은 교안에서 뽑을 수 없어 운영자가 직접 붙여넣는다. **이해도 점수와 섞지 않는다**(8-3).

**PDF 자동 추출은 v1에서 만들지 않는다.** 그걸 만들면 완성 전까지 아무것도 못 하고, 실제 교안은 암호가 걸려 있어 파싱이 막힐 수 있다. **이미 등록된 교안 분석 결과의 `teaches` 목록을 그대로 후보로 띄우고 3건 고르게 하면 된다.**

### 6-4. 교안 정제 — 어휘 무관 규칙만

교안 분석 결과를 그대로 쓰면 안 된다. **정제는 전부 문자열·위치 연산이고 어휘 사전을 만들지 않는다.** 한글이든 영어든, 어떤 도메인이든 같은 규칙이 돈다.

| # | 규칙 | 예 |
|---|---|---|
| **R1** | 섹션을 **페이지 순 정렬** | 현재 뒤죽박죽 |
| **R2** | 섹션 **겹침 해소** — 소속 개념 페이지의 이상치 제거 후 재계산 | `p.77-154` · `p.95-156` · `p.128-150`이 서로 포함 |
| **R3** | **비교 항목 → 형제 엣지** — `A vs B` · `A와 B 비교` · `A 대 B` | `조건부 루프 vs Supervisor 구조 비교` 등 7건 |
| **R4** | **섹션 마지막 페이지 항목 = 요약** → 개념에서 빼고 섹션 설명으로 | `역할 기반 설계 요약` p.46 (섹션 p.37-46) |
| **R5** | **이름 포함 → 부모-자식** — A ⊂ B이고 B가 길면 B는 A의 자식 | HITL 13개가 `HITL` 아래로 |
| **R6** | 이름의 **괄호·콜론 뒤 부연 제거**, 부연은 정의로 | `면접 준비 및 진행 절차 (서류 검토 → …)` |

**추출 프롬프트(교안 분석 ②단계)에 두 가지를 추가한다.**

```
1. caution 판정 강화
   "이렇게 하면 어떤 나쁜 결과가 생기는가"를 설명하면 caution.
   "~가 필요한 이유"는 대개 "없으면 생기는 문제"이므로 caution일 가능성이 높다.

2. 출력 언어 한국어로 통일
```

> **`warns`가 현재 0건이다.** 교안에 경고 재료가 있는데 전부 concept으로 잘못 분류됐다 — `HITL이 필요한 이유(무한 재시도 비용 증가·법적 보안 사고)` · `기술 부채` · `모델 드리프트 리스크` 등. **이게 L4 질문 재료의 유일한 공급원이므로 선행 조건이다.**

## 7. 소재 선별 — 개념은 고정, 지점만 고른다. 점수 없음

### 7-1. 왜 기존 방식을 버리나

현행 선별은 `fan_in`(참조 횟수)과 정의 중복 횟수로 중요도를 정한다.

| # | 문제 |
|---|---|
| 1 | **fan_in은 공용 모듈을 가리킨다.** 공용 모듈이 되려면 범용적이어야 하고, 범용적이려면 특정 판단이 빠져 있어야 한다. **결정 밀도와 음의 상관** |
| 2 | **팀이 이미 알고 있었다.** 주석의 오탐 패치가 전부 "프레임워크 관례를 결정으로 오인" — `idiom_filter.py`의 존재 자체가 인정 |
| 3 | **denylist라 끝이 없다.** createContext → useQuery → Redux slice(미탐지) → 프레임워크 수만큼 |
| 4 | **AI 코드에 가장 관대하다.** 복붙·중복은 사람이 급할 때 나오지 AI가 짤 때 안 나온다. **잡으려는 대상에게 가장 무른 필터** |

**교안 기반은 allowlist라 유한하다.** → `idiom_filter.py`가 통째로 불필요해진다.

### 7-2. 교안 사전 (교안당 1회, LLM 0)

**`shows_code`와 `concept` 정의에 코드 식별자가 그대로 들어 있다.** 별도 사전 생성이 필요 없다.

| 항목 | 페이지 | 추출되는 식별자 |
|---|---|---|
| AgentState에 HITL 필드 추가 | p.54 | `AgentState` `TypedDict` `human_decision` `next_step` |
| HITL Trigger 조건 함수 | p.55 | `should_trigger_hitl` `max_iterations` `REJECTED` |
| SQLite DB와 테이블 생성 | p.135 | `sqlite3.connect` `cursor.execute` `commit` `close` |
| Streamlit 예제1 | p.146 | `st.title` `st.markdown` `st.button` |

**정규식 3종**

| kind | 패턴 |
|---|---|
| snake | `[a-z][a-z0-9]*(_[a-z0-9]+)+` |
| pascal | `[A-Z][a-zA-Z0-9]*[a-z][A-Z][a-zA-Z0-9]*` |
| call·attr | `[\w.]+\(\)` · `\.[a-z]\w+` |

**언어별 DENYLIST**(약 50개)와 **최소 길이 4자**로 노이즈를 거른다.

각 식별자는 **출처**(어느 개념·페이지·부모)를 갖고 간다.

### 7-3. 선별 — 확실 / 가능성으로 나눈다

**무엇을 물을지(개념 3건)는 이미 정해져 있다.** 선별이 정하는 것은 **어디서 물을지(코드 지점)뿐이다.**

```
0  개념    운영자가 확정한 teaches 3건                ← 입력. 선별 대상 아님
1  files  = find_src_files(repo)                 # 기존 함수 재활용
2  struct = tier_a_structural_scan(files)        # 기존 함수 재활용 → 고립 파일
3  hits   = grep(lexicon[3건], files)            # LLM 0 · 사전을 3건으로 좁힘
4  spans  = expand_to_block(hits)                # AST · 7-5
5  필터    형제 있음 OR gap 있음                  ← "선택이 확실한 지점"만
6  제외    고립 파일 (어디서도 import 안 됨)
7  개념별  warns 있음 → 학생 간 중복 적음 순으로 1개
8  결과    개념 1건당 지점 1개 = 3문제
```

| 신호 | 뜻 | 쓰임 |
|---|---|---|
| **형제 있음** | 교안이 대안을 가르쳤다 → **선택이 있었음이 확실** | **필터** |
| **gap 있음** | 교안 예시와 다르게 구현했다 → **선택했음이 확실** | **필터** |
| warns 있음 | 갈림길이 있었다 | 순서 |
| 매직넘버·비자명 분기 | 값·조건을 골랐다 | 폴백 |

**개념별 1개는 다양성 휴리스틱이 아니라 구조다.** 개념 3건이 고정 입력이므로 **3문제 = 3개념**이 자동으로 성립하고, 한 개념에서 2개를 뽑을 여지 자체가 없다(폴백 제외 · 7-7).

**팀당 레포가 하나여도 팀원끼리 문제가 갈린다.** 7단계에서 같은 팀 안의 이미 배정된 지점을 피하기 때문이다. 개념은 같고 지점은 다른 것이 6-1의 설계 그대로다.

**고립 파일 제외가 중요하다.** 교안 개념이 매칭됐어도 그 파일이 어디서도 import되지 않으면 **동작하지 않는 코드**다. 기존 `cognition-isolation`이 여기서 정반대 용도로 살아난다.

### 7-4. 단계별 재료 매핑

| 턴 | 축 | 교안 재료 |
|---|---|---|
| **L1** | 코드이해 | `concept` 정의 |
| **L2** | 설계논리 | **`gap`** — 교안 예시와 다르게 한 부분 → "왜 그렇게?" |
| **L3** | 대안비교 | **`siblings`** — 형제 개념 |
| **L4** | 반례대응 | **`warns`** — 교안 경고 |

**L3·L4가 선택 구간이라 `siblings`·`warns`가 질문으로 쓰이는 빈도는 낮다.** 그러나 **선별 필터·순서에는 항상 쓰인다.** 선별 신호와 질문 재료가 같을 필요는 없다.

### 7-5. 블록 확장 — 파일이 아니라 지점

```python
def expand_to_block(file, line):
    if file.ext == ".py":
        tree = ast.parse(source)
        return innermost(FunctionDef|ClassDef containing line)
    else:
        return brace_or_indent_fallback(file, line)   # 못 찾으면 line ± 15
```

**200줄 초과 시 `line ± 30`으로 자른다**(거대 함수 방어).

**파일을 주면 학생이 "여기서 뭘 묻는 거지"를 먼저 찾아야 하고, 그 시간은 이해도가 아니라 코드 리딩 속도를 잰다.**

### 7-6. 출력

```json
{
  "file": "nodes.py", "lines": [12, 18], "code": "…",
  "concept":  { "name": "HITL Trigger 조건 함수", "page": 55, "parent": "HITL",
                "definition": "should_trigger_hitl 함수는 …" },
  "siblings": [{ "name": "HITL Design Checklist과 사용자 부담 Trade-off", "page": 58 }],
  "warns":    [{ "name": "HITL이 필요한 이유", "page": 49,
                 "text": "무한 재시도로 인한 비용 증가 …" }],
  "gap":      { "expected": ["위험키워드","REJECTED","max_iterations"],
                "found": ["REJECTED","max_iterations"],
                "missing": ["위험키워드"] },
  "context":  { "imported_by": ["graph.py"] }
}
```

**`gap.missing`이 L2 질문의 직접 재료다.** *"교안은 세 조건을 봤는데 여기선 두 개만 보네요. 왜 그렇게 하셨나요?"*


### 7-7. 폴백

**폴백은 개념마다 따로 돈다.** 개념 3건이 고정이므로 "3개를 채운다"가 아니라 **"각 개념에서 지점 1개를 찾는다"** 이다.

```
개념 1건에 대해
  형제 or gap 있는 span  →  있으면 끝
    ↓ 없음
  warns만 있는 span
    ↓ 없음
  매직넘버·비자명 분기만 있는 span
    ↓ 없음
  기존 스캐너 (architecture-diffusion만. duplicate-definition 제외)
    ↓ 0개
  그 개념은 "코드에 없음" 표시 → 문항에서 빠짐
```

**"교안 없음" 경로는 존재하지 않는다**(6-3). 교안은 항상 연결돼 있으므로 폴백은 **"교안은 있는데 코드 매칭이 0개"** 뿐이고, 그 자체가 신호다.

**한 개념이 코드에 없으면 그 문항은 만들지 않는다 — 다른 개념에서 2개를 뽑아 채우지 않는다.** 채우면 학생마다 개념 구성이 달라져 비교 축이 무너진다. **2문제로 진행하고 매니저·운영자 화면에 `개념 N — 코드 매칭 0`을 남긴다.** 팀 전원에서 같은 개념이 비면 그건 학생 문제가 아니라 **개념 선택이 프로젝트와 안 맞았다는 신호**다(다음 프로젝트에서 운영자가 교체).

### 7-8. 기존 자산 처분

| 자산 | 처분 |
|---|---|
| `tier_a_structural_scan` | **재활용** — 고립 파일 제외 · 문맥 제공 |
| `find_hub` / fan_in 중요도 | **폐기** (7-1) |
| `find_duplicate_definitions` | **폐기** — 중복은 실수지 결정이 아니다 |
| `idiom_filter.py` | **폐기** — allowlist로 바뀌어 불필요 |
| `find_architecture_diffusion_point` | **폴백에서만** |
| `tier_b_risk_triggered_scan` (보안) | 이해도 경로에서 제외 |

## 8. 요구사항 P/F

**요구사항은 선택 입력이다.** 교안과 별개 필드로 둔다 — 요구사항은 "무엇을 만들었나"(맥락)이고 교안은 "무엇을 배웠나"(측정 대상)다.

### 8-1. 로직 (LLM 2회, 요구사항 있을 때만)

```
1  items = 요구사항.split("\n")             # 한 줄에 하나
2  [LLM 1] items → 후보 키워드 5~8개        # 영/한, camelCase 변형 포함
3  grep → item별 후보 파일 상위 3            # LLM 0
4  [LLM 1] 후보 블록만 넣어 판정
```

### 8-2. 출력 — 시스템이 정하고 이유를 말한다

```
 ✓  좋아요 버튼    버튼을 누르면 서버에 저장까지 이어집니다
                   LikeButton.tsx:8-24 · api/like.ts:12
 ✓  댓글 작성      입력한 내용이 저장되고 목록에 나타납니다
                   CommentForm.tsx:15-40
 ✗  정렬 기능      정렬 값을 담을 자리는 만들었지만 쓰이지 않았어요
                   BookList.tsx:55 · setSortBy를 부르는 곳이 없음
 ✗  검색           관련된 코드를 찾지 못했어요
```

| verdict | 조건 | 화면 문구 |
|---|---|---|
| **P** | 이름 매칭 + **동작 연결**(핸들러 → 상태 변경 또는 API 호출) | 무엇이 이어지는지 |
| **F** | 관련 변수·타입만 있고 **쓰이지 않음** | `자리는 만들었지만 쓰이지 않았어요` |
| **F** | 이름만 있고 본문이 비었거나 TODO | `함수는 있지만 안이 비어 있어요` |
| **F** | 매칭 0 | `관련된 코드를 찾지 못했어요` |

**`?`(확인 필요) 등급을 두지 않는다.** 이전 판은 애매한 경우를 매니저 확인으로 넘겼는데,
**매니저는 강사가 아니라 코드를 보고 판단할 수 없다**([16번](16-intervention-design.md) 0절).
판단할 수 없는 사람에게 넘기면 아무도 결정하지 못하고 `?`가 영원히 남는다.

**대신 P 조건을 좁힌다.** `handleLike`가 껍데기만 있으면 동작 연결이 없으므로 F다 —
False Positive를 등급이 아니라 **판정 기준**으로 막는다.

**시스템이 정하고 이유를 말한다.** 매니저는 그 문장을 읽고 학생에게 전달한다.

### 8-3. 이해도 점수와 섞지 않는다

**"구현했는가"는 산출물 검사이지 이해도 측정이 아니다.** 구현했다고 이해한 것도 아니고(AI가 짜줬을 수 있음), 안 했다고 이해 못 한 것도 아니다(시간이 없었을 수 있음).

**쓸모는 셋.**

| | |
|---|---|
| 진도 파악 | 매니저가 "이 팀이 어디까지 왔나"를 안다 |
| 소재 필터 | **P인 것만 물어야 한다** — 안 만든 걸 물으면 답할 게 없다 |
| **L3 재료** | **미구현이 좋은 대안비교 질문이다** — "검색은 왜 안 하셨나요?" |

## 9. 위험·우수 판정

### 9-1. 위험 — 절대 기준

**2단 이하인 검증 개념이 있으면 처방 대상.** 검증 개념 단위로 본다(5-3).

기준에 못 미치면 도와야 하므로 절대 기준이 맞다. 반 평균이 낮아도 못하는 사람은 못하는 것이다.

**개수에 따라 하는 일이 다르다.**

| 2단 이하 개념 | |
|---|---|
| **1개** | 그 개념만 **재시험**(11절). 위험 유형은 안 붙는다 |
| **2개 이상** | 재시험 + **위험 유형 판정**(9-2) — 직전 회차와 비교 |

**1개를 위험으로 올리지 않는 이유:** 3문제 중 1개는 흔한 변동이다. 전부 위험으로 올리면 목록이 반 절반이 되어 **매니저가 목록을 안 본다.**

### 9-2. 위험 유형

| 이름 | 정의 | 최소 표본 |
|---|---|---|
| **단계 하락** | **2단 이하 개념 개수가 0~1 → 2 이상**으로 늘어남 | 미프 2개 |
| **지속 저점** | **2회 연속 2단 이하 개념이 2개 이상** | 미프 2개 |
| **무효 응시** | 0단 (9-4) | 1개 · 즉시 |
| **코드 대비 이해 부족** | 빅프 — 기여도 높음 · 도달 단계 낮음 | 빅프 1회 |
| **참여 저조** | 빅프 — 기여도 낮음 · 도달 단계 낮음 | 빅프 1회 |

**두 유형 모두 "2단 이하 개념 개수"라는 한 가지 값으로 정의한다.** 도달 단계 평균이나 하락 폭 같은 파생값을 쓰지 않는다 — 5-3에서 평균을 금지한 이유가 여기서도 그대로 적용된다.

```
프로젝트마다  n = (2단 이하인 개념 개수)   ∈ 0 ~ 3

단계 하락   n(이전) ≤ 1  이고  n(이번) ≥ 2
지속 저점   n(이전) ≥ 2  이고  n(이번) ≥ 2
```

**한 번 떨어졌다고 하락이 아니다.** 3개 중 1개가 2단인 것은 흔한 변동이고, 미프마다 소재·팀·코드가 바뀌므로 개념 하나쯤은 흔들린다. **2개 이상이면 3문제 중 과반이라 변동으로 보기 어렵다.**

**두 유형은 배타적이다.** `n(이전)`이 1 이하면 하락, 2 이상이면 지속 저점 — 같은 학생이 같은 회차에 둘 다로 잡히지 않는다. 처방이 다르기 때문이다: 하락은 **이번 프로젝트에서 무슨 일이 있었나**를 묻고, 지속 저점은 **누적된 공백**을 본다.

**"기초 공백"이 아니라 "지속 저점"인 이유** — 데이터가 말해주는 것은 "계속 낮다"(결과)이지 "기초가 비어 있다"(원인)가 아니다. 계속 낮은 이유는 기초 부족일 수도, 참여 부족일 수도, 말로 설명하는 게 약한 것일 수도 있다. **원인을 이름에 박으면 매니저가 진단을 건너뛰고 처방부터 한다.**

**빅프 유형과는 겹칠 수 있다.** 정렬은 5-2의 사전식.

### 9-3. 우수 교육생 — 반 상위 1~2명

**반마다 존재한다.** 정렬(5-2) 상위 1~2명. 3문제 중 **최저값**으로 비교한다.

**상대 기준인 이유:** 용도가 상대적 질문이다. "누구를 팀 리더로 쓸까", "이 반에서 눈여겨볼 사람이 누구인가"는 그 반 안에서의 비교다. 매니저가 25명 중 진짜 눈여겨볼 사람은 1~2명이고, 3명을 넘어가면 실용 가치가 떨어진다.

**근거를 함께 표시한다.** `우수 교육생 · 김OO — 4단 도달 · 힌트 0회 · 미프 3차`

**프로젝트별로 따로 뽑는다.** 미프 6~8회 × 반당 1~2명이면 **프로젝트별 프로필**이 쌓인다. 팀 구성에 쓰는 것은 우수 명단이 아니라 그 프로필이다.

**담당 매니저 화면에도 노출한다.** 우수 정보를 매니저가 본다.

### 9-4. 무효 응시 (0단)

**채점하지 않고 판정과 평균에서 뺀다.**

> **실측 오분류:** 어떤 학생은 5개 축이 전부 1점이었는데, 첫 답변이 `"시간이라는 형식이 깨지지 않기 위해서입니다"` 한 문장이고 마지막 답변은 **질문 문장을 그대로 복사해 붙인 것**이었다. **실력이 아니라 응시를 안 한 것**인데 시스템은 "전 항목 1점"이라는 실력 판정을 냈다. **같은 학생이 다른 세션에서는 4~5점을 받았다.**

#### 원칙 — 내용이 아니라 행동으로 판정한다

**내용으로 판정하면 "못하는 학생"과 "안 하는 학생"이 섞인다.** 위 실측이 정확히 그 사례다.

#### 즉시 무효 — 단일 신호로 충분

| 신호 | 판정 근거 |
|---|---|
| **무응답·공백** | 명백 |
| **질문 복붙** | 답변과 질문의 유사도 0.7 이상. **실측 사례 존재** |
| **의미 없는 문자열** | `ㅁㄴㅇㄹ` `asdf` · 같은 글자 3회 이상 반복 |
| **3문항 동일 답변** | 문항이 다른데 답이 같을 수 없다 |

#### 복합 무효 — 2개 이상 동시 발생

| 신호 | 임계 (가정값) |
|---|---|
| 응답 길이 | **15자 미만** |
| 소요 시간 | 질문당 **20초 미만** |
| 첫 타이핑 지연 | **5초 미만** (읽지도 않음) |

**단일 신호로 확정하지 않는 이유:** 짧은 답변 하나로 무효 처리하면 **간결하게 답한 학생**이 걸린다. 실측에서 1점을 받은 답변이 `"시간이라는 형식이 깨지지 않기 위해서입니다"`(24자)였는데 **짧지만 시도는 했다.** 그건 무효가 아니라 1단 미달이다.

**소요 시간 임계의 근거:** L1 질문이 3문장이면 **읽는 데만 20~30초**다. 20초 미만은 읽지 않았다는 뜻이다.

#### 매니저 확인 대상이다

**자동 확정하지 않는다.** 무효 처리는 그 문항의 결과를 지우는 것이라 오탐 비용이 크다. 목록에 올리고 매니저가 확인한다.

**위험 목록에 눈에 띄게 올린다.** 못하는 것보다 안 하는 것이 더 급하고 개입 방법도 다르다.

### 9-5. 유형이 켜지는 시점

| 시점 | |
|---|---|
| 미프 1차 | **"관찰"** — 유형 없이 `2단 이하 개념 n개`만 표시 |
| 미프 2차 | **단계 하락 · 지속 저점 둘 다 확정** (이전 회차 1개면 충분) |

**둘 다 미프 2차에서 켜진다.** 정의가 직전 회차 하나만 참조하기 때문이다(9-2). 3차까지 기다리면 **미프 6~8회 중 초반 3회를 관찰만 하고 흘려보낸다.**

미프가 4~7일씩이니 **1차 관찰은 1주차, 확정은 2주차**다.

### 9-6. 집단 미달 처리

**한 검증 개념에서 반 절반 이상이 미달하면 개인 위험 사유에서 제외하고 반 단위로 표시한다.**

매니저가 12명에게 똑같은 면담을 개별로 잡는 일을 막는다. 이후 처리는 기관 판단이다 — 시스템은 표시까지만 한다.

가능한 후속: 반 전체 공지 한 번(교안 위치 안내) · 다음 프로젝트 검증 개념에 재투입 · 기수 리포트에 기록.

## 10. 검증 시점과 리포트

### 10-1. 미프 — 세션은 분산, 리포트는 일괄

```
학생 제출 → 코드 분석 → [분석 완료] ──24시간──▶ 세션 응시 창    ← 분산
                                          ↓
                          미프 마감 → 리포트 일괄 발행           ← 매니저는 한꺼번에
```

**24시간의 기산점은 제출이 아니라 코드 분석 완료다.** 문항은 분석 결과(교안 매칭 지점)로 만들어지므로 **분석이 끝나기 전에는 응시할 것 자체가 없다.** 제출 기준으로 재면 분석에 2시간 걸린 학생과 20분 걸린 학생의 실제 응시 시간이 달라진다.

**응시 창이 열리면 학생에게 알린다.** 학생이 상태를 폴링하지 않게 한다.

**세션을 제출 직후에 붙이는 이유:** 시간이 지나면 **"잊어서 못 답한 것"과 "이해 못 한 것"이 섞인다.** 미프는 4~7일짜리라 하루만 지나도 세부가 날아간다.

**부수 효과:** 먼저 끝낸 학생이 먼저 봐서 자연 분산되고, 리포트를 마감 후 일괄 발행하면 먼저 본 학생이 답을 흘리는 경로도 줄어든다.

### 10-2. 빅프 — 3회, 2주 간격

**첫 측정은 주차가 아니라 "첫 동작하는 코드가 나온 시점"** 이다.

| 회차 | 시점 | 역할 |
|---|---|---|
| 1 | 첫 기능 동작 | **기준점** |
| 2 | +2주 | **개입 트리거** — 고칠 시간이 남는다 |
| 3 | 마감 | 성장 확인 |

**줄여야 하면 3회차를 뺀다.** 성장 확인은 나중에 해도 되지만 개입 기회는 지나가면 없다.

**미프·빅프는 순차다.** 미프가 앞에서 몇 개월, 빅프가 마지막 8주. 일정 충돌이 없다.

### 10-3. 리포트

| | 학생 | 매니저 |
|---|---|---|
| 종합 | 검증 개념별 도달 상태 + 서술 | 문제 3개 종합 |
| 문제별 | **전체 문답 + 어디서 막혔는지 해설** | **요약 + 핵심만** |
| 교안 | 참고 위치 | 같음 |
| 점수 | **없음** | **없음** — 도달 단계 + 축별 서술 |
| 원문 문답 | 있음 | **화면에 없음 (저장은 함)** |

**원문은 반드시 저장한다.** 이의 조사·기능 추가·재채점 실험의 입력이 전부 원문이다. 화면에서 경로를 안 여는 것뿐이다.

#### 숫자 점수는 어느 화면에도 없다 — 학생·매니저·운영자 전부

**0~5 루브릭 점수는 내부 값이다.** 저장하고, 정렬 tie-break에 쓰고(5-2), 재채점 실험에 쓴다. **화면에는 나오지 않는다.**

| | 화면에 나오는 것 | 화면에 없는 것 |
|---|---|---|
| 값 | **도달 단계**(0~4단) · 힌트 횟수 · 축별 **서술** | 축별 0~5점 · 평균 · 총점 · 백분위 |

> **근거:** 총점을 만들지 않기로 한 이상(5-1) 화면에 남은 숫자는 **합칠 수 없는 숫자**다. `코드이해 3 · 설계논리 3 · 대안비교 5 · 반례대응 4`를 본 사람은 반드시 머릿속에서 평균을 내고, 그 순간 비보상 원칙이 사용자 머릿속에서 무너진다. 15-2 검증이 정확히 이걸 묻는다.
>
> **그리고 4단 도달 + 힌트 0회는 이미 서열 정보를 다 담고 있다.** 점수를 병기하면 정보가 늘지 않고 해석만 갈린다.

**대신 축별 서술(`evidence`)을 보여준다.** 매니저가 읽는 것은 그 문장이다(부록 A).

> "Service와 Ingress의 역할 분리에서, 왜 그렇게 했는지는 설명했지만 다른 방법이 있는지는 확인되지 않았습니다. 교안 3장(36~46쪽)을 보고 다시 응시하세요."

**히트맵은 학생에게 보여주지 않는다.**

### 10-4. 피드백은 막힌 만큼 두꺼워진다

계단은 학생마다 다른 수의 질문을 준다. 그대로 두면 **도움이 가장 필요한 학생이 가장 적게 받는다.**

**막힌 단계의 해설과 교안 위치를 리포트에서 제공한다.**

| | 측정 | 피드백 | 총량 |
|---|---|---|---|
| 못하는 학생 | 짧음 (18분) | **두꺼움** | 비슷 |
| 잘하는 학생 | 김 (66분) | 얇음 | 비슷 |

**종료 문구도 바꾼다.** `"세션이 종료되었습니다"` → **`"이 부분은 리포트에서 자세히 설명해드릴게요"`**. 비용 0.

### 10-5. 교육생 리포트 아카이브

**신설한다.** 프로젝트별 목록 → 리포트 상세(1차 / 재시험 나란히).

## 11. 재시험

| | |
|---|---|
| 대상 | **도달 2단 이하 전원** |
| 문항 | **같은 문항** |
| 힌트 | **없음** — 자력만 |
| 횟수 | 검증 개념당 **1회** |
| 판정 반영 | **없음.** 조직 단위 수치는 1차만 |
| 통보 | 리포트와 **동시** |
| 응시 창 | **3일 또는 다음 프로젝트 제출일 중 빠른 쪽** |

| 상태 | 재시험 | 개입 |
|---|---|---|
| 무효 응시(0단) | **재응시** — 1차로 취급 | 면담 |
| 1단 | **재시험** | 개입 |
| 2단 | **재시험** | 위험 판정에 따라 |
| 3~4단 | 없음 | 없음 |

**재시험과 개입은 별개로 병행한다.** 도달 단계가 낮다고 재시험 기회를 빼지 않는다.

### 응시 창 — 3일과 다음 제출일 중 빠른 쪽

```
리포트 발행 ──┬── +3일 ─────────────────▶  둘 중
              └── 다음 프로젝트 제출일 ─▶  먼저 오는 날 마감
```

**3일을 두는 이유:** 리포트를 읽고 교안을 다시 보는 데 필요한 최소 시간이다. 하루면 못 보는 학생이 나온다.

**다음 제출일로 자르는 이유:** 미프가 4~7일 간격이라 3일을 그대로 두면 **다음 미프 마감과 재시험이 겹친다.** 겹치면 학생은 다음 과제를 우선하고 재시험은 미응시가 되며, 그 미응시가 다시 위험 신호로 잡혀 **시스템이 만든 위험**이 된다.

**두 기한이 겹칠 만큼 촘촘한 회차는 창이 1~2일로 줄어든다.** 그건 의도한 결과다 — 재시험은 판정에 반영되지 않으므로(위 표) 짧은 창이 성적을 깎지 않는다.

### 같은 문항을 쓸 때의 귀결 — 명시해야 한다

**① 재시험은 재측정이 아니라 "리포트를 읽고 이해했는가"를 확인하는 것이 된다.** 그래서 어떤 집계에도 쓰지 않는다.

**② 리포트가 답안지가 될 수 있다.** 학생 리포트에 문항별로 "어디가 부족했는지"가 들어가는데, 같은 문항을 다시 내면 그걸 보고 답할 수 있다.

### 완화 장치 — 상세 해설을 재시험 후에 공개

```
1차 리포트
  ├ 도달 단계 · 어디서 막혔는지      ← 즉시 공개
  ├ 교안 참고 위치                    ← 즉시 공개
  └ 문항별 상세 해설                  ← 재시험 대상 문항은 재시험 후
```

**"무엇을 공부해야 하는지"는 주고 "정답"은 안 주는 것**이라 학습 목적은 유지되고 답안지 문제만 사라진다. 리포트 섹션 조건부 노출이라 개발 비용이 낮다.

**재시험에는 힌트를 주지 않는다.** 1차에서 재진술을 받았어도 재시험은 자력만으로 본다. 같은 문항이므로 이미 두 번 들은 셈이다.

**재시험 결과를 평균에 섞지 않는 이유:** 재시험은 못한 학생만 본다. 그 개선치를 섞으면 **하위권 개선분만 평균을 위로 밀어 올린다.**

**재시험 해제는 별도 기능을 만들지 않는다.** 자동 지정 + **매니저가 발송 버튼을 누른다.** 목록에서 체크를 풀면 제외된다.

## 12. 화면

### 12-1. 히트맵 — 열 머리가 2단이다

| | |
|---|---|
| **행** | 조직 단위 (기수 → 반 → 팀 → 개인) |
| **열 1단** | **프로젝트** (미프 1차 · 2차 …) |
| **열 2단** | 그 프로젝트의 **검증 개념 3개** |
| 값 | 평균 도달 단계 |

```
              │      미프 1차       │      미프 2차       │
              │ HITL  Graph  State  │ 배포   모니터  RAG  │
──────────────┼─────────────────────┼─────────────────────┤
  A반         │  3.2   2.8    3.5   │  2.1    3.0   2.4   │
  B반         │  3.0   3.1    2.9   │  2.8    3.2   3.0   │
```

**프로젝트를 열 머리로 올려야 하는 이유:** 검증 개념은 **프로젝트마다 다른 3건**이다(6-3). 개념만 한 줄로 늘어놓으면 미프 1차의 `HITL`과 미프 2차의 `배포`가 같은 층에 붙어 **어느 프로젝트의 개념인지 사라지고, 서로 다른 시점의 값이 나란히 비교 가능한 것처럼 보인다.**

**가로가 시간축이 된다.** 왼쪽에서 오른쪽으로 읽으면 그게 성장 추이고, 9-2의 단계 하락이 화면에서 그대로 보인다.

**빈 칸이 정상이다.** 아직 안 한 프로젝트, 코드 매칭 0인 개념(7-7)은 회색으로 비운다. **0단과 다른 색이어야 한다** — 미응시·미실시를 0점으로 읽히게 하면 14-1이 무너진다.

**기술영역 개념은 삭제한다.** 라벨도 히트맵 축도 만들지 않는다. 검증 개념이 그 역할을 한다.

**드릴다운은 행에서 한다.** 기수 → 반 → 팀 → 개인. **프로젝트가 열로 올라가서 행 계층에서 빠졌다** — 이전 설계는 프로젝트를 행 드릴다운 단계에 뒀다.

**규모:** 행 10반 × 열(미프 8회 × 3개념) = 240칸. 프로젝트 단위 접기/펴기로 폭을 줄인다.

### 12-2. 위험·우수 통합 테이블

| | |
|---|---|
| 프로젝트 | **반드시 하나 선택.** "전체" 없음 |
| 기본 | 위험만 · 위험 정렬 |
| 우수 | 세그먼트 토글. **담당 매니저에게도 노출** |

**프로젝트를 반드시 고르게 하는 이유:** "프로젝트마다 판정이 달라진다"가 이 화면의 전제인데, 그렇다면 프로젝트 없는 통합 판정은 정의상 의미가 없다.

### 12-3. 기관 운영자 화면

| 화면 | 매니저 | 운영자 |
|---|---|---|
| 대시보드 | 담당 반 | 기수 전체 + 반 필터 |
| 위험·우수 | 담당 반 | 전체 + 반 필터 |
| 히트맵 | 담당 반 → 팀 → 개인 | **기수 → 반** → 팀 → 개인 |
| 운영 관리 | 없음 | 기수·반·명단·매니저 배정 |
| AI 비용 | 없음 | 기관 총량 + 기수/반 |
| **검증 개념 3건 확정** | **없음 (읽기만)** | **프로젝트 생성 시 전체** |

**호칭을 통일한다** — 총괄 매니저 → **기관 운영자(Operator)**.

## 13. 인프라

### 13-1. 학생 API 키 — 발급하지 않는다

```
브라우저 ──(로그인 토큰)──▶ 서버 ──(플랫폼 키 1개)──▶ LLM
                              └─▶ 사용량 기록 (user_id·모델·토큰)
```

**"플랫폼이 발급해서 매핑"도 위험이 같다.** 발급한 키가 쓰이려면 결국 브라우저에 내려가야 하고, 그 순간 탈취 가능성은 동일하다. **키가 서버 밖으로 안 나가는 구조라면 그건 이미 "학생 키"가 아니라 사용량 표시일 뿐이다.**

**절반은 되어 있다** — 프록시 서버가 이미 있다. 키를 서버 비밀값으로 옮기고, 요청마다 로그인 토큰을 확인하고, 프론트에서 키 입력칸을 삭제하면 된다.

**부수 효과:** 학생이 키를 갖고 있으면 모델을 바꿔 부를 수 있어 **채점 모델 고정이 불가능**하다. 서버 호출이면 강제할 수 있다.

### 13-2. GitHub 접근

**GitHub App 조직 설치.** 운영자가 1회 승인하면 기관 레포 전체가 커버된다. 학생 개인 토큰(PAT)은 받지 않는다. 조직 밖 레포는 ZIP 업로드(이미 구현).

### 13-3. 토큰 한도

```
학생 1명 체크포인트 = 미프 6~8 + 빅프 3 = 9~11회
세션 = 11회 × 문제 3개 = 33세션
기수 = 250명 × 33 = 약 8,300세션
```

| 층 | 한도 | 막는 것 |
|---|---|---|
| 세션당 토큰 | 상한 설정 | 한 세션 폭주 |
| 학생·체크포인트당 | 4세션분 | 반복 호출 남용 |
| 기관·월 | 계약 기준 | 청구 사고 |

**초과 시 동작은 기존 규칙을 쓴다** — "세션 시간 상한 초과 시 완료 DP 기준 저장". 토큰 축만 추가한다.

**이상 사용은 절대량이 아니라 증감으로 본다.**

### 13-4. 비용 가시성

| 역할 | 범위 |
|---|---|
| 서비스 업체 | 전 기관 · 모델별 단가 · 증감 |
| 기관 운영자 | 자기 기관 총량 + 기수/반 |
| **매니저** | **안 봄** |

매니저에게 비용을 보여주면 **"비싸니까 세션 짧게"** 라는 잘못된 압력이 생긴다.

### 13-5. 채점 모델

**채점은 플랫폼 고정.** 서비스 업체만 변경하고, 변경 시 전 기관 재캘리브레이션.

**질문 생성·요약은 3티어 추상화**("정확도 우선 / 균형 / 비용 우선"). 티어↔모델 매핑은 플랫폼이 관리하므로 모델이 단종돼도 기관은 아무것도 하지 않는다.

> **근거:** 모델 교체가 실제로 파이프라인을 깨뜨린 이력이 코드 주석에 있다 — 출력 길이 예산 부족으로 채점 결과가 문장 중간에 끊기는 사고가 6번 중 3번 발생했고, 실제 사용자 세션이 종료됐다.

`Score`에 `model_version`·`prompt_version`·`rubric_version`에 더해 **`calibration_version`을 저장**한다. 버전이 다른 점수끼리는 화면에서 비교를 막는다.

## 15. 검증 — 개발 전에 할 것

### 15-1. 있는 테스트 기록으로는 이 문서를 검증할 수 없다

그 8세션은 계단으로 물어본 게 아니라 **코드에서 따로 뽑은 독립 질문 세 개**였고, 루브릭도 지금 것이 아니며 소재도 교안과 무관했다.

| 그 기록으로 확인된 것 | 확인 안 되는 것 |
|---|---|
| 축 두 개가 같은 답변으로 같은 점수 | 계단이 나은가 |
| 질문에 보기가 붙으면 만점 | 도달 경계를 어디로 |
| 무성의 응답이 실력 1점으로 | 난이도가 적정한가 |
| 자기수정이 다른 축과 무상관 | 학생을 잘 구분하는가 |

**왼쪽이 이 문서 3·4·5·9절의 근거다.**

### 15-2. 검증 A · 표현이 읽히는가 (30분, 데이터 불필요)

같은 상태를 두 방식으로 적어 나란히 놓고 **개발 안 하는 팀원**에게 하나만 묻는다.

> **①** 코드 이해 3 · 설계 논리 3 · 대안 비교 5 · 반례 대응 4
> **②** 왜 그렇게 했는지까지는 설명했으나, 다른 방법이 있는지는 설명하지 못함 **(2단)**
>
> **"이 학생에게 무엇을 해줘야 할 것 같나요?"**

①을 보고 답을 못 하거나 사람마다 다른 말을 하면 그 표현은 실패다.

> **①은 이미 화면에서 뺐다**(10-3). 이 검증은 "①이냐 ②냐"를 고르는 것이 아니라 **②의 문장이 실제로 행동으로 이어지는지**를 확인하는 것으로 목적이 바뀐다. ②를 보고도 무엇을 해줄지 못 말하면 서술 템플릿을 다시 쓴다.

### 15-3. 검증 B · 계단이 실제로 계단인가 (1시간)

**LLM도 코드도 필요 없다.** 팀원 2~3명이 각자 자기가 최근에 쓴 코드 한 군데를 고르고, 다른 사람이 순서대로 묻는다.

```
1  이게 무슨 일을 하는 코드인가요? 어디랑 연결되나요?
2  왜 그렇게 했나요? 무엇을 고려했나요?
3  다른 방식으로 할 수도 있었을까요?
4  (상황을 던지고) 이러면 어떻게 되나요?
```

묻는 사람은 **"여기까지 됐다 / 여기서 막혔다"** 만 표시한다.

| 관측 | 대응 |
|---|---|
| 순서가 안 뒤집힘 · 판정 일치 | **계단으로 간다** |
| **특정 순서가 일관되게 뒤집힘** | **순서를 교체한다** (폐기 아님) |
| 사람마다 다른 순서로 뒤집힘 | 계단을 버리고 5축을 다듬는다 |

**집중해서 볼 것: L3 ↔ L4 (대안비교 ↔ 반례대응).** 실측 성립률이 2/5로 가장 약하다. 역전이 반복되면 두 층을 병렬로 묶는다(1층 / 2층 / **3층 병렬**).

### 15-4. 통과 후 착수 순서

| 순위 | 작업 | Tier |
|---|---|---|
| 1 | L1 질문을 WHAT으로 · **한 턴 한 질문** · 보기 제거 | 1 |
| 2 | 교안 `caution` 판정 강화 · 비교 항목 → 형제 엣지 | 1 |
| 3 | `shows_code`·`concept`에서 식별자 추출 → grep 선별 | 1 |
| 4 | 시간 안내 + 붙여넣기 차단 | 1 |
| 5 | 프로젝트 생성 — 교안 `teaches` 3건 선택 UI + 요구사항 붙여넣기 칸 | 1 |
| 6 | 도달 단계 저장 · 힌트 기록 · 판정 | 2 |
| 7 | 리포트·히트맵을 도달 단계 기준으로 | 2 |
| 8 | `idiom_filter` · `duplicate-definition` 제거 | 2 |

**1~5가 전부 Tier 1이고 프롬프트·정규식·입력칸이다.** 검증 결과와 무관하게 지금 할 수 있다.

### 15-5. 마지막 — 재측정

**팀원 7명이 교안 기반 코드로 응시한다. 7명 × 3문제 = 21세션.**

학생 없이 가능하고, 이번엔 조건이 맞으므로(교안 기반 · 검증 개념 앵커 · 문항을 고르지 않음) **여기서 나온 분포로 도달 경계를 정한다.** 2인 독립 채점을 겸하면 골든셋 초안이 된다.

## 부록 A · 채점 기준 · 4축 × 0~5

### 공통 척도 — 모든 축이 같은 구조로 나뉜다

```
0  Prestructural      요점을 놓침
1  Unistructural      한 가지만
2  Multistructural    여러 개를 나열하나 연결 없음
3  Relational 하      연결해서 설명                ← 도달 경계
4  Relational 상      정확한 연결 + 근거
5  Extended abstract  다른 맥락으로 일반화·전이
```

**축 간 비교가 가능해야 도달 경계를 하나로 정할 수 있다.** 그것이 계단 구조가 요구하는 조건이다.

### L1 · 코드이해

| | |
|---|---|
| **0** | 답이 질문과 무관하거나 `"그냥 이렇게 했습니다"` 수준 |
| **1** | 구성 요소를 **하나만** 언급. 나머지는 모름 |
| **2** | 여러 요소를 **나열하나 연결 관계를 설명 못 함** |
| **3** | 요소들이 **어떻게 이어지는지** 설명 (일부 불명확해도) |
| **4** | 구성 요소 간 관계와 **데이터 흐름을 정확히** 설명 |
| **5** | 그 구조가 **왜 그렇게 될 수밖에 없는지**까지 (프레임워크 제약·패턴) |

### L2 · 설계논리

| | |
|---|---|
| **0** | 왜 그렇게 했는지 **설명 자체를 못함** |
| **1** | `"필요해서"` 수준. 이유가 하나뿐이고 구체성 없음 |
| **2** | 고려사항을 **나열하나 선택과 연결되지 않음** |
| **3** | 의도와 **제약 하나**를 연결 |
| **4** | 의도와 **여러 제약**을 연결. **트레이드오프를 인식** |
| **5** | **다른 상황이었다면 다르게 했을 것**임을 조건부로 설명 |

### L3 · 대안비교

| | |
|---|---|
| **0** | **대안이라는 개념 자체를 이해하지 못함** |
| **1** | `"다른 방법이 있을 것 같다"` 수준. 구체성 없음 |
| **2** | 대안 **이름은 대나** 어떻게 다른지 설명 못 함 |
| **3** | 대안 **하나를 구체적으로** 설명 |
| **4** | 대안과 현재 방식을 **비교**. 각각의 장단 |
| **5** | **어떤 상황에서 무엇을 골라야 하는지** 조건화 |

### L4 · 반례대응

| | |
|---|---|
| **0** | 반례를 던져도 **이해 불가** |
| **1** | 반례를 인지하나 **왜 문제인지** 설명 못 함 |
| **2** | 왜 문제인지 설명하나 **어떤 경우에 터지는지 모름** |
| **3** | **언제 문제가 되는지 조건을 특정** |
| **4** | 조건 특정 + **대응 방향** 제시 |
| **5** | **던지기 전에 스스로** 한계를 언급 |

### 태도 요소는 척도에서 뺐다

기존 루브릭의 `"사후적으로 짜맞추는 티"` · `"문제없다고 주장"` · `"탐색 시도 없이 고수"`는 **완전성이 아니라 태도**다. 한 척도가 두 차원을 재면 점수 해석이 불가능해진다.

**버리는 게 아니라 `evidence` 서술로 옮긴다.** 채점기가 모든 점수에 근거를 인용하므로 그 문장에 들어간다.

```json
{ "axis": "설계논리", "score": 2,
  "evidence": "고려사항을 나열했으나 선택과 연결되지 않음.
               '성능 때문에'라고 했으나 질문 전에는 의식하지 못했던 것으로 보임" }
```

**매니저는 점수가 아니라 이 문장을 읽는다.**

### 실측 대조 — 급격한 변화가 아니다

| 답변 | 기존 | 새 척도 |
|---|---|---|
| `"시간이라는 형식이 깨지지 않기 위해서입니다"` | 설계논리 1 | **1** |
| `"m이 전체 도서 평균이 필요해서 allBooks를 쓴겁니다… filter로 평점있는 책들만 골라서 평균을 낸거였습니다"` | 코드이해 3 | **3** |
| `"데이터와 결과를 보며 일일이 조정… 과학적 근거보다는 실험과 경험에 따른 임계값입니다"` | 설계논리 3 | **3** |
| `"저는 3번, 서버에서 비동기로 업데이트하는 방식이…"` (보기에서 선택) | 대안비교 **5** | **1~2** |

**앞 셋은 일치하고 마지막만 크게 내려간다.** 보기에서 고른 답이 만점이던 오염이 척도 차원에서도 잡힌다.

### 근거

**SOLO taxonomy**(Biggs & Collis 1982) — "가르칠 목표"가 아니라 **"학생 답변의 구조"** 를 분류하는 틀. 우리가 하는 일이 정확히 그것이다.
**BARS**(Smith & Kendall 1963) — 각 점수에 관찰 가능한 행동을 붙인다. 기존 루브릭이 부분적으로 하던 것을 일관되게 만든 것.

> **계단(축 사이)과 SOLO(축 안)는 층위가 다르다.** 계단은 "무엇을 물었나", SOLO는 "그 답변이 얼마나 구조화됐나"다. 중복이 아니다.
>
> **자기수정 축과 그 루브릭은 삭제했다.** 3-3의 근거 참조.
