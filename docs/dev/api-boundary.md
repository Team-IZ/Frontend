# API 경계 — 무엇이 서버에서 오고, 무엇이 화면 것인가

> **목적:** 지금은 API가 없어 목 데이터로 화면을 만든다. 그런데 목 데이터·기획 상수·표시
> 규칙·UI 상태가 한 파일에 섞이면 **연동할 때 무엇을 지워야 하는지 아무도 모른다.**
> 이 문서는 그 경계를 미리 긋고, 백엔드와 합의할 항목을 모은다.
>
> **원칙: 화면은 목이 아니라 `*Api.ts`의 함수 시그니처에 의존한다.** 연동은 그 함수
> 안쪽만 갈아끼우는 일이 되어야 하고, 화면 코드는 한 글자도 안 바뀌어야 한다.
> (`features/auth/authApi.ts`가 이미 이 방식이다 — 선례를 따른다)

---

## 0. 소관 분류 — 다섯 갈래

| 갈래 | 뜻 | 연동 시 |
|---|---|---|
| **① 서버 데이터** | 서버가 그대로 내려주는 값 | 목 삭제, fetch로 교체 |
| **② 서버 판정** | 서버가 계산해서 내려줘야 하는 값 | **지금 화면이 계산 중인 것들** — 옮긴다 |
| **③ 계약** | 서버와 이름·값을 맞춰야 하는 것 (enum·에러코드) | **미리 합의** |
| **④ 기획 상수** | 양쪽이 같이 아는 규칙 값 | 값이 바뀌면 양쪽 수정 |
| **⑤ 화면 것** | 표시·입력·정렬 UI. 서버와 무관 | 그대로 둔다 |

**②가 이 문서의 핵심이다.** 목 데이터가 배열이라 화면에서 `filter`·`reduce`로 계산하면
당장은 돌지만, **실제 API는 그 값을 서버가 준다.** 그대로 두면 연동할 때 화면을 다시 짜야 한다.

## 1. 지금 코드 전수 — 어디에 속하나

### ① 서버 데이터

| 지금 | 어디 | 실제 |
|---|---|---|
| `PROJECTS` | `projectFixtures.ts` | `GET /cohorts/{id}/projects` |
| `CURRICULA` | 〃 | `GET /cohorts/{id}/curricula` |
| `COHORT_SCOPE` | 〃 | `GET /cohorts/{id}` — 반 수·인원 |

### ② 서버 판정 — **지금 화면이 계산하고 있다** ⚠

| 값 | 지금 어디서 | 왜 서버여야 하나 |
|---|---|---|
| **필터·검색 결과** | `ProjectListScreen` `rows` useMemo — 전체 배열을 `filter` | 회차가 쌓이면 전량을 못 내려받는다. **쿼리 파라미터**가 된다 |
| **정렬** | 〃 `sort` | 페이지네이션과 함께 가야 한다 — 클라이언트 정렬은 **현재 페이지 안에서만** 맞다 |
| **상태별 집계**(`준비 중 2 · 진행 중 1 · 종료 1`) | 〃 `counts` useMemo | 전체 모집단 기준이라 **페이지가 나뉘면 클라이언트가 셀 수 없다** |
| **총 개수**(`총 5개`) | `PROJECTS.length` | 〃 |
| **후보 개수**(`후보 5건에서 3건`) | `ConceptCell`이 `CURRICULA`에서 `reduce` | 교안 전량을 안 받으면 못 센다. 프로젝트 응답에 **숫자로** 넣는다 |
| **남은 일수**(`5일 남음`) | `dueLabel`이 클라 시각으로 계산 | 클라 시계는 틀릴 수 있다. **서버 기준 시각**이 정확하다 (판단 필요 — 2-3절) |

> **가장 큰 구조 차이가 여기 있다.** 지금 화면은 *"전체 배열을 받아 내가 거른다"* 인데
> 실제는 *"거른 결과 한 페이지를 받는다"* 다. **이 둘은 화면 코드 모양이 다르다.**
> 목 단계에서 미리 후자로 맞춰 두지 않으면 연동이 재작성이 된다.

### ③ 계약 — 백엔드와 **미리** 합의

| 항목 | 지금 값 | 문제 |
|---|---|---|
| **`ProjectStatus`** | `PREP · READY · RUNNING · DONE` | 목업의 `준비 중/준비됨/진행 중/종료`와 1:1. **누가 판정하나** — 서버가 내려주는 값이어야 한다(화면이 조합으로 유추하면 안 됨) |
| **`ProjectErrorCode`** | `PROJECT_CREATE_FAILED` · `CONCEPT_SAVE_FAILED` | 목업 케이스 표에서 가져왔다. 서버가 같은 문자열을 쓰는지 확인 |
| **날짜 형식** | `'2026-07-21T18:00'` | 타임존 없음. **서버가 UTC로 줄지 KST 오프셋을 붙일지** 정해야 한다 |
| **id 형식** | `'mif-3'`(슬러그) | 목업 URL에서 왔다. 실제가 숫자 PK면 라우트가 바뀐다 |

### ④ 기획 상수 — 양쪽이 같이 안다

| 값 | 지금 | 출처 |
|---|---|---|
| **`CONCEPT_COUNT = 3`** | `projectTypes.ts` | 14번 Tier1-4. **서버도 검증해야 한다** — 클라 검증만 있으면 우회된다 |
| **`DUE_SOON_DAYS = 7`** | `projectFixtures.ts` | ⚠ **기획에 없다. 내가 정했다.** 2-2절 |

### ⑤ 화면 것 — 그대로 둔다

`PROJECT_STATUS_LABEL` · `KIND_LABEL` · `STATUS_ORDER` · `*_OPTIONS`/`*_ITEMS` ·
`VARIANT`(배지 색) · `formatDue` · 필터·모달 열림 상태 · `CreateBlocker`(응답에서 파생).

> `STATUS_ORDER`는 서버 정렬로 옮기면 화면에서 사라진다. 다만 **정렬 옵션 라벨**은 화면 것이다.

## 2. 결정이 필요한 것

### 2-1. 목록 조회를 서버 페이징으로 갈 것인가

**가야 한다.** 기수당 회차가 6~8개라 지금은 전량도 되지만, 같은 표 구조를 OP-06 명단
(250명)·교안 목록이 쓴다. **한 번 클라이언트 필터로 짜면 그 화면들이 전부 따라 한다.**

```
GET /cohorts/{cohortId}/projects
    ?search=&curriculum=&kind=&status=&sort=
→ { items: Project[], total: number, counts: { PREP, READY, RUNNING, DONE } }
```

`counts`를 응답에 같이 넣는 이유 — 헤더 내역(`준비 중 2 · 진행 중 1`)이 **필터와 무관한
전체 모집단** 기준이라, 목록만 받으면 못 만든다.

> **`page`·`size`는 아직 안 넣었다.** 기수당 회차가 6~8개라 한 페이지에 들어가고,
> OP-03은 페이저를 그리지 않는다(E7). **아무도 안 보내는 필드를 계약에 먼저 넣지
> 않는다** — 실제로 나뉘어야 하는 화면(OP-06 명단 250명)에서 더하고, 그때 `total`이
> `items.length`와 갈린다. 응답 모양은 이미 그 분기를 담고 있다.

### 2-2. `마감 임박`의 기준은 누가 정하나 ⚠

목록의 **유일한 경고가 `마감 임박 + 준비 중` 조합**인데(목업 doc-head) **임박의 정의가
어느 문서에도 없다.** 목업은 `5일 남음`은 붉게, `72일 남음`은 회색으로 그려 경계가 그
사이라는 것만 말한다.

지금 코드는 **7일**이고 근거는 *"다음 주에 시작할 회차를 이번 주에 준비한다"* 하나뿐이다.
`01-design-checklist` E8이 *"화면이 기준을 정하지 않는다"* 고 했으므로 **이건 그 경계에 있다.**

| 안 | |
|---|---|
| **기획이 값을 정한다** | 가장 깔끔. `DUE_SOON_DAYS` 한 줄만 바뀐다 |
| 서버가 `dueSoon: boolean`을 내려준다 | 판정이 한 곳에 모인다. 다만 **기준 없이는 서버도 못 정한다** |
| 화면이 계속 갖는다 | 지금 상태. **근거를 댈 수 없다** |

→ **기획 확인 필요.** 그 전까지는 코드에 `⚠ 기획에 없는 값` 주석을 유지한다.

### 2-3. `남은 일수`를 누가 계산하나

클라이언트 시계는 사용자가 바꿀 수 있고 타임존도 다르다. **마감 같은 값은 서버 기준이
안전하다.** 다만 응답에 `daysLeft`를 넣으면 **응답이 캐시되는 순간 틀린다.**

→ **서버는 마감 시각(+타임존)만 주고, 화면이 계산한다.** 단 화면은 `now`를 주입받아
테스트 가능해야 한다(지금 그렇게 돼 있다).

## 3. 구조 — auth 선례를 따른다

```
features/operator/
├─ projectTypes.ts     ③ 계약 — 서버와 주고받는 타입 · 에러코드 · 쿼리/응답 모양
│                        (백엔드 합의 대상. 값이 바뀌면 여기부터 바뀐다)
├─ projectRules.ts     ④ 기획 상수 — CONCEPT_COUNT · DUE_SOON_DAYS · canCreate
│                        (양쪽이 아는 규칙. 서버도 같은 값을 검증한다)
├─ projectApi.ts       ★ 경계 — 화면이 유일하게 의존하는 곳.
│                        실제 시그니처 그대로, 내부만 목. 연동 시 이 파일만 고친다
├─ projectMockDb.ts    ① 목 데이터 — 연동 시 **파일째 삭제**
└─ projects/
   ├─ ProjectListScreen.tsx        ⑤ 서버 응답을 그리기만
   └─ components/…
```

**auth와 같은 표식을 쓴다** — `mockDb.ts` 머리에 *"⚠️ Mock 전용 … 백엔드 연동 시 이 파일을
통째로 삭제하세요"*, `*Api.ts` 각 함수에 *"===== Mock 버전 (현재 활성) ====="* 블록.
**검색 한 번으로 지울 것이 다 나와야 한다.**

### 화면이 보게 되는 모양

```ts
// projectApi.ts — 연동 후에도 이 시그니처는 그대로다
export function listProjects(q: ProjectQuery): Promise<ProjectPage>
export function listCurricula(cohortId: string): Promise<Curriculum[]>
export function createProject(req: CreateProjectRequest): Promise<Project>
```

화면은 `PROJECTS`를 import하지 않는다. **`listProjects(query)`를 부르고 `items`를 그린다** —
목이든 실서버든 화면 코드가 같다.

### 이때 따라오는 것

`Promise`가 되면 **로딩·에러 상태가 화면에 필요해진다.** 지금은 동기 배열이라 그 상태가
아예 없는데, 케이스 표에는 있다(`PROJECT_CREATE_FAILED` 등). **구조를 바꾸는 김에 같이
들어온다** — 나중에 붙이면 화면을 또 고친다.

## 4. 남는 질문 (백엔드와)

1. id가 슬러그(`mif-3`)인가 숫자 PK인가 — **라우트가 걸린다**
2. 날짜 타임존 표기
3. `counts`를 목록 응답에 포함할 수 있나
4. `검증 개념 후보 개수`를 프로젝트 응답에 넣을 수 있나 (아니면 교안을 매번 조회)
5. `status` 판정 주체 — 서버인가
6. `CONCEPT_COUNT = 3` 서버 검증 여부

## 5. 적용 범위

이 문서는 **OP-03에서 처음 드러난 문제**를 정리한 것이지만, 경계 자체는 오퍼레이터
6화면·매니저 9화면이 전부 같다. **표·목록 화면이 15개**라 여기서 정한 모양이 그대로
반복된다 — 그래서 두 번째 화면(OP-04) 전에 정한다.
