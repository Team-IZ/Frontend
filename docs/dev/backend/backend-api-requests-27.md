# 백엔드 API — 27차 요청 · 잠든 인스턴스가 **아무 응답도 주지 않습니다**

> **로그인이 안 돼서 원인을 추적하다 나온 것입니다.** 화면 하나의 결함인 줄 알았는데
> 재 보니 서버가 **모든 경로에 침묵하는 구간**이 있었습니다.
>
> 그리고 죽은 것이 아니었습니다 — **충분히 기다리니 200이 왔습니다.** 즉 깨어나는
> 중이었는데, 밖에서는 그 사실을 알 방법이 없어 **장애와 구분되지 않습니다.**
>
> 측정 — 2026-08-14 · 실서버 · 프록시(Lambda URL) 경유 · **비로그인 상태**.

---

## 0. 한눈에

| | 무엇 | 우선순위 |
|---|---|---|
| **R1** | 🚨 인스턴스가 잠들면 **모든 경로가 무응답**입니다 — 죽은 것과 구분되지 않습니다 | 🚨 |
| **R2** | 🔴 **깨어나는 중임을 알릴 수단이 없습니다** — `503` + `Retry-After` 하나면 됩니다 | 🔴 |
| **R3** | 🟠 비로그인 첫 진입이 **왕복 2회**라, 콜드스타트 비용을 두 번 냅니다 | 🟠 |
| **R4** | 🟡 확인 — **배포 중에도 기존 인스턴스가 응답하나요?** | 🟡 |
| **✅** | 프론트가 흡수한 것 5건 (요청 아님, 알려 드리는 것) | — |

## 1. 🚨 R1 — 잠들어 있으면 전 경로가 무응답입니다

같은 시각, 순서대로 보낸 것입니다.

```
GET  /api/v0/members/me          60초 대기 → 응답 없음   ×3   (status 000 · TTFB 0)
GET  /v3/api-docs                20초 대기 → 응답 없음
GET  /                           20초 대기 → 응답 없음
POST /api/v0/auth/login  {}      20초 대기 → 응답 없음        ← 형식 오류라 즉답 가능한 요청입니다
POST /api/v0/auth/refresh        20초 대기 → 응답 없음

── 여기서 끊지 않고 150초까지 기다려 봤습니다 ──

GET  /v3/api-docs                200 · 13.5초                 ← 깨어났습니다
```

**TCP 연결은 0.05초에 붙습니다.** 네트워크·DNS·보안그룹 문제가 아니라, 연결은 됐는데
**애플리케이션이 응답을 시작하지 못하는 상태**입니다.

### 배포가 끝난 뒤 같은 요청을 다시 보냈습니다 — **전부 1초 안에 옵니다**

```
GET  /api/v0/members/me      401 · 0.50s / 0.52s / 0.73s
POST /api/v0/auth/refresh    403 · 0.72s
POST /api/v0/auth/login {}   400 · 0.85s
GET  /cohorts/{없는 id}       401 · 0.70s
```

**서버가 느린 것이 아닙니다.** 깨어 있으면 빠릅니다. 문제는 **잠들어 있는 동안의
침묵**이고, 그 구간이 사용자에게 그대로 노출됩니다 — 아침 첫 접속자·시연 직전이
정확히 그 자리입니다.

두 가지가 겹쳐 있습니다.

| | |
|---|---|
| **범위가 엔드포인트가 아니라 인스턴스입니다** | 25차 R4에서는 *「없는 것」을 물으면 무응답*이라고 적었는데, 이번엔 **있는 것도** 무응답입니다. 스웨거 문서(`/v3/api-docs`)까지 안 옵니다 |
| **형식 오류도 침묵합니다** | 25차에서 *"형식 400은 1초에 오므로 프록시 층이 아닙니다"* 라고 말씀드렸는데, 잠든 구간에서는 그 400도 안 옵니다 |

### 같은 증상의 다섯 번째입니다

18차 R1·R7(분석 전 교안 `/sections`, 없는 회차 상세) · 21차(발행 전 리포트) ·
25차 R4(「없는 것」 전반) · **27차 R1(잠든 인스턴스 전체)**.

앞의 넷은 "특정 상황에서 상태코드 대신 침묵"이었고, 이번 것은 **"특정 시간대에 전부
침묵"** 입니다. 원인은 달라도 **프론트에서 보이는 모습은 같습니다** — 화면이 영원히
기다립니다.

### 부탁 — 셋 중 하나면 됩니다

1. **최소 인스턴스 1 상시 가동** — 가장 확실하고, 저희 쪽에서 할 수 있는 게 없습니다
2. **주기적 warm-up 핑**(예: 5분마다 `/actuator/health`) — 비용을 아끼면서 잠들지 않게
3. 위 둘이 어려우면 **최소한 깨어나는 동안 즉답**을 주세요 (→ R2)

## 2. 🔴 R2 — "깨어나는 중"이라고 말해 주시면 화면이 사실을 말할 수 있습니다

지금 프론트는 **침묵을 해석해야 합니다.** 그런데 침묵은 여러 뜻입니다.

```
응답이 없다  →  ① 서버가 깨어나는 중       기다리면 된다
             →  ② 서버가 죽었다            기다려도 안 된다
             →  ③ 사용자의 인터넷이 끊겼다  사용자가 고쳐야 한다
```

셋을 가를 근거가 하나도 없어서, 화면은 **아무 말도 못 하거나 추측해서 말합니다.**
저희는 지금 *"서버가 깨어나는 중일 수 있습니다"* 라고 **`~수 있습니다`** 로 적어 두었는데,
이건 모른다는 뜻이라 사용자에게 도움이 안 됩니다.

### 필요한 것은 응답 하나입니다

```http
503 Service Unavailable
Retry-After: 30
```

프록시(Lambda)에 **깨우기 로직이 있다**고 하셨으니, 그 깨우는 동안 위 응답을 **즉시**
돌려주실 수 있다면 화면이 이렇게 바뀝니다.

| 지금 | `503 + Retry-After`가 오면 |
|---|---|
| 흰 화면 → (운 좋으면) 뒤늦게 성공 | **"서버가 깨어나는 중입니다 · 약 30초"** |
| 실패했는지 진행 중인지 모름 | 남은 시간을 세어 **자동으로 다시 시도** |
| 인터넷 문제와 구분 불가 | 인터넷 문제는 여전히 따로 안내 |

`Retry-After`는 이미 저희가 429에서 쓰고 있는 값이라, 오기만 하면 **화면 수정 없이**
바로 동작합니다.

## 3. 🟠 R3 — 비로그인 첫 진입이 왕복 2회입니다

리프레시 토큰이 **httpOnly 쿠키**라 JS가 "이 사람이 로그인했는지"를 미리 볼 수 없습니다.
그래서 앱은 부팅할 때 항상 한 번 물어봅니다.

```
로그인 화면 진입
  → GET /api/v0/members/me        401 (토큰 없음)
  → POST /api/v0/auth/refresh     401 (쿠키 없음)
  → 비로그인 확정 → 로그인 폼
```

평소에는 이 왕복 2회가 비용의 전부라 괜찮습니다. 그런데 **콜드스타트에서는 이게
그대로 두 배가 됩니다** — 로그인조차 안 한 사람이 서버가 깨어나기를 두 번 기다립니다.

### 여쭙는 것

**인증 토큰이 아예 없는 요청의 401을, 애플리케이션이 깨어나기 전에 앞단(프록시·필터)에서
즉답할 수 있을까요?**

가능하다면 **로그인 화면은 콜드스타트를 기다릴 이유가 없어집니다.** 로그인을 눌렀을 때만
기다리면 되고, 그때는 사용자가 자기 행동의 결과를 기다리는 것이라 훨씬 낫습니다.

구조상 어렵다면 R1·R2로 충분합니다 — 이건 있으면 좋은 것이지 막힌 것은 아닙니다.

## 4. 🟡 R4 — 확인: 배포 중에도 응답이 되나요?

이 문서를 쓰는 동안 배포 중이라고 알려 주셔서 재측정을 못 했습니다. 그래서 확인만
남깁니다.

- 배포 중 **기존 인스턴스가 계속 응답**하나요(무중단)?
- 아니면 교체되는 동안 **응답이 없나요**?

후자라면 사용자에게는 R1과 똑같이 보입니다 — 흰 화면입니다. 배포 시간대를 알려주시거나,
그동안 `503`을 주실 수 있으면 화면이 **"점검 중"** 이라고 정확히 말할 수 있습니다.

## 5. ✅ 프론트가 흡수한 것 — 요청이 아니라 알려 드리는 것

R1이 고쳐지기 전에도 화면이 무한히 멈추지는 않게 다섯 가지를 넣었습니다.

| | 무엇 | 근거 |
|---|---|---|
| 1 | **요청 예산 90초** — 넘기면 끊고 실패로 그립니다 | `fetch`에 기본 타임아웃이 없어 지금까지 **무한 대기**였습니다 |
| 2 | 값을 90초로 정한 이유 | App Runner 깨우기 **최대 76초**. 30초로 끊으면 **정상적으로 깨어나는 중인 요청을 죽입니다** |
| 3 | **파일 업로드만 180초** | 교안 PDF·명단 CSV는 서버가 받아서 파싱까지 하므로 같은 예산을 쓰면 멀쩡한 업로드가 죽습니다 |
| 4 | **예산 초과는 재시도하지 않습니다** | 네트워크 실패 재시도(3회)를 그대로 적용하면 사용자가 **6분**을 기다립니다 |
| 5 | **문구를 갈랐습니다** | 예산 초과에 *"인터넷 연결을 확인해 주세요"* 가 나가면 사용자가 **멀쩡한 자기 와이파이를 고치러 갑니다** |

그리고 **로그인 화면이 세션 확인 동안 흰 화면이던 것**을 로딩 표시로 바꿨습니다.
12초를 넘기면 *"서버가 깨어나는 중일 수 있습니다"* 를 덧붙입니다 — R2가 오면 이 문장에서
**`~수 있습니다`를 뗄 수 있습니다.**

> ⚠️ 이건 **증상 완화이지 해결이 아닙니다.** 90초 예산은 "끝나기는 하게" 만든 것이지
> 대기를 짧게 만든 것이 아닙니다. R1이 해결되면 이 값을 더 짧게 되돌립니다.
