## 2. 왜 체리픽으로 새로 만들지 않았나

가장 먼저 든 생각은 *"새 브랜치 파서 체리픽으로 정리하자"* 였다. **하지 않았다.**

확인해보니 쌓인 것이 사고가 아니었다.

```
dashboard/DashboardScreen.tsx  → import @/stores/cohortScope
analysis/AnalysisScreen.tsx    → import @/stores/cohortScope
                                        ↑ projects 브랜치에서 만든 파일
```

OP-01과 OP-02가 OP-03·04에서 만든 `cohortScope.ts`를 **실제로 쓴다.** 그것 없이는 컴파일이
안 된다. 그리고 각 브랜치의 자기 커밋은 **자기 폴더만** 건드린다 — 잘 나뉜 스택이다.

체리픽으로 새로 만들면 SHA만 새로 생기고, 똑같이 force push해야 하고, PR 3개를 닫고 다시
열어야 하는데 **구조는 지금과 똑같아진다.** 얻는 것이 없다.

### 합치지도 않았다

| | 파일 수 |
|---|---|
| #164 | 31 |
| #165 자기 몫 | 6 |
| #167 자기 몫 | 7 |

합치면 **44개 파일 한 PR**이 된다. 이슈(#162·#163·#166)와 PR이 1:1로 붙어 있는 것을
깨뜨릴 이유도 없다. **각각 머지, 스택 순서대로.**

## 3. `#164` — 충돌 2건, 성격이 달랐다

### 왜 CI가 실패하고 있었나

우리 코드가 아니라 **스펙 품질 게이트**(`api:check`)였다. `[required] Manager` — 백엔드
스키마에 `required`가 없다는 error.

여기서 한 번 헛돌았다. 최신 스펙을 당겨보니 그건 고쳐졌고 대신 `[nullable]` 4건이 떴는데,
넷 다 **우리 체커의 오탐**이었다. 백엔드가 10차 질문에 *"항상 값이 있다 — DB도 NOT NULL이다"*
라고 **답한 문장** 때문에 정상 필드가 잡힌 것이다.

그래서 `assertsNull()`을 고쳤는데 — **develop에 이미 같은 수정이 있었다**(`453aa7d`,
다른 터미널). 그쪽이 더 정교했다(문장 단위 + 남의 필드 인식). 내 수정을 걷어냈다.

> **교훈:** 시작 전에 `git fetch && git log origin/develop`. 30분 날렸다.

**결론: rebase만 하면 CI는 통과한다.** develop이 새 스펙과 체커 수정을 다 갖고 있었다.

### 충돌 ① `src/shells/Header.tsx` — 진짜 의미 충돌

양쪽이 **같은 버그를 각자 다르게** 고쳤다.

| | 무엇을 했나 |
|---|---|
| develop (OP-06) | `options`/`onChange`를 얹어 **실제 기수 전환**을 가능하게 함 |
| `#164` | 얼어붙는 `useState(scope?.value)`를 제거 |

어느 한쪽만 택하면 안 됐다. **develop 판에도 같은 버그가 남아 있었기 때문이다** —
`onChange`를 안 넘기는 화면(OP-01·02·03·04가 전부)은 여전히 첫 렌더 값에 얼어붙어,
조회해 온 기수 이름을 넘기면 **본문은 `9기`인데 스위처만 `7기`** 가 된다.

**둘을 합쳤다.** `options`/`onChange`는 살리고 `local` 상태만 제거:

```tsx
<Select
  value={scope.value}                                   // 프롭이 곧 값 — 얼어붙지 않는다
  onValueChange={(v) => scope.onChange?.(v ?? scope.value)}
  items={...(scope.options ?? [현재 값 하나])}
>
```

`onChange`가 없는 화면은 선택지도 하나뿐이라 눌러도 바뀔 것이 없다 — 값을 들어 둘 이유가
애초에 없다. OP-06 화면은 동작이 그대로다(이미 `onChange`를 넘긴다).

### 충돌 ② `docs/dev/README.md` — 중복

develop이 10~13차 줄을 이미 정리해뒀다. 내 10차 줄을 버렸다.

### 커밋이 7 → 6이 된 이유

10차 문서를 develop이 이미 갖고 있어 내 문서 커밋이 **빈 커밋이 되어 자동 제외**됐다.
정상이다. `#167`에서도 12차 문서 커밋이 같은 이유로 드롭됐다(`patch contents already upstream`).

## 4. `#165`, `#167` — 스택을 유지한 채 옮겼다

`#164`가 아직 머지 전이라 develop이 아니라 **rebase된 `#164` 위로** 옮겼다.

```bash
git rebase --onto feat/connect-op-projects 4f3df76
```

`4f3df76`이 옛 projects tip이다. `--onto <새 base> <옛 base>`는 옛 base **이후** 커밋만
새 base에 얹는다 — 그래서 남의 커밋을 끌고 오지 않는다.

둘 다 충돌 0건.

## 5. `#167`에 붙인 12차 반영

12차는 "아직 반영 안 됐다"고 전달받았지만 **실측해보니 R1·R2 둘 다 이미 올라와 있었다.**

| 12차 | 요청 | 확인 |
|---|---|---|
| R1 | `roundNo`가 요청/응답에서 다른 뜻 | ✅ `cohortRoundNo` 신설 |
| R2 | `sameCurriculumOnly=true`면 0건 | ✅ `true`도 7건 |
| Q1 | `cohortId`가 쿼리라고 적혀 있음 | ✅ `in=path` · 설명문 정정 |

### R1 — 지어낸 번호를 서버 값으로

열 번호를 **정렬 후 자리**로 매기고 있었다. `roundNo`가 프로젝트 안 번호라 미니프로젝트에서는
전부 `1`이었고, 그대로 쓰면 열 키가 겹쳐 React가 행을 뭉갰다(중복 키 경고 45건).

지어낸 값이라 **범위를 좁히면 남은 열이 늘 `1차`부터 다시 세어졌다** — 같은 회차가 화면마다
다른 이름을 가졌다. 서버가 기수 안 순번(`cohortRoundNo`)을 주므로 그대로 쓴다. 요청의
`fromRoundNo`·`toRoundNo`와 **같은 축**이라 받은 값을 범위 조건에 되넣을 수 있다.

> 검증: 3~6차로 좁혀 열이 `3차 4차 5차 6차`로 나오는 것을 렌더로 확인(예전이면 `1차`부터).

### R2 — 단언과 요청이 어긋나 있었다

`sameCurriculumOnly`를 **아예 안 보내고 있었다.** 서버 기본값이 `false`라 교안이 바뀐 개념까지
섞여 오는데, 이 탭은 머리글·표 머리·타입 주석 **세 곳에서** *"같은 교안 · 같은 개념"* 이라고
단언한다. 표기가 사실과 달랐다.

12차 전에는 `true`가 0건을 돌려줘 켤 수 없었다. 이제 켠다.

**토글로 두지 않았다** — 끌 수 있는 것이었다면 표가 눈금을 바꿔야 한다. 값의 차이가 교육생
것인지 교안 것인지 갈라지지 않으면 절대 눈금(1~4단)을 두 기수에 걸쳐 쓸 근거가 사라진다.

### 덤 — `null%`

검증하다 발견했다. 인원 0명인 반 행에 **`null%`가 그려지고 있었다**(9기 `1반`, 네 회차 모두).

집계 상태가 `AGGREGATED`면 비율도 있다고 보고 `${cell.ratio}%`를 썼는데, 채점 대상이 0명이면
서버가 `riskRate`를 `null`로 준다 — 분모가 0이라 비율이 성립하지 않는다. 상태는 그대로
`VALUE`라 그 조합이 분기에서 빠져 있었다.

`집계 전`으로 낮춰 쓰지 않았다. 집계는 실제로 끝났고 셀 수 있는 사람이 없었을 뿐이라 그렇게
쓰면 거짓이 된다. `—`만 그리고 이유는 호버·스크린리더에 적는다.

## 8. 동시 작업할 때 명심할 것

이번에 실제로 겪은 것만.

**1. 공유 파일이 머지 순서를 정한다.**
`cohortScope.ts` **하나**가 세 브랜치의 순서를 강제했다. 새 작업을 시작하기 전에
*"이거 남의 브랜치에도 필요한가?"* 를 먼저 묻고, 필요하면 **그 파일만 먼저 작은 PR로 떼서**
develop에 넣는다. 그러면 스택이 안 생긴다.

**2. 생성물은 손으로 고치지 않는다 — `develop 것 + 재생성`.**
`api/openapi.json`·`src/api/**`는 두 터미널이 반드시 겹친다. 충돌 나면 고민하지 말고:

```bash
git checkout origin/develop -- api/openapi.json && npm run api:gen
```

어느 쪽 hunk가 맞나 따지기 시작하면 진다.

**3. 시작 전에 develop부터 본다.**
같은 `api-check` 오탐을 두 터미널이 각자 고쳤다. `git fetch && git log origin/develop`
한 번이면 안 겹쳤다.

**4. 스택은 아래부터 머지하고, `--force-with-lease`만 쓴다.**
`--force`는 남의 푸시를 지운다. `--with-lease`는 그 사이 누가 밀었으면 거부한다.

**5. 문서는 한 번 보내면 그 회차는 닫는다.**
번호(10차·12차)가 곧 백엔드와의 동기화 지점이다. 이미 보낸 문서를 고치면 상대가 무엇을 보고
작업했는지 알 수 없어진다.

**6. 서버가 내려가 있을 수 있다.**
작업 중 백엔드가 통째로 404가 됐다(`v3/api-docs`·`swagger-ui`·`login` 전부, `server: envoy`만
오고 upstream 헤더 없음). 브라우저에는 **CORS 오류로 보인다** — 404 응답에는 CORS 헤더가
없기 때문이다. 내 코드를 의심하기 전에 `curl`로 스펙 URL부터 찍어본다.
