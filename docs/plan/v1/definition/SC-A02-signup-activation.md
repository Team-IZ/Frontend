# SC-A02 · 회원가입 · 계정 활성화

> 소스: 기능명세서 v8 AUTH-01(매니저 회원가입) + AUTH-06(교육생 계정 활성화). 동의(개인정보보호법 §15·17·22·26)·슈퍼어드민 초대·초대=인증 통일은 결정 D12·D13·D14 반영.
> 배치: P0 · 진입 순서 2번. **초대 토큰 유형에 따라 두 변형**으로 렌더.
> ⚠️ 명세와 달라진 점(보완): ①이메일 읽기전용·초대링크=인증(D13, AUTH-02 별도 인증 제거) ②동의 섹션 추가(D14) ③슈퍼어드민 초대=변형 A 재사용(D12).

## 2. 목적 & UX 설계 근거

- **한 화면, 토큰이 변형을 결정.** 초대 토큰이 매니저용이면 **회원가입 폼**(이름 + 비밀번호), 교육생용이면 **계정 활성화 폼**(비밀번호). 서버가 토큰으로 판정, 사용자는 변형을 선택하지 않음.
- **이름의 출처가 역할마다 다르다.** 매니저는 **본인 계정을 스스로 생성**하므로 이름을 직접 입력(변형 A). 교육생은 **매니저가 명단(SC-M02·ORG-01)에 이름+이메일을 이미 등록**했으므로 활성화 시 이름을 다시 받지 않는다(변형 B) — 활성화 폼은 비밀번호+동의만. (그래서 M11 리스트·M06 상세는 미활성 교육생도 이름이 보인다.)
- **이메일은 초대값·읽기전용(D13).** 초대 메일은 해당 주소로만 가고 토큰이 서명돼 있으므로 **초대 링크 클릭이 이메일 소유 증명** = 인증. 이메일을 편집·재입력·재인증할 이유가 없다 → 이메일 필드는 세 역할 모두 **읽기전용(초대값 표시)**. 별도 인증 메일 단계 제거.
- **비밀번호 정책 사전 노출.** AUTH-01·06 case6. 정책(길이·복잡도) 힌트를 필드 옆 상시 노출.
- **개인정보 동의(D14).** 서비스가 코드(지적재산)·세션 전문·AI 위험 판정·기여도 등 민감 데이터를 처리 → 개인정보보호법상 동의 필수. **대상 차등:** 학생은 5개(AI 분석·기관 공유 포함), 매니저은 2개(이용약관·개인정보 수집). 필수 전체 동의 전 제출 불가, 선택은 미동의해도 진행.
- **계정 존재 비노출.** 중복 계정(AUTH-01 case5)은 "이미 가입된 이메일" 안내로, 재발송은 계정 유무 무관 동일 응답.

## 3. 정보 구조 & 레이아웃

**데스크톱 2단 분할**(좌 브랜드 패널 · 우 폼 — SC-A01 레이아웃 일관). 우측 폼 변형:

**변형 A — 매니저 회원가입:** "회원가입" · `InlineAlert` 슬롯 · 이름 `TextField` · 이메일 `ReadonlyField`(초대값) · 비밀번호 `PasswordField`+정책 힌트 · 비밀번호 확인 · **동의 그룹(필수 2)** · `PrimaryButton` "가입하기"
**변형 B — 교육생 계정 활성화:** "계정 활성화" · `InlineAlert` 슬롯 · 이메일 `ReadonlyField`(명단) · 비밀번호+정책 힌트 · 비밀번호 확인 · **동의 그룹(필수 4 + 선택 1)** · `PrimaryButton` "활성화하기"

**동의 그룹:** 폼 표면 위 **구분선 리스트**(회색 박스·인라인 설명 문단 없음 — 가독성). 항목마다 체크박스 + [필수]/[선택] 배지 + **구체적 제목** + "전문 보기"(전문은 링크로). 상세(수집 항목·목적·보유기간·제3자 대상)는 전문에서 충족. 거부 시 불이익("미동의 시 평가 불가")만 AI 분석 항목 제목에 노출. 필수 전체 체크 전 제출 버튼 비활성.
반응형(옵션): 좁은 폭에서 브랜드 패널 상단 축소, 폼 폭 확장, 정보구조 불변.
