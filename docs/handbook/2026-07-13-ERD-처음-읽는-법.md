# ERD 처음 읽는 법 — IZ 스키마 실물로

ERD를 한 번도 짜본 적 없는 사람을 위한 문서다. 개념을 추상적으로 설명하지 않고, 팀원이 실제로 그린 `ai_lms_v2.xlsx`의 진짜 테이블·진짜 컬럼으로 처음부터 끝까지 걸어간다. 순서대로 읽을 것 — 0번 없이는 1번이 안 읽힌다.

---

## 0. 테이블이 뭐고, 왜 하나로 안 몰아넣는가

**테이블은 규칙이 있는 엑셀 시트**다. 한 줄(행)이 실제 사물이나 사건 하나 — 학생 한 명, 제출 한 건, 점수 한 개 — 를 나타내고, 세로 칸(컬럼)이 그 사물의 속성이다.

제일 흔한 실수는 **모든 걸 시트 한 장에 다 넣는 것**이다. 예를 들어 "제출 목록"이라는 시트 하나에 학생 이름, 기관 이름, 제출한 코드, 그 코드에서 나온 판단지점, 점수까지 한 줄에 다 적으면:

| 학생 | 기관 | 파일 | 축 | 점수 |
|---|---|---|---|---|
| 이서연 | 코드스쿼드 | orderService.ts | 설계논리 | 2 |
| 이서연 | 코드스쿼드 | orderService.ts | 코드이해 | 3 |
| 이서연 | 코드스쿼드 | orderService.ts | 대안비교 | 4 |

- **문제 ①**: "이서연"·"코드스쿼드"가 세 줄 다 반복된다. 이서연이 이름을 바꾸면 세 줄을 다 고쳐야 하고, 하나라도 놓치면 데이터가 서로 모순된다.
- **문제 ②**: 학생이 아직 한 축도 채점 안 됐으면 이 시트엔 그 학생이 아예 존재하지 않는다 — "지금 몇 명이 대기 중인가"를 셀 수 없다.

쪼개면, 사람 정보는 이 테이블 하나에만 있다:

**app_user 테이블**

| user_id | name | org_id |
|---|---|---|
| u_083 | 이서연 | org_001 |

**score 테이블**

| score_id | user_id | axis | value |
|---|---|---|---|
| s_1 | u_083 | 설계논리 | 2 |
| s_2 | u_083 | 코드이해 | 3 |

이서연이라는 사실은 **딱 한 줄에만** 존재한다. 점수 테이블은 `user_id`라는 짧은 값으로 그 한 줄을 "가리키기"만 한다. 이서연 이름이 바뀌면 고칠 곳은 한 곳뿐이다.

이 "가리키기"가 ERD의 전부다. 두 가지만 알면 된다:

- **기본키 (PK, Primary Key)**: 그 테이블에서 각 줄을 유일하게 식별하는 값. 주민등록번호 같은 것.
- **외래키 (FK, Foreign Key)**: 다른 테이블의 기본키를 그대로 가져와 "이 줄은 저 테이블의 그 줄과 관련 있다"고 선언하는 값.

아래부터는 표의 **구분** 칸에 `PK`, `FK → 테이블명`으로 표시한다. 비어 있으면 그냥 값이다.

## 1. 이서연이 코드를 제출하는 순간, DB에서 무슨 일이 생기는가

추상 예시 대신 진짜 시나리오 하나를 끝까지 따라간다. **코드스쿼드** 기관의 **7기 백엔드 부트캠프**, 학생 **이서연**이 2회차 체크포인트에 `orderService.ts`를 제출하고, AI가 그 코드에서 판단지점을 뽑아 소크라틱 질문을 던지고, 답변에 점수를 매기기까지 — 이 13개 테이블이 정확히 이 순서로 관여한다.

### organization — 교육기관 하나

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | org_id | 이 기관의 유일한 이름표 | UUID |
| | name | 기관 이름 | VARCHAR(200) |

예시: `org_id = org_001` · `name = "코드스쿼드"`

**1개 기관 : N개 기수** ↓

### cohort — 그 기관의 교육 기수 하나

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | cohort_id | 이 기수의 유일한 이름표 | UUID |
| FK → organization | org_id | 어느 기관 소속인가 | UUID |
| | name | 기수 이름 | VARCHAR(100) |

예시: `cohort_id = cohort_007` · `org_id → org_001` · `name = "7기 백엔드 부트캠프"`

**1개 기관 : N명 사용자** ↓

### app_user — 학생 이서연 본인

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | user_id | 이서연의 유일한 이름표 | UUID |
| FK → organization | org_id | 어느 기관 소속인가 | UUID |
| | name | 이름 | VARCHAR(100) |
| FK → role | role_id | 매니저인지 학생인지 | SMALLSERIAL |

예시: `user_id = u_083` · `org_id → org_001` · `name = "이서연"` · `role = TRAINEE`

**기수 : 학생 = N : M (그래서 아래 연결 테이블이 따로 있다)** ↓

### cohort_member — 이서연이 이 기수 소속이라는 연결고리

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK, FK → cohort | cohort_id | 어느 기수 | UUID |
| PK, FK → app_user | user_id | 어느 학생 | UUID |
| | track | 교육 트랙 | VARCHAR(30) |

예시: `cohort_id → cohort_007` · `user_id → u_083` · `track = "백엔드"`

> **왜 이 테이블이 따로 있나** — 한 학생이 여러 기수에 걸칠 수도 있고, 한 기수에 여러 학생이 있다(N:M 관계). `app_user`에 `cohort_id` 컬럼 하나만 넣으면 "학생 1명 = 기수 1개"만 표현할 수 있어서 안 된다. N:M을 표현하려면 항상 이렇게 두 PK를 합쳐 하나의 PK로 쓰는 연결 테이블이 필요하다.

**1개 기수 : N개 회차** ↓

### checkpoint — 2회차 체크포인트

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | checkpoint_id | 이 회차의 유일한 이름표 | UUID |
| FK → cohort | cohort_id | 어느 기수의 회차인가 | UUID |
| | round_no | 몇 회차인가 | SMALLINT |
| | due_at | 제출 마감 시각 | TIMESTAMPTZ |

예시: `checkpoint_id = cp_002` · `cohort_id → cohort_007` · `round_no = 2`

**1개 기수 : N개 프로젝트** ↓

### project — 이서연의 개인 프로젝트

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | project_id | 이 프로젝트의 유일한 이름표 | UUID |
| FK → cohort | cohort_id | 어느 기수 소속인가 | UUID |
| FK → app_user | owner_user_id | 개인 프로젝트면 소유자 | UUID |

예시: `project_id = proj_014` · `cohort_id → cohort_007` · `owner_user_id → u_083`

**1개 회차 : N개 제출 (학생마다 하나씩)** ↓

### submission — 이서연이 2회차에 제출한 그 순간

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | submission_id | 이 제출의 유일한 이름표 | UUID |
| FK → project | project_id | 어느 프로젝트를 제출했나 | UUID |
| FK → checkpoint | checkpoint_id | 몇 회차 제출인가 | UUID |
| FK → app_user | user_id | 누가 제출했나 | UUID |
| | head_commit_sha | 제출 시점 커밋 | CHAR(40) |

예시: `submission_id = sub_221` · `project_id → proj_014` · `checkpoint_id → cp_002` · `user_id → u_083`

**1개 제출 : N개 판단지점** ↓

### decision_point — AI가 코드에서 뽑은 판단지점

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | dp_id | 이 판단지점의 유일한 이름표 | UUID |
| FK → submission | submission_id | 어느 제출에서 뽑았나 | UUID |
| | file_path | 파일 경로 | VARCHAR(500) |
| | code_snippet | 할인 로직 코드 조각 | TEXT |
| | is_selected | 실제 채점 대상으로 뽑혔나 | BOOLEAN |

예시: `dp_id = dp_552` · `submission_id → sub_221` · `file_path = "src/services/orderService.ts"` · line 16~19

**1개 제출 : 1개 세션** ↓

### assessment_session — 이서연의 2회차 검증 세션(소크라틱 대화)

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | session_id | 이 세션의 유일한 이름표 | UUID |
| FK → submission | submission_id | 어느 제출에 대한 세션인가 | UUID |
| | status | 진행 상태 | ENUM |
| | depth_cap | 질문 최대 깊이 | SMALLINT |

예시: `session_id = sess_331` · `submission_id → sub_221` · `status = IN_PROGRESS`

**1개 세션 : N개 턴 (판단지점당 여러 번 오갈 수 있음)** ↓

### session_turn — 실제 질문-답변 한 턴

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | turn_id | 이 대화 턴의 유일한 이름표 | UUID |
| FK → assessment_session | session_id | 어느 세션의 턴인가 | UUID |
| FK → decision_point | dp_id | 어느 판단지점에 대한 질문인가 | UUID |
| | question / answer | 질문과 답변 내용 | TEXT |
| | depth | L1/L2/L3 중 어느 깊이인가 | ENUM |

예시: `session_id → sess_331` · `dp_id → dp_552` · Q: `"Math.floor를 쓴 이유는?"` · A: `"결제 금액에 소수점이…"`

**세션 : 판단지점 = N : M (그래서 아래 테이블이 또 따로 있다)** ↓

### dp_session_result — 그 판단지점, 결국 얼마나 이해했나 (요약)

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK, FK → assessment_session | session_id | 어느 세션인가 | UUID |
| PK, FK → decision_point | dp_id | 어느 판단지점인가 | UUID |
| | final_state | 최종 이해 상태 | ENUM |
| | reached_depth | 최종 도달 깊이 | ENUM |

예시: `session_id → sess_331` · `dp_id → dp_552` · `final_state = DEFENDED` · `reached_depth = L2`

`session_turn`이 대화 한 마디 한 마디의 원본 로그라면, `dp_session_result`는 "그래서 이 판단지점 결론이 뭐였나"를 판단지점당 한 줄로 요약한 것 — 원본 로그와 요약 결과를 별도 테이블로 나눈 것도 같은 이유(용도가 다르면 테이블을 나눈다)다.

**1개 세션 : 5개 점수 (축마다 하나씩)** ↓

### score — 설계논리 축, 최종 2점

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | score_id | 이 점수의 유일한 이름표 | UUID |
| FK → assessment_session | session_id | 어느 세션의 채점인가 | UUID |
| | axis | 코드이해/설계논리/… | ENUM |
| | value | 1~5점 | SMALLINT |

예시: `score_id = score_998` · `session_id → sess_331` · `axis = "설계논리"` · `value = 2`

**1개 점수 : N개 근거 인용** ↓

### score_evidence — 그 2점의 근거가 된 답변 인용문

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| PK | evidence_id | 이 근거의 유일한 이름표 | UUID |
| FK → score | score_id | 어느 점수의 근거인가 | UUID |
| | quote | 원본 답변 인용문 | TEXT |

예시: `evidence_id` · `score_id → score_998` · `quote = "결제 금액에 소수점이 생겨서 원 단위로 내림했습니다"`

여기까지가 이서연 한 명, 한 회차, 한 판단지점이 DB를 통과하는 전체 경로다. 나머지 36개 테이블도 전부 이 논리(사물 하나 = 테이블 하나, 관계는 FK로 연결, N:M은 연결 테이블)의 반복이다.

## 2. 이 스키마에 반복해서 나오는 세 가지 기법

단순 컬럼 하나하나가 아니라 "패턴"으로 읽으면 나머지 테이블도 같은 논리로 읽힌다.

### 기법 1 — 값을 덮어쓰지 않고 새 줄을 쌓는다 (버전 관리)

`UPDATE`로 값을 고치면 "고치기 전에 뭐였는지"가 영원히 사라진다. 이 스키마는 나중에 "그때 뭐였는지"를 다시 봐야 하는 값은 이렇게 짠다.

**score 테이블**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | score_id | |
| | value | 채점된 값 (1~5) |
| | is_active | 지금 유효한 점수인가 |
| FK → score (자기 자신) | supersedes_score_id | 이 점수가 무엇을 대체했는가 |

**왜 이렇게 짰을까**: 재채점이나 이의제기로 점수가 바뀌면, 옛 점수 줄은 지우지 않고 `is_active=false`로 꺼두고 새 줄을 추가한다. 옛 줄은 그대로 DB에 남아 "그때 매니저 화면에 뭐라고 떠 있었는가"를 나중에도 재현할 수 있다. 사람을 평가하는 제품이라 이의제기(GOV-01)가 들어오면 이 재현이 필수다.
> 근거: `data-contract.md` — "이의제기가 들어오면 그때 화면에 뭐라고 떠 있었는가를 재현해야 한다"

### 기법 2 — 상태가 바뀔 때마다 별도 로그 테이블에 한 줄씩 쌓는다 (이력 로그)

지금 상태가 뭔지는 원본 테이블의 `status` 컬럼 하나로 충분하다. 그런데 "언제부터 이 상태였는가"는 그 컬럼만으론 알 수 없다.

**intervention_status_log 테이블**

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| FK → intervention | intervention_id | | UUID |
| | from_status | 바뀌기 전 상태 | ENUM |
| | to_status | 바뀐 후 상태 | ENUM |
| | changed_at | 언제 바뀌었나 | TIMESTAMPTZ |

**왜 이렇게 짰을까**: 매니저 화면(개입 관리)이 "이 건, 진행 상태로 바뀐 지 7일째 — 정체"라는 배지를 보여줘야 한다. `intervention.status='진행'`만 봐서는 언제부터 진행이었는지 알 방법이 없다. 로그 테이블이 있어야 경과일을 계산할 수 있다. 확정 액션의 감사(누가·언제·왜 바꿨는지)를 남기라는 요구사항(GOV-02)도 같은 테이블이 해결한다.

### 기법 3 — 시간이 지나면 달라지는 "평균값"은 그 순간을 스냅샷으로 박제한다

"이번 기수 평균 78점"은 반쪽짜리 문장이다 — 회차마다 평균이 다르다.

**benchmark_snapshot 테이블**

| 구분 | 컬럼 | 설명 | 타입 |
|---|---|---|---|
| FK → checkpoint | checkpoint_id | 몇 회차 기준인가 | UUID |
| | cohort_mean | 그 회차 마감 시점의 기수 평균 | JSONB |
| | captured_at | 이 평균을 찍은 시각 | TIMESTAMPTZ |

**왜 이렇게 짰을까**: 3회차 시점 평균과 6회차 시점 평균은 다른 숫자다. 매번 "지금 기준으로" 다시 계산하면, 3회차 화면을 나중에 다시 열어도 최신 값(6회차 기준)이 나와버려 "3회차 때 평균 대비 몇 등이었나"를 영영 알 수 없다. `checkpoint_id`별로 그 순간을 찍어 박제해두면 언제 다시 봐도 똑같은 값이 나온다.
> 근거: `ux-principles.md` C5 — "회차 due_at 시점 스냅샷이므로 회차마다 값이 다르다"

## 3. 거의 모든 테이블에 붙어있는 org_id

49개 중 40개 가까이 — 혹시 몰라서가 아니라 설계 원칙이다.

다른 교육기관(부트캠프)이 같은 서버를 같이 쓴다. A기관 매니저가 B기관 학생 점수를 절대 보면 안 된다. 이걸 **멀티테넌시**(multi-tenancy)라고 부르는데, 지키는 방법은 하나다 — **조회 가능한 모든 테이블에 소속 기관을 직접 박아두고, 모든 쿼리에 "내 기관 것만" 조건을 강제로 건다.**

| 단계 | 테이블 | org_id |
|---|---|---|
| 1 | organization | PK |
| 2 | cohort | FK → organization |
| 3 | checkpoint | FK → organization |
| 4 | submission | FK → organization |
| 5 | decision_point | FK → organization |
| 6 | score | FK → organization |

단계마다 `cohort_id`·`submission_id`처럼 "직전 단계"를 가리키는 화살표도 있지만, `org_id`만은 매 단계에서 한 번 더 직접 반복된다 — 중간 테이블을 여러 번 조인하지 않고도 "이거 우리 기관 것 맞아?"를 한 번에 확인하기 위해서다. "역할이 매니저인가"와 "그 매니저의 기관 소속인가"를 아예 다른 두 개의 체크로 분리해서, 하나라도 빠지면 바로 눈에 띄게 만든 것이다.

---

## 4. 팀원한테 그냥 물어보면 되는 것들

설계 의도가 아니라 작업 중 흔적으로 보이는 부분:

| # | 항목 | 왜 이상한가 |
|---|---|---|
| 1 | `submission.project_id2`, `cohort.org_id2`, `role_permission.permission_id2` | 컬럼 이름 끝에 "2"가 붙어 있다. ERD 툴이 같은 이름의 화살표가 겹칠 때 자동으로 "2"를 붙이는 경우가 있는데, 그걸 실제 이름으로 안 고치고 둔 것으로 보인다. 실제로는 각각 `project_id`, `org_id`, `permission_id`가 맞다. |
| 2 | `role.Field`, `view_setting`·`focus_area`의 마지막 줄 | 컬럼 이름 자리에 "Field"라는 툴 기본값 문구가 그대로 남아 있다. 아직 이름을 안 정했거나 지우는 걸 잊은 빈 줄로 보인다. |
| 3 | `audit_log`의 기본키 이름이 테이블 이름과 똑같이 `audit_log` | 보통은 `audit_log_id`로 짓는다. 오타일 가능성이 크다. |

### 와이어프레임과 다를 수 있는 지점

이 ERD는 목업을 안 보고 기능명세서·플로우만 보고 짠 것이라 몇 군데 결이 다르다.

- `notification` 테이블이 있는데 지금 16개 화면엔 알림 UI가 따로 없다 — ERD가 앞서간 게 아니라 이번 배치 화면으로 아직 안 뽑힌 것뿐일 가능성이 높다.
- `report_snapshot`(매니저용 종합 리포트)과 `trainee_report`(교육생용 개인 리포트)가 분리 저장되는데, 이 경계가 화면상으론 잘 안 드러난다 — API 설계 때 팀원과 한 번 맞춰보면 좋겠다.
