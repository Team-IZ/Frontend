# MG-07 프로젝트 목록 — 연동

> 담당 반의 회차가 **어디까지 왔고 무엇이 밀렸나**에 답하는 표. 쓰기가 없다 —
> 회차는 오퍼레이터(OP-03)가 만든다.
>
> 연동 — 2026-08-18 · 실서버 · `manager@example.com`(9기 · C반) ·
> 스펙 `sha256 63512bad30a1`

## 1. 조회 흐름

```
useManagerCohort()   GET /members/me/enrollments      ─┐ 기수가 정해져야
useManagedClasses()  GET /cohorts/{id}/classrooms     ─┤ 반 필터 선택지가 생긴다
useProjectList()     GET /projects?classId=…          ─┘ (반은 목록과 **나란히** 부른다)
```

**`GET /projects` 하나가 표 전체를 준다.** 목이 `classes[]`를 회차마다 들고 있던 것과
달리 서버는 회차별 집계 하나(`progress`)와 조치 배열(`actionItems`)로 준다.

⚠ **`cohort`와 `classId` 중 정확히 하나가 필수다.** 안 주면 400
`PROJECT_LIST_SCOPE_AMBIGUOUS`. 이 화면은 담당 반 스코프라 **`classId`**를 쓴다.

```
cohort=9기      8개   ← 기수 전체. 담당 반과 무관한 회차가 섞인다
classId=C반     6개   ← 이 화면의 범위
```

## 2. 대조표 — 목 계약 vs 서버 응답

### ① 이름까지 같다 — 그대로 산다

| 목 | 서버 |
|---|---|
| `name` | `name` |
| `conceptCandidateCount` | `conceptCandidateCount` |
| `counts: Record<Status, number>` | `counts` — **필터를 안 탄다**(실측: `status=RUNNING`으로 좁혀도 `{PLANNED:0,RUNNING:1,CLOSED:5}` 그대로). 목 주석이 「필터와 무관한 전체 모집단」이라고 적어 둔 것과 정확히 같다 |
| `total` | `total` |

### ② 서버 모양이 더 낫다 — 서버를 따른다

| 목 | 서버 | 왜 |
|---|---|---|
| `status: PLANNED\|RUNNING\|**DONE**` | `PLANNED\|RUNNING\|**CLOSED**` | 이름만 다르다. 서버 값을 쓰고 라벨 표만 고친다 |
| `classFilter: ClassName`(`'A반'`) | `classId: UUID[]` | 반 이름은 기수마다 바뀐다. **배열이라 담당 반이 여럿이면 합쳐서 볼 수 있다**(실측: 두 번 넘겨도 200) |
| `curriculum: string`(이름) | `curriculumId: UUID` | 같은 이름의 교안이 둘일 수 있다. **`materialId`·`versionId` 둘 다 받는다**(실측) |
| `sort: START\|DUE` | `READINESS\|DUE_SOON\|START_DATE` | 서버가 하나 더 준다(`READINESS` = 준비 필요 순, 기본) |
| `progressCell()`이 화면에서 합산 | `progress{assessedCount, targetTraineeCount, laggingClass}` | 화면이 반별 값을 더하던 것을 서버가 낸다. **판정을 화면이 다시 하지 않는다.** `laggingClass`는 담당 반이 둘 이상일 때 「진행률이 가장 낮은 반」을 **집계까지** 준다 |
| `actionItems()`가 화면에서 조립 | `actionItems[]{classId,className,type,teamCount}` | 반 이름까지 실어 온다 — 목이 `prefix()`로 만들던 `C반 미제출 2팀`이 그대로 나온다 |

### ③ 목이 지어낸 축이다 — 버린다

| 목이 가정한 것 | 서버 실제 |
|---|---|
| `classes: ClassProgress[]` — **회차마다 반별 7개 지표** | `progress` **하나**(회차 전체) + `actionItems[]`(반별이지만 두 종뿐) |
| `ClassProgress.interviewCount` — 종료 회차의 「면담 N명」 | **없다.** `ActionItem.type`은 `UNSUBMITTED_TEAMS`·`ANALYSIS_FAILED_TEAMS` 둘뿐 |
| `ClassProgress.attendable`(응시 가능 인원) | `targetTraineeCount`(대상 인원)만. **분모의 뜻이 다를 수 있다** |
| `progress`가 늘 있다고 가정 | **`null`인 조건이 셋**이다(스펙) — 빅프로젝트 · `PLANNED` · 회차 없음 |
| `MANAGED_CLASSES` A·B·C반 · `SCOPE_TOTAL` 75명 | 실제 담당 반은 **C반 하나 · 26명** — 상수를 조회로 바꾼다 |
| `COHORT_NAME = '7기'` | 실제 9기 — 스코프 훅이 이미 준다 |
| `MOCK_TODAY = '2026-07-18'` | 실제 오늘 |

**`interviewCount`가 없는 것이 이 연동에서 유일하게 화면을 줄이는 항목이다.** 종료된
회차의 조치 열이 목에서는 「면담 N명」이었는데 서버에 자리가 없다 → §5 요청서.

### 값 모양이 다른 것

```
startAt   목 ISO datetime         →  startDate       "2026-08-03"   date-only
dueAt     목 ISO datetime         →  submissionDueAt "2026-08-21T14:59:00Z"  datetime
curricula 목 "이름 버전" 문자열     →  curriculumNames ["spring_backend_v1.pdf"]  파일명만
```

`curriculumNames`에 **버전이 없다.** 목은 `spring_backend_v1.pdf v1`처럼 붙여 뒀는데
서버는 파일명만 준다 — 같은 교안의 v1/v2가 함께 쓰이는 기수가 생기면 구분이 안 된다.
지금 9기는 둘 다 v1이라 안 드러난다(32차 Q3에서 같은 이유로 「지금은 필요 없다」고 답한
자리다). **화면은 파일명 그대로 그린다.**

### 살아남는 것

```
attendanceReachLevel()   응시율 5단 색 — 화면 표현이라 서버와 무관하다
STATUS_LABEL             코드 → 사람 말 (DONE 항목만 CLOSED로)
dueLabel()               마감 임박 문구 — 기준일만 MOCK_TODAY → 실제 오늘
filterState.ts           세션 필터 기억 — 값 타입만 바뀐다
```

# 하드닝 1차 (2026-08-18)

> `screen-hardening.md` 절차대로. 연동 직후라 **연동에서 고른 것이 맞았나**를 다시 보는
> 것이 이번 라운드의 중심이었고, 실제로 스코프 선택이 뒤집혔다.

## 1단계 · 컨트롤을 세고 시작한다

```
상태 4 · 반 2 · 정렬 3 · 검색칸 1 · 지우기 1 · 행 6      합 17종
필터 곱 4 × 2 × 3 = 24
```

데이터 축은 얕다 — 9기는 `RUNNING 1 · CLOSED 5`뿐이고 `PLANNED`가 안 보였다.
**그 「안 보인다」가 첫 발견이 됐다**(아래 §3-1).

## 2단계 · 실측

### 성능 — **회차 수에 비례한다**

```
0개  1892ms      1개  2721ms      5개  6308ms      6개  6962ms   (각 3회 평균)
                 → 고정 1888ms + 회차당 861ms
8개 예측 8775ms · 실제 7958ms                      (오차 817ms — 모델이 맞다)
```

대조군(같은 매니저·같은 시각)이 전부 1.4~2.3초다 — 교안 1.6 · 반 1.5 · 면담 1.7 ·
이번 회차 1.8 · 프로젝트 상세 2.3. **이 조회만 회차마다 값을 얹는다.**

### 경계

```
없는 classId        1228ms 200 · 0개      ← 400이 아니다
형식 틀린 classId     500ms 400
빈 classId / 없음 / 둘 다   ~600ms 400 PROJECT_LIST_SCOPE_AMBIGUOUS
모르는 status         607ms 400
긴 검색어(200자)     2178ms 200 · 0개
```

## 3단계·4단계 · 고친 것

### 3-1. 🔴 **연동에서 고른 스코프가 회차를 숨기고 있었다**

연동할 때 「담당 반 화면이니 `classId`」로 골랐다. 하드닝에서 두 스코프를 **대조**하니
이렇게 갈렸다.

```
cohort   8개   PLANNED 2 · RUNNING 1 · CLOSED 5
classId  6개              RUNNING 1 · CLOSED 5      ← 다가올 회차 둘이 없다
```

스펙이 `classId`를 **「그 반의 팀이 편성된 프로젝트만(team.class_id 경유)」**이라고
적어 뒀고, 그 두 회차는 **팀이 0개**다(실측). 즉 팀 편성 전 회차는 구조적으로 안 온다.

**매니저가 「이번에 뭐가 오나」를 보는 화면에서 그게 빠지면 안 된다.** 겹치는 6개는
`progress`·`actionItems`까지 값이 완전히 같아(대조 확인) 바꿔도 잃는 것이 없었다.

> 연동 단계에서는 **한쪽만 부르고 「담당 반이니 맞겠지」로 넘어갔다.** 두 스코프를
> 나란히 놓고 응답을 비교하는 데 1분이면 됐다. 대조표를 만들 때 「파라미터가 둘 중
> 하나」인 자리는 **둘 다 불러 보고 차이를 적어야** 한다.

### 3-2. 🔴 진입이 직렬 두 왕복이었다

```
전   반 목록 2.1초 ──▶ 목록 7.6초        표 10.0초
후   둘이 164ms에 나란히 출발            표  8.5초
```

`classId`를 쓰려니 **반 목록이 와야 조회를 만들 수 있었다.** 기수 스코프로 바꾸니
그 의존이 사라졌다 — 3-1을 고치자 성능이 딸려 왔다.

### 3-3. 🔴 네 실패가 한 문장이었다 (규칙 I)

```
403 · 404 · 400 · 500  →  전부 「목록을 불러오지 못했습니다 · 잠시 후 다시 시도해 주세요」
                          넷 다 [다시 시도] 버튼
```

권한 없음·스코프 오류에 재시도를 주면 **같은 실패를 반복시킨다.** `lib/errorCopy`로
갈랐고, `PROJECT_LIST_SCOPE_AMBIGUOUS`는 표에 없어 새로 넣었다(화면 버그라 재시도 없음).

```
403   회차 목록을 볼 수 있는 권한이 없습니다        재시도 ✗
404   담당 범위 밖입니다                          재시도 ✗
400   조회 범위가 정해지지 않았습니다               재시도 ✗
500   잠시 후 다시 시도해 주세요                   재시도 ⭕
```

### 3-4. 🔴 반 필터가 「예정」을 지우는 것을 화면이 안 말했다

3-1의 뒷면이다. `예정 + C반` = 0건인데 `예정 + 전체` = 2건이라, 빈 상태가
「조건에 맞는 회차가 없습니다」뿐이면 **「내 반에는 다음 회차가 없다」**로 읽힌다.
실제로는 아직 팀이 안 짜인 것이고 그건 곧 생긴다 — 빈 상태에 그 이유를 적었다.

### 3-5. 응시 칸을 **배경 칩**으로

`text-reach-*`로 칠하고 있었는데 흰 면에서 대비가 1.61~3.52다(캔버스 픽셀 실측).
같은 색을 배경으로 두면 4.90~11.29로 통과한다.

⚠ **전역 `REACH_STYLE`은 안 건드렸다.** 그 상수는 히트맵·명부·상세·리포트가 함께 쓰고
0·4단이 흰 글자인데, 그 화면들에서는 그 모양이 맞다 — 여기만 쓰는 `REACH_CHIP`을
따로 뒀다.

> 한 번 전역을 고쳤다가 **되돌렸다.** 「대비가 미달이니 전역을 고치면 된다」로 갔는데
> 다섯 화면의 모양이 같이 바뀌었고 사용자가 「보기 불편해졌다」고 했다.
> **공용 상수를 고치기 전에 그것을 쓰는 화면을 먼저 세야 한다.**
