# MG-03 면담 목록 — 상황 전수

> **절차는 [screen-hardening.md](../screen-hardening.md).** 이 문서는 1단계(상황 목록)와
> 그 뒤 단계에서 나온 실측·판정·고침을 담는다.
>
> 연동은 끝났다(PR #226). 여기는 **값이 오기 전·안 올 때·이상하게 올 때** 화면이 무엇을
> 하는가다.
>
> 매니저 4화면 중 **쓰기가 있어 먼저 돌린다**(하드닝 §화면이 크면 — 쓰기 있는 탭이 2순위,
> MG-04와 함께 앞선다). 공통 축(헤더·스코프·전환)은 여기서 한 번만 재고 나머지 화면은
> 참조한다.

---

## 1. 조회 흐름

```
useManagerCohort()   GET /members/me/enrollments        ─┐ 이름만 쓴다(헤더)
                                                        │ 목록은 이걸 안 기다린다
useInterviewRounds() GET /interviews/rounds            ─┐ 이게 끝나야
useInterviewList()   GET /interviews?assessmentRoundId ─┘ 목록이 나간다

쓰기
  POST   /interviews/{caseId}/exclusion     제외
  DELETE /interviews/{caseId}/exclusion     되돌리기
  → 성공하면 interventionKeys.all 무효화 (목록·회차·브리프 전부)
```

**회차가 정해지기 전에는 목록을 안 부른다** — `assessmentRoundId`가 필수 파라미터라
빈 값으로 부르면 400이다. 기본값은 `rounds`의 **마지막 회차**다.

> ⚠ **직렬 구간이 있다.** `rounds` → `list`가 순차라 첫 진입이 두 왕복이다. 실측 필요
> (2단계) — 백엔드 응답이 1.5~2초대라 4초가 될 수 있다.

## 2. 축

```
A. 회차 (rounds)
  A1 회차 여럿 · 마지막이 READY      A2 마지막이 OPEN(결과 전)
  A3 회차 0개                        A4 조회 실패

B. 목록 (interviews)
  B1 대상 여럿(예정·종결 섞임)       B2 대상 0명(회차 전체가 빔)
  B3 필터로 0건                      B4 제외된 행이 있음
  B5 round가 null(담당 밖 회차 id)   B6 조회 실패

C. 케이스 상태
  C1 PLANNED · briefState=NONE       C2 PLANNED · FAILED
  C3 PLANNED · DRAFT/CONFIRMED       C4 DONE
  C5 EXCLUDED                        C6 voidReviewPending=true

D. 위험 유형
  D1 LOW_PERSISTENT  D2 DECLINE  D3 INVALID  D4 OBSERVE(1차)  D5 모르는 코드

E. 쓰기
  E1 제외 성공        E2 제외 실패      E3 되돌리기 성공
  E4 되돌리기 실패    E5 연타           E6 배너의 케이스가 현재 필터에 없음

F. 스코프
  F1 담당 기수 1개    F2 여러 개    F3 0개    F4 조회 실패
```

**조합 수** — A4 × B6 × C6 × D5 × E6 × F4 = 4·6·6·5·6·4 = **17,280**. 전부 못 보므로
2단계에서 **실제로 갈리는 지점**만 추린다.

## 4. 실측 · 판정 · 고침

> 고친 것은 **지우지 않고 ✅** 로 남긴다.

### 2-1. 첫 진입이 **직렬 두 왕복** — 스피너 5~6초

```
rounds  TTFB 1.12 / 1.35 / 1.14초   (연결 0.04초 — 네트워크가 아니라 서버 계산)
list    TTFB 1.78 / 1.44 / 1.56초   4407B
합계    2.5 ~ 3.1초 + 콜드스타트
```

브라우저 실측(사이드바 클릭 → 프레임 단위): **0~5초 스피너, 6초에 첫 행.**
본문 높이는 752px로 고정이라 **레이아웃 시프트는 없다.**

`assessmentRoundId`가 필수라 회차를 받아야 목록을 부를 수 있다. **명부
(`findTraineeRoster`)는 생략하면 서버가 「이번 회차」를 골라 준다** — 같은 패턴을
면담에도 주면 왕복이 하나로 준다. → §5

### 2-2. ✅ 빵부스러기가 `면담 › › 담당 반`이 됐다 (플로우 관찰)

기수가 오기 전 1.5초 동안 구분자만 남았다. `?? ''`로 채우고 이었기 때문이다.

**고침 — `['면담', cohortName, '담당 반'].filter(Boolean).join(' › ')`.**
같은 패턴을 grep해 **MG-05 명부에도 있어 함께 고쳤다.**

> 오퍼레이터는 `cohortName ? ... : undefined`로 이미 막고 있었다(op-02 §255).

### 2-3. ✅ `[WARN]` 태그가 판정 근거에 그대로 노출됐다 (렌더)

```
[WARN] 응시 기간 종료까지 세션을 시작하지 않음
```

교육생 상세(MG-06)에만 벗김 함수를 붙이고 **면담 목록·브리프에는 안 붙였다.**
30차 R8에서 백엔드가 *"실서버 시드는 이 PR로 안 바뀐다"* 고 했으므로 계속 온다.

**고침 — `lib/riskSummary.ts`로 올리고 세 자리에 붙였다**(명부 상세 · 면담 목록 ·
브리프). 두 도메인이 쓰는 순간이 공용으로 올릴 때다(D14).

### 2-4. ✅ 결과 전 회차에서 **머리글과 본문이 다른 말**을 했다 (가로채기)

`resultStatus: PENDING`인데 `items`·`counts`가 채워져 오는 회차가 있다(실측 5차 —
PENDING인데 대상 4명). 그대로 그리면 이렇게 된다.

```
머리글   면담 1명 · 예정 1 · 종결 0 · 제외 0
본문     이 회차는 아직 결과가 없어요
```

**고침 — PENDING이면 개수·내역을 그리지 않는다.** 본문 쪽을 기준으로 맞췄다.
스펙이 「PENDING이면 그 안내를 그린다」이고, **아직 뒤집힐 수 있는 판정을 숫자로
단언하는 쪽이 더 나쁘다.** 서버 모순 자체는 §5로 나간다.

### 2-5. ⓘ 액션 열 잘림은 **오측이었다**

표가 1120px인데 본문이 1016px이라 「액션 열이 잘렸다」고 판정할 뻔했다. 컨테이너가
`overflow-x-auto`라 **잘리는 것이 아니라 스크롤**이고, 스크롤 래퍼로 다시 재니
950/950으로 넘치지도 않았다(하드닝 §측정 대상을 확인한다).

폭 지정은 `w-44` 같은 고정값에서 **퍼센트 합 100%** 로 바꿨다 — 서버 판정 근거
문장이 목보다 길어 열 균형이 어긋나 있었다. 잘림 문제는 아니었다.

### 2-6. ✅ 정상으로 확인된 것

| 축 | 결과 |
|---|---|
| **제외 쓰기** | 상태 전이 · 개수 갱신(예정 1→0, 제외 0→1) · 행 흐림 · 배너 · `08.16 제외 · 이담` |
| **되돌리기 쓰기** | 상태 복귀 · 개수 복구 · 배너 사라짐 · 액션 복원. **서버 상태도 원복 확인** |
| 한글 입력 | `ㅅ → 시 → 심 → 심예` — 조합 안 깨짐(입력은 로컬, 디바운스로만 올림) |
| 검색 0건 | `"존재하지않는이름"와 맞는 대상이 없습니다` — 「필터에 안 걸림」 문구 |
| 공백만 입력 | 검색으로 안 나감(행 그대로) |
| 조회 실패(500) | `목록을 불러오지 못했습니다` + 다시 시도 |
| 회차 전수(6개) | 1.26~1.79초 · 전부 200 |
| 정렬 | 스펙대로(제외는 예정과 같은 그룹 → 이름순). 무효는 데이터가 없어 미확인 |
| 담당 밖 회차 id | **200 + 빈 목록**(404 아님) → §5 |

## 5. 요청서로 나갈 것

| 무엇 | 근거 |
|---|---|
| **`resultStatus: PENDING`인데 `items`가 온다** | 5차 실측 — `round.resultStatus=PENDING`, `total=4`, `counts.PLANNED=4`. 스펙은 *"PENDING이면 위험 판정 자체가 없는 상태"*. 화면이 둘 중 하나를 버려야 한다 |
| **`assessmentRoundId`를 선택으로** | 필수라 `rounds` → `list` 두 왕복(2.5~3.1초). 명부는 생략하면 서버가 「이번 회차」를 골라 주고 응답으로 알려준다 — 같은 패턴 요청 |
| **담당 밖 회차 id가 200** | `00000000-…`로 불러도 200 + 빈 목록. 권한 없음이 「데이터 없음」으로 보인다. 30차 R3에서 `class-progress`에는 404를 넣어 줬는데 여기는 안 들어갔다 |
| `[SEVERE]`·`[WARN]` 시드 잔존 | 30차 R8에서 *"실서버에서 태그가 계속 보이면 알려 달라"* 고 했다 — **계속 보인다**(4차 `[WARN]`·`[SEVERE]` 실측) |
| `ProjectDetailResponse` 폐기 표시 누락 | 28차에서 회차 응시 창을 폐기하며 `UpcomingRoundResponse`에만 🔴를 붙였다. 실응답은 3차·6차 모두 `null`인데 설명문은 *"개요 타임라인의 응시 창이 이 값으로 그려진다"* — MG-08이 맞는다 |

```
컨트롤      드롭다운을 열어 항목이 읽히는지 · 반 필터 · 상태/위험 유형 조합
접근성      배지 색 대비 계산 · 키보드로 제외·되돌리기 · 스크린 리더
브리프 진입 목록 → 브리프 왕복(캐시가 있는 경로)에서 나는 사고 — MG-04에서 함께
```
