## 2. 🔴 R1 — `PENDING`인데 `items`가 옵니다

**스펙**은 이렇게 적고 있습니다.

> `resultStatus` — `PENDING`이면 화면이 **"이 회차는 아직 결과가 없어요"** 를 그린다.
> 리포트 발행 전이라 **위험 판정 자체가 없는 상태**다.

**실응답**(9기 · 미니프로젝트 5차)입니다.

```jsonc
"round": { "resultStatus": "PENDING", "publishedAt": null, "daysSincePublish": null },
"total": 4,
"counts": { "PLANNED": 4, "DONE": 0, "EXCLUDED": 0 },
"items": [
  { "name": "송지안", "status": "PLANNED", "riskType": "LOW_PERSISTENT", "briefState": "NONE" },
  { "name": "임윤슬", … }, { "name": "장수아", … }, { "name": "한유진", … }
]
```

**위험 판정이 없다면서 위험 유형이 붙은 케이스 4건을 함께 보냅니다.**

### 화면이 둘 중 하나를 버려야 합니다

그대로 그리면 한 화면이 서로 다른 말을 합니다.

```
머리글   면담 4명 · 예정 4 · 종결 0 · 제외 0
본문     이 회차는 아직 결과가 없어요
```

**저희는 본문 쪽을 기준으로 맞췄습니다** — 스펙이 「PENDING이면 그 안내를 그린다」이고,
**아직 뒤집힐 수 있는 판정을 숫자로 단언하는 쪽이 더 나쁘다**고 봤습니다. 그래서
`PENDING`이면 머리글의 개수·내역도 그리지 않습니다.

**다만 그 4명은 화면에서 사라집니다.** 실제로 면담이 필요한 사람이라면 매니저가
못 보게 되는 것이라, 어느 쪽이 사실인지 확인 부탁드립니다.

| 만약 | 그러면 |
|---|---|
| ① `PENDING`인데 판정이 나온 것이 **버그** | `items`·`counts`를 비워 주세요 |
| ② 판정은 나왔는데 `resultStatus`가 **안 따라온 것** | 그 회차는 `READY`가 맞습니다 |
| ③ 둘 다 의도 — **판정 전 미리보기** | 그런 뜻의 상태 값을 따로 주세요(`PROVISIONAL` 등). 저희가 「잠정」으로 그리겠습니다 |

> 5차는 리포트 발행 전(`publishedAt: null`)이고 응시가 진행 중인 회차입니다.
> ②일 가능성이 높아 보이지만 저희가 단정할 근거가 없습니다.

## 3. 🟠 R2 — 첫 진입이 두 왕복입니다

`assessmentRoundId`가 **필수**라, 화면은 회차 목록을 먼저 받아야 면담 목록을 부를 수
있습니다. 실측입니다(같은 시각 · 같은 토큰 · 3회).

```
GET /interviews/rounds       TTFB 1.12 / 1.35 / 1.14초   (연결 0.04초)
GET /interviews?...          TTFB 1.78 / 1.44 / 1.56초   4407B
                             ────────────────────────
합계                          2.5 ~ 3.1초  (직렬)
```

**연결은 0.04초입니다** — 네트워크도 크기도 아니고 서버 계산입니다. 브라우저에서
사이드바를 눌러 들어가면 **0~5초 스피너, 6초에 첫 행**입니다(콜드스타트 포함).

### 명부는 이미 그 문제를 풀어 두셨습니다

`GET /cohorts/{id}/trainees`는 `assessmentRoundId`를 **생략하면 서버가 「이번 회차」를
골라** 응답의 같은 이름 필드로 알려줍니다. 그래서 명부 화면은 **한 왕복**입니다.

```
명부    생략 → 서버가 고름 → 응답에 assessmentRoundId          1왕복
면담    필수 → rounds를 먼저 받아야 함                          2왕복
```

**면담에도 같은 규칙을 주시면** 왕복이 하나 줄고, 회차 드롭다운은 지금처럼
`/interviews/rounds`로 따로 채우면 됩니다(그건 병렬로 나갈 수 있습니다).

> 우선순위는 낮습니다 — 화면이 죽는 문제가 아니라 진입이 느린 것뿐입니다.
> 다만 두 API가 같은 자리에서 다른 규칙인 것이 걸립니다.

**권한이 없는 것과 데이터가 없는 것이 같은 응답입니다.** 화면은 이때

여기에도 그대로 적용됩니다.

> 그것으로 가를 수는 있습니다. 다만 **빈 결과와 권한 없음을 화면이 판정하게 되는 것**이라

## 7. 🟠 R6 — 질문 근거에 내부 UUID가 들어 있습니다

브리프(MG-04)를 실제로 생성해 화면에 그려 보고 나왔습니다. `questionRationale`은
스펙상 **「매니저만 보는 근거. 어떤 데이터에서 나온 질문인지」** 인데, 실제 값이
이렇습니다.

```
· JPA 엔티티 관계 설정 부분이 어려우셨던 것 같은데, 제가 도와드릴 방법 있을까요?
  문제 1 L3 인터뷰 (interviewSourceId 7d017b49-1095-49dd-a8c7-c8d135eb78ab) 기반 Q&A 질문

· 문답에서 계속 어려움을 겪는 것 같은데, 혹시 요즘 학습에 부담 느끼시나요?
  PERSISTENT_LOW 위험 사유에 기반한 확인 질문
```

**질문 문장은 자연스러운데 근거 줄만 개발자용입니다.** `interviewSourceId`는 매니저에게
아무 뜻이 없고, `PERSISTENT_LOW`도 화면 어디에서도 그 코드로 부르지 않습니다
(옆의 배지가 `지속 저점`이라고 말합니다).

**화면에서 벗기지 않았습니다** — 서버가 만든 문장이라 정규식으로 자르면 문장 구조가
바뀔 때 깨지고, **어디까지가 개발자용인지 화면이 판정하게 됩니다.** 그건 저희가
지켜 온 경계 밖입니다.

```
문제 1 L3 인터뷰 (interviewSourceId …) 기반 Q&A 질문
  →  1번 문항의 대안 비교 단계에서 나온 답변을 근거로

PERSISTENT_LOW 위험 사유에 기반한 확인 질문
  →  지속 저점 판정을 근거로
```

같은 뜻을 사람 말로 주시면 그대로 그리겠습니다.

## 8. 🟡 R7 — AI 생성이 24초입니다

스펙에는 「`POST .../brief` — AI 생성, **수 초 대기**」라고 적혀 있습니다.
브라우저에서 클릭 순간부터 재니 이렇습니다.

```
[150ms]    「만드는 중…」 · 버튼 잠김
[24001ms]  여는 말 + 질문 8개 도착
```

**화면이 줄일 수 있는 시간이 아닙니다**(서버가 AI를 부르는 구간). 다만 24초 동안
매니저가 보는 것은 버튼 문구 하나뿐이라, 두 가지 중 하나가 있으면 좋겠습니다.

- **문구를 사실에 맞춰** 주세요 — 「수 초」를 보고 저희가 화면 안내를
  *「잠시 걸립니다」* 로 썼는데, 24초는 「잠시」가 아닙니다
- 또는 **오래 걸리는 이유**를 화면이 말할 수 있게 (예: 응답에 예상 소요를 싣거나,
  생성 단계를 알려 주는 방법이 있으면)

> 급하지 않습니다. 다만 이 값을 모르면 다음 사람이 「느리다 = 버그」로 읽습니다.

## 9. 🟠 R8 — 빈 상세 사유가 `(기록 없음)`으로 저장됩니다

브리프를 실제로 저장하고 다시 열어 보고 나왔습니다.

```jsonc
// 보낸 것
PUT /interviews/{caseId}/brief
{ "causes": ["CONCEPT_GAP"], "why": "", "nextAction": "하드닝 저장 실패 테스트" }

// 다시 조회한 것
"savedRecord": { "causes": ["CONCEPT_GAP"], "why": "(기록 없음)", "nextAction": "…" }
```

**스펙은 이렇게 적혀 있습니다.**

> `why` — 상세 사유. **매니저가 타이핑한 서술.** 비워도 저장됩니다

빈 값을 그대로 저장하지 않고 **한국어 문구로 치환**합니다. 그러면 셋이 어긋납니다.

- **화면 문구를 서버가 만듭니다.** 「없음」을 무엇이라 쓸지는 화면이 정해 온 것이고,
  다른 자리에서는 저희가 `—`로 그리고 있습니다
- **다시 열면 입력칸에 그 글자가 들어 있습니다.** 매니저가 이어서 쓰려면 `(기록 없음)`을
  **먼저 지워야** 합니다
- 그 상태로 저장하면 **`(기록 없음)`이 진짜 타이핑한 서술로 남습니다.** 다음에 열 때
  「안 쓴 것」과 「그렇게 쓴 것」을 구분할 수 없습니다

**빈 문자열이나 `null`로 그대로 저장해 주세요.** 화면은 이미 빈 값을 다룰 준비가 돼
있습니다(추후 계획이 비면 확인 모달을 띄우는 것도 같은 이유입니다).

> `nextAction`은 이런 치환이 없었습니다 — 같은 요청에서 보낸 값이 그대로 왔습니다.
> 두 필드가 같은 규칙이어야 할 것 같습니다.

## 10. 🔴 R9 — 매니저 조회 둘이 7초·13초입니다

### ① 명부 — 7초

교육생 명부(MG-05)를 하드닝하며 쟀습니다. **변수를 바꿔도 안 줄어듭니다**(같은 시각·
같은 토큰·같은 매니저).

```
GET /cohorts/{id}/trainees?size=20               7774ms   29450B   rows=20
GET /cohorts/{id}/trainees?size=1                7865ms    2922B   rows=1
GET /cohorts/{id}/trainees?size=20&회차 지정      6862ms   29450B
GET /cohorts/{id}/trainees?size=1 &회차 지정      7154ms    2922B
GET /cohorts/{id}/trainees?query=노주안           2621ms    2921B   rows=1   ← 여기만 빠릅니다

── 대조군 (같은 매니저 · 같은 시각) ──
GET /interviews?assessmentRoundId=…              1449ms
GET /cohorts/{id}/classrooms                     1516ms
GET /members/me/enrollments                      1149ms
```

### `size`로는 안 줄고 `query`로만 줍니다

이 둘이 갈림길로 보입니다.

| 바꾼 것 | 결과 | 읽은 것 |
|---|---|---|
| `size` 20 → 1 (응답 29KB → 2.9KB) | **7.8초 그대로** | 크기도 직렬화도 아닙니다 |
| 회차 생략 → 지정 | 그대로 | 「이번 회차 고르기」가 원인이 아닙니다 |
| **`query`로 1건** | **2.6초** | 모집단이 줄면 그만큼 줍니다 |

`size`는 결과를 **자르는** 것이라 집계는 26명분을 다 돌고, `query`는 **모집단을 줄이는**
것이라 계산량이 함께 준다 — **행마다 도는 계산이 있다**는 뜻으로 읽었습니다. 회차
지표·우수 누적·위험 판정이 행당 붙는 값들이라 그쪽이 후보로 보입니다.

**저희가 줄일 수단이 없습니다.** 페이지 크기는 이미 20이고, 지표를 빼고 부르는
파라미터가 없습니다. 브라우저에서는 사이드바 클릭 후 **11초에 첫 행**이 그려집니다.

> ⚠ **담당 반이 26명일 때의 수치입니다.** 기수 전체(208명)를 보는 오퍼레이터 쪽은
> 재보지 않았는데, 행에 비례한다면 그쪽이 더 무거울 수 있습니다.

### ② 교육생 타임라인 — 13~17초, `size`가 무시됩니다

교육생 상세(MG-06)입니다. 이쪽은 더 분명합니다 — **`size`를 바꿔도 응답이 바이트까지
같습니다.**

```
GET .../trainees/{id}/timeline?size=100   13474ms   14512B   이벤트 15 · hasNext=false
GET .../trainees/{id}/timeline?size=20    15014ms   14512B   이벤트 15
GET .../trainees/{id}/timeline?size=5     12374ms   14512B   이벤트 15   ← 5를 줘도 15건

── 같은 교육생 대조군 ──
GET .../trainees/{id}                      2822ms    6601B
GET /projects/{pid}/evaluations/{uid}      1546~2088ms
```

스펙은 커서 페이징(`size`·`cursor`·`hasNext`)이라고 적고 있는데 **`size`가 안 걸립니다.**
`hasNext: false`로 오는 것도 15건을 다 보냈으니 사실이지만, 그러면 페이지 크기를 준
의미가 없습니다.

**이벤트가 15건인데 13초입니다.** 같은 교육생의 상세가 2.8초이므로 교육생 조회 자체가
느린 것도 아닙니다. 브라우저에서는 **격자가 200ms에 그려지고 이력만 12초** 동안
스피너입니다(조회를 나눠 둬서 화면 전체가 멈추지는 않습니다).

### 두 건이 같은 종류로 보입니다

명부는 `size`로 안 줄고 `query`로 줄고, 타임라인은 `size`가 아예 안 걸립니다.
둘 다 **결과를 자르기 전에 전량을 계산**하는 모양이라, 한쪽 원인을 찾으면 다른 쪽도
같이 풀릴 수 있어 함께 적습니다.

**저희가 줄일 수단이 없습니다** — 페이지 크기는 이미 주고 있고, 지표나 이벤트를 빼고
부르는 파라미터가 없습니다.

## 11. 이번에 확인한 화면

**매니저 4화면을 전부 하드닝했습니다**(MG-03 면담 목록 · MG-04 브리프 · MG-05 명부 ·
MG-06 교육생 상세) — 연동이 아니라 「값이 오기 전·안 올 때·이상하게 올 때」를 재는
단계입니다.

| 축 | 결과 |
|---|---|
| 회차 전수(6개) | 200 · 1.26~1.79초 |
| 쓰기 2건 | 제외 → 되돌리기 왕복. 상태·개수·서버 상태 모두 정상 복귀 |
| 조회 실패(500) | 화면이 실패로 그림 + 재시도 |
| 한글 입력 | 조합 안 깨짐 |
| 정렬 | 스펙대로(제외는 예정과 같은 그룹 → 반 → 이름) |
| 브리프 생성·저장 | 24초 후 생성 · 저장하면 목록 복귀 + 개수 갱신 · 실패해도 입력 유지 |

| 명부 페이지네이션 | 2쪽 이동 · **2쪽에서 검색해도 없는 3쪽을 안 부름** · 정렬 4종 |
| 상세 조회 3종 | 격자 200ms · 이력 12초 · 「자세히」의 채점 근거가 **개념 이름으로 정확히 매칭**(전수) |

**아직 못 본 것** — `INVALID`(무효 응시) 케이스가 시드에 없어 **정렬 ①순위와
`[무효 확인]` 게이트를 확인하지 못했습니다.** 30차 §14에서 보강 예정이라고 하신
목록에 포함돼 있어 함께 기다리겠습니다.

> 버튼을 열지 않고 사유를 화면에 적어 뒀습니다. 열리면 그 줄만 지웁니다.
