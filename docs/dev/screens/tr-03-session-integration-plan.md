# TR-03 세션 — 목과 서버 계약 대조 · 연동 계획

> **왜 이 문서가 먼저인가.** 세 화면(홈·제출·리포트)을 붙일 때 배운 것이 하나 있다 —
> **목이 지어낸 축을 늦게 발견할수록 비싸다.** 리포트에서 두 개(개념별 공개 범위 ·
> 문답 2벌)를 코드 다 쓴 뒤에 발견해 자료구조부터 다시 짰다.
>
> 세션은 그 차이가 훨씬 크다. **점수를 서버가 안 준다**는 것 하나가 목 자료구조의
> 중심을 무너뜨린다. 그래서 코드를 쓰기 전에 대조부터 끝낸다.

---

## 1. 한눈에 — 무엇이 다른가

| 축 | 목 | 서버 | 영향 |
|---|---|---|---|
| **점수** | 답변마다 `score: 0~5` | **주지 않는다** | 🔴 자료구조 변경 |
| **진행 위치** | 화면이 인덱스로 관리 | **서버 커서가 정본** | 🔴 리듀서 축소 |
| **결과 코드** | 3종 | **5종** | 🟡 분기 재작성 |
| **데이터 단위** | 개념 3개를 한 번에 | **문제 하나씩 조회** | 🟡 로딩 지점 추가 |
| **힌트** | 문제마다 2개 미리 보유 | **열릴 때 하나씩** | 🟡 |
| **도달 단계** | 화면이 계산(`통과 수`) | 세션 중에는 **안 알려준다** | 🟡 표시 제거 |
| **문제 수** | `3` 고정 | `problemTotal`(0~3) | 🟢 값 사용 |
| **모드 이름** | `RETRY` | `REVIEW` | 🟢 이름 변경 |

---

## 2. 🔴 점수를 안 준다 — 여기가 중심이다

목은 답변마다 점수를 받아 타임라인에 쌓는다.

```ts
type ThreadItem =
  | { kind: 'answer'; text: string; score: Score }   // ← score를 채울 값이 없다
  | { kind: 'hint'; text: string }
```

서버는 점수도 통과 여부도 응답에 넣지 않는다. 대신 **미달을 다른 방식으로 전한다.**

> 💡 **`hint`가 오는 것이 점수를 알려주지 않으면서 미달을 전하는 유일한 신호다.**
> (스펙 원문)

| 답변 결과 | 응답 | 화면이 아는 것 |
|---|---|---|
| 통과 | `outcome=NEXT_TURN` 등 · `hint: null` | 다음으로 간다 |
| 미달 (힌트 남음) | `outcome=RETRY_WITH_HINT` · **`hint` 있음** | 같은 질문에 다시 답한다 |
| 미달 (힌트 소진) | `outcome=PROBLEM_CLOSED` · `hint: null` | 이 문제는 끝 |

**화면은 점수를 몰라도 된다.** 애초에 학생에게 안 보여주기로 한 값이고(정의서 §7),
화면이 하는 일은 *"다시 답할 자리인가 다음으로 갈 자리인가"* 를 아는 것뿐이다.

### 그래서 `ThreadItem`이 이렇게 바뀐다

```ts
type ThreadItem =
  | { kind: 'answer'; text: string }     // score 제거
  | { kind: 'hint'; text: string }
```

점수를 쓰던 자리를 전수 조사해서 지운다. **"미달이라 힌트가 열렸다"는 사실만 남는다.**

---

## 3. 🔴 진행 위치를 서버가 갖는다

목 리듀서는 `conceptIndex` · `answered` · `current`로 **화면이 어디에 서 있는지**를
직접 관리한다. 서버는 그것을 커서로 갖고 있다.

> ⚠️ **어느 문제의 어느 질문인지는 요청에 싣지 않는다.** 진행 위치는 서버 커서가
> 정본이다 — 클라이언트가 지목하게 두면 계단을 건너뛰거나 이미 닫힌 문제에 답을 붙이는
> 요청이 만들어진다. (스펙 원문)

`POST /answers`의 본문은 `{ answerText }` 하나다. 문제 번호도 질문 번호도 없다.

### 무엇이 남고 무엇이 사라지나

| 목 상태 | 처리 |
|---|---|
| `conceptIndex` · `concepts[]` | **서버가 준다** — `currentProblemNo` · `problemTotal` |
| `answered[]` (끝난 질문들) | **서버가 준다** — `GET /problems/{no}`의 `turns[]` |
| `current[]` (지금 질문 타임라인) | **화면이 유지** — 응답을 이어 붙인다 |
| `reached[]` (도달 단계) | **세션 중에는 모른다** — 지운다 |
| `phase` · `transitionReason` | **화면 것** — `outcome`에서 파생 |
| `callersExpanded` | **화면 것** — 그대로 |

리듀서는 사라지지 않고 **얇아진다.** 남는 일은 *"서버 응답을 화면 상태로 옮기는 것"*
과 순수 UI 상태(펼침·전환 애니메이션)뿐이다.

---

## 4. 🟡 결과 코드 5종을 어떻게 그리나

| `outcome` | 뜻 | 화면 |
|---|---|---|
| `RETRY_WITH_HINT` | 미달 · 힌트가 열렸다 | 같은 질문 자리에 **힌트를 덧붙이고** 답을 다시 받는다 |
| `NEXT_TURN` | 통과 · 같은 문제의 다음 질문 | 새 질문 말풍선 |
| `NEXT_PROBLEM` | 이 문제 끝 · 다음 문제로 | 전환 화면 → `GET /problems/{nextProblemNo}` |
| `PROBLEM_CLOSED` | 힌트 다 쓰고도 미달 · 문제가 닫혔다 | 전환 화면(**접힘**) → 다음 문제 |
| `SESSION_ENDED` | 세션 종료 | 종료 화면 |

목의 3종(`SAME_QUESTION`·`NEXT_QUESTION`·`NEXT_CONCEPT`)과 대응은 이렇다.

```
SAME_QUESTION  → RETRY_WITH_HINT
NEXT_QUESTION  → NEXT_TURN
NEXT_CONCEPT   → NEXT_PROBLEM · PROBLEM_CLOSED · SESSION_ENDED  (셋으로 갈린다)
```

**목이 하나로 뭉쳐 두었던 것이 셋으로 갈린다.** 특히 `NEXT_PROBLEM`과 `PROBLEM_CLOSED`는
전환 화면 문구가 달라야 한다 — 앞은 통과해서 넘어가는 것이고 뒤는 못 풀고 접힌 것이다.
목에도 그 구분(`TransitionReason: 'STOP' | 'NEXT'`)이 있으니 **연결만 하면 된다.**

---

## 5. 🔴 힌트를 두 번 쓰지 않게

가장 조심할 지점이다.

> ⚠️ `POST /answers`가 `hint`를 함께 준 뒤에 이 경로를 또 부르면 **두 번째 힌트가
> 열린다.** 자동으로 받은 힌트는 이미 소진된 것이므로 화면은 그것을 그리기만 하고
> 다시 부르지 않는다. (스펙 원문)

```
답변 제출 → 응답에 hint 있음 → 화면은 그것을 그리기만 한다
                              → POST /hints를 부르면 안 된다 (2개째 소모)
```

힌트가 열리는 경로가 둘인데 **같은 횟수(질문당 2회)를 나눠 쓴다.** 남은 수는 서버가
`hintsUsed`·`hintsLeft`로 알려주므로 화면이 세지 않는다.

---

## 6. 🟢 그대로 쓸 수 있는 것

목을 만들 때 요청했던 것들이 그 모양으로 왔다.

| | |
|---|---|
| `outcome`을 서버가 판정 | 화면이 *"힌트 다 썼는데도 미달인가"* 를 안 센다 |
| `hintsUsed` · `hintsLeft` | 화면이 힌트 수를 안 센다 |
| `lastTurnOfSession` | 버튼 문구를 `답변 제출하고 마치기`로 바꾸는 신호 |
| `shownHints[]` | 새로고침해도 이미 연 힌트가 복원된다 |
| `highlight` | 질문마다 코드 강조 구간이 옮겨간다 |
| 힌트가 즉답 | AI를 안 부른다 — 분석 시점에 동결된 문구 |

**화면 컴포넌트 7개는 거의 그대로 산다** — 코드 패널·질문 스레드·입력바·전환·종료·
인트로·이탈 토스트. 바뀌는 것은 그것들에 값을 넣어 주는 층이다.

---

## 7. 새로고침을 어떻게 살리나

목에는 없던 요구다. 서버가 커서를 가지므로 **복원이 가능해졌다.**

```
진입 → GET /current            세션이 있나 · 어느 상태인가
     → status READY            시작 전 안내를 그린다
     → status IN_PROGRESS      GET /problems/{currentProblemNo} 로 이어서 그린다
```

`GET /problems/{no}`가 `turns[]`(끝난 질문들)와 `current`(지금 질문)를 함께 주므로
**중간에 새로고침해도 그 자리가 복원된다.** `shownHints[]`까지 와서 이미 연 힌트도 산다.

> `POST /start`는 두 번 눌러도 안전하다 — 이미 진행 중이면 그대로 돌려준다(스펙 명시).

---

## 8. 다시 보기(REVIEW) — 별도 경로다

```
POST /assessment-sessions/reviews   { reportId }   → 새 세션 생성
```

- 도달 **2단 미만** 문제만, **L1부터** 다시
- 문제·질문·힌트는 1차와 **완전히 동일**(복사) — AI를 다시 안 부른다
- `hintsLeft`는 **항상 0** — 다시 보기에는 힌트가 없다

화면은 1차와 같은 컴포넌트를 쓰되 `mode === 'REVIEW'`로 문구만 바꾼다. 목의
`SessionMode`를 `RETRY` → `REVIEW`로 고친다.

---

## 9. 작업 순서

**한 번에 다 붙이지 않는다.** 읽기부터 확인하고 쓰기로 간다 — 쓰기는 되돌릴 수 없다.

| | 무엇 | 되돌릴 수 있나 |
|---|---|---|
| ① | `_/api/` 어댑터 · 타입 대조 반영(점수 제거 등) | — |
| ② | `GET /current` 붙이기 → 시작 전 안내 화면 | ✅ 읽기만 |
| ③ | `POST /start` → `GET /problems/1` | ❌ **세션이 시작된다** |
| ④ | `POST /answers` 한 번 → `outcome` 확인 | ❌ |
| ⑤ | 힌트·전환·종료 | ❌ |
| ⑥ | 다시 보기 | ❌ |

**②까지는 안전하다.** ③부터는 계정 하나를 소모하므로, 시작 전에 그 계정으로 확인할
것을 다 확인해 둔다.

> 응시 가능 계정이 **10개** 있다(28차 R1). 한 번에 하나씩 태우면 여섯 단계를 다
> 밟아도 여유가 있다.

## 10. 시간 상한은 **서버가 잰다** — 화면은 표시만

목은 화면이 재서 스스로 종료시켰다. 서버가 두 상한을 다 갖고 있고, **넘긴 요청을
409로 거절하면서 상태를 이미 바꿔 둔다.**

| | 상한 | 넘기면 | 그다음 |
|---|---|---|---|
| 세션 | `timeLimitAt`(기본 60분) | 세션이 닫힌다 | `GET /current`가 **204** |
| 문제 | 그 문제 시작 + 20분 | 그 문제만 접고 **커서가 다음 문제로** | `GET /current`가 새 번호 |

> ⚠️ **둘 다 409를 받은 시점에 서버 상태는 이미 바뀌어 있다.** 응답에 다음 자리가
> 실리지 않으므로 화면은 `GET /current`를 다시 불러 커서를 읽는다 — 200이면 그 문제로
> 이동, **204면 종료 화면**이다. (스펙 원문)

**그래서 화면은 시간을 재되 막지 않는다.** 카운트다운은 보여주고, 끝났는지는 서버가
정한다. 목의 `CONCEPT_TIMEOUT`·`TIMEOUT` 액션이 "화면이 종료를 결정"하던 것을
**"409를 받으면 다시 읽는다"** 로 바꾼다.

### 답변 제출에서 처리해야 할 오류가 여덟이다

| 코드 | 화면 |
|---|---|
| `SESSION_TIMEOUT` · `PROBLEM_TIME_LIMIT_EXCEEDED` | `GET /current` 재조회 → 이동 또는 종료 |
| `ASSESSMENT_WINDOW_CLOSED` · `REVIEW_DUE_AT_PASSED` | 종료 안내 — 더는 못 받는다 |
| `ANSWER_ALREADY_SUBMITTED` | 다시 불러오면 된다(낙관적 잠금) |
| `GRADING_FAILED`(503) | **같은 답을 그대로 재전송** — 서버가 자리마다 멱등키를 고정한다 |
| `SESSION_NOT_STARTED` | `POST /start`를 안 불렀다 |
| `ANSWER_TEXT_REQUIRED` | 빈 본문 — 화면이 먼저 막는다 |

> ⚠️ **AI 채점에 4.5~7.7초가 걸린다**(스펙 명시). 클라이언트 타임아웃을 짧게 잡지 않는다.

## 11. 🔴 `GET /current`는 조회가 아니다 — 실측으로 확인

**읽기만 하지 않는다.** 상한을 넘긴 세션·문제를 **그 자리에서 닫고** 결과를 반영해
돌려준다(스펙 명시). 실제로 확인했다.

```
조회 전   홈: ASSESSMENT_IN_PROGRESS / RESUME_ASSESSMENT
GET /current  →  204
조회 후   홈: ASSESSMENT_COMPLETED / WAIT_FOR_REPORT · 세션 INTERRUPTED
```

한 번의 조회로 세션이 닫히고 홈 카드까지 바뀌었다. 응시 중이던 다른 계정도 같았다.

| 넘긴 상한 | 이 조회가 하는 일 | 응답 |
|---|---|---|
| 세션 | `INTERRUPTED`로 닫는다 | **204** |
| 문제 | 그 문제를 접고 커서를 다음으로 | 200 · 새 `currentProblemNo` |

**의도된 설계다** — 학생이 아무것도 제출하지 않고 새로고침만 해도 상한이 반영된다.
종전에는 쓰기 요청만 상한을 봐서 남은 시간이 음수인 화면이 그려졌다(스펙 각주).

### 그래서 테스트할 때 조심한다

**세션 화면에 들어가는 것만으로 계정이 소모될 수 있다.** 이미 상한을 넘긴 계정은
진입 즉시 닫힌다. 시작 전(`READY`) 계정은 안전하다 — 아직 상한이 없다.

---

## 12. 🔴 204를 "완료"로 읽지 않는다

> **204는 살아 있는 세션이 하나도 없다는 뜻일 뿐이고 그 이유는 여섯 가지다** —
> 이미 완료했다 · 방금 상한을 넘겨 닫혔다 · 응시 창이 닫혔다 · 아직 분석이 안 끝났다 ·
> 분석이 실패했다 · 팀 배정이 끊겼다. (스펙 원문)

**본문이 없으므로 세션 응답만으로는 사유를 가릴 수 없다.** 화면은 홈의
`representativeStatus`를 함께 봐야 한다.

```
GET /current → 204
  ↓
GET /assessment-rounds 의 representativeStatus 로 사유를 가른다
  ASSESSMENT_COMPLETED      → 응시를 마쳤다
  ASSESSMENT_WINDOW_CLOSED  → 창이 닫혔다
  ANALYZING · ANALYSIS_FAILED → 아직/실패
```

**즉 세션 화면은 두 조회를 함께 본다.** 목에는 없던 의존이다 — 목은 세션 데이터만으로
모든 것을 알 수 있었다.

---

## 13. 그 밖에 스펙에서 확인한 것

**① `null`인 필드는 키가 통째로 빠진다**(`NON_NULL` 직렬화). `x === null`이 아니라
`x == null`로 판정해야 한다 — 시작 전에는 `startedAt`·`timeLimitAt` 키 자체가 없다.

**② 문제 번호를 세션 API가 다시 매긴다.** 원본에 빈틈이 있어도(1번이 미생성이면 2·3만
남는다) 세션은 `1~problemTotal`로 다시 준다. **받은 번호를 그대로 쓴다.**

**③ `PAUSED`는 세션 응답에 오지 않는다.** `GET /current`의 `status`는 `READY`·
`IN_PROGRESS` 둘뿐이다(스펙 표 명시). 세션 상태 8종은 더 넓은 집합이고 화면이 보는
것은 둘이다.

## 14. 남은 판단 — 코드 쓰기 전에 정할 것

| | 무엇 | 선택지 |
|---|---|---|
