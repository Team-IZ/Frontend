## 1. 🔴 R1 — 교안 섹션 조회가 90초 넘게 안 옵니다

### 관측

같은 엔드포인트인데 교안에 따라 갈립니다.

```
GET /api/v0/curricula/{materialId}/sections

1de9d031…  섹션 2개 ·  38쪽  →  200   9.16초   1,146B
2e390105…  섹션 7개 · 120쪽  →  ❌ 90초 타임아웃 (응답 없음)
```

**둘 다 `analysisStatus: SUCCEEDED`입니다.** 단건 상세(`GET /curricula/{materialId}`)는
같은 교안에 대해 **1.06초**에 200으로 옵니다 — 느린 것은 섹션 조회 하나입니다.

> 10차 §2(프록시 502)와 다른 건입니다. 그쪽은 **동시 요청**에서 나는 502이고, 이건
> **단일 요청**이 안 끝납니다. 순차로 한 건만 보내도 같습니다.

### 이게 저희를 막는 이유

교안 상세가 이 조회 위에 서 있습니다 — 섹션 목록(마스터)과 가르친 항목(디테일)이
전부 여기서 옵니다. 안 오면 화면 절반이 `섹션을 불러오지 못했습니다`입니다.

그리고 **섹션이 많은 교안일수록 안 열립니다.** 7섹션에서 이미 90초를 넘으니, 실제
교안(120쪽·수십 섹션)은 더 심할 것으로 봅니다 — 지금 시드에서 가장 큰 것이 그 7개입니다.

### 요청

**응답 시간을 재 주세요.** 저희 쪽에서 보이는 것은 여기까지입니다.

섹션 2개짜리도 **9.16초**라 크기와 무관한 고정 비용이 있어 보입니다(같은 토큰으로 부른
다른 조회는 1초 안팎입니다). 항목마다 `usedAsVerificationConcept`·`usedRoundLabels`를
채우면서 회차 조회가 반복되는 것이 아닐까 짐작하지만, 저희가 확인할 수는 없습니다.

**타임아웃을 늘려 달라는 요청이 아닙니다** — 9초도 화면이 기다리게 하기에는 깁니다.

## 2. 🟠 R2 — 교육생 초대 재발송이 "보냈다"고 말할 수 없습니다

### 관측

같은 일을 하는 API가 역할마다 다릅니다.

| 대상 | API | 인증 | 결과를 알 수 있나 |
|---|---|---|---|
| 오퍼레이터 | `POST …/operators/invitations/{tokenId}/resend` | ✅ | ✅ |
| 매니저 | `POST …/manager-invitations/{tokenId}/resend` | ✅ | ✅ (9차 R7) |
| **교육생** | `POST /auth/invitations/resend` | ❌ **없음** | ❌ |

교육생만 **받는 사람용 API**를 쓰고 있습니다. 계정 존재 여부를 숨기려 **항상 같은 202**를
주고(*"응답이 갈리면 그 자체가 계정 확인 수단"* — 스펙 명시), 쿨다운에 걸리면 202를
받고도 메일이 안 나갑니다.

### 이게 화면에 만든 것

명단 탭에서 여러 명을 골라 재발송하는데, **몇 명에게 실제로 나갔는지 쓸 수가 없습니다.**

```
전:  "3명에게 활성화 초대를 다시 보냈어요"       ← 서버가 뒷받침하지 않는 말
후:  "3명에게 활성화 초대를 다시 요청했어요
      — 메일 도착까지 시간이 걸릴 수 있습니다"   ← 지금 이렇게 씁니다
```

**받는 사람용 API라 이메일 하나씩 받습니다** — 고른 사람 수만큼 호출이 나갑니다.

### 요청

**오퍼레이터·매니저와 같은 모양으로 하나 더 만들어 주세요.**

```
POST /api/v0/cohorts/{cohortId}/trainees/{traineeId}/invitations/resend
```

또는 여러 명을 한 번에 받는 형태여도 됩니다(명단은 골라서 보내는 화면이라 그쪽이 더
맞습니다). 필요한 것은 **인증된 경로**와 **실제로 나간 수**입니다 — `registerTrainees`가
이미 `invitationSentCount`를 주고 있으니 같은 값이면 됩니다.

> `TraineeRosterEntry`에 `pendingInvitationTokenId`가 없어서 토큰 기반으로는 못 부릅니다.
> 매니저처럼 그 필드를 같이 주시면 화면이 재발송 버튼을 정확히 켤 수 있습니다 —
> 지금은 `status === 'INVITED'`로 유추합니다.

## 3. 🟠 R3 — 재분석 경고를 좁힐 수 없습니다

### 관측

```jsonc
// GET /api/v0/curricula/{materialId}/projects
["미니프로젝트 4차", "미니프로젝트 5차"]     // ← 이름 배열이 전부입니다
```

### 이게 저희를 막는 이유

다시 분석하면 **섹션이 합쳐지거나 쪽 번호가 달라집니다.** 그러면 이미 발행된 리포트의
교안 위치가 실제와 어긋나고, 면담에서 `3장 36~46쪽`을 폈는데 다른 내용이 나옵니다.

그래서 재분석 전에 **응시가 시작된 회차**를 경고해야 하는데, 응시 여부를 알 수 없어
**연결된 회차가 하나라도 있으면 경고**하게 됐습니다.

```
전:  응시가 시작된 회차만 경고 (attended > 0)
후:  연결된 회차가 있으면 무조건 경고
```

**좁은 쪽으로 틀리는 것보다 낫다고 판단했습니다** — 아직 응시 전인 회차에도 경고가
뜨는 것은 과하지만, 응시가 시작된 회차를 조용히 지나가면 발행된 리포트가 어긋납니다.
다만 **경고가 늘 뜨면 아무도 안 읽습니다.**

그리고 `연결된 프로젝트` 탭이 표에서 **칩 목록으로 바뀌었습니다** — 열 넷 중 셋(기수·
확정 개념·응시 수)이 비어서 표를 세울 수가 없었습니다.

### 요청

이름 대신 **객체 배열**로 주시면 좋겠습니다.

```jsonc
[
  { "projectId": "…", "name": "미니프로젝트 4차",
    "cohortName": "9기",
    "attendedCount": 24,        // ← 이 값 하나가 경고 문턱을 정합니다
    "conceptNames": ["트랜잭션 경계 설정", "…"] }
]
```

**`attendedCount` 하나만이라도** 주시면 경고를 원래대로 좁힐 수 있습니다. 나머지는
표를 되살리는 값이라 급하지 않습니다.

> `projectId`가 있으면 회차 이름을 눌러 프로젝트 화면으로 갈 수 있습니다. 지금은
> 이름만 있어 링크를 못 겁니다.

## 4. 🟠 R4 — 매니저의 소속 기수가 항상 비어 있습니다

### 관측

```
GET /api/v0/managers?cohortId=f7011ddf…

송다온   cohortId=null  cohortName=null  classroomNames=[A반]
이담     cohortId=null  cohortName=null  classroomNames=[C반]
장윤슬   cohortId=null  cohortName=null  classroomNames=[H반]
```

**`cohortId`로 걸러서 7명이 나왔는데 그 7명 전원의 `cohortId`가 `null`입니다.**
담당 반은 정상으로 옵니다.

스펙 설명은 *"가장 최근 매니저 초대의 `target_cohort_id` 기준"* 이라고 적고 있습니다 —
시드 계정은 초대 이력 없이 만들어져서 그 값이 비는 것으로 보입니다.

### 화면에서

매니저 탭의 `기수` 열이 **모든 행에서 `—`** 입니다.

그리고 이 값 때문에 **반 담당 배정 모달의 후보를 기수로 좁히지 못했습니다.** 좁히면
`cohortId`가 null인 사람이 전부 빠져 **새로 배정할 사람이 사라집니다**(9기로 좁히면
이미 담당인 7명뿐이었습니다). 지금은 기관 매니저 전원을 후보로 두고, 옆에 쓰는
담당 반만 반 목록에서 다시 세어 이 기수 것으로 맞췄습니다.

### 요청

**둘 중 하나면 됩니다.**

| | 방식 |
|---|---|
| **ⓐ** | 초대 이력이 없어도 **담당 반에서 기수를 채운다** — 반이 기수에 붙어 있으므로 파생 가능합니다 |
| **ⓑ** | 시드 데이터에 초대 이력을 넣는다 — 실제 운영에서는 항상 초대를 거치므로 이 값이 빌 일이 없다면 그쪽이 맞습니다 |

**어느 쪽인지만 알려 주시면** 화면을 맞추겠습니다. ⓑ라면 `기수` 열을 그대로 두고,
운영 데이터에서는 채워질 값으로 보겠습니다.

## 5. 🟡 R5 — `usedRoundLabels`에 같은 회차가 반복됩니다

### 관측

```jsonc
// GET /curricula/{materialId}/sections → items[].usedRoundLabels
["미프 4차","미프 5차","미프 6차","미프 4차","미프 5차","미프 6차",
 "미프 5차","미프 6차","미프 4차","미프 5차","미프 6차"]

11건 → 유일 3건
```

두 항목 모두 같았습니다(`인증 흐름과 토큰 검증`도 11건 → 3건).

**한 회차에 반이 여럿이라 배정마다 한 줄씩 오는 것**으로 짐작합니다 — 9기가 8반이고
반복 횟수가 3~4회씩이라 그 정도로 보입니다.

### 화면에서

*"✓ 검증 개념으로 사용 · 미프 4차 · 미프 5차 · 미프 6차 · 미프 4차 · …"* 로 한 줄이
넘칩니다. **지금은 화면에서 접습니다**(`new Set`).

### 요청

**서버가 유일하게 주는 편이 맞다고 봅니다.** 이 값이 답하는 질문은 *"어느 회차에
나갔나"* 이지 *"몇 반에 나갔나"* 가 아니라서, 중복을 화면이 접으면 **그 판단이 화면에
생깁니다** — 만약 반 수를 세는 것이 의도였다면 저희가 그 정보를 지우는 셈입니다.

**의도된 것이면 알려 주세요.** 그때는 회차별 반 수로 표기를 바꾸겠습니다.

## 6. 🟡 R6 — 비활성 사유 코드가 문자열입니다

### 관측

```jsonc
"inactivatedReasonCode": { "type": ["string", "null"] }
```

설명에는 넷이 예로 적혀 있습니다 — `RESIGNED` · `ADMIN_SUSPENDED` · `CONTRACT_ENDED` ·
`SECURITY`. **실제로 오는 것은 다섯이고 그중 둘이 설명에 없습니다.**

```
OTHER · CONTRACT_ENDED · RESIGNED · ADMIN_SUSPENDED · SECURITY_ACTION
                                                      ^^^^^^^^^^^^^^^ 설명은 SECURITY
```

`SECURITY`가 아니라 `SECURITY_ACTION`이고, `OTHER`는 설명에 없습니다.

### 이게 저희를 막는 이유

타입이 `string`이라 **컴파일러가 못 잡습니다.** 라벨 표를 만들어 두고 모르는 코드가
오면 조용히 빈칸이 됩니다 — 실제로 처음 렌더했을 때 `OTHER · 장기 연락 두절로…`처럼
**코드가 그대로 노출**됐습니다.

지금은 아는 코드는 한글로, 모르는 코드는 **그대로 보여줍니다**(빈칸으로 삼키면 사유가
사라지므로). 다만 그러면 화면에 영문 코드가 나갑니다.

### 요청

**enum으로 만들어 주세요.**

```jsonc
"InactivationReasonCode": {
  "type": "string",
  "enum": ["RESIGNED", "ADMIN_SUSPENDED", "CONTRACT_ENDED", "SECURITY_ACTION", "OTHER"]
}
```

그러면 값이 늘 때 **타입 검사가 라벨 누락을 잡습니다.** 지금 라벨은 이렇게 두었으니
어휘가 다르면 알려 주세요 — `퇴사` · `운영자 조치` · `계약 종료` · `보안 조치` · `기타`.

## 7. 🟡 R7 — 목록 조회 셋에 없는 것

셋 다 **지금은 화면이 흡수했습니다.** 재작성이 되는 지점만 적어 둡니다.

| 어디 | 없는 것 | 지금 | 언제 문제가 되나 |
|---|---|---|---|
| `findClassrooms` | `query`·담당 유무 필터 | 전량 받아 화면이 거른다 | 반이 한 화면을 넘으면 |
| `findCohorts` | `sort` | 화면이 정렬한다 | 기수가 100개를 넘으면 |
| `findOrganizationCurricula` | 상태별 개수 | 헤더 내역을 **안 그린다** | 지금도 못 그린다 |

**앞의 둘은 급하지 않습니다.** 한 기수에 6~10반이고 기관당 기수가 반년에 하나꼴이라
전량이 한 페이지에 들어옵니다 — 페이지가 나뉘는 순간 클라이언트 필터·정렬은 **현재
페이지 안에서만** 맞게 되므로, 그때 서버로 옮겨야 합니다.

**셋째만 지금 못 그리는 것입니다.** 다른 목록은 모집단을 따로 줍니다.

```
기수    counts        { PLANNED, RUNNING, CLOSED }
매니저  statusCounts  { INVITED, ACTIVE, INACTIVE }   ← 필터와 무관한 기관 전체
명단    cohortTotal · unassignedCount
교안    (없음)                                        ← totalElements는 필터 적용 후
```

그래서 교안 탭만 헤더에 `12개 · 분석 완료 9 · 실패 1` 같은 내역을 못 씁니다 —
`totalElements`를 쓰면 걸러 보는 동안 헤더가 필터 결과를 반복해 **그게 전체인 줄
읽힙니다.** 매니저와 같은 모양이면 됩니다.

## 8. 🟡 R8 — `Manager`에 `required`가 없습니다

9차 회신 §1에 이렇게 적어 주셨는데,

```jsonc
"Manager": { "required": ["memberId", "name", "email"], … }
```

**실제 스펙에는 `required`가 없습니다.** 저희 검사기가 잡은 유일한 error입니다.

```
❌ [required] 객체 스키마에 required가 없다 — 1건
     · Manager
```

세 필드가 optional로 생성되어 호출부에 `?`가 붙습니다. **응답에는 항상 오고 있어서
화면을 막지는 않습니다** — 9차 때 넘겼던 것을 다시 적습니다.

> `memberId`가 `uuid`로 바뀐 것과 `email`이 추가된 것은 **정상 반영됐습니다.** 그 덕에
> 반 담당 배정이 되읽기→다시 보내기로 돌아갑니다(9차 R5).

## 9. 🟡 확인 셋

### Q1. 담당 배정 시각을 줄 수 있나요

`ClassroomResponse`에 담당이 **언제·누구 손으로** 정해졌는지가 없습니다.

배정이 기간형 이력이라(OP-06 §3) 서버는 구간을 닫고 여는데, 그 구간의 시작을 화면에
내려주는 필드가 없습니다 — 담당이 바뀐 것을 보고도 *"누가 언제 바꿨지"* 를 물을 데가
없습니다. **`담당 시작` 열을 통째로 뺐습니다**(빈 칸으로 두면 값 없는 반처럼 읽혀서).

```jsonc
"managers": [
  { "memberId": "…", "name": "송다온", "email": "…",
    "assignedAt": "2026-06-01T00:00:00Z",   // ← 이 구간이 언제 열렸나
    "assignedByName": "김오퍼레이터" }
]
```

**급하지 않습니다.** 이력 전체를 주는 엔드포인트가 따로 생길 계획이면 그쪽이 맞습니다 —
어느 쪽인지만 알려 주세요.

### Q2. 개강 전 기수를 정리할 방법이 없습니다

```
POST   /cohorts            생성 ✅
PATCH  /cohorts/{id}/end   종료 — **진행 중인 기수를 CLOSED로**(스펙 명시)
DELETE                     없음
PATCH  /cohorts/{id}       없음 — 이름·기간 수정
```

**잘못 만든 기수를 되돌릴 수 없습니다.** `endCohort`는 진행 중 기준이라 개강 전 기수에는
쓸 수 없고(화면도 그래서 `RUNNING`에만 종료 버튼을 답니다), 삭제도 수정도 없습니다.

반은 9차 R6로 수정·삭제가 생겼는데 기수에는 없어서, **기수명 오타 하나를 못 고칩니다.**

- 개강 전 기수(`PLANNED`)에 한해 `PATCH`·`DELETE`를 두실 수 있나요?
- 아니면 `endCohort`를 `PLANNED`에도 허용하는 쪽인가요? (그때는 화면 문구를
  `종료`가 아니라 `취소`로 바꾸겠습니다)

> 반 삭제처럼 **서버가 판정**해 주시면 됩니다 — 명단이 들어갔거나 회차가 만들어진
> 기수는 막고, 빈 기수만 지우는 식으로요.

### Q3. 받아 놓고 안 쓰는 필드 둘 — 화면에서 뺐습니다

스펙이 스스로 그렇게 적고 있어 **입력 칸을 지웠습니다.**

| 필드 | 스펙 원문 |
|---|---|
| `CreateCohortRequest.initialTrainees` | *"⚠ 요청에 넣어도 저장되지 않는다"* |
| `CreateClassroomRequest.managerIds` | *"⚠ 지금은 서버가 사용하지 않는다"* |

**보내도 아무 일이 안 일어나는 칸을 두면 화면이 거짓말을 합니다** — 담당을 골라 반을
만들었는데 목록에는 `담당 없음`으로 뜹니다. 그래서 기수 생성 모달에서 초기 명단 칸을,
반 추가 모달에서 담당 매니저 칸을 뺐습니다.

**나중에 채우실 계획이면 알려 주세요.** 그때 칸을 되살립니다. 계획이 없다면
**스펙에서 필드 자체를 빼시는 편**이 맞다고 봅니다 — 생성 타입에 남아 있으면 다음
사람이 다시 채워 넣습니다.

## 10. 9차 반영본 검증 결과 — **OP-06 여섯 탭 전부 붙었습니다**

브라우저에서 실제로 눌러 확인했습니다.

| 탭 | |
|---|---|
| ① 기수 | ✅ 목록·검색·상태 필터 · 생성 모달 · 종료(사유 필수) |
| ② 반 | ✅ 목록 · **수정·삭제**(9차 R6) · **담당 배정 다중 선택**(9차 R5) |
| ③ 명단 | ✅ 223명 · 23쪽 · 반/계정 필터 · 배정 모드 · **드라이런**(9차 Q3-③) |
| ④ 매니저 | ✅ 목록 · 초대 · **정지·재발송·취소**(9차 R7) · **담당 반 일괄 교체**(9차 Q3-①) |
| ⑤ 교안 | ⚠️ 목록 정상 · **상세가 R1에 막힘** |
| ⑥ 비용 | ✅ 요약·월별·반별 매트릭스 — 필드가 목 계약과 그대로 일치했습니다 |

### 9차에서 청한 것들이 실제로 도는지

| | 결과 |
|---|---|
| **R5** `Manager.memberId` UUID | ✅ 반 담당을 **되읽어 그대로 다시 보냅니다** — 이게 안 되던 것이 9차의 최우선이었습니다 |
| **R6** 반 수정·삭제·`capacity` | ✅ `PATCH`가 부분 수정이라 이름만 고쳐도 정원이 안 덮입니다 |
| **R7** 매니저 조작 3종 | ✅ `suspendable`로 정지 버튼이 잠기고, `pendingInvitationTokenId`로 재발송·취소가 켜집니다 |
| **R8** 교안 목록·상세 | ✅ 단건 상세가 목록과 같은 스키마라 주소로 바로 들어와도 머리글이 채워집니다 |
| **Q3-①** 담당 반 일괄 교체 | ✅ 한 트랜잭션이라 절반만 반영되는 상태가 없습니다 |
| **Q3-②** `LOCKED` 제거 | ✅ 도달 못 하던 분기를 지웠습니다 |
| **Q3-③** 드라이런 | ✅ 등록과 같은 스키마라 미리보기와 결과를 한 컴포넌트로 그립니다 |
| **Q3-④** `emailDomain` | ✅ 매니저 초대에서 `example.com 주소만 초대할 수 있습니다`로 막힙니다 |

### 화면이 세던 것을 서버 값으로 바꿨습니다

`suspendable`·`pendingInvitationTokenId`·`managerAssignmentRequired`·`capacity`를 주신
덕분에, 목일 때 화면이 세거나 유추하던 판정이 없어졌습니다.

특히 **`needsManager`를 지웠습니다** — 목에서는 `managerId === null`로 셌는데, 반 하나에
매니저가 **여럿**일 수 있어 그 등가가 성립하지 않았습니다. 서버 판정을 그대로 씁니다.

## 11. 참고 — 요청하지 않는 것

| | 어떻게 흡수하나 |
|---|---|
| 탭 이름 옆 개수 전용 API | **안 만듭니다.** 각 목록 응답의 `totalElements`·`cohortTotal`·`statusCounts`로 됩니다 — 전용 API를 두면 화면 진입에 조회 다섯 건이 나갑니다 |
| `findCohort.traineeCount`가 0 | **10차 R3에 있습니다.** 기수 탭의 `교육생` 열을 뺐습니다 — `0`을 그리면 "이 기수엔 아무도 없다"는 거짓말이 됩니다. 그 값이 채워지면 열을 되살립니다 |
| 기수 목록에 반 개수 없음 | 10차 R3 각주에 있습니다. 지금은 `반` 열도 빼 두었습니다 |
| 프록시 병렬 502 | **10차 R2에 있습니다.** OP-06에서도 같은 증상을 봤습니다 — 교안 상세가 조회 3건을 동시에 보내는데 그중 하나가 CORS 오류로 죽고, `다시 시도`를 누르면 붙습니다 |
| 분석 실패 사유 | 교안 상세에 `failureReason`이 없어 **흔한 원인을 대신 적었습니다**(암호 걸린 PDF·이미지 PDF). 실제 사유를 주시면 그대로 씁니다 — 급하지 않습니다 |
| `POST /curricula`가 분석을 안 건다 | 스펙 명시대로 **등록 뒤 분석을 이어서 부릅니다.** 사용자에게 두 호출로 보이지 않게 합니다 — 등록만 하고 `분석 전`으로 남는 건 아무도 원하지 않는 상태입니다 |
| 교안 버전 입력 | 서버가 매기므로 **입력 칸을 뺐습니다.** 새 버전은 같은 자리에 다시 올리는 것이지 사람이 번호를 적는 것이 아닙니다 |
