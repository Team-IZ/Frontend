# AU-03 · 비밀번호 재설정

> **v1 그대로.** 바뀐 것 없음.

## 1. 한 줄

메일 링크에서 **새 비밀번호를 정한다.** 요청 → 설정 두 단계.

## 2. 진입 · 이탈

AU-01의 `비밀번호를 잊으셨나요?` → 요청 → (메일) → 링크 → 설정 → AU-01.

## 3. 뷰

```
① 요청                        ② 설정 (링크 진입)
이메일 [           ]          새 비밀번호     [        ]  정책 힌트
     [재설정 메일 보내기]      새 비밀번호 확인 [        ]
                                          [비밀번호 변경]
메일을 보냈습니다.
받은 편지함을 확인해 주세요.
```

**요청 결과는 계정 유무와 무관하게 같은 문구다.** 다르게 답하면 어떤 이메일이 가입돼
있는지 알려주는 셈이 된다.

## 4. 데이터

이메일(요청) · 토큰 + 새 비밀번호(설정). 성공 시 **기존 세션 전부 만료.**

## 5. 액션

메일 발송 · 비밀번호 변경 · 재발송.

## 6. 상태 — 왜 그렇게 정했나

> **케이스 표는 목업에 있다** — [`shared/password-reset.html#cases`](../wireframe/shared/password-reset.html#cases).
> 정의서에 두면 안 읽힌다. 표는 목업 한 곳에만 두고, 이 절은 표로 설명이 안 되는 판단만 적는다.

### ① 요청에서는 계정 상태를 화면에 절대 드러내지 않는다

v2 초안에 **`미활성 계정` 화면**이 있었다 — *"아직 계정을 열지 않으셨어요. 초대 메일의 링크로 먼저 활성화해 주세요."* **뺐다.**

| | |
|---|---|
| **왜 구멍인가** | 이 화면이 뜨는 조건 자체가 정보다. 이메일을 하나씩 넣어 보면 **그 주소가 명단에 있고 아직 활성화 전이라는 것**을 알아낼 수 있다 |
| **자기모순이었다** | 바로 옆 `#sent`가 *"보안을 위해 계정이 있는지는 알려드리지 않습니다"*라고 말한다. 두 화면이 정면으로 어긋났다 |
| **대신** | **화면은 `#sent`로 같게 두고 메일만 바꿔 보낸다** — 미활성이면 재설정 메일 대신 **활성화 메일**. 사용자는 받은 편지함에서 맞는 것을 받고, 화면은 아무것도 흘리지 않는다 |

**정상 · 없는 이메일 · 미활성 셋이 같은 화면·같은 202다.** 하나라도 다르면 그 차이가 곧 계정 열거 수단이다.

### 만료·사용됨은 한 화면, 위변조는 따로

| | 화면 | 왜 |
|---|---|---|
| **만료 · 이미 사용됨** | `#expired` · [다시 요청하기] | 할 일이 `재요청`으로 같다 |
| **위변조 · 목적 불일치** | `#invalid` · [문의하기] | **보안 로그를 남긴다.** 재요청해도 같은 일이 반복될 것이라 문의로 보낸다 |

### 세션 폐기가 실패하면 완료 화면을 그대로 쓸 수 없다

정상 완료 문구가 **"다른 기기에서는 모두 로그아웃되었어요"**다. 폐기가 실패하면 **그 문장이 거짓**이 된다 — 공용 PC에서 바꾼 사람에게 안전하다고 말하는 셈이다.

→ `#donepartial`: 변경은 됐다고 말하되 **다른 기기가 남아 있을 수 있다**고 알리고, 직접 로그아웃을 권한다. 서버는 폐기를 계속 재시도한다.

### 토큰 없이 ② 설정에 들어오면 막다른 화면을 만들지 않는다

v1은 `잘못된 접근입니다` 400을 띄웠다. v2는 **① 요청으로 보낸다** — 사용자가 할 일이 그것뿐인데 에러를 먼저 읽힐 이유가 없다.

## 7. 안 하는 것

| | |
|---|---|
| 계정 존재 여부 노출 | 위 §6 — 화면·응답·소요시간 전부 같아야 한다 |
| 미활성 계정 전용 화면 | **두지 않는다** — 그 자체가 계정 열거 |
| 토큰 TTL·정책값 노출 | 백엔드 정책이다 |
| 이메일 변경 | 프로필 소관 |
