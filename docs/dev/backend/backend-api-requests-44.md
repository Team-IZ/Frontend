# 백엔드 API — 44차 요청 · 교안 버전을 화면에 붙이려니 읽기 쪽이 최신으로 튑니다

> **42차 R1(새 버전 등록)에 이어 읽기 쪽까지 받았습니다.** `GET /curricula/{materialId}/versions`
> (버전 이력)와 `GET /curricula/{materialId}/sections?versionId=`(옛 버전 섹션),
> 그리고 `CURRICULUM_ANALYSIS_FAILED`까지 왔습니다 — 42차 문서에 *"읽기 쪽 구버전 상세·버전
> 목록 API는 이번에도 추가하지 않는다"* 라고 적어 두셨던 것이 채워졌습니다. 감사합니다.
>
> **제목 중복이 `DATA_INTEGRITY_VIOLATION`으로 새던 것도 고쳐진 것 확인했습니다**(§1).
>
> 이제 화면에 버전 축을 붙이려는데, **읽기 조회 셋이 아직 버전을 안 받습니다.**
> 저희가 지키려는 규칙은 하나입니다 — **회차가 연결한 그 버전을 그대로 보여준다.**
> 1기의 1차가 v1을 쓰고 7기의 1차가 v2를 쓰면, 각 화면이 각자의 버전을 그립니다.
>
> 측정 — 2026-08-20 · App Runner · `operator@example.com` · 스펙 `sha256 b95ddf692259`

## 1. ✅ 확인한 것

### 제목 중복이 제 코드로 옵니다

전에는 같은 제목으로 등록하면 `409 DATA_INTEGRITY_VIOLATION`(DB 제약이 그대로 샌 것)이
나와서, 화면이 원인을 알 수 없었습니다. 지금은 정확합니다.

```
POST /curricula  title="AI_딥러닝_교안"(이미 있는 제목)
  → 409 CURRICULUM_TITLE_DUPLICATED "이미 존재하는 교안 제목입니다."
```

저희 등록 다이얼로그가 이 코드를 **제목 입력란 인라인 오류**로 이미 처리하고 있어서,
따로 고칠 것 없이 바로 맞는 자리에 뜹니다.

> ⚠ 저희 문구 하나가 이 변경으로 **거짓이 됐습니다.** 제목 중복 안내에
> *"지운 교안도 제목을 계속 차지합니다"* 라고 적어 두었는데, 삭제 스펙에
> *"제목은 더 이상 점유되지 않는다"* 로 바뀌었더군요. 저희 쪽에서 정정합니다.

### 버전 이력이 살아 있습니다

```
GET /curricula/{materialId}/versions → 200
  [{ versionId, materialId, versionNo: 1, originalFileName, pageCount,
     analysisStatus, teachesCount, createdAt }]
```

## 2. 🔴 R1 — `GET /curricula/{materialId}`에 `versionId`가 없습니다

**섹션만 버전이 고정되고 머리글은 최신으로 튑니다.**

교안 상세 화면은 조회 둘로 만들어집니다.

```
GET /curricula/{materialId}                    제목 · 버전번호 · 쪽수 · 분석상태   ← versionId 못 받음
GET /curricula/{materialId}/sections?versionId= 섹션 트리                        ← 받습니다
```

이번에 `sections`에 `versionId`를 붙여 주셔서 **본문은** 옛 버전을 그릴 수 있게 됐는데,
**머리글은 여전히 최신 버전을 말합니다.** 한 화면 안에서 두 버전이 섞입니다.

```
1기 매니저가 v1을 눌러 들어감
  머리글   Spring 백엔드 설계 v2 · 42쪽 · 분석 완료   ← 최신(v2)
  섹션     v1의 섹션 7개                              ← 고정됨(정상)
```

지금은 교안마다 버전이 하나뿐이라 안 드러나지만, 저희가 **새 버전 올리기 화면을 켜는
순간** 실제로 어긋납니다. 그래서 그 화면을 이것 없이는 못 켭니다.

### 요청

`GET /curricula/{materialId}`에 **`versionId` 쿼리(선택)**를 붙여 주세요.
`sections`와 같은 규칙이면 됩니다 — 생략하면 최신, 넘기면 그 버전. 그 교안의 버전이
아니면 `404 CURRICULUM_VERSION_NOT_FOUND`.

> 💡 **`GET .../versions`에서 골라 쓰는 우회를 먼저 검토했는데 안 됩니다.**
> 그 응답(`CurriculumVersionResponse`)에는 상세 화면이 그려야 하는 필드가 없습니다.
>
> ```
> 상세에만 있는 것   title · sectionCount · conceptCount · usedProjectCount
>                    uploadedAt · uploadedByName
> ```
>
> 오퍼레이터 교안 상세의 머리글이 **`title`**(파일명이 아니라 교안 제목)이고,
> 그 아래가 `12섹션 · 개념 48건` · `3개 회차에서 사용 중`입니다 — 버전 배열로는
> 한 줄도 못 그립니다.

## 3. 🔴 R2 — `linked-curricula`가 버전이 갈려도 한 행입니다

매니저 교안 화면(MG-09)이 쓰는 조회입니다. 스펙에 이렇게 적혀 있습니다.

> **한 교안이 여러 회차에 걸리면 한 번만 나오고** `linkedProjects[]`에 그 회차가 모두 담긴다.

그런데 응답의 `versionId`·`versionNo`는 **단수**입니다. 한 기수 안에서 회차마다 다른
버전을 연결하면 그 값이 무엇이 되는지 알 수 없습니다.

```
9기 1차 → Spring 백엔드 설계 v1 연결
9기 3차 → Spring 백엔드 설계 v2 연결   (개정판을 올린 뒤)

GET /cohorts/{9기}/linked-curricula
  → 행 하나 · versionNo = ?          ← v1인지 v2인지 계약에 없음
    linkedProjects = [1차, 3차]      ← 두 버전의 회차가 섞임
```

매니저가 이 행을 눌러 상세로 들어갈 때 **어느 버전을 열어야 하는지 정할 근거가
없습니다.** 1차를 보러 왔는데 v2가 열릴 수 있습니다.

### 요청 — 둘 중 하나면 됩니다

1. **버전 단위로 행을 나눠 주세요.** 같은 교안이라도 v1 행 / v2 행으로 각각.
   `linkedProjects[]`는 그 버전을 쓰는 회차만 담습니다. (저희가 선호합니다 —
   화면이 그대로 한 줄에 한 버전을 그립니다)
2. 행은 그대로 두되 **`linkedProjects[]`의 각 항목에 `curriculumVersionId`를 실어
   주세요.** 회차를 눌렀을 때 그 회차의 버전으로 들어갈 수 있으면 됩니다.

## 4. 🟡 R3 — `/projects`가 버전을 못 좁힙니다

`GET /curricula/{materialId}/projects`는 스펙에 **"이 교안의 모든 버전을 쓰는"**
회차를 준다고 적혀 있습니다(`usedProjectCount`와 같은 기준).

교안 상세에 **연결된 프로젝트** 탭이 있는데, 옛 버전 상세를 열었을 때 그 탭이
*"이 버전을 쓰는 회차"* 가 아니라 **모든 버전의 회차**를 보여주게 됩니다.
v1 화면에서 v2만 쓰는 회차가 섞여 나옵니다.

### 요청

`GET /curricula/{materialId}/projects`에 **`versionId` 쿼리(선택)**를 붙여 주세요.
생략하면 지금과 같이 전체(`usedProjectCount`와 일치), 넘기면 그 버전을 쓰는 회차만.

> ⚠ **삭제 판정은 지금 기준이 맞습니다.** 삭제는 교안 원장 단위라
> `CURRICULUM_MATERIAL_IN_USE`가 전 버전 합으로 도는 것이 정확합니다 —
> 이 요청은 **표시용**이고 삭제 판정을 바꿔 달라는 뜻이 아닙니다.

## 5. 🔴 R4 — `POST /versions`에 분석 언급이 없습니다

`POST /curricula/{materialId}/versions`의 설명 전체에 **분석이 한 번도 안 나옵니다.**
등록과 동시에 분석이 시작되는지, 저희가 `POST /analyses`를 이어 붙여야 하는지
계약으로 알 수 없습니다.

**새 버전은 내용이 비슷해도 다른 파일입니다.** 쪽 번호도 섹션 구성도 바뀔 수 있어서
분석이 반드시 다시 돌아야 하고, 안 돌면 그 버전은 검증 개념을 못 뽑아
회차에 붙일 수 없는 상태로 남습니다.

참고로 `POST /curricula`(새 교안)는 **등록과 동시에 분석이 시작됩니다**(실측 —
201 직후 `analysisStatus: PENDING`). 저희 등록 화면은 그 동작을 전제로,
이어 붙인 `POST /analyses`가 `409 CURRICULUM_ANALYSIS_IN_PROGRESS`로 거절되면
무시하도록 짜여 있습니다.

### 요청

`POST /versions`도 **등록과 동시에 분석을 시작**해 주시고, 그 사실을 스펙에
적어 주세요. 이미 그렇게 돌고 있다면 **문서만 채워 주시면 됩니다** —
저희가 이어 붙일지 말지를 그 문장으로 정합니다.

---

## 6. 🟡 R5 — 제목만 고치는 길이 없습니다

교안 제목을 바꾸는 방법이 **`POST /versions`에 `title`을 실어 보내는 것뿐**입니다
(`PATCH`·`PUT`이 없습니다).

그래서 *"파일은 그대로인데 제목에 오타가 있다"* 는 사람이 제목을 고치려면
**같은 파일을 한 번 더 올려 쓸모없는 버전을 하나 만들어야** 합니다. 그 버전은
분석까지 한 번 더 돌게 됩니다.

### 요청

제목만 고치는 경로를 하나 주세요 — `PATCH /curricula/{materialId}` 정도면 됩니다.
검사는 `POST /versions`의 `title`과 같으면 됩니다(기관 + 새 제목이 **다른** 교안과
겹치는지).

**급하지 않습니다.** 그때까지는 새 버전 다이얼로그에 제목란을 두고
*"비우면 기존 제목을 그대로 씁니다"* 로 안내하겠습니다.

## 7. 저희가 이번에 하는 것

요청과 무관하게 저희 쪽에서 도는 것들입니다 — 참고용입니다.

```
· CURRICULUM_ANALYSIS_FAILED 문구 신설    영구 실패를 「기다리면 됩니다」로 안내하던 것
· 제목 점유 문구 정정                     삭제하면 제목이 풀리는 것으로 바뀐 것 반영
· 회차 → 교안 상세 링크 신설              회차가 쓰는 버전으로 들어갑니다
· 교안 상세 URL에 버전을 담기             1기의 v1과 7기의 v2가 같은 주소였습니다
```

**새 버전 올리기 화면과 버전 이력 화면은 R1·R4가 온 뒤에 켭니다** — 지금 켜면
§2에서 적은 대로 머리글과 본문이 서로 다른 버전을 말하게 됩니다.
