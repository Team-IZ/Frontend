## 1. 🔴 R1 — 답변 채점이 응답하지 않습니다

### 무엇이 일어났나

`s016@algohouse.io`로 세션을 시작해 답변을 냈습니다. **세 번 시도했고 세 번 다
연결이 끊겼습니다.**

```
05:31:30  → POST /api/v0/assessment-sessions/{id}/answers
05:33:00  ✗ net::ERR_ABORTED          ← 90초

05:35:05  → POST /api/v0/assessment-sessions/{id}/answers
05:36:35  ✗ net::ERR_ABORTED          ← 90초
```

**두 번 다 정확히 90초입니다.** 브라우저(Chrome)와 서버 밖 스크립트(Node) 양쪽에서
같았고, 스크립트에서 120초까지 기다려도 응답이 오지 않았습니다.

### 저장도 되지 않습니다

끊긴 뒤 `GET /problems/{no}`를 다시 읽으면 이렇습니다.

```
turns: 0          ← 답변이 한 건도 없습니다
current.sequenceNo: 1     ← 질문이 그대로입니다
current.hintsUsed: 0
```

### 채점만 그렇습니다 — 쓰기 경로 자체는 정상입니다

**같은 세션·같은 시각에** 힌트를 열어 봤습니다.

| 호출 | 결과 |
|---|---|
| `POST /hints` | ✅ **200 · 1.2초** · `hintsUsed 1` · `hintsLeft 1`로 정확히 반영 |
| `POST /answers` | 🔴 **90초 뒤 끊김** · 아무것도 저장 안 됨 |
| `POST /start` | ✅ 200 · 즉시 |
| `GET /current` · `GET /problems/{no}` | ✅ 200 · 1~2초 |

**힌트는 AI를 부르지 않는 즉답**이라고 스펙에 적혀 있습니다. 그것만 되고 답변만 안 되는
것으로 보아 **AI 채점 구간**으로 좁혀집니다.

> 90초라는 값이 일정한 것도 단서로 보입니다 — 채점이 느린 것이라면 시간이 들쭉날쭉할
> 텐데, 두 번 다 90초에 정확히 끊겼습니다. 게이트웨이·람다 쪽 상한이 아닌지 봐 주세요.

### 그래서 세션 하나가 통째로 날아갔습니다

시작부터 종료까지 정상적으로 흘렀는데 **남은 데이터가 0건**입니다.

```
05:02  세션 시작 (문제 2개)
05:22  문제 1 — 20분 상한 만료 → 서버가 닫고 커서를 2번으로
05:42  문제 2 — 20분 상한 만료 → 세션 자동 완료
       GET /current → 204 · 홈 → ASSESSMENT_COMPLETED / WAIT_FOR_REPORT
```

**답을 세 번 냈는데 한 번도 접수되지 않은 채 시간만 지나 끝났습니다.** 실제 학생에게
이 일이 일어나면 미응시와 구분되지 않습니다.

### 저희 쪽에서 한 것

**실패를 삼키지 않게 했습니다.** 종전에는 요청이 끊기면 화면이 조용히 원래대로 돌아가
학생이 접수된 줄 알고 기다렸습니다. 지금은 이렇게 말합니다.

```
답변을 보내지 못했어요. 쓰신 내용은 그대로 있으니 다시 제출해 주세요.
```

다만 **다시 눌러도 같게 실패합니다.** 저희가 우회할 수 있는 부분이 아닙니다.

## 1b. 🔴 ZIP 제출은 아직 막혀 있고, GitHub 제출은 열렸습니다

### ZIP — 원인은 찾아 주셨는데 아직 그대로입니다

오늘(8/18) 실제 저장소 압축본으로 다시 태웠습니다.

```
파일: Backend-develop.zip · 1,109개 파일 · 1.94MB
POST /api/v0/submissions/zip  →  500 ARTIFACT_STORE_FAILED  (53.6초)
```

말씀하신 **Dockerfile 권한 분석**(`/app`이 root 소유라 `app` 유저가 `var/submissions`를
못 만든다)이 맞다면 **아직 배포가 안 된 것으로 보입니다.** 재배포되면 바로 다시
확인하겠습니다. 함께 말씀하신 **S3 이전도 저희 쪽 영향은 없습니다** — 화면은
`POST /submissions/zip` 하나만 부르고 저장 위치를 모릅니다.

### GitHub 제출은 오늘 붙였고 **끝까지 통과합니다**

`GITHUB_URL`이 허용된 계정으로 실제로 냈더니 접수됐습니다.

```
POST /api/v0/submissions        →  201
홈                              →  ANALYZING / WAIT_FOR_ANALYSIS
GET  /projects/{id}/my-submission →  method: GITHUB_URL · submissionId 발급됨
```

**파일을 저장하지 않으니 위 권한 문제를 안 탑니다.** 즉 지금 학생이 코드를 낼 수 있는
길은 이쪽뿐입니다 — ZIP이 고쳐질 때까지 안내를 이쪽으로 몰아도 되는지 알려 주세요.

`POST /submissions/repository-checks`도 함께 붙였습니다. 서버가 준 문구를 그대로
보여줍니다(`저장소 주소 형식이 올바르지 않습니다` / `Team-IZ/Backend 확인했어요`).

> ℹ️ **저희 실수 하나를 적어 둡니다.** `POST /submissions`도 `Idempotency-Key`가
> 필수인데 저희가 안 보내 400이 났습니다. 고쳤습니다. 그리고 그 키는 **UUID여야
> 합니다**(`IDEMPOTENCY_KEY_INVALID`) — 스펙 파라미터 설명에는 있는데, 혹시 다른
> 팀에서도 걸릴 수 있어 남깁니다.

## 2. 🔴 R2 — 다시 보기에도 힌트를 주세요

### 회신에서 주신 선택지

> ⓐ 그 축을 바로 `NOT_PASSED`로 닫고 다음으로 넘길지, ⓑ 힌트 없이 재답변을 허용할지

**저희 쪽 결론은 「1차와 똑같이 간다」입니다.** 교착의 원인이 "미달을 어떻게 처리하나"가
아니라 **다시 보기에서 힌트를 막아 둔 것** 자체이기 때문입니다.

```
힌트를 막았다  →  *_hint_presented_at 이 안 찍힌다
               →  hintsUsed() 가 항상 0
               →  nextSlot() 이 영원히 QUESTION
               →  미달하면 그 축에 갇힌다
```

**힌트를 주면 이 사슬이 첫 칸에서 끊깁니다.** `SessionTurnStore`에 분기를 넣지 않아도
되고, 1차에서 이미 도는 경로를 그대로 씁니다.

### 화면에서도 이쪽이 맞습니다

지금 화면은 `outcome` 5종으로만 갈립니다. ⓐ·ⓑ 어느 쪽이든 **다시 보기에만 있는 규칙**이
생겨 화면이 `mode`로 갈라져야 합니다.

| | 1차 | 다시 보기 |
|---|---|---|
| ⓐ를 고르면 | 미달 → 힌트 → 재답변 | 미달 → **즉시 닫힘** |
| ⓑ를 고르면 | 미달 → 힌트 → 재답변 | 미달 → **힌트 없이** 재답변 |
| **R2면** | 미달 → 힌트 → 재답변 | **같음** |

### 학생 입장에서도요

다시 보기는 **1차에서 2단에 못 닿은 사람**이 합니다. 그 사람에게 힌트를 빼고 같은
질문을 다시 물으면 1차보다 어려운 조건에서 같은 벽을 다시 만나게 됩니다.

> ⚠️ **저희도 하나 짚어 둡니다.** 다시 보기의 문제·질문·힌트는 1차의 복사본이라,
> 1차에서 이미 힌트를 본 학생은 **같은 문장을 다시 봅니다.** 새 힌트가 생기지 않습니다.
> 그래도 "답을 못 하면 그대로 끝"보다 낫다고 판단했습니다.

### 무엇을 바꾸시면 되나

| 어디 | 지금 | 요청 |
|---|---|---|
| `openHint` | `HINT_NOT_AVAILABLE`로 거절 | 1차와 동일하게 지급 |
| 자동 지급 | `isReview()`로 무시 | 1차와 동일하게 지급 |
| `SessionResponse.mode` | *"REVIEW는 힌트가 없고 판정에 반영되지 않는다"* | **힌트 문구만** 빼 주세요 |
| `CurrentQuestion.hintsLeft` | *"다시 보기는 항상 0이다"* | 1차와 같은 값 |

**`판정에 반영되지 않는다`는 그대로 둡니다** — 힌트와 별개 규칙이고, 저희도 그 전제로
`기록에만 남아요` 배지를 그리고 있습니다.

## 3. 🟡 R3 — 문제 상한 시각을 주세요

**문제당 20분인데 그 문제가 언제 시작됐는지를 알 수 없습니다.**

| 응답 | 시각 필드 |
|---|---|
| `SessionResponse` | `startedAt` · `timeLimitAt` ✅ |
| `ProblemResponse` | **없음** |
| `CurrentQuestion` | **없음** (`sequenceNo`·`questionText`·`shownHints`·`hintsUsed`·`hintsLeft`·`highlight`·`lastTurnOfSession`) |

세션 시작 시각에서 재 봤더니 **두 번째 문제부터 전부 틀립니다** — 방금 시작한 문제에
`1:03 남음`이 떴습니다(실측). 그래서 **문제별 카운트다운을 아예 뺐습니다.** 틀린
카운트다운은 없는 것만 못합니다.

```
지금 화면:  25:31 남음      ← 세션 마감(timeLimitAt)에서 잰 값. 정확합니다
없앤 것:    이 문제 1:03 남음  ← 계산할 근거가 없어 지웠습니다
```

**`ProblemResponse`에 `problemTimeLimitAt`(또는 `problemStartedAt`) 하나만 주시면**
바로 되살립니다. 학생이 실제로 관리해야 하는 시간이 이쪽이라 필요합니다.

## 4. 🟡 R4 — 코드 스니펫과 줄 번호가 안 맞습니다

`GET /problems/1`에서 실제로 받은 값입니다(`s016@algohouse.io`).

```json
"code": { "lineStart": 20, "lineEnd": 32, "references": [] }
"current": { "highlight": { "lineStart": 21, "lineEnd": 24 } }
```

그런데 **`snippet`은 4줄입니다.**

```
20| public Optional<Result> handle(Request req) {
21|     // Optional을 활용한 값 존재 여부 처리
22|     return repository.find(req.id());
23| }
```

| | 말하는 것 | 실제 |
|---|---|---|
| `code.lineEnd` | 32번째 줄까지 | **23번째 줄까지** (13줄 차이) |
| `highlight.lineEnd` | 24번째 줄 강조 | **그 줄이 없습니다** |

화면은 `lineStart`부터 번호를 붙이므로 없는 줄은 자연히 안 그려집니다 — **깨지지는
않습니다.** 다만 강조가 파일 끝에서 잘리고, `lineEnd`를 믿는 계산은 전부 틀립니다.

**시드 데이터 문제로 보입니다.** 실제 제출 코드로 만든 회차라면 맞을 수도 있는데,
저희는 그런 데이터를 본 적이 없어 확인하지 못했습니다.

> **`references`가 빈 배열이라 호출부 패널을 한 번도 못 봤습니다.** 화면은 비어 있으면
> 버튼 자체를 안 그리게 해 뒀습니다(눌러도 빈 칸이 열리면 고장으로 읽혀서). 값이
> 채워지는 케이스가 있으면 그 계정을 알려 주세요.

## 5. 🟡 R5 — 이어하기: **`IN_PROGRESS`는 저희가 열었습니다. `PAUSED`만 남았습니다**

이어하기가 두 갈래였는데 회신에서 하나로 뭉쳐 있어, 나눠서 적습니다.

| | 서버 | 화면 | 지금 |
|---|---|---|---|
| **`IN_PROGRESS`** (정상 진행 중 이탈) | ✅ 잘 돌려줍니다 | ❌ 저희가 막고 있었습니다 | **✅ 오늘 열었습니다** |
| **`PAUSED`** | ❌ 되돌릴 코드가 없습니다 | — | 🟡 서버가 열리면 됩니다 |

### `IN_PROGRESS` — 저희 쪽 문제였습니다

**서버는 처음부터 제대로 주고 있었습니다.**

```
홈    ASSESSMENT_IN_PROGRESS / RESUME_ASSESSMENT
세션  200 · IN_PROGRESS · currentProblemNo 1 · startedAt · timeLimitAt
문제  turns[] · shownHints[] 까지 그대로 복원
```

그런데 저희가 **홈 버튼에 일부러 경로를 안 줬습니다**(*"한 번에 끝낸다"* 약속을 지키려고).
그래서 학생이 창을 닫았다 돌아오면 **들어갈 길이 없었습니다.** 회신에서 인용해 주신
저희 주석이 그 자리입니다.

**판단을 바꿨습니다.** 실제로 일어나는 일은 학생이 약속을 어기는 것이 아니라 **사고로
끊기는 것**이고, 그때 막아 봐야 시계는 서버에서 계속 돕니다. 못 들어오게 하면 남은
시간을 그대로 잃고 미응시로 기록될 뿐이라, **막는 쪽이 오히려 약속을 깨뜨립니다.**

실계정으로 확인했습니다 — 홈의 `이어서 하기`를 누르면 1/2번 문제·남은 힌트·지난 문답이
그대로 복원됩니다.

### `PAUSED` — 여기는 서버가 열어 주셔야 합니다

말씀하신 대로 `PAUSED`를 `IN_PROGRESS`로 되돌리는 코드가 없고, 앱이 만들지 않는
상태라는 것도 확인했습니다. **저희가 화면에서 할 수 있는 일이 없습니다** — 지금은
`POST /answers`가 `409 SESSION_NOT_STARTED`로 막습니다.

`STAGE_NOT_FOUND` 오분류도 함께 봐 주시면 좋겠습니다.

## 6. 🟡 R6 — 응시 가능 계정에 여분이 없습니다

```
분석 완료 시트   9행 중 ACTIVE 8개  ← 전부 씁니다. 여분 0
미응시           ACTIVE 127개       ← 넉넉합니다
분석 실패        ACTIVE 15개        ← 넉넉합니다
```

**세션을 한 번 테스트할 때마다 하나씩 사라집니다.** 오늘 둘을 썼습니다.

| 계정 | 무엇을 확인했나 | 지금 상태 |

## 8. 저희가 한 것 ✅

**목을 지우고 실호출로 바꿨습니다.** 지운 파일이 넷입니다(`api.ts` · `script.ts` ·
`sessionReducer.ts` · `parseRefLines.ts`).

| 무엇 | 어떻게 |
|---|---|
| 시작 | `POST /start` — 응답의 `currentProblemNo`로 커서를 세웁니다 |
| 문제 | `GET /problems/{no}` — 코드·지난 문답·지금 질문이 이 하나로 옵니다 |
| 답변 | `POST /answers` — `outcome` 5종이 화면 넷을 정합니다 |
| 힌트 | `POST /hints` — `HINT_EXHAUSTED`는 오류로 안 올리고 버튼을 문구로 바꿉니다 |

**화면이 상태를 조립하지 않습니다.** 답변 응답에 `next`·`hint`가 실려 오지만 쓰지 않고,
무효화된 `GET /problems/{no}`를 다시 읽습니다 — 같은 것을 두 경로로 만들면 갈립니다.
응답에서 쓰는 것은 `outcome`과 `nextProblemNo`뿐입니다.

그 과정에서 **점수·통과 여부·도달 단계가 화면에서 통째로 사라졌습니다.** 목이 계산하던
것인데 서버가 주지 않으므로(정의서 §7) 계산 자리 자체를 없앴습니다.

### 커서가 옮겨간 것을 화면이 따라가게 했습니다

문제 상한이 지나면 서버가 그 문제를 닫고 커서를 옮기는데, 화면이 들고 있던 번호로
조회하면 이렇게 옵니다.

```
GET /problems/1  →  409  PROBLEM_ALREADY_CLOSED  "이미 끝난 문제는 다시 열 수 없습니다"
GET /current     →  200  currentProblemNo: 2
```

**이 동작은 스펙대로이고 문제가 아닙니다.** 저희가 낡은 번호를 들고 있었던 것이라,
그 코드를 받으면 `/current`를 다시 읽어 따라가게 고쳤습니다. 적어 두는 이유는 다른
화면에서 같은 것을 겪을 수 있어서입니다.

## 8b. 관찰 신호도 붙였습니다 ✅

`POST /{sessionId}/activity`를 화면에 이었습니다. 이 경로가 비어 있으면 **무효 응시
판정과 매니저 브리프의 "어느 답변이 의심스러운가"가 빈 값으로 남는다**고 스펙에 적혀
있어, 미루지 않고 함께 붙였습니다.

| 신호 | 언제 보내나 |
|---|---|
| `awaySeconds` | 창을 떠났다 **돌아온 시점에 한 번** |
| `disconnectedSeconds` | 재연결 **시점에 한 번** |
| `firstKeystrokeDelayMs` | 질문이 보인 뒤 첫 글자를 칠 때 |

실계정으로 본문까지 확인했습니다 — **값이 맞고 사건마다 한 번씩만 나갑니다.**

```
→ {"firstKeystrokeDelayMs":7846}   ← 질문을 보고 7.8초 뒤 첫 글자
← 204
→ {"awaySeconds":6}                ← 6초 이탈 후 복귀
← 204
```

경계 두 가지도 스펙대로 처리했습니다.

```
빈 본문        → 400 ACTIVITY_SIGNAL_REQUIRED   → 보낼 것이 없으면 아예 안 부릅니다
끝난 세션      → 409 SESSION_ALREADY_ENDED      → 무시합니다(스펙: "끝난 세션의 신호는 버린다")
```

**실패해도 재전송하지 않습니다.** `awaySeconds`는 보낼 때마다 횟수가 1 올라가므로,
실패했다고 다시 보내면 한 번 나간 것이 두 번으로 기록됩니다 — 잃는 편이 낫다고
판단했습니다.

## 9. 보고해 주신 나머지 둘은 **저희 버그였습니다** ✅

### ① `리포트 보기`를 누르면 리포트가 안 보인다 — 화면이 터지고 있었습니다

원인은 **id를 잘못 넘긴 것**입니다.

```
홈 링크        /trainee/report?round=d242f040…   ← reportId
리포트 화면     reportsById[…] 로 찾음            ← 키가 assessmentRoundId
```

둘은 다른 값이라 `undefined`가 나왔고, 그것을 그리다 화면이 통째로 죽었습니다
(`TypeError: Cannot read properties of undefined (reading 'status')`).

**서버는 두 값을 정확히 주고 있었습니다** — `past[].assessmentRoundId`와
`past[].reportId`가 따로 옵니다. 저희가 뒤엣것을 링크에 넣었습니다.

고쳤고, **모르는 회차 id가 와도 안 죽게** 막았습니다(주소창은 사람이 고칠 수 있습니다).

### ② 이해도 확인을 마쳤는데 시작 버튼이 눌린다 — 캐시였습니다

세션이 **시간이 지나 끝나는 경우**는 아무 요청도 아니라서, 저희 캐시가 무효화되지
않았습니다. 그래서 종료 직후 30초 동안 홈이 이전 카드(`이해도 확인을 시작할 차례예요`)를
그대로 그렸습니다.

세션이 끝날 때 홈 조회를 무효화하도록 고쳤습니다.

> 참고로 **완료 상태 자체는 정상**입니다. `s016@algohouse.io`로 확인하니 홈이
> `리포트를 기다리는 중이에요` · 버튼 비활성(`발행되면 알려드릴게요`)로 정확히 나옵니다.
