# AU-02 · 회원가입 · 계정 활성화

> **v1 구조 유지.** 변형 A/B 두 개 그대로, 교육생 이름 읽기전용 그대로.
> **바뀐 것은 하나** — 초대 모달의 `권한(담당/총괄)` 선택이 사라진다(총괄/담당 폐기).

## 1. 한 줄

초대 링크로 들어와 **비밀번호를 정하고 동의**하면 계정이 열린다.

**초대 링크 클릭이 이메일 소유 증명**이다. 별도 인증 메일 단계가 없고 이메일 필드는 초대값 읽기전용.

## 2. 진입 · 이탈

| | |
|---|---|
| 진입 | **초대 메일 링크만.** 직접 URL 접근 불가 |
| 이탈 | 완료 → AU-01 |

**토큰이 변형을 결정한다.** 사용자가 고르지 않는다.

## 3. 뷰 — 변형 2

### 변형 A · 회원가입 (오퍼레이터 · 매니저)

```
회원가입
  이메일    kim@green.com          (읽기전용 · 초대값)
  이름      [                    ]  ← 본인이 입력
  비밀번호  [                    ]  정책 힌트
  비밀번호 확인 [                ]
  ─────────────────────────────
  [필수] 이용약관                   전문 ↗
  [필수] 개인정보 수집·이용          전문 ↗
                          [가입하기]
```

### 변형 B · 계정 활성화 (교육생)

```
계정 활성화
  이메일    lee@student.com        (읽기전용 · 명단값)
  비밀번호  [                    ]  정책 힌트
  비밀번호 확인 [                ]
  ─────────────────────────────
  [필수] 이용약관 · 개인정보 수집·이용 · 코드/문답 AI 분석 · 기관 공유
         AI 분석 미동의 시 이해도 검증 불가
  [선택] 서비스 개선 활용
                        [활성화하기]
```

**교육생에게 이름을 다시 받지 않는 이유:** 명단(OP-06)에 이름+이메일이 이미 등록돼
있다. **활성화 전에도 반 편성·미제출 관리가 돌아야 하므로** 이름이 그때 필요하다.

**동의 항목 수가 다른 이유:** 교육생은 코드·문답·이탈 기록까지 처리 대상이다.
필수 전체 동의 전 제출 불가, 선택은 미동의해도 진행.

## 4. 데이터

| 읽는다 | 토큰(역할·기관·이메일, 교육생은 명단 이름) |
|---|---|
| 쓴다 | 비밀번호 해시 · `status=ACTIVE` · 토큰 사용완료 · 동의 기록(약관 버전·시각·항목) |

## 5. 액션

가입/활성화 · 전문 보기(펼침) · 만료 시 재발송.

## 6. 상태 — 왜 그렇게 정했나

> **케이스 표는 목업에 있다** — [`shared/signup-activation.html#cases`](../wireframe/shared/signup-activation.html#cases).
> 정의서에 두면 안 읽힌다. 표는 목업 한 곳에만 두고, 이 절은 표로 설명이 안 되는 판단만 적는다.

### 「이미 쓰인 토큰」과 「깨진 토큰」을 가른다

v1은 `A2 재사용`과 `A3 위변조`가 각각 다른 문구였고, v2 초안은 둘을 **한 화면에 합쳐** `이미 사용했거나 잘못된 링크예요 + [로그인] [문의하기]`로 두었다. **둘 다 틀렸다.**

| 서버가 아는 것 | 화면 | 왜 |
|---|---|---|
| **쓰인 토큰이다**(DB에 있다) → 계정이 이미 있다 | `#already` · **[로그인]** | 할 일이 로그인 하나로 정해진다 |
| **서명이 깨졌거나 모르는 토큰이다** | `#invalid` · **[문의하기]** | 로그인할 계정 자체가 없다 |

합쳐 두면 **로그인만 하면 되는 사람에게 "문의하세요"를 같이 보여주게 된다.** 버튼 두 개를 주고 고르라는 건 화면이 판단을 미룬 것이다.

### 재수강생 — 그림은 같고 백엔드가 다르다

명단에 `직전 기수` 열이 있으므로([OP-06](OP-06-admin.md)) **이전 기수 계정을 가진 사람이 새 기수 초대를 받는 일이 실제로 있다.**

| | |
|---|---|
| **화면** | `#already`와 같다 — 사용자가 할 일이 `로그인`으로 같다. 이전 기수 계정인지 이번 기수인지는 **사용자에게 아무 차이가 없다** |
| **백엔드** | 다르다 — **새 계정을 만들지 않고 기존 계정을 새 기수 명단에 잇는다.** 계약 표에서 행을 나눈 이유가 이것이다 |

> **판단 필요 — 초대 자체를 보내야 하나.** 이미 활성 계정인 사람에게 활성화 초대를 보내면 그 링크는 무조건 `#already`로 끝난다. **명단 추가 시 기존 계정을 감지해 초대를 건너뛰는 것**이 맞아 보이는데, 이건 OP-06 소관이라 여기서 정하지 않는다.

### 저장 실패는 계정 생성 전에 막는다

동의 기록만 남고 계정은 없는 상태를 만들지 않는다. 그 상태가 되면 다시 시도할 때 **동의를 또 받아야 하는지** 아무도 모른다.

## 7. 안 하는 것

| | 어디에 |
|---|---|
| 자유 회원가입 | **없다** — 초대 기반 |
| 역할 선택 | **없다** — 토큰이 정한다. **초대 모달에도 권한 선택이 없다**(초대하는 화면이 곧 역할) |
| 반·기수 배정 | **OP-06 › 매니저 · 배정 모드** |
| 이메일 변경 | 프로필 소관 |
| 이메일 인증 단계 | **없다** — 초대 링크 클릭이 소유 증명 |

## v1 대조 (SC-A02) — 검수 결과

> v1 **17행**(A 8 + B 8 + 동의 3)을 전량 대조했다. 합친 것은 근거를, 버린 것은 이유를 남긴다.

| v1 | 판정 | |
|---|---|---|
| A1·B2 토큰 만료 / B1 명단 외 / A6·B6 비번 정책 / CS1 필수 미동의 / A7·B7·CS3 저장 실패 | **그대로** | 두 변형이 같은 것은 한 행으로 합쳤다 |
| A2 재사용 · A3 위변조 | **다시 가름** | v2 초안이 한 화면에 합쳐 뒀던 것을 **서버가 아는 것 기준**으로 갈랐다 — 위 §6 |
| A5 이메일 중복 · B4 이미 활성화 | **합침** | 둘 다 `이미 계정이 있다 → 로그인`. 매니저·교육생 구분이 사용자 행동을 바꾸지 않는다 |
| B5 이메일 중복 등록 | **살림 · 행만** | 재수강생. 그림은 `#already`, 백엔드 동작이 달라 표 행은 나눔 |
| B8 잘못된 기관·기수 토큰 | **A3에 흡수** | 사용자에게 `유효하지 않은 링크` 하나. 보안 로그는 둘 다 남긴다 |
| CS2 선택 미동의 | **표 행만** | 정상 진행이라 그림이 필요 없다 |
| A4 이메일 불일치 | **버림** | 이메일이 초대값 읽기전용이라 **불일치가 구조적으로 불가** (v1도 N/A로 닫음) |
| A8 인증 메일 트리거 실패 | **버림** | **단계 자체가 없다** — 초대=인증 (v1도 N/A) |
| **B3 초대 메일 미수신** | **버림 · 자리 옮김** | **이 화면에 도달할 수 없는 케이스다.** 링크를 받아야 여기 오는데 "메일을 못 받았다"를 여기서 물을 수 없다 → AU-01 `#inactive`의 `[초대 메일 다시 받기]`가 그 경로. **v1의 자리 오류** |

### v2 초안에서 채운 것

| | |
|---|---|
| 제출 중 상태 없음 | → 추가(`#loading`). AU-01에는 있었는데 여기만 빠져 있었다 |
| 재수강생 케이스 없음 | → 추가. `직전 기수` 열이 있는데 그 사람이 초대를 받으면 어떻게 되는지가 없었다 |
| `#invalid`가 `#already`를 침범 | → 문구·버튼 정리. 위 §6 |
