## ① 회원가입 시 개인정보 수집 및 이용 동의 — 완료

- `src/features/auth/consents.ts`: 매니저(2개, 전부 필수) / 교육생(5개, 필수4+선택1) 차등 동의, 거부 시 불이익(`note`) 표기, 위탁 고지(`subNote`, §26 대응)까지 이미 반영. 근거가 화면정의 D14로 문서화돼 있음.
- 가이드 예시(①)와 동일한 패턴(필수/선택 구분, 미동의 시 제한 안내) 충족.

## ② 비밀번호 규칙 안내/적용 — 부분 완료

- `src/features/auth/passwordPolicy.ts`: 8자 이상 + 영문·숫자·특수문자 3종 전부 요구.
- 가이드(p.34): "2종류 조합 10~16자리, 3종류는 8~16자리" — **상한(16자) 검사가 없음.** 하한만 있고 상한이 없으면 극단적으로 긴 입력을 그대로 서버에 보내는 부담이 남는다.
- 권고: `checkPasswordPolicy`에 최대 길이(16자 또는 백엔드 정책에 맞는 값) 검사 추가. 사소한 수정 1파일.

## ③ 개인정보 표시 제한(마스킹) — 완료

- `src/lib/utils/mask.ts`의 `maskEmail`이 "동일 방식으로 전체 화면 통일" 요건까지 파일 머리말에 원칙으로 박아둠. `TraineeListScreen.tsx`에서 실사용 확인.

## ④ 개인정보 처리방침 등록 — 미흡 (보류 · 2026-08-08 재확인)

- `consents.ts` 동의 항목 문구에 "개인정보 처리방침"이라는 **말**은 나오지만, 가이드 예시(④)처럼 실제 처리방침 **본문/링크**가 화면(푸터 등)에 상시 노출되는 곳이 코드베이스에 없음(`처리방침` 텍스트 검색 결과 `consents.ts`·자동생성 스키마뿐).
- **재확인 결과: `GET /api/v0/consents`(`ConsentItemResponse`)에도 본문·링크 필드가 없다** — `title`·`description`·`policyVersion`뿐. 링크를 걸 대상(정책 본문/페이지)이 백엔드·프론트 어디에도 아직 없음 — 사용자 확인.
- **판단: 보류.** 이건 프론트 작업이 아니라 법무·백엔드가 처리방침 본문을 먼저 만들어야 하는 선행 작업 — 문서가 생기면 그때 정적 페이지 호스팅 또는 외부 링크 여부를 다시 판단.

## ⑤ 개인정보 암호화 적용 — N/A(백엔드), 프론트 대응은 완료

- 가이드의 SHA-256 해시는 서버 책임. 프론트가 할 수 있는 부분(비밀번호 평문 미저장, HTTPS 전송, `type="password"`)은 이미 충족.
- `authStore.ts`가 accessToken을 **메모리에만** 두고 localStorage/sessionStorage에 안 남기는 설계(파일 머리말에 XSS 대응 근거 명시) — 가이드 취지(민감정보 보호)를 오히려 넘어서는 수준.

## ⑥ 접근통제(비밀번호 유효기간·계정 잠금·캡챠) — 부분 완료

- `LoginScreen.tsx`: "연속 실패 시 잠시 차단된다(**잠금 아님**) — 서버가 남은 시간을 알려준다"고 명시 — 레이트리밋은 있으나 가이드가 말하는 "계정 잠금"과는 다른 정책(의도적 설계로 보임, D-근거 확인 필요).
- 캡챠: 코드베이스 전체에 없음.
- 비밀번호 유효기간: 없음.
- 권고: 이 세 가지는 **정책 결정이 먼저**(캡챠 도입 여부·계정 잠금 전환 여부는 백엔드와 합의 필요) — 프론트 단독으로 판단해 구현할 항목이 아님. 팀장 확인 필요.

## 시큐어1 · 위험한 형식 파일 업로드 — 부분 완료

- 파일 업로드 지점 3곳 확인: `SubmissionForm.tsx`(`.zip`, 클라이언트 사이즈 검증 `validateZipSize`), `RosterCsvField.tsx`(`.csv,text/csv`), `RegisterCurriculumDialog.tsx`(`.pdf,application/pdf`).
- `accept` 속성 + 클라이언트 사이즈 체크는 있으나, 가이드가 강조하는 "확장자 위변조 대응(시그니처 확인)"은 **서버 책임**이고 프론트가 `accept`만으로 대체할 수 없음 — 이 부분은 이미 구조적 한계이자 정상(클라이언트 검증은 UX 보조일 뿐, 실제 방어는 백엔드).
- 권고: 프론트에서 추가로 할 일은 크지 않음. 서버 측 MIME/시그니처 검증 여부만 백엔드에 확인 요청.

## 시큐어2 · 신뢰되지 않은 URL 자동접속(Open Redirect) — 완료(구조적으로 해당 없음)

- `authStore.ts`의 로그인 후 이동은 **서버 응답의 role → 클라이언트 고정 매핑**(`INITIAL_SCREEN`)이며, 사용자 입력 URL이나 쿼리 파라미터를 `navigate()`에 그대로 흘리는 코드 없음(grep 결과 `redirect` 매칭 3건 전부 이 파일·타입 정의뿐). Open Redirect 취약점 패턴 자체가 없음.

## 시큐어3 · CSRF — 완료(구조적으로 해당 없음)

- 인증된 요청은 **쿠키가 아니라 `Authorization: Bearer` 헤더**로 실린다(`client.ts`의 `authMiddleware`) — 공격자 페이지가 피해자 대신 쿠키로 자동 인증되는 CSRF의 전제 자체가 성립하지 않음. 쿠키가 자동으로 실리는 건 `refresh`·`logout`뿐인데 둘 다 상태 변경 폭이 작고(토큰 재발급/로그아웃), `credentials: 'include'` + 서버 CORS 화이트리스트 조합으로 방어되는 영역 — 프론트 추가 조치 불필요, 백엔드 CORS·쿠키 `SameSite` 설정만 재확인 권고.

## 시큐어4 · HTTP 응답분할 — N/A(백엔드 전용)

- 이 저장소는 SSR·서버리스 함수가 없는 순수 SPA(`vercel.json`은 rewrite만 함) — 응답 헤더를 직접 구성하는 코드가 프론트에 없음. 전적으로 백엔드 대응 영역.

## 시큐어5 · 관리자 권한 접속 — **완료**

- `src/shells/RequireRole.tsx` 공용 가드 컴포넌트 신설 — `useSession()`으로 role 확인, 세션 로딩 중 렌더 안 함, 비로그인은 로그인 화면, role 불일치는 `initialScreenFor(user.role)`로 즉시 리다이렉트.
- superadmin 3라우트(이슈 #144 — 파일럿) → operator 8라우트(#146, PR #147) → manager 10라우트(#148, PR #149) → trainee 4라우트(#150, PR #151) 순서로 전부 머지 완료. 전체 라우트 28개(auth 3개 제외 25개 대상) 전수 재확인 결과 `RequireRole` 미적용 파일은 로그인·초대·비밀번호 재설정(비로그인 화면이라 정상) 3개뿐 — **롤아웃 100% 완료.**
- 검증: `npx tsc -b` 0에러·`npx prettier --check` 통과(4개 PR 공통), 각 라우트 파일 `allow` 값이 도메인과 정확히 일치함을 grep으로 재확인(superadmin→`SUPER_ADMIN`, operator→`OPERATOR`, manager→`MANAGER`, trainee→`TRAINEE`).
- ⚠ **잔여 검증 갭:** role 불일치 리다이렉트의 완전한 브라우저 E2E 확인은 아직 안 됨 — 백엔드 `/auth/refresh` 미완성으로 풀 리로드 시 세션 복원이 401로 실패해 전체 시나리오 재현이 막혀 있음(아래 별개 이슈 참고). 로직은 "비로그인 → 로그인 화면" 분기와 동일 패턴이라 코드 리뷰로는 문제없다고 판단했으나, 리프레시 완성 후 재검증 필요.
