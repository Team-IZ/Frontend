## 0. 한 줄 원칙

**표현은 "사용자가 지금 무엇을 잃는가"로 정한다.** 얼마나 걸리는가가 아니다.

| 상황 | 사용자가 잃는 것 | 그래서 |
|---|---|---|
| 첫 진입 | 없음 (아직 본 게 없다) | **모양을 미리 준다** — 스켈레톤 |
| 조건 변경(필터·검색·정렬·페이지) | **보고 있던 결과** | **안 뺏는다** — 이전 결과를 남긴다 |
| 사용자 액션(저장·삭제·재시도) | 화면 전체 | **누른 자리에서만** 표시한다 |
| 백그라운드 갱신 | 없음 | **아무것도 안 그린다** |

경계선은 하나 — **사용자가 기다리는 줄 아는가.** 앞의 셋은 안다(들어왔다·바꿨다·눌렀다),
넷째는 모른다. 모르는 대기를 화면에 띄우면 사용자는 **자기가 뭘 잘못 눌렀는지 찾는다.**

세 번째 열이 이 문서의 전부다. 아래는 그 근거와 구현이다.

## 1. 로딩 — 스피너는 기본값이 아니다

### 1-1. 지금 무엇이 어긋나 있나

같은 상황을 화면마다 다르게 그리고 있다.

| | 첫 진입 | 조건 변경 |
|---|---|---|
| 슈퍼어드민 화면들 | **스켈레톤** | — |
| OP-01 · 02 · 03 · 04 · 05 | **가운데 스피너** | **본문이 사라지고 스피너** |
| OP-06 운영 관리 6탭 | **가운데 스피너** | **표가 사라지고 스피너** |

**둘 중 하나가 틀린 게 아니라, 정해지지 않아서 갈린 것이다.** 이 절이 그것을 정한다.

### 1-2. 첫 진입 — 스켈레톤

**스피너는 "기다려"만 말하고, 스켈레톤은 "이런 것이 올 것이다"를 말한다.**

| | 스피너 | 스켈레톤 |
|---|---|---|
| 전달하는 것 | 진행 중 | 진행 중 **+ 결과의 모양** |
| 레이아웃 | 데이터가 오면 **높이가 급변** | 자리를 미리 차지 |
| 만드는 비용 | 한 줄 | 화면마다 형태를 맞춰야 함 |

실측한 점프 폭 — 명단 탭에서 스피너가 표로 바뀔 때 본문 높이가 **808 → 869px**로 61px
튄다. 스피너 자리(`py-16`)와 표 높이가 다르기 때문이다. 표가 클수록 커진다.

| 대상 | 표현 |
|---|---|
| **표·목록·카드 격자** — 모양이 정해져 있다 | **스켈레톤.** 행 수는 그 화면의 페이지 크기만큼 |
| **한 줄짜리 값**(헤더 개수·배지) | **스켈레톤 한 조각.** 자리만 유지 |
| **모양을 모르는 것**(응답에 따라 구조가 갈림) | 스피너 허용 |

> **스켈레톤 행 수는 실제 페이지 크기와 맞춘다.** 10행짜리 목록에 3행을 그리면 데이터가
> 올 때 또 점프한다 — 스켈레톤을 쓰는 이유 자체가 없어진다.

### 1-3. 페이지 뼈대는 조회와 무관하게 먼저 그린다

`PageHeader`·탭 목록·툴바는 **응답이 필요 없는 상수**다. 데이터를 기다렸다 그리면 도착
순간 페이지 전체가 아래로 밀린다.

```tsx
// ✗ 헤더가 통째로 없다가 생긴다 (OP-01·OP-04가 이렇다)
{data && <PageHeader title="대시보드" breadcrumb={...} />}

// ○ 제목은 상수, 값이 필요한 조각만 늦게 채운다
<PageHeader title="대시보드" breadcrumb={cohortName ? `대시보드 › ${cohortName}` : '대시보드'} />
```

값이 붙는 조각(`count`·`breakdown`)은 **자리를 잡아 두거나** 늦게 붙되, **그 줄의 높이가
바뀌지 않아야** 한다. 탭 목록은 상수이므로 로딩 중에도 그린다 — 도착 후에 탭이 생기면
사용자가 이미 커서를 올려둔 자리가 밀린다.

### 1-4. 조건 변경 — 이전 결과를 남긴다

**이게 지금 가장 큰 결함이다.** 명단 탭에서 2쪽을 누르면 이렇게 된다(실측).

```
누르기 전   표 1개 · 행 10줄 · 본문 869px
누른 직후   표 0개 · 행  0줄 · 본문 808px + 가운데 스피너
```

**표가 통째로 사라진다.** 검색어를 한 글자 칠 때마다, 필터를 바꿀 때마다 같은 일이 난다.

원인은 캐시 라이브러리의 기본 동작이다.

> **쿼리 키(query key)** — 캐시를 구분하는 열쇠. 필터·페이지 값이 여기 들어가므로 조건을
> 바꾸면 **다른 키**가 되고, 그 키에는 캐시가 없다 → `isPending`이 참 → 화면이 빈다.

```ts
useFindTraineeRoster(params, {
  // 조건이 바뀌어도 이전 결과를 남긴다 — 새 결과가 오면 갈아 끼운다
  placeholderData: keepPreviousData,
})
```

그리고 **갱신 중이라는 것을 표시한다.** 값이 옛 것이므로 그 사실을 숨기면 안 된다.

| 표현 | 쓰는 법 |
|---|---|
| 표 전체를 흐리게 | `isPlaceholderData`일 때 `opacity-60 transition-opacity` |
| 보조 기술에 알림 | 그 영역에 `aria-busy` |
| 컨트롤 잠금 | 페이저를 그동안 `disabled` (필터·검색은 **잠그지 않는다** — 계속 치고 있다) |

**한 줄 요약: 첫 조회만 비우고, 두 번째부터는 안 비운다.**

### 1-5. 검색 입력은 300ms 디바운스한다

`lib/useDebounced.ts`가 이미 있고 OP-06 6탭·슈퍼어드민이 쓴다. 안 걸면 **글자 수만큼
요청**이 나가고, 1-4가 없으면 글자마다 표가 사라진다.

### 1-6. 컨트롤은 고를 것이 준비된 뒤에 켠다

로딩 중 옵션이 빈 셀렉트를 그리면 **열어도 아무것도 없다.** 실패보다 나쁘다 — 우리가
스스로 정한 *"누를 수 없는 컨트롤은 장식이다"*(E7)의 같은 자리다. `disabled`로 두거나
스켈레톤으로 대체한다.

### 1-7. 백그라운드 갱신 — 아무것도 안 그린다

저장 후 목록을 다시 읽거나 캐시가 만료돼 뒤에서 받아올 때다. **사용자가 요청하지 않은
갱신**이라 로딩을 그리면 화면이 저 혼자 깜빡인다. `isFetching`으로 분기하지 않는다.
필요하면 **표 밖의 아주 작은 표시** 하나까지가 상한이다.

### 1-8. 200ms 문제 — 캐시가 있으면 아예 안 그린다

캐시에 값이 있으면 응답이 0ms다. 그때 로딩을 그리면 한 프레임 번쩍이고 사라진다 —
없느니만 못하다. **타이머로 풀지 않는다.** 1-4를 지키면 저절로 없어진다 — 캐시가 있으면
로딩 분기 자체를 안 타기 때문이다.

### 1-9. `isPending` 대신 `isLoading`을 쓴다

`isPending`은 **"데이터가 없다"** 이지 **"불러오는 중"** 이 아니다. `enabled: false`인 조회는
요청이 나가지도 않았는데 영원히 `isPending === true`다 — 그대로 그리면 **끝나지 않는
스피너**가 된다.

```ts
// ✗ 꺼 둔 조회가 로딩으로 보인다
const status = useProjectStatus(id, active === 'status')
if (status.isPending) return <Spinner />

// ○ isLoading = isPending && isFetching — 실제로 요청이 떠 있을 때만 참
if (status.isLoading) return <StatusSkeleton />
```

지금 `isPending` 116곳 · `isLoading` 4곳이다. 사고가 안 난 이유는 **가드 순서가 우연히
막아주고 있어서**다(예: `StatusTab`이 `conceptsFixed`를 먼저 본다). 순서를 바꾸면 터진다.

## 2. 빈 상태 — 3종을 실제로 갈라 쓴다

정의와 생김새는 [02-layout-system §4](../plan/v2/definition/02-layout-system.md)가 갖는다.
여기서는 **어느 것을 쓰는지 판정**만 정한다.

### 2-1. 판정 — 질문 하나로 갈린다: 사용자가 지금 할 일이 있나?

| 유형 | 질문의 답 | 테두리 | 문구에 반드시 넣을 것 |
|---|---|---|---|
| **1 · 아직** | 기다리면 된다 | **점선** | **언제** 채워지는지 |
| **2 · 없음** | 만들거나 조건을 풀면 된다 | **실선** | **0건이 무슨 뜻인지** + 그 행동 버튼 |
| **3 · 실패** | 다시 시도 | 실선 + danger | 다시 시도 버튼 |

`0`과 `없음`은 다르다(F3). 분석 실패 0건은 `—`이지 `0`이 아니다.

### 2-2. ⚠ 지금 전부 유형 1로 그려지고 있다

`Empty` 프리미티브의 **기본값이 점선**이다(`border-dashed`). 그래서 `<Empty>`를 그냥 쓰면
유형 1이 된다. OP-06 6탭의 빈 상태 **10곳이 전부 기본값**인데 내용은 전부 유형 2다.

```
"조건에 맞는 기수가 없습니다"    → 필터를 풀면 된다  = 유형 2 (실선)
"아직 등록된 교육생이 없습니다"  → 등록하면 된다     = 유형 2 (실선)
```

**둘 다 점선으로 그려지고 있다** — 화면이 "기다리면 채워진다"고 잘못 말하는 중이다.

고치는 방향은 프리미티브 쪽이다. **기본값을 유형 2(실선)로 바꾸고 유형 1을 명시적으로
고르게 한다.** 근거 둘 — 실제 등장 빈도가 유형 2가 압도적(10:0)이고, **잘못 쓰였을 때 덜
위험하다**("만들 수 있다"를 "기다리라"고 말하는 쪽이 그 반대보다 나쁘다).

### 2-3. 0건이 좋은 소식인 자리를 구분한다

```
이 교안을 쓰는 회차가 아직 없습니다
다시 분석해도 이미 발행된 리포트에 영향이 없습니다.   ← 0건이 안전하다는 뜻

아직 등록된 교육생이 없습니다
CSV로 한 번에 넣거나 직접 입력할 수 있습니다.         ← 0건이 할 일이라는 뜻
```

**"없음"만 쓰지 않는다**(02-layout §4-1). 0건이 조치 대상인지 좋은 소식인지는 화면이 말한다.

### 2-4. 잘 돼 있는 것 — 유지한다

빈 결과의 **이유**가 갈리는 자리는 이미 정확하다. 새로 만들지 말고 이 수준을 따라간다.

- OP-03 — `필터에 안 걸림`(전체 N개에서 찾았습니다) vs `아직 없음`(+ 생성 버튼)
- OP-02 — `안 골랐다`(고르면 채워진다) vs `비교할 기수가 없다`(첫 기수라 기다려야 한다)
- OP-04 현황 탭 — `개념 미확정`(구성 탭으로) vs `제출 전`(언제 채워지는지) vs `실패`

## 3. 실패 — 원인이 있던 자리에, 원인에 맞는 말로

**실패를 상단 배너로 몰지 않는다.** 조작이 여럿인 화면에서 배너 하나만 뜨면 **어느 것이
실패했는지 모른다.**

| 실패한 것 | 어디에 표시 |
|---|---|
| 화면 전체 조회 | 본문 자리에 **유형 3** + 다시 시도 |
| 한 섹션 조회 | **그 섹션 자리에만.** 나머지는 그대로 그린다 (OP-01 `BlockBody`가 이미 이렇다) |
| 모달 안 조작 | **모달을 닫지 않고** 모달 안에 |
| 목록 행 조작 | 그 행 근처 또는 흐름 안 배너 |

### 3-1. 문구는 `status`로 갈린다 — "잠시 후 다시"로 덮지 않는다

`ApiError.status`가 이미 있다(`api/_contract/errors.ts`). 사용자가 **할 일이 다르므로**
문구도 갈려야 한다.

| status | 뜻 | 문구 | 붙는 것 |
|---|---|---|---|
| `0` | 네트워크 끊김 | 인터넷 연결을 확인해 주세요 | 다시 시도 |
| `403` | 권한 없음 | 볼 수 있는 권한이 없습니다 | **다시 시도 없음** |
| `404` | 없음·지워짐 | 지워졌거나 주소가 잘못됐습니다 | 목록으로 |
| `5xx`·그 외 | 서버 문제 | 잠시 후 다시 시도해 주세요 | 다시 시도 |

**도메인 에러 코드가 있으면 그것이 먼저다**(`isGenericCode`가 그 판정을 준다). 예 —
OP-05의 `COHORT_REPORT_NOT_FOUND`는 실패가 아니라 **아직 발행 전**(유형 1)이다. 지금은
일반 실패로 잡혀 "다시 시도"가 붙는데, 눌러도 리포트는 안 생긴다.

### 3-2. 재시도가 의미 없는 실패에는 "다시 시도"를 주지 않는다

권한 없음·검증 실패처럼 **같은 요청을 다시 보내도 같은 결과**인 것에 다시 시도를 권하면
거짓말이다. 그때는 **무엇을 고쳐야 하는지**를 쓴다.

### 3-3. 재시도 버튼은 자기 대기를 보여준다

에러 상태에서 `refetch()`를 불러도 `isError`는 그대로라 **화면이 아무 반응도 안 한다.**
사용자는 연타한다.

```tsx
<Button variant="ghost" disabled={q.isFetching} onClick={() => q.refetch()}>
  {q.isFetching && <Spinner className="size-3.5" />}
  다시 시도
</Button>
```

### 3-4. 모달은 실패하면 닫지 않는다

닫으면 목록이 그대로인 것을 보고 *"안 눌렸나?"* 하며 다시 누른다. 그리고 **입력값이
사라진다.** `실패 시 — 모달 유지 · 입력 유지 · 모달 안에 사유 · 버튼 되살림.`

### 3-5. 부분 실패는 화면을 비우지 않는다

**그 줄만** 유형 3 톤으로 표시한다. 전체를 실패 화면으로 덮으면 멀쩡한 데이터까지 못 본다.
부분 성공(일부 단계만 됨)은 **무엇이 안 됐고 이어서 어디서 하나**를 쓴다 — OP-03 생성이
이미 이렇게 한다(`PARTIAL_MESSAGE` → 상세 구성 탭으로).

### 3-6. 렌더 예외로 흰 화면이 되지 않게 한다

라우터에 `errorElement`가 0개다. 응답 형태가 하나만 어긋나도(옵셔널 필드 `null`) 화면이
아니라 **앱이** 사라진다. 라우트 최상위에 하나 둔다 — 화면마다 만들지 않는다.

## 4. 액션 피드백 — 넷 중 하나를 고른다

이 프로젝트에는 이미 넷이 있다. 언제 무엇을 쓸지 정한다.

| 방식 | 쓰는 때 | 이유 |
|---|---|---|
| **흐름 안 배너** | **되돌리기가 있는 것** | 되돌릴 시간을 준다. 토스트는 사라진다 |
| **모달 안 Alert** | 모달에서 한 조작 | 실패해도 입력이 남는다 |
| **토스트** | 확인만 하면 되는 것 | 화면을 안 막는다 |
| **아무것도 안 함** | **결과가 화면에 즉시 보이는 것** | 목록에서 사라진 걸 봤으면 됐다 |

네 번째가 가장 자주 빠진다. **삭제한 행이 목록에서 사라졌으면 "삭제했습니다" 토스트는
잉여다.** 모달도 마찬가지 — **닫히는 것이 성공 피드백**이라 토스트를 겹치지 않는다.

### 4-1. 되돌리기가 있으면 확인 모달을 세우지 않는다

| | 확인 모달 | 되돌리기 |
|---|---|---|
| 언제 | **되돌릴 수 없는 것** | **여러 번 반복하는 것** |
| 예 | 기수 종료 · 계정 정지 | 반 배정(수십 번 반복) |

배정처럼 반복하는 조작에 확인 모달을 세우면 250명을 스무 번 나눠 넣는 동안 스무 번
눌러야 한다.

### 4-2. 처리 중에는 그 버튼만 잠근다

화면 전체에 오버레이를 씌우지 않는다. **누른 버튼 안에 스피너**를 넣고 그 모달의 버튼만
잠근다. 제출 가드에 `isPending`을 반드시 포함한다 — 없으면 더블 클릭이 두 번 만든다.

### 4-3. 서버가 확인해주지 않는 것을 단정하지 않는다

```
서버가 발송 수를 준다  → "3명에게 보냈어요"
안 준다(항상 202)      → "3명에게 요청했어요 — 도착까지 시간이 걸릴 수 있습니다"
```

### 4-4. 낙관적 업데이트는 기본이 아니다

**응답을 기다리지 않고 화면을 먼저 바꾸는 것**은 이 프로젝트에서 기본이 아니다. 셋을 다
만족할 때만 쓴다 — 실패가 **드물다** · 되돌리기가 **싸다** · 되돌아가도 **사용자가 손해를
안 본다.**

운영 관리의 조작은 대부분 **되돌릴 수 없거나 남에게 영향을 준다**(계정 정지·담당 해제·기수
종료). 여기서 낙관적으로 그리면 실패 시 사용자는 **이미 됐다고 믿고 다음 일로 넘어간
뒤**다. 토글 스위치처럼 값이 하나고 되돌리기가 즉시인 것에만 쓴다.

## 5. 스코프(기수)는 URL이 갖는다

로딩 표현보다 먼저 정해져야 하는 것이 **"지금 어느 기수를 보고 있나"** 다. 지금 같은 콘솔
안에서 화면마다 답이 다르다.

| 화면 | 어디서 오나 | 새로고침·뒤로가기 | 링크 공유 |
|---|---|---|---|
| OP-06 운영 관리 | **URL `?cohort=`** | 유지 | **가능** |
| OP-01·02·03·04 | `stores/cohortScope` — 서버가 고른 진행 중 기수 | 유지(다시 조회) | 불가 |
| OP-05 리포트 | **하드코딩 UUID 상수** | — | 불가 |

**OP-06 방식이 표준이다.** 스코프는 화면 상태가 아니라 **주소의 일부**다 — 그래야 링크
하나가 "9기의 매니저 탭"을 가리키고, 새로고침·뒤로가기가 따라오고, OP-01 `조치 필요`가
특정 기수의 특정 탭으로 딥링크할 수 있다.

지금 상태의 실제 증상 — **리포트와 프로젝트가 서로 다른 기수를 보고 있을 수 있다.** 화면은
아무 경고도 안 낸다. 상단 기수 스위처가 붙을 때 세 곳을 한 번에 맞춘다(`stores/cohortScope`
하나만 URL을 읽게 하고 나머지는 지운다).

## 5-1. 눈으로 보는 자리

**`/operator/__async`** — 이 표준이 실제로 어떻게 그려지는지 단계별로 클릭해 본다.

`ConsoleShell` 안에서 그리므로 **거기서 본 크기가 실제 크기**이고, `ErrorState`·`Empty`·
`staleProps`를 실물로 부른다 — 스크린샷이 아니라 앱과 같은 코드다. 그래서 **그 페이지가
깨지면 앱도 깨져 있다.**

단계는 `?step=`으로 붙는다(`?step=2`). 실제 앱에 이 페이지로 오는 링크는 없다
(`/trainee/__cases`와 같은 관례).

## 6. 착수 점검표

화면 하나를 서버에 붙일 때 이 여덟을 확인한다.

```
□ 첫 진입이 스켈레톤인가 (표·목록이면 반드시)
□ 헤더·탭·툴바가 로딩 중에도 그려지는가 — 도착 전후 높이가 같은가
□ 필터·검색·페이지를 바꿔도 이전 결과가 남는가
□ 검색이 디바운스되는가 — 글자 수만큼 요청이 나가지 않는가
□ 빈 상태가 3종 중 어느 것인지 정해져 있는가 — 기본값(점선)을 그냥 쓰지 않았나
□ 0건이 무슨 뜻인지 문구에 있는가
□ 실패가 "원인이 있던 자리"에 뜨고, status·에러 코드에 맞는 말을 하는가
□ 성공 피드백이 잉여가 아닌가 — 화면에 이미 보이면 안 띄운다
```

### 확인 방법 — 눈으로는 레이아웃 점프를 못 잡는다. 높이를 잰다

```js
// 조건을 바꾸기 전후로 본문 높이와 행 수를 비교한다
const m = () => ({ rows: document.querySelectorAll('tbody tr').length,
                   h: document.querySelector('main').scrollHeight })
// … 페이지 버튼 클릭 후 …
// 표가 사라지거나(rows 0) 높이가 크게 튀면 1-2·1-4 위반이다
```

네트워크를 `Slow 3G`로 두고 새로고침 · 오프라인으로 바꾸고 재조회 · 재시도 연타 —
셋은 매번 손으로 해 본다.
