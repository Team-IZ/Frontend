# 작업 방법론 총합 — 다음 프로젝트에서 그대로 쓰는 절차

`작업정리`·`학습로드맵`·`협업-플레이북` 세 문서와 오늘 git 변경사항에서 **내용(무엇을 만들었나)은 빼고 절차(어떻게 만들었나)만** 추렸다. 이 프로젝트 얘기가 아니라 **다음 프로젝트에 복붙할 것**.

---

## 0. 전체 파이프라인 — 실제로 밟은 순서

```
[0] 준비
    기술 스택 결정(ADR) → 리포 스캐폴딩(+ 관련 스킬 설치) → 명세 파싱해 역매핑 자동 생성
    → 브레인스토밍 → 설계 명세 → 실행 계획(태스크 목록) 작성
[1] 생성
    실행 계획대로 서브에이전트 병렬 생성
[2] 통일 ★ 계획 단계에서 미리 못박아 둘 것
    "전 산출물 일관성 하모나이제이션은 반드시 격리 안 된 단일 세션이 수행" 을 계획서에 명시
[3] 감사 1 — 기준 충실도
    산출물이 원본 명세와 맞는지 전수 대조 → 위반을 리스트업
[4] 감사 2 — 단위별 전수 감사
    산출물 단위(화면/모듈/컴포넌트)마다 체크리스트로 전수 검사
[5] 감사 3 — 통일성 기준서
    "일관되게 하라"는 검증 불가능 → 규칙을 grep/명령어로 셀 수 있게 문서화 → 그 기준으로 감사
[6] 감사 4 — 데이터/계약 기준
    "이 값을 누가·언제 만드나"를 산출물마다 판정 → 기준 문서화 → 감사
```

**핵심 규칙:** 감사 4종은 앞 감사의 실패가 다음을 부른 것 — 이건 **루브릭을 *학습하는* 과정이지 유지할 구조가 아니다.** 한 번 배웠으면 다음엔 전 축을 한 번에 설계해 **1패스**로 돌린다. 그리고 재귀엔 멈춤 조건을 건다: **"더 감사해도 고칠 게 안 나오면 멈춘다."** (문서가 문서를 부르는 무한 루프 차단)

**공유 소스 문서를 먼저 만든다.** 병렬 에이전트가 전부 읽는 읽기 전용 앵커(도메인 규범·시스템 앵커·뷰 패턴 결정·교차 항목 관계) 없이 병렬 생성하면 산출물마다 용어·색·구조가 제각각이 된다.

**안 바꾼 것에도 근거를 남긴다.** 결정 문서에 "바꾼 것"만 적지 말고 **"유지 결정 — 왜 안 바꿨는가"** 섹션을 반드시 둔다. 전부 바꾸는 건 설계가 아니라 리뉴얼이다.

## 1. 역할을 뽑아내는 법 — 실패에서 역산한다

역할은 "필요할 것 같은 직군"을 나열해서 나오지 않는다. **"이게 망한다면 어떤 방식으로 망하는가"** 를 먼저 적고, 망하는 방식 하나마다 그걸 막는 사람을 한 명씩 세운다.

### 절차 (새 프로젝트 시작할 때 30분)

1. **실패 모드를 적는다 — 종류가 다른 것만.** "원인의 종류가 다른 것만 골라. 비슷한 건 묶어."
2. **"무엇을 몰라서" 열을 보고 역할 이름을 붙인다.** 직군 이름표를 먼저 붙이지 않는다 — 모르는 것의 종류가 역할을 정한다.
3. **병합 테스트.** 두 역할을 한 사람이 겸하면 급할 때 어느 쪽이 밀리는지 판정한다. 밀리는 쪽이 있으면 분리한다. (조용히 밀리는 쪽 = 대개 규범/원칙 층)
4. **5~6개를 넘으면 멈춘다.** 7번째가 필요해 보이면 기존 역할의 **권한을 넓힌다**, 새 역할을 만들지 않는다.
5. **"한 역할이 여러 개를 진다" 신호가 오면 — 분할인가 게이트인가.** 두 테스트를 각각 돌린다.
   - **KIND 테스트**: 다른 종류의 전문성인가? → 예면 **역할로 분할**.
   - **압력 테스트**: 급하면 조용히 밀리는가? → KIND는 같은데 밀리면 **분할하지 말고 소스마다 셀 수 있는 게이트를 붙인다.** (밀린 이유는 "역할이 많아서"가 아니라 "셀 수 있는 게 없어서")

### 복붙 프롬프트
```
이 일을 시작하기 전에 역할 모델부터 세우자.

1. 이게 실패한다면 어떤 방식으로 실패할 수 있어?
   원인의 "종류"가 다른 것만. 비슷한 건 묶어.
2. 각 실패마다 "무엇을 몰라서 나는가"를 한 단어로.
3. 그걸 막는 역할에 이름을 붙이고, 소유할 문서를 지정해.
4. 두 역할을 한 사람이 겸하면 급할 때 어느 쪽이 밀리는지 판정해.
   밀리는 게 있으면 분리하고, 없으면 합쳐.
5. 6개를 넘으면 멈추고, 대신 기존 역할의 권한을 넓혀.
6. 한 역할이 여러 개를 지면: 종류가 다르면 분할, 같은데 밀리면 소스마다 게이트를 붙여.
```

## 2. 순서를 세우는 법 — 오염 방향이 순서를 정한다

**"중요한 것부터"가 아니다.** 판정 질문 하나: **A를 B보다 나중에 하면, A의 결과가 B를 무효로 만드는가?**

- 규범/원칙을 뒤로 미루면 → 이미 만든 산출물을 다 다시 만들어야 함 → **오염된다** → 먼저.
- 시각적 스타일을 뒤로 미루면 → 색·값만 바꾸면 됨 → **오염 안 됨** → 나중에 해도 된다.

일반형 순서 (역할 수는 프로젝트마다 다르지만 관계는 동일):
```
1. 규범가        — 그 값/개념이 무엇인가 + 무엇을 보여줘도 되나 + 항목 사이 관계   ★ 여기가 품질의 대부분
2. 시스템 아키텍트 — (1을 받아) 그 값을 누가 만드나, 언제, 얼마
3. 정보 설계자   — 어떤 형태로, 얼마나 보여주는가
4. 인터랙션 설계 — 어떤 액션·상태·전이
5. 비주얼 시스템 — 색·타이포·간격
6. 실행/엔지니어 — 실제로 돌리면 그렇게 나오는가
```

> **함정 1 — "기초적이다"와 "먼저다"는 다르다.** 아키텍트(2)의 판정은 규범가(1)의 산출물을 **소비**한다 → 규범가가 먼저. 순서는 "근본적인가"가 아니라 "뒤집으면 앞이 오염되는가"로 정한다.
> **함정 2 — "먼저"를 "완벽히 먼저"로 오해하지 마라.** 규범은 그려봐야 발견되는 게 많다(회차 평균이 수평선이라는 건 렌더해야 보인다). 상류를 *완결*하고 내려가는 워터폴이 아니라, **얇게 한 바퀴 돌려 규범을 드러낸 뒤 채운다.** 반복은 순서 위반이 아니라 탐색 도구다. 단, 되돌리기 비싼 결정(데이터 모델·생산자 계약)만 미리 확정하고 싼 것(색·이름)은 나중에 — **Type-1/Type-2 구분.**

### 병렬 가능 지점은 보통 하나뿐이다
- **대조·통일이 목적인 단계는 항상 병렬 금지.** (규범 정독, 정보 설계 비교, 비주얼 통일, 최종 검수)
- **뷰/경계가 이미 고정된 뒤의 독립 실행 단계만 병렬 이득.** (개별 항목별 상세 구현)

> "병렬로 하면 빠르다"의 함정: 대조·통일이 목적인 작업을 병렬로 쪼개면 목적 자체가 사라진다.

### 게이트 2개 — 통과 못 하면 되돌아간다
- **게이트 A** (아키텍트 뒤): 원본 명세의 예외/분기 수 = 산출물의 상태·행 수. **숫자로 세는 계약**이라 논쟁 여지가 없다.
- **게이트 B** (인터랙션 뒤): 전체 산출물을 **사람이 직접 렌더/실행해서 눈으로 본다.** 정의서가 완벽해도 실물은 따로 깨진다.

## 3. 역할별로 시킬 것 — 산출물 형태 · 안 했을 때 신호

역할마다 "산출물의 형태"와 "일 안 했을 때의 신호"가 다르다. 신호를 알아야 검수할 수 있다.

| 역할 | 시킬 것 | 산출물 형태 | 안 했을 때 신호(🚩) |
|---|---|---|---|
| **규범가** | 원본을 **전수 정독**(키워드 grep 아님). 규칙에 번호+근거 붙여 목록화 | 규칙 목록, 요약 금지 (규칙 1개 = 1줄 + 근거) | 금지어 grep만 했다 / 표현 규범만 있고 "이 값이 무엇인가"(의미 규범)가 없다 / 근거 출처가 안 붙어 있다 |
| **아키텍트** | 규범가 산출물을 받아 **생산자·시점·비용을 판정**(받아쓰기 금지) | 표: 값\|생산자\|시점\|타입\|틀렸을 때 누가 잡나 + 호출/비용 예산 | "명세에 이렇게 쓰여 있다"로 끝난다 / 호출 수를 안 센다 |
| **정보 설계자** | **전체를 나란히 놓고 한 번에** 비교. 개별로 맡기지 않는다 | 항목당 "문제 진단→결정→이유" 3줄 + **유지 결정과 그 이유** | 전부 같은 패턴(예: 전부 카드 그리드)이다 / 안 바꾼 것에 대한 언급이 없다 |
| **인터랙션 설계** | 항목당 상태 표. **원본의 예외 case 수 = 상태 행 수**(게이트 A) | 상태별 표 + 액션→처리 매핑 표 | 상태가 정상/로딩/에러 3개뿐이다 (원본 case를 안 본 것) |
| **비주얼 시스템** | **grep/명령어로 셀 수 있는 계약**으로만 쓴다. "일관되게 하라"는 검증 불가능 | 계약 + 검사 명령어 (예: `grep ... \| sort -u` → N개여야 함) | "일관성 있게 정리했다"고만 한다 (건수가 없으면 안 한 것) |
| **실행/엔지니어** | **발행/배포 환경 기준**으로 직접 실행해서 결과를 눈으로 확인 | 스크린샷/실행 로그 | 로컬에서만 열어봤다 (증거 아님) / 결과물 첨부가 없다 |

## 4. 협업 대화 규칙

1. **역할을 명시적으로 지정한다.** "이거 좀 봐줘"가 아니라 "지금부터 규범가로서만 봐. 다른 층은 지금 말하지 마."
2. **한 번에 한 역할만.** 역할을 섞으면 거부권 방향이 무너진다 — "규범가로서는 이게 필수인데, 정보설계자로서는 지저분하니 지우자"는 스스로를 이기는 것.
3. **피드백을 줄 때 그게 어느 역할에 대한 것인지 말한다.** 하류 역할(정보설계·비주얼)에서 나온 지적은 상류 역할(규범)의 결정을 뒤집을 권한이 없다.
   > **일반 규칙: 규범과 하류 설계가 충돌하면 답은 거의 항상 "삭제"가 아니라 "온디맨드"다.** 규범이 요구하는 건 "도달 가능할 것"이지 "항상 동시에 보일 것"이 아니다. 삭제 전에 접기(disclosure)를 먼저 검토한다.
4. **산출물을 건수로 요구한다.** "검토했다"는 검증이 아니다. "34종 → 6종", "누락 5건" 같은 숫자가 검증이다.
5. **Trust, but verify — 최고 위험 1건.** 무작위 1건이 아니라 **틀리면 가장 크게 다치는 1건**(낙인 라벨·확정 액션·돈 계산)을 검산한다. 틀리면 전부 의심. **단, 통과해도 배치가 깨끗한 건 아니다** — 통과는 "이 1건 OK"이지 "배치 OK"가 아니다.
   - "고쳤다"고 하면 → **diff를 직접 읽는다.**
   - 숫자를 대면 → **가장 무거운 값 하나를 계산기로 검산한다.**
   - "전부 고쳤다"고 하면 → **검사 명령어를 직접 돌려본다.**

## 5. 위상 이탈 관리 — 지금 단계가 아닌 말이 나올 때

겸직자와 AI는 아는 걸 지금 다 말하려는 경향이 있고, **그 말이 대개 맞기 때문에 위험하다.** 규범을 정하는 중에 "그 디자인 좀 별로인데"가 나오면, 맞는 말이라 거기로 끌려가고 규범은 미완으로 남는다.

**판정 질문 하나만 쓴다: "이 말이 맞다면, 지금까지 한 작업이 무효가 되는가?"**

| 답 | 처리 | 이름 |
|---|---|---|
| 무효가 된다 | **즉시 멈추고 앞 단계로 되돌아간다** | STOP (선행 오염) |
| 무효가 안 된다 | **한 줄로 적어두고 계속 진행한다** (논의하지 않는다) | PARK (위상 이탈) |

**판별법:** 앞 단계(상류)에서 오는 말 = STOP. 뒤 단계(하류)에서 오는 말 = PARK. §2의 "오염 방향"과 같은 규칙이다. **무효가 되는지 모르겠으면 STOP** — 확인 30초가 재구축 6화면보다 싸다.

### 주차장(Parking Lot) 파일 — `docs/_parking-lot.md`
```markdown
# 주차장 — 지금 단계가 아닌 것들

## [단계명] (n단계에서 처리)
- [ ] 내용 한 줄  (날짜 제기)
```
**규칙 셋:**
1. 한 줄로 적고 즉시 계속 진행한다. 그 자리에서 논의하지 않는다.
2. 해당 단계에 들어갈 때 주차장을 열어 한꺼번에 처리한다.
3. 주차장이 비었는데 한 단계가 끝났다면 그 단계를 대충 한 것이다 — 정상적으로 일하면 뒤 단계 얘기는 반드시 쌓인다.

### 매 응답에 걸어두는 규율 (복붙)
```
현재 단계: [지금 단계명]

이 단계 밖의 얘기가 떠오르면:
- 지금까지 한 작업을 "무효화"하는 거면 → 즉시 멈추고 알려. 앞 단계로 되돌아간다.
- 무효화하지 않는 거면 → docs/_parking-lot.md 에 한 줄로 적고 그냥 진행해. 논의하지 마.

그리고 매 응답 첫 줄에 현재 단계와 남은 게이트 조건을 적어.
```

## 6. 새 프로젝트 시작 템플릿 (복붙용, 전 과정 통합)


## 7. 구체 스킬 워크플로우 — shadcn 컴포넌트 작업

1. **항상 실제 값부터 조회한다.** `shadcn info`(또는 동등 명령)로 프로젝트 설정(alias, 스타일 베이스, 아이콘 라이브러리 등)을 먼저 확인 — 하드코딩·추측 금지.
2. **추가 전 존재 확인.** 이미 설치된 것인지 먼저 확인하고, 미설치일 때만 검색 → 공식 문서를 실제로 fetch해서 API 확인 → 설치.
3. **변경 전 항상 미리보기.** `--dry-run` / `--diff`로 영향 파일을 먼저 보고, 로컬 커스터마이징이 있으면 diff 기반으로 업스트림 변경분만 반영(전체 덮어쓰기는 사용자 명시 승인 없이 금지).
4. **설치 후 반드시 직접 읽고 검증한다.** import 누락, 규칙 위반(접근성 필수 요소 누락 등), 아이콘 라이브러리 불일치를 스스로 고친 뒤에만 다음으로 넘어간다.
5. **결정은 우선순위 사다리로.** 기존 컴포넌트 검색 → 조합(컴포지션) → 내장 variant → className → 신규 variant → 래퍼, 이 순서로 시도하고 상위 단계에서 해결되면 멈춘다.
6. **모호하면 절대 추측하지 않고 사용자에게 확인한다** — 특히 레지스트리·프리셋처럼 되돌리기 번거로운 선택.

## 8. 구체 워크플로우 — Radix → Base UI 같은 라이브러리 마이그레이션

**사전 준비:** 실제 설정 조회(추측 금지) → git 클린 상태에서 컴포넌트 단위 1커밋 → 손대기 전에 baseline 빌드/타입체크로 "원래 있던 실패"와 "내가 낸 실패"를 구분해 둔다.

**전략은 우선순위 순으로 시도한다:**
1. 공식 대응쌍(예: 프레임워크가 제공하는 stock 버전)이 있으면 최우선 — 원본과 diff해서 "손 안 댐(그대로 덮어쓰기 가능)" vs "커스터마이징됨(3-way 병합 필요)"으로 분류.
2. 공식 대응쌍이 없으면, 그것으로 "커스터마이징 여부"만 판별하고 실제 변환은 수작업 엔진으로 — 원본 그대로 옮겨쓰기 금지(스타일이 달라지면 안 됨).
3. 그마저 없을 때만 순수 수작업 변환.
4. **병합이 충돌 없이 "깨끗하게" 끝나도 잔여 스캔을 한 번 더 돌린다.** 클린 머지가 클린 결과의 증거는 아니다.

**진행은 컴포넌트 하나씩(strangler-fig 방식):** 의존 관계 있는 것부터(leaf 먼저) → 새 버전 작성 후 타입체크 → 소비처(consumer)를 하나씩 전환 → 마지막 소비처 전환 후에만 원본 삭제 → 최종 체크 → 커밋. 재개 시 이미 만든 새 버전이 있으면 재시작이 아니라 이어서 한다.

**보편 체크리스트(라이브러리 무관하게 반복):** import 경로 두 형태 모두 확인 / prop 리네임은 "선언 → 구조분해 → 하위로 명시적 전달" 3단계를 매번 확인(그냥 `...props`로 흘려보내면 타입에러 없이 조용히 깨진다) / 데이터 속성·CSS 변수는 기계적 치환 가능하지만 애니메이션은 원래 의도를 재해석해서 다시 작성(1:1 치환 금지) / 대상이 아닌 패키지는 "의도적으로 남김"으로 명시 보고.

**검증 순서:** 파일 단위 타입체크 → 배치 단위 빌드 → 전체 완료 후 baseline 대비 전체 빌드. 리포트는 컴포넌트당 1파일, 고정 포맷(변경됨/그대로 둠/동작 변화/수동 확인 항목)으로 남겨 재실행 시 그 파일만 갱신한다.

## 9. 디자인/애니메이션 리뷰 방법론

**감사는 3단계로 한다:**
1. **정찰** — 스택·기존 토큰·제품 성격·빈도(자주/가끔/드묾 노출)를 먼저 파악한 뒤 관련 패턴을 코드 전수 스윕.
2. **관점별 병렬 감사** — 서로 다른 관점(목적/타이밍, 물리성, 중단 가능성, 성능, 접근성, 일관성, 놓친 기회 등)으로 나눠 각자 근거(파일:줄)만 수집, 수정안은 이 단계에서 내지 않는다.
3. **검증 및 우선순위화** — 모든 발견을 원본에서 재확인해 의도된 설계·오귀속·중복을 제외하고, "효과 ÷ 비용"으로 순위를 매겨 확정된 것만 제시. 신규 제안은 실제 관찰된 이음매 기준으로 소수만.
4. **심각도는 3단계로 채점**: 느낌 자체를 깨는 것(상) / 눈에 띄게 어긋나는 것(중) / 다듬으면 좋은 것(하).

**실행 계획은 발견 1건당 파일 1개로 자기완결형 작성:** 문제(위치+현재 코드) → 목표(구체적 값까지, "더 낫게" 같은 모호한 표현 금지) → 이 저장소의 기존 관례(모방할 예시 파일 포함) → 파일별 구체 편집 단계 → 하지 말 것(신규 의존성 금지 등, 코드가 예상과 다르면 즉시 중단·보고) → 검증(기계적 체크 + 사람이 직접 느껴보는 체크 + 완료 기준). 여러 계획이 있으면 인덱스 문서에 우선순위·실행 순서·의존관계를 갱신한다.

**작업 시작 전 게이트:** 코드를 작성하기 전에 "이 작업이 어떤 종류의 화면/오디언스/방향을 지향하는가"를 한 줄로 먼저 선언한다. 모호하면 추측하지 말고 질문 하나만 한다. 리디자인이면 손대기 전에 반드시 현재 상태부터 감사(무엇을 보존하고 무엇을 버릴지 문서화)하고, 위험이 낮은 순서(타이포 → 여백 → 색 → 모션 → 구조 재편)로 단계적으로 적용한다. 산출 직전에는 정해진 체크리스트를 전부 통과해야 완료로 친다 — 하나라도 실패하면 미완성.

## 10. 명세 → 산출물 실행 방법론 (명세 주도 개발의 세부 절차)

**역추출 원칙:** 산출물을 상상해서 만들지 않는다. 원본 명세에서 "이 항목이 어느 단위(화면/모듈 등)에 속하는가"를 태깅한 컬럼을 파싱해 단위→항목 역매핑을 먼저 만들고, 그 역매핑에서 산출물 목록을 도출한다 — 명세와 산출물의 불일치를 구조적으로 차단하는 방식.

**7단계 절차:** ① 단위 인벤토리 역매핑 → ② 단계(배치) 기준 확정 → ③ 표준 템플릿 확정 → ④ 정보구조는 상위 흐름도를 골격으로 사용 → ⑤ 배치 순서대로 작성 → ⑥ 저해상도 시안 제작 → ⑦ 원본의 항목·예외 케이스가 전량 반영됐는지 역추적 체크리스트로 검증.

**태스크 1개당 공통 6스텝:** Step0 공유 앵커(읽기 전용) 확인 — **절대 수정 금지, 충돌 방지** → Step1 소스 읽기 → Step2 산출물 작성(원본의 예외 case 수 = 산출물의 상태/행 수로 1:1 대응시키는 원칙) → Step3 시각 산출물 제작(앵커의 기존 패턴만 사용, 임의 스타일 신설 금지) → Step4 발행 → Step5 링크 연결 → Step6 커버리지 자기검증(케이스 개수 대조).

**공유 앵커를 확장해야 할 때:** 담당자가 공유 파일을 직접 고치지 않는다. 자기 산출물에 "앵커 확장 제안" 섹션만 남기고, 이후 통합 단계에서 전부 취합해 재사용 가치가 있는 것만 앵커에 반영한 뒤 제안 섹션을 지운다.

**하모나이제이션(통합) 대조 방법:** 병렬로 만든 산출물 전체를 한 세션이 동시에 열어, 미리 정한 대조 축(용어/문구, 색상, 내부 배치 순서, 빈 상태·에러 톤, 위계, 서술 방식 등) 몇 가지 기준으로만 대조하고 불일치만 고친다. 결과는 인덱스 문서에 기록한다.

## 11. 판정·감사 방법 모음

- **생산자 판정(이 값을 누가 만드는가) — 순서대로 묻는 3문:** ① 정답이 열려 있는가(닫혀 있으면 자동/결정론 금지) → ② 틀렸을 때 누가 잡는가(사람 승인/교차검증이 없고 사람 판정에 직결되면 금지) → ③ 결정론으로 같은 품질이 나오는가(나오면 결정론 우선). 부가로: 호출 수·크기를 실제로 세어 빈도와 곱해 비용을 추산하고, "호출당 산출 가치"로 최종 판정한다. 같은 호출에 필드 하나 더 얹어 추가 비용이 0이면 그걸 우선 채택.
- **"일관되게 하라"를 검사 가능한 계약으로 바꾸는 기법:** 모든 규칙을 grep/count로 셀 수 있는 형태로 재작성하고, 규칙마다 실행 가능한 검사 명령을 같이 적는다(예: "이름은 N개 축으로 수렴해야 한다" + 실제로 세는 명령 한 줄). 감사 결과는 계약별 통과/위반 + 조치를 표로 남긴다.
- **도메인 규범 분류·번호화:** 원본의 처리로직·규칙·예외 문구를 전수 훑어 규범 문장만 추출하고, 카테고리(표현/의미/흐름 등 성격이 다른 것)로 나눠 "카테고리문자+일련번호"를 붙인다. 산출물마다 해당 규칙 번호를 인용하고, 해당 사항이 없으면 "해당 없음"이라고 명시(누락과 구분하기 위해).
- **뷰/구조 결정 절차:** 화면·항목마다 "문제 진단(기존 구조가 왜 목적을 방해하는가) → 결정(패턴명 + 근거 규칙/항목 연결) → 이유" 순으로 서술한다. 바꾸지 않은 것도 반드시 "유지 근거"를 남긴다(왜 대안이 개선이 안 되는지). 결정 판단 기준은 고정된 소수(예: 의사결정 속도, 스캔 효율, 맥락 유지)로 미리 정해 둔다.
- **감사 전수 워크시트:** 검사 항목을 원본 단위(트리거/입력/처리단계/규칙/출력/예외/전이/표현/산술 등)로 고정해 "명세의 무엇이 산출물의 무엇과 1:1 대응해야 하는가"를 항목마다 정의하고, 단위별 진행 상태·발견 건수·조치 여부를 표로 추적한다.
- **명세 충실도 감사(다층 대조):** 원본 컬럼 전수 계약 + 다단 추적(요구사항→세부규칙→산출물) + 교차 관계 계약, 이렇게 세 겹으로 검증한다. 심각도는 3단계(치명/중요·국소/경미)로 표기하고 건별로 원문 인용을 붙인다. 문서 간 내용이 충돌하면 어느 쪽을 우선할지 원칙을 명시적으로 선언하고 근거를 남긴다. 감사자 스스로의 오판도 별도 섹션으로 인정하고, 재발 방지를 절차 규칙으로 흡수한다(예: "없다고 단정하기 전에 전수 검색을 먼저 해야 한다").
- **독립 2차 검토(외부 리뷰):** 내부 자체 감사가 끝난 뒤에만 실시. ① 실제 실행/발행 환경에서 렌더해 육안 확인 ② 소스에서 값을 스크립트로 직접 추출해 대조(추측 배제) ③ 대상을 나눠 서로 격리된 여러 검토자가 각자 대조 후 종합(교차 오염 방지). "문제없이 재확인된 것"도 실측 근거와 함께 먼저 표로 제시한 뒤 신규 발견으로 넘어가고, "범위 밖이라 다루지 않은 것"도 별도로 남긴다.

## 12. 산출물 문서 템플릿 & 인덱스 관리법

**개별 산출물 문서(예: 화면정의서) 공통 섹션 순서:**
제목 → 개요(권한·진입경로·연계 근거 전체·이번 배치 범위/후속 범위) → 목적과 결정 근거(서술형 논증) → 정보 구조·배치 순서 → 데이터-컴포넌트 매핑(표) → 액션→API 계약(표: 트리거·요청·응답/부수효과·근거·권한규칙) → 상태별 UI(공통 상태 + 원본의 예외 case 전량을 표로) → 인터랙션/전이 → 컴포넌트 매핑(재사용 vs 신규) → 규범 준수 체크(해당 규칙 인용, 미해당은 "해당 없음"으로 명시적으로 닫음) → 시각 산출물 링크.
**공통 원칙:** 모든 섹션은 "서술형 근거"와 "표 형식 스펙"을 항상 세트로 둔다 — 결정 이유와 실행 가능한 스펙을 동시에 남긴다.

**인덱스(README형) 관리법:** ID·이름·역할·문서 링크·시각 산출물 링크를 표로 관리하고, 두 산출물이 모두 있어야 "완료"로 친다. 전체를 "이번 배치(완료)"·"다음 배치(미착수)"로 나눠 관리하고, 공유 소스 문서 목록을 별도 절로 고정해 둔다. 배치 완료 후 정해진 대조 축으로 전량 재점검하고 "발견/수정"과 "수정 안 함(근거)"을 구분 기록한다. 이후 시점의 추가 검증 라운드는 날짜와 함께 새 절로 누적하되, 상세 근거는 별도 문서로 링크만 남겨 인덱스는 요약 상태를 유지한다.

## 13. 낯선 자료 구조(ERD 등)를 처음 읽는 법

**읽는 순서 자체가 방법이다:**
1. 왜 이렇게 쪼개 놨는지부터 체감한다 — 안 쪼개면 뭐가 깨지는지(중복 수정, 값 없으면 존재 자체가 안 보임)를 먼저 이해한 뒤 세부 용어(키·관계 등)를 도입한다.
2. 실제 사례 하나를 처음부터 끝까지 추적한다. 추상적 설명 대신 "행위자 하나가 시스템을 통과하는 경로"를 따라가며 구성요소를 등장 순서대로 훑고, 요소 사이 관계를 화살표로 명시한다.
3. 반복되는 설계 기법을 패턴으로 묶어 재설명한다 — 개별 항목이 아니라 "왜 이렇게 짰는가"의 패턴 단위(예: 값을 덮어쓰지 않고 이력을 분리해 쌓는다, 특정 시점 값을 스냅샷으로 고정한다)로 다시 훑는다.
4. 전체를 관통하는 공통 요소(거의 모든 단위에 반복되는 값)를 별도로 짚어 "우연이 아니라 원칙"임을 표로 증명한다.
5. 마지막으로 "의도된 설계 vs 작업 흔적(오타·툴 오류)"을 구분하는 체크리스트로 마무리한다.

**설계 근거를 정리하는 프레임워크:** 전체 구성요소를 알파벳/등장순이 아니라 **실제 프로세스가 돌아가는 순서**로 묶어 훑는다. 단위마다 동일한 질문 3개에 답한다 — ① 존재 이유(안 나누면 구체적으로 뭐가 깨지는가) ② 개별 항목의 존재 이유(없으면 어떤 요구사항을 못 지키는가) ③ 관계(어디를 가리키고 카디널리티는 몇 대 몇인가). 무언가를 둘로 쪼갠 경우엔 "변하는 속도가 다른가 / 생명주기가 다른가 / 보는 대상이 다른가" 중 어느 것이 쪼갠 이유인지 명시한다. 근거는 추측이 아니라 항상 원 문서 인용으로 뒷받침하고, 마지막에 반복되는 기법들을 다시 묶어 "이 설계들이 결국 하나의 상위 요구사항에서 파생됐다"는 식으로 수렴시킨다.

## 14. 한 문장 요약

**역할 목록을 외우지 말 것.** "이게 어떻게 망하는가"를 먼저 적으면 역할은 저절로 나온다. **순서는 "오염 방향"으로, 단 상류를 *완벽히* 끝내려 말고 얇게 한 바퀴 돌려 규범을 드러내라.** 검증은 최고 위험 1건. 그리고 **이 방법론이 코드보다 무거워지면 방법론을 멈추고 만들어라** — 안 만든 것은 감사할 수도 없다.
