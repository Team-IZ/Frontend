## 1. 🔴 R1 — 분석 전 교안의 `/sections`가 영원히 응답하지 않습니다

`GET /api/v0/curricula/{materialId}/sections`

회차 생성 모달은 교안을 고른 뒤 **그 교안이 가르친 항목**에서 검증 개념 3건을 고릅니다.
그 후보를 이 API가 줍니다. 그런데 **분석이 안 끝난 교안에서는 응답이 오지 않습니다.**

### 재현 — 9기 교안 7종 전수 (curl, 각 60초 상한)

| 교안 | `pageCount` | 결과 |
|---|---|---|
| 20250214 부산교육청…붙임.pdf | `null` | **HTTP 000 · 60초 타임아웃** |
| a-practical-guide-to-building-agents.pdf | `null` | **HTTP 000 · 60초 타임아웃** |
| Classroom_discussion_guide_-_AI_and_coursework_v2.4.pdf | `null` | **HTTP 000 · 60초 타임아웃** |
| spring_backend_basics.pdf | `null` | **HTTP 000 · 60초 타임아웃** |
| 똑디와함께하는생성형AI…(1).pdf | `null` | **HTTP 000 · 60초 타임아웃** |
| spring_backend_v1.pdf | 120 | 200 · TTFB **2.51초** · 섹션 7 |
| spring-test-ops-v1.pdf | 38 | 200 · TTFB **2.03초** · 섹션 2 |

**`pageCount`가 `null`인 교안 다섯이 정확히 전부 타임아웃**이고, 값이 있는 둘은 2초 대에
정상 응답합니다. 상관이 완전합니다.

### 무엇이 문제인가

**에러가 아니라 무응답입니다.** 4xx/5xx라면 화면이 「이 교안은 아직 분석 중입니다」라고
말할 수 있는데, 연결이 열린 채 아무것도 오지 않아 **화면은 영원히 로딩입니다.**
브라우저에서는 여기에 15차 R3(프록시가 동시 요청 프리플라이트를 502)가 겹쳐,
교안을 둘 이상 고르면 `net::ERR_FAILED`가 되어 **개발자 도구에는 「요청이 나가지도
않은 것」처럼** 보입니다.

**실제 영향 — 이 기수에서는 회차를 만들 수 없었습니다.** 교안 7종 중 5종이 이 상태라,
그 교안을 고른 순간 개념을 못 고르고 생성이 멈춥니다.

### 요청

1. **분석 전에는 즉시 응답해 주세요.** 빈 배열(`[]`)이든 `409 CURRICULUM_NOT_ANALYZED`든
   좋습니다 — 화면이 「분석이 끝나면 고를 수 있습니다」라고 말할 수 있으면 됩니다.
2. 무응답의 원인이 분석 파이프라인 대기라면, **타임아웃을 걸어 주세요.** 지금은 커넥션이
   물려 있어 재시도가 쌓입니다.

**화면은 임시로 막아 두었습니다** — `pageCount == null`인 교안은 못 고르게 하고
「분석 중 · 아직 못 고름」을 붙였습니다. R2가 오면 그 값으로 바꿉니다.

## 2. 🔴 R2 — 교안이 분석됐는지 알 방법이 없습니다

`GET /api/v0/cohorts/{cohortId}/curricula` → `CurriculumVersionResponse`

```
versionId · materialId · versionNo · originalFileName · pageCount · createdAt
```

**상태 필드가 없습니다.** 지금 화면은 `pageCount`가 `null`인지로 분석 여부를 **추측**하고
있는데, 이건 「쪽수를 아직 모른다」는 뜻이지 「분석 중」이라는 뜻이 아닙니다. 분석이
**실패**한 교안과도 구분이 안 됩니다.

### 요청

`analysisStatus` 같은 필드를 실어 주세요. 값은 화면이 이렇게 씁니다.

| 값 | 화면 |
|---|---|
| `ANALYZING` | 「분석 중 — 끝나면 고를 수 있습니다」 · 못 고름 |
| `READY` | 고를 수 있음 |
| `FAILED` | 「분석 실패 — 다시 올려 주세요」 · 못 고름 |

`teachesCount`(가르친 항목 수)가 같이 오면 더 좋습니다 — 고르기 전에 *"이 교안에서 개념
3건을 뽑을 수 있나"* 를 알 수 있습니다. 지금은 골라 봐야 압니다.

## 3. 🟠 R3 — 목록에 교안 이름과 개념 이름이 없습니다

`GET /api/v0/cohorts/{cohortId}/projects` → `ProjectResponse`

```
curriculumCount        1      ← 개수만
conceptCount           3      ← 개수만
conceptCandidateCount  12
```

화면의 표는 이렇게 됩니다.

```
프로젝트          상태     기간              교안     검증 개념 3건
미니프로젝트 1차   종료    03-09 ~ 03-20     1개      3건 확정
```

**교안 필터를 걸어도 무엇이 걸린 것인지 표에서 확인할 수 없습니다.** `spring_backend_v1`로
걸러 7건이 나왔는데, 표의 「교안」 열은 여전히 `1개`라고만 말합니다. 다른 교안으로 걸면
0건인데, 그게 *"정말 없어서"* 인지 *"필터가 안 먹어서"* 인지 화면이 구분해 줄 수 없습니다.

검증 개념도 같습니다 — `3건 확정`이 아니라 **무엇을 확정했는지**가 이 회차의 정체입니다.
그걸 보려면 지금은 회차마다 상세를 열어야 합니다.

### 요청

목록 항목에 **이름을 실어 주세요.** 전량이 아니어도 됩니다.

```jsonc
"curriculumNames": ["spring_backend_v1.pdf"],          // 또는 대표 1개 + 나머지 수
"conceptNames":    ["예외 처리와 롤백 전략", "API 응답 계약 설계", "영속성 매핑과 지연 로딩"]
```

목록이 전량 반환(페이지 없음)이라 항목 수가 곧 회차 수입니다 — 한 기수 수십 건 수준이라
페이로드 부담은 크지 않을 것으로 봅니다.

## 4. 🟠 R4 — 정렬 셋이 사실상 같고, 셋 다 「종료」가 맨 앞입니다

`sort=READINESS` · `DUE_SOON` · `START_DATE` (9기, 2026-08-12 기준 · 오늘은 08-12)

| 순위 | `READINESS`(준비 필요 순) | `DUE_SOON`(마감 임박 순) | `START_DATE`(시작 이른 순) |
|---|---|---|---|
| 1 | 1차 CLOSED 03-09~03-20 | 1차 CLOSED | 1차 CLOSED |
| 2 | 2차 CLOSED 04-13~04-24 | 2차 CLOSED | 2차 CLOSED |
| 3 | 3차 CLOSED | 3차 CLOSED | 3차 CLOSED |
| 4 | 4차 CLOSED | 4차 CLOSED | 4차 CLOSED |
| 5 | 5차 CLOSED 07-20~07-31 | 5차 CLOSED | 5차 CLOSED |
| 6 | **투투투 PLANNED 08-11~08-18** | **투투투 PLANNED** | 6차 RUNNING 08-03~08-21 |
| 7 | 6차 RUNNING 08-03~08-21 | 6차 RUNNING | 투투투 PLANNED 08-11~08-18 |

`READINESS`와 `DUE_SOON`이 **완전히 같고**, `START_DATE`만 6·7이 바뀝니다. 셋 다 날짜
오름차순으로만 정렬된 것으로 보입니다.

### 이 화면이 정렬로 답하려는 질문

목록은 **「손댈 것이 남은 회차 찾기」** 가 목적입니다. 그런데 기본 정렬(`READINESS`)이
**5개월 전에 끝난 회차**를 맨 위에 놓습니다. 오퍼레이터가 매일 보는 화면에서 가장 위
다섯 줄이 전부 「할 일 없음」입니다.

### 제안하는 정렬 규칙

**공통 — 끝난 것은 뒤로.** `CLOSED`는 어떤 정렬에서도 마지막 그룹입니다. 지난 일은
목록의 목적(준비)과 무관하고, 필요하면 상태 필터로 봅니다.

| 정렬 | 1차 키 | 2차 키 | 뜻 |
|---|---|---|---|
| `READINESS`<br>준비 필요 순 | **준비도**: `PREP`(교안·개념·일정 중 빈 것 있음) → `PLANNED/READY` → `RUNNING` → `CLOSED` | 마감 가까운 순 | *"지금 손대야 하는 것"* |
| `DUE_SOON`<br>마감 임박 순 | **아직 안 지난 마감**만 가까운 순 | 지난 마감은 뒤로(최근 순) | *"곧 닫히는 것"* |
| `START_DATE`<br>시작 임박 순 | **아직 시작 안 한 것**(`startDate >= 오늘`) 가까운 순 | 이미 시작한 것 → 끝난 것 | *"곧 열리는 것"* |

핵심은 **오늘을 기준선으로 쓰는 것**입니다. 지금은 날짜만 보고 오늘을 안 봅니다.

`START_DATE`는 스펙 설명이 *"시작 이른 순"* 이라 **동작과는 맞습니다** — 화면 라벨이
「시작 임박 순」이라 어긋났습니다. 위 규칙으로 바꿀지, 이름을 「시작 이른 순」으로 둘지
정해 주시면 화면을 맞추겠습니다. **저희 의견은 「임박」입니다** — 이 화면에서 지난
시작일은 볼 이유가 없습니다.

## 5. 🟠 R5 — 회차 기간에 시각이 없습니다

`CreateProjectRequest.startDate` · `endDate` — 둘 다 `format: date`, 스펙 주석에도
*"날짜만이며 시각 의미가 없다"* 고 적혀 있습니다(9차 Q2).

**제출 마감이 몇 시인지 정할 수 없습니다.** 화면에는 한때 `<input type="time">`이 있었는데,
서버가 저장하지 않아 **받아 놓고 버리는 입력**이 되어 뺐습니다(운영자는 `23:59 마감`이라고
믿는데 실제로는 그 시각이 아무 데도 없는 상태였습니다).

실제로 이게 필요한 자리 — 제출 마감(교육생이 언제까지 내나) · 응시 창(세션이 몇 시에
열리고 닫히나). 둘 다 「그 날 아무 때나」로는 운영이 안 됩니다.

### 요청 — 셋 중 하나로 정해 주세요

| | 방식 | 장 | 단 |
|---|---|---|---|
| **ⓐ** | `endDate`를 `date-time`으로 | 지금 구조 그대로, 운영자가 정확히 지정 | DB 마이그레이션 |
| **ⓑ** | `submissionDueAt`을 별도 필드로 | 기간(날짜)과 마감(시각)이 분리돼 뜻이 또렷 | 필드 추가 |
| **ⓒ** | 서버가 파생(`endDate` 23:59:59 KST 고정) | 변경 없음 | 회차마다 다르게 못 정함 |

**저희는 ⓑ를 제안합니다.** 「기간」과 「마감 시각」은 다른 개념이고, 응시 창이 나중에
붙을 때도 같은 자리에 얹을 수 있습니다. 정해지면 화면에 시각 입력을 되살립니다
(`SchedulePicker`에 그때 뺀 이유와 되살릴 조건을 적어 두었습니다).

### 지금 화면이 어떻게 하고 있나

**날짜만 씁니다. 시각을 지어내지 않습니다.** 상세 개요·헤더·타임라인 전부
`2026-08-21`까지만 표기하고, 「23:59」 같은 값을 붙이지 않습니다 — 화면이 그렇게 말하면
학생은 그 시각까지 낼 수 있다고 믿는데 서버는 그 약속을 모릅니다.

**연도는 이번에 되살렸습니다.** `07-21`처럼 월·일만 쓰고 있어서 **어느 해 7월인지 알 수
없었습니다** — 기수가 해를 넘겨 이어지고 종료 회차는 몇 달 전 것이라, 목록·상세·타임라인이
전부 연도 없이 같은 값을 말하고 있었습니다. 시각이 오면 그 뒤에 붙입니다.

## 6. 🟡 R6 — `pageCount`를 두 스키마가 다르게 말합니다

```
CurriculumVersionResponse.pageCount   integer          required: true   ← 실제로 쓰는 것
CurriculumCatalogItem.pageCount       [integer, null]  required: true
                                      "페이지 수. 분석 전이거나 확정되지 않았으면 null"
```

실측에서 `null`이 옵니다(7종 중 5종). 서버 동작은 nullable 쪽인데
`CurriculumVersionResponse`가 아니라고 선언합니다.

**요청** — `CurriculumVersionResponse.pageCount`를 `["integer","null"]`로 맞춰 주세요.
설명도 같은 문장이면 생성된 타입이 실제와 맞습니다.

증상은 작았습니다 — 생성 모달의 교안 줄에 숫자 없이 **`쪽`만** 떴습니다. 화면은
「모르면 아예 안 쓴다」로 고쳤고 타입도 `number | null`로 내렸습니다.

> 14차 `readinessCounts`와 같은 종류입니다 — 스펙이 `required`라 해서 화면이 믿었는데
> 응답이 다른 말을 하는 것. 저희는 스펙에서 타입을 생성해 쓰므로 **스펙이 곧 계약**입니다.

## 7. 🔴 R7 — 없는 리소스를 조회하면 404가 아니라 **무응답**입니다

`GET /api/v0/projects/{projectId}`

**R1과 같은 증상이 다른 엔드포인트에서도 납니다.** 형식은 맞지만 존재하지 않는 UUID로
회차 상세를 부르면 응답이 오지 않습니다.

### 재현 (curl, 70초 상한)

| `projectId` | 결과 |
|---|---|
| `00000000-0000-0000-0000-000000000000` (형식 O · 없음) | **HTTP 000 · 70초 타임아웃** |
| `073c7e8b-…` (존재) | 200 · TTFB 2.10초 |
| `abc` (형식 X) | **400** · TTFB 0.70초 · 0.1KB |

형식이 틀린 값은 **0.7초에 400**으로 정확히 돌아옵니다. 존재하지 않는 값만 무응답입니다.

### 무엇이 문제인가

화면에서는 상세 진입이 **영원히 로딩**입니다(실측 40초까지 스피너, 이후로도 계속).
사용자에게는 「느린 화면」과 구분되지 않아 계속 기다리게 됩니다. 프론트의 전역 재시도
(5xx·네트워크 3회)도 여기서는 도움이 안 됩니다 — 실패로 판정될 일이 없습니다.

### 요청

**404를 주세요.** 코드가 있으면 더 좋습니다(`PROJECT_NOT_FOUND`) — 화면이
「이 회차를 찾을 수 없습니다 · 목록으로」로 정확히 갈리고, 재시도 버튼도 안 그립니다
(다시 눌러도 생기지 않을 것이므로).

같은 패턴이 다른 상세 조회에도 있는지 함께 봐 주시면 좋겠습니다 — R1(`/sections`)과
이것이 같은 층에서 나오는 문제로 보입니다.

**화면은 임시로 이렇게 합니다** — 타임아웃으로 끊지 않고(잠든 서버가 깨는 데 최대 76초가
걸립니다) **12초가 지나면 오래 걸린다는 사실과 주소 확인을 안내**합니다. 끊지 않는 이유는
정상적으로 깨어나는 중인 요청을 죽이지 않기 위해서입니다.

## 8-1. R1·R7·R8은 **같은 문제로 보입니다**

세 엔드포인트가 같은 규칙으로 갈립니다.

| 엔드포인트 | 정상 | **무응답** |
|---|---|---|
| `/curricula/{id}/sections` | 분석된 교안 (2.0~2.5초) | **분석 전 교안** |
| `/projects/{id}` | 존재하는 회차 (2.1초) | **없는 회차** |
| `/projects/{id}/class-progress` | 시작·종료된 회차 (2.2~2.8초) | **시작 전 회차** |

**「보여 줄 데이터가 아직 없는 상태」에서만 응답이 오지 않습니다.** 세 군데 모두
정상 경로는 2~3초로 일정하고, 실패 경로만 에러 없이 매답니다. 공통 층(집계 대기·
비동기 파이프라인 조회 등)에서 나는 문제라면 **한 곳을 고치면 셋이 같이 풀릴 것**으로
보입니다 — 그쪽에서 먼저 봐 주시면 좋겠습니다.

형식이 틀린 값(`/projects/abc`)은 **0.7초에 400**으로 정확히 오므로 라우팅·검증 층은
정상입니다.

## 10. 참고 — 15차 R3(동시 요청 502)가 여기서도 나옵니다

교안을 N개 고르면 섹션 조회가 N건 나가는데, **동시에 보내면 전부 죽습니다.**

```
동시(Promise.all) — 교안 4개 → 3건 모두 net::ERR_FAILED → 재시도도 동시에 나가 또 실패
순차(하나씩)     — 전부 200
```

화면은 **순차로 바꿔서 피했습니다**(`useCohortScope`의 기수+반 조회도 같은 이유로
순차화). 다만 이건 우회이지 해결이 아닙니다 — 교안이 늘수록 그만큼 느려집니다.

**여유가 되면**, 여러 교안의 섹션을 한 번에 주는 형태(`?materialIds=a,b,c`)나
`projectId` 없이 부를 수 있는 후보 API가 있으면 요청 자체가 1건이 됩니다.
급하지 않습니다 — R1이 풀리면 실사용에서 교안 2~3개 수준입니다.
