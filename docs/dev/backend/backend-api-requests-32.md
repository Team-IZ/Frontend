## 2. 🔴 R1 — `PENDING`인데 `items`가 옵니다

**스펙**은 이렇게 적고 있습니다.

> `resultStatus` — `PENDING`이면 화면이 **"이 회차는 아직 결과가 없어요"** 를 그린다.
> 리포트 발행 전이라 **위험 판정 자체가 없는 상태**다.

**실응답**(9기 · 미니프로젝트 5차)입니다.

```jsonc
"round": { "resultStatus": "PENDING", "publishedAt": null, "daysSincePublish": null },
"total": 4,
"counts": { "PLANNED": 4, "DONE": 0, "EXCLUDED": 0 },
"items": [
  { "name": "송지안", "status": "PLANNED", "riskType": "LOW_PERSISTENT", "briefState": "NONE" },
  { "name": "임윤슬", … }, { "name": "장수아", … }, { "name": "한유진", … }
]
```

**위험 판정이 없다면서 위험 유형이 붙은 케이스 4건을 함께 보냅니다.**

### 화면이 둘 중 하나를 버려야 합니다

그대로 그리면 한 화면이 서로 다른 말을 합니다.

```
머리글   면담 4명 · 예정 4 · 종결 0 · 제외 0
본문     이 회차는 아직 결과가 없어요
```

**저희는 본문 쪽을 기준으로 맞췄습니다** — 스펙이 「PENDING이면 그 안내를 그린다」이고,
**아직 뒤집힐 수 있는 판정을 숫자로 단언하는 쪽이 더 나쁘다**고 봤습니다. 그래서
`PENDING`이면 머리글의 개수·내역도 그리지 않습니다.

**다만 그 4명은 화면에서 사라집니다.** 실제로 면담이 필요한 사람이라면 매니저가
못 보게 되는 것이라, 어느 쪽이 사실인지 확인 부탁드립니다.

| 만약 | 그러면 |
|---|---|
| ① `PENDING`인데 판정이 나온 것이 **버그** | `items`·`counts`를 비워 주세요 |
| ② 판정은 나왔는데 `resultStatus`가 **안 따라온 것** | 그 회차는 `READY`가 맞습니다 |
| ③ 둘 다 의도 — **판정 전 미리보기** | 그런 뜻의 상태 값을 따로 주세요(`PROVISIONAL` 등). 저희가 「잠정」으로 그리겠습니다 |

> 5차는 리포트 발행 전(`publishedAt: null`)이고 응시가 진행 중인 회차입니다.
> ②일 가능성이 높아 보이지만 저희가 단정할 근거가 없습니다.

## 3. 🟠 R2 — 첫 진입이 두 왕복입니다

`assessmentRoundId`가 **필수**라, 화면은 회차 목록을 먼저 받아야 면담 목록을 부를 수
있습니다. 실측입니다(같은 시각 · 같은 토큰 · 3회).

```
GET /interviews/rounds       TTFB 1.12 / 1.35 / 1.14초   (연결 0.04초)
GET /interviews?...          TTFB 1.78 / 1.44 / 1.56초   4407B
                             ────────────────────────
합계                          2.5 ~ 3.1초  (직렬)
```

**연결은 0.04초입니다** — 네트워크도 크기도 아니고 서버 계산입니다. 브라우저에서
사이드바를 눌러 들어가면 **0~5초 스피너, 6초에 첫 행**입니다(콜드스타트 포함).

### 명부는 이미 그 문제를 풀어 두셨습니다

`GET /cohorts/{id}/trainees`는 `assessmentRoundId`를 **생략하면 서버가 「이번 회차」를
골라** 응답의 같은 이름 필드로 알려줍니다. 그래서 명부 화면은 **한 왕복**입니다.

```
명부    생략 → 서버가 고름 → 응답에 assessmentRoundId          1왕복
면담    필수 → rounds를 먼저 받아야 함                          2왕복
```

**면담에도 같은 규칙을 주시면** 왕복이 하나 줄고, 회차 드롭다운은 지금처럼
`/interviews/rounds`로 따로 채우면 됩니다(그건 병렬로 나갈 수 있습니다).

> 우선순위는 낮습니다 — 화면이 죽는 문제가 아니라 진입이 느린 것뿐입니다.
> 다만 두 API가 같은 자리에서 다른 규칙인 것이 걸립니다.

```

GET /cohorts/{id}/trainees?size=1                7865ms    2922B   rows=1

### `size`로는 안 줄고 `query`로만 줍니다

이 둘이 갈림길로 보입니다.

| 바꾼 것 | 결과 | 읽은 것 |
|---|---|---|
| `size` 20 → 1 (응답 29KB → 2.9KB) | **7.8초 그대로** | 크기도 직렬화도 아닙니다 |

`size`는 결과를 **자르는** 것이라 집계는 26명분을 다 돌고, `query`는 **모집단을 줄이는**
것이라 계산량이 함께 준다 — **행마다 도는 계산이 있다**는 뜻으로 읽었습니다. 회차
지표·우수 누적·위험 판정이 행당 붙는 값들이라 그쪽이 후보로 보입니다.

**저희가 줄일 수단이 없습니다.** 페이지 크기는 이미 20이고, 지표를 빼고 부르는
파라미터가 없습니다. 브라우저에서는 사이드바 클릭 후 **11초에 첫 행**이 그려집니다.

> 재보지 않았는데, 행에 비례한다면 그쪽이 더 무거울 수 있습니다.

### ② 교육생 타임라인 — 11~12초

> ⚠️ **8/17 정정 — 「`size`가 무시된다」는 8/16 관측을 취소합니다.**
>
> 다시 재보니 **`size`는 정확히 걸립니다.** 그때 무엇을 잘못 봤는지는 확실치 않은데

## 15. 🟠 R13 — 다른 회차의 `teamId`가 400이 아니라 200 + 빈 결과입니다

히트맵은 계층이 `TRAINEE`일 때 `classroomId`와 `teamId`를 **필수로** 요구합니다.
빠지면 정확히 400을 주십니다.

```
level=TEAM     반 없이 → 400 HEATMAP_SCOPE_INVALID
level=TRAINEE  팀 없이 → 400 HEATMAP_SCOPE_INVALID
```

그런데 **다른 회차에 속한 `teamId`를 주면 200이 옵니다.**

```
5차 회차(projectId=a8778dbf… · roundId=46196f94…) + 6차 팀 id(9213b5f7…)

200
scope    { classroomId, classroomName: "C반", teamId: "9213b5f7…" }   ← teamName이 없습니다
rows     []
summary  null
concepts 3건
```

### 화면이 거짓말을 하게 됩니다

팀은 프로젝트에 매인 값이라 회차가 바뀌면 뜻을 잃는데, 응답만 보면 **「그 팀에 결과가
없다」와 「그 팀이 이 회차에 없다」가 구별되지 않습니다.** 화면은 앞의 뜻으로 읽고
「이 범위에는 아직 결과가 없습니다」라고 말합니다 — 사실이 아닙니다.

`scope.teamName`이 안 오는 것으로 보아 서버도 그 팀을 못 찾은 것 같습니다.

**저희 쪽은 막았습니다** — 회차·반을 바꾸면 팀을 비우고 팀 격자로 내려옵니다. 다만
같은 값이 딥링크·뒤로가기로도 들어올 수 있어, 서버가 400(`HEATMAP_SCOPE_INVALID`)을
주시면 화면이 「그 팀은 이 회차 것이 아닙니다」라고 정확히 말할 수 있습니다.

## 16. 🟠 R14 — 화면에 있는데 매니저가 부를 자리가 없는 것 셋

목업 단계에서 그려 둔 기능인데 실서버에 자리가 없어 **버튼을 뺐습니다.** 화면이
지어낸 성공은 새로 고치면 사라져서, 흉내 내지 않고 지웠습니다.

### ① 팀 삭제

팀 오퍼레이션 전수입니다 — **팀 자체를 지우는 것만 없습니다.**

```

PATCH  /projects/{id}/teams/{teamId}               updateTeam
POST   /projects/{id}/teams/{teamId}/members       assignTeamMember
DELETE /projects/{id}/teams/{teamId}/members/{tid} removeTeamMember   ← 팀원 해제는 있습니다

POST   /projects/{id}/teams/confirm                confirmTeams
PATCH  /projects/{id}/teams/reopen                 reopenTeams
GET    /projects/{id}/teams                        findTeams
```

실제로 지금 9기 6차에 **인원 0명짜리 `7팀`이 남아 있고 지울 방법이 없습니다** — 그 팀이
제출 현황에서 「미제출 ⚠」로 잡혀 조치가 필요한 것처럼 보입니다.

### ② 다시 보기 활성화·비활성화 — **매니저가 열 수 있는 자리가 없습니다**

```

전제        리포트는 "본인 것이고 공개된 것"이어야 한다

그런데 **그 사람에게 열어 주는 행위**가 매니저 쪽에 없습니다.

**그래서 이건 요청이 아니라 질문입니다.**

- 다시 보기는 **교육생이 스스로 여는 것**이 설계인가요? 그렇다면 매니저 화면의
  「활성화」는 성립하지 않는 개념이라 **영구히 지우겠습니다** — 결과 탭은 「대상 N명」만

목업에는 「활성화 → 기한 지정 → 응시 여부 추적 → 비활성화」가 있었는데, 그 흐름 전체가
교육생 주도라면 화면 설계가 달라집니다.

### ③ 리포트 발행

`reportPublished`는 읽기 전용으로만 옵니다. 발행 버튼과 확인 절차를 뺐습니다.

지금은 「아직 없다」인지 「매니저는 못 한다」인지 구분이 안 됩니다.

## 19. ❓ Q3 — 교안 버전 축이 둘입니다

목록과 상세가 **다른 버전을 가리킬 수 있습니다.**

| | 무엇을 주나 |
|---|---|
| `GET /cohorts/{id}/linked-curricula` | `versionId` · `versionNo` — **이 기수가 연결한 버전** |
| `GET /curricula/{materialId}` 외 2건 | `materialId`를 받아 **최신 버전으로 해석**(스펙 명시) |

교안이 v1 → v2로 올라갔는데 9기가 아직 v1을 쓰고 있으면, **목록 행은 `v1`인데 상세를
열면 `v2` 내용**이 나올 것으로 보입니다. 매니저는 회차가 실제로 가르친 교안을 보러
오는 자리라 그러면 어긋납니다.

지금 9기 교안 둘은 **둘 다 v1이라 드러나지 않았습니다** — 그래서 「그렇다」가 아니라
**「이 해석이 맞습니까」**로 여쭙습니다.

### 필드 설명 하나가 그 반대를 가리킵니다

```
CohortCurriculumResponse.versionId
  "curriculum_version_id — 교안 상세로 갈 때 쓰는 ID"
```

그런데 **`versionId`를 받는 오퍼레이션이 스펙 전체에 하나도 없습니다**(경로·쿼리 전수
확인). 상세 셋은 전부 `materialId`입니다.

이 설명을 그대로 따르면 **13차 R1이 그대로 재현됩니다** — 그때도 화면이 교안 축에
버전 id를 넣어 늘 빈 배열을 받았고, 목록은 「24개 회차에서 사용 중」인데 상세는
「쓰는 회차가 아직 없습니다」라고 답했습니다.

저희는 `materialId`로 붙였습니다. 설명 쪽을 고쳐 주시면 다음 사람이 같은 데 안 빠집니다.

맞다면 상세 셋이 `versionId`로도 조회되면 좋겠습니다(`?versionId=` 선택 파라미터든,
경로를 하나 더 주시든 형태는 편하신 대로입니다).
