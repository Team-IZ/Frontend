# OP-01 대시보드 — 일어날 수 있는 모든 상황

> **이 화면을 고치기 전에 이 문서를 본다.** 무엇이 일어날 수 있고, 지금 그중 무엇이
> 처리돼 있고, 무엇이 안 돼 있나.
>
> 화면의 설계 근거는 [op-01-dashboard.md](op-01-dashboard.md), 비동기 상태 표준은
> [async-states.md](../async-states.md)가 갖는다. 여기는 **상황 목록과 실측 결과**다.
>
> 실측 — 2026-08-11 · 운영 계정 · 9기(RUNNING) · 10기(PLANNED) · 실서버.

---

## 0. 왜 이 문서가 필요한가

이 화면은 **조회 하나가 아니다.** 기수를 먼저 묻고, 그다음 셋을 병렬로 부르고, 그중 하나는
안에서 또 둘을 순차로 부른다. 조회 다섯이 각자 성공·실패·지연하므로 **조합이 곱해진다.**

```
useCohortId()        GET /cohorts                     ─┐ 이게 끝나야
                                                       │ 나머지가 시작한다
useDashboard(cohortId)                                ─┘
  ├─ risk      GET /cohorts/{id}/analytics/risk-trainees
  ├─ todos     GET /cohorts/{id}/analytics/actions
  └─ pipeline  GET /cohorts/{id}/projects            ─┐ 순차
               GET /projects/{pid}/class-progress    ─┘
```

한 화면이 **다섯 응답 × (성공/실패/느림) × 데이터 상태**를 견뎌야 한다. 아래는 그것을
축으로 나눈 것이다.

## 1. 상황 축 — 무엇이 달라질 수 있나

### 축 A. 기수 스코프

| 값 | 언제 | 지금 화면 |
|---|---|---|
| A1 · 기수가 정해짐 | 정상 | 조회 나감 |
| A2 · 기수 조회 중 | 진입 직후 1.2초 | 제목만 · 본문 스피너 |
| A3 · 기수가 하나도 없음 | 신규 기관 | 「없는 것」 유형 2 |
| A4 · 기수 조회 실패 | 네트워크·5xx | **A3과 같은 문구를 쓴다** ⚠ |
| A5 · 진행 중 기수 없음(전부 PLANNED/CLOSED) | 기수 사이 | 목록 첫 기수를 씀 |

| 값 | 언제 | 반 비교 블록 |

| 값 | 화면 |
|---|---|

| 값 | 화면 |

## 2. 실측 — 지금 실제로 어떤가

### 2-1. 🔴 로딩이 8초다

실측(9기, 실서버, 로컬 dev):

```
 1,169ms  GET /cohorts                     ← 이게 끝나야 아래가 시작
 2,016ms  GET .../analytics/risk-trainees  ─┐
 2,105ms  GET .../analytics/actions         │ 병렬
 5,227ms  GET .../projects                 ─┘  ← 느리다
 1,678ms  GET /projects/{id}/class-progress    ← projects 뒤에 순차
────────
 ≈ 8.1초  화면 전체가 스피너 하나
```

세 가지가 겹쳐 있다.

| | 무엇 | 왜 아픈가 |
|---|---|---|
| ① | `/projects`가 **5초** | 파이프라인 블록 하나가 전체를 8초로 만든다 |
| ② | 기수 조회가 **직렬** | 대시보드 조회가 1.2초 뒤에야 시작한다 |
| ③ | 블록 셋이 **한 쿼리** | 1.5초에 온 조치 필요를 6.6초 더 기다린다 |

**③이 가장 아깝다.** 블록별로 실패는 갈라 놨는데(`Block<T>`) **도착은 안 갈라져 있다** —
`Promise.all`이 셋을 묶어 놔서 가장 느린 하나에 맞춰진다. 화면은 이미 블록마다 독립적으로
그릴 수 있게 돼 있으므로, 쿼리를 셋으로 나누면 **조치 필요가 1.5초에 뜬다.**

### 2-2. 🔴 인원이 화면마다 다르다

같은 9기를 세 곳이 다르게 센다.

| 화면 | 값 | 출처 |
|---|---|---|
| 대시보드 머리글 | **196명** | `risk.cohortSummary.traineeCount` |
| 파이프라인 분모 | **208명** | `class-progress.summary.targetTraineeCount` |
| 운영 관리 · 명단 | **224명** | `trainees.cohortTotal` |

**한 화면 안에서도 갈린다** — 머리글이 `196명`인데 바로 아래 파이프라인이 `0/208`이다.
셋 다 뜻이 다를 수는 있지만(등록 / 이번 회차 대상 / 명부 전체), **화면이 그 차이를 한
글자도 설명하지 않는다.** 사용자는 셋 중 무엇이 맞는지 알 수 없다.

> 이건 프론트가 혼자 못 고친다 — 각 값의 정의를 백엔드에 확인해야 한다(15차 요청 후보).
> 정의가 정해지면 화면은 **한 줄 주석**으로 차이를 말하면 된다.

### 2-3. 🟠 「아직」을 「실패」로 그린다 (C2 · B4)

10기(PLANNED)에 실제로 물어본 결과:

```
projects        6개 (전부 PLANNED)
risk-trainees   200 · rounds 6개 전부 NOT_STARTED · classes 0 · traineeCount 0
actions         200 · actionCount 0
```

이때 화면은 이렇게 된다.

| 블록 | 지금 문구 | 사실 |
|---|---|---|
| 반 비교 | **"반별 위험 비율을 불러오지 못했습니다" + 다시 시도** | 조회는 200이다. 집계된 회차가 아직 없을 뿐 |
| 머리글 | `0명 · 0반` | 반이 아직 안 만들어진 것 |

**조회는 성공했는데 실패라고 말한다.** 「다시 시도」를 눌러도 회차가 돌기 전에는 영영
같다 — async-states §3-2가 금지한 그 버튼이다. 회차가 0개인 기수(B4)도 같은 경로다.

`toCompare`가 `null`을 돌려주는 것은 **의도된 판단**이었지만(0%를 사실로 그리지 않으려고),
`{ ok: false }`로 떨어뜨리는 순간 그 의도가 "실패"로 바뀐다. **`Block<T>`에 세 번째 상태가
필요하다** — `ok` / `pending`(아직) / `failed`.

### 2-4. 🟠 실패 원인을 버린다

```ts
async function block<T>(load: () => Promise<T>): Promise<Block<T>> {
  try { return { ok: true, value: await load() } }
  catch { return { ok: false } }          // ← 에러가 여기서 사라진다
}
```

`catch`가 원인을 통째로 버려서 **권한 없음·서버 오류·오프라인이 전부 같은 문구**가 된다.
1단계에서 만든 `errorCopy`가 이 화면에서만 못 쓰이는 이유다. 잡되 **들고 있어야** 한다.

### 2-5. 🟠 블록 하나를 재시도하면 다섯이 다시 나간다

`BlockFailed`의 「다시 시도」가 `page.refetch()`를 부른다 — 쿼리가 하나라 **조회 다섯이
전부 다시** 나가고 **8초를 다시 기다린다.** 조치 필요만 실패했는데 잘 뜬 파이프라인까지
사라졌다 다시 온다. 2-1의 쿼리 분리가 이것도 같이 고친다.

### 2-6. 🟡 `riskRate: null`을 `0%`로 그린다

```ts
const toPercent = (rate) => (rate == null ? 0 : Math.round(rate * 100))
```

실제 응답에 `riskRate: null`이 온다(집계 전 셀). 이걸 `0`으로 만들면 **"위험자 0%"라는
사실을 주장**하는데 실제로는 아직 안 센 것이다. F3(0과 없음은 다르다)의 같은 자리 —
`graded`가 0이면 `—`로 그려야 한다.

### 2-7. 🟡 회차 선택 근거가 화면에 없다 (B5)

`RUNNING`이 둘 이상이면 `find`가 첫 번째를 집는데, **화면은 그것을 골랐다고 말하지 않는다.**
일정이 겹치는 기수에서 사용자는 "왜 6차를 보여주지"에 답을 얻을 수 없다. 서버 정렬 순서에
의존하고 있어 순서가 바뀌면 조용히 다른 회차가 뜬다.

### 2-8. ✅ 잘 돼 있어 건드리지 않는 것

- **블록 단위 실패 격리**(`Block<T>` · `BlockBody`) — 하나가 죽어도 나머지를 그린다
- **제목 줄이 조회를 안 기다린다** — 도착해도 페이지가 안 밀린다(4단계에서 고침)
- **마감이 판별선** — 같은 `19명 미제출`을 마감 전/후로 색이 갈린다
- **UTC 마감을 로컬로 파싱** — `split('T')`였으면 KST 23:59가 14:59로 보였다
- **분석 실패는 팀 수** — 단위가 명→팀→명으로 튀지 않게 단계 밖으로 내림
- **없음과 0** — 제출 전 뒤 단계를 `—`로
