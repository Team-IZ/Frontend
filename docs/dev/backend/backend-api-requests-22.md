## 1. 🔴 R1 — `required`인데 `null`인 필드가 **25개**입니다

`joinedAt` 하나를 보고하려다 **전수로 세어 보니 훨씬 넓었습니다.** 오퍼레이터가 쓰는
응답을 전부 받아, 스펙의 `required` 목록과 실제 값을 대조했습니다(9기 · 실서버).

| 스키마 | 행 | `required`인데 `null` |
|---|---|---|
| **`TraineeRosterEntry`** | 100 | **21개** |
| **`ManagerRosterEntry`** | 8 | **4개** |
| `CurriculumVersionResponse` | 7 | `analysisStatus` 2 · `pageCount` 5 ← 18차 R6에서 `pageCount`만 고쳤습니다 |
| `CohortResponse` | 1 | 없음 ✅ |

### `TraineeRosterEntry` — 21개

```
leftAt 96      inactivatedAt 96        inactivatedById 96     inactivatedReason 96
inactivatedReasonCode 96               inactivatedByName 96
className 4    classroomId 4           joinedAt 1             pendingInvitationTokenId 99
attemptId 100  assessmentRoundId 100   roundTerminalAt 100    roundResultStatus 100
roundPrimaryStatusCode 100             rowAggregationStatus 100
matchedRiskTypeCodes 100               conceptResultItems 100
lowStageConceptCount 100               expectedConceptCount 100
excellentOccurrenceCount 100
```

**대부분이 「그 상태일 때만 있는 값」입니다** — 이탈자만 `leftAt`, 비활성만
`inactivatedAt`, 회차 결과가 있을 때만 `round*`. 즉 **`null`이 정상이고 선언이 틀린
것**으로 보입니다.

### `ManagerRosterEntry` — 4개

```
invitedAt 8    invitedByName 8    lastLoginAt 7    pendingInvitationTokenId 8
```

### 실제로 화면을 죽인 것

```
TypeError: Cannot read properties of null (reading 'slice')
  RosterTab.tsx   {t.joinedAt.slice(0, 10)}
```

명단 탭의 **반 필터에서 「미배정」을 고르는 순간 화면이 통째로 죽었습니다.**
라우터의 `errorElement`가 화면을 대신 그렸고, 10초를 기다려도 안 돌아왔습니다.
**9기 미배정이 17명이라 실무에서 반드시 밟는 경로**입니다.

나머지 24개는 **아직 안 터졌을 뿐**입니다. 저희가 화면에서 쓰는 자리를 훑어 보니
지금은 우연히 방어돼 있거나(`t.inactivatedAt?.slice()`) 안 쓰고 있는데, **타입이
`string`이라 다음에 누가 `.slice()`를 붙이면 그 자리에서 또 죽습니다.**

### 요청

**`null`이 정상인 필드는 스펙도 그렇게 말하게 해 주세요.**

```jsonc
"joinedAt": { "type": ["string","null"], … }
```

또는 `required`에서 빼 주시면 됩니다. **저희는 스펙에서 타입을 생성해 쓰므로 스펙이
곧 계약**이고, `required`라고 적힌 값은 화면이 그대로 믿습니다.

> 14차 `readinessCounts` · 18차 R6 `pageCount` · 이번 25개 — **같은 종류를 세 번째**
> 만납니다. 한 건씩 고치는 대신 **한 번 전수로 훑어 주시면** 이 유형이 끝날 것 같습니다.
> 위 표가 그 목록입니다.
>
> **화면은 `joinedAt`을 방어했습니다**(값이 없으면 `—`). 같은 형태의 날짜 필드
> `linkedAt` · `uploadedAt`도 선제적으로 막아 두었습니다.

## 2. 🔴 R2 — 마감 시각: **생성에서 못 받고, 어디서도 못 읽습니다**

**18차 R5를 ⓑ안으로 만들어 주셔서 감사합니다.** 그런데 붙이려고 보니 **입구도 출구도
반쪽**이라, 지금 화면이 **틀린 마감을 그리고 있습니다.**

### 🔴 먼저 — 화면이 실제로 틀린 값을 보여주고 있습니다

9기 회차 전부의 `endDate`와 실제 마감을 대조했습니다.

| 회차 | `endDate` | `class-progress.submissionDueAt` | |
|---|---|---|---|
| 6차 (RUNNING) | 2026-08-21 | `2026-08-21T14:59:00Z` = 23:59 KST | 같음 |
| 1~4차 (CLOSED) | 각각 | 각 `endDate` 23:59 KST | 같음 |
| **5차 (CLOSED)** | **2026-07-31** | **`2026-08-11T18:00:00Z`** = **8/12 03:00 KST** | **12일 차이** |

**회차 상세 화면은 「제출 마감 2026-07-31」이라고 말합니다.** 실제 마감은 8월 12일입니다.

`endDate`와 마감이 **자동으로 연결되지 않는다**고 회신에서 짚어 주신 그대로인데,
화면이 읽을 값이 없어서 `endDate`를 마감이라고 계속 쓰고 있었습니다.

### 입구 — 생성에 `submissionDueAt`이 없습니다

```
CreateProjectRequest          name · category · startDate · endDate          ← 없음
UpdateProjectScheduleRequest  startDate · endDate · submissionDueAt          ← 있음
```

**회차를 만들 때는 마감 시각을 정할 수 없고**, 만든 뒤 일정 수정으로 다시 들어가야 합니다.
생성 모달에서 시작·마감을 고르는 흐름인데 시각만 다른 화면에서 정하는 것은 어색합니다.

> 18차 R5를 저희가 *"회차 기간에 시각이 없습니다"* 로만 적어 **생성을 명시하지 않은 것**이
> 원인입니다. 죄송합니다.

### 출구 — 상세·목록에서 못 읽습니다

| 스키마 | `submissionDueAt` |
|---|---|
| `ClassProgressResponse` | ✅ — **현황 탭 전용** |
| `CurrentRoundResponse` · `MySubmissionResponse` | ✅ — 교육생 화면 |
| **`ProjectResponse`**(목록·이번 회차) | ❌ |
| **`ProjectDetailResponse`**(상세) | ❌ |

마감을 **정하고 보여주는 자리**는 회차 상세인데, 그 화면이 읽는 것은
`GET /projects/{projectId}`입니다. `class-progress`는 **현황 탭의 조회**이고
**개념 3건이 확정된 뒤에만** 값이 있습니다 — 일정을 정하는 시점에는 대개 없습니다.

게다가 위 5차 사례처럼 **`PLANNED` 회차는 `class-progress`가 아예 응답하지 않습니다**(§6).

### 요청 — 쓰는 자리를 전수로 적습니다

**한 곳만 열리면 다른 화면이 여전히 `endDate`를 마감이라고 말합니다.** 이 값이 오가는
자리를 전부 적어 둡니다.

| | 스키마 | 화면 | 지금 |
|---|---|---|---|
| **쓰기** | `CreateProjectRequest` | 회차 생성 모달 | ❌ **없음** |
| 〃 | `UpdateProjectScheduleRequest` | 일정 수정 모달 | ✅ 18차 R5 |
| **읽기** | `ProjectDetailResponse` | 상세 개요 타임라인 · 일정 수정 **초기값** | ❌ |
| 〃 | `ProjectResponse` | OP-03 목록 「기간」 열 | ❌ |
| 〃 | `ProjectResponse`(`/projects/current`) | OP-01 대시보드 「이번 회차」 | ❌ |
| 〃 | `ClassProgressResponse` | OP-04 현황 탭 | ✅ — 단 `PLANNED`는 무응답(§7) |

1. **`CreateProjectRequest`에 `submissionDueAt` 추가**(선택 필드). 생략하면 지금처럼
   `endDate` 23:59 KST로 파생해 주시면 됩니다 — 지금 동작이 그래 보입니다.
2. **`ProjectDetailResponse`에 추가.** 없으면 `null`. **일정 수정 모달의 초기값**이라
   이것이 없으면 시각 입력을 켤 수 없습니다(고쳐도 다시 열면 비어 있음).
3. **`ProjectResponse`에도** — 목록과 대시보드가 상세와 다른 마감을 말하면 안 됩니다.

**오면 바로 켜겠습니다** — `SchedulePicker`에 시각 입력을 되살리고, 개요 타임라인과
목록이 `endDate` 대신 실제 마감을 씁니다. 회신에서 *"`endDate`에 `23:59`을 붙이지
마시라"* 고 하신 것을 그때 지킬 수 있습니다.

## 3. 🟠 R3 — `/projects/current`가 **필드 하나 때문에 안 쓰이고 있습니다**

**15차 R1로 만들어 주신 엔드포인트를 아직 한 번도 못 썼습니다.** 저희가 요청해서 신설된
것인데 놀고 있는 상태라, 정확히 무엇이 모자란지 적습니다.

### 이 블록이 목록에서 쓰는 값 — 전수

OP-01 대시보드 「이번 회차」가 목록(`GET /cohorts/{id}/projects`)에서 꺼내 쓰는 것은
**딱 다섯 가지**입니다.

| 쓰는 값 | `/projects/current`에 | |
|---|---|---|
| `projectId` · `name` · `sequenceNo` · `startDate` | ✅ 있음 | |
| `status` (→ 화면의 `진행 중` / `다음 예정 회차` / `마지막으로 끝난 회차`) | ✅ 있음 | |
| **총 회차 수** (`3차 / 6회`의 분모) | ❌ **없음** | ← **이것 하나** |

```
미니프로젝트 3차
3차 / 6회        ← sequenceNo 는 있는데 분모가 없다
```

이 하나 때문에 목록을 계속 부르고 있고, **그러면 `current`를 부를 이유가 사라집니다**
(둘 다 부르면 왕복만 늘어납니다).

### 요청 ⓐ — `totalRounds` 한 필드

```jsonc
{
  "projectId": "…", "name": "미니프로젝트 3차", "sequenceNo": 3,
  "totalRounds": 6,        // 🆕 이 기수의 전체 회차 수
  "status": "RUNNING", …
}
```

**이것만 오면 목록 조회를 걷어내고 바로 갈아탑니다.**

### 요청 ⓑ — 여유가 되시면: 진행 수치도 같이 (선택)

지금 이 블록은 **두 번 왕복**합니다.

```
① GET /cohorts/{id}/projects            ← 회차 고르기      1.9초
② GET /projects/{id}/class-progress     ← 진행 수치        ~2초
                                          합계 약 4초
```

ⓐ만 반영되면 ①이 `current`로 바뀔 뿐 **왕복 수는 그대로 2회**입니다(1.9초 + 2초).
`current` 응답에 아래가 같이 실리면 **1회로 줄어 블록이 절반 시간에 뜹니다.**

```jsonc
"progress": {
  "submittedCount": 231, "targetTraineeCount": 250,
  "analysisSucceededCount": 198, "assessedCount": 180,
  "analysisFailedTeamCount": 2,
  "reportPublished": false,
  "submissionDueAt": "2026-08-18T14:59:00Z"
}
```

전부 `class-progress`가 이미 주는 값이고, 대시보드는 **반별 내역 없이 합계만** 씁니다
(반별은 OP-04 현황 탭이 따로 부릅니다). **ⓑ는 계약이 커지는 일이라 ⓐ만이어도 좋습니다** —
다만 이 블록이 대시보드에서 가장 느린 자리라 적어 둡니다.

> 참고로 응답 크기 차이는 이 지연에서 의미가 없었습니다 — 목록 3,502B와 current 488B의
> TTFB가 사실상 같습니다(1.9초 대 1.7~2.9초). **줄일 것은 바이트가 아니라 왕복 수입니다.**

### 그동안 화면은

목록을 쓰되 **선택 규칙만 회신대로 맞췄습니다**(`RUNNING` 중 가장 늦게 시작 →
가장 이른 `PLANNED` → 마지막). 전에는 목록 순서상 첫 `RUNNING`을 골랐는데, 18차 R4로
정렬이 바뀌면서 **`?sort=`에 따라 다른 회차가 「이번 회차」가 될 수 있는** 상태였습니다.

## 4. 🔴 R4 — 교안 등록: **413은 사라졌는데 이제 500입니다**

15차 R2 회신에서 *"백엔드는 60MB 허용 중이고 막는 것은 envoy"* 라고 하셨는데,
**그 층은 풀린 것으로 보입니다.** 대신 다음 층에서 막힙니다.

### 지금 무슨 일이 나나 (`POST /api/v0/curricula?title=…`)

| 파일 | 결과 | 누가 답했나 |
|---|---|---|
| 413KB · **Chrome이 만든 진짜 PDF** | **500** | 앱(스프링 형식 본문) |
| 3MB | **502** (1회) | 프록시 |
| 4MB | **500** | 앱 |
| 5MB 이상 | **413** | **Lambda** |

**15차 때와 달라진 것** — 3MB에서 나던 `server: envoy` + `content-length: 0` 413이
**안 납니다.** 요청이 앱까지 도달하고 있습니다.

**남은 문제는 둘입니다.**

### ① 앱이 500을 냅니다 — 유효한 PDF인데도

```jsonc
{"timestamp":"…","status":500,"error":"Internal Server Error","path":"/api/v0/curricula"}
```

에러 코드가 없는 **일반 500**이라 `ApiExceptionHandler`를 안 거친 것으로 보입니다
(처리되지 않은 예외). 스펙상 이 엔드포인트의 응답은 `201 · 400 · 401` 셋뿐이라
**계약에 없는 상태**이기도 합니다.

`title` 쿼리를 빠뜨렸을 때는 정상적으로 **400**이 왔으므로 요청 형식 자체는 맞습니다
(`file` 파트 + `title` 쿼리). 서버 로그를 봐 주시면 좋겠습니다.

> 저희가 처음에 `title` 없이 보내 400을 받고 *"유효한 PDF인데 400"* 이라고 읽을 뻔했습니다.
> 필수 쿼리를 빠뜨린 저희 실수였고, 채우니 500으로 바뀌었습니다.

### ② 상한이 **Lambda 6MB**로 옮겨 갔습니다 — 실질 4.5MB

```jsonc
{"Message":"6992369 byte payload is too large for the RequestResponse invocation type (limit 6291456 bytes)"}
```

5MB 파일이 **6,992,369바이트**로 계산됩니다 — **base64로 부풀어**(×4/3) 6,291,456
한계를 넘습니다. 즉 **실제로 올릴 수 있는 파일은 4.5MB 안쪽**입니다.

교안 PDF가 수십 MB인 것이 흔해서 이 상한으로는 실무가 안 됩니다. 15차에서 이야기한
**presigned S3**가 이 층을 통째로 비켜가는 답인데, 계약 변경이라 별건으로 잡아야 합니다 —
**착수 여부만 알려 주시면 요청서를 따로 올리겠습니다.**

## 5. 🔴 R5 — 프록시가 동시 요청을 못 받습니다 (15차 R3 재발)

15차 R3에서 *"프록시 Lambda는 이 저장소 밖"* 이라고 하셔서 인프라로 넘어간 건인데,
**아직 그대로이고 증상 범위가 저희가 알던 것보다 넓습니다.**

### 🔴 스웨거 UI가 안 열리는 것이 같은 원인입니다

*"스웨거 문서가 웹에서 흰 화면만 보이고 502가 뜬다"* — **백엔드 팀도 겪고 계신 그 증상**이
이것입니다. 브라우저로 열어서 요청 하나하나를 봤습니다.

```
200  /swagger-ui/index.html                        ← 껍데기는 온다
502  /swagger-ui/index.css                         ✗
502  /swagger-ui/swagger-ui-standalone-preset.js   ✗
502  /swagger-ui/swagger-initializer.js            ✗   ← UI 를 시작할 코드
200  /swagger-ui/swagger-ui.css
200  /swagger-ui/swagger-ui-bundle.js
200  /swagger-ui/favicon-32x32.png

10건 중 6건이 502 · 화면 본문은 빈 문자열
```

브라우저가 자산을 **동시에** 받는데 그중 절반이 죽습니다. 특히
`swagger-initializer.js`가 실패하면 **UI를 시작할 코드 자체가 없어** 흰 화면이 됩니다.

### 서버는 죽지 않았습니다 — 순차는 100% 성공입니다

| 방식 | 결과 |
|---|---|
| `/v3/api-docs` 단건 | **200 · 707KB · 1.91초** |
| 같은 요청 **순차 5회** | `200 200 200 200 200` |
| 같은 요청 **동시 5개** | **`502 502 200 200 200`** |
| `OPTIONS` 동시 3개 × 3회 | 9번 중 **3번 502** |

**순차는 한 번도 안 죽고 동시에서만 죽습니다.** 서버 자체가 내려간 것이라면 순차도
실패해야 합니다.

### 증상 셋이 전부 이 한 층입니다

| 겉으로 보이는 것 | 실제 |
|---|---|
| 스웨거 UI 흰 화면 | 자산 6개가 동시에 나가 502 |
| 화면에서 랜덤한 「불러오지 못했습니다」 | 프리플라이트가 동시에 나가 502 → `net::ERR_FAILED` |
| **18차 R1의 「무응답」** | 503이 재시도를 부르고, 재시도가 동시에 나가 여기서 502 |

**18차 R1은 503을 409로 고쳐 주셔서 그 경로는 막혔지만, 이 층이 남아 있으면 다른
재시도에서 같은 일이 또 납니다.** 지금 프론트의 전역 재시도(5xx·네트워크 3회)가
언제든 이 결함을 밟을 수 있습니다.

### 요청 — 인프라 담당자에게

15차 회신에서 **동의해 주신 처방이 그대로 유효**합니다.

1. **Lambda 예약 동시성(reserved concurrency) 확인.** 순차는 되고 동시만 죽는 것은
   동시성이 1~2로 잡혀 있을 때의 전형적인 모양입니다.
2. **프리플라이트(`OPTIONS`)는 프록시가 직접 200으로 답하고 Lambda를 안 거치게.**
   본문도 인증도 없는 정형 응답이라 백엔드에 부작용이 없다는 것을 15차 회신에서
   확인해 주셨습니다.
3. **정적 자산(`/swagger-ui/*`)도 같은 이유로 Lambda를 거칠 필요가 없습니다.**

## 11. 15차 Q1 — 인원 정의, **저희가 재보니 회신대로 맞았습니다**

15차 §4에서 네 값의 모집단을 정의해 주셨는데, 9기에서 **부분합까지 전부 맞아떨어집니다.**

```
전체 225   = 활성 209 + 초대 대기 1 + 비활성 15
미배정 17  = 활성  13 + 초대 대기 1 + 비활성  3
반 배정    = 225 − 17 = 208            ← classrooms 합계(0 + 26×8)와 일치
```

명단 필터의 `활성`이 **`left_at IS NULL`(재적)** 과 같은 값(209)이고, `비활성` 15가
**이탈자**입니다. 회신의 정의(① 재적 · ③ 전량 + 초대 대기)와 정확히 맞습니다.

저희 쪽에서 잠깐 *"209와 208이 1 차이라 산술이 안 맞는다"* 고 읽었는데, 「재적」과
「반 배정」은 애초에 다른 값이고 9기에서 우연히 1만큼 갈린 것이었습니다. **회신 주신
정의가 맞습니다** — 제안하신 라벨(`재적` · `교육생` · `명단` · `이번 회차 대상`)로
화면을 고치겠습니다.

**아직 답을 못 드린 것** — 15차 §4의 🔴 진단 쿼리(①의 12명 정체)는 **저희가 운영 DB에
접근할 수 없어** 돌리지 못했습니다. 인프라·백엔드 쪽에서 확인 부탁드립니다.
