# OP-06 운영 관리 — 일어날 수 있는 모든 상황

> **이 화면을 고치기 전에 이 문서를 본다.** 무엇이 일어날 수 있고, 지금 그중 무엇이
> 처리돼 있고, 무엇이 안 돼 있나.
>
> 화면의 설계 근거는 [op-06-admin.md](op-06-admin.md), 비동기 상태 표준은
> [async-states.md](../async-states.md)가 갖는다. 여기는 **상황 목록과 실측 결과**다.
>
> **이 문서를 만든 절차는 [screen-hardening.md](../screen-hardening.md)에 있다.**
> 이 화면은 탭이 여섯이라 **탭 하나를 화면 하나로 취급한다** — 공통을 한 번 돌고,
> 탭마다 축→실측→판정→고침을 끝낼 때마다 여기에 적는다.
>
> 실측 — 2026-08-13 · 운영 계정 · 프록시 경유 · 실서버 · 9기.

## 0. 이 화면의 성격

**앞의 다섯과 규모가 다르다** — 7,226줄 · 탭 6개 · 그 아래 전체 화면 2개(반 배정 · 교안 상세).

| | OP-01~05 | OP-06 운영 관리 |
|---|---|---|
| 단위 | 화면 하나 | **탭 여섯 + 하위 화면 둘** |
| 조회 | 화면이 다 안다 | **탭이 자기 것만** — 안 연 탭은 안 부른다 |
| 개수 표기 | 화면이 센다 | **각 탭이 자기 수를 알린다**(`onCount`) — 서버에 합계 API가 없다 |
| 스코프 | `stores/cohortScope` | **`admin/_/cohortScope`**(따로 있다 — §2-4) |
| 쓰기 | 없음~5종 | **탭마다** 있다 |

```
AdminScreen         GET /cohorts?size=100          스코프 + 기수 탭이 같이 쓴다
 ├ 기수             (위 목록 재사용 — 추가 조회 0)
 ├ 반               GET /cohorts/{id}/classrooms
 ├ 명단             GET /cohorts/{id}/trainees
 ├ 매니저           GET /managers?cohortId=
 ├ 교안             GET /organizations/{id}/…       기관 전체
 └ 비용             GET /organizations/{id}/…       기관 + 기수
```

**반·명단·비용은 기수 범위, 매니저·교안은 기관 전체다.**

## 2. 실측 — 공통

### 2-0. 진입 타임라인 ✅

```
0ms      클릭 — 탭 6개 + 스켈레톤 6개가 **즉시** 선다
2250ms   GET /cohorts?size=100  200 (2187ms) → 데이터
```

**요청 1건**으로 스코프와 기수 탭을 같이 채운다. CLS **0.0002**.
OP-01~05에서 고쳤던 「진입 백지」가 여기엔 처음부터 없다 — 이 화면은 스켈레톤으로 지어졌다.

### 2-1. 탭 전환 — 크래시 0건 ✅

여섯 탭을 **클릭으로** 순회하고 왕복까지(`반→명단→매니저→교안→비용→기수→명단→기수`).
OP-04를 죽인 종류의 사고는 없다.

| 탭 | 0.5초 시점 | 첫 진입 요청 | 왕복 시 |
|---|---|---|---|
| 반 | 스켈레톤 4 | 1건 | — |
| 명단 | 스켈레톤 8 | 1건 | **3건** |
| 매니저 | 스켈레톤 7 | 1건 | — |
| 교안 | 스켈레톤 6 | 2건 | — |
| **비용** | **스피너 1** | 3건 | — |
| 기수 | 스켈레톤 5 | **0건**(스코프 목록 재사용) | 1건 |

배지 — `기수 4 · 반 9 · 명단 225 · 매니저 8 · 교안 7 · 비용(없음)`.
안 연 탭은 빈칸이고, 연 탭만 채워진다 ✅

### 2-2. ⚠ 비용 탭만 스피너였다

다섯 탭이 스켈레톤인데 **비용만 `Loading`**이었다. 같은 화면 안에서 탭마다 기다리는
모양이 다를 이유가 없다.

판정도 `cost.isLoading`이라 `enabled: false` 동안 `false`인데, 앞의 두 가드
(`!organizationId || !cohortId`)가 우연히 막고 있었다 — `enabled`가 바뀌면 조용히 깨진다.

### 2-3. ⚠ 인원이 API마다 다르다 — **산술이 안 맞는다**

| 출처 | 값 |
|---|---|
| `GET /cohorts/{id}` · `traineeCount` | **209** |
| `GET /reports/class-diagnosis` · `traineeCount` | **209** |
| `GET /cohorts/{id}/trainees` · `cohortTotal` | **225** (`unassignedCount` 17) |

탭 배지가 `명단 225`인데 OP-01 대시보드는 같은 기수를 `209명`이라고 한다 — **같은 콘솔의
두 화면이 다른 수를 말한다.**

> ⚠ 여기서 *"산술이 안 맞는다"* 고 적었다가 **§5-1에서 뒤집었다** — 조합 필터로 세니
> 전부 맞았다. 셋이 다른 것을 센다(활성 209 · 배정 208 · 전체 225).

### 2-4. ⚠ 기수 스코프가 **두 벌**이다

| | `stores/cohortScope` | `admin/_/cohortScope` |
|---|---|---|
| 쓰는 곳 | OP-01~05 | **OP-06만** |
| 조회 | `size=50` | `size=100` |
| 기본 선택 | `RUNNING` ?? 첫 번째 | `RUNNING` ?? `PLANNED` ?? 첫 번째 |
| 주소 쓰기 | **`push`** | **`replace`** |

**같은 콘솔에서 「지금 어느 기수를 보나」의 답이 둘이다.** 쿼리 키도 달라
(`size` 50 vs 100) 기수 목록을 **두 번 조회**한다.

`stores/cohortScope`의 주석에 *"admin이 아직 자기 상수를 갖고 있다 — 그쪽이 연동될 때
여기로 합친다"* 고 적혀 있는데, **그쪽은 이미 연동됐다.**

뒤로가기 규칙이 정반대인 것도 그대로 남아 있다 — 어느 쪽이 맞는지 정해야 한다.

#### 실측 — 대가가 둘 다 실재한다 (2026-08-13)

**① 들어갈 때마다 요청 하나를 버린다.** 운영 관리 진입을 6회 반복했다.

```
6/6  ✗ net::ERR_ABORTED  /cohorts?page=0&size=50    ← ①이 던진 것을 라우트 이동이 끊는다
6/6  ← 200              /cohorts?size=100          ← ②가 같은 목록을 다시 받는다 (~1.8초)
```

흔들리는 것이 아니라 **6/6 결정적**이다. 프록시 결함(22차 R5)이 아니라 우리가 만든 것이다.
`size`가 50과 100으로 달라 쿼리 키가 갈리기 때문이고, 그래서 **기수가 50개를 넘는 기관에서는
화면마다 스위처 내용이 달라진다.**

**② 뒤로가기가 기수 전환을 삼킨다.** 기수 탭에서 「이 기수로」를 두 번 눌렀다.

| 누른 것 | 주소 |
|---|---|
| 시작 | `(없음)` |
| 8기로 | `?cohort=4f459e1f…` |
| 7기로 | `?cohort=0972abc4…` |
| **뒤로 1회** | **`(없음)`** ← 8기가 아니다 |

`replace`라 히스토리에 안 쌓인다. 같은 동작이 대시보드에서는 8기로 돌아온다.

**판단: `push`로 통일하고 스토어를 하나로 합친다.** 운영 관리에서 기수를 바꾸면 반 · 명단 ·
매니저 · 비용이 **전부** 바뀐다 — 필터가 아니라 「다른 것을 보러 가는 것」이고,
`stores/cohortScope`의 주석이 이미 그렇게 적어 뒀다. 상한은 100으로 맞춘다(50이면
`개강 전 n · 진행 n · 종료 n` 집계가 잘린다).

> 합칠 때 같이 볼 것: 기수가 **100개를 넘으면 두 벌 다 깨진다.** 지금은 4개라 안 보인다.

### 2-5. 🔴 탭을 옮기면 **고른 기수가 사라진다**

기수 탭에서 10기(개강 전)를 고르고 반 탭을 눌렀다.

```
10기 선택 직후   /operator/admin?cohort=eb5afbe2…
반 탭 클릭 후    /operator/admin/classes            ← 쿼리가 통째로 없다
```

`AdminScreen`이 `navigate(\`/operator/admin/${v}\`)`로 **경로만** 넘겼다. `?cohort=`가
없어지니 `useCohortScope`의 `requested`가 `null`이 되고 `pickDefault()`가 **진행 중
기수**를 골랐다.

| 보이는 것 | 실제 |
|---|---|
| 상단 스위처 `10기` | — |
| 기수 탭 `10기 현재` | — |
| **반 탭 머리 `반 9개 9기`** | `GET /cohorts/f7011ddf…(9기)/classrooms` |
| **`개강 후에는 반 구성을 바꿀 수 없습니다`** | 10기는 개강 전인데 반을 못 만든다 |

**개강 전 기수를 골라 반을 만들려던 사람이 탭을 옮기는 순간 9기 화면을 보게 되고,
화면은 그 사실을 말해 주지 않는다.** 8기로 바꾸면 요청조차 안 나갔다(9기 캐시).

이 화면의 설계 주석이 *"기수는 `?cohort=`로 같이 실린다"* 라고 적어 뒀는데 코드가 그렇지
않았다 — **코드가 사실이라고 적어 둔 것을 재 본다**(절차)에 걸린 사례다.

> §2-4의 「두 벌」과는 다른 버그다. 저건 두 스토어가 갈린 것이고, 이건 **한 스토어가
> 입력을 잃는 것**이다. 이것이 §2-4의 뒤로가기 실측을 처음에 헷갈리게 했다.

### 2차 — 사용자가 직접 눌러 보고 알려준 것들 (2026-08-14)

**「다이얼로그를 열고 Esc만 눌러 놓고 전수라고 적었다」**는 지적을 받았다. 실제로 끝까지
누르니 **여덟 건이 더 나왔다.** 아래는 전부 눌러서 확인한 것이다.

| | 무엇이 잘못됐나 | 어떻게 고쳤나 | 다시 잰 값 |
|---|---|---|---|

### 인원 — **산술은 맞았다. 내가 틀렸다**

§2-3에서 *"`225 − 17 = 208`인데 다른 둘은 209라 산술이 안 맞는다"* 고 적었다.
**조합 필터로 전수를 세니 전부 맞는다** — 셋이 다른 것을 셀 뿐이다.

```
전체 225   = 활성 209 + 초대 대기 1 + 비활성 15
미배정 17  = 활성  13 + 초대 대기 1 + 비활성  3
반 배정    = 225 − 17 = 208          ← classrooms 합계(0 + 26×8)와 일치
활성 209   = 미배정 활성 13 + 배정 활성 196
```

| 필드 | 값 | 무엇 |
|---|---|---|
| `cohorts/{id}.traineeCount` | 209 | **활성 계정** |
| `classrooms[].traineeCount` 합 | 208 | **반 배정** |
| `trainees.cohortTotal` | 225 | **전체** |

**209와 208이 1 차이인 것은 우연이다** — 애초에 다른 값인데 9기에서 우연히 1만큼 갈렸고,
그걸 off-by-one 버그로 읽었다.

> ⚠ **하마터면 틀린 것을 백엔드에 보낼 뻔했다.** OP-02의 `sameCurriculumOnly`와 같은
> 실수다(그때도 재보니 서버가 맞았다). **「안 맞는다」고 쓰기 전에 한 번 더 센다** —
> 이 경우엔 조합 필터로 부분합을 재는 것이 답이었다.

22차는 **스펙 설명 한 줄** 요청으로 바꿨다. 다만 화면 쪽 문제는 남는다 — 탭 배지가
`명단 225`인데 대시보드는 `209명`이라, **둘 다 맞는데 사용자에게는 모순으로 보인다.**

8기(종료·현재)는 액션이 하나도 없다. 규칙이 셋 다 맞물린다.

## 5-6. 교안 — ✅ 컨트롤 14종 + 상세 화면

기수와 무관한 **기관 전체** 범위다(매니저와 같다).

### 상태 필터 — **부분합이 안 맞는데 맞다**

```
머리   분석 완료 2 · 분석 중 1 · 실패 2 · 분석 전 2   = 7
필터   전체 7 / 완료 2 / 분석 실패 2 / 분석 전 2      = 6
```

「분석 중」 1건을 고를 방법이 없다. **의도된 것이고 코드에 이유가 적혀 있다** —
`PENDING`과 `RUNNING`이 같은 라벨(`분석 중`)을 쓰는데 서버 `status`가 값 하나만 받아
둘을 한 번에 못 거른다.

**그 전제를 다시 쟀다.**

```
status=PENDING                  200 · 1건
status=RUNNING                  200 · 0건
status=PENDING&status=RUNNING   200 · 1건   ← 두 번째 값을 조용히 버린다
status=PENDING,RUNNING          400
```

전제는 그대로다. 그리고 **값을 둘 보내면 거절이 아니라 절반짜리 목록을 성공처럼 준다** —
요청서에 넣는다. `status`가 배열을 받게 되면 필터를 되살린다.

### 정렬 3종 ✅

`최근 등록순` · `이름순`(`localeCompare('ko')`로 숫자·영문·한글이 섞여도 맞는다) ·
`사용 많은 순`. 셋 다 실제로 순서가 갈린다.

### 검색 ✅ · 빈 결과 ✅

`spring` → 3행 · 공백만 → 7행(요청 안 나감) · `zzz없는` → 0행 +
`"zzz없는"에 맞는 교안이 없습니다 / 전체 7개에서 찾았습니다.`

### 등록 다이얼로그 ✅

`PDF 고르기`(accept `.pdf,application/pdf`) · 교안명 · `등록 · 분석 시작`.
**둘을 채우기 전에는 잠겨 있다**(`disabled`). 암호 걸린 파일이 왜 실패하는지 먼저 적는다.

> ⚠ **업로드 자체는 못 눌러 봤다.** 실서버가 크기와 무관하게 500이다(22차 R2 —
> 50KB짜리도 500). 다이얼로그까지만 확인했다.

### 상세 화면 — 4상태 전부 진입 ✅

| 상태 | `/sections` | 화면 |
|---|---|---|
| 완료 | 200 | 섹션 7 · 연결된 프로젝트 26 · 쪽 번호까지 |
| 분석 중 | **409** `CURRICULUM_ANALYSIS_NOT_COMPLETED` | 「분석이 아직 끝나지 않았습니다」 |
| 분석 전 | **409** 같은 코드 | 같은 문구 + `분석 시작` |
| 분석 실패 | **409** 같은 코드 | **「분석하지 못했습니다」** + 원인 + `다시 분석` |

409 셋은 **정상 처리**다 — 상태마다 다른 말을 하고, 실패를 「아직」이라고 하지 않는다.

> **`/sections`를 상태로 막지 않는다.** 「완료가 아니면 안 부른다」로 게이팅하면 상태를
> 먼저 받아야 해서 **가장 흔한 완료 케이스가 왕복 하나 늦어진다.** 지금은 셋이 병렬로
> 나가고 409는 화면이 제대로 그린다 — 그대로 둔다.

**키보드로 상세에 닿는다** ✅ — 행 클릭 말고 제목이 실제 `<a>`라 Tab → Enter로 간다.

### ⚠ 분석이 도는 중에 **또 요청할 수 있었다**

`POST /curricula/{id}/analyses`에 **「이미 진행 중」 에러 코드가 없다**(스펙의 에러가
`NOT_FOUND`·인증 둘뿐) — 돌고 있어도 202로 접수한다. 화면도 `다시 분석`을 그대로 열어
둬서, 누를 때마다 AI 분석이 한 번 더 걸린다.

**버튼을 잠그지 않았다.** `PENDING`에서 멈춰 있는 교안이 실제로 있어서, 잠그면 그것을
풀 길이 사라진다 — 여기가 유일한 출구다. 대신 **다이얼로그가 먼저 말한다.**

> 이 교안은 지금 분석 중입니다 — 다시 요청하면 **처음부터 다시** 분석합니다.
> 돌고 있는 것이 빨라지지는 않습니다. 오래 멈춰 있을 때만 누르세요.

### ⚠ 경고가 회차 이름 **18개를 나열**하고 있었다

완료 교안을 다시 분석하려니 이렇게 나왔다.

```
미니프로젝트 1차 · 미니프로젝트 2차 · … · 미니프로젝트 1차 · 미니프로젝트 2차 · …
```

여러 기수가 같은 교안을 쓰면 **같은 이름이 세 번씩** 나온다(9기·8기·7기). 이름만으로는
어느 것인지 구분이 안 되는데 문장만 길어진다. 여기서 답할 질문은 *"얼마나 넓게 쓰이나"*
이고, 어느 회차인지는 뒤의 **연결된 프로젝트 탭**이 표로 답한다.

→ `이 교안으로 응시 중인 회차가 18개 있습니다 — 9기 6개 · 8기 6개 · 7기 6개`

### ⚠ 조사가 둘 더 있었다

`{회차이름}가 {교안명}으로 응시 중입니다` — **둘 다 받침에 따라 갈린다**(`이/가` ·
`으로/로`). 서버가 주는 이름이라 미리 알 수 없다. 고정 명사 뒤로 옮기고 값은 뒤에 뒀다.

### 정원 미리보기 ✅ — **막지 않고 알린다**

| 고른 것 | 미리보기 | 막나 |
|---|---|---|
| 2명 → A반 26/30 | `26 → 28 / 30 · 2자리 남음` | 안 막음 |
| 2명 → D반 28/30 | `28 → 30 / 30 · 0자리 남음` | 안 막음 |
| **4명 → D반 28/30** | **`28 → 32 / 30 · 2명 초과`**(경고색) | **안 막음 — 의도대로** |
| 2명 → 1반 0/30 | `0 → 2 / 30 · 28자리 남음` | 안 막음 |

> 처음에 **반 카드**에서 미리보기를 찾다가 *"안 나온다"* 고 적을 뻔했다. 카드에 두지 않은
> 것이고 이유도 코드에 있다 — 고른 반에만 뜨는 값이라 비교에 안 쓰이고, 넣기 버튼 위에
> 같은 값이 또 나오기 때문이다. **두 번 틀린 곳을 쟀다**(카드 → 버튼의 3번째 부모).
> 세 번째에 화면 문자열(`N → M / C · …`)로 직접 찾아서 맞췄다.

### 선택이 **쪽을 넘어 유지된다** ✅

1쪽에서 고르고 2·3·5쪽을 돌아도 `1명 선택`이 남고, 다른 쪽에서 더 고르면 `2명 선택`이
된다. 47명을 여러 쪽에서 골라 한 번에 넣을 수 있다.

### ⚠ 완료 카드가 **`7기`라고 말하고 있었다**

전원 배정이 끝나면 뜨는 카드에 기수 이름이 **하드코딩**돼 있었다.

```
9기에서 배정을 끝냈는데   →   7기 · 미배정 없음
```

상단 제목(`반 배정 · 9기`)은 스코프에서 이름을 받는데 이 카드만 목업 값이 남아 있었다.
**방금 무엇을 끝냈는지를 화면이 틀리게 말하는 자리**라 고쳤다.

> **실데이터로는 못 봤다.** 미배정이 0이면 명단 탭의 진입 버튼 자체가 사라져서, 그 화면에
> 들어갈 방법이 없다. 응답을 가로채 `unassignedCount: 0`으로 바꿔 재현했다.
>
> ⚠ **처음엔 가로채기가 안 먹었다.** 진입 후에 걸었더니 교체가 1건(범위=전체)뿐이고
> 미배정 쪽은 캐시라 옛 화면이 그대로였다 — **정상 화면을 보고 「통과」라고 적을 뻔했다.**
> 교체 건수를 세고 있어서 걸렸다(절차의 「가로채기는 먹었는지 먼저 본다」).

### ⚠ 빈 목록이 셋 다 같은 말이었다

`조건에 맞는 사람이 없습니다` 하나로 셋을 덮고 있었다. 그중 하나는 **좋은 소식**이다.

| 상황 | 지금 |
|---|---|
| 검색에 안 걸림 | `"김철수없음"에 맞는 사람이 없습니다` + `이름 · 이메일로 찾습니다.` |
| 미배정 0 (옮기기 모드) | `미배정 교육생이 없습니다` + `이 기수는 전원 반에 들어가 있습니다.` |
| 그 밖 | `조건에 맞는 사람이 없습니다` + `범위를 「전체」로 넓혀 보세요.` |

검색어 뒤에 조사를 붙이지 않는다 — §5-4·§5-6과 같은 이유.

> 가운데 분기는 **평소엔 안 닿는다.** 미배정 0이면 화면 전체가 완료 카드로 바뀌기
> 때문이다(`finished`). 다만 그 판정이 `옮기기` 모드를 일부러 빼 놓아서, 옮기기 중에
> 범위를 `미배정만`으로 바꾸면 여기로 온다.

### 배정 실행은 **안 눌렀다**

되돌리기가 서버 API(`rollbackAssignment`)에 있긴 하지만 실서버 데이터를 바꾸는 일이라
**버튼 잠금·미리보기·경고까지만** 봤다. 모든 측정에서 **쓰기 요청 0건**을 확인했다.
