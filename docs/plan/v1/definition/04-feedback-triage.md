## 0. 읽는 법 — 두 개의 렌즈

### 렌즈 ①: "총괄 매니저" 리프레임 (가장 중요)
이 피드백 대부분은 **총괄 매니저(ORG_MANAGE) 개념이 생기기 전**에 쓰였다. 그래서 "이거 슈퍼어드민이 해야 하나, 매니저가 해야 하나"로 갈등하는 항목이 많다 — **그 갈등의 답이 대개 당시엔 없던 중간 계층(총괄 매니저)이다.**

| 당시 피드백의 고민 | 총괄 매니저 이후의 답 |
|---|---|
| "기수 추가는 슈퍼어드민 권한으로?" | **총괄 매니저**(운영 관리에서 이미 구현). 슈퍼어드민은 **기관**만 생성. |
| "프로젝트도 슈퍼어드민이 생성했으면" | **총괄 매니저**(기관 내부 커리큘럼). 슈퍼어드민이 기관 100개 커리큘럼까지 만들면 확장 불가. |
| "매니저는 모니터링·개입만" | 맞음 — 단 그 '매니저'는 **담당 매니저**. 생성은 총괄. |

권한 3층: **슈퍼어드민**(플랫폼·기관 간) → **총괄 매니저**(한 기관의 조직·커리큘럼 구성) → **담당 매니저**(배정 기수·반 모니터링·개입).

### 렌즈 ②: RealiZe이 실제로 '무엇을' 측정하는가
성장추이·회차 관련 피드백을 판단하려면 이 전제가 필요하다: RealiZe은 **프로젝트 내용 지식**을 채점하는 게 아니라, 소크라틱 5축 루브릭으로 **자기 코드를 이해·설명·방어하는 메타인지 능력**(L1~L5 depth, 반례 대응 등)을 측정한다. 이 구분이 아래 FB-L2의 핵심이다.

## 2. 항목별 다전문가 분석

### FB-L1 · 프로젝트/회차/체크포인트 용어 정의 【P0·개념】
**전문가:** 도메인 규범가(온톨로지) · 정보 설계자 · 심리측정 전문가
**현상:** M13은 "1차 · CLI 과제"처럼 **회차=프로젝트로 라벨**하고, M08은 "체크포인트(회차)"로 부른다. 세 단어가 한 층을 가리키는지 다른 층인지 미확정.
**복합 분석:**
- 도메인 규범가: 세 개는 **다른 층위**여야 혼란이 안 생긴다. 제안 온톨로지 —
  - **프로젝트(Project)** = 교육과정상 하나의 완성 산출물 단위(예: "Multi-Agent 챗봇"). 기수 내 N개.
  - **회차/체크포인트(Checkpoint)** = 그 프로젝트에 대한 **측정 이벤트 1회**. M08이 이미 "회차 종료마다 자동생성, 직전 대비 diff"로 쓰고 있으니 **체크포인트 ≡ 회차**(동의어, 하나로 통일 권장 — '회차'를 사용자 노출어, 'checkpoint'를 내부어로).
- 심리측정: 한 프로젝트가 3일이면 매일 측정할 수도(프로젝트당 다회차), 프로젝트 끝에 1회 측정할 수도(프로젝트당 1회차) 있다. **이건 제품 정책 결정**이지 용어 문제가 아니다 — 다만 결정하면 라벨을 **"프로젝트명 · N회차"로 항상 복합 표기**해야 팀원 예시("A-1회차, A-2회차, B-1회차")처럼 명확해진다.
**권고:**
1. 용어 통일: 프로젝트(산출물) ⊃ 회차(측정 이벤트, =체크포인트). '체크포인트' 단독 노출 제거, '회차'로 통일.
2. 라벨은 항상 **`{프로젝트} · {n}회차`** 복합(단독 "1차" 금지).
3. 프로젝트당 회차 수 = 정책 결정 필요.

**✅ 확정(2026-07-15) — D76 (초기 "동의어·일괄치환" 결론은 오류였고 되돌림. 아래가 최종):**
- **3층 모델:** 프로젝트(산출물, 순차) ⊃ **회차**(프로젝트 내부 라운드, 항상 "{프로젝트}·{n}회차") / **체크포인트**(각 회차의 트랙 누적 글로벌 순번, **리포트·측정계획 전용어**).
- **누적식:** 3차 프로젝트 2회차 = 앞(1차 3회차 + 2차 1회차) + 2 = **6번째 체크포인트**.
- **트랙 스코프:** 프로젝트가 반별로 달라(M13) 체크포인트 연번·성장추이·비교코호트는 **트랙(반) 단위**.
- **화면별:** report/measurement-plan = 체크포인트(+프로젝트·회차 병기) / intervention·M13·트레이니 = 회차(프로젝트 명시) / 규칙명(최종회차 B3·회차별 스냅샷 B1)·라운드 이벤트 = 회차 유지.
- **후속(별건):** 프로젝트 생성 시 회차 수 지정→트랙 체크포인트 자동파생 = FB-F5. 성장추이 X축=체크포인트 = FB-L2/E1.

### FB-L2 · 회차별 성장추이의 논리적 허점 【P0·측정 — 최대 쟁점】
**전문가:** 심리측정 전문가(구인타당도) · 학습분석 전문가 · 데이터 시각화 전문가
**현상:** "회차=프로젝트면 프로젝트마다 내용·언어가 달라(파이썬 거북이→자바 클래스), 점수 하락이 태도/능력 저하라고 단정 못 한다." 정당한 지적.
**복합 분석:**
- 심리측정(핵심): 이건 교과서적인 **구인타당도(construct validity) + 교란변수** 문제다. 두 층을 분리해야 한다.
  - (a) **측정 구인:** RealiZe은 프로젝트 *내용 숙련도*가 아니라 *자기 코드 이해·설명·반례대응(메타인지)*을 잰다. 이 구인은 **원래 내용-무관하게 설계**돼 있어 교란을 상당 부분 완화한다. "자바를 몰라도, 자기가 짠 자바 코드를 설명·방어하는 능력"은 잴 수 있다.
  - (b) **잔여 교란:** 그럼에도 낯선 언어/패러다임에선 *자기 코드를 추론하는 깊이 자체가 실제로* 떨어진다. 교란이 0은 아니다. 팀원 지적이 옳다.
- 학습분석(해법의 핵심): 교란을 없앨 순 없으니 **상대 기준(norm-referenced)으로 신호를 걸러야** 한다. **"학생은 떨어졌는데 코호트 전체도 같이 떨어졌다"면 그건 콘텐츠 난이도지 개인 위험이 아니다.** 반대로 "코호트는 유지인데 이 학생만 급락"이면 진짜 신호. → **위험 판정을 절대 점수 하락이 아니라 '코호트 대비 이탈(residual)'로 정의**하면 자바-신규 문제가 자동 상쇄된다(모두 낮으니 개인 신호 아님).
- 데이터 시각화: 성장추이 라인에 **코호트 평균 밴드**를 배경에 깔면 "내 등락 vs 전체 등락"이 한눈에 보인다. 절대 점수 축 하나만 그리면 오독을 유발.

**난이도 태그는 어떻게 붙이나 (후속 질문 — 중요):**
- **난이도는 사람이 매기는 사전 라벨이 아니라, 코호트 응답에서 나오는 사후·경험적 값이다.** IRT에서 난이도(difficulty)는 추정 파라미터지 손으로 다는 태그가 아니다. 사전 태깅("이 프로젝트 중난도")은 (1) 주관적이고 (2) **이 코호트의 사전지식을 모른다** — 파이썬만 아는 코호트엔 "중난도 자바"가 지옥. FB-L2 예시 자체가 "난이도=학습자 배경에 상대적"이라는 증거라 **사전 태깅은 자기모순**(FB-L2가 없애려던 주관 편향을 재도입).
- **그래서 별도 난이도 태그는 불필요.** 코호트 평균 밴드가 곧 경험적 난이도다 — 자바 회차에 밴드가 3.1→2.3으로 내려앉으면 그게 "어려운 회차". 위험 판정은 **잔차만** 쓰므로 태그가 아예 안 들어간다. 태그/밴드는 사람이 읽는 시각화용이고 그것마저 코호트 평균에서 공짜로 나온다.
- **부트스트랩 문제 없음:** 학생을 **같은 회차의 코호트 분포**와 비교하므로 과거 기수 데이터 불필요(기수 1호도 성립). 회차별 스냅샷(B1)이 이미 그 분포 제공.
- **유일하게 정당한 사전 속성 = 팩트 플래그**(난이도 점수 아님): 총괄이 프로젝트 생성 시 **"신규 언어/패러다임 도입 여부"** 체크. 판단이 아니라 사실이라 편향 없고, 밴드가 왜 내려갔는지 **설명**한다("코호트 급락 + 신규 언어 = 콘텐츠성").

**권고:**
1. **위험 신호 = 코호트 상대 잔차 기반**(절대 하락 아님). 전원 하락한 회차는 개인 위험으로 안 띄움. → M04/M07 판정 로직에 반영.
2. 성장추이는 **회차별**로(전체 총합 평균 지양). 각 점에 **코호트 평균 밴드** 오버레이 + 프로젝트명 + (있으면)신규 언어 팩트 플래그. **손으로 매기는 난이도 라벨은 넣지 않는다** — 밴드가 경험적 난이도.
3. 측정 구인이 '내용-무관 메타인지'임을 정의서에 명문화(백엔드가 내용 정답률로 오구현하는 것 방지 — 스냅샷 B1과 같은 급의 P0 의미론).
**확정 필요:** 예 (위험 판정을 상대 기준으로 전환 + 프로젝트에 '신규 언어 도입' 팩트 플래그 필드 추가).

### FB-L3 · M11 교육생 리스트에 팀·회차 표시 【P1·IA】
**전문가:** 정보 설계자 · 인터랙션 설계자
**현상:** 리스트에 "팀 A / 회차 응시완료"가 컬럼으로 있음. 팀·회차는 계속 바뀌므로 정적 리스트에 고정 표시가 논리적으로 어색하다는 지적. 현재 문서도 "이번 회차=가벼운 신호"라 자인.
**복합 분석:**
- IA: 리스트의 **정체성 축(누구인가)**과 **시변 상태(지금 무슨 회차에서 어떤가)**를 섞으면, 회차가 바뀔 때마다 리스트의 의미가 흔들린다. 교육생 리스트는 *명부(roster)*이지 *현황판(dashboard)*이 아니다 — 현황은 SC-M01 대시보드 소관.
- 인터랙션: 다만 "누가 지금 미제출인가"는 운영상 유용하다. 완전 제거보다 **어느 회차 기준인지 컬럼 헤더에 명시**("3회차 응시현황")하고, 팀은 **현재 회차 기준 스냅샷임을 라벨**로 못박는 절충이 낫다.
**권고:** (택1, 창립자 취향)
- **A(순수 명부):** 팀·회차 컬럼 제거, 리스트는 정체성·계정상태만. 현황은 대시보드로. ← IA 정석.
- **B(맥락 명시):** 유지하되 헤더에 **"기준: N회차"** 고정 라벨 + 팀은 "현재 회차 스냅샷" 표기. ← 실용 절충.
권고는 **A**(리스트=명부 단일 책임) + 대시보드에서 회차별 현황 제공. FB-L2의 "회차별로 봐야 의미 있다"와도 일치.
**확정 필요:** 예 (A/B).

### FB-L4 · M06 전체 문답 열람 【P2·인터랙션】
**전문가:** 인터랙션 설계자 · 평가 방법론(적응형 검사) · 노출 규범가
**현상:** "무너진 구간만 보여주나? 전체 문답 다 보고 싶다." depth 적응형(견고하면 조기종료 최소 L2 1회, 약하면 심화)이라 문답 길이가 가변.
**복합 분석:**
- 적응형 검사: depth가 적응형이라 세션마다 문답 수가 다르다(15개 강제 아님). 표면 지점이 경고색으로 튀는 현재 설계는 "어디서 막혔나" 스캔엔 최적이나, 전체 맥락 파악엔 부족.

- 노출 규범: 단 판정·근거는 **매니저 전용**(교육생 비노출) 규칙 유지 — 전체 열람은 매니저 화면에 한함.
**권고:** M06에 **"전체 문답 펼치기"** 토글 추가. 기본=경고 지점 요약, 확장=L1~L5 전체 스레드. 판정 근거는 매니저 뷰 한정.
**확정 필요:** 아니오 (설계 개선, 바로 반영 가능).

### FB-L5 · M07 개입 = push vs pull 【P1·워크플로우】
**전문가:** 운영 워크플로우 설계자 · 행동설계 전문가 · 알림 설계
**현상:** "문제→자동으로 상담리스트에 쌓임(push)" vs "문제→시그널만, 매니저가 판단해 리스트에 넣음(pull)"? 결과는 비슷하나 매니저 심리가 다름.
**복합 분석:**
- 행동설계: **push(자동 적재)**는 '일거리가 쌓인다'는 압박·알림피로를 낳고, 오탐(FB-L2의 콘텐츠성 하락)까지 리스트에 쌓이면 신뢰가 무너진다. **pull(시그널→매니저 판단)**은 자율성·통제감을 주지만, 바쁜 매니저가 방치하면 놓친다.
- 워크플로우: 이분법이 아니라 **3-state 큐**가 정석 — `감지(시그널) → 검토 대기(triage) → 개입 착수`. 시스템은 **'검토 대기'까지만 자동**으로 올리고(자동 개입 아님), 매니저가 **'개입 시작/기각(사유)'**를 누른다. 기각 사유는 FB-L2 위험로직 학습에 환류(서비스플로우의 환류 경로와 일치).
- 알림 설계: 자동 적재하되 **위험도·코호트상대성으로 정렬**하고, 콘텐츠성 하락은 하위로 강등하면 push의 압박을 줄인다.
**권고:** **하이브리드** — 감지는 자동으로 '검토 대기' 큐에 적재(push의 누락방지) + 실제 개입은 매니저 명시 액션(pull의 통제감). 기각 시 사유 → 규칙 환류. 자동 '개입 확정'은 금지(기존 P0 규칙 준수).
**확정 필요:** 예 (큐 3-state 채택).

### FB-F5 · 프로젝트·측정계획 생성 주체 【P0·권한】

**권고:**
1. **프로젝트 생성 = 총괄 매니저**(슈퍼어드민 아님). 담당 매니저 = 모니터링·개입 한정(창립자 의도 유지, 주체만 교정).
2. **측정계획(체크포인트 회차)은 프로젝트 생성 시 자동 파생** + 총괄이 조정. M03을 '생성'에서 '조정·확인'으로 재정의.
3. M02의 프로젝트 생성 UI를 총괄 권한으로 이동(운영 관리 탭 계열과 정합).
**확정 필요:** 예 (프로젝트/측정계획 생성을 총괄로 확정 — 화면 재배치 동반).

### FB-F6 · 검증 포커스 자동/수동 생성 【P1·측정설계】
**전문가:** 측정 설계자 · 도메인 규범가
**현상:** 검증 포커스(Multi-Agent→LLM·책임분리·협업구조·상태관리·Tool·프롬프트·RAG)를 프로젝트 생성 시 (a)프로젝트 연관 자동 생성 (b)총괄 직접 추가.
**복합 분석:** 둘은 배타 아님 — **자동 시드 + 수동 편집**이 정석. 프로젝트 유형에서 기본 포커스를 자동 제시(속도), 총괄이 가감(정확도). AI가 프로젝트 설명에서 포커스 후보를 추출→총괄 승인 형태면 이상적.
**권고:** 검증 포커스 = **자동 제안(프로젝트 기반) → 총괄 확정/편집**. FB-F5의 프로젝트 생성 플로우 안에 스텝으로 편입.
**확정 필요:** 아니오 (F5에 흡수).

### FB-M02a · 팀 매핑: 미배정 디폴트 + 골라담기, 신규 vs 재배정 【P1·IA】
**전문가:** 정보 설계자 · 인터랙션 설계자
**현상:** 현재 팀 구성 화면이 '이미 배정됨/미배정 디폴트 + 재배정' 형태로 보임. 제안: 전원 미배정 두고 전체 명단에서 골라 담기. + 2맥락(신규 생성 / 운영 중 재배정) 구분.
**복합 분석:** 이건 우리가 방금 확정한 **명단 기반 배정(D75)과 정확히 같은 원리** — 넓은 소스(전체 명단)에서 좁은 타겟(팀)으로 골라 담는 정방향. 팀 배정 = 반 배정(roster-assign)의 형제.
- **맥락1 최초 생성:** 팀 없음 → 전원 미배정 + 전체 명단 골라담기. (제안 채택)
- **맥락2 운영 중 재배정:** 기존 소속 이력 보존하며 이동 → 현재 소속 표시 + 이동 UI(D16 기간형 이력).
**권고:** 팀 매핑을 **명단 기반 골라담기**로 통일(roster-assign과 동일 패턴 재사용) + 2맥락 분기(신규=미배정 풀 / 재배정=소속 표시+이력 보존). FB-F4(팀 정보 표시)를 여기에 결합.
**확정 필요:** 아니오 (D75 패턴 확장 적용).

### FB-M02b · '프로젝트 매핑' 요구사항의 의미 (질문) 【P2·개념】
**전문가:** 도메인 규범가 · 측정 설계자
**현상:** "프로젝트 매핑 화면의 '요구사항'이 뭘 의미? Decision Point 추출 기준인가?" — 팀원 질문.
**복합 분석:** 검증 세션이 캘 **결정 지점(Decision Point)**의 씨앗이 프로젝트 요구사항이다. 즉 요구사항 = "이 프로젝트에서 학생이 내렸어야 할 설계 판단들"의 근거 → 소크라틱 질문 생성의 앵커. FB-F6 검증 포커스와 같은 계열(포커스=측정 축, 요구사항=질문 소재).
**권고:** '요구사항'을 **"검증 질문의 소재가 되는 프로젝트 결정 지점"**으로 정의서에 명시. FB-F6 검증 포커스와 관계 도식화.
**확정 필요:** 예 (정의 확정).

### FB-T04 · 검증 세션 답변 수정 vs 게이밍 【P0·측정/보안】
**전문가:** 측정 신뢰도 전문가 · 보안·부정방지 전문가 · 인터랙션 설계자
**현상:** 학생이 오타/실수로 '답변 완료'를 눌렀을 때 수정 버튼 요청. 반론(이미 목업 피드백에 적힘): 자유 재작성은 (1)AI가 그 답변 기반 다음 질문을 이미 던져 맥락 붕괴 (2)어려운 후속 질문 본 뒤 앞 답 유리하게 고치는 게이밍.
**복합 분석:**
- 측정 신뢰도: 소크라틱은 **답변 원문에 근거해 다음 질문·5축 채점**이 실시간 진행된다. 제출 후 자유 수정은 측정의 인과사슬을 끊는다. 반론이 정확.
- 보안: **후행 정보를 본 뒤 선행 답 수정 = 전형적 게이밍 벡터.** 막아야 함.
- 인터랙션(구제 방향은 옳음): 의도(오타·실수)는 정당하니 **전면 금지 아니라 좁은 창(window)**으로 푼다. 표준 해법 —
  - **제출 전 확인 단계**(‘답변 완료’ → "이대로 제출?" 미리보기)로 실수 클릭 원천 차단.
  - 제출 직후 **다음 질문이 생성되기 전 짧은 취소 구간**(예: 몇 초, "방금 답변 수정")만 허용. **다음 질문이 뜬 순간 잠금**(그 시점부터는 후행 정보 노출 → 수정 불가).
  - 오타 수준의 **비의미적 편집**과 내용 변경을 구분할 순 없으니, 시간창 잠금이 가장 방어적.
**권고:** **① 제출 전 확인 프리뷰(실수 방지) + ② 다음 질문 생성 전까지만 수정 가능(게이밍 차단).** 다음 질문 노출 = 하드 잠금. 전면 자유수정 불가. 이 규칙을 T04 상태·case에 명문화.
**확정 필요:** 아니오 (규칙 확정적, 반영). 단 '취소 구간 길이'는 정책 수치로 창립자 확인.
