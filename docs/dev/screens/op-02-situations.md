## 0. 이 화면의 성격

OP-01과 결정적으로 다르다.

| | OP-01 대시보드 | OP-02 분석 |
|---|---|---|
| 조회 | 셋을 **병렬**로, 블록마다 따로 | **탭마다 하나씩**, 안 보는 탭은 안 부름 |
| 상태 | 서버 응답 그대로 | **화면이 든 상태가 조회 조건**(계층·반·회차·정렬) |
| 실패 단위 | 블록 하나 | **탭 전체** |

즉 여기서 축이 곱해지는 곳은 응답이 아니라 **사용자 조작**이다. 계층 · 반 선택 · 회차
범위 · 정렬 · 비교 기수 다섯이 조합으로 조회 키를 만든다.

```
탭 = rounds  →  useRoundGrid   GET .../analytics/risk-trainees
                 (팀 계층이면 회차 목록용으로 한 번 더 — Promise.all)
탭 = cohorts →  useCohortCompare GET .../analytics/cohort-comparison
```

## 2. 실측

### 2-1. ✅ 기수 간 비교가 기본 상태에서 아무것도 안 보여줬다

화면에 처음 들어가면 이 문구가 뜬다.

```
견줄 기수를 골라 주세요
같은 교안을 쓴 기수와 같은 개념끼리 맞대어 봅니다.
```

**서버에 물어본 결과 — 고를 수 있는 기수가 실제로 있다.**

```
availableBaselineCohorts:
  10기  comparable=false
   8기  comparable=true    ← 있다
   7기  comparable=true    ← 있다
```

그런데 `baselineCohortId`를 **안 보내면 서버가 자동으로 고르지 않는다.**

```
baselineCohortId 없음                    → concepts 0건 · baselineCohort null
baselineCohortId=4f459e1f…(8기)          → concepts 7건 · baselineCohort 8기
baselineCohortId=0972abc4…(7기)          → concepts 7건 · baselineCohort 7기
```

**화면은 `compareId`를 `null`로 시작한다.** 그래서 이 탭은 **사용자가 셀렉트를 만지기
전까지 영원히 비어 있다.**

문구 자체는 정확하다("골라 주세요"). 문제는 **고를 수 있는 것이 하나뿐일 때도 고르게
한다**는 것이다 — 비교 가능한 기수가 8기·7기 둘뿐인데 사용자가 그걸 알려면 셀렉트를 열어야
한다. 탭을 열자마자 볼 수 있어야 하는 화면에서 **한 번의 조작이 항상 강제**된다.

**고침 — 안 골랐고 결과가 0건이면 한 번 더 부른다.** 서버가 준 목록의 **첫 `comparable`** 로
다시 조회한다.

```ts
if (!q.compareCohortId && r.concepts.length === 0) {
  const fallback = r.availableBaselineCohorts.find((c) => c.comparable)
  if (fallback) r = await call(fallback.cohortId)
}
```

**우리가 정렬하지 않는다.** 「어느 기수가 기본인가」는 도메인 판단이라(가장 최근? 같은
교안을 가장 많이 쓴?) 화면이 정하면 근거 없는 규칙이 코드에 박힌다 — 서버가 준 순서를
그대로 믿는다. **서버가 기본값을 고르게 되면 이 블록을 지운다**(요청서 대상).

셀렉트도 같이 고쳤다 — 화면 state만 보면 표는 8기를 그리는데 셀렉트는 `없음`이라 **둘이
다른 말을 한다.** 실제로 견준 기수(`compareCohortId`)를 보여준다.

실측: 탭을 열면 `비교 · 8기` + 개념 7건이 바로 뜬다(조회 한 번 더는 캐시된다).

### 2-2. ✅ `sameCurriculumOnly`는 정상이었다 — 관측을 잘못 읽었다

처음엔 **서버가 파라미터를 무시한다**고 봤다.

```
요청 sameCurriculumOnly=true   → 응답 sameCurriculumOnly: false
```

**그게 아니었다.** 비교 대상을 명시하고 다시 재니 정상이다.

```
baselineCohortId 없음            → same=false · concepts 0    ← 조회 자체가 안 돈 것
baselineCohortId=8기 · true      → same=true  · concepts 7
baselineCohortId=8기 · false     → same=false · concepts 7    ← 파라미터가 실제로 먹는다
```

**비교 대상이 없으면 서버가 아무것도 안 하고 응답을 기본값으로 채운다** — `sameCurriculumOnly`가
`false`인 것은 필터를 안 건 것이 아니라 **비교를 안 한 것**이다. 즉 §2-1의 증상 하나가
두 가지로 보였던 것뿐이다.

교안 버전도 확인했다 — 7개 개념 전부 `(baseline v1, target v1)`이라 실제로 같은 교안이다.

> **이 항목을 남기는 이유** — "응답 필드가 이상하다"를 백엔드 요청서에 올릴 뻔했다.
> **한 변수만 바꿔 다시 재는 것**으로 갈렸다(screen-hardening 2단계).

### 2-3. ✅ 회차가 0개인데 표 껍데기가 남았다 (D3)

응답을 비워(회차·반·팀 0) 재현했다.

```
기수 전체 › 팀        ← 반별 계층인데 «팀»이라고 쓴다(§2-4)
0개 팀
[빈 표 머리]  채점에서 빠진 사람  미응시 무효 중단
기수 전체 196명 → 채점 170        26  8  7  11
아래 색의 기준
```

**열이 하나도 없는 표를 그린다.** 「없는 것」 3종 중 어디에도 안 들어간다 — 사용자는 빈
격자를 보고 *"데이터가 왜 안 나오지"* 를 묻게 된다.

**고침 — `columns.length === 0`이면 격자 대신 「아직」**(유형 1 · 점선 · 재시도 없음).
회차가 돌면 채워지므로 다시 시도가 아무것도 바꾸지 못한다. OP-01에서 만든 판정과 같다.

### 2-4. ✅ 반별 계층인데 머리글이 「팀」이라고 썼다

위 캡처의 `기수 전체 › 팀 · 0개 팀`은 **반별 계층에서 나온 것**이다. 정상 데이터에서도
같다 — 첫 화면 머리글이 `기수 전체 › 팀 / 9개 팀`인데 실제로는 **9개 반**이다.

**원인 — 문자열로 계층을 판정했다.**

```ts
const showCount = grid.baselineName !== '기수'   // 실제 값은 '기수 전체'
```

**이 비교가 영원히 참**이었다. 그래서 머리글이 늘 「팀」이었고, **팀 계층에만 붙어야 할
칸 안 실수 표시가 반별에도 붙어 있었다**(4명 팀에서 비율이 튀는 것을 보정하려던 것이라
25명 반에는 필요 없다).

**고침 — `RoundGrid.level`을 추가해 그것으로 판정한다.** 라벨 문자열로 상태를 알아내면
문구를 바꿀 때 조용히 깨진다.

### 2-5. ✅ 실패·빈 상태에서 `0반` · `0회` · `1 – 1`

실패·빈 응답일 때 툴바가 이렇게 뜬다.

```
반 전체 0반    회차 1 – 1    등록 0회      ← 실패 시
반 전체 0반    회차 0 – 0    등록 0회      ← 빈 응답 시
```

`전체 0반`·`등록 0회`는 OP-01에서 고친 것과 같은 문제(모르는 것을 0으로 단언)인데,
**조건이 `loading`이라 실패·빈 상태에는 안 닿았다.**

**고침 — 조건을 「고를 것이 없다」로 넓힌다.** 로딩 중이든 실패든 빈 응답이든 **반 수를
모른다는 점에서 같다.**

```ts
const unknown  = loading || allClasses.length === 0
const noRounds = loading || allRounds.length === 0
```

회차 범위의 `?? 1`도 지웠다 — 회차가 없는데 `1 – 1`이라고 쓰면 1차가 있는 것처럼 읽힌다.
`null`이면 셀렉트가 `고르세요`를 그린다.

### 2-9. 🔴→✅ 진입 직후 1.8초 동안 **빨간 실패 화면** (플로우 관찰)

**§2-6에서 «성능 문제없음 · CLS 0.0009»라고 적은 직후에 나왔다.** URL로 직접 들어가면
안 보이고 **사이드바를 클릭해야** 보인다.

```
[76ms]   ⚠ 분석 결과가 표시되지 않았습니다
         화면을 새로 고쳐도 같으면 담당자에게 알려주세요.   [다시 시도]
[2.5s]   (스피너)
[7s]     실제 표
```

**OP-01과 같은 버그의 다른 형태다.** 기수가 정해지기 전에는 이 조회가 `enabled: false`라
`isLoading`이 거짓인데, 분기가 이랬다.

```ts
) : grid.isLoading ? <Loading />
) : grid.isError || !g ? <ErrorState />      // ← 값이 아직 없는 것이 실패로 떨어진다
```

**고침 — `isError`만 실패로 보고, 값이 없으면 로딩이다.** 상류를 기다리는 것은 실패가 아니다.

같이 나온 둘.

| | 무엇 | 고침 |
|---|---|---|
| 빵부스러기 `분석 › › 회차 흐름` | 기수 이름 자리가 `?? ''`로 채워져 구분자가 둘 | 있는 조각만 `filter(Boolean).join(' › ')` |
| 헤더 `기수 7기` | 셸 자리표시자 — 실제로는 9기 | `cohort={cohortName ?? ''}` (op-01 §2-13) |

고친 뒤 실제 사용자 흐름(대시보드를 보고 나서 사이드바 클릭)은 이렇다.

```
[142ms]  분석 › 9기 › 회차 흐름  (툴바까지 · 빨간 화면 없음)
[2.5s]   표
```

> **덤 — 없는 문제를 쫓을 뻔했다.** 처음엔 클릭 전 4초만 기다려서 `/cohorts`가 아직 안
> 끝난 상태로 눌렀고, 그걸 보고 *"기수 조회가 캐시가 안 된다"* 고 판단할 뻔했다. 캐시는
> 정상이었다(재호출 0건). **앞 화면을 끝까지 기다리고 재는 것**이 절차에 들어간 이유다.

### 2-10. ✅ 0~2.5초 본문이 통째로 비었다

툴바는 있는데 아래가 스피너다. **표 모양을 아는데 스켈레톤이 없다.**

OP-01보다 까다롭다 — 격자는 **열(회차 수)도 행(반 수)도 응답이 와야 안다.**

**판정 사다리를 탔다**(screen-hardening «발견 하나를 처리하는 법»).

| | |
|---|---|
| ① 우리 코드로 되나 | **된다** — 스켈레톤은 순수 프론트 |
| ② 이미 있는 응답에 값이 | 반 수·회차 수가 **이 조회에만** 있다. 첫 진입엔 못 쓴다 |
| ③ 스웨거에 다른 API | `GET /cohorts/{id}/classrooms`가 반 목록을 준다 — **1.4~1.7초** |

**③을 기각했다.** 스켈레톤 행 수 하나를 맞추려고 1.5초짜리 조회를 늘리면 **실제 데이터가
그만큼 늦어진다** — 본말전도다. 분석에서 오는 경로에는 그 조회의 캐시도 없다.

**고침 — 열은 안 그리고 행만 그린다.**

```
열이 가변  → 그리면 반드시 어긋난다  → 왼쪽 행 이름 열 + 오른쪽 빈 면
행은 고정  → 세로만 ±1행
```

`TableSkeleton`은 못 쓴다 — 그건 **열 폭 배열**을 받는 표 전용이고 격자는 열이 균등 분할이다.

**높이는 재서 박았다.** 눈대중으로 하면 어긋난다는 것을 두 번 확인했다.

```
전부 50px로 잡음   스켈레톤 576px vs 실제 434px  → 142px 부풀었다
기준선 행만 50px   696px vs 716px               →  20px
범례 자리 추가     724px vs 716px               →   8px  ✅
```

실측: 헤더 42px · **기준선 행 50px**(「아래 색의 기준」 줄이 있어 혼자 높다) · 반 행 35px ·
마지막 행 32px(아래 테두리 없음) · 범례 16px. **행 수는 반 수 + 1**이다(기준선 행).

CLS 0.0009 유지.

### 2-11. ✅ **탭 하나만 고쳤었다** — 기수 간 비교에 같은 버그가 남아 있었다

회차 흐름 탭을 다 고친 뒤 **같은 관찰을 두 번째 탭에는 안 돌렸다.** 탭을 클릭해 보니
§2-9와 **똑같은 코드**가 그대로 있었다.

```ts
) : compare.isError || !compare.data ? (   ← 값이 아직 없는 것이 실패로 떨어진다
```

그리고 3.5초 동안 **셀렉트도 본문도 빈** 채였다.

**고침 — 회차 흐름에 한 것을 그대로.**

| | |
|---|---|
| `isError`만 실패로 | 값이 없으면 로딩이다 |
| `CompareSkeleton` | 표 모양으로 자리를 잡는다 |
| 로컬 `Loading`(스피너) 삭제 | 두 탭 다 스켈레톤이라 쓸 데가 없어졌다 |

이 표는 격자보다 정직하게 그릴 수 있다 — **열이 5개로 고정**이고 행 높이도 47px 균일이다
(실측: 헤더 40px · 행 47px × 7 · 범례 45px). 행 수(개념 수)만 모르는데, 이 표가 화면 맨
아래라 어긋나도 아무것도 밀지 않는다.

```
스켈레톤 698px → 도착 716px  (18px · 탭 전환 CLS 0.0004)
```

**문구 하나도 같이 고쳤다.** 비교 대상이 없으면 서버가 `sameCurriculumOnly: false`를 주는데
(§2-2), 그때도 «교안이 바뀐 개념이 섞여 있다»고 써서 **하지도 않은 비교를 설명**하고 있었다.
견줄 행이 실제로 있을 때만 낮춘다.

> **교훈** — 탭·모드가 여럿인 화면은 **각각에 플로우 관찰을 돌려야 한다.** 한 탭에서 고친
> 것이 다른 탭에 자동으로 적용되지 않는다.

### 2-12. ✅ 컨트롤을 실제로 눌러 보니 넷이 나왔다

축으로 **적어만 두고**(C1 · 반 선택) 안 눌러 봤던 자리다. 눌러 보니 이렇게 나왔다.

| | 증상 | 원인 |
|---|---|---|
| ① | 「전체 선택/해제」가 **아무 일도 안 함** | `[]`(전체)와 `[9개 id]`(=전체)가 **같은 뜻** |
| ② | 마지막 한 반을 해제하면 **전체로 튐** | 위와 같은 원인 — `[]`가 되니까 |
| ③ | 반·회차를 다 골라도 **「골라 주세요」가 5초 남음** | 그 판정이 **응답**(`g.needs`)에 실려 왔다 |
| ④ | 계층을 바꿔도 **이전 표가 남음** | `placeholderData`가 계층을 안 봤다 |

**①②** — 「전체 보기」 하나로 바꾸고, 이미 전체면 **버튼을 안 그린다**(E7). 마지막 하나는
해제할 수 없게 잠근다 — 반 0개짜리 격자는 뜻이 없다(기준선이 곧 비교 대상).

**③** — 판정에 쓰는 값이 둘 다 **화면 상태**(고른 반·고른 회차)라 서버에 물을 일이 아니었다.
화면에서 계산하니 고르는 즉시 사라진다.

**④** — `_shared/listQuery`의 규칙 그대로다. *"같은 것의 다른 조각"* 은 유지하고
*"다른 것"* 은 유지하지 않는다 — 반별 격자와 팀 격자는 **행도 열도 기준선도 다른 표**다.

```ts
placeholderData: (prev) => (prev?.level === q?.level ? prev : undefined)
```

④를 고치다 하나 더 나왔다 — **팀 계층에서 반 칩이 `전체 1반`이 되어 다른 반으로 옮길 수
없었다.** 팀 응답이 고른 반 하나만 담는데 그것으로 선택지를 만들고 있었다(회차 목록을 따로
받는 것과 같은 이유로 전량을 쓴다).

### 2-13. ✅ 팀별에서 고르는 순서를 회차 → 반으로

**팀은 회차마다 다시 짜인다.** 그러니 *"어느 회차의 팀이냐"* 가 먼저 정해져야 반 안의 팀
목록이 뜻을 갖는다 — 고르는 순서가 곧 질문의 순서다.

| | 전 | 후 |
|---|---|---|
| 툴바 순서 | 반 → 회차 | **회차 → 반** |
| 계층 이름 | `반별` / **`팀`** | `반별` / **`팀별`** |
| 빈 상태 문구 | 「반과 회차를」 | 「회차와 반을」 |
| 팝오버 자동 열기 | 팀 전환 즉시(반) | **회차를 고른 뒤**(반) |
| 팝오버를 닫으면 | **`반별`로 튕김** | 그대로 — 격자 자리가 안내한다 |

마지막 줄이 중요하다. 전에는 「반 없이 팀 계층에 머무를 이유가 없다」고 보고 되돌렸는데,
회차를 먼저 고르는 지금은 **되돌리면 그 선택까지 사라진다.**

### 2-14. ✅ 「비교 · 없음」은 눌러도 아무 일이 없었다

기수 간 비교 셀렉트에 있던 선택지다. 고르면 `compareId = null`이 되는데, **그러면 폴백이
첫 `comparable`을 다시 고른다**(§2-1) — 즉 **누를 수는 있는데 아무것도 안 바뀐다.**

애초에 이 탭은 **견주는 것이 목적**이라 「안 견줌」은 화면을 비우는 것 말고 뜻이 없다. 뺐다.

### 2-15. ✅ 잠긴 컨트롤이 이유를 말하지 않았다

팀별로 바꾸면 계층이 달라 목록을 새로 받는데(§2-12 ④), 그동안 셀렉트가 **「고르세요」인 채로
잠겨** 있었다 — 눌러 보면 안 열리니 고장으로 읽힌다.

```
전  회차 [고르세요 ▾]   반 [고르세요 ▾]      ← 잠겨 있는데 고르라고 한다
후  회차 [불러오는 중 ▾] 반 [불러오는 중 ▾]
```

폭도 `w-24` → `w-28`로 늘렸다 — 「불러오는 중」이 잘렸다.

### 2-6. ✅ 성능은 문제없다

```
risk-trainees (기본)                   1.89s  1.88s
risk-trainees?level=TEAM               1.25s  1.28s
risk-trainees?fromRoundNo=1&toRoundNo=3 2.02s  2.18s
cohort-comparison                      1.36s  1.12s
```

**OP-01의 `/projects`(4.6초) 같은 것이 없다.** 응답도 12KB로 작고, 필터를 걸면 오히려
빨라진다(팀 계층 1.25초) — 요청이 실제로 반영된다는 뜻이다.

**CLS 0.0019** — 표 하나짜리 화면이라 블록 간 밀림이 없다.

⚠ **다만 이 측정은 URL 직접 진입이다.** 사이드바를 클릭해 들어오는 실제 경로는 §2-9를 본다.

### 2-7. ✅ 실패 문구가 원인에 맞는다

1단계에서 넣은 `errorCopy`가 이 화면에서도 그대로 동작한다.

```
500 → 분석 결과를 불러오지 못했습니다 / 잠시 후 다시 시도해 주세요  [다시 시도]
403 → 분석 결과를 볼 수 있는 권한이 없습니다 / 담당자에게 요청하세요  (버튼 없음)
```

### 2-8. ✅ 잘 돼 있어 건드리지 않는 것

- **안 보는 탭은 조회하지 않는다** — 탭 진입 시점에 처음 부른다
- **계층별 선택을 따로 기억한다** — 팀에서 고른 반이 반별로 돌아와도 안 남는다
- **팀 계층에서 회차 목록을 따로 받는다** — 안 그러면 고르는 순간 다른 회차가 사라진다
- **빈 결과의 이유가 갈린다** — "견줄 기수를 골라 주세요" vs "이 기관의 첫 기수예요"
- **`조건 변경 시 표 유지`**(`listQueryOptions`)가 두 조회에 다 걸려 있다
- **로딩 중 툴바 잠금**(2단계에서 넣음)
