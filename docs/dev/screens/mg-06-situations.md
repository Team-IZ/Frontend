# MG-06 교육생 상세 — 상황 전수

> **절차는 [screen-hardening.md](../screen-hardening.md).**
>
> 공통 축(헤더·스코프·기수 이름·빵부스러기)은
> [mg-03-situations.md](mg-03-situations.md)에서 한 번 쟀다.
>
> **조회가 셋이고 각자 도착한다** — 이 화면의 축은 거기서 나온다. 그리고 셋째는
> 사용자가 **펼쳐야** 나간다(지연 조회).

---

## 1. 조회 흐름

```
useManagerCohort()      GET /members/me/enrollments        ─┐ cohortId가 정해져야
                                                            │ 아래 둘이 시작한다
useTraineeDetail()      GET .../trainees/{id}              ─┤ 병렬 — 헤더·회차 격자
useTraineeTimeline()    GET .../trainees/{id}/timeline     ─┘ 이력(커서, size=100)

「자세히」를 펼칠 때만
useTraineeEvaluation()  GET /projects/{pid}/evaluations/{uid}   채점 근거(축별 note)
```

**둘을 하나의 로딩으로 묶지 않는다**(async-states §2-1) — 격자가 먼저 오면 먼저
그린다. 셋째는 회차마다 `projectId`가 달라 **쿼리 키가 회차별로 갈리고**, 펼친 것만
나간다(회차 6개를 미리 받으면 안 볼 것까지 6콜).

**권한 없음은 서버가 판정한다** — 담당 밖 교육생은 404(`MANAGER_SCOPE_NOT_FOUND`).
화면이 id 목록으로 가르지 않는다. ⚠ 다만 **그 404가 지금 무응답**이라(32차 R1)
카드가 뜰 일이 없고 요청 예산을 다 쓴 뒤 실패로 떨어진다.

## 2. 축

```
A. 조회 조합
  A1 셋 다 정상          A2 상세만 옴(타임라인 늦음)
  A3 상세 실패           A4 타임라인만 실패
  A5 상세 404(담당 밖)   A6 채점 근거 실패

B. 헤더
  B1 위험 배지 있음      B2 없음(riskTypeCode: null)
  B3 riskWhy에 태그(`[SEVERE]`)   B4 className: null(반 미배정)

C. 회차 격자
  C1 응시 회차 3개 이상(최근 3만)   C2 1~2개   C3 0개(아직 응시 없음)
  C4 reachLevel: null(문항 없음)     C5 notGenerated
  C6 개념 수가 회차마다 다름

D. 타임라인
  D1 이벤트 5종 전부      D2 REVIEW만 없음      D3 이벤트 0건
  D4 회차 6개(2개만 펼침)  D5 hasNext(100건 초과)
  D6 면담 recorded=false   D7 nextAction: null

E. 채점 근거(지연 조회)
  E1 펼치면 note가 온다        E2 reportPublished=false → note 전부 null
  E3 개념 이름이 안 맞아 못 찾음  E4 조회 실패    E5 접었다 폈다(캐시)

F. 값의 빈 구석
  F1 dateRange 한쪽만 있음   F2 teamName: null
  F3 hintUsedCount: null     F4 conceptId: null(개인 기여 문항)
```

**조합 수** — 6 × 4 × 6 × 7 × 5 × 4 = **20,160**.

## 3. 공통 축 (MG-03에서 잰 것은 참조만)

| | 이 화면 고유로 무엇을 묻나 |
|---|---|
| 네트워크·인프라 | 조회 **둘이 동시에** · 펼칠 때 셋째 · **404 무응답**(담당 밖 교육생) |
| 인증·세션 | 펼친 채로 토큰 만료 |

| 표현·성능 | 이벤트 15건 세로 길이 · 회차 6개 · 격자 가로 스크롤 |

## 4. 실측 · 판정 · 고침

### 4-1. 🔴 타임라인이 **13~17초**다. `size`가 무시된다

```
size=100   13474ms   14512B   회차 5 · 이벤트 15 · hasNext=false
size=20    15014ms   14512B   회차 5 · 이벤트 15
size=5     12374ms   14512B   회차 5 · 이벤트 15   ← 5를 줘도 15건이 온다

── 같은 교육생 대조군 ──
상세        2822ms    6601B
채점 근거   1546~2088ms
```

**`size`를 5로 줘도 응답이 바이트까지 같다**(14512B). 커서 페이징이라 적혀 있는데
페이지 크기가 안 걸린다 — 그래서 화면이 조절할 수단이 없다.

이벤트 15건에 13초면 **행 수 때문이 아니다.** 같은 교육생의 상세가 2.8초이므로
교육생 조회 자체가 느린 것도 아니다. → §5

> MG-05 명부(7초)와 함께 **매니저 화면에서 가장 느린 둘**이다.

### 4-2. ✅ 조회를 나눈 설계가 실제로 값을 한다

```
[201ms]    격자=있음  이력=없음(스피너)
[12000ms]  격자=있음  이력=있음
본문 높이 790 고정
```

**격자가 200ms에 먼저 그려진다.** 둘을 하나의 로딩으로 묶었으면 화면 전체가 12초
비었을 것이다(async-states §2-1). 레이아웃 시프트도 없다.

### 4-3. ⓘ `published=true`인데 `note`가 0건 — **미응시라 정상이다**

```
5차   reportPublished: true   resultStatus: NOT_ATTENDED   steps=[] · note 0건
4차   reportPublished: true   resultStatus: AVAILABLE      L3에 note 있음
```

「발행됐는데 근거가 없다」로 적을 뻔했다. **응시를 안 한 회차**라 채점할 단계 자체가
없고(`steps: []`), 그래서 근거도 없다. 화면은 그 회차를 **격자에서 이미 제외**한다
(`attended = !!attemptId`) — 펼칠 일이 없다.

> 화면의 「발행 전에는 근거가 없다」 안내는 `reportPublished=false`일 때만 뜬다.
> 이 경우와 안 겹친다.

### 4-4. ✅ 채점 근거가 축별로 정확히 붙는다

개념 이름으로 맞추는 방식이 실제로 맞는지 전수로 확인했다.

```
4차   타임라인 ["JPA 엔티티 관계 설정","계층 분리와 의존성 방향","예외 처리와 롤백 전략"]
      채점     ["JPA 엔티티 관계 설정","계층 분리와 의존성 방향","예외 처리와 롤백 전략"]  전부 맞음
5차   〃 전부 맞음
```

렌더도 맞다.

```
2단  JPA 엔티티 관계 설정   자력
     L3  트랜잭션 경계 설정에서 선택 이유까지 설명했지만, 어떤 상황에서
         이 방식이 깨지는지는 답하지 못했습니다.
1단  예외 처리와 롤백 전략   자력
     L2  무엇을 하는지까지는 설명했지만, 왜 그 구조를 선택했는지에서 막혔습니다.
```

### 4-5. ✅ 이벤트 필터 5종이 정확하다

```
전체 15건 = 이해도 확인 5 + 다시 보기 4 + 리포트 4 + 면담 2
aria-pressed 반영 · 전체로 복귀됨
```

「다시 보기 4건」이 `REVIEW`·`REVIEW_CLOSED` 둘을 한 칸에 담은 결과다(설계대로).

## 5. 요청서로 나갈 것

| 무엇 | 근거 |
|---|---|
| **타임라인 13~17초 · `size` 무시** | `size=5`로 줘도 응답이 **바이트까지 같다**(14512B · 15건). 같은 교육생 상세는 2.8초 · 채점 근거 1.5~2.1초. 커서 페이징이라는데 페이지 크기가 안 걸려 화면이 조절할 수단이 없다 |
