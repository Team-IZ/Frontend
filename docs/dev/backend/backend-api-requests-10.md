## 1. 🔴 R1 — 검증 개념을 한 번 정하면 바꿀 수 없습니다

### 관측

확정된 회차에서 개념 1건을 교체하고 저장했더니 409였습니다.

```
PUT /api/v0/projects/{projectId}/concepts   (최초 확정, 생성 시)  → 200 OK
PUT /api/v0/projects/{projectId}/concepts   (변경)                → 409
```

```jsonc
{
  "status": 409,
  "error": "DATA_INTEGRITY_VIOLATION",
  "code": "DATA_INTEGRITY_VIOLATION",
  "message": "요청을 처리할 수 없습니다. 데이터 제약 조건에 맞지 않습니다."
}
```

### 최소 재현 — **같은 값을 그대로 다시 보내도 409입니다**

바뀌는 것이 없는 요청이라 데이터를 건드리지 않고 재현됩니다.

```
① GET  /api/v0/projects/{projectId}          → concepts[].mappingId 3건을 그대로 받는다
② PUT  /api/v0/projects/{projectId}/concepts
        { "mappingIds": [ ①에서 받은 3건 그대로 ] }
   → 409 DATA_INTEGRITY_VIOLATION
```

**실제로 확인한 값** (10기 · `미니프로젝트 1차`)

```jsonc
projectId  : (10기 미니프로젝트 1차)
mappingIds : ["1f8d3d98-3f9f-3de7-0fff-221deb6a7665",
              "afbe7905-9421-5d32-bfb2-0ed0ba5f78d0",
              "312c2038-5c25-5ec0-a205-3b15ce932310"]
→ 409
```

같은 세트를 다시 확정하는 것은 **아무것도 바꾸지 않는 요청**입니다. 그것조차 409라면 교체(supersede) 경로 자체가 제약에 걸리는 것으로 보입니다 — 새 세트를 넣기 전에 기존 활성 세트를 닫지 않아 `UNIQUE`가 충돌하는 모양입니다.

### 9차 회신과 다릅니다

> §1 `confirmConcepts` — *"선택한 매핑들을 이 프로젝트의 검증개념으로 확정한다. **기존 활성 세트는 자동으로 교체(supersede)되며**, 과거 세트는 지워지지 않고 이력으로 남는다."*

**최초 확정만 됩니다.** 교체는 안 됩니다.

### 이게 저희를 막는 이유

구성 탭의 **`변경` 버튼이 아무 일도 못 합니다.** 그리고 더 큰 문제는 —

**개념 공백을 발견해도 고칠 수가 없습니다.** OP-04 현황 탭이 존재하는 이유가 *"고른 개념이 학생 코드에 없어서 물어보지 못했다"* 를 찾아 **다음 회차에 항목을 교체하는 것**인데(OP-04 §6), 교체 경로가 막혀 있으면 그 발견이 아무 데도 이어지지 않습니다.

> 화면은 실패를 정상적으로 처리합니다 — 실패 알림을 띄우고 고른 값을 유지합니다. **다만 사용자는 영원히 저장할 수 없습니다.**

### 요청

`PUT /concepts`가 **몇 번을 불러도 같은 결과가 되게** 해 주세요(멱등). 기존 활성 세트를 먼저 닫고 새 세트를 넣는 순서면 될 것 같습니다.

**같은 세트를 다시 보내는 것도 성공**이어야 합니다 — 화면이 "값이 바뀌었나"를 먼저 판정해서 걸러낼 수는 있지만, 그러면 같은 규칙이 화면과 서버 두 곳에 생깁니다.

## 2. 🔴 R2 — 프록시가 병렬 요청에서 502를 냅니다

### 관측

화면 하나가 진입할 때 조회 3~4건이 동시에 나가는데, **그중 절반이 죽습니다.** 브라우저에는 CORS 오류로 보입니다(502 응답에 `Access-Control-Allow-Origin`이 없어서입니다).

**같은 요청 4건을 프록시와 App Runner 직접 주소에 각각 두 번씩 보냈습니다.**

```
PROXY   round1:  502  200  200  200
PROXY   round2:  502  502  200  200
DIRECT  round1:  200  200  200  200
DIRECT  round2:  200  200  200  200
```

- 프록시 = `xvdanr6m362b2ge232vdmfbrny0kwakz.lambda-url.ap-northeast-1.on.aws`
- 직접 = `mmbvymzj5k.ap-northeast-1.awsapprunner.com`

**순차로 보내면 프록시도 전부 200입니다.** 동시에 보낼 때만 깨집니다.

### 원인 추정

프록시는 원래 **App Runner가 잠들어 있을 때 깨우려고** 둔 것입니다(`.env.example` 주석). App Runner가 상시 깨어 있는 지금은 그 역할이 끝났고, 오히려 동시 요청을 감당하지 못해 병목이 됐습니다.

### 요청

**둘 중 하나만 정해 주세요.**

| | 방식 |
|---|---|
| **ⓐ** | 프론트가 **App Runner 직접 주소**를 쓴다 — 프록시를 걷어낸다 |
| **ⓑ** | 프록시의 동시성 문제를 고친다 (Lambda 동시 실행 수·타임아웃 설정) |

**저희는 ⓐ를 권합니다.** 프록시가 풀던 문제(콜드 스타트)가 이미 없어졌고, 층이 하나 줄면 이런 종류의 장애도 같이 사라집니다.

> 지금은 **저희 로컬 `.env.local`만** 직접 주소로 바꿔서 검증했습니다. 팀 공용 파일(`.env.example`·`api/codegen.config.json`)은 아직 프록시를 가리키고 있어, 결정이 나오면 그때 같이 바꾸겠습니다.

## 3. 🟠 R3 — `findCohort.traineeCount`가 **항상 0**입니다

### 관측

같은 기수의 교육생 수를 세 곳에서 물었더니 한 곳만 0입니다.

```
       findCohort.traineeCount   반(classrooms) 합계   명단(trainees) total
10기            0                        0                    0
 9기            0                      208                  223
 8기            0                      208                  223
 7기            0                      208                  223
```

**`GET /api/v0/cohorts/{cohortId}`의 `traineeCount`만 0**이고, `GET …/classrooms`의 `traineeCount` 합계와 `GET …/trainees`의 `totalElements`는 정상입니다. 목록(`GET /cohorts`)의 `traineeCount`도 같이 0입니다.

> 반 합계(208)와 명단(223)이 다른 것은 **반 미배정 15명**으로 보여 정상입니다.

### 화면에서

OP-03 목록 머리의 스코프 문구가 **`8반 0명`** 으로 나옵니다. 반 개수는 맞고 인원만 0입니다.

### 요청

`traineeCount`를 실제 인원으로 채워 주세요. **어느 모집단인지도 정해 주시면** 화면 문구를 맞추겠습니다 — 반에 배정된 208명인지, 명단 전체 223명인지에 따라 `8반 208명`과 `8반 223명`이 갈립니다. 저희는 **명단 전체(223)** 가 맞다고 봅니다(스코프는 "이 기수에 속한 사람"이므로).

> **9차 §7에서 "반 개수를 안 줘서 `findClassrooms`를 한 번 더 부른다"** 고 적었는데, 이 값을 채우실 때 **반 개수(`classroomCount`)도 같이** 주시면 그 추가 조회가 없어집니다. 급하지 않습니다.

### 🟢 앞선 초안에서 철회한 요청 — 시드 데이터는 이미 충분합니다

처음에는 *"교육생·제출·응시 데이터가 없어 현황 탭을 확인할 수 없다"* 고 적었습니다. **저희가 잘못 봤습니다** — 진행 중이라 아직 제출 전인 회차(9기 6차)만 보고 판단했습니다.

**종료된 회차에는 데이터가 다 있고, 현황 탭이 전부 정상 렌더됩니다.**

```
9기 미니프로젝트 1차 — 반 8개 · 제출 26/26 · 분석 실패 4·5건 · 응시 24/26 · 담당 매니저 이름
9기 미니프로젝트 5차 — 개념 공백 경고: "테스트 경계와 대역 설계" 6개 팀 전원 미매칭
```

**개념 공백 경고까지 실제로 확인했습니다.** 시드 추가는 필요 없습니다.

## 4. 🟡 R4 — `endDate`가 `null`인 회차를 만들 수 없습니다

응답 타입은 `null`을 허용하는데(`ProjectResponse.endDate: ["string","null"]`) **생성 API가 `endDate`를 필수로 받습니다.**

```
POST /api/v0/cohorts/{cohortId}/projects
  body: { name, category, startDate, endDate }   ← endDate 필수
```

그래서 화면의 `마감 미설정` 표시 세 곳을 확인할 수 없습니다 — 목록 기간 열, 개요 `제출 마감 미설정`, 현황 `제출 마감이 정해지지 않아 학생에게 아직 열리지 않았습니다`.

### 요청

`endDate`가 `null`인 회차를 하나 넣어 주세요. **아울러 확인 부탁드립니다** — 만들 수 없는 상태를 응답 타입이 허용하는 것이 맞나요? 실제로 안 생기는 값이라면 타입에서 `null`을 빼는 편이 정확합니다(화면이 없는 분기를 그리고 있게 됩니다).

## 5. 🟡 확인 두 가지

### Q1. `counts`가 준비 중·준비됨을 가르지 않습니다

`ProjectListResponse.counts`는 세 키입니다.

```jsonc
"counts": { "PLANNED": 2, "RUNNING": 1, "CLOSED": 2 }
```

그런데 화면의 상태 필터는 **4값**입니다(9차 §14에서 `readiness`를 별도 축으로 주기로 한 그대로 — `PLANNED`를 `준비 중`·`준비됨`으로 가릅니다). 그래서 **그 두 항목만 개수를 못 씁니다.**

```
상태 · 전체 (7)      ← 됨
준비 중              ← 개수 없음
준비됨               ← 개수 없음
진행 중 (1)          ← 됨
종료 (2)             ← 됨
```

`0`으로 채우지 않았습니다 — 없는 사실을 주장하게 되고, 실제로 0건인 상태와 구분이 안 됩니다.

**`counts`를 `readiness`까지 가른 4키로 주실 수 있나요?** 예: `{ PREP, READY, RUNNING, CLOSED }`. 어렵다면 지금대로 두고 화면이 그 둘만 개수 없이 그리겠습니다 — **급하지 않습니다.**

### Q2. `ProjectConfirmedConcept.extractedName`이 `null` 가능인 이유

```jsonc
"concepts": [
  { "mappingId": "…", "teachesId": "…",
    "extractedName": "트랜잭션 경계 설정",   // 타입은 string|null
    "curriculumVersionId": "…", "pageStart": 53, "pageEnd": 55 }
]
```

**확정된 검증 개념인데 이름이 없을 수 있는 경우가 무엇인가요?** 구성 탭이 이 값을 개념 이름으로 그대로 그립니다(`ConfigTab.tsx`). `null`이 실제로 온다면 그 자리를 어떻게 쓸지 정해야 하고, 안 온다면 타입에서 빼는 편이 정확합니다.

> 후보 조회(`concept-candidates`)의 `extractedName`은 `null` 불가인데 확정본만 `null` 가능이라 갈립니다 — 같은 값이 확정되면서 사라질 수 있는 건지가 궁금합니다.

## 6. 9차 반영본 검증 결과 — **읽기·쓰기 전 경로 통과**

브라우저에서 실제로 눌러 확인했습니다. 10기에 회차를 만들고 편집하고 지우는 전 과정입니다.

### 쓰기

| | 결과 |
|---|---|
| 회차 생성(4콜 순차) | ✅ `POST projects 201` → `POST curricula 201` → `PUT concepts 200` → `PUT requirements 200` |
| 요구사항 저장 | ✅ 저장 후 상세에 `2건`으로 되읽힘 |
| 교안 연결 | ✅ `POST …/curricula 201` |
| **교안 해제** | ✅ `DELETE …/curricula/{projectCurriculumId} 204` (9차 R4) |
| 일정 수정 | ✅ `PATCH /projects/{id}` — 헤더·요약·타임라인 전부 갱신 |
| 회차 삭제 | ✅ `DELETE /projects/{id} 204` → 목록에서 빠짐 |
| **개념 변경** | 🔴 **409 — §1** |

### 읽기

| | 결과 |
|---|---|
| 상세 3배열(9차 R1) | ✅ `curricula` · `concepts` · `requirementTitles` 전부 옴 |
| 개념 출처·페이지 | ✅ 구성 탭이 `· spring_backend_v1.pdf v1 · p.28–30`을 그림 |
| 후보 10필드(9차 R2) | ✅ `sectionTitle`·`pageStart/End`·`definitionMissing`으로 **교안·섹션별 묶음** 렌더 |
| `readiness`(9차 Q1) | ✅ `PLANNED`+`PREP` → `준비 중`, `PLANNED`+`READY` → `준비됨` |
| `sort=READINESS` | ✅ 교안 0건 회차가 목록 맨 위로 |
| 목록 서버 필터 | ✅ `?search=3차&sort=READINESS` — 화면에서 거르지 않음 |
| `counts` | ✅ 세 키가 항상 옴 (다만 §5 Q1) |
| **현황 탭 전체** | ✅ 반 8개 표 · 분석 실패 `4`/`—` 구분 · 응시 `24/26` · 담당 매니저 · `담당 없음` |
| **개념 공백 경고** | ✅ `"테스트 경계와 대역 설계"가 학생 코드에서 발견되지 않습니다 · 6개 팀 전원 미매칭` |
| 삭제 제약 안내 | ✅ 이름·순번 재사용 불가를 삭제 확인 문구에 넣었습니다(9차 §10) |

**교안 잠금도 서버 규칙과 화면이 일치했습니다** — 확정 개념이 쓰는 교안은 체크박스가 잠기고, 이유와 개념 이름 3개가 그 자리에 나옵니다.

## 7. 참고 — 요청하지 않는 것

이번에도 저희가 흡수하기로 한 것들입니다.

| | 어떻게 |
|---|---|
| `findCohort`에 반 개수 없음 | `findClassrooms`를 한 번 더 불러 셉니다 |
| `class-progress`에 전체 팀 수 없음 | 분모를 지어내지 않고 **`6개 팀 전원 미매칭`** 으로 문구를 바꿨습니다 — 실제로 그렇게 렌더됩니다 |
| 개념 후보의 지난 회차 이력 | 주는 API가 없어 **표시를 뺐습니다.** 판단을 대신하던 값이 아니라 없어도 고를 수 있습니다 |
| `roundId === projectId` (임시) | 경계에서 접어 뒀습니다 — 화면이 그 가정을 모릅니다 |

### 9차 §15(마감 시각) — 저희 쪽 조치

**ⓒ로 가정하고 화면에서 시각을 걷어냈습니다.** `endDate`가 `DATE`이고 실제 마감(`submission_due_at`)과 연결돼 있지 않다고 하셨으므로, 화면이 `23:59`을 붙여 마감이라고 쓰던 것을 **날짜만 표시·입력**으로 바꿨습니다 — 받아 놓고 버리는 입력은 사용자에게 거짓말이기 때문입니다.

**ⓐ·ⓑ로 정하시면 되돌리겠습니다.** 다만 그때는 **회차 생성 API**(`project_assessment_round`)와 같이 봐야 한다는 말씀에 동의합니다.
