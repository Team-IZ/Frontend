## 1. 🔴 R1 — 목록과 상세가 다른 말을 합니다

### 관측

같은 교안(`materialId=2e390105…`)을 두 API에 물었습니다.

```
GET /organizations/{orgId}/curricula → content[].usedProjectCount   24
GET /curricula/{materialId}/projects                                 []   ← 빈 배열
```

**연결이 없는 것이 아닙니다.** 같은 교안의 섹션 조회에는 회차 라벨이 정상으로 옵니다.

```jsonc
// GET /curricula/2e390105…/sections → items[]
{ "extractedName": "예외 처리와 롤백 전략",
  "usedAsVerificationConcept": true,
  "usedRoundLabels": ["7기 미프 1차", "7기 미프 2차", "8기 미프 1차", …] }
```

검증 개념으로 쓰인 항목이 **7개**이고 각각 회차 라벨을 들고 있습니다 — 그런데
`/projects`만 빈 배열입니다.

> 대조군으로 다른 교안(`1de9d031…`)은 **목록 0 · 상세 0건**으로 일치합니다.
> 연결이 있는 쪽에서만 갈립니다.

### 화면에서

교안 목록은 **`24개 회차에서 사용 중`** 이라고 쓰는데, 그 행을 눌러 들어간 상세의
`연결된 프로젝트` 탭은 **`이 교안을 쓰는 회차가 아직 없습니다`** 라고 답합니다.

두 문장이 한 화면 전환 안에서 서로를 부정합니다.

**그리고 이것이 안전장치를 무력화합니다.** 11차 R3으로 `attendedCount`를 주신 덕에
재분석 경고를 *응시가 시작된 회차만* 으로 좁혔는데, 목록이 비면 **경고가 아예 안 뜹니다** —
7기·8기·9기가 실제로 이 교안을 쓰고 있는데 `다시 분석`을 눌러도 아무 확인이 없습니다.
경고를 좁힌 것이 오히려 위험해진 셈입니다.

### 요청

**어느 쪽이 맞는지 정해 주세요.** 저희는 `usedProjectCount=24` 쪽이 맞다고 봅니다 —
섹션 조회의 회차 라벨과 일치하기 때문입니다.

`/projects`가 세는 기준이 다른 것이라면(예: 특정 상태의 회차만) 그 기준을 설명에
적어 주시면 화면 문구를 맞추겠습니다. 다만 **같은 화면의 두 자리가 다른 기준으로
세는 것은 그대로 두기 어렵습니다** — 어느 쪽을 믿어야 할지 화면이 정할 수 없습니다.

> 11차 R3 회신에 *"연결된 회차 중 빅프로젝트가 있으면 400으로 조회 전체가 실패하던
> 것을 고쳤다"* 고 적어 주셨는데, 그 수정과 관련 있는지도 확인 부탁드립니다.

## 2. 🟡 R2 — `분석 전`만 골라 볼 수 없습니다

### 관측

교안 목록의 상태 필터는 `CurriculumAnalysisStatus` 넷입니다.

```
PENDING · RUNNING · SUCCEEDED · FAILED
```

그런데 **한 번도 분석하지 않은 교안은 이 값이 `null`입니다**(스펙 명시 · 11차 R7로
`notAnalyzedCount`를 따로 주신 그 이유). 그래서 그 교안들만 걸러 볼 수가 없습니다.

### 화면에서

11차 R7 덕분에 헤더에는 **`12개 · 분석 완료 9 · 분석 전 2`** 라고 쓸 수 있게 됐는데,
그 `분석 전 2`를 눌러 좁힐 수단이 없습니다. **알려 주고 못 찾게 두는 자리**입니다.

`분석 전`은 실제로 조치가 필요한 상태입니다 — 등록만 하고 분석을 안 건 교안은
프로젝트에 연결할 수 없어서, 운영자가 찾아서 분석을 걸어야 합니다.

### 요청

**필터 값에 `NOT_ANALYZED`(이름은 편하신 대로)를 하나 더해 주세요.**

```
?status=NOT_ANALYZED   →  analysis_status IS NULL 인 것만
```

enum에 넣기 어려우면 `notAnalyzedOnly=true` 같은 별도 파라미터여도 됩니다 —
명단의 `unassignedOnly`와 같은 모양입니다.

> **급하지 않습니다.** 지금은 헤더로 몇 개인지는 보이고, 목록에서 `분석 전` 배지로
> 눈에 띄기는 합니다. 교안이 수십 개가 되면 그때 필요해집니다.

## 3. 🟡 Q1 — 기수 응답의 반 개수

10차 R3 각주로 *"`traineeCount`를 채우실 때 반 개수도 같이 주시면 추가 조회가
없어집니다"* 라고 청했는데, `traineeCount`만 반영됐습니다.

```
CohortResponse: cohortId · organizationId · name · status ·
                startDate · endDate · traineeCount · managers
```

### 화면에서

기수 탭에서 **`반` 열을 그리지 않습니다.** 세려면 기수마다 `findClassrooms`를 불러야
하는데, 목록에 기수가 넷이면 조회가 넷 더 나갑니다.

교육생 수는 이제 나오므로 `9기 · 208명`까지는 쓰는데, 목업의 `10반 250명`에서
반 개수만 빠진 모양입니다.

### 확인

- 넣으실 계획이 있나요? 있으면 그때 열을 되살리겠습니다.
- 없으면 **열 없이 그대로 갑니다** — 지금도 화면은 성립합니다(반 탭에 가면 보입니다).

> 11차 R7에서 `findClassrooms`의 검색·`findCohorts`의 정렬을 *"페이지가 나뉘는 순간
> 말씀해 달라"* 고 하신 것과 같은 성격이라, **묶어서 판단하셔도 됩니다.**

## 4. 참고 — 11차 회신에서 저희가 답할 것

### Q1(담당 배정 시각) — 이력 엔드포인트에 동의합니다

*"지금 값을 한 줄 얹으면 그 자리가 채워진 것처럼 보여 이력 API가 더 미뤄진다"* 는
판단에 동의합니다. `담당 시작` 열은 계속 빼 두겠습니다.

**이력 조회가 필요해지는 시점**은 담당 교체가 실제로 일어나기 시작할 때로 봅니다 —
지금은 시드 데이터라 배정이 한 번뿐이라서 그 질문이 안 나옵니다.

### Q3-② — 칸을 되살렸습니다

반 추가 모달의 담당 매니저 칸을 되돌렸습니다. **사과하실 일이 아닙니다** — 저희도
설명만 보고 판단했고, 코드를 확인해 사실을 알려 주신 덕에 기능이 살아났습니다.

### R5 — 원인이 저희 짐작과 달랐습니다

중복을 *"한 회차에 반이 여럿"* 으로 짐작했는데 **서로 다른 기수**였습니다. 화면에서
접고 있던 코드가 **그 사실을 지우고 있었습니다** — 기수 이름을 붙여 주신 덕에
그대로 그립니다. 짐작을 그대로 반영하지 않고 원인을 확인해 주셔서 다행이었습니다.

## 6. 11차 반영 검증 — **열한 건 전부 확인했습니다**

브라우저에서 실제로 눌러 확인했습니다.

| | 요청했던 것 | 지금 |
|---|---|---|
| **R1** | 섹션 조회 90초 타임아웃 | ✅ **2.3초.** 7섹션짜리 교안 상세가 즉시 열립니다 |
| **R2** | 재발송이 "보냈다"고 못 함 | ✅ 운영자용 API로 바꾸고 문구를 `요청했어요` → **`보냈어요`** 로 되돌렸습니다 |
| **R3** | 재분석 경고 못 좁힘 | ✅ `attendedCount > 0`만 경고. 칩 목록을 **표로 되돌렸습니다** |
| **R4** | `cohortName` 항상 null | ✅ `9기`로 옵니다. 매니저 탭 `기수` 열이 찹니다 |
| **R5** | `usedRoundLabels` 중복 | ✅ `7기 미프 1차 · 8기 미프 1차 · …` — **접던 코드를 지웠습니다** |
| **R6** | 사유 코드가 string | ✅ enum 5값. 라벨 누락을 타입 검사가 잡습니다 |
| **R7** | 교안 상태별 개수 | ✅ 헤더가 `교안 2개 · 분석 완료 2`를 그립니다 |
| **R8** | `Manager.required` | ✅ 저희 검사기 **error 0건**이 됐습니다 |
| **Q1** | 담당 배정 시각 | 🔷 이력 엔드포인트 판단에 동의 — §4 |
| **Q2** | 개강 전 기수 정리 | ✅ 10기(개강 전)에만 `수정`·`삭제`가 붙습니다 |
| **Q3** | 안 쓰는 필드 둘 | ✅ 하나는 제거 확인, 하나는 **칸을 되살렸습니다** |

### 10차 것도 확인했습니다

`findCohort.traineeCount`가 실제 인원으로 옵니다 — 기수 탭의 `교육생` 열을
되살렸습니다.

```
10기  개강 전    0명
 9기  진행 중  208명
 8기  종료     208명
```

**재적 기준(208)이라 명단 탭의 223명과 다른 것이 정상**이라는 설명도 화면 주석에
남겼습니다 — 다음 사람이 "두 수가 왜 다르지"를 다시 묻지 않게요.

### 저희 검사기

```
error 0건 · warn 4건
```

`nullable` 규칙이 정상인 넷을 잡아서 **저희 쪽을 고쳤습니다** — 설명문 전체에서
'null'을 찾다가 *"항상 값이 있다"* 같은 부정문과 **남의 필드를 지목한 문장**을
못 걸렀습니다. 문장 단위로 판정하게 바꿨고 회귀 테스트를 붙였습니다.
