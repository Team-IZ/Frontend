## 1. 🚨 R1 — `Team.submission`·`Team.analysis`가 `required`인데 `null`입니다

**지금 저희 CI를 막고 있는 것이 이것입니다** (오퍼레이션 122 · 스키마 277 기준).

```
❌ [nullable] 설명에는 null이라 적혀 있는데 타입이 null을 허용하지 않는다 — 2건
     · Team.submission
     · Team.analysis
```

두 필드가 **`required` 목록에 있으면서 `$ref`**입니다. `$ref`는 `null`을 담을 수
없는데, 설명은 정확히 반대를 말합니다.

```jsonc
"Team": {
  "required": ["analysis", "submission", …],        // ← 반드시 온다
  "properties": {
    "submission": {
      "$ref": "#/components/schemas/Submission",    // ← null 이 못 들어간다
      "description": "아직 아무도 제출하지 않았으면 null입니다.
                      **레코드 존재가 아니라 이 값으로 미제출을 판정합니다.**"
    },
    "analysis": {
      "$ref": "#/components/schemas/Analysis",
      "description": "… 제출이 없거나 아직 분석이 걸리지 않았으면 null입니다."
    }
  }
}
```

**설명이 「이 값으로 미제출을 판정하라」고 지시하는데, 타입은 그 값이 절대 `null`이
아니라고 말합니다.** 생성 타입이 `Submission`(non-null)이 되어 컴파일러가 `null`
검사를 요구하지 않고, 런타임에 `.` 접근이 그대로 터집니다.

> **이 조합이 실제로 화면을 죽였습니다.** `TraineeRosterEntry.joinedAt`이 똑같이
> `required` + non-nullable이었는데 미배정 교육생에게 `null`이 왔고, `.slice()`가
> 명단을 통째로 날렸습니다(§4 R4). 같은 사고를 한 번 더 예약해 둔 자리입니다.

`anyOf`로 감싸 주시면 됩니다.

```jsonc
"submission": {
  "anyOf": [{ "$ref": "#/components/schemas/Submission" }, { "type": "null" }],
  "description": "…"
}
```

`required`에 그대로 두셔도 됩니다 — **「키는 항상 있다, 값은 null일 수 있다」**가
정확한 표현이고, 저희 화면은 그 뜻으로 그립니다.

## 2. 🔴 R2 — 교안 등록: **413은 사라졌는데 이제 500입니다**

15차 R2 회신에서 *"백엔드는 60MB 허용 중이고 막는 것은 envoy"* 라고 하셨는데,
**그 층은 풀린 것으로 보입니다.** 대신 다음 층에서 막힙니다.

### 지금 무슨 일이 나나 (`POST /api/v0/curricula?title=…`)

| 파일 | 결과 | 누가 답했나 |
|---|---|---|
| **50KB** | **500** (1.4초) | 앱(스프링 형식 본문) |
| 413KB · Chrome이 만든 진짜 PDF | **500** | 앱 |
| **3.5MB** | **500** (2.3초) | 앱 |
| 4MB | **500** | 앱 |
| 5MB 이상 | **413** | **Lambda** |

**15차 때와 달라진 것** — 3MB에서 나던 `server: envoy` + `content-length: 0` 413이
**안 납니다.** 요청이 앱까지 도달하고 있습니다.

🔴 **그리고 2026-08-13 재측정에서 하나가 더 분명해졌습니다 — 크기 문제가 아닙니다.**
**50KB짜리도 500입니다.** 앞서 「4MB에서 500」이라 적어 크기 경계처럼 보였는데,
작은 파일로 내려도 똑같이 500입니다. 즉 상한(②)과 별개로 **업로드 자체가
어떤 크기에서도 안 됩니다.**

**남은 문제는 둘입니다.**

### ① 앱이 500을 냅니다 — 유효한 PDF인데도

```jsonc
{"timestamp":"…","status":500,"error":"Internal Server Error","path":"/api/v0/curricula"}
```

에러 코드가 없는 **일반 500**이라 `ApiExceptionHandler`를 안 거친 것으로 보입니다
(처리되지 않은 예외). 스펙상 이 엔드포인트의 응답은 `201 · 400 · 401` 셋뿐이라
**계약에 없는 상태**이기도 합니다.

`title` 쿼리를 빠뜨렸을 때는 정상적으로 **400**이 왔으므로 요청 형식 자체는 맞습니다
(`file` 파트 + `title` 쿼리). 서버 로그를 봐 주시면 좋겠습니다.

**이것이 지금 저희 쪽 최대 막힘입니다.** 교안을 못 올리니 회차 생성 흐름 전체
(교안 등록 → 분석 → 회차에 연결 → 개념 확정)를 실데이터로 못 돌립니다.

> 저희가 처음에 `title` 없이 보내 400을 받고 *"유효한 PDF인데 400"* 이라고 읽을 뻔했습니다.
> 필수 쿼리를 빠뜨린 저희 실수였고, 채우니 500으로 바뀌었습니다.

### ② 상한이 **Lambda 6MB**로 옮겨 갔습니다 — 실질 4.5MB

```jsonc
{"Message":"6992369 byte payload is too large for the RequestResponse invocation type (limit 6291456 bytes)"}
```

5MB 파일이 **6,992,369바이트**로 계산됩니다 — **base64로 부풀어**(×4/3) 6,291,456
한계를 넘습니다. 즉 **실제로 올릴 수 있는 파일은 4.5MB 안쪽**입니다.

교안 PDF가 수십 MB인 것이 흔해서 이 상한으로는 실무가 안 됩니다. 15차에서 이야기한
**presigned S3**가 이 층을 통째로 비켜가는 답인데, 계약 변경이라 별건으로 잡아야 합니다 —
**착수 여부만 알려 주시면 요청서를 따로 올리겠습니다.**

## 3. 🔴 R3 — 502는 사라졌는데, 이제 **Lambda 동시 실행 한도**에 걸립니다

15차 R3(프록시 502)이 **다른 코드로 바뀌었습니다.** 502는 더 안 나옵니다.

```
/v3/api-docs  동시 5 × 4판   →  200 ×20 전부 성공 ✅
              순차 5        →  200 ×5
```

**대신 동시 요청이 8을 넘으면 429가 옵니다.**

```
동시  3   200 200 200
동시  5   200 200 200 200 200          ← 여기까지 안전
동시  8   429 200 200 200 200 200 200 200
동시 12   429 429 429 429 429 200 …    ← 5건만 통과
```

429 본문이 저희 에러 규약이 아니라 **AWS 것**입니다.

```json
{ "Reason": "ConcurrentInvocationLimitExceeded", "Type": "User", "message": "Rate Exceeded." }
```

**즉 앱이 막는 것이 아니라 Lambda 동시 실행 한도(≈5)입니다.** 예약 동시성이 아주 낮게
잡혀 있는 것으로 보입니다.

### 왜 지금 말씀드리나

- **스웨거 UI가 안 열리던 것이 이것입니다.** 자산 10개를 동시에 받는데 **3개가 429**로
  떨어집니다(실측) — 그래서 흰 화면이었습니다. 502가 아니라 429였을 뿐 원인은 같습니다.
- **저희 화면은 지금은 안전합니다.** 한 화면이 동시에 2~4건을 부릅니다. 다만
  운영 관리처럼 탭이 여섯인 화면이나, 대시보드 블록이 늘어나면 곧 닿습니다.
- **`Retry-After` 헤더가 없습니다.** 저희 계약(`_contract/errors.ts`)은 429에서
  그 값으로 카운트다운을 그리게 돼 있는데, 없으면 *"잠시 후 다시"* 밖에 못 씁니다.

### 부탁

1. **예약 동시성을 올려 주세요** — 최소 20~30이면 지금 화면들은 여유가 생깁니다.
2. 한도를 유지하셔야 한다면 **`Retry-After`를 실어 주세요.** 그러면 화면이 정확한
   시간을 말하고, 그 시간에 맞춰 한 번만 재시도합니다.
3. 429 본문을 저희 에러 규약(`{ code, message }`)으로 감싸 주시면
   `RATE_LIMITED` 하나로 화면이 분기합니다. 지금은 AWS 원문이라 코드가 없습니다.

## 4. 🔴 R4 — 명단에 `required`인데 `null`인 필드가 **10개** 남았습니다

**25개에서 10개로 줄었습니다.** 매니저·교안은 다 고쳐 주셨습니다 — 감사합니다.

| 스키마 | 이전 | 지금 |
|---|---|---|
| `ManagerRosterEntry` | 4개 | ✅ **0개** (8행 전수) |
| `CurriculumCatalogItem` | 2개 | ✅ **0개** (7행 전수) |
| **`TraineeRosterEntry`** | 21개 | **10개** (100행 전수) |

### 남은 10개

```
joinedAt                    100행 중 12행이 null   ← 이것이 화면을 죽였습니다
assessmentRoundId           100/100
attemptId                   100/100
roundResultStatus           100/100
rowAggregationStatus        100/100
matchedRiskTypeCodes        100/100
conceptResultItems          100/100
lowStageConceptCount        100/100
expectedConceptCount        100/100
excellentOccurrenceCount    100/100
```

### ① `joinedAt` — 실제로 화면을 통째로 날렸습니다

반 필터를 「미배정」으로 놓으면 화면이 사라졌습니다. `required` 문자열이라
`.slice(0, 10)`을 바로 불렀는데 **미배정 교육생에게는 값이 없습니다.**
라우터 errorElement가 화면을 먹어서 「데이터가 없다」가 아니라 **「아무것도 없다」**로
보였습니다. 저희 쪽은 막아 뒀지만, **선언이 사실과 다른 것은 그대로입니다.**

미배정에는 등록일이 없는 것이 맞다면 **`nullable`로 선언**해 주세요.

### ② 회차 지표 9개 — 전부 `null`입니다

서버가 고른 회차(미니프로젝트 6차)가 아직 제출 0건이라 값이 없는 것으로 보입니다.
**그렇다면 그것이 정상 상태이고, 정상 상태를 담을 수 있게 선언돼야 합니다.**

지금은 `required` + non-nullable이라 생성 타입이 전부 non-null이 됩니다 —
`joinedAt`과 **똑같은 사고를 9개 더 예약해 둔 자리**입니다.

### 부탁

`required`에 그대로 두시고 **타입만 `null`을 허용**해 주세요.

```jsonc
"joinedAt": { "type": ["string", "null"], "format": "date" }
"matchedRiskTypeCodes": { "anyOf": [{ "type": "array", … }, { "type": "null" }] }
```

**「키는 항상 있다, 값은 null일 수 있다」**가 정확한 표현이고, 저희 화면은 그 뜻으로
「아직 없음」을 그립니다. §1의 `Team`도 같은 부탁입니다.

## 5. 🔴 R5 — 마감 시각: **생성에서 못 받고, 어디서도 못 읽습니다**

**18차 R5를 ⓑ안으로 만들어 주셔서 감사합니다.** 그런데 붙이려고 보니 **입구도 출구도
반쪽**이라, 지금 화면이 **틀린 마감을 그리고 있습니다.**

### 🔴 먼저 — 화면이 실제로 틀린 값을 보여주고 있습니다

9기 회차 전부의 `endDate`와 실제 마감을 대조했습니다.

| 회차 | `endDate` | `class-progress.submissionDueAt` | |
|---|---|---|---|
| 6차 (RUNNING) | 2026-08-21 | `2026-08-21T14:59:00Z` = 23:59 KST | 같음 |
| 1~4차 (CLOSED) | 각각 | 각 `endDate` 23:59 KST | 같음 |
| **5차 (CLOSED)** | **2026-07-31** | **`2026-08-11T18:00:00Z`** = **8/12 03:00 KST** | **12일 차이** |

**회차 상세 화면은 「제출 마감 2026-07-31」이라고 말합니다.** 실제 마감은 8월 12일입니다.

`endDate`와 마감이 **자동으로 연결되지 않는다**고 회신에서 짚어 주신 그대로인데,
화면이 읽을 값이 없어서 `endDate`를 마감이라고 계속 쓰고 있었습니다.

### 입구 — 생성에 `submissionDueAt`이 없습니다

```
CreateProjectRequest          name · category · startDate · endDate          ← 없음
UpdateProjectScheduleRequest  startDate · endDate · submissionDueAt          ← 있음
```

**회차를 만들 때는 마감 시각을 정할 수 없고**, 만든 뒤 일정 수정으로 다시 들어가야 합니다.
생성 모달에서 시작·마감을 고르는 흐름인데 시각만 다른 화면에서 정하는 것은 어색합니다.

> 18차 R5를 저희가 *"회차 기간에 시각이 없습니다"* 로만 적어 **생성을 명시하지 않은 것**이
> 원인입니다. 죄송합니다.

### 출구 — 상세·목록에서 못 읽습니다

| 스키마 | `submissionDueAt` |
|---|---|
| `ClassProgressResponse` | ✅ — **현황 탭 전용** |
| `CurrentRoundResponse` · `MySubmissionResponse` | ✅ — 교육생 화면 |
| **`ProjectResponse`**(목록·이번 회차) | ❌ |
| **`ProjectDetailResponse`**(상세) | ❌ |

마감을 **정하고 보여주는 자리**는 회차 상세인데, 그 화면이 읽는 것은
`GET /projects/{projectId}`입니다. `class-progress`는 **현황 탭의 조회**이고
**개념 3건이 확정된 뒤에만** 값이 있습니다 — 일정을 정하는 시점에는 대개 없습니다.

게다가 위 5차 사례처럼 **`PLANNED` 회차는 `class-progress`가 아예 응답하지 않습니다**(§6 R6).

### 요청 — 쓰는 자리를 전수로 적습니다

**한 곳만 열리면 다른 화면이 여전히 `endDate`를 마감이라고 말합니다.** 이 값이 오가는
자리를 전부 적어 둡니다.

## 10. 🟠 R10 — `/projects/current`가 **필드 하나 때문에 안 쓰이고 있습니다**

**15차 R1로 만들어 주신 엔드포인트를 아직 한 번도 못 썼습니다.** 저희가 요청해서 신설된
것인데 놀고 있는 상태라, 정확히 무엇이 모자란지 적습니다.

### 이 블록이 목록에서 쓰는 값 — 전수

OP-01 대시보드 「이번 회차」가 목록(`GET /cohorts/{id}/projects`)에서 꺼내 쓰는 것은
**딱 다섯 가지**입니다.

| 쓰는 값 | `/projects/current`에 | |
|---|---|---|
| `projectId` · `name` · `sequenceNo` · `startDate` | ✅ 있음 | |
| `status` (→ 화면의 `진행 중` / `다음 예정 회차` / `마지막으로 끝난 회차`) | ✅ 있음 | |
| **총 회차 수** (`3차 / 6회`의 분모) | ❌ **없음** | ← **이것 하나** |

```
미니프로젝트 3차
3차 / 6회        ← sequenceNo 는 있는데 분모가 없다
```

이 하나 때문에 목록을 계속 부르고 있고, **그러면 `current`를 부를 이유가 사라집니다**
(둘 다 부르면 왕복만 늘어납니다).

### 요청 ⓐ — `totalRounds` 한 필드

```jsonc
{
  "projectId": "…", "name": "미니프로젝트 3차", "sequenceNo": 3,
  "totalRounds": 6,        // 🆕 이 기수의 전체 회차 수
  "status": "RUNNING", …
}
```

**이것만 오면 목록 조회를 걷어내고 바로 갈아탑니다.**

### 요청 ⓑ — 여유가 되시면: 진행 수치도 같이 (선택)

지금 이 블록은 **두 번 왕복**합니다.

```
① GET /cohorts/{id}/projects            ← 회차 고르기      1.9초
② GET /projects/{id}/class-progress     ← 진행 수치        ~2초
                                          합계 약 4초
```

ⓐ만 반영되면 ①이 `current`로 바뀔 뿐 **왕복 수는 그대로 2회**입니다(1.9초 + 2초).
`current` 응답에 아래가 같이 실리면 **1회로 줄어 블록이 절반 시간에 뜹니다.**

```jsonc
"progress": {
  "submittedCount": 231, "targetTraineeCount": 250,
  "analysisSucceededCount": 198, "assessedCount": 180,
  "analysisFailedTeamCount": 2,
  "reportPublished": false,
  "submissionDueAt": "2026-08-18T14:59:00Z"
}
```

전부 `class-progress`가 이미 주는 값이고, 대시보드는 **반별 내역 없이 합계만** 씁니다
(반별은 OP-04 현황 탭이 따로 부릅니다). **ⓑ는 계약이 커지는 일이라 ⓐ만이어도 좋습니다** —
다만 이 블록이 대시보드에서 가장 느린 자리라 적어 둡니다.

> 참고로 응답 크기 차이는 이 지연에서 의미가 없었습니다 — 목록 3,502B와 current 488B의
> TTFB가 사실상 같습니다(1.9초 대 1.7~2.9초). **줄일 것은 바이트가 아니라 왕복 수입니다.**

### 그동안 화면은

목록을 쓰되 **선택 규칙만 회신대로 맞췄습니다**(`RUNNING` 중 가장 늦게 시작 →
가장 이른 `PLANNED` → 마지막). 전에는 목록 순서상 첫 `RUNNING`을 골랐는데, 18차 R4로
정렬이 바뀌면서 **`?sort=`에 따라 다른 회차가 「이번 회차」가 될 수 있는** 상태였습니다.

## 11. 🟠 R11 — 비용 `previousTotal`이 기수로 안 걸러집니다

> 모순된 문장이 나왔습니다 — 반올림해 0이 되는 양수는 `<$1`로 씁니다.

```jsonc
expectedConceptCount · excellentOccurrenceCount · conceptResultItems
```

`rounds`는 **실제로 6건이 옵니다.** 다만 행의 회차 지표 10개는 **100행 전부 `null`**
입니다(서버가 고른 6차가 아직 제출 0건이라 그럴 것으로 보입니다).

**저희 오퍼레이터 명단 탭에는 회차 드롭다운이 없습니다.** 스펙 설명이 *"화면의
'회차 · 미프 N차' 드롭다운"* 이라고 특정 화면을 가리키는데, 그것이

- **매니저 교육생 목록(MG-05)** 이면 → 저희는 안 건드리면 됩니다
- **오퍼레이터 명단(OP-06)** 이면 → 저희가 드롭다운과 지표 열을 붙여야 합니다

어느 쪽인지만 알려 주세요. `matchedRiskTypeCodes`·`lowStageConceptCount` 같은 위험 판정
값이라 매니저 쪽으로 보이는데, `unassignedOnly`가 「오퍼레이터 전용」이라 한 엔드포인트를
둘이 나눠 쓰는 구조여서 확신이 안 섭니다.
