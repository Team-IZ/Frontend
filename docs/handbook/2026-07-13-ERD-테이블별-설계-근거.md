# ERD 테이블별 설계 근거 — IZ 스키마 49개 테이블 전체

앞 문서(`2026-07-13-ERD-처음-읽는-법.md`)가 "테이블·PK·FK가 뭔지"를 가르쳤다면, 이 문서는 그 도구로 **우리 프로젝트 49개 테이블 전부**를 하나씩 훑는다. 각 테이블마다 세 가지를 답한다 — ① 이게 왜 별도 테이블로 존재하는가(안 나누면 뭐가 문제인가) ② 컬럼 하나하나가 왜 필요한가 ③ 어디를 가리키고(FK) 관계가 몇 대 몇인가. 근거는 전부 기능명세서 발췌(`p0-fr-source.md`)와 데이터 계약(`data-contract.md`)에서 인용한다 — 추측이 아니라 문서 대조다.

49개를 아무 순서 없이 훑으면 못 따라간다. 그래서 **기능 단위 8개 묶음**으로 나눈다. 이 순서가 곧 제품이 돌아가는 순서와도 거의 같다: 기관이 있고 → 기수·팀·계획을 짜고 → 학생이 제출하고 → AI가 판단지점을 뽑아 채점하고 → 위험 시그널이 나오면 개입하고 → 교안과 매핑하고 → 리포트를 만들고 → 그 위에 알림·로그가 깔린다.

| 묶음 | 테이블 수 | 한 줄 요약 |
|---|---|---|
| A. 조직·인증·권한 | 8 | 누가(기관·계정) 무엇을(role) 할 수 있는가 |
| B. 기수·팀·측정 계획 | 8 | 몇 회차를, 누구 대상으로, 무엇을 기준으로 측정할지 |
| C. 프로젝트·제출·기여 | 7 | 학생이 뭘 냈고, 그중 자기 몫이 뭔지 |
| D. 판단지점·채점·세션 | 10 | 제품의 심장 — 코드에서 질문을 뽑고 채점하는 엔진 |
| E. 시그널·개입·상담 | 8 | 위험을 감지하고 매니저가 손 쓰는 흐름 |
| F. 교안·매핑 | 4 | 취약점을 교안 어디로 연결할지 |
| G. 리포트 | 2 | 집계 결과를 굳혀서 문서로 |
| H. 운영·알림·AI 사용량 | 2 | 알림 발송·AI 호출 비용 추적 |

표기 규칙은 앞 문서와 같다: 구분 칸에 `PK` 기본키, `FK → 테이블`이면 외래키(가리키는 대상), 비어 있으면 일반 컬럼.

---

## A. 조직·인증·권한 (8개)

이 묶음의 존재 이유 하나로 요약: **"누가"와 "그 사람이 어느 기관 소속인가"를 완전히 분리된 두 개의 체크로 만든다.** `AUTH-09`(RBAC)가 이걸 명시한다 — *"역할 권한과 별도로 SYS-02 org_id 소속 범위 검증"*.

### organization

**존재 이유**: 이 서비스를 쓰는 교육기관(부트캠프) 하나. 멀티테넌시의 뿌리 — 이 테이블의 PK(`org_id`)가 다른 거의 모든 테이블에 FK로 퍼진다.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | org_id | 이 기관의 유일한 이름표 |
| | name | 기관 이름 |
| | status | 계정 상태 (기본값 ACTIVE) |
| | retention_until | 삭제 후 보존 마감일 |
| | deleted_at | 소프트 삭제 시각 |

`retention_until`·`deleted_at`이 왜 있나: `SYS-01`이 *"삭제는 soft-delete 후 보존기간 경과 시 파기 ... 보존기간 경과 전 파기 요청 발생 시 파기 차단"*이라고 명시한다. 기관을 실제로 `DELETE`하면 학생·매니저의 전체 이력이 함께 사라지므로, 먼저 "죽었다고 표시만"(`deleted_at`) 하고 일정 기간 뒤에야 진짜 지운다.

### app_user

**존재 이유**: 로그인하는 사람 — 매니저든 교육생이든 슈퍼어드민이든 전부 이 한 테이블에 있다. 셋을 별도 테이블로 안 나눈 이유는, 로그인·비밀번호·이메일 같은 "계정으로서의 속성"은 역할과 무관하게 완전히 동일하기 때문이다. 역할별로 달라지는 속성(예: 매니저의 담당 기수)은 다른 테이블(`cohort_member` 등)이 담당한다.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | user_id | 유일한 이름표 |
| FK → organization | org_id | 어느 기관 소속인가 |
| | email | 로그인 이메일 (CITEXT = 대소문자 구분 없이 비교) |
| | password_hash | 암호화된 비밀번호 (평문 저장 금지) |
| FK → role | role_id | 매니저/교육생/슈퍼어드민 중 무엇인가 |

`AUTH-01`·`AUTH-03`이 정확히 이 컬럼들을 요구한다 — *"비밀번호 해시 생성"*, *"role=MANAGER, 소속 org_id 기준 계정 생성"*.

### role / permission / role_permission

**존재 이유 (셋이 세트)**: "역할"과 "할 수 있는 일"을 직접 연결하지 않고, 그 사이에 `role_permission`이라는 다리를 하나 더 놓는다. 이게 바로 **RBAC(역할 기반 접근 제어)**의 표준 모양이다.

**role**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | role_id | |
| | code | MANAGER/TRAINEE/… |
| | name | |

**permission**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | permission_id | |
| | resource | 권한이 적용되는 대상 자원 |
| | operation | 허용되는 작업 |

**role_permission** (역할과 권한을 잇는 다리)

| 구분 | 컬럼 |
|---|---|
| PK, FK → role | role_id |
| PK, FK → permission | permission_id |

**왜 role에 권한을 직접 안 넣나**: `app_user.role_id`에 "매니저는 이런이런 권한들"을 하드코딩하면, 나중에 "팀장" 같은 새 역할이 생길 때마다 코드를 고쳐야 한다. `role_permission`을 별도 다리로 두면 **역할-권한 매핑을 데이터로 바꿀 수 있다** — 코드 배포 없이 운영자가 조정 가능하다. `AUTH-09` 비고란이 이걸 그대로 설계 원칙으로 적어뒀다: *"권장 permission code 예: ORG_MANAGE, SCORE_REVIEW... NIST식 사용자-역할-권한 분리 구조를 기준으로 역할은 권한 묶음으로 관리."*

### one_time_token / refresh_token

**존재 이유 (둘을 나눈 이유)**: 둘 다 "토큰"이지만 완전히 다른 생명주기를 갖는다. `AUTH-01`·`AUTH-02`·`AUTH-06`이 요구하는 건 "이메일 인증·초대·비밀번호 재설정"용 **1회용** 토큰이고, `AUTH-03`이 요구하는 건 "로그인 세션 유지"용 **여러 번 갱신되는** 토큰이다.

**one_time_token**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | token_id | |
| FK → organization | org_id | |
| FK → app_user | user_id | nullable — 가입 전엔 아직 계정이 없음 |
| | target_email | 토큰이 어느 이메일 대상인가 |
| | purpose | 가입/인증/재설정 중 무엇인가 |
| | expires_at | 만료 시각 |
| | used_at | 사용 완료 시각 (재사용 방지) |

**refresh_token**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | token_id | |
| FK → app_user | user_id | |
| | issued_at / expires_at / revoked_at | |
| | user_agent / ip | 발급 클라이언트 추적 |

`user_id`가 `one_time_token`에서는 nullable인 이유: `AUTH-01`(회원가입) 흐름에서는 **토큰을 받는 시점에 아직 계정이 없다** — 이메일만 있고 계정은 가입 완료 후에 생긴다. `refresh_token`이 `user_agent`·`ip`를 남기는 이유는 `AUTH-03`이 *"Refresh Token JWT ... DB 저장"*, `AUTH-04`(로그아웃)가 *"DB Refresh Token과 쿠키 토큰 불일치 발생 시 토큰 폐기·보안 로그 기록"*을 요구하기 때문 — 도난된 세션을 나중에 추적하려면 어느 클라이언트에서 발급됐는지 남아 있어야 한다.

### audit_log

**존재 이유**: "누가, 언제, 무엇을, 어떻게 바꿨는가"를 기록하는 감사 로그. `GOV-02`(자동확정 금지)가 요구하는 핵심 인프라다.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | audit_log | (이름이 테이블명과 같은 건 오타로 보임 — audit_log_id가 맞다) |
| FK → organization | org_id | |
| FK → app_user | actor_id | 누가 했나 |
| | action | 수행한 행위 |
| | resource_type | 어떤 종류의 자원인가 (예: "score", "intervention") |
| | resource_id | 그 자원의 구체적 ID |
| | before / after | 변경 전후 데이터 (JSONB — 자원 종류마다 모양이 다르므로) |
| | reason | 사유 |

`resource_type` + `resource_id` 조합으로 대상을 가리키는 이유: 감사 대상이 `score`도 되고 `intervention`도 되고 `view_setting`도 된다 — **대상마다 별도 FK 컬럼을 두면 컬럼이 무한히 늘어난다.** 대신 "어떤 테이블의 어떤 ID"를 문자열+UUID로 담아 범용화한 것이다(이런 방식을 "다형성 연관"이라 부른다). `GOV-02`가 요구하는 정확한 문장: *"승인자·시각·근거 기록 후 확정 전후 상태 AuditLog 저장"* — `actor_id`+`occurred_at`+`before`/`after`가 그대로 이 요구를 채운다.

## B. 기수·팀·측정 계획 (8개)

### cohort

**존재 이유**: 기관 하나가 운영하는 교육 기수(예: "7기 백엔드 부트캠프") 하나.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | cohort_id | |
| FK → organization | org_id2 | "2" 접미사는 ERD 툴 흔적, 실제로는 org_id |
| | name / start_date / end_date / stage / status | |
| | deleted_at | 소프트 삭제 |

`ORG-01`이 요구: *"기관 org_id 기준 기수 레코드 생성 후 기수 기간·단계·운영 상태 정보 저장"*.

### cohort_member

**존재 이유**: "이 학생이 이 기수 소속이다"라는 사실 자체를 담는 연결 테이블. 학생 테이블(`app_user`)에 `cohort_id` 컬럼을 직접 두지 않은 이유는, 한 학생이 이론적으로 여러 기수를 거칠 수 있고(N:M), `app_user`는 "계정"이라는 더 일반적인 개념이라 특정 기수에 종속되면 안 되기 때문이다.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK, FK → cohort | cohort_id | |
| PK, FK → app_user | user_id | |
| FK → organization | org_id | |
| | track | 교육 트랙 (백엔드/프론트엔드 등) |
| | joined_at | |

### team / team_membership

**존재 이유 (team_membership을 따로 둔 이유)**: `team`에 학생 목록을 직접 넣지 않고 `team_membership`을 또 하나의 연결 테이블로 둔 이유는, 팀 배정이 **바뀔 수 있고 그 이력을 남겨야 하기** 때문이다.

**team**

| 구분 | 컬럼 |
|---|---|
| PK | team_id |
| FK → cohort | cohort_id |
| FK → organization | org_id |
| | name |

**team_membership**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | membership_id | |
| FK → team | team_id | |
| FK → app_user | user_id | |
| | from_at / end_at | 이 학생이 이 팀에 언제부터 언제까지 있었나 |
| FK → organization | org_id | |

`ORG-02`(팀 구성·재배정)가 정확히 이 구조를 요구한다: *"재배정 대상은 기존 membership의 to_at을 재배정 시각으로 마감 후 신규 팀 membership을 from_at 기준으로 생성하고 이력 보존"*. 만약 `team`에 `user_id` 컬럼을 직접 뒀다면, 재배정 시 옛 값을 덮어써서 "이 학생이 예전엔 어느 팀이었는지"가 사라진다. `contribution_stat`(팀 내 기여 편차)이 "그 시점 팀 구성 기준"으로 통계를 내야 하므로(팀 구성이 바뀌면 통계 구간도 나눠야 함 — `ORG-02` 예외 case 참조) 이 이력이 반드시 있어야 한다.

### checkpoint

**존재 이유**: 기수 안의 "N회차 측정" 하나. 앞 문서에서 다뤘듯 이게 있어야 회차마다 다른 "그 시점 기준"을 만들 수 있다.

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | checkpoint_id | |
| FK → cohort | cohort_id | |
| | round_no | 몇 회차인가 |
| | measured_on | 측정 기준일 |
| | open_at / due_at | 응시 시작·마감 |
| | is_final | 최종 회차인가 (등급은 이 회차에만 부여됨 — ENG-01 규칙) |
| | status | |

`PLAN-01`: *"최종 회차 대상 1건에 is_final=true 설정"*, *"최종 회차가 2건 이상 발생 시 저장 차단"*.

### view_setting / extract_scope_setting / focus_area

**존재 이유 (셋을 묶어 설명)**: 이 셋은 전부 "매니저가 설정한 값이지만, 나중에 그때 뭐로 설정돼 있었는지 재현해야 하는 값"이다. 그래서 다들 같은 모양(`version` + `is_active` 대응 컬럼 + `set_by`/`changed_by`)을 반복한다 — 앞 문서 [기법 1: 버전 관리] 패턴 그대로다.

**view_setting (GOV-03 공개범위)**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | setting_id | |
| FK → cohort | cohort_id | |
| FK → organization | org_id | |
| | scope | 전체/요약/비공개 |
| | version | |
| FK → app_user | set_by | |
| | is_active | |

**extract_scope_setting (분석 범위)**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | setting_id | |
| FK → project | project_id | |
| FK → organization | org_id | |
| | scope | 전체코드/본인커밋기여분 |
| | version | |
| FK → app_user | changed_by | |
| | changed_at / is_active | |

**focus_area (검증 포커스)**

| 구분 | 컬럼 | 설명 |
|---|---|---|
| PK | focus_id | |
| FK → checkpoint | checkpoint_id | |
| FK → organization | org_id | |
| | area | 중점 평가 영역 |
| | version | |
| FK → app_user | user_id | |

`GOV-03`이 이 패턴이 왜 필요한지 정확히 설명한다: *"선택된 열람 범위 저장 후 적용 시각·설정자·설정 버전 기록"*, *"설정 변경 중 교육생 조회 요청 발생 시 마지막 확정 설정 버전 기준 응답"* — 즉 설정이 바뀌는 도중에도 조회는 "그 순간 확정돼 있던 버전"을 봐야 한다. `version` 컬럼 없이 값 하나만 있으면 이걸 보장할 수 없다.

`focus_area`는 조금 다른 이유도 하나 더 있다 — 교육생에게 **절대 노출되면 안 되는** 값이라는 것(`PLAN-03`: *"교육생 노출 대상 데이터에서 focus_area 제외"*). 별도 테이블로 분리해두면 "교육생용 API가 이 테이블을 아예 조회하지 않는다"는 걸 코드 레벨에서 명확히 보장하기 쉽다 — 다른 테이블에 컬럼으로 섞여 있으면 실수로 같이 노출될 위험이 커진다.

## C. 프로젝트·제출·기여 (7개)

### project / project_repo

**존재 이유 (나눈 이유)**: `project`는 "이 과제가 무엇인가"(요구사항), `project_repo`는 "그 코드가 어디 있고 접근 가능한가"(레포 상태)로, 서로 변하는 속도와 이유가 다르다.

**project**

| 구분 | 컬럼 | 설명 |

## D. 판단지점·채점·세션 (10개) — 제품의 심장

이 묶음이 `data-contract.md`가 "철칙 D1"이라 부르는 핵심 원칙의 무대다 — *"LLM은 쓰기 시점에 한 번 돌고, 구조화된 값으로 굳는다."* 앞 문서에서 이 13개 중 대부분을 이미 한 시나리오로 훑었으니, 여기서는 "왜"에 집중한다.

## 전체를 관통하는 세 가지 (다시 요약)

49개를 다 훑고 나면 반복되는 게 보인다. 앞 문서 [기법 1~3]이 정확히 이 세 가지였다:

| 기법 | 쓰인 테이블 |
|---|---|
| 버전 관리 (값을 안 덮어씀) | score, view_setting, extract_scope_setting, focus_area, counseling_note(+revision) |
| 이력 로그 (상태 변경마다 한 줄) | intervention_status_log, curriculum_status_log |
| 스냅샷 (그 순간을 박제) | benchmark_snapshot, report_snapshot, trainee_report, submission의 커밋 해시들 |

그리고 이 세 가지가 전부 존재하는 근본 이유는 하나다 — **이 제품은 사람을 판정하고, 그 판정에 이의를 제기할 권리(GOV-01)가 있다.** 이의가 들어오면 "그때 뭐가 어떻게 보였는지"를 재현해야 하고, 값을 그냥 덮어쓰는 설계로는 그게 불가능하다. 49개 테이블 중 상당수가 이 요구사항 하나에서 파생된 것이다.
