# OP-04 · 프로젝트 상세 (오퍼레이터) — 탭 3

## 1. 한 줄

이 회차를 **무엇으로 잴지** 정하고, 그 선택이 맞았는지 확인한다.

## 2. 진입 · 이탈

OP-03 행 → 여기. `현황`의 경고 → OP-02.

## 3. 뷰

```
미프 3차 [진행 중] 미프                              마감 07-14 23:59 · 지남
[ 개요 ] [ 현황 ] [ 구성 ]
```

**머리에는 정체와 마감만 둔다.** 탭을 옮겨도 지금 보는 회차가 무엇인지, 언제까지인지가
사라지면 안 된다(B1). 나머지 값은 `개요`가 갖는다 — 두 곳에 그리면 한쪽만 고쳐질 때 두
곳이 다른 말을 한다(D1).

### 개요

```
기본 정보   검증 개념   HITL 정의 · Supervisor 역할 분리 · Critic 역할
            교안       AI_LLMOps v2 · Streamlit 실습 v1
            유형       미프 · 문항 3개 = 검증 개념 3건
────────────────────────────────────────────────────────────
일정        제출 마감   07-14 23:59 · 시작 2026-06-30          [수정]
            응시 창    코드 분석 완료 시점부터 24시간
            재시험 창  3일 또는 다음 프로젝트 제출일 중 빠른 쪽
            리포트     제출 마감 후 일괄
────────────────────────────────────────────────────────────
측정 규칙   문항 3 · 단계 4 · 힌트 2 · 세션 70분   (전 기수 공통 · 읽기 전용)
```

### 구성

```
교안 연결      교안 1  AI_LLMOps v2 · 등록 06-28            [변경]
               교안 2  Streamlit 실습 v1 · 등록 07-02
──────────────────────────────────────────────────────────────
질문 항목 3건  1  Supervisor 패턴의 HITL 실행 흐름 · AI_LLMOps v2 · HITL p.53
               2  Supervisor 패턴과 역할 분리 구조  · AI_LLMOps v2 · 역할설계 p.41  [변경]
               3  Snapshot 개념과 구성 요소        · AI_LLMOps v2 · 시점관리 p.63
──────────────────────────────────────────────────────────────
요구사항       좋아요 버튼                                  (교안과 별개)
               댓글 작성
               정렬 기능
```

**교안은 1개 이상이다.** 여러 개면 `teaches`가 합쳐져 후보가 되고, 확정된
3건은 **어느 교안 어느 섹션에서 왔는지를 달고 다닌다** — 리포트의 교안 위치와 면담 브리프가 그
값을 읽으므로 출처가 없으면 `3장 p.55`를 어느 문서에서 펼지 알 수 없다.

**질문 항목과 요구사항은 출처도 용도도 다르다.** 항목은 교안에서 나와 **문항 3개**가
되고, 요구사항은 과제 문서에서 나와 **구현 P/F**에만 쓴다. 시각적으로 갈라 놓는다.

> **`일정`은 별도 탭이었다가 `개요`로 들어갔다**(§6). 마감 시각은 목업의 `18:00`이 아니라
> **`23:59`** 다 — 그날 안에 끝난다는 뜻이고, `24:00`은 다음 날 `00:00`이라 "9/26 마감"이
> 27일에 끝나는 것처럼 읽힌다. 기획이 정하면 `rules.ts`의 `DUE_TIME` 한 줄만 바뀐다.

### 현황

```
반별      A 25/25 · B 24/25 · C 23/25 …            제출 → 분석 → 응시
경고      ⚠ "시점 관리" 문항 생성 0 — 팀 6/8
          → 학생 문제가 아니라 개념 선택이 프로젝트와 안 맞았을 수 있습니다
```

**`현황` 탭이 오퍼레이터에게 필요한 이유:** 팀 전반에서 같은 항목이 비면 다음 회차에
**항목을 교체할 사람이 오퍼레이터**다.

### 검증 개념 선택 — 지난 회차 이력을 붙인다

9-6의 후속(*"다음 프로젝트 검증 개념에 재투입"*)이 실제로 쓰이는 자리는 **목록이 아니라
여기**다.

```
교안 AI_LLMOps v2 · 가르친 항목 8건
☑ HITL Trigger 조건 함수                          p.55
  should_trigger_hitl에서 최대 반복 횟수와 …
☐ Graph 구성                                      p.62
  ⚠ 미프 3차에서 집단 미달 — 7개 반에서 절반 이상 2단 이하
  노드와 엣지로 실행 순서를 정의하고 …
☑ State 관리                                      p.71
  미프 3차에서 사용 · 평균 3.3단
  AgentState를 TypedDict로 정의하고 …
```

**같은 교안이 붙었을 때만 이력이 나타난다.** 검증 개념은 그 회차 교안이 가르친 것에서만
나오므로(4-3) 교안이 바뀌면 후보 자체가 달라진다 — **조건이 자연히 충족되는 자리**라서
*"불가능한 일을 권하는"* 문제가 안 생긴다.

**목록에 열로 만들지 않은 이유:** 미프 3차가 AI_LLMOps고 미프 5차가 Kubernetes면
Graph 구성은 후보에 아예 없다. 목록에 `재투입 검토 →`를 두면 **대부분의 경우 불가능한
일을 권하는 링크**가 된다.

### 이력은 판단을 대신하지 않는다

| 표시 | 뜻 | 뜻이 아닌 것 |
|---|---|---|
| `⚠ 집단 미달` | 지난 회차에 반 절반 이상이 2단 이하였다 | *"피해야 한다"* 도 *"다시 물어야 한다"* 도 아니다 |
| `⚠ 코드 매칭 0` | 그 개념이 학생 코드에 없어 **묻지 못했다** | 학생이 못한 것이 아니다 |
| `평균 3.3단` | 지난 회차에 썼고 결과가 이랬다 | — |

**교안을 보강했다면 다시 넣어 확인할 수 있고, 그대로면 같은 결과가 나온다.** 어느 쪽인지는
시스템이 모른다 — 9-6이 *"시스템은 표시까지만 한다"* 고 한 그대로다.

**`코드 매칭 0`은 다른 신호다** — 개념이 과제와 안 맞았다는 뜻이라 **개념을 바꿔야** 한다.

## 4. 데이터

**교안 n개** · 질문 항목 3(각각 출처 교안·섹션) · 요구사항 · 일정 · 반별 파이프라인 · 항목별 문항 생성 결과.

## 5. 액션

교안 추가·해제 · 질문 항목 3건 변경 · 요구사항 편집 · 일정 수정.

**이미 고른 항목의 출처 교안은 해제할 수 없다.** 해제하려면 그 항목부터 바꿔야 한다 —
출처가 끊긴 항목은 교안 위치를 가리킬 수 없다.

**측정이 시작된 뒤 항목을 바꾸면 비교 축이 깨진다** — 응시가 하나라도 있으면 변경에
확인 모달을 세우고, 바꾸면 그 회차 이전 결과와 비교하지 않는다.

### 개념 3건이 이 화면의 관문이다 — 다만 **잠그지 않는다**

3건이 정해져야 학생에게 낼 문항 3개가 만들어지고, 그때부터 현황이 집계된다. 그것이 관문인 것은 맞다.

> **개정 (2026-08-03).** 원안은 *"흐린 탭 + 툴팁이 아니라 **탭 자체를 잠근다**"* 였다.
> **구현에서 뒤집었다** — 잠긴 탭은 **왜 잠겼는지도 어떻게 열리는지도 말하지 못한다.**
> 점검표 **C1**이 금지한 *"흐린 버튼 게이팅"* 과 같은 문제이고, 잠금은 툴팁보다 오히려
> 말이 적다.
>
> 대신 **각 탭이 자기가 왜 비었는지를 쓴다.** [02-layout §4](02-layout-system.md)의
> 「없는 것」 3종 구분을 그대로 쓴다 — 기다려도 안 채워지는 것에는 **다음 행동**을 붙이고,
> 기다리면 채워지는 것에는 **언제 채워지는지**만 쓴다.

### 탭 순서 — 개요 → 현황 → 구성

> **개정 (2026-08-03).** 원안은 `구성 · 일정 · 현황`이었다. 셋을 **읽는 순서**로 다시 놓았다.

| | | 왜 |
|---|---|---|
| **1 · 개요** | 이 회차가 **무엇인가** | 검증 개념·교안·유형·일정·측정 규칙. **기본 탭이다** — 들어오면 *"무엇이 비었는지"* 가 탭을 열기 전에 읽힌다 |
| **2 · 현황** | 잘 **굴러가고 있나** | 반별 진행 · 개념 공백 |
| **3 · 구성** | 무엇을 **바꿀 것인가** | 교안·개념·요구사항 편집 |

**`일정` 탭을 없애고 `개요`에 넣었다.** 일정 탭이 이미 측정 규칙까지 들고 있어서 *"이 회차의
기본 정보"* 에 가까웠고, 날짜 넷 중 사람이 정하는 것은 제출 마감 하나뿐이라 탭 하나를 쓸
분량이 아니었다.

### 개념 공백은 학생 문제가 아니다

고른 개념이 학생 코드에 없으면 **그 개념은 물을 수 없다.**

| | |
|---|---|
| **화면이 말하는 것** | `개념 선택이 이 프로젝트와 맞지 않았을 수 있습니다` · 몇 팀인지 |
| **그 학생** | 남은 문항으로 진행한다(2문제) |
| **다음 회차** | 개념 교체를 검토하라고 안내 |

학생을 탓하는 문구로 쓰면 오퍼레이터가 **엉뚱한 곳을 고친다.**

### 개념 선택에 지난 회차 이력을 붙인다

같은 개념을 반복해서 고르면 **회차 간 비교가 되지 않는다** — 무엇을 이미 물었는지 그 자리에서 보여준다.

## 8. 구현 상태 (2026-08-03)

> **정의서에 이 절을 두는 이유** — 위 §1~§7은 *"무엇을 만들기로 했나"* 이고, 구현하면서
> **몇 군데를 의도적으로 뒤집었다.** 그 사실이 여기 없으면 다음 사람이 원안대로 다시
> 만든다(실제로 §6 잠금이 그런 자리였다).
>
> 코드 결정·파일 배치·다음 할 일은 [`docs/dev/op-projects-progress.md`](../../../dev/op-projects-progress.md)가
> 갖는다. **여기는 화면 계약만** 적는다.

### 8-1. 상태별로 무엇을 보여주나

**빈 상태를 잠금으로 대신하지 않는다**(§6). 셋을 구분한다 — 기다려도 안 채워지는 것에는
**다음 행동**, 기다리면 채워지는 것에는 **언제 채워지는지**, 못 가져온 것에는 **다시 시도**.

| 탭 | 조건 | 유형 | 화면 |
|---|---|---|---|
| **개요** | 마감 미설정 | 없음 | `아직 정하지 않았습니다 · 마감이 있어야 학생이 언제까지 내는지 알 수 있습니다` + **`[일정 설정]`** |
| | 〃 | | **응시·재시험 창의 계산된 날짜를 지운다** — 마감이 없으면 계산할 수 없는데 규칙만 남기면 정해진 것처럼 읽힌다 |
| | 개념 0건 | | `⚠ 미확정 · 후보 N건에서 3건` · 교안 0이면 `교안 없음` · 빅프는 `해당 없음` |
| **현황** | 개념 < 3 | 없음 | `아직 집계할 것이 없습니다 · 지금 N건` + **`[구성 탭에서 개념 정하기]`** |
| | 개념 3 · 제출 0 | **아직** | `아직 제출한 학생이 없습니다` + 마감 있으면 그 날짜, 없으면 `개요 탭에서 일정을` |
| | 조회 실패 | 실패 | `[다시 시도]` |
| | 개념 공백 **0건** | | **경고 없음 · 표만.** 평상시 화면이다 |
| | 개념 공백 **1건** | | `“X”가 학생 코드에서 발견되지 않습니다 · 50개 팀 중 27개` → 해당 학생은 **`2문제`** |
| | 개념 공백 **2건 이상** | | `검증 개념 2건이 …` + **개념마다 줄을 나눠** 몇 팀인지. 문항 수는 **쓰지 않는다**(아래) |
| | **반 0개** | 없음 | `이 기수에 반이 없습니다` — 빈 배열에 `every`가 참이라 *"제출한 학생이 없습니다"* 로 삼켜지던 자리다(F3) |

**반별 행이 덮는 것** — 정상(전원) · 미제출 · 분석 실패 1·3건 · 담당 없음 · 응시 저조.
`5/18`처럼 **판정 없이 숫자만** 쓴다(E8 — 낮다/높다의 기준이 기획에 없다).

> **몇 문제로 진행되는지는 공백이 하나일 때만 쓸 수 있다**(A4). 둘 이상이면 미매칭 팀이
> 서로 다르고(12개 팀 · 31개 팀) **겹치는지 아닌지가 응답에 없다** — 어떤 팀은 하나만,
> 어떤 팀은 둘 다 빠진다. `3 − 공백 수`로 쓰면 **모든 팀이 전부 놓쳤다고 주장**하는 셈이다.
> → 2건 이상이면 `해당 팀의 학생은 매칭된 개념의 문항만 받습니다`.
| **구성** | 교안 0 | | `연결된 교안이 없습니다` |
| | 개념 0 | | 교안 0이면 `교안을 먼저 연결해야 후보가 나옵니다`, 아니면 `아직 정하지 않았습니다` |
| | 요구사항 0 | 없음 | `요구사항 없이 진행하는 회차입니다 — 구현 P/F를 판정하지 않습니다` |

**요구사항 0건은 `아직`이 아니라 `없음`이다.** 빅프처럼 요구사항 없이 끝나는 회차가 실제로
있어서 **기다릴 것이 없다.** *"없음"* 만 쓰지 않고 **0건이 무슨 뜻인지**를 쓴다.

### 8-2. 원안에서 뒤집은 것

| | 원안(§1~§7) | 구현 | 왜 |
|---|---|---|---|
| 탭 잠금 | 개념 3건 전까지 **잠근다** | **안 잠근다** | 잠긴 탭은 왜 잠겼는지도 어떻게 열리는지도 못 말한다(C1) |
| 탭 구성 | `구성 · 일정 · 현황` | **`개요 · 현황 · 구성`** | 읽는 순서. `일정`은 측정 규칙까지 들고 있어 *"기본 정보"* 에 가까웠다 |
| 마감 시각 | `18:00` | **`23:59`** | 그날 안에 끝난다는 뜻. `24:00`은 다음 날로 읽힌다 |
| 교안 해제 | *"해제할 수 없다"* (§5) | **막고 이유를 쓴다** | `검증 개념 2건이 쓰고 있어 뺄 수 없습니다 — HITL 정의 · Critic 역할`. 못 누르는 체크박스만 두면 **무엇부터 바꿔야 하는지** 모른다 |
| 요구사항 | 줄 목록 | **칩 입력** | 항목 하나가 **MG-08의 판정 단위**다(`✓ 2 · ✗ 1`). 덩어리 텍스트면 그 판정을 걸 자리가 없다 |

### 8-2-1. 상태별로 무엇을 할 수 있나

**액션마다 조건을 쓰지 않고 `rules.ts` 한 곳에 모았다** — 화면마다 `status === 'RUNNING'`을
쓰면 상태가 늘 때 갈리고, **버튼은 막혔는데 URL로 모달이 열리는** 상태가 생긴다.

| | PREP | READY | RUNNING | DONE |
|---|:--:|:--:|:--:|:--:|
| 교안 · 검증 개념 · 요구사항 | ⭕ | ⭕ | **✗** | **✗** |
| 일정 | ⭕ | ⭕ | **연장만** | **✗** |
| 삭제 | ⭕ | ⭕ | **✗** | **✗** |

가르는 축은 **학생 데이터가 이미 붙었나** 하나다.

- **READY까지 여는 이유** — 준비는 끝났지만 **아직 아무도 안 냈다.** 깨질 축이 없다.
  여기서 막으면 준비를 끝낸 순간 수정 불가가 되어, 실수를 고치려고 회차를 다시 만든다.
- **RUNNING에서 구성을 막는 이유** — 먼저 본 학생과 나중 학생이 다른 문항을 받으면
  그 회차는 비교 축이 아니게 된다(§5). 요구사항도 같다 — 구현 P/F 기준이라 이미
  판정된 팀과 기준이 갈린다(MG-08).
- **일정만 RUNNING에 여는 이유** — 장애·공지 지연으로 **미루는 것**은 실무에 있다.
  전부 막으면 그 수단이 없어져 회차를 다시 만들게 된다. 다만 **당기는 것은 막는다**:
  학생은 이미 "언제까지"를 알고 있고, 앞당기면 **낼 수 있다고 알던 기회가 조용히 사라진다**(B1).
- **DONE에서 삭제까지 막는 이유** — 제출·분석·응시·리포트가 그 회차에 매달려 있다.
  지우면 **학생이 실제로 한 일**이 같이 사라진다. 끝난 회차는 기록이다.

**막힌 곳에는 사유를 쓴다**(`lockedReason`) — 흐린 버튼만 두면 왜인지 모르고, 툴팁은
hover해야 보여 키보드 사용자가 못 읽는다(C1).

### 8-2-2. 삭제 — 왜 구성 탭 맨 아래인가

| | |
|---|---|
| **구성 탭** | 이 탭이 *"무엇을 바꿀 것인가"* 이고 삭제는 그 극단이다. 개요는 읽는 탭이라 파괴적 액션을 두면 성격이 섞인다 |
| **맨 아래** | 다른 작업 중에 눈에 걸리지 않고, 스크롤 아래라 우발적 클릭이 준다 |
| **목록 행이 아니다** | 거기서는 **이름만 보고** 누른다. 상세를 열었다는 것은 **내용을 봤다**는 뜻이다. 열이 하나 더 느는 문제도 있다(OP-03 §8-1) |

**확인 모달이 무엇이 사라지는지 센다** — `교안 1개 연결 · 검증 개념 3건 · 요구사항 2건 ·
일정(마감 07-21 23:59)`. `정말 삭제하시겠습니까?` 만 묻는 창은 아무 정보도 주지 않는다(B5).
**이름 재입력은 시키지 않는다** — 학생 데이터가 붙은 회차는 애초에 못 오고, 남는 것은
오퍼레이터 본인의 설정 작업이라 그 비용에 비해 과하다.

### 8-3. 만든 것 · 안 만든 것

```
⭕ 탭 3 · 편집 모달 5(개념 · 교안 · 요구사항 · 일정 · 삭제)
⭕ 8-1의 빈 상태 전부 — 목 회차 7건으로 실제 렌더 확인
⭕ 8-2-1 편집 정책 — 4상태 × 3액션을 rules.ts에 모으고 스크립트로 고정
⭕ 탭이 URL에 있다(/operator/projects/:id/:tab?) · 모르는 탭은 주소까지 교정
✗  측정 시작 후 개념 변경 확인 모달(§5) — RUNNING에서 아예 막았으므로 필요 없어졌다
✗  개념 공백 → OP-02 이탈(§2) — OP-02가 아직 없다
```

### 8-3-1. 개요 탭을 한 번 갈아엎었다

처음에는 `라벨-값` **12행을 세로로 쌓았다.** 전부 같은 시각 무게(회색 라벨 + 검정 값)라
어느 것이 중요한지가 안 읽혔고, 설명이 값보다 길어 본문을 덮었다.

| | 고침 | 근거 |
|---|---|---|
| 핵심값이 나머지와 같은 크기 | **요약 3칸**(마감 · 검증 개념 · 교안) | 되돌릴 수 없는 마감이 가장 커야 한다(B1). 셋은 목업 doc-head의 *"교안 · 개념 3건 · 마감"* — **빈 칸이 곧 할 일** |
| 일정 5항목이 **시간 순서인데 나열** | **세로 타임라인** | H3 — 같은 시간축 이벤트를 갈라 놓으면 순서가 사라진다. 마감이 없으면 뒤 셋을 계산할 수 없다는 사실이 **빈 점**으로 읽힌다 |
| 측정 규칙이 늘 펼쳐져 있다 | **기본 접힘**(네이티브 `<details>`) | *"전 기수 공통 · 여기서 바꾸지 않음"* — 매번 볼 것이 아니다 |
| 설명이 본문을 덮는다 | **응시 창 한 줄만 남김** | `제출 시점이 아닙니다`는 실제 오해를 막는다(14번 10-1). 나머지는 값이 이미 말한다 |

### 8-4. 확인이 필요한 것

| | |
|---|---|
| **케이스 표가 없다** | §6이 가리키는 `#cases-op04` 앵커가 목업에 없다. **실패 문구·에러코드가 정해진 게 없어** 구현은 실패를 하나로만 그린다. 표를 만들면 코드를 나눈다 |
| **마감 유효 범위**(#64) | 기수 기간 밖·`시작 > 마감`은 **달력이 막는다.** 다음 회차보다 늦은 마감은 **막지 않고 사실만 쓴다** — 막을지 경고만 할지 미결이라 화면이 정하면 기준을 만드는 것이 된다(E8) |
| **목록 헤더 내역** | 목업이 `준비 중 2 · 진행 중 1 · 종료 1`로 그려 **`준비됨`을 안 센다**(E1 — 처리하면 줄어드는 수만). 총계와 내역이 안 맞아 보이는데 의도인지 확인 필요 |
| **마감이 지났는데 `진행 중`** | `미프 3차`가 마감 07-14인데 오늘 07-16, 상태는 `진행 중`이다. 응시 창이 **개인별 24시간**이라 마감 후에도 도는 것이 맞지만 **화면이 그 이유를 말하지 않는다** — 오퍼레이터는 *"왜 안 끝났지"* 로 읽는다 |
| **상태 전이 주체** | `준비됨 → 진행 중`을 누가 언제 하나(첫 제출? 시작일 도래?). 서버 판정이라고만 돼 있어 **오퍼레이터가 자기 회차의 시작 시점을 못 읽는다** |
| **일정을 되돌릴 수 없다** | `준비됨`에서 마감을 비워 `준비 중`으로 가는 경로가 없다(달력에서 지우기가 없다). 잘못 잡은 일정을 *"일단 지우고 다시"* 가 안 된다 |
| **교안·유형 필터** | 회차 6~8개에 필터 4개 — 걸러낼 모집단이 없다(OP-03 §8-2) |
