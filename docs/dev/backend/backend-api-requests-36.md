## 2. 34차 R9는 아직 안 끝났습니다 — 여기서 이어받습니다

34차에서 물었던 것은 셋 중 하나를 골라 달라는 것이었습니다.

| 34차 R9 안 | 회신 | 실제 |
|---|---|---|
| **A** 인박스 전용 조회 하나 — 6종을 한 응답으로 | 「이미 있습니다」(`/notifications/inbox`) | **조회는 있는데 409로 죽어 있습니다**(R1) |
| **B** 지금 셋을 쓰되 미응시 행 + 체크 쓰기 추가 | 미응시는 뷰 수정으로 해결, 체크는 안 만듦 | 미응시는 **원래 되고 있었습니다**(§1 — 저희가 회차를 안 넣었습니다) · 체크 쓰기는 없음 |
| **C** 되는 3종만, 체크 없이 | — | **지금 이렇게 붙였습니다**(4종 + 신규 1종, §11) |

즉 **R9는 A로 답이 왔지만 A가 동작하지 않아 실질적으로는 미해결**입니다.
회신에 적어 주신 `ABSENT`·`RETRY` 수정도 R1이 409인 동안에는 확인할 방법이 없습니다 —
그 값들이 이 조회로만 나오기 때문입니다.

```
R9 상태   A안으로 답변 받음 → 배포본에서 409 → 확인 불가 → R1로 이어받음
```

**R1이 풀리면 R2·R3·R5가 없어집니다** — 인박스 응답의 `subject`가 팀명을 주고
(R2), `evidence`가 근거 문구를 주며(R3), 회차를 생략하면 담당 반 전체가 옵니다(R5).

**R4·R6은 남습니다.** 스펙을 다시 읽고 확인했습니다.

| | R1이 풀리면 | 왜 |
|---|---|---|
| R2 팀 이름 | 없어짐 | `items[].subject` = 「대상 이름(교육생명 또는 팀명)」 |
| R3 signals `summary` | 없어짐 | signals를 아예 안 부르게 됩니다 |
| R5 전 회차 면담 | 없어짐 | `assessmentRoundId` 생략 = 담당 반 전체 |
| **R4 마지막 방문 시각** | **남음** | 인박스 응답에 `lastVisitedAt`이 **없습니다**. `since` 인자는 있는데 넣을 값이 없습니다 |
| **R6 `class-progress`** | **남음** | 인박스는 제출·응시 **숫자**를 안 줍니다. 진행 줄 때문에 이 조회를 계속 부릅니다 |

## 3. R1 🔴 인박스 조회가 **모든 정상 호출에서 409**입니다

`GET /api/v0/cohorts/{cohortId}/notifications/inbox`

스펙에는 `x-readiness: available` · `✅ 사용 가능`으로 적혀 있는데, 실제로는
정상 호출이 전부 실패합니다. **Lambda·App Runner 두 호스트 모두 같습니다.**

```jsonc
{"timestamp":"2026-08-18T02:44:33.459847309Z","status":409,
 "error":"DATA_INTEGRITY_VIOLATION","code":"DATA_INTEGRITY_VIOLATION",
 "message":"요청을 처리할 수 없습니다. 데이터 제약 조건에 맞지 않습니다."}
```

**인증·스코프·인자 문제가 아닙니다.** 세 갈래로 잘라 봤습니다.

| 잘라 본 것 | 결과 | 뜻 |
|---|---|---|
| `?size=0` · `?size=101` | **400** `VALIDATION_FAILED` (0.5s) | 검증은 돌고, 정상 인자는 **통과합니다** |
| `?since=2099-01-01T00:00:00Z`(결과가 반드시 빈 창) | 여전히 **409** | 데이터 양·내용 문제가 아닙니다 |
| 같은 토큰·같은 기수로 명부 · signals · projects | 전부 **200** | 토큰·담당 반 스코프는 정상입니다 |

전 조합입니다(같은 기수 `f7011ddf-8b38-437e-9917-97725f258d78`).
**아래 9줄은 Lambda 실측**이고, App Runner에서도 무인자·`size=100`·
`includeResolved=true&size=100` 셋을 다시 재서 **똑같이 409**를 받았습니다
(0.46~0.65초). 위 예시 응답은 App Runner 것입니다.

```
(무인자)                        409  1234ms
?size=1 / ?size=20              409   925 / 840ms
?includeResolved=false          409   841ms
?includeResolved=true&size=100  409   639ms
?since=2026-01-01T00:00:00Z     409  1017ms
?since=2099-01-01T00:00:00Z     409   945ms
?cursor=                        409   984ms
?size=0 / ?size=101             400   523 / 643ms   ← 검증은 통과한다는 증거
```

GET이 `DATA_INTEGRITY_VIOLATION`을 내는 경로는 사실상 쿼리가 터지는 것뿐이라고
보고 있습니다. 회신에 적어 주신 `JdbcManagerNotificationRepository.findInbox`의
`attendance` CTE 수정이 배포에 반영됐는지, 반영됐는데도 이 증상이면 그 쿼리에서
나는 예외인지 확인 부탁드립니다.

> ⚠ 참고로 **스펙 해시로는 배포 여부를 못 가립니다.** 리포지토리 SQL 수정은
> OpenAPI에 안 드러나서, 저희가 한 번 「스펙이 같으니 미배포」라고 오판했습니다.

**우선순위 — 가장 높습니다.** R2·R3·R5가 여기 딸려 있고,
**34차 R9의 실질적인 답도 이것입니다**(§2).

## 5. R3 🟡 signals `summary`가 **JSON 문자열**입니다

`GET /api/v0/cohorts/{cohortId}/analytics/signals`

```jsonc
"summary": "{\"attemptId\": \"2fb96286-…\", \"attemptStatus\": \"COMPLETED\", \"contributionStatus\": null, \"validityReviewStatus\": \"CONFIRMED_INVALID\", \"contributionSnapshotId\": null}"
```

객체가 아니라 **문자열 하나**로 옵니다. 화면이 `JSON.parse`로 풀어

> ⚠ 이 응답에 **`className`이 없는 것**(`classroomId`만)도 같이 올리려다 뺐습니다 —
> 담당 반 목록을 저희가 이미 받아 두고 있어서 화면에서 이어 붙였습니다. 요청 아닙니다.

## 6. R4 🟡 「지난 방문 이후」의 기준 시각을 아무도 갖고 있지 않습니다

인박스에는 `지난 방문 이후` / `전체` 두 범위 칩이 있었습니다. 인박스 조회의

없습니다** — 응답에도 없고 저희 저장소에도 없습니다(목은 `7/26 14:20`이라는

## 7. R5 🟡 전 회차 대기 면담을 **한 번에** 받을 수 없습니다

`GET /api/v0/interviews`는 `assessmentRoundId`를 생략하면 **이번 회차만** 옵니다
(32차 R2 회신대로입니다). 그런데 대기 면담은 회차가 지나도 안 없어집니다.

```
1차  0건            4차  12건 (PLANNED 8)
2차  5건 (PLANNED 5) 5차   4건 (PLANNED 4)
3차  8건 (PLANNED 7) 6차   1건 (PLANNED 1)
                     → 전 회차 대기 25건
```

회차 수만큼 반복 호출하는 방법은 있습니다(`useQueries`). 다만 **이 레포에 전례가
0건**이라 이번에는 안 썼습니다 — 화면 하나 때문에 새 패턴을 들이는 것보다 조회
쪽이 맞는 모양이라고 봤습니다. 그래서 지금은 **고른 프로젝트의 회차 것만** 그리고
있고, 다른 회차의 대기 면담은 인박스에 안 나옵니다.

`GET /interviews?status=PLANNED`처럼 **회차를 생략하면 전 회차**가 오는 형태가
가능할까요? (R1이 풀리면 인박스 조회가 이미 합쳐 주므로 이 요청은 없어집니다.)

## 8. R6 🔴 **「없는 것에 답이 없다」가 Lambda 한정입니다** — 18차부터의 요청이 여기 걸립니다

이번에 두 호스트를 나란히 재면서 알았습니다. **같은 계정·같은 요청인데 답이 다릅니다.**

```
                        Lambda                    App Runner
없는 교안 상세          무응답(25초 끊음)          404 · 0.69s  CURRICULUM_MATERIAL_NOT_FOUND
없는 교안 섹션          무응답(25초 끊음)          404 · 0.47s  CURRICULUM_MATERIAL_NOT_FOUND
없는 프로젝트 상세      무응답(25초 끊음)          404 · 0.47s  PROJECT_NOT_FOUND
없는 기수 인박스        무응답(25초 끊음)          404 · 0.47s  MANAGER_SCOPE_NOT_FOUND
아직 회차 없는 프로젝트  무응답(40초 끊음 · 2회)     404 · 0.6~1.0s  PROJECT_ROUND_NOT_CREATED
아직 안 만든 브리프      무응답(35초 끊음)          404 · 0.50s  INTERVIEW_BRIEF_NOT_CREATED
```

**App Runner는 6/6 전부 정확합니다** — 도메인 코드까지 1초 안에 옵니다.
**Lambda는 6/6 전부 답이 없습니다.**

### 이게 왜 큰가

저희가 **18차부터 여러 차례 올린 요청**이 전부 이 하나였을 수 있습니다.

| 차수 | 무엇으로 올렸나 |
|---|---|
| 18차 R1 · R7 | 「없는 회차를 물으면 404 대신 매달린다」 |
| 21차 · 25차 R4 | 같은 증상 |
| 29차 R1 · 30차 R1 | 「없는 브리프의 404가 무응답이다」 |
| 32차 R12 | 「없는 `materialId`가 404가 아니라 매달린다」 |

**저희는 그동안 계속 Lambda로 재고 있었습니다**(`vite.config.ts`의 프록시 대상과
`api/codegen.config.json`의 `spec.url`이 둘 다 Lambda입니다). 그래서 화면 곳곳에
「404를 부르지 않고 피해 가는」 우회를 넣어 뒀습니다 — 브리프는 `briefState`로
갈라서 `GET`을 아예 안 보내고, 교안 상세는 12초에 안내를 띄웁니다.

### 여쭙고 싶은 것

1. **어느 쪽이 정식 호스트인가요?** App Runner가 정식이면 저희 프록시·스펙 대상을
   그쪽으로 옮기고, **위 우회들을 걷어내겠습니다**(코드가 그만큼 단순해집니다).
2. Lambda를 계속 쓰신다면, 없는 자원에 답이 없는 것이 **그쪽에서만** 나는 이유를
   봐 주실 수 있을까요. 화면은 「없다」와 「아직 안 왔다」를 갈라야 하는데,
   무응답이면 그 둘이 같아 보입니다.

> ⚠ **정상 조회는 두 호스트가 똑같습니다** — `class-progress`(RUNNING) 200,
> `projects` 200, `trainees` 200, 그리고 **인박스 409도 양쪽 다** 납니다(R1).
> 차이는 「없는 것을 물었을 때」뿐입니다.

## 9. R7 ⚪ 회신 §3 — 수동 처리 표시 버튼은 **실제로 있었습니다**

> 회신 §3 「목업 화면을 확인했습니다 … "처리했음"을 표시하고 목록에서 지우는
> 버튼은 없었습니다」

와이어에는 없지만 **저희 구현에는 있었습니다.** 결정 로그 D56 C절에서 「독촉·알림
발송」을 「매니저가 직접 연락한 뒤 스스로 체크」로 바꾸면서 만든 것이고,
2026-08-08에 문구를 `연락함` → `체크`로 한 번 더 조정했습니다.

**이번 연동에서 그 버튼을 걷어냈습니다.** 서버에 상태를 저장할 자리가 없어서
목은 브라우저 안에서만 들고 있었고, **새로고침하면 체크가 사라졌습니다** —
「처리했다」고 믿게 만든 뒤 다음 방문에 되살아나는 것이 제일 나쁘다고 판단했습니다.

회신대로 **실제 처리(응시·제출·면담 완료)로 자동으로 빠지는 방식**으로 갑니다.
확인만 부탁드립니다 — 되살릴 계획이 있으시면 알려 주세요.

## 10. ⚪ 저희가 고친 것 — 브리프가 안 열리던 문제

팀에서 「5차에서 브리프 열기를 눌렀더니 아무것도 안 온다」는 보고를 받았습니다.
**저희 화면 버그가 맞았고 고쳤습니다** — 대시보드가 브리프 화면에 `?state=`를
안 넘겨서, 아직 안 만든 브리프를 `GET`으로 부르고 있었습니다. 그 404가 Lambda에서
무응답이라(R6) 90초를 기다렸습니다.

고친 뒤 **0.67초**에 「아직 브리프가 없습니다 · [브리프 만들기]」로 갑니다.
서버 쪽 요청은 없습니다 — **R6이 풀리면 이런 우회 자체가 필요 없어집니다.**

참고로 9기 브리프 상태 분포입니다. **`NONE`이 가장 흔합니다.**

```
1차 PLANNED 0
2차 PLANNED 5  {FAILED 2, NONE 3}
3차 PLANNED 7  {DRAFT 1, FAILED 1, NONE 5}
4차 PLANNED 8  {NONE 6, FAILED 1, CONFIRMED 1}
5차 PLANNED 4  {NONE 4}     ← 전부 NONE이라 매번 걸렸습니다
6차 PLANNED 1  {NONE 1}
```

`FAILED`는 `GET`이 200으로 내용을 줍니다(1.2초) — **`NONE`만 404**입니다.

## 11. 지금 화면이 무엇으로 그려지고 있나

R1이 풀릴 때까지 조회 **넷**을 화면에서 합칩니다.

```
GET /projects?cohort=              7.0s   프로젝트 선택기 + 미제출 경보
GET /projects/{id}/class-progress  1.7s   진행 줄 + 분석 실패 팀 + 이 프로젝트의 회차
GET /trainees?assessmentRoundId=   6.0s   미응시 · 응시 중단
GET /interviews?assessmentRoundId= 0.9s   면담 대기
                                          (시간은 App Runner 실측입니다)
```

`class-progress`가 주는 `assessmentRoundId`를 뒤의 둘에 물려서 회차 조회를
따로 안 하고 있습니다. **3단 직렬이라 최악 14.7초**입니다(①→②→③④) — 병렬로
접을 수 없습니다. R1이 풀리면 **둘로 줄어듭니다** — 인박스 하나 + `class-progress`
하나입니다(인박스가 제출·응시 **숫자**는 안 줘서 진행 줄 때문에 남습니다).

연동 직후 하드닝(`docs/dev/screens/mg-01-hardening.md`)에서 **화면 결함 10건**을
찾아 전부 고쳤습니다 — 전부 저희 코드였고, 서버 쪽으로 넘긴 것은 위 R1~R6뿐입니다.
