## 1. 🟠 Q1 — 연속 실패 차단이 확률적으로만 걸린다

### 관측

같은 계정·같은 머신·**같은 헤더**로 틀린 비밀번호를 연속으로 보냈다.

```
 1~5회 :  400 LOGIN_INVALID
 6회   :  429 LOGIN_TEMPORARILY_BLOCKED   retryAfter=37
 7회   :  400 LOGIN_INVALID               ← 차단 중인데 통과
 8회   :  400 LOGIN_INVALID
 9회   :  429 LOGIN_TEMPORARILY_BLOCKED   retryAfter=35
10회   :  400 LOGIN_INVALID

그 상태에서 올바른 비밀번호 →  200 로그인 성공

다른 시도에서는 8회째에 429가 뜨고 retryAfter=119였다(2단계 차단 = 120초).
```

**두 가지가 동시에 관측된다.**

| | |
|---|---|
| 차단이 **유지되긴 한다** | `retryAfter`가 37 → 35로 줄어든다 — 같은 차단 창이 이어지고 있다 |
| 그런데 그 사이 요청 일부가 **통과한다** | 400이 섞여 나오고, 올바른 비밀번호면 로그인까지 된다 |

### 이미 배제한 것 — 헤더 스푸핑은 아니다

차단 상태에서 `X-Forwarded-For`를 바꿔 보내 봤다.

```
기본              → 400
XFF 203.0.113.7   → 400
XFF 198.51.100.9  → 400   ← 값을 바꿔도 결과가 같다
```

**클라이언트가 보낸 `X-Forwarded-For`를 서버가 신뢰하지 않는다.** 헤더로 차단을 우회하는
취약점은 없다 — **잘 되어 있는 부분이니 확인차 적어 둔다.**

### 원인을 단정하지 않았다 — 후보가 둘이고 **해법이 완전히 다르다**

3차 회신 4절이 *"카운터는 이 인스턴스의 메모리에만 있다 … 인스턴스를 늘리면 인스턴스마다
따로 센다"* 고 예고했으므로 **인스턴스 다중이 가장 유력하다.** 다만 **똑같은 증상을 내는
다른 원인이 하나 더 있다.**

| 후보 | 왜 같은 증상이 나나 | 해법 |
|---|---|---|
| **A. 인스턴스가 여러 개** | 각자 따로 세니 차단이 확률적으로 걸린다 | 공유 저장소 (아래) |
| **B. 클라이언트 IP를 잘못 읽는다** | Railway는 프록시 뒤다. `getRemoteAddr()`면 **프록시 IP**를 읽고, 그 값이 요청마다 달라지면 **키가 매번 바뀌어** 카운터가 안 쌓인다 | **헤더 파싱 한 곳** — 저장소가 전혀 필요 없다 |

> ### B라면 인프라를 늘릴 일이 아예 없다. 그래서 **원인 확정이 먼저**다.

### 그리고 A라도 — Redis가 유일한 답은 아니다

3차 회신이 `login_blocked_until`이 **계정 단위**라 IP를 못 담는다고 하셨는데, 그건
**기존 컬럼의 한계지 DB의 한계가 아니다.** 이미 Postgres가 있으니 **테이블 하나**면 된다.

```sql
login_attempt(key PK, fail_count, blocked_until, updated_at)
-- INSERT ... ON CONFLICT DO UPDATE 로 원자적 증가
```

로그인은 초당 수 건 수준이라 write 부하가 논점이 아니고, 만료 행은 조회 시 무시 + 주기
삭제로 충분하다. **새 인프라를 얹는 것과 테이블 하나를 만드는 것은 비용이 다르다.**

### 우선순위 — 급하진 않지만 "안 고쳐도 된다"는 아니다

지금 실질 위험은 낮다. 사람의 오타 반복은 5회를 잘 안 넘고, **Origin 검사가 브라우저 밖
자동화를 이미 걸러낸다**(우리가 Node 테스트에서 실제로 막혔다). 이 서비스는 초대로만
계정이 생기는 내부 도구이기도 하다.

**다만 지금 상태는 "차단 장치가 있다고 믿는데 실제로는 새는" 상태**라, 그게 가장 나쁜
종류다. **원인 확인만이라도 먼저** 해 두시길 권한다 — B로 밝혀지면 그 자리에서 끝난다.

> **프론트는 손댈 것이 없다.** 429와 `retryAfter`를 정상 파싱해 카운트다운 UI가
> 그대로 동작하는 것을 확인했다(3절).

## 관측 (프론트가 실서버에 보낸 결과)

같은 계정 · 같은 머신 · 같은 헤더로 틀린 비밀번호를 연속 전송:

 1~5회 : 400 LOGIN_INVALID
 6회   : 429 LOGIN_TEMPORARILY_BLOCKED  retryAfter=37
 7회   : 400 LOGIN_INVALID        ← 차단 중인데 통과
 8회   : 400 LOGIN_INVALID
 9회   : 429 LOGIN_TEMPORARILY_BLOCKED  retryAfter=35
10회   : 400 LOGIN_INVALID
그 상태에서 올바른 비밀번호 → 200 로그인 성공
다른 시도에서는 8회째에 429가 뜨고 retryAfter=119였다(2단계 차단 = 120초).

두 가지가 동시에 관측된다:
- 차단이 유지되긴 한다 — retryAfter가 37 → 35로 줄어든다(같은 차단 창이 이어짐)
- 그런데 그 사이 요청 일부가 400으로 통과한다

## 이미 배제한 것

- 클라이언트가 보낸 X-Forwarded-For를 서버가 신뢰하지 않는다.
  차단 상태에서 값을 바꿔 보내도 결과가 동일했다 → 헤더 스푸핑 우회는 아니다.

## 확인해 달라 — 순서대로

1. 클라이언트 IP를 어떻게 얻고 있나  ← 가장 먼저
   - HttpServletRequest.getRemoteAddr()인가, X-Forwarded-For를 파싱하나?
   - Railway는 프록시 뒤다. getRemoteAddr()면 프록시 IP를 읽게 되고,
     그 IP가 요청마다 달라지면 키가 매번 바뀌어 카운터가 안 쌓인다.
   - server.forward-headers-strategy 설정이 있는지 확인
   - 로그인 시도마다 "최종적으로 사용한 클라이언트 IP"를 로그로 남기고 10회 재현해 달라.
     IP가 여러 개로 흩어지면 이게 원인이다.

2. 인스턴스가 실제로 몇 개인가
   - Railway replica 수 확인 / 배포 중 old·new 겹침만의 문제인지 상시인지
   - 인스턴스 식별자(호스트명 등)도 위 로그에 같이 남겨 달라.
     같은 IP인데 인스턴스가 갈리면 이게 원인이다.

3. 카운터 자료구조와 만료 로직
   - 자료구조가 무엇인가 (ConcurrentHashMap? Caffeine? 자체 구현?)
   - 만료 판정이 조기에 리셋되지 않는지 — 차단 창 계산의 오프바이원·시각 비교 실수
   - eviction 정책이 카운터를 지우고 있지는 않은지

4. 키 생성 로직
   - 이메일 정규화(대소문자·공백)를 하는가
   - IPv6 / IPv4-mapped(::ffff:1.2.3.4) 표기가 섞이면 같은 클라이언트가 두 키가 된다

5. 증가·검사 경로가 모든 분기에서 도는지
   - "차단 확인 → 비밀번호 대조" 순서라고 문서에 적혀 있는데 코드가 실제로 그런지
   - 비밀번호 불일치의 모든 분기에서 카운터가 증가하는지
     (일부 예외 경로가 증가를 건너뛰면 5회를 못 채운다)

## 원인이 확정되면 — 해결 후보 (Redis 도입은 마지막 수단)

원인에 따라 답이 다르니 원인을 먼저 확정하고 그에 맞는 것만 적용해 달라.

- 원인이 1번(IP 파싱)이면 → 프록시 헤더에서 클라이언트 IP를 제대로 읽는 것으로 끝난다.
  공유 저장소가 전혀 필요 없다.

- 원인이 2번(인스턴스 다중)이면 — Redis 전에 이것부터 검토해 달라:
  (a) 이미 있는 Postgres에 테이블 하나. 새 인프라가 아니다.
      login_attempt(key PK, fail_count, blocked_until, updated_at)
      INSERT ... ON CONFLICT DO UPDATE 로 원자적 증가
      로그인은 초당 수 건이라 write 부하가 문제되지 않는다.
      만료 행은 조회 시 무시 + 주기 삭제로 충분하다.
  (b) 인스턴스를 1개로 고정. 지금 트래픽에서 가용성 손해가 없다면 설정 한 줄이다.
  (c) 이중 방어 — 계정 단위(기존 app_user.login_blocked_until, 임계값 느슨하게)
      + IP 단위(메모리). 계정 단위는 DB라 인스턴스 간 공유되므로 최소한의 바닥이 생긴다.
      단 계정 단위만 촘촘히 막으면 "남의 이메일로 그 사람을 막는" 문제가 돌아오니
      임계값을 충분히 높게(예: 20회) 둬야 한다.

- 원인이 3~5번이면 → 그 로직만 고치면 된다.

- 추측으로 고치지 말고 로그로 원인을 확정한 뒤 고쳐 달라.

## 2. ✅ 확인 결과 — R1 · R2 · R3

### R1 — 쿠키

```
set-cookie: refresh_token=…; Path=/api/v0/auth; Max-Age=604800; Secure; HttpOnly; SameSite=None
```

요청한 그대로다. `Path`도 유지됐다.

> **`Secure` 자동 강제 안전장치**를 같이 넣어 주신 것이 특히 좋았다.
> `SameSite=None`인데 `Secure`가 꺼지면 브라우저가 **경고 없이 쿠키를 버려서**
> 증상이 이번 `Lax` 건과 똑같이 보인다. **같은 함정을 두 번 밟지 않게 막은 것**이다.

### R2 — Origin

```
https://frontend-eight-neon-73.vercel.app   200 · allow-credentials: true
http://localhost:5173                       200
http://localhost:5174                       200
http://localhost:5175                       200
http://127.0.0.1:5173                       200
http://localhost:4173                       200
https://evil.example.com                    403   ← 넓어진 게 아니라 정확히 6개만 열렸다
```

**환경변수 반영 전후를 다 봤다.** 코드 배포 직후에는 스펙에 `/me`가 있는데도 Origin이 여전히
403이었고, 변수가 들어간 뒤 6개가 전부 열렸다. **회신 6절이 그 순서를 미리 적어 주지 않았다면
"배포가 안 됐다"고 오판했을 것이다.**

### R3 — `GET /members/me`

```
GET /api/v0/members/me
→ 김민준 · OPERATOR · status=ACTIVE · organizationId=288bb1b6…
   로그인 응답의 role과 일치 ⭕
```

`role`·`status`가 기존 공유 enum을 그대로 참조해 **생성 타입에 새 타입이 안 생겼다** —
말씀하신 대로다. 프론트는 이걸로 **역할을 브라우저에 저장하는 것을 없앤다.**

> **`INACTIVE`가 오는 경우가 의미 있다**고 짚어 주신 것, 그대로 쓰겠다.
> 세션 도중 정지된 계정을 그 값으로 알아채는 것이 우리가 "역할이 낡는다"고 걱정한 지점이다.

## 3. 프론트 쪽 확인 — 생성 코드가 실서버에서 전 구간 동작한다

```
로그인 4계정          SUPER_ADMIN · OPERATOR · MANAGER · TRAINEE 전부 성공
/me                   로그인 응답과 역할 일치
인증 API              findOrganizations 정상 (Authorization 헤더 자동 주입)
틀린 비밀번호         400 LOGIN_INVALID          ← 코드 분기 동작
차단                  429 LOGIN_TEMPORARILY_BLOCKED · retryAfter 파싱 ⭕
토큰 없이 호출        401 UNAUTHENTICATED        ← 재발급을 시도하지 않는다(의도대로)
```

**2차에서 나눠 주신 에러 코드가 그대로 화면 분기로 쓰이고 있다.**
스펙에서 코드 61종을 뽑아 **오퍼레이션별 유니온 타입**을 자동 생성하므로,
앞으로 코드를 추가·변경하시면 **우리 쪽 `switch`가 컴파일 에러로 알려준다.**

## 4. 특히 도움이 된 것 (이번 회신에서)

요청 범위 밖인데 잡아 주신 것들이라 따로 적는다.

| | 왜 중요했나 |
|---|---|
| **CORS 필터와 Origin 검사가 같은 설정을 다르게 파싱**하던 것 | 끝 슬래시 하나로 *"CORS는 통과했는데 403"* 이 날 수 있었다. **증상만 보고는 절대 못 찾는 종류** |
| **`UNAUTHENTICATED`가 스펙에서 조용히 빠지고 있던 것** | 코드 추출기가 밑줄 있는 토큰만 뽑아서, 도메인 코드를 하나라도 적으면 더 자주 나가는 코드가 사라졌다. **우리 생성 유니온에 직접 영향** |
| **로그아웃 삭제 쿠키 속성 일치** | name·path가 같아도 SameSite가 다르면 브라우저가 다른 쿠키로 본다 — 안 맞췄으면 로그아웃이 조용히 안 됐을 것 |
| **차단을 이메일+IP로 센 것** | 이메일만 세면 *"남의 이메일에 5번 틀려 그 사람을 막는"* 게 되고, 그게 v2가 계정 잠금을 버린 바로 그 문제다 |

**요청서 부록의 확인 명령을 회귀 테스트로 옮겨 주신 것**(`LoginOriginPreflightTest`)도
좋았다. 허용 목록이 조용히 줄면 배포 전에 깨진다.

## 5. 앞으로 — 프론트가 다음에 필요한 것

## 부록 — 재현

```bash
API=https://backend-production-37e3.up.railway.app

# R1 · 쿠키 속성
curl -s -i -X POST "$API/api/v0/auth/login" \
  -H 'Content-Type: application/json' -H 'Origin: http://localhost:5173' \
  -d '{"email":"<이메일>","password":"<비밀번호>"}' | grep -i set-cookie

# R2 · Origin 전수 (마지막 evil은 403이어야 정상)
for O in https://frontend-eight-neon-73.vercel.app \
         http://localhost:5173 http://localhost:5174 http://localhost:5175 \
         http://127.0.0.1:5173 http://localhost:4173 https://evil.example.com; do
  printf '%-46s %s\n' "$O" \
    "$(curl -s -o /dev/null -w '%{http_code}' -X OPTIONS "$API/api/v0/auth/login" \
        -H "Origin: $O" -H 'Access-Control-Request-Method: POST')"
done

# Q1 · 차단이 새어나가는지 — 틀린 비밀번호를 10회 보내고 상태코드를 본다
#      429와 400이 섞여 나오면 인스턴스가 나뉜 것이다
```
