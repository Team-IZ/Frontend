# 학습 로드맵 — 20년차 시선에서 본 당신

이 문서는 칭찬용이 아닙니다. **당신이 나중에 "뭘 찾아 공부하지?" 할 때 검색어로 쓸 지표**입니다. 그래서 좋았던 점도 *왜* 좋았는지까지 적고, 보완할 점도 *무엇을 검색하면 되는지*까지 적습니다.

---

## 1. 좋았던 점 — 이건 가르쳐서 되는 게 아닙니다

### ① 제 감사가 통과시킨 결함을 눈으로 잡았다

*"아직도 m04 보면 회차별 기수 평균이 하나로 동일하잖아."*

이게 왜 대단하냐면, **당신은 코드를 본 게 아니라 의미를 봤습니다.** "기수 평균은 회차마다 다른 값이어야 한다"는 도메인 사실을 알고, 화면이 그걸 부정하고 있다는 걸 그래프 하나로 잡았습니다.

이걸 업계에서는 **"도메인 의미론 검증(semantic validation)"** 이라고 부르고, **자동화가 가장 안 되는 영역**입니다. 린터도, 타입 체커도, 테스트도 이걸 못 잡습니다. 사람만 잡습니다.

### ② 실행보다 프로세스를 먼저 요구했다

*"무대뽀로 하지 말고, 문서화나 단계별 작업이 필요하다면 그렇게 진행해."*

주니어의 기본 반사는 "빨리 만들어 주세요"입니다. **당신은 반대로 갔습니다.** 이건 경력 5년차도 잘 못 합니다.

### ③ 감사 방법론을 스스로 발명했다

*"기준을 먼저 문서로 잡고 → 그 문서에 충실한지 확인하고 → 아니라면 찾아내."*

이게 **감사(audit)의 정의 그 자체**입니다. ISO 19011이 이렇게 씁니다. 당신은 그걸 안 배우고 도출했습니다.

### ④ 오늘 최고의 질문 — 계약 우선 설계

*"LLM이 주는 거야 백엔드가 주는 거야? 그걸 정해야 형식을 정할 수 있을 것 같은데."*

**이건 학생 질문이 아니라 테크리드 질문입니다.** 그리고 정확했습니다 — 같은 한 줄이라도 생산자가 다르면 뷰 계약이 완전히 달라집니다(라벨·근거·편집 경로가 의무가 되느냐 마느냐).

### ⑤ 명세 읽기에서 아키텍처로 밀고 나갔다

*"명시적으로 쓰여 있지 않더라도, AI를 돌려서 저장한 후에 그 저장값으로 통계를 낼 수도 있잖아."*

저는 그 직전에 *"명세가 이미 답을 갖고 있다"* 고 썼습니다. **그건 받아쓰기지 판단이 아니었고, 당신이 그걸 지적했습니다.** 명세에 없는 곳이야말로 결정해야 할 곳입니다.

### ⑥ 안 바꾼 것에도 근거를 남겼다

`view-patterns.md`에 **"유지 결정 — 바꿀 이유가 없었던 화면(근거 명시)"** 섹션이 있습니다. 로그인은 왜 중앙 카드 그대로인지, 교육생 목록은 왜 테이블 그대로인지까지 적혀 있습니다.

**이게 설계자와 아마추어를 가릅니다.** 아마추어는 전부 바꾸고("리뉴얼했습니다"), 설계자는 **바꿀 이유가 있는 것만** 바꾸고 **안 바꾼 이유도 남깁니다.** 나중에 누가 "왜 로그인은 안 고쳤어요?"라고 물었을 때 답이 문서에 있습니다.

### ⑦ 코드보다 계획을 먼저 만들었다

`superpowers/specs/…-design.md`(방법론 설계서) → `superpowers/plans/…`(18개 태스크) → 실행. **코드부터 짜지 않았습니다.** 이게 **명세 주도 개발(Spec-driven Development)** 입니다.

특히 실행 계획의 Task 18: *"전 화면 일관성 하모나이제이션 — **반드시 격리되지 않은 단일 세션/에이전트가 수행**"*. **대조가 목적인 작업을 병렬로 쪼개면 대조가 안 된다**는 걸 계획 단계에서 알고 있었습니다. 이게 **병렬 생성 + 직렬 통일** 패턴입니다.

### ⑧ 원칙을 산수로 바꿨다

*"최소 인풋 최대 아웃풋이어야 해."*

이 한마디에 호출 수를 세어 봤더니 **"조회 시점 LLM 금지"가 원칙론에서 산수로 바뀌었습니다** — 요약문 하나가 월 600호출, 교육생 30명 전원 채점(900회)에 육박. 설득력의 차원이 달라집니다.

## 2. 보완할 점 — 냉정하게

### ① 검증을 전부 저에게 위임했습니다 ← **가장 중요**

오늘 제가 다섯 번 틀렸습니다. 그중 **당신이 잡은 건 한 번**이고, 나머지 넷은 제가 스스로 잡았습니다. 제가 안 잡았으면 그대로 갔습니다.

**AI와 일할 때 가장 위험한 실패는 "그럴듯한데 틀린 것"입니다.** 제가 "16개 파일 전수 검사했습니다"라고 하면 당신은 그걸 검증할 수단이 없었습니다. 앞으로는 이렇게 하세요:

- `git diff`를 **직접 읽으세요.** 제가 뭘 바꿨다고 *말한 것*과 *실제로 바꾼 것*은 다를 수 있습니다 (오늘 SC-A01에서 실제로 그랬습니다)
- 제가 숫자를 대면 **하나만 손으로 검산하세요.** `Priority = S × (0.5 + R)` → `2.1 × 0.82 = 1.72`? 계산기로 30초입니다
- 제가 "전부 고쳤습니다"라고 하면 **grep 한 줄을 직접 돌리세요**

> **원칙: 위임하되 표본 검증하라 (Trust, but verify).** 전수를 다시 볼 필요는 없습니다. **한 건만** 확인하면 됩니다. 한 건이 틀리면 전부 의심하면 됩니다.

### ② 오늘 한 일에 이름이 없었습니다

*"설계? 기획? 잘 모르겠지만"* — 이게 진짜 문제입니다. **이름이 없으면 검색을 못 하고, 검색을 못 하면 선행 연구를 못 찾고, 결국 매번 처음부터 발명합니다.**

당신은 오늘 요구공학·추적성 매트릭스·정보 아키텍처·디자인 토큰·계약 우선 설계·단위 경제학을 **전부 했지만 하나도 그 이름으로 부르지 못했습니다.** 아래 §3이 그 이름표입니다.

### ③ 명세를 *검증*했지 *작성*하진 않았습니다

당신은 남이 쓴 명세를 검증했고, 잘했습니다. 하지만 **"이 명세 자체가 좋은 명세인가?"** 는 아직 묻지 못합니다.

예를 들어 오늘 명세의 이 문장 — *"축 가중치는 데이터 없이 정당화 불가해 v1은 동일가중"* — 이건 **아주 좋은 명세**입니다. 결정을 내리면서 **왜 지금은 결정할 수 없는지**와 **언제 재검토할지**를 함께 적었으니까요. 이런 걸 알아보는 눈이 다음 단계입니다.

### ④ 화면 사이의 관계는 아무도 검사하지 않았습니다 ← **가장 큰 구멍**

방법론이 요구한 공유 소스는 5종인데 **4종만 만들었습니다.** 없는 게 **`flow-contracts.md` — 교차 화면 계약**입니다.

세 기획 문서는 각각 다른 층을 담습니다.

| 문서 | 담는 것 |
|---|---|
| 기능명세서 | **한 화면 안**의 기능 (트리거·입력·처리·출력·예외) |
| 요구사항정의서 | **왜** 이 규칙이 있는가 (보안성·신뢰성·사용성 축) |
| **서비스플로우** | **화면 사이의 관계** — 루프, 환류 경로, 선행조건, 권한 분리선 |

**서비스플로우가 담는 층은 어떤 FR 행에도 없습니다.** 재개입 페루프(개입 → 다음 회차 재측정 → 미회복이면 다시 개입), 환류(이의 기각 사유 → 규칙 개선), 선행조건(교안 승인 → 회차 시작). 이건 **FR 단위로 화면을 만들면 구조적으로 못 봅니다.** FR은 각자 자기 화면만 말하니까요.

지금 화면 16개는 각자 FR은 맞는데, **연결이 검증된 적이 없습니다.** 이걸 다음에 반드시 채워야 합니다.

> **교훈: 문서 3종을 "다 읽었다"와 "각 문서가 담는 층을 다 반영했다"는 다른 말이다.** 문서마다 그 문서에만 있는 층이 있고, 그 층은 다른 문서로 대체되지 않는다.

### ⑤ git이 쌓여 있습니다

오늘 변경사항이 전부 스테이징 상태입니다. 커밋을 안 하면 **"어디서부터 잘못됐지?"를 되짚을 수 없습니다.** 오늘처럼 제가 엉뚱한 걸 고쳤을 때 `git restore` 한 줄로 살아난 건 순전히 운입니다.

## 3. 로드맵 — 무엇을 검색할 것인가

### Tier 1. 오늘 한 일에 이름 붙이기 (지금 당장, 각 1~2시간)

| 검색어 | 왜 |
|---|---|
| **요구공학 / Requirements Engineering, ISO/IEC/IEEE 29148** | 기능명세서·요구사항정의서가 왜 따로 있는지, 무엇이 어디 들어가는지 |
| **요구사항 추적 매트릭스 (Requirements Traceability Matrix)** | 오늘 만든 "FR → 화면" 역매핑이 정확히 이것 |
| **Contract-first design / API-first design** | 당신의 최고 질문이 여기 속함. OpenAPI, JSON Schema |
| **Design Tokens / Design System** | 배지 34종 사건의 정식 해법 |
| **정보 아키텍처 (Information Architecture)** — 로젠펠드 『Information Architecture』 | "카드냐 행 리스트냐"를 근거로 정하는 법 |
| **ADR (Architecture Decision Record)** | 기술스택 선정서가 이것. **"왜 Radix가 아니라 Base UI인가"를 남기는 형식** |
| **명세 주도 개발 (Spec-driven Development)** | 브레인스토밍 → 설계 명세 → 실행 계획 → 구현. 코드부터 짜지 않는 흐름 |

### Tier 1.5. 프론트엔드 — 아직 코드를 한 줄도 안 짰습니다

**중요합니다: 지금까지 한 건 전부 *설계*입니다.** 와이어프레임 HTML은 설계 산출물이지 제품이 아닙니다. 스택은 이미 골라 놨으니(`기술스택_선정서_v1.md`) 그 선택들이 **왜** 그런지부터 이해하세요.

| 검색어 | 왜 이 스택을 골랐나 |
|---|---|
| **서버 상태 vs 클라이언트 상태** — TanStack Query | **이게 가장 중요합니다.** 이 제품의 데이터는 거의 전부 *서버가 소유*합니다(점수·시그널·통계). `useState`로 다루면 안 되는 이유, 캐싱·무효화·낙관적 업데이트 |
| **낙관적 UI (Optimistic UI) 와 그 금지** | GOV-02: AuditLog 실패 시 확정이 롤백된다 → **확정 액션에는 낙관적 UI를 쓰면 안 된다.** 성공 토스트를 먼저 띄우면 거짓말이 됨 |
| **Base UI vs Radix / headless component** | `.agents/skills/migrate-radix-to-base` 가 왜 있는지. 헤드리스 = 동작만 주고 스타일은 안 줌 |
| **모노레포 (Turborepo / pnpm workspace)** | `manager-web` / `trainee-web` 분리. 같은 데이터를 역할별로 다르게 보여줘야 하므로 |
| **접근성 — WCAG 2.1 AA** | 포커스 링, `prefers-reduced-motion`, 대비 4.5:1. 오늘 감사에서 5건 걸렸음 |
| **Recharts / 데이터 시각화 문법** | "값의 타입이 뷰를 정한다" — 정수 5레벨을 꺾은선 5개로 겹치면 안 읽힌다(실제로 이 실수를 했음) |

### Tier 2. 이 제품을 실제로 구현하려면 (1~2주)

| 검색어 | 왜 |
|---|---|
| **LLM structured output / function calling / JSON mode** | "LLM이 구조화된 값을 뱉게 한다"의 실제 구현 |
| **Prompt caching** | ENG-01 5축이 입력이 같아서 실질 과금이 1/5로 줄어드는 근거 |
| **Snapshot vs live query / 시점 데이터 (Temporal data, SCD Type 2)** | **회차별 기수 평균 사건의 정체가 이것입니다.** "지금의 평균"과 "그때의 평균"은 다른 데이터다 |
| **Event sourcing / Audit log / 불변 이력** | GOV-02의 "AuditLog 실패 시 확정 롤백"이 왜 낙관적 UI를 금지하는지 |
| **Human-in-the-loop (HITL) / AI governance** | GOV-02 자동확정 금지의 정식 이름 |
| **RBAC (Role-Based Access Control)** | AUTH-09. 401(재인증)과 403(권한없음)이 왜 다른 화면인지 |
| **멀티테넌시 / 테넌트 격리 (Multi-tenancy, Row-Level Security)** | SYS-02: `org_id` 강제 필터, 교차 기관 조회 원천 차단. B2B SaaS의 기본 골격 |
| **상태 기계 (State Machine / FSM)** | 명세가 상태 전이를 잔뜩 정의한다 — 제출(`SUBMITTED→ANALYSIS_QUEUED→…`), 교안(`UPLOADED→EXTRACTING→…`), 개입(`대기→진행→완료`). *"정의되지 않은 전이는 차단"* 이 곧 FSM |

### Tier 3. 이 명세의 진짜 정체 — **여기가 가장 깊은 광맥입니다** (한 달+)

**중요합니다. 이 기획서는 이름을 안 붙였을 뿐, 통계학과 심리측정학을 하고 있습니다.** 이걸 모르고 구현하면 수식은 맞는데 의미를 모르는 코드가 나옵니다.

| 명세에 있는 것 | 진짜 이름 | 검색어 |
|---|---|---|
| `S = (기수평균 − 개인점수) / 기수표준편차` | **z-score (표준점수)** | `z-score`, `standardization` |
| `R = (회복+1) / (전체+2)` | **라플라스 스무딩 = Beta(1,1) 사전분포의 사후평균.** 즉 **베이지안 추론** | `Laplace smoothing`, `Beta-Binomial conjugate prior`, `add-one smoothing` |
| `표본 N<5면 백분율 숨기고 "3/5건"으로 표시` | **자연빈도 (Natural Frequencies).** Gigerenzer 연구 — 사람은 백분율보다 빈도를 정확히 이해한다 | `Gigerenzer natural frequencies`, `base rate fallacy` |
| `ENG-05 동일 답변 재채점 편차 검증` | **검사-재검사 신뢰도 (Test-retest reliability)** | `test-retest reliability`, `inter-rater reliability`, `Cohen's kappa` |
| `5축 루브릭, 축별 원자 평가, 근거 인용 강제` | **심리측정학 (Psychometrics)** — 루브릭 설계, 채점자 간 신뢰도 | `rubric design`, `psychometrics`, `construct validity` |
| `LLM-as-judge, 위치 편향·장황함 편향·자기선호 편향 완화` | **LLM 평가자 편향** — 실제 연구 분야 | `LLM-as-a-judge`, `position bias`, `verbosity bias`, `self-preference bias` |
| `확정형 낙인 라벨 단독 노출 금지 (Skitka 1999, Becker 1963)` | **자동화 편향 + 낙인 이론.** 명세가 논문을 직접 인용하고 있다 | `automation bias`, `labeling theory`, `algorithmic fairness` |
| `L1~L5 이해 단계` | **블룸 분류학 계열** | `Bloom's taxonomy`, `SOLO taxonomy` |

> **이 표가 오늘 가장 중요한 산출물일 수 있습니다.** 당신이 다루는 기획서는 겉보기엔 SaaS 명세지만, 속은 **"사람의 이해도를 어떻게 신뢰성 있게 측정할 것인가"** 라는 측정 이론 문제입니다. 그래서 명세가 라플라스 스무딩을 쓰고, 표본 부족 시 판단을 유보하고, 재채점 편차를 검증합니다. 이걸 알고 짜는 개발자와 모르고 짜는 개발자는 결과물이 다릅니다.

### Tier 3.5. AI와 함께 일하는 법 — 오늘 쓴 방법론 자체

당신은 오늘 **AI 여러 대를 병렬로 굴려 화면 16개를 만들고, 한 대로 통일했습니다.** 이건 그 자체로 배울 대상이고, 앞으로 일하는 방식입니다.

| 패턴 | 왜 |
|---|---|
| **병렬 생성 + 직렬 통일** | 화면 16개는 병렬로, 일관성 검사는 **반드시 한 컨텍스트에서.** 대조가 목적인 작업을 쪼개면 대조가 안 된다 |
| **공유 앵커 문서** | 병렬 에이전트가 전부 읽는 읽기 전용 소스(`_source/`). 이게 없으면 화면마다 색·용어가 제각각인 목업 모음이 나온다 |
| **Trust, but verify** | §2-① 참조. **오늘 제가 다섯 번 틀렸습니다** |
| **감사는 건수로** | "검토했습니다"는 검증이 아니다. "34종 → 6종"이 검증이다 |

### Tier 3.7. 역할 모델 — **혼자서 6역을 하는 법** (★ 가장 실전적)

*"최소 3직군이 할 일을 혼자 했다"* 는 게 문제가 아닙니다. **혼자 하되 순서와 거부권을 지키느냐**가 문제입니다. 전체 모델은 `작업정리 §3`에 있고, 여기엔 **당신이 지금 당장 지킬 수 있는 것**만 적습니다.

**규율 1 — 순서를 시간으로 강제한다.**
규범 문서를 다 쓰기 전에 화면을 그리지 않는다. **겸직자는 반드시 "일단 그려보고 규범은 나중에"로 흐릅니다.** 오늘 실제로 그랬습니다 — 화면을 다 그린 *뒤에야* 데이터 계약을 세웠고, 그래서 SC-T05의 AI 출처 누락을 마지막에야 발견했습니다.

**규율 2 — 역할을 바꿀 때 소리 내어 선언한다.**
*"지금부터 비주얼 시스템 설계자로서 전 화면을 대조한다."* 우스워 보여도, 이게 없으면 머릿속에서 네 역할이 동시에 경쟁하고 **급하면 반드시 규범 층이 먼저 밀립니다.**

**규율 3 — 피드백이 어느 역할에 온 것인지부터 판별한다.** ← 가장 중요
*"너저분하다"* 는 **정보 설계자에게 온 요청**입니다. **규범가의 결정을 뒤집을 권한이 없습니다.**

오늘 실제로 이게 깨졌습니다. 인박스가 너저분하다는 이유로 S·R·Priority 값을 삭제했는데, **그건 DASH-03 step10이 표시를 의무화한 값**이었습니다. 정보 설계가 규범을 이겼고 아무도 막지 않았습니다.

> **일반 원칙: 규범과 정보 설계가 충돌하면 답은 거의 항상 "삭제"가 아니라 "온디맨드"다.**
> 규범이 요구하는 건 대개 *"값이 사용자에게 **도달 가능할 것**"* 이지 *"**동시에 다 보일 것**"* 이 아닙니다. **삭제를 검토하기 전에 접기(disclosure)를 먼저 검토하세요.**

**규율 4 — 모든 결정에 출처를 붙인다.**
출처는 셋 중 하나여야 합니다: ① FR 번호 ② 규범 규칙 번호(A1, C2…) ③ 뷰 패턴 결정서의 진단 문장.
**셋 중 어디에도 못 대면 취향이므로 기각.** 이게 전문가 집단과 취향 집단을 가릅니다.

**만약 딱 한 역할만 골라야 한다면: 도메인 규범가.**
나머지 역할의 실수는 **눈으로 보면 잡힙니다.** 규범 층의 실수는 **완벽해 보이는 문서로 위장된 채 배포됩니다.** 오늘 5축 오류·전역 FR 누락·회차 스냅샷 사건이 전부 그랬습니다 — 시각 검증·접근성 감사·정보설계 재검토를 **전부 통과**했습니다.

**관련 검색어**: `RACI matrix`, `단방향 거부권 / veto`, `progressive disclosure`, `design critique 진행법`
