## 1. 🔴 R1 — 팀 해체가 204인데 실제로 반영되지 않습니다

### 재현

```
대상  미프 5차 (projectId 871802ba-d318-428b-ba14-855226e3ab9a)
      E반 (classId 5d5866b3-5522-56c6-abe1-da4ba3ef2dcd)
      "2팀" (teamId fe67cdc0-08f1-4067-8d93-f56bfb15e009) · 0명 · DRAFT

DELETE /projects/{projectId}/teams/fe67cdc0-08f1-4067-8d93-f56bfb15e009
  → 204 No Content

곧바로
GET /projects/{projectId}/teams?classId=5d5866b3-...
  → 200, teams[]에 fe67cdc0-...("2팀")가 그대로 있음

수 분 뒤 페이지를 완전히 새로 고쳐도(캐시 없는 새 요청)
  → 여전히 있음
```

곧바로 온 200 응답을 그대로 옮깁니다 — `teams[]`에 방금 지운 `"2팀"`이 그대로 있습니다.

```jsonc
{
  "teams": [
    { "teamId": "88fdda73-...", "name": "1", "status": "DRAFT", "memberCount": 0, "members": [] },
    { "teamId": "fe67cdc0-...", "name": "2팀", "status": "DRAFT", "memberCount": 0, "members": [] }
    // ← 방금 204로 지운 팀이다
  ],
  "unassignedCount": 25
}
```

### 이중으로 확인했습니다

해체가 실제로는 안 먹혔다는 것을 다른 경로로도 확인했습니다 — 같은 이름(`"2팀"`)으로
새 팀을 또 만들었더니 **409 `DATA_INTEGRITY_VIOLATION`**(제약 위반)이 났습니다. 정말
지워졌다면 그 이름은 비어 있어야 합니다. DB에 그 팀 행이 여전히 살아 있다는 뜻입니다.

```json
{ "status": 409, "code": "DATA_INTEGRITY_VIOLATION", "message": "요청을 처리할 수 없습니다. 데이터 제약 조건에 맞지 않습니다." }
```

### 왜 급한가

- **매니저가 잘못 만든 팀을 되돌릴 방법이 없습니다.** 화면의 유일한 삭제 경로가
  이 API인데, 눌러도 반영되지 않아 잘못 만든 팀이 영구히 남습니다.
- **같은 이름을 다시 못 씁니다.** 위 재현처럼 지운 줄 알고 같은 이름으로 다시 만들면
  409로 거절됩니다 — 사용자에게는 "방금 지웠는데 왜 또 막히지"로 보입니다.
- **팀원이 있던 팀이면 더 나쁩니다.** 스펙은 해체 시 팀원이 미배정으로 돌아간다고
  명시하는데, 팀 자체가 안 지워지는 것이 팀원 배정 해제에도 영향이 있는지 저희는
  확인하지 못했습니다(재현에 쓴 팀은 0명이었습니다) — 팀원이 있는 팀으로도 같은
  증상인지 봐 주시면 좋겠습니다.

### 부탁드리는 것

`DELETE /projects/{projectId}/teams/{teamId}`가 204를 반환하는 경로에서 실제 커밋이
빠지는 지점이 있는지 확인 부탁드립니다. 재현에 쓴 팀(`fe67cdc0-08f1-4067-8d93-f56bfb15e009`)을
그대로 남겨 뒀습니다 — 필요하시면 이 팀으로 바로 재현하실 수 있습니다.

## 2. 🟡 R2 — `teamFormationStage`가 실제 팀 존재와 어긋납니다

### 재현 — 같은 반, 같은 순간에 두 조회가 다른 말을 합니다

```
대상  같은 프로젝트 · 같은 classId(E반)

GET /projects/{projectId}/teams?classId=E반
  → teams: [ { teamId: "88fdda73-...", name: "1", status: DRAFT, memberCount: 0 } ]
  (팀이 1개 있다)

GET /projects/{projectId}/submissions?classId=E반
  → teamFormationStage: "NOT_STARTED", teams: [], summary.teamCount: 0
  (팀이 0개라고 한다)
```

**서로 다른 조회가 아니라 정말 같은 순간·같은 반입니다.** `/teams`는 팀 1개를 돌려주고
`/submissions`는 팀이 0개(`NOT_STARTED`)라고 답합니다.

### 자동 배분 자체는 진짜 상태를 압니다 — 표시만 틀립니다

같은 상태에서 자동 배분을 실행했더니, 실행 조건 판정은 `/teams`가 맞다는 쪽으로
정확히 동작했습니다. **409로 막혔고, message도 정확했습니다:**

```json
{ "status": 409, "code": "AUTO_ASSIGN_NOT_ALLOWED", "message": "그 반에 이미 팀이 편성되어 있어 자동 배분을 실행할 수 없습니다." }
```

즉 **쓰기 판정(자동 배분 실행 조건)은 정확한데, 읽기 판정(`teamFormationStage`)만
틀렸습니다.** 화면은 `teamFormationStage`만 보고 배지("편성 전")와 버튼 노출을
정하므로("화면은 이 필드만 보고 판정한다" — 33차 R2), 사용자에게는 실제로 팀이 있는데
"편성 전"으로 보이고 자동 배분 버튼이 계속 떠 있다가 누르면 막히는 것으로 보입니다.

### 참고 — 다시 보니 일관되지 않았습니다

이후 페이지를 새로 고치자 한 번은 `teamFormationStage`가 `FORMING`(정확)으로 나온
적도 있습니다. 그런데 §1의 해체 시도(실패) 이후 다시 새로 고치자 또 `NOT_STARTED`로
돌아갔습니다. 시간이 지나면 저절로 맞는 것도, 항상 틀린 것도 아니라 — 캐싱이나 읽기
일관성 쪽을 의심하고 있는데 저희 쪽에서는 원인을 더 좁히지 못했습니다.

### 부탁드리는 것

`GET /projects/{projectId}/submissions`의 `teamFormationStage`·`teams[]`·
`summary.teamCount` 계산이 `GET /projects/{projectId}/teams`와 같은 원본을 보는지,
계산에 캐시가 끼는지 확인 부탁드립니다. §1의 재현 프로젝트·반이 그대로 있으니 같은
조합으로 재현하실 수 있습니다.

## 3. ℹ️ R3(질문) — 반 하나를 통째로 비우는 API가 있으면 좋겠습니다

지금 반 하나를 자동 배분으로 짜고 다시 짜려면, 팀마다 `DELETE`를 순서대로 눌러야
합니다. 자동 배분이 **한 번에 여러 팀을 만드는** 액션이라, 되돌리는 쪽도 한 번에
되면 좋겠습니다.

지금 급한 요청은 아닙니다 — R1(해체 자체가 안 먹히는 버그)이 먼저 고쳐져야 이
기능도 검증할 수 있습니다. 계획에 있는지, 있다면 어떤 모양일지만 여쭤봅니다.

### 여쭙는 것

- `그 반의 DRAFT 팀 전부 해체` 같은 일괄 API를 낼 계획이 있으신가요?
- 있다면 **CONFIRMED 팀도 포함**인지, **DRAFT만**인지 궁금합니다 — 화면은 확정 전
  되돌리기 용도로 쓸 생각이라 DRAFT만이어도 충분합니다.
- 없다면 지금처럼 프론트가 팀 수만큼 `DELETE`를 순차로 부르는 방식으로 갑니다 —
  그러려면 R1이 먼저 고쳐져야 합니다.

## 4. 저희가 이번에 하는 것

R1이 고쳐지기 전까지는 화면이 더 할 수 있는 게 없습니다 — 해체 버튼을 누르면 204를
받고 목록을 다시 그리는 것까지가 화면의 역할이고, 그 이후 서버가 실제로 지우는지는
화면이 확인할 방법이 없습니다.

R2는 화면이 자체 판정을 만들지 않습니다 — 33차 R2가 "화면은 `teamFormationStage`만
보고 정한다"고 정한 것을 그대로 따릅니다. 화면이 `/teams`의 팀 개수로 자체 국면을
계산하면 규칙이 두 곳에 생기고, 다음에 계산 방식이 바뀌면 또 갈립니다.
