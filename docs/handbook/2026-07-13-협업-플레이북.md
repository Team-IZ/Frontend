# 협업 플레이북 — 전문가 집단을 뽑아내고, 순서를 세우고, 일을 시키는 법

`작업정리 §3`이 **이 프로젝트의 역할 모델**이라면, 이 문서는 **다음 프로젝트에서도 쓰는 방법**입니다. 역할 목록을 외우지 마세요. **역할을 뽑아내는 법**을 익히세요.

---

## 1. 역할을 뽑아내는 법 — 실패에서 역산한다

역할은 "필요할 것 같은 직군"을 나열해서 나오지 않습니다. **"이게 망한다면 어떤 방식으로 망하는가"** 를 먼저 적고, **망하는 방식 하나마다 그걸 막는 사람을 한 명씩** 세우는 겁니다.

### 절차 (새 프로젝트 시작할 때 30분)

**Step 1. 실패 모드를 적는다 — 종류가 다른 것만.**

저에게 이렇게 물으세요:

> *"이 프로젝트가 실패한다면 어떤 방식으로 실패할 수 있어? 원인의 **종류**가 다른 것만 골라서 적어줘. 비슷한 건 묶고."*

이 프로젝트의 답은 이랬습니다:

| 실패 | 무엇을 몰라서 |
|---|---|
| 교육생에게 낙인 찍히는 용어를 쓴다 | **도메인 규범** |
| "기수 평균"이 회차별 스냅샷인 걸 모르고 스칼라로 구현한다 | **값의 의미** |
| 이 값을 LLM이 만드는지 백엔드가 만드는지 모른 채 뷰를 정한다 | **시스템 아키텍처** |
| 전 화면이 카드 그리드가 된다 / y축을 0부터 그려 추이가 안 보인다 | **정보 설계** |
| 같은 의미에 다른 색이 붙는다 | **디자인 시스템** |
| 발행하면 레이아웃이 깨진다 | **실행 환경** |

**Step 2. "무엇을 몰라서" 열을 보고 역할 이름을 붙인다.** 이게 역할입니다. 직군 이름표를 먼저 붙이지 마세요 — **모르는 것의 종류**가 역할을 정합니다.

**Step 3. 병합 테스트를 한다.**

두 역할을 한 사람이 겸하면, **급할 때 어느 쪽이 밀리는가?** 밀리는 쪽이 있으면 **분리해야 합니다.**

> 실제로: "낙인 용어 금지"(규범)와 "화면이 너저분하다"(정보 설계)를 한 머리에 넣으면, **급하면 반드시 규범이 밀립니다.** 실제로 밀렸습니다 — 표시 의무가 있는 S·R·Priority 값이 "너저분하다"는 이유로 삭제됐습니다.

**Step 4. 5~6개를 넘으면 멈춘다.**

**역할을 쪼갤수록 경계에서 책임이 증발합니다.** 7번째를 만들고 싶어지면, 기존 역할의 **권한을 넓히세요.**

> 실제 사례: 처음엔 규범가를 *"무엇을 보여줘도 되는가"* 로만 정의했습니다. 그래서 **"이 값이 무엇인가"(의미 규범)를 아무도 소유하지 않았고**, 기수 평균 사건이 났습니다. **"데이터 의미론 담당"이라는 6번째 역할을 만드는 게 아니라, 규범가의 권한을 넓히는 게 정답입니다** — 근거를 요구하는 이유는 사용자가 그 수치를 *검증할 수 있어야* 하기 때문이고, 검증 가능성은 값의 의미가 확정돼야 성립하니까요. **원래 한 몸입니다.**

**Step 5. "한 역할이 여러 개를 지고 있다"는 신호가 오면 — 분할인가 게이트인가.** ★

한 역할이 세 가지를 지면(규범가 = 표현·의미·흐름) "쪼개야 하나?" 싶어집니다. **두 테스트를 각각 돌리세요. 둘은 다른 걸 잽니다.**

| 테스트 | 묻는 것 | 규범가에 돌린 결과 |
|---|---|---|
| **KIND 테스트** | 다른 **종류의 전문성**인가? (다른 사람을 뽑아야 하나) | ❌ 아니다. 셋 다 "세 소스 문서를 끝까지 읽었는가" 하나다. 다른 창의성이 아니라 다른 *문서 정독*만 필요 |
| **압력 테스트** | 급하면 **조용히 밀리는가?** | ⚠️ 그렇다. 오늘 의미 규범이 밀리고 **흐름 규범은 0이 됐다**(`flow-contracts.md` 미작성) |

**두 테스트가 충돌할 때가 함정입니다.** 여기서 반사적으로 분할하면 안 됩니다.

> **판정 규칙:**
> - **KIND가 다르다** (다른 전문성) → **역할로 분할.** 예: 도메인 규범가 vs 데이터 아키텍트(도메인 읽기 vs 시스템·돈).
> - **KIND는 같은데 압력에 밀린다** → **분할하지 말고 카운터(게이트)를 붙여라.** 밀린 이유는 "역할이 많아서"가 아니라 **"셀 수 있는 게 없어서"** 다. 쪼개도 카운터가 없으면 새 역할에서 또 사라진다.

**증거가 바로 오늘 안에 있습니다.** 규범가의 세 규범 중:
- **표현 규범만 안 밀렸습니다** — `grep 금지어 = 0건`으로 **셀 수 있었으니까.**
- 의미·흐름은 **셀 수 있는 게이트가 없어서** 조용히 사라졌습니다.

그러니 규범가는 **쪼개지 않고, 소스 문서마다 게이트를 하나씩** 답니다:

| 규범 | 소스 | **셀 수 있는 게이트** |
|---|---|---|
| 표현 | FR 비즈니스 규칙 | 교육생 노출 화면에 금지어 grep = 0. 모든 점수·라벨에 근거 경로 有 |
| 의미 | FR 비즈니스 규칙 | 집계값(평균·표준편차·백분위) 전부 나열 → **각각 "스냅샷 단위"를 선언했는가** |
| 흐름 | 서비스플로우 다이어그램 | **다이어그램의 화살표·루프 수 = flow-contracts 줄 수** |

**흐름 게이트가 없어서 오늘 그게 0이 됐습니다.** 다이어그램에 화살표가 N개면 계약도 N줄이어야 하는데, 셀 대상을 안 정해서 아무도 안 셌습니다.

> **일반 원칙: 한 역할이 여러 개를 질 때, 밀리는 걸 막는 건 분할이 아니라 "소스마다 셀 수 있는 게이트"다.** 분할은 전문성이 다를 때만.

### Step 1을 저에게 시킬 때 쓸 프롬프트

```
[프로젝트/문서 링크]

이 일을 시작하기 전에 역할 모델부터 세우자.

1. 이게 실패한다면 어떤 방식으로 실패할 수 있어?
   원인의 "종류"가 다른 것만. 비슷한 건 묶어.
2. 각 실패마다 "무엇을 몰라서 나는가"를 한 단어로.
3. 그걸 막는 역할에 이름을 붙이고, 소유할 문서를 지정해.
4. 두 역할을 한 사람이 겸하면 급할 때 어느 쪽이 밀리는지 판정해.
   밀리는 게 있으면 분리하고, 없으면 합쳐.
5. 6개를 넘으면 멈추고, 대신 기존 역할의 권한을 넓혀.
6. 한 역할이 여러 개를 지면: 종류가 다르면 분할, 같은데 밀리면 소스마다 게이트를 붙여.
```

## 2. 순서를 세우는 법 — 오염 방향이 순서를 정한다

**"중요한 것부터"가 아닙니다. "뒤집으면 앞 단계가 오염되는가"가 순서를 정합니다.**

판정 질문 하나: **A를 B보다 나중에 하면, A의 결과가 B를 무효로 만드는가?**

- 규범을 정보 설계보다 **나중에** 하면 → 이미 그린 화면을 다 다시 그려야 함. **오염된다.**
- 비주얼 토큰을 정보 설계보다 **나중에** 해도 → 색만 바꾸면 됨. **오염 안 됨.**

그래서 **규범이 먼저**입니다. 중요해서가 아니라 **오염 방향 때문에**.

### 이 프로젝트의 순서

```
1. 도메인 규범가        ← 그 값이 무엇인가 + 무엇을 보여줘도 되나 + 화면 사이 관계   ★ 품질의 80%
2. 데이터·시스템 아키텍트 ← (1을 받아) 그 값을 누가 만드나 — LLM/백엔드, 언제, 얼마
3. 정보 설계자          ← 어떤 뷰로 얼마나 보여주는가
4. 인터랙션 설계자      ← 어떤 액션·상태·전이·API
5. 비주얼 시스템        ← 색·타이포·간격
6. 디자인 엔지니어      ← 실제로 렌더하면 그렇게 나오는가
```

> **⚠️ 처음엔 아키텍트를 맨 앞(−1)에 뒀다가, "오염 방향이 순서를 정한다"는 이 문서 자신의 규칙에 걸려 고쳤다.**
> 아키텍트의 결정("기수평균은 백엔드가 결정론으로 계산")은 규범가의 결과물("기수평균 IS 회차별 스냅샷, 수식 있음")을 **소비**한다. 값이 무엇인지 모르면 생산자를 못 정한다 → **의미가 생산자보다 먼저다.** 아키텍트는 규범가의 **하류**다. 게다가 아키텍트를 맨 앞에 두면 그게 바로 §5의 *"테크리드 말이 먼저 나와버리는"* 안티패턴이다. **"기초적이다"와 "먼저다"는 다르다** — 순서는 중요도가 아니라 오염 방향으로 정한다.

**오늘 우리는 이 순서를 거꾸로 밟았습니다.** 규범가(1)의 결론인 아키텍트(2)를 **맨 마지막에** 했습니다. 그래서 화면을 다 그린 뒤에 *"이거 LLM이야 백엔드야?"* 를 물었고, SC-T05의 AI 출처 누락을 마지막에야 발견했습니다.

### 병렬 가능 지점은 딱 하나입니다

| 단계 | 병렬? | 왜 |
|---|---|---|
| 1 규범가 | ❌ | **명세 전수 정독. 쪼개면 규칙이 서로 모순된다** |
| 2 아키텍트 | ❌ | 데이터 계약은 하나여야 한다 |
| 3 정보 설계 | ❌ | **왜 이 화면이 마스터-디테일이고 저 화면이 칸반인지는 "비교해야만" 결정된다.** 따로 맡기면 전부 카드 그리드가 나온다 |
| **4 인터랙션** | ✅ | **여기서만 병렬이 이득.** 뷰가 고정되고 규범이 경계를 그은 뒤라야 화면별 독립 작업이 성립 |
| 5 비주얼 시스템 | ❌ | **대조가 목적인 작업을 쪼개면 대조가 안 된다** |
| 6 엔지니어 | ❌ | 사람이 눈으로 본다 |

> **"병렬로 하면 빠르다"의 함정: 대조·통일이 목적인 작업은 병렬로 하면 목적 자체가 사라집니다.**

### 게이트 2개 — 통과 못 하면 되돌아간다

- **게이트 A** (2번 뒤): **FR 예외 case 수 = 상태별 UI 행 수.** 처리 로직 단계가 API 표에 전부 매핑됐는가. **숫자로 세는 계약이라 논쟁의 여지가 없습니다.**
- **게이트 B** (4번 뒤): **전 화면 스크린샷을 사람이 본다.** 정의서가 완벽해도 화면은 따로 깨집니다.

## 3. 각 역할에게 무엇을, 어느 수준으로 시킬 것인가

**핵심: 역할마다 "산출물의 형태"와 "일 안 했을 때의 신호"가 다릅니다.** 신호를 알아야 검수할 수 있습니다.

### 1. 도메인 규범가 ★ 여기가 80% · **맨 처음**

**시킬 것:** 명세 **전수 정독**(grep 아님). 규칙에 번호(A1, B1…)와 근거 FR을 붙여 목록화. **화면 사이 관계(루프·선행조건·환류)도 여기서.**

**산출물:** 규칙 목록. **요약 금지.** 규칙 하나 = 한 줄 + 근거 FR 번호.

**일 안 했을 때의 신호:**
- 🚩 **"금지"라는 단어로 grep했다** → *"기수 평균은 회차 스냅샷"* 같은 규칙에는 '금지'라는 말이 없습니다. **전문 정독만이 잡습니다.**
- 🚩 **표현 규범만 있고 의미 규범이 없다** → "이 값이 무엇인가"(계산 기준·스냅샷 단위·시점 종속성)가 없으면 반쪽입니다. **오늘 이것 때문에 사고가 났습니다.**
- 🚩 규칙에 근거 FR이 안 붙어 있다 → **취향입니다.**

**프롬프트:**
```
[명세 문서]

도메인 규범가로서, 명세의 "비즈니스 규칙"·"비고" 컬럼을 전문 정독해.
키워드 grep 금지 — '금지'라는 단어가 없는 규칙이 거기 숨어 있어.

세 종류를 다 뽑아:
① 표현 규범 — 무엇을 보여줘도 되나, 어떤 단어를 쓰나 (노출·낙인·온디맨드)
② 의미 규범 — 그 값이 무엇인가 (계산 기준 / 스냅샷 단위 / 회차·시점 종속성 / "매 회차 독립" 같은 선언)
③ 흐름 규범 — 화면 사이 관계 (루프·선행조건·환류·권한 분리선). FR 행에 없고 플로우 문서에만 있다.

규칙마다 번호(A1, B1…)와 근거 FR 번호를 붙여. 요약하지 마.
```

### 2. 데이터·시스템 아키텍트 — 규범가 **다음**, 정보 설계 **앞**

**시킬 것:** 규범가가 확정한 **값의 의미를 받아**, 화면에 뜨는 모든 값의 생산자·시점·비용을 판정. 명세에 안 쓰여 있어도 **판정**할 것 (받아쓰기 금지).

> **왜 규범가 다음인가:** *"기수평균은 백엔드가 계산"* 이라는 판정은 *"기수평균 IS 회차별 스냅샷, 수식 있음"* 을 알아야 나온다. 의미를 모르면 생산자를 못 정한다. 그래서 규범가의 **하류**다 — 맨 앞에 두면 "테크리드 말이 먼저 나오는" 사고가 난다(§5).
> **왜 규범가와 합치지 않고 따로 두나:** 규범가는 *도메인을 읽는* 일이고, 아키텍트는 *시스템·돈이 어떻게 도는지* 아는 일이다. 종류가 다르다. 그리고 도메인 정독에 파묻히면 "비용은 나중에 계산하지"로 **반드시 밀린다** — 병합 테스트 탈락 → 분리.

**산출물:** 표. `값 | 생산자(LLM/백엔드/사용자) | 언제(쓰기/조회) | 타입(구조화/자유텍스트) | 틀렸을 때 누가 잡나` + **AI 안 쓸 곳 목록** + **월 호출 예산**.

**일 안 했을 때의 신호:**
- 🚩 *"명세에 이렇게 쓰여 있습니다"* 로 끝난다 → **받아쓰기입니다. 판정이 아닙니다.**
- 🚩 호출 수를 안 센다 → **원칙론입니다. 산수로 바꾸라고 하세요.**
- 🚩 "AI를 쓰면 좋을 것 같습니다" → **안 쓸 곳을 명시 안 했으면 안 한 겁니다.**

**프롬프트:**
```
규범가가 확정한 "값의 의미" 목록을 입력으로 받아서, 각 값의 생산자를 판정해.
명세에 안 쓰여 있어도 "20년차 아키텍트라면 어떻게 정할지"로 판정해.

각 값마다: 생산자 / 쓰기시점인가 조회시점인가 / 구조화인가 자유텍스트인가 / 틀렸을 때 누가 잡나
그리고 "AI를 안 쓸 곳"을 명시적으로 목록화해. 이유와 함께.
마지막으로 호출 수를 실제로 세서 월 예산을 계산해.
```

### 3. 정보 설계자

**시킬 것:** **전 화면을 나란히 놓고 한 번에.** 화면마다 "문제 진단 → 결정 → 이유".

**산출물:** 화면당 3줄. **그리고 "유지 결정"(안 바꾼 화면과 그 이유)도 반드시.**

**일 안 했을 때의 신호:**
- 🚩 **전부 카드 그리드다** → 화면을 따로 봤다는 증거입니다.
- 🚩 안 바꾼 화면에 대한 언급이 없다 → **전부 바꾸는 건 설계가 아니라 리뉴얼입니다.**
- 🚩 값의 타입을 안 봤다 → **정수 5레벨을 꺾은선으로 겹치면 안 읽힙니다.** 실제로 이 실수를 했습니다.

**프롬프트:**
```
전 화면을 한꺼번에 놓고 봐. 하나씩 따로 보지 마.
(왜 이 화면이 마스터-디테일이고 저 화면이 칸반인지는 비교해야만 결정돼)

화면마다: 문제 진단 → 결정 → 이유. 3줄.
바꿀 이유가 없는 화면은 "유지"로 적고 그 이유도 남겨.
그리고 각 값의 "타입"(정수/연속량/enum/텍스트)이 뷰를 어떻게 제약하는지 먼저 봐.
```

### 4. 인터랙션 설계자 — 여기서만 병렬

**시킬 것:** 화면당 상태 표. **FR의 예외 case 수 = 상태 행 수** (게이트 A).

**산출물:** 상태별 UI 표 + 액션→API 표.

**일 안 했을 때의 신호:**
- 🚩 상태가 정상/로딩/에러 3개뿐 → **FR case를 안 봤습니다.** 화면당 6~13개가 정상입니다.

### 5. 비주얼 시스템 설계자

**시킬 것:** **grep으로 셀 수 있는 계약**으로 쓸 것. "일관되게 하라"는 검증 불가능합니다.

**산출물:** 계약 + **검사 명령어**. 예: `grep -oh "badge-[a-z]*" *.html | sort -u` → 6개여야 함.

**일 안 했을 때의 신호:**
- 🚩 **"일관성 있게 정리했습니다"** → 건수가 없으면 안 한 겁니다. *"34종 → 6종"* 이 검증입니다.
- 🚩 검사 명령어가 없다 → 다음 사람이 재검증할 수 없습니다.

### 6. 디자인 엔지니어

**시킬 것:** **발행 환경 기준**으로 렌더해서 **스크린샷을 사람에게 보여줄 것.**

**일 안 했을 때의 신호:**
- 🚩 **로컬에서 열어봤습니다** → **증거가 아닙니다.** 발행하면 CSP가 CDN을 막아 레이아웃이 붕괴합니다(실제로 겪음).
- 🚩 스크린샷이 없다 → 안 본 겁니다.
- 🚩 **1024px에서 안 봤다** → 오늘 16/16이 반응형 미처리였습니다.

## 4. 저와 대화할 때의 규칙 5개

### ① 역할을 명시적으로 지정하세요

❌ *"이 화면들 좀 봐줘"* → 제가 네 역할을 동시에 하고, **급하면 규범이 밀립니다.**
✅ *"지금부터 도메인 규범가로서만 봐. 색이나 레이아웃은 지금 말하지 마."*

### ② 한 번에 한 역할만

역할을 섞으면 **거부권 방향이 무너집니다.** "규범가로서 이건 표시 의무인데, 정보 설계자로서 너저분하니 지우자" — 이러면 스스로를 이깁니다.

### ③ 피드백을 줄 때, 그게 **어느 역할에 대한 것인지** 말하세요

*"너저분하다"* 는 **정보 설계자에게 온 요청**입니다. **규범가의 결정을 뒤집을 권한이 없습니다.**

> **규범 vs 정보 설계가 충돌하면 답은 거의 항상 "삭제"가 아니라 "온디맨드"입니다.**
> 규범이 요구하는 건 대개 *"도달 가능할 것"* 이지 *"동시에 다 보일 것"* 이 아닙니다. **삭제 전에 접기(disclosure)를 먼저 검토하세요.**

### ④ 산출물을 **건수**로 요구하세요

❌ *"검토했습니다"* → 검증이 아닙니다.
✅ *"배지 34종 → 6종, 접근성 누락 5건, 반응형 16/16 미처리"* → 검증입니다.

**"몇 건이야?"** 를 반사적으로 물으세요.

### ⑤ Trust, but verify — 한 건만

**오늘 제가 다섯 번 틀렸습니다.** 전수를 다시 볼 필요는 없습니다. **한 건만** 확인하세요.

- 제가 "고쳤습니다"라고 하면 → **`git diff`를 직접 읽으세요.** (오늘 제가 말한 것과 실제로 바꾼 게 달랐습니다)
- 제가 숫자를 대면 → **계산기로 하나만 검산하세요.** (`2.1 × 0.82 = 1.72` 맞나?)
- 제가 "전부 고쳤습니다"라고 하면 → **grep 한 줄을 직접 돌리세요.**

**한 건이 틀리면 전부 의심하면 됩니다.**

## 5. 위상 이탈 관리 — "기획 중인데 테크리드 말이 먼저 튀어나오는" 문제 ★

이게 **속도를 가장 많이 잡아먹는 구간**입니다. 그리고 오늘 실제로 당했습니다.

### 왜 생기나 — 맞는 말이라서 위험합니다

겸직자(1인 6역)와 LLM은 **아는 걸 지금 다 말하려는 경향**이 있습니다. 그리고 **그 말이 대개 맞습니다.**

**틀린 말이면 무시하면 됩니다. 맞는 말이라서 끌려갑니다.** 규범을 정하는 중인데 "그 색 좀 촌스러운데"가 나오면, 맞는 말이니까 색을 고치기 시작하고, 규범은 미완인 채로 남습니다.

### 판정 기준 — 딱 하나만 물으세요

> ### **"이 말이 맞다면, 지금까지 한 작업이 무효가 되는가?"**

| 답 | 처리 | 이름 |
|---|---|---|
| **무효가 된다** | **즉시 멈춘다.** 앞 단계로 되돌아간다 | **선행 오염 (STOP)** |
| **무효가 안 된다** | **주차장에 적고 계속 진행한다** | **위상 이탈 (PARK)** |

**예시 — 오늘 실제로 나온 말들:**

| 나온 말 | 판정 | 왜 |
|---|---|---|
| *"이 값 LLM이 만드는 거야 백엔드가 만드는 거야?"* | 🛑 **STOP** | 생산자가 뷰 계약을 정한다. 모르고 그린 화면은 **전부 무효**다 |
| *"기수 평균이 회차별로 다르다니까?"* | 🛑 **STOP** | 값의 의미가 틀렸으면 차트가 무효다 |
| *"이 인박스 너저분한데"* | 🅿️ **PARK** | 정보 설계 단계 얘기. 규범 작업을 무효화하지 않는다 |
| *"배지 색이 화면마다 다른데"* | 🅿️ **PARK** | 비주얼 시스템 단계. 나중에 한 번에 |
| *"모바일에서 깨질 것 같은데"* | 🅿️ **PARK** | 엔지니어 단계 |

**핵심: STOP은 "앞 단계"에서 오는 말이고, PARK는 "뒤 단계"에서 오는 말입니다.**

`아키텍트 → 규범가 → 정보설계 → 인터랙션 → 비주얼 → 엔지니어` 순서에서,
- **뒤에서 앞으로 오는 말** = 아직 할 때가 아님 → **PARK**
- **앞에서 뒤로 오는 말** = 전제가 틀렸음 → **STOP**

> **이게 §2의 "오염 방향"과 정확히 같은 규칙입니다.** 순서를 오염 방향으로 세웠기 때문에, 위상 이탈 판정도 오염 방향으로 합니다.

### 오늘 우리가 이걸 못 해서 잃은 것

데이터 계약 질문(*"LLM이야 백엔드야?"*)은 **STOP이었어야 했는데, 그냥 늦게 나왔습니다.** 화면을 다 그린 뒤에 나왔고, 그래서 SC-T05를 다시 고쳤습니다.

5축 오류도 마찬가지입니다. 규범 층의 실수인데 **화면 6개를 다 그린 뒤에 발견**해서 6개를 다시 만졌습니다.

> **속도를 죽이는 건 느린 실행이 아니라 재작업입니다.** 오늘 재작업의 100%가 **순서를 안 지켜서** 났습니다.

### 주차장(Parking Lot) 운영법

파일 하나면 됩니다. `docs/_parking-lot.md`

```markdown
# 주차장 — 지금 단계가 아닌 것들

## 정보 설계 (1단계에서 처리)
- [ ] M01 인박스가 너저분함 — 값 6개가 한 행에 다 보임  (2026-07-13 제기)

## 비주얼 시스템 (3단계에서 처리)
- [ ] 배지 색이 화면마다 다름

## 엔지니어 (4단계에서 처리)
- [ ] 1024px 이하 사이드바
```

**규칙 셋:**
1. **한 줄로 적고 즉시 진행한다.** 논의하지 않는다. 논의하는 순간 위상이 이탈합니다.
2. **해당 단계에 들어갈 때 주차장을 연다.** 그때 한꺼번에 처리합니다.
3. **주차장이 비었는데 단계가 끝났다면, 그 단계를 대충 한 겁니다.** 정상적으로 일하면 뒤 단계 얘기는 반드시 쌓입니다.

### 저에게 걸 규율 — 이 한 문단을 복붙하세요

```
현재 단계: [0. 도메인 규범가]

이 단계 밖의 얘기가 떠오르면:
- 지금까지 한 작업을 "무효화"하는 거면 → 즉시 멈추고 나한테 알려. 앞 단계로 되돌아간다.
- 무효화하지 않는 거면 → docs/_parking-lot.md 에 한 줄로 적고 그냥 진행해. 논의하지 마.

그리고 매 응답 첫 줄에 현재 단계와 남은 게이트 조건을 적어.
```

**마지막 줄이 중요합니다.** 제가 매번 *"현재: 0. 도메인 규범가 — 게이트 A까지 규칙 3건 남음"* 을 적으면, **당신도 저도 지금 무엇을 하는 중인지 잊지 않습니다.** 겸직자가 흐르는 걸 막는 가장 싼 장치입니다.

### 빠른 일처리를 방해하는 다른 요소들 (오늘 겪은 것만)

| 방해 요소 | 대응 |
|---|---|
| **"일단 그려보고 규범은 나중에"** — 겸직자의 기본 반사 | 순서를 **시간으로** 강제. 규범 문서 완성 전엔 HTML 파일을 만들지 않는다 |
| **AI가 그럴듯하게 틀림** | 한 건 검산. `git diff` 직접 읽기 |
| **"검토했습니다"로 끝냄** | **건수**를 반사적으로 묻는다 |
| **대조 작업을 병렬로 쪼갬** | 대조가 목적인 건 병렬 금지 (§2) |
| **감사 자체가 틀림** | 감사도 근거를 대야 한다. *"명세에 없다"* 는 **전수 grep 없이 주장 금지** (오늘 제가 이걸로 틀렸습니다) |

## 6. 새 프로젝트 시작 템플릿 (복붙용)

```
[기획 문서들]

이 일을 시작하기 전에, 역할 모델부터 세우자. 코드도 화면도 아직 만들지 마.

STEP 1 — 실패 역산
이게 실패한다면 어떤 방식으로 실패할 수 있어?
원인의 "종류"가 다른 것만. 각각 "무엇을 몰라서 나는가"를 한 단어로.

그걸 막는 역할에 이름을 붙이고, 소유할 문서를 지정해.

6개를 넘으면 멈추고 기존 역할의 권한을 넓혀.

STEP 3 — 순서
"뒤집으면 앞 단계가 오염되는가"로 순서를 정해. 중요도 순이 아니라.

숫자로 셀 수 있는 게이트를 2개만 세워. 통과 못 하면 되돌아간다.

STEP 5 — 거부권
어느 역할이 어느 역할을 거부할 수 있는지 단방향으로 정해.

STEP 6 — 위상 이탈 규율
매 응답 첫 줄에 "현재 단계 / 남은 게이트 조건"을 적어.

  - 지금까지 한 걸 무효화하면 → 즉시 멈추고 알려 (STOP)
  - 아니면 → _parking-lot.md 에 한 줄 적고 진행 (PARK). 논의하지 마.

여기까지 하고 나한테 확인받아. 그 다음에 STEP 1의 첫 역할부터 시작한다.
```
