# 권한 4계층 구조 (RBAC)

> 소스: 기능명세서_v8 AUTH-01~11, ORG-01~03, GOV-01~03 + `01-decision-log.md` D63·D64·D66·D67·D68.
> 핵심: 실제 `role` enum은 **3개**(SUPER_ADMIN / MANAGER / TRAINEE)뿐이다. "4계층"은 MANAGER 역할 안에서 권한 묶음을 총괄/담당 둘로 쪼갠 결과다(별도 4번째 역할 아님).

## 왜 "4번째 역할"이 아니라 "권한 2단 분리"인가 (D63)

기수를 매니저가 만든다면 "담당 기수가 있어야 할 매니저가 아직 없는 기수를 만든다"는 닭-달걀 모순이 생기고, 그렇다고 슈퍼어드민이 만들면 테넌트(기관) 경계를 침범한다. 이를 풀 때 두 안을 저울질했다.

- **안 A** — "기관 관리자"라는 4번째 역할 신설
- **안 B** — 매니저 역할 하나 안에 권한 묶음만 총괄/담당으로 분리

**B를 택한 이유:**
1. 실제 타깃은 소규모라 총괄·담당을 겸직하는 경우가 대부분이다.
2. 역할을 늘리면 RBAC·온보딩·화면 게이팅 비용이 배로 늘어난다.
3. 명세(AUTH-09)가 이미 "역할은 권한 묶음"이라는 답을 갖고 있었다(`ORG_MANAGE`, `COHORT_MANAGE` 같은 permission code를 역할과 별개로 나열).
4. 나중에 필요해지면 권한→역할 승격이 역방향보다 쉽다.

유일 예외는 대기업의 엄격한 직무 분리 요구가 실제로 발생할 때뿐이다(그때 권한을 별도 역할로 승격).

**부트스트랩 체인** (닭-달걀 해소 순서): 슈퍼어드민 → 기관 생성 + 첫 총괄 매니저 초대 → 총괄이 기수·매니저 세팅 → 담당이 기수 운영.

## 4계층 표

| 계층 | `role` 값 (AUTH-09) | 구분 기준 | 관할 범위 | 누가 부여하나 | 핵심 permission code | 대표 화면 | 대표 업무 | 못 하는 것(경계) |
|---|---|---|---|---|---|---|---|---|
| **① 슈퍼어드민** | `SUPER_ADMIN` | 별도 역할 | 전체 기관(테넌트) | 시스템(최초 발급) | 기관 관리·전역 운영 | SC-S01 플랫폼 콘솔 | 기관 생성, **첫 총괄 매니저 초대(부트스트랩)뿐** | 기수·반·명단·프로젝트 등 특정 기관 내부 운영에는 개입 안 함(테넌트 경계). 매니저 초대·배정도 부트스트랩 이후엔 관여 안 함(D64) |
| **② 총괄 매니저** | `MANAGER` (+`ORG_MANAGE`) | 같은 역할의 권한 묶음(상위) | 기관 전체 | 슈퍼어드민이 최초 1인 지정 → 이후 총괄이 다른 매니저 초대 | `ORG_MANAGE`, `COHORT_MANAGE`, `MANAGER_ASSIGN` | 운영 관리(program-admin: 기수·반명단·매니저 3탭) | 기수 개설/종료, 반·명단 편성, 담당 매니저 초대·배정 — **"조직 구조를 정하는 일"·"남의 범위에 영향 주는 일"**(D66) | 배정 안 된 타 기관 접근 불가(SYS-02) |
| **③ 담당 매니저** | `MANAGER` (ORG_MANAGE 없음) | 같은 역할의 권한 묶음(하위) | 배정된 기수/반 한정 | 총괄이 배정(ManagerAssignment N:M) | `ASSESSMENT_RUN`, `SCORE_REVIEW`, `INTERVENTION_MANAGE`, `REPORT_VIEW`, `APPEAL_REVIEW` | 대시보드·프로젝트·위험분석·교육생·개입·리포트·이의검토 (총괄 nav = 담당 nav + 운영관리 하나, D67) | 배정 기수 안에서 측정 실행·채점검토·개입·리포트·이의판정 — **"배정 범위 안에서 완결되는 일"**(D66) | 조직 구조(기수 개설·반 편성·매니저 배정)는 총괄 전용이라 접근 불가 |
| **④ 교육생** | `TRAINEE` | 별도 역할 | 본인 데이터만 | 명단 등록(ORG-01) → 초대(AUTH-06) | `OWN_RESULT_VIEW` | SC-T01~T05 (홈·제출·세션·결과) | 코드 제출, 검증 세션 응시, 본인 결과 열람, 이의제기(GOV-01 트리거만, 판정 수정은 매니저 액션) | 채점 근거·루브릭 원본 비공개(DASH-09), 처방형 콘텐츠 금지(GOV-03), 타인 데이터 접근 불가 |

## 보조 참고 — RBAC 집행 원칙 (AUTH-09, 전 계층 공통)

- **default deny + 최소권한**: 정의 안 된 role·미등록 operation은 전부 차단.
- **ownership 검증**: 역할 권한이 있어도 본인 소유 자원인지 별도 확인.
- **GOV-02 자동확정 금지**: 매니저 권한이 있어도 시스템이 대신 확정하는 경로는 원천 차단 — RBAC 레벨에서도 걸림.
- **AUTH-11**: "직책명"(팀장·센터장 등)은 코드에 안 박고 `can_view_all_manager_history` 같은 권한 플래그로만 관리 — 실제 조직 직책 매핑은 배포 전 운영 정책(Q14, 보류 중).

## 발표용 요약표

| 계층 | 범위 | 핵심 역할 |
|---|---|---|
| **슈퍼어드민** | 전체 기관 | 기관 생성 + 첫 총괄 매니저 초대 |
| **총괄 매니저** | 기관 전체 | 기수 개설, 반·명단 편성, 담당 매니저 배정 |
| **담당 매니저** | 배정된 기수 | 측정 실행, 채점 검토, 개입, 리포트, 이의 검토 |
| **교육생** | 본인 데이터 | 코드 제출, 검증 응시, 결과 열람, 이의제기 |

> 3-role RBAC(SUPER_ADMIN/MANAGER/TRAINEE) + MANAGER 내부 권한 2단(총괄/담당) = 실질 4계층.
