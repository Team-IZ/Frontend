OP-06 · 오퍼레이터 · 웹

운영 관리 — 탭 5 + 배정 모드

v1 운영 관리 셸을 그대로 쓴다. 탭 구조·표·벌크바·CSV 검증·좌측 반 레일 배정이 전부 유지되고, 바뀐 것은 탭 구성과 권한 모델이다.

  • `반`과 `명단`을 한 탭으로 합쳤다. 반을 만드는 것과 명단을 넣는 것은 한 흐름인데 탭이 갈리면 계속 오간다.
  • `교안`과 `비용`이 새로 들어왔다. 교안은 v1에서 매니저 나브에 있었는데 하루에 안 여는 화면이라 한 층 아래로 내렸다. 매니저 쪽에는 목록 없이 개념 한 장 뷰어(MG-09)만 남는다.
  • 매니저 초대에 권한 선택이 없다. 총괄/담당이 폐기되어 매니저가 한 종류뿐이다 — 대신 반 배정만 고른다.
  • 배정은 표가 아니라 작업이라 모드로 연다. 여러 번 반복 배정하는 동안 좌우가 동시에 보여야 한다.
케이스 계약 · 운영 관리 전량 (구현 근거)
#상태에러코드 · API문구 · 다음 행동목업
① 기수 — 반·명단이 여기 담긴다
—기수 목록GET /admin/cohorts진행 중 · 종료 · 반·교육생 수→ 행 클릭 → 반·명단#cohort
—기수 생성POST /admin/cohorts이름 · 기간→ 생성#cohort-create
—기수 0—첫 기수를 만드세요 + 생성 유도→ 생성 — 여기가 시작점#empty
② 반 · 명단 — 한 탭에 둘을 같이
—반 · 명단GET /admin/classes반별 인원 · 담당 매니저 · 명단→ —#classes
—반 추가POST /admin/classes이름 · 정원→ 추가#class-add
—명단 추가 · CSVPOST /admin/roster유효 n · 이미 등록 n(건너뜀) · 형식 오류 n(행 번호)→ 유효 행은 등록 — 한 줄 때문에 전체를 막지 않는다#roster-add
—명단 추가 · 직접 입력—지각 등록 1~2명→ 형식·중복을 그 자리에서#roster-manual
—도메인 밖 이메일DOMAIN_NOT_ALLOWED등록 차단→ 기관 도메인 주소만#roster-add
—벌크 선택—여러 명 선택 → 벌크바→ 반 배정 · 초대 재발송#bulk
반 배정 모드 — 좌우가 동시에 보여야 한다
—① 진입—반·교육생 모두 미선택 · 실행 비활성→ 둘 다 고른다#assign-idle
—② 선택PATCH /admin/roster/assign반 + 교육생 선택 → 실행 활성→ 배정#assign
—③ 배정 직후—되돌리기가 남는다→ 잘못 넣으면 되돌린다#assign-done
—④ 미배정 0—더 배정할 사람이 없습니다→ 모드 종료#assign-empty
③ 매니저 — 계정이 아니라 담당 배정
—매니저 목록GET /admin/managers담당 반 · 담당 인원 · 상태→ 반 배정 · 정지#managers
—매니저 초대POST /admin/managers/invite권한 선택이 없다 — 매니저는 한 종류→ 반 배정만 고른다#mgr-invite
—담당 없는 반—담당 없음 배지 + 배정 유도→ OP-01 조치 필요와 같은 신호#managers
④ 교안 — 검증 개념의 원천
—교안 목록GET /admin/curricula섹션 · 항목 · 연결된 프로젝트 · 상태→ 행 클릭 → 상세#curriculum
—섹션 상세—가르친 항목 · 페이지→ —#cur-detail
—연결된 프로젝트—어느 회차가 이 교안을 쓰는가→ 재분석 전 안전장치#cur-used
—재분석 — 쓰는 회차가 있음—확인 모달 — 이미 응시한 문항·리포트는 유지→ 새 결과는 다음 회차부터#cur-reanalyze
—분석 실패—사유 + 재분석 · 파일 교체→ 그 교안은 프로젝트에 연결할 수 없다#cur-fail
⑤ 비용
—비용GET /admin/cost기수·반별 AI 비용→ —#cost
실패
—저장 실패ADMIN_SAVE_FAILED저장하지 못했습니다 · 입력값 유지→ 재시도 — 그림 없음—
· CSV는 한 줄 때문에 전체를 막지 않는다. 유효 행은 등록하고 오류 행만 행 번호로 알린다 — 수백 명을 다시 올리게 하면 아무도 안 쓴다.
· 배정은 표가 아니라 작업이라 모드로 연다. 여러 번 반복하는 동안 좌우가 동시에 보여야 하고, 배정 직후에는 되돌리기를 남긴다.
· 매니저 초대에 권한 선택이 없다. 총괄/담당이 폐기되어 매니저가 한 종류뿐이다 — 고를 것은 반 배정뿐이다.
· 교안 재분석은 쓰는 회차를 먼저 보여준다. 이미 응시한 문항과 리포트는 그대로 두고 새 결과는 다음 회차부터 — 지난 회차 결과가 바뀌면 비교가 깨진다.
· 오퍼레이터 계정은 여기서 다루지 않는다. 초대·정지는 슈퍼어드민(SA-02) 소관이다.
· 왜 그렇게 정했는지는 정의 문서에 있다.

HITL (Human In The Loop)

AI_LLMOps v2 · p.48–60 — 리포트와 면담이 이 위치를 가리킵니다
이 섹션이 가르친 것 9프로젝트에서 이 중 3개를 골라 문항을 만듭니다
HITL 개념 정의p.48
HITL은 LLM 시스템의 의사결정을 통제하기 위한 Control Layer로, 실행 결과를 검증·차단·수정하며 사람을 시스템의 구성요소로 설계한다.
HITL이 필요한 이유p.49
무한 재시도로 인한 비용 증가, Tool/API 호출 비용 리스크, 정책 위반으로 인한 법적·보안 사고를 통제하기 위해 HITL이 필요하다.
HITL 적용 사례 비교p.50
콘텐츠 생성·고객 응대 사례에서 Trigger 조건에 따라 사람이 승인/수정/차단/직접 응답으로 개입하는 패턴을 보여준다.
HITL의 위치와 역할p.51
HITL은 특정 단계가 아니라 Design–Run–Trace–Evaluate–Improve 전체 운영 사이클을 관통하는 정책이다.
Supervisor 패턴에서 HITL 구현 원칙p.52
HITL은 중앙에서 통제되어야 하므로 Supervisor가 흐름과 개입을 모두 통제하며, Worker는 HITL을 호출하지 않고 사람도 하나의 Node로 취급한다.
Supervisor 패턴의 HITL 실행 흐름p.53
Supervisor가 HITL Trigger 함수로 개입 조건을 판정하고, Human은 APPROVE/REVISE/ABORT로 최종 의사결정을 수행한다.
HITL Design Checklist과 사용자 부담 Trade-offp.58
개입 조건(정량+정책), 개입 방식, 개입 이후 흐름을 정의해야 하며, 안전성 vs 사용성 Trade-off를 위해 3가지 방안을 고려한다.

AI Agent 설계 — 면접관 예제

AI_LLMOps v2 · p.21–35 — 리포트와 면담이 이 위치를 가리킵니다
이 섹션이 가르친 것 16프로젝트에서 이 중 3개를 골라 문항을 만듭니다
AI 면접관 Agent 문제 제기p.21
채용 절차에서 면접이 가장 어려운 영역(46.4%)이며, 본인의 강점을 설명하는 질문의 답변이 가장 어렵다는 조사 결과로 필요성을 제기한다.
Agent 역할 정의서p.26
각 Agent의 책임과 역할을 명확히 분리하여, Agent 이름/역할/입출력/사용 모델·도구/제약 조건/실패 시 리스크 항목을 정의한다.
Workflow Specp.27
Agent들의 실행 순서, 상태 흐름, 분기 조건, 반복 구조, 종료 조건을 정의하여 시스템의 흐름과 의사결정 구조를 명시하는 명세서이다.
State 정의서p.28
Agent 간에 전달되는 데이터 구조를 정의하여 시스템이 무엇을 기억하고 무엇을 전달하는지 명확히 한다.
Decision Policyp.29
Workflow의 분기와 반복을 일관되고 통제 가능하게 만들기 위해 판단 기준 State와 선택지·조건·결과·구현 방식을 규칙으로 정의한다.
