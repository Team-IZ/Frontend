## 2. 파일 구조와 그 이유

```
features/operator/projects/
├─ types.ts      계약 — 서버와 주고받는 모양·에러코드   (백엔드 합의 대상)
├─ rules.ts      기획 상수 + 판정 — 서버도 같은 값 검증  (연동해도 남는다)
├─ labels.ts     한글 라벨 — 화면 것                     (연동해도 남는다)
├─ api.ts        ★ 경계 — 화면이 유일하게 의존하는 곳
├─ mockDb.ts     목 데이터                               (연동 시 파일째 삭제)
├─ useAsync.ts   조회 훅 (loading·failed·reload·enabled)
├─ components/   목록·상세 공유 — StatusBadge · ConceptPicker · SummaryCells · SchedulePicker
├─ list/         목록 전용 — 화면 · filterState · components/
└─ detail/       상세 전용 — 화면 · components/(탭 3 + 헤더 + 모달 4)
```

**공유물을 `list/`에 넣지 않은 이유:** 상세가 같은 타입·규칙·라벨을 쓴다. 넣었으면
상세 만들 때 도로 꺼내야 했다.

> **미적용 — 폴더 이름.** 위 배치는 *"`detail/`과 `components/`가 나란히 있어 구분이
> 안 된다"* 는 지적을 아직 반영하지 않은 상태다. 결론은
> [frontend-architecture §2-1](frontend-architecture.md)로 정해졌다 — **`features/operator/`
> 전 도메인이 URL 축(`{url-세그먼트}/` + `_/`)을 쓴다.** admin은 이미 그 배치이고
> `projects/`만 남았다. 적용하면 이렇게 된다:
>
> ```
> components/                   → _/components/   ConceptPicker · ProjectSummaryCells
> types·api·mockDb              → _/api/
> rules·labels·useAsync         → _/
> list/ · detail/               그대로 — 화면 하나 = 폴더 하나
> ```
>
> `list/`·`detail/`은 **글자 그대로의 URL 세그먼트는 아니다**(`/projects`와
> `/projects/:id/:tab?`). `:id`를 폴더 이름으로 쓸 수 없어서 붙인 이름이고, 축은 같다 —
> **화면 하나에 폴더 하나.** admin은 세그먼트가 그대로 이름이 되는 경우라 더 명확할 뿐이다.

## 3. 화면별 상태

### OP-03 목록 — 커밋됨 (PR #63)

목록(필터 4 · 정렬 2 · 빈 상태 2종) · 생성 모달(이름·유형·기간·교안·개념 3건·요구사항).

> **유형 라벨을 전체 이름으로 바꿨다** — `미프`·`빅프` → **`미니 프로젝트`·`빅 프로젝트`**.
> 기획 문서는 약어만 쓰지만(650회·144회) 그건 팀 안에서만 통한다 — 오퍼레이터가 새로
> 들어오면 *"미프가 뭐지"* 를 물어야 한다(G1과 같은 이유). **회차 이름**(`미프 3차`)은
> 운영자가 붙인 데이터라 화면이 고치지 않는다. `KIND_LABEL` 한 곳만 바꿨다.

**목업과 의도적으로 다르게 한 것 — 전부 여기 모은다.** 흩어 두면 리뷰에서 *"목업과
다른데요"* 가 나올 때마다 근거를 다시 찾게 된다.

| | 목업 | 우리 | 왜 |
|---|---|---|---|
| 컬럼 폭 | 6열 **전부** 지정 | **흡수 열 1개** | `table-layout:fixed`는 전 열에 폭이 있으면 남는 폭을 비례 분배한다 — 목업 선언값 112·64·180·230·124·108이 실제로는 175·100·281·359·194·169로 렌더돼 **462px가 흩어져 무의미**했다. 체크리스트가 이미 *"마지막 열에만 폭을 주지 않는다"* 고 정했고 MG-05는 지킨다 |
| `준비됨` 배지 | primary | **neutral** | Badge 변형은 의미 색과 1:1. `준비됨`은 **오퍼레이터가 할 일이 없는** 상태라 색으로 끌 이유가 없다(E1) |
| 정렬 2차 키 | 없음 | **마감** | 같은 `준비 중`이면 마감이 가까운 쪽이 급하다 — 행 배경 경고와 같은 회차가 맨 위로 온다 |
| **마감 시각** | `18:00` | **`23:59`**(`DUE_TIME`) | 실제 운영 기준이 그날 자정까지다. `24:00`을 안 쓰는 이유는 그것이 **다음 날 `00:00`** 이라 "9/26 마감"이 27일에 끝나는 것처럼 읽히기 때문. **기획이 정하면 `rules.ts` 한 줄만 바뀐다** |
| **교안 행 `사용 중`** | 없음 | **`· 검증 개념 2건 사용 중`** | 그 표시가 없으면 `변경`을 눌러서야 못 뺀다는 것을 안다 — 되돌아 나와 개념부터 바꿔야 한다. **`변경`이 왜 막히는지를 누르기 전에 말한다**(OP-04 §5) |
| **요구사항 빈 상태 문구** | 없음 | **`요구사항 없이 진행하는 회차입니다`** | `유형 2 · 없음`이지 `아직`이 아니다(02-layout §4) — 빅프처럼 요구사항 없이 끝나는 회차가 실제로 있어 **기다릴 것이 없다.** *"없음"* 만 쓰지 않고 **0건이 무슨 뜻인지**를 쓴다 |

**회차 기간을 생성 시 받는다**(목업엔 없다). 원래 마감은 OP-04 일정 탭에서만 정할 수
있어 만들자마자 `미설정`으로 남았다. 입력 둘(시작일·마감일)이고 **마감 시각은 `23:59`
고정** — `24:00`은 다음 날 `00:00`이라 "9/26 마감"이 27일에 끝나는 것처럼 읽힌다.
**범위 성질은 유지**: 마감 달력이 시작일 이전을, 시작 달력이 마감일 이후를 막아
`시작 > 마감`이 애초에 안 만들어진다. 기수 기간 밖도 같은 방식.

### OP-04 상세 — 미커밋

탭 3(**개요·현황·구성**) + 편집 모달 4(개념 선택 · 교안 변경 · 요구사항 편집 · 일정 수정).

> **탭을 다시 짰다 — 잠금 폐지 + 순서 변경.** 정의서 원안(`구성·일정·현황` + 개념 3건
> 전까지 잠금)을 뒤집었다. 근거와 상태별 문구는 **정의서 §6·§8에 적었다** —
> [OP-04-project-detail.md](../plan/v2/definition/OP-04-project-detail.md). 정의서를 안
> 고치면 다음 사람이 원안대로 다시 만든다.

**검증 개념 3건이 관문인 것은 맞다** — 3건이 정해져야 문항이 만들어지고 현황이 집계된다.
다만 **잠그지 않는다.** 각 탭이 자기가 왜 비었는지를 쓰고, 기다려도 안 채워지는 것에는
다음 행동을 붙인다(현황의 `[구성 탭에서 개념 정하기]`).

**탭이 URL 경로에 있다**(`/operator/projects/:id/:tab?`). OP-01 `조치 필요`가 탭별로
딥링크하기 때문(개념 공백 → 현황 / 집단 미달 → 구성). 잠긴 탭 URL로 직접 들어오면
내용만이 아니라 **주소도** 구성으로 되돌린다 — 내용만 바꾸면 주소는 `/schedule`인데
화면은 구성이라 어긋난 채 남고, 이미 활성인 탭을 눌러도 `onValueChange`가 안 와서
스스로 안 고쳐진다. **렌더로 잡은 결함이다**(typecheck·lint는 통과했다).

**교안 해제에 규칙이 둘이다** — 같은 상황인데 화면이 달라서다.

| | 규칙 | 왜 |
|---|---|---|
| 생성(OP-03) | `dropOrphanConcepts` — 개념이 같이 빠진다 | 저장 전이고 `지금 2건`이 그 자리에서 보인다. 되돌릴 수 있다 |
| 상세(OP-04) | `canUnlinkCurriculum` — **막는다** | 확정 상태에서 3건이 조용히 2건이 되면 **관문이 풀려 탭이 닫힌다.** 교안만 건드렸는데 화면이 되돌아간다 |

**한쪽을 다른 쪽에 쓰면 안 된다.** 중복으로 보여 합치기 쉬운 자리라 근거를
`check-project-rules.mts`에도 박아 뒀다.

**요구사항은 관문이 아니다.** 교안과 별개로 과제 문서에서 나와 **구현 P/F에만**
쓴다(14번 6-3) — 비어 있어도 일정·현황이 열린다.

**입력을 `Textarea`(한 줄에 하나) → 칩으로 바꿨다.** 처음 것이 셋 다 틀렸다.

| 틀린 것 | |
|---|---|
| **편집 UI가 읽기 UI와 다르게 생겼다** | 상세는 번호 붙은 목록인데 편집은 덩어리 텍스트 — 같은 것을 두 모양으로 배운다 |
| **계약이 눈에 안 보인다** | 개행이 구분자라는 것을 화면이 말하지 않아 **저장해야 몇 건인지 안다.** 빈 줄이 조용히 사라지고 중복이 그대로 들어간다 |
| **판정 단위와 안 맞는다** | MG-08이 항목마다 `✓`/`✗`와 이유를 붙인다(`✓ 2 · ✗ 1`) — 문장 덩어리로 두면 그 판정을 걸 자리가 없다 |

> **계약을 위젯에 맞췄던 것이 진짜 실수다.** `requirements: string`을 두고 *"통째로 붙여
> 넣고 통째로 고치니 배열일 이유가 없다"* 고 근거를 댔는데, 그건 `Textarea`를 정당화한
> 것이었다. **입력 모양이 틀리면 그 위에 쌓은 계약 근거도 같이 틀린다.** MG-08을 먼저
> 봤으면 `string[]`이 바로 나왔다.

> **한글 IME 조합 중 Enter — 칩이 두 개 생겼다.** `ㅂㅂㅂㅇㅇㅇ`를 치고 Enter를 누르면
> `ㅂㅂㅂㅇㅇㅇ`와 `ㅇ`이 각각 칩이 됐다. 조합이 안 끝난 상태의 Enter는 **IME 것**인데
> 그것까지 받아서, 조합을 확정하는 keydown 하나 + 확정 뒤 keydown 하나가 둘 다 커밋됐다.
> → `if (e.nativeEvent.isComposing) return`.
>
> **참조 구현에 원래 있던 버그다.** `InputCompositionsPreview.tsx`의 `ChipInput`을 그대로
> 옮겨 왔는데 거기에 가드가 없었다 — **그 파일도 같이 고쳤다.** 그러지 않으면 다음 사람이
> 같은 것을 또 옮긴다. 한글 서비스에서 Enter로 커밋하는 입력은 **전부** 이 가드가 필요하다.
>
> `features-v1/curriculum/SectionTopicTable.tsx`에도 같은 패턴이 있으나 **라우팅되지 않는
> 격리 보관고**이고(D16) MG-09는 이미 v2로 이식됐다 — 죽은 코드라 두었다.
>
> **두 곳을 손으로 고치고 끝내지 않았다.** 그러면 **세 번째 칩 입력에서 또 난다** —
> `Field`·`ButtonGroup`·`Badge`를 세 번 다시 만든 것과 같은 구조다. `check:korean`이
> Enter 확정 입력을 전수 검사한다(`scripts/check-korean-input.mts`). **가드를 실제로
> 빼 보고 종료코드 1을 확인**했다 — 통과만 본 검증은 이 세션에서 이미 한 번 틀렸다.

`RequirementsField`는 **손으로 만들지 않았다** — `input-inventory.md` F 범주가 칩 입력을
`InputGroup + Badge`로 확정해 뒀고 `InputCompositionsPreview.tsx:107`에 조립돼 있다.
여기서는 도메인 규칙(`addRequirements` — trim · 빈 항목 · 중복)에 붙이기만 했다.
**정리를 저장이 아니라 입력 시점에** 해서 저장된 것과 화면에 보이는 것이 갈리지 않게 한다.
붙여넣기에 개행이 있으면 그 자리에서 나눈다(과제 문서에서 통째로 복사하는 것이 실제 동선).

> **`createProject`가 `requirements`를 흘리고 있었다.** 생성 폼이 받은 값이 `Project`에
> 안 담겨서 상세 요구사항 블록이 **데이터와 무관하게 늘 비어** 있었다. 화면이 아니라
> 경계에서 새던 것이라 화면만 보면 안 잡힌다.

**일정은 사람이 정하는 날짜가 둘뿐이다**(시작일 · 제출 마감). 응시 창·재시험 창·리포트
발행은 규칙에서 파생되므로 **저장하지 않는다** — 값으로 저장하면 규칙이 바뀔 때 이미
만든 회차만 옛 값을 들고 남는다. 일정 탭이 그 넷을 읽기 전용으로 그리는 것과 같은 이유다.

**`SchedulePicker`를 `list/` → `components/`로 올렸다.** 상세도 같은 입력을 쓰므로
공유물이다(mock-first §3-1 *"공유물을 `list/` 안에 넣지 않는다"*). **새 추상화가 아니라
자리 이동**이라 D14의 "세 번째 등장" 규칙과 무관하다.

**목 회차 6건이 상태를 하나씩 덮는다** — 최신일수록 덜 준비된 사다리(6차 아무것도 없음 →
5차 교안만 → 4차 준비됨·제출 전 → 빅프 → 3차 진행 중 → 2차 종료). **여기 없는 칸은 렌더를
확인할 수 없다.** 현황 리포트도 회차 상태로 갈랐다 — `READY`는 0인 리포트, `DONE`은 그
회차 교안(k8s) 개념의 리포트. 하나만 두면 k8s로 돌린 회차에 AI_LLMOps 개념 이름이 뜬다.

> **개념 id가 교안에 없었다.** `mif-3`의 `hitl-trigger·graph·state`, `mif-2`의
> `service·deployment·configmap`이 전부 `CURRICULA`에 **없는 id**라 구성 탭이 출처 페이지
> (`p.53`)를 못 찾고 있었다. 현황의 `conceptName`도 프로젝트 개념과 달랐다
> (`State 관리` vs `시점 관리`) — **같은 회차가 탭마다 다른 이름**을 보여줬다.
> 실제 교안 항목으로 통일했고, 정의서 §3 구성 스케치와도 이제 일치한다.

**편집 정책을 `rules.ts`에 모았다** — `canEditConfig` · `canEditSchedule` ·
`canOnlyExtendDue` · `canDelete` · `lockedReason`. 4상태 × 3액션 표는
[정의서 §8-2-1](../plan/v2/definition/OP-04-project-detail.md)에 있다.

> **화면마다 `status === 'RUNNING'`을 쓰면 안 되는 이유가 실측으로 나왔다.** 감사 전에는
> **네 액션이 모든 상태에서 다 열려 있었다** — 종료된 회차의 검증 개념도 바꿀 수 있었다.
> 조건을 화면에 흩으면 상태가 하나 늘 때 어디를 고칠지 모르고, **버튼은 막혔는데 URL로
> 모달이 열리는** 상태가 생긴다. 서버(`api.ts`)도 같은 함수를 쓴다 — 클라이언트 검증만
> 있으면 우회되고, 그때 사라지는 것은 학생이 실제로 한 제출·응시다.

**#64 마감 유효 범위 — 절반만 구현했다.**

| | 상태 |
|---|---|
| ② 기수 기간 안 | **달력이 막는다.** 기수 종료 다음 날부터 비활성(실측: 10월 35칸 중 31칸) |
| ③ `시작 > 마감` | 달력이 서로를 막아 **애초에 안 만들어진다** — 검증도 에러 문구도 없다 |
| **① 회차 순서** | **막지 않는다.** 대신 **사실을 쓴다** — `다음 회차 미프 4차의 마감이 07-21 23:59이라 이번 마감이 더 늦습니다` |

①을 막지 않는 이유: 막을지 경고만 할지가 **#64 미결**이라 화면이 정하면 기준을 만드는
것이 된다(E8). 그래서 `늦추지 마세요`·`권장하지 않습니다` 같은 판정 문구를 안 쓰고
**무슨 일이 일어나는지만** 쓴다 — 재시험 창이 열리지 않는다는 것은 정의서가 이미 정한
규칙(`3일 또는 다음 제출일 중 빠른 쪽`)에서 그대로 나오므로 내가 만든 기준이 아니다.
**다만 조용하지는 않게 한다** — 조용히 사라지는 것이 #64 ①의 성질이다.

**헤더에 회차 요약 카드**(검증 개념 · 교안 · 기간). 처음엔 이름 한 줄만 뒀는데 들어가면
교안 목록부터 보였다 — *"기본 정보가 먼저 나와야 한다"* 는 지적을 반영. **헤더는 값,
구성 탭은 출처·근거·편집 버튼**으로 갈랐다(D1 중복 방지). 그 과정에서 구성 탭의
미확정 Alert를 지웠다 — 자물쇠·헤더·빈 상태가 이미 말해서 **네 번째 반복**이었다.

**커밋 메시지 초안이 필요하면** 이슈 #65 본문에 작업 내용·하지 않는 것이 정리돼 있다.

## 7. 검증 스크립트

```bash
npm run check:project   # 개념 3건 · 토글 · 마감 라벨 · 교안 해제 · 요구사항
npm run check:korean    # 한글 IME — Enter 확정 입력에 조합 가드가 있나
npm run typecheck && npm run lint && npm run check:design && npm run build
```

> **가드 스크립트가 CI에 없었다.** `check:project`·`check:admin`·`check:pagination`이
> 넷 다 `package.json`에만 있고 `ci.yml`에는 한 줄도 없었다 — **사람이 손으로 쳐야만
> 도는 규칙**이었다(D15: *"규칙이 있다는 것과 규칙이 작동한다는 것은 다르다"*).
> 검증 개념 3건이 Tier-1 불변식인데 아무도 안 지키는 상태였다. → `Domain rules` 단계 추가.
>
> **`check:admin`만 뺐다.** OP-06 코드(`admin/_/rules.ts`)를 import해서, 04가 먼저
> 머지되면 그 파일이 없어 CI가 즉시 깨진다. **06 브랜치에서 같이 넣는다.**

**렌더 검증은 Playwright로 직접 잰다.** 추측하지 않는다 — 죽은 포트를 보고 있었던 적도,
목업 `zoom` 때문에 착시였던 적도 있다. 스크립트는 세션 스크래치패드에 있었고 영구
보관하지 않았다(필요하면 다시 만든다).

> **렌더가 정적 검사보다 먼저 잡는 것이 있다.** 잠긴 탭 URL이 안 고쳐지는 결함은
> `typecheck`·`lint`·`check:project`를 **전부 통과한 채로** 있었다 — 타입도 규칙도
> 맞는데 주소와 화면이 어긋난 것이라 눌러 봐야만 보인다.
>
> MCP 브라우저를 다른 세션이 잡고 있으면(`Browser is already in use`) **뺏지 않는다.**
> `playwright-core`를 스크래치패드에 깔고 캐시된 크로미움을 직접 띄우면 서로 안 겹친다.
>
> ```js
> import { chromium } from 'playwright-core'   // 스크래치패드에 npm i
> const EXE = `${os.homedir()}/Library/Caches/ms-playwright/chromium-1223/`
>            + `chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing`
> const browser = await chromium.launch({ executablePath: EXE })
> ```
>
> 실측값(1512·1920): 본문 폭 **1264 / 1280px** · 가로 넘침 **0** · 콘솔 오류 **0**.
> 1264는 `1512 − 184(나브) − 64(패딩)`이라 **상한 1280에 안 닿는 것이 정상**이다(H8).

> **주의 — `routes.tsx`가 glob으로 모든 `*.route.tsx`를 모은다.** 다른 도메인 화면
> 하나가 깨지면 **앱 전체가 안 뜬다.** 내 화면이 안 보이면 먼저 `npm run typecheck`로
> 어디가 깨졌는지 본다. **남의 폴더를 치우지 않는다**(git-convention §5).
