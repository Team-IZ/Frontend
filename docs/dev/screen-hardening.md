# 화면 하나를 단단하게 만드는 법

> **연동이 끝난 화면을 다음 단계로 올릴 때 이 문서를 연다.** "값이 오나"까지가 연동이고,
> 여기는 **값이 오기 전·안 올 때·이상하게 올 때** 화면이 무엇을 하는가를 다룬다.
>
> OP-01 대시보드에서 한 번 끝까지 돌려 본 절차다. **나머지 화면도 이대로 한다** —
> 화면마다 다른 것은 1단계(상황 목록)뿐이고 나머지는 그대로 쓴다.
>
> | 이 문서 | 무엇을 **어떤 순서로** 하나 |
> |---|---|
> | [async-states.md](async-states.md) | 로딩·빈 상태·실패를 **무엇으로** 그리나(표준) |
> | [mock-first-screens.md](mock-first-screens.md) | 화면을 **처음 만들** 때 |
> | [api/api-boundary.md](api/api-boundary.md) | 무엇이 서버 것이고 무엇이 화면 것인가 |

---

## 0. 전제 — 왜 이 단계가 따로 있나

연동을 마친 화면은 **정상 경로에서만 검증된 상태**다. 실제 사용자는 그 경로로만 다니지
않는다 — 서버가 자고, 기수에 회차가 없고, 권한이 없고, 자정을 넘겨 켜 둔 채 방치한다.

OP-01에서 실제로 나온 것들이다.

| 겉보기 | 실제 |
|---|---|
| "들어가자마자 빨간 에러가 떠요" | 조회는 **200**이었다. 아직 집계된 회차가 없을 뿐 |
| "느려요" | 8.1초. 그중 **6.6초는 안 기다려도 되는 것**이었다 |
| "숫자가 이상해요" | 같은 기수 인원을 **네 API가 다르게** 세고 있었다 |

셋 다 **연동 테스트로는 안 걸린다.** 값이 오긴 왔기 때문이다.

## 1단계 · 상황을 전수로 적는다

**결과물** — `docs/dev/screens/{화면}-situations.md`

먼저 **무엇이 달라질 수 있나**를 축으로 나눈다. 화면마다 다르지만 만드는 방법은 같다.

### 축을 뽑는 법

이 화면이 부르는 조회를 전부 그린다. **순서와 의존을 그린다** — 여기서 성능 문제의 절반이
보인다.

```
useCohortId()        GET /cohorts                     ─┐ 이게 끝나야
useDashboard()                                        ─┘ 나머지가 시작한다
  ├─ risk      GET .../analytics/risk-trainees
  ├─ todos     GET .../analytics/actions
  └─ pipeline  GET .../projects            ─┐ 순차
               GET /projects/{pid}/class-progress ─┘
```

그다음 조회마다 **응답이 가질 수 있는 상태**를 적는다. 성공/실패가 아니라 **데이터 상태**다.

```
축 B. 회차 상태
  B1 RUNNING 하나        B2 RUNNING 없고 PLANNED   B3 전부 CLOSED
  B4 회차가 0개          B5 RUNNING이 둘 이상
```

**조합 수를 계산해 적는다**(OP-01은 2,400개였다). 전부 못 보므로 2단계에서 **실제로 갈리는
지점**만 추린다는 것을 문서가 스스로 말하게 한다.

### 공통 축 — 화면마다 다시 생각하지 않는다

3절은 **그대로 복사해서 채운다.** 여섯 갈래다.

| | 무엇을 묻나 |
|---|---|
| 네트워크·인프라 | 오프라인 · 콜드 스타트 · 타임아웃 · 느린 3G · 프록시 한계 |
| 인증·세션 | 토큰 만료 · 리프레시 실패 · **탭 두 개에서 동시에 401** · 권한 없는 자원 |
| 시간·타이밍 | **자정 넘김** · 서버 UTC ↔ 로컬 · 브라우저 시계 오차 · 마감 직후 |
| 사용자 조작 | 로딩 중 이탈 · **재시도 연타** · 뒤로가기 · 스코프 전환 · 확대 200% |
| 표현·성능 | 첫 진입 · 목록이 아주 길 때 · 이름이 아주 길 때 · 다크 모드 |
| 접근성 | 스크린 리더 로딩·실패 · 색만으로 상태 · 키보드 이동 · 숫자 낭독 |

## 2단계 · 실제로 물어본다 — 추측하지 않는다

**이 단계가 이 절차의 핵심이다.** 1단계는 "그럴 수 있다"이고 2단계는 "실제로 그렇다"다.

### 서버에 직접 묻는다

```bash
TOKEN=$(curl -s -X POST "$BASE/api/v0/auth/login" -H 'Content-Type: application/json' \
  -d '{"email":"operator@example.com","password":"..."}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["accessToken"])')
curl -s "$BASE/api/v0/..." -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

**경계 데이터를 가진 기수를 찾아 쓴다.** OP-01은 9기(RUNNING·집계 있음)와 10기
(PLANNED·집계 0)를 같이 봤고, 10기에서 「아직」이 「실패」로 그려지는 것이 나왔다.

### 시간을 잰다 — 느낌으로 말하지 않는다

```bash
curl -s -o /dev/null -w '%{time_connect}  %{time_starttransfer}  %{time_total}  %{size_download}B\n' "$URL"
```

`time_connect`(네트워크)와 `time_starttransfer`(TTFB=서버 계산)를 **갈라서** 본다.
OP-01의 `/projects`는 연결 79ms·TTFB 4.62초·2.4KB였다 — **네트워크도 크기도 아니고 서버
계산**이라는 증거가 이 한 줄에서 나왔다.

**변수를 바꿔 가며 잰다.**

```
회차 7개 5.28s / 6개 4.22s / 6개 4.00s   → 개수에 비례하지 않는다
?status=RUNNING(1건) 4.48s               → 필터로도 안 줄어든다
?size=1              5.03s               → 무시된다
```

여기까지 나오면 "느리다"가 아니라 **"요청과 무관한 고정 집계를 돌고 있다"** 고 말할 수 있다.

### 브라우저에서 잰다 — 서버 시간과 화면 시간은 다르다

블록·구역이 **각각 언제 나타나는지**, 그리고 **레이아웃이 움직이는지**를 잰다.

```js
// 레이아웃 시프트
new PerformanceObserver(l => { for (const e of l.getEntries())
  if (!e.hadRecentInput) console.log(Math.round(performance.now()), e.value)
}).observe({ type: 'layout-shift', buffered: true })

// 블록 높이·위치 추적
setInterval(() => console.log([...document.querySelectorAll('main [data-slot="card"]')]
  .map(c => Math.round(c.getBoundingClientRect().top))), 120)
```

OP-01에서 CLS 0.0445 · **마지막 이동이 8.7초**가 나왔다 — 사용자가 읽고 있을 때 화면이
움직인다는 뜻이고, 이건 서버 시간만 봐서는 절대 안 보인다.

### 응답을 가로채 이상 상황을 만든다

정상 데이터로는 못 보는 상태를 **실제 화면에서** 본다.

```js
// 조회는 200인데 그릴 것이 없는 상태
await page.route(u => u.pathname.includes('/analytics/risk-trainees'), async r => {
  const res = await r.fetch(); const j = await res.json()
  j.rounds = j.rounds.map(x => ({ ...x, aggregationStatus: 'NOT_STARTED' }))
  await r.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify(j) })
})

// 권한 없음 · 서버 오류를 동시에
await page.route('**/analytics/actions**', r => r.fulfill({ status: 500, contentType: 'application/json',
  body: JSON.stringify({ status: 500, code: 'INTERNAL_SERVER_ERROR', message: 'x' }) }))
```

**여기서 대부분의 거짓말이 잡힌다.**

### 스펙이 사실인지 확인한다

```bash
curl -s "$BASE/v3/api-docs" -o /tmp/live.json   # 실서버 스웨거
# 로컬 api/openapi.json 과 경로·필드를 대조한다
```

OP-01에서 `readinessCounts`가 **스펙엔 `required`인데 응답에 없어** 목록이 흰 화면이 됐다.
스펙을 믿고 짠 코드가 죽은 것이다.

## 3단계 · 판단은 기준을 세워 놓고 한다

고칠 것이 정해지면 **바로 코드를 쓰지 않는다.** 안을 여럿 두고 같은 기준으로 잰다.

### 기준 — 순서가 곧 가중치다

| | |
|---|---|
| 1 · **거짓말을 하나** | 화면이 사실이 아닌 것을 주장하면 최우선 |
| 2 · **원인이 있는 곳에서 고치나** | 증상만 덮으면 다음 사람이 또 만난다 |
| 3 · **이미 있는 것을 쓰나** | 새 개념은 유지비가 붙는다 |
| 4 · **저쪽 레포와 충돌하나** | 공용 파일 수정은 조용한 사고 |

### 쓰기 전에 있는 것부터 찾는다

```bash
grep -rn "패턴" src/features src/components src/lib | sed 's|src/||'
```

OP-01에서 이렇게 찾아 쓴 것들이다.

| 필요했던 것 | 이미 있던 것 |
|---|---|
| 「없음」 표기 | `—` 패턴이 6곳에 (`RoundGridTable` · `StatusTab` · …) |
| 실패 문구 | `lib/errorCopy` |
| 자리표시자 | `ui/Skeleton` · `TableSkeleton`의 "실측해서 박는다" 방식 |
| 이전 결과 유지 | `_shared/listQuery` |
| 회차 선택 근거 표시 | `Section`의 `note` prop |

**새 파일은 하나였다**(`BlockSkeleton`). 나머지는 전부 있는 것으로 됐다.

### 안을 표로 늘어놓고 하나를 고른다

```
| 안 | 내용 | 판정 |
| A · 최소 높이 고정 | min-h-[80px] | 데이터가 늘면 또 어긋남 |
| B · 실제 모양 스켈레톤 | 블록마다 자기 모양 | ✅ |
| C · 셋 다 올 때까지 대기 | 원래대로 | 8.8초 스피너로 회귀 |
| D · 늦는 블록을 아래로 | 순서 변경 | 정보 위계가 응답 속도에 끌려간다 |
```

**버린 안과 그 이유를 남긴다.** D를 버린 근거("조치 필요가 주인공인 것이 이 화면의 설계다")가
없으면 다음 사람이 같은 제안을 다시 한다.

### 화면이 혼자 못 푸는 것은 요청서로

프론트에서 못 고치는 것은 **실측 근거와 함께** 백엔드 요청서로 넘긴다
(`docs/dev/backend/backend-api-requests-N.md`).

| 넣는 것 | OP-01 예 |
|---|---|
| 관측 — 숫자와 응답 원문 | TTFB 표 · `server: envoy` 헤더 |
| **없다는 증명** | 스웨거 82개 전수 확인, 로컬 스펙과 동일 |
| 대조군 | 단건 상세는 2.1초(목록보다 2.5초 빠름) |
| 왜 화면이 못 푸나 | `rounds[]`에 `status`·`startDate`가 없다 |
| 요청과 **대안** | `projects/current` 신설 · 어려우면 필드 2개 |
| 재현 명령 | 붙여넣어 바로 돌아가는 `curl` |

**"고쳐 주세요"가 아니라 "이렇게 관측됐고 이래서 우리가 못 푼다"** 로 쓴다. 정의를 묻는
것이면(Q) 값을 통일해 달라고 하지 않는다 — 모르는 채 화면을 맞추면 틀린다.

## 4단계 · 고친다 — 한 번에 하나씩, 매번 다시 잰다

**고칠 때마다 2단계 측정을 다시 돌린다.** OP-01에서 이것 때문에 잡은 것들이다.

| 언제 | 무엇이 나왔나 |
|---|---|
| 쿼리를 나눈 뒤 | 푸터가 앞서 감(1쪽 데이터에 `21–30`이라고 씀) |
| 스켈레톤을 넣은 뒤 | **CLS가 오히려 올라감**(0.0445 → 0.0939) |
| 그 원인을 캐다가 | **진입 1.3초 동안 블록 셋이 전부 "불러오지 못했습니다"** ← 사용자가 말한 그 문제 |

**세 번째가 핵심이다.** 스켈레톤을 넣지 않았으면 CLS가 안 올라갔고, 안 올라갔으면 그
1.3초를 안 봤을 것이다. **고치다가 나온 이상 신호를 그냥 넘기지 않는다.**

### 자주 나오는 함정

| 함정 | 왜 |
|---|---|
| `isLoading`으로 「아직」을 판정 | `enabled: false`면 거짓이다 — **상류를 기다리는 것을 실패로 그린다** |
| 스켈레톤 높이를 눈대중으로 | OP-01은 133px, `TableSkeleton`도 처음에 어긋났다. **실제에서 재서 박는다** |
| 파생값으로 「없음」 판정 | `ratio`가 아니라 `graded > 0`(원인이 되는 값)으로 |
| 성공/실패 두 상태만 | 「아직」이 없으면 200을 실패라고 말하게 된다 |

## 5단계 · 눈으로 본다 — 코드로는 안 보이는 것이 있다

**렌더 확인은 선택이 아니다.** 코드만 봐서는 절대 안 나오는 것들이 있다.

| OP-01에서 렌더로만 잡힌 것 |
|---|
| `ErrorState` 버튼 두 개가 **세로로 쌓임**(둘 다 주요 액션처럼 보임) |
| 툴바가 **「전체 0반」** — 모르는 것을 0으로 단언 |
| 리포트 헤더가 **7기**인데 본문은 **9기** |
| 반 비교의 `분석에서 보기 ↗`가 **데이터 없어도** 떠 있음 |

### 확인 순서

```
□ 첫 진입 — 스켈레톤이 올 것과 같은 자리인가 (CLS 0에 가까운가)
□ 조건 변경 — 표가 사라지지 않는가
□ 데이터 없음 — 「아직」인가 「실패」인가, 버튼이 맞는가
□ 실패 — status별로 다른 말을 하는가, 재시도가 의미 있을 때만 있는가
□ 오프라인 — "서버 문제"라고 하지 않는가
□ 재시도 연타 — 막히는가
□ 링크 — 갈 곳이 있을 때만 있는가
```

**dev 프리뷰(`/operator/__async`)에 넣는다.** 실제 화면 모양 그대로 전/후를 나란히 두면
말로 설명할 필요가 없어진다.

## 6단계 · 남긴다

| 무엇 | 어디 |
|---|---|
| 상황 목록 · 실측 · 고친 것 | `screens/{화면}-situations.md` — 고친 것은 **지우지 말고 ✅** |
| 화면 전체에 걸치는 규칙 | `async-states.md` |
| 백엔드가 풀 것 | `backend/backend-api-requests-N.md` — **화면 하나마다 보내지 않는다.** OP 전수를 훑고 한 번에 묶어야 저쪽이 우선순위를 정할 수 있다 |
| 눈으로 보는 자리 | `/operator/__async` |
| 되돌아가는 것 막기 | `scripts/check-*.mjs` + CI |

### ✅를 남기는 이유

```
### 2-3. ✅ 「아직」을 「실패」로 그렸다
   (관측) … (원인) … (고침) … (실측 전/후)
```

지우면 **왜 지금 코드가 이렇게 생겼는지**가 사라진다. 다음 사람이 "이 `pending` 상태 왜
있지" 하고 지운다.

### CI로 굳히는 기준

**되돌아가면 아픈 것만.** OP-01~06에서 둘을 넣었다.

- 조회 분기의 `isPending` → 끝나지 않는 스피너가 된다
- `variant` 없는 `<Empty>` → 화면이 "기다리면 채워진다"고 잘못 말한다

**규칙을 일부러 되돌려서 실제로 걸리는지 확인한다.** 안 걸리는 규칙은 없느니만 못하다.

## 한 장 요약

```
1. 적는다    조회 흐름 → 축 → 조합 수 → 공통 6갈래(복사해서 채운다)
2. 잰다      curl(TTFB·변수) · 브라우저(CLS·도착 시각) · 응답 가로채기 · 스펙 대조
3. 고른다    안 여럿 → 기준 4개로 판정 → 있는 것부터 찾기 → 못 푸는 건 요청서
4. 고친다    하나씩 · 매번 다시 재기 · 이상 신호 안 넘기기
5. 본다      렌더 확인 7개 · 프리뷰에 전/후
6. 남긴다    ✅로 · 규칙은 CI로
```

**이 순서가 중요한 이유** — 2단계(측정) 없이 3단계(판단)로 가면 **추측으로 고치게 된다.**

6.6초를 더 기다린다"* 였고, 그건 재보기 전에는 아무도 몰랐다.
