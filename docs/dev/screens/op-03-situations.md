> **이 화면을 고치기 전에 이 문서를 본다.** 무엇이 일어날 수 있고, 지금 그중 무엇이

## 0. 이 화면의 성격

OP-01·02와 또 다르다.

| | OP-01 대시보드 | OP-02 분석 | OP-03 목록 |
|---|---|---|---|
| 조회 | 블록 셋 병렬 | 탭마다 하나 | **셋 병렬**(목록·교안·스코프) |
| 상태 | 응답 그대로 | 화면 상태가 조회 조건 | 화면 상태가 조회 조건 |
| 실패 단위 | 블록 하나 | 탭 전체 | **목록만** — 교안·스코프 실패는 조용하다 |
| 쓰기 | 없음 | 없음 | **있다** — 생성이 호출 4개 |

여기서 처음 나오는 축이 둘이다.

1. **쓰기가 있다.** 생성이 `create → link×N → concepts → requirements` 순차 4콜이고,
   중간에 실패해도 회차는 이미 만들어져 있다. 되돌릴 수 없다 — 이름·순번이 점유된다(9차 §10).
2. **입력이 있다.** 검색은 사용자가 글자를 치는 동안 계속 바뀌는 조회 조건이다.

```
useProjectList   GET /cohorts/{id}/projects?search&curriculumId&status&sort
useLinkableCurricula  GET …/curricula        (교안 필터 선택지)
useCohortScope        GET …                  (반·인원 문구)
useCreateProjectFlow  POST + PUT×3           (생성)
```

## 2. 실측

측정 대상 — 9기 · 회차 7개(종료 5 · 준비됨 1 · 진행 중 1) · 교안 6종 · 반 9개 209명.

### 2-0. 진입 타임라인

```
0ms      클릭
         ─ 조회 4개가 동시에 나간다
1372ms   curricula   200
1621ms   cohort      200
2150ms   classrooms  200
5252ms   projects    200   ← 표를 만드는 것
6056ms   첫 행이 그려짐
```

CLS **0.0001** — 밀림은 없다. 총계·스코프 문구가 제목과 **같은 줄**(inline)에 있어
도착해도 아래를 안 민다. 툴바 `top`은 진입 내내 148px로 고정이었다.

### 2-1. ⚠ 6초 동안 본문이 **완전히 비어 있다** — 스피너조차 없다

`op03_loading.png` — 1.2초 시점에 헤더와 툴바만 있고 그 아래가 백지다.
코드에는 스피너가 있는데(`ProjectListScreen.tsx:158`) 안 그려진다.

```
기수 미정 → q === undefined → enabled: false
          → isLoading === false  (조회가 시작조차 안 했으므로)
          → isError false · data undefined
          → 마지막 `page.data && (…)` 가 undefined
          → 아무 분기도 안 탄다
```

**OP-01·OP-02에서 고친 것과 같은 뿌리다**(async-states §1-9). 거기서는 "기다리는 중을
실패로 그린다"였고 여기서는 "기다리는 중을 **아무것도 아닌 것으로** 그린다".

### 2-2. ⚠ 교안을 고르면 툴바가 두 줄이 되고 표가 44px 내려간다

`op03_switching.png`. 트리거가 파일명 전체를 그린다 —
`교안 · 20250214 부산교육청,'생성형 AI와 함께 생각하고, 질문하는 수업' 교수학습자료 개발보급 _붙임.pdf v1`
가 580px를 먹어 정렬이 다음 줄로 밀리고, 그만큼 표 전체가 내려간다.
**조건을 하나 바꿨을 뿐인데 읽던 자리가 움직인다.**

### 2-3. 조건 전환 — 이전 결과가 최대 9초 흐리게 남는다

| 고른 값 | 요청 | 응답 | 4초 시점 화면 | 12초 시점 |
|---|---|---|---|---|
| 준비 중 (0) | `status=PLANNED` | 1건 → 클라이언트가 0으로 좁힘 | 0행 | 0행 |
| 준비됨 (1) | **안 나감**(같은 키) | 캐시 | 1행 | 1행 |
| 진행 중 (1) | `status=RUNNING` | 1건 | 1행 | 1행 |
| 종료 (5) | `status=CLOSED` | 5건 | **1행**(직전 결과) | 5행 |

흐리게 남기는 것 자체는 표준대로다(§1-4, `staleProps` 동작 확인 ✅). 문제는
**5초가 지나도록 「무엇을 기다리는지」를 아무도 말하지 않는 것**이다 — 4초 시점의
「종료 (5)」 + 1행은 개수와 표가 서로 다른 말을 하는 상태로 보인다.

준비 중·준비됨이 **쿼리 키를 공유**하는 것은 의도대로다(둘 다 `PLANNED`로 나가고
`readiness`로 가른다) — 그래서 둘 사이 전환은 요청이 안 나가고 즉시 바뀐다.

### 2-4. 검색 — 디바운스는 제대로 돈다 ✅

| | 결과 |
|---|---|
| `프로젝트` 4자(90ms 간격) | 목록 요청 **1건** (`?search=프로젝트`) |
| 지우기(X) | 요청 0건 — 조건 없는 결과가 캐시에 있다 |
| 공백 3칸 | **⚠ `?search=%20%20%20`이 그대로 나간다** — `trim` 안 함 |

### 2-5. 상태 개수 — `readinessCounts`가 이제 온다 ✅

```json
"counts": {"PLANNED":1,"RUNNING":1,"CLOSED":5},
"readinessCounts": {"PREP":0,"READY":1}
```

**14차 요청서 건이 해소됐다**(스펙엔 `required`인데 응답에 없어 목록이 흰 화면이 됐던 것).
`?? {}` 방어는 남긴다 — 서버가 다시 빼면 앱이 아니라 개수만 사라진다.

### 2-6. 상세를 갔다 뒤로 오면 조건이 전부 초기화된다

| | 가기 전 | 뒤로 온 뒤 |
|---|---|---|
| 검색어 | `spring` | **`""`** |
| 상태·교안·정렬 | 고른 값 | **초기값** |
| URL | `/operator/projects` | `/operator/projects` — **조건이 어디에도 없다** |

`useState`라 언마운트에서 사라진다. 표 자체는 캐시라 빨리 뜨는데, **좁혀 놓은 조건만
날아가서** 사용자는 목록이 갱신된 줄 안다.

### 2-7. 조용히 실패하는 조회 둘

| | 실패하면 | 사용자가 아는가 |
|---|---|---|
| `useLinkableCurricula` | 교안 셀렉트가 「전체」 하나 | **모른다** — 교안이 0개인 것과 구분 불가 |
| `useCohortScope` | `9기 전체 · 9반 209명` 줄이 없음 | 모른다 |

목록만 `ErrorState`를 갖는다. 나머지 둘은 실패해도 화면이 정상으로 보인다.

### 2-8. 페이지가 없다

스웨거 `GET /cohorts/{id}/projects`의 파라미터는 `search·curriculumId·status·sort`
넷뿐이고, `total`은 *"`projects`의 길이와 항상 같다"* 라고 스펙이 못 박는다 —
**서버가 전량을 준다.** 지금 7건이라 문제가 없고, 푸터도 페이저를 안 그린다(E7).
한 기수의 회차가 수십 개가 되기 전에는 부채가 아니다.

## 4. 고친 것

고친 줄은 지우지 않는다 — 같은 실수를 다시 하지 않으려면 **무엇이 왜 그랬는지**가 남아야 한다.

| | 무엇 | 어떻게 | 다시 잰 값 |
|---|---|---|---|
| ✅ 2-1 | 6초 백지 | 분기를 `isLoading` → **데이터 유무**로. `TableSkeleton` 7행 | 스켈레톤 456px vs 실제 458px — **2px** |
| ✅ 2-2 | 툴바 두 줄 접힘 | 트리거 폭을 박고(`w-56`) 이름은 말줄임 + `title` | 표 `top` 197 → **197**(조작 CLS 0) |
| ✅ 2-2b | *(그 수정이 만든 회귀)* 팝업까지 좁아져 열어도 이름이 안 보임 | 팝업만 `w-auto min-w-(--anchor-width)` | 항목 폭 214 → **557px** |
| ✅ 2-4 | 공백만 친 검색이 서버로 감 | `useDebounced(...).trim()` — **한 곳에서만** 다듬는다 | |
| ✅ 2-6 | 상세 왕복에 조건이 날아감 | `useState` → `useSearchParams`(`replace`) | 뒤로 **150ms에 7행 · 요청 0건** |
| ✅ 2-7 | 교안 조회 실패가 조용함 | 셀렉트가 「불러오는 중」·「불러오지 못했습니다」를 말하고 그동안 잠긴다 | |
| ✅ — | 툴바가 `라벨 · 값` 문자열 | 이름표를 컨트롤 안으로(`ControlLabel`) — OP-02와 같은 형태 | 셀렉트 셋 다 h36 · 값 `rgb(24,27,32)` |

`ControlLabel`을 `components/common`으로 올렸다 — OP-02 툴바와 이 화면이 같은 것을 쓴다.
**같은 모양을 두 번 적으면 다음 화면에서 셋이 된다.**

### 4-2. 2차 관찰에서 나온 것 — **앞 수정이 만든 것 둘 포함**

| | 무엇 | 누가 | 어떻게 |

#### 무한 로딩의 원인 — 동시 요청이 아니었다

처음엔 15차 R3(프록시가 동시 요청을 죽임)로 판정하고 순차화했다. **그래도 안 왔다.**
브라우저를 믿지 않고 curl로 **교안 7종 전수**를 돌리니 갈렸다.

| 교안 | `pageCount` | `/sections` |
|---|---|---|
| 5종 | `null` | **HTTP 000 · 60초 타임아웃 · 에러조차 없음** |
| spring_backend_v1 | 120 | 200 · TTFB 2.51초 · 섹션 7 |
| spring-test-ops-v1 | 38 | 200 · TTFB 2.03초 · 섹션 2 |

**상관이 완전하다** — 분석 전 교안에서만 무응답이다. 브라우저에서는 여기에 프록시 502가
겹쳐 `net::ERR_FAILED`가 되어 *"요청이 나가지도 않은 것"* 처럼 보였다.

화면은 `pageCount == null`인 교안을 **못 고르게 잠그고** 「분석 중 · 아직 못 고름」을
붙였다. 분석된 교안 2개로 후보 9건이 정상 표시되어 **생성 테스트가 가능해졌다.**
서버가 상태 필드를 주면 그 값으로 바꾼다(18차 R1·R2).
