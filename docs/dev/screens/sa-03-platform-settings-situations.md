### 축 K. 계정 행 액션(정지·재활성, `useUpdateSuperAdminStatus`) 파생 상태

| | |
|---|---|
| K1 | `ACTIVE`, `deactivatable: true` — 정지 가능 |
| K2 | `ACTIVE`, `deactivatable: false`(마지막 활성) — 버튼 비활성 + `title`("마지막 활성 슈퍼어드민은 정지할 수 없습니다") |
| K3 | `INACTIVE` — 행 `opacity-60`, "재활성" 링크(확인 없이 즉시 `mutateAsync`) |
| **K4** | **`PENDING`은 `INACTIVE` 분기에 안 걸려 `ACTIVE`와 같은 "정지" 버튼 분기를 탄다.** 파일 머리말 주석이 "PENDING도 INACTIVE로 정지할 수 있어 들어오지 못하게 하는 것은 된다"고 의도를 밝혀 뒀지만, 버튼 문구는 여전히 "정지"다 — 아직 활성화도 안 한 초대에 "정지"라는 말이 사용자에게는 "취소"로 안 읽힐 수 있다. 기능은 맞는데 문구가 상태를 안 따라간다 |
| **K5** | 정지 버튼을 눌렀는데 서버가 `LAST_SUPER_ADMIN`으로 거절(목록을 받은 뒤 다른 세션이 먼저 마지막 활성 계정을 정지시킨 경합). `catch`에서 전용 문구로 처리하는 코드는 있으나 실제 두 세션 경합으로 재현한 적 없음(SA-02 E7과 동일 성격) |
| **K6** | **자기 자신(`isSelf`) 행에서도 `deactivatable`이 참이면 "정지" 버튼이 그대로 활성이다.** 슈퍼어드민이 자기 자신을 정지시킬 수 있다는 뜻 — 마지막 한 명일 때만 막는 `deactivatable`은 "이 계정을 정지해도 되는가"만 판정하지 "지금 로그인한 사람인가"는 보지 않는다. 정의서 §6은 "마지막 슈퍼어드민은 정지할 수 없다"만 다루고 자기 자신 정지는 언급이 없다 — 의도된 것인지(정지 후 즉시 세션 만료 등 서버 쪽 처리가 있는지) 정책 확인 필요 |

## 조합 수

탭은 한 번에 하나만 보이므로 탭 간 상태는 곱하지 않는다. 축별로 세면 A(4) + B(4) + C(1) +
D(2) + E(3) + F(4) + G(10) + H(6) + I(8) + J(6) + K(6) — **개별 상황 약 54개.**
SA-02(약 55개)와 비슷한 폭이지만, SA-02가 탭 4개·모달 7개였던 것과 달리 SA-03은 **탭
2개·모달 4개 + 행 액션 2종**으로 진입점 수는 더 적다 — 대신 "되돌릴 수 없는 액션"(채점
모델 변경)과 "돈이 걸린 값"(단가) 비중이 더 높아 축 하나하나의 실패 비용이 크다.

| **G10 — 정책 확정: 차단** | 사용자 판단 — 채점 모델은 전 기관 강제 적용 단일 모델이라 단가 미설정으로 바뀌면 전 기관 채점 비용이 통째로 집계에서 빠진다(정의서 §6 "0으로 계산하지 않는다"와 같은 결). `ModelChangeDialog.tsx`의 옵션 목록에서 `pricingMissing` 모델을 제외(현재 채점 모델이 마침 그 상태면 목록엔 남기되 `SelectItem disabled`로 선택만 막음, 트리거 빈 값 방지). 재검증: 합성한 단가 미설정 모델이 옵션 목록에서 완전히 빠짐 확인, 현재 모델을 단가 미설정으로 흘리면 목록엔 남고 `data-disabled` 확인. |
| **K6 — 정책 확정: 차단** | 사용자 판단 — `deactivatable`(마지막 활성 여부)과 `isSelf`(로그인한 사람인지)는 서버가 보는 축이 다르니, 프론트가 후자를 추가로 막는다. `SuperadminAccountsTab.tsx`에서 `isSelf`면 `deactivatable`과 무관하게 "정지" 버튼 비활성 + `title="본인 계정은 정지할 수 없습니다"`(두 사유가 겹치면 본인 쪽을 우선 표시). 재검증: 실제 DB 정지는 재현 수단 부재로 보류(K6 실측 때와 같은 이유 — `.env.local`에 다른 슈퍼어드민 두 계정 비밀번호가 없어 되돌릴 방법이 없음) — 대신 렌더으로 내 행 `disabled=true`+`title` 확인, 다른 사람(김운영) 행은 그대로 `enabled`(회귀 없음) 확인. |
| **H6 — 팀장 답변: "확인 모달을 전부 다 띄우는 게 좋겠다"** | 범위는 화면 안 설정 변경 액션 전부. 채점 모델 변경(`ModelChangeDialog`)은 이미 확인 절차가 있어 그대로 두고, 나머지 4곳에 `AlertDialog`(Base UI 원시 컴포넌트, `ResultTab.tsx` 관례를 따라 각자 인라인)로 확인 단계를 추가했다: `TierModelDialog.tsx`(매핑 변경) · `PricingDialog.tsx`(단가 저장 — 기존 `willUnset` 실시간 경고 `Alert`는 그대로 두고 확인 모달에도 같은 사실을 한 번 더 담음, 타이핑 중 피드백과 커밋 직전 게이트는 성격이 달라 둘 다 유지하기로 판단) · `SuperadminInviteDialog.tsx`(초대) · `SuperadminAccountsTab.tsx`(정지·재활성 — 이 화면에 2곳뿐이라 D14 관례대로 공용 컴포넌트로 안 올리고 각자 인라인, 정지/취소는 danger 톤·재활성은 중립 톤). 재검증: 5곳 전부 "확인 모달 없이 절대 실행 안 됨"(버튼 클릭 직후 네트워크 요청 0건) 확인, 확인 모달에서 확정해야만 실제 요청이 나감 확인. 실패 시 모달이 안 닫히고 실패 문구가 모달 안에 남는 것도 확인(`ConfirmDialog.tsx` 관례와 동일). 기존 동작 회귀 없음 — J5(초대 메일 실패 시 목록 무효화)·K5(정지 시 LAST_SUPER_ADMIN) 둘 다 확인 모달 안에서도 그대로 동작. |
| **접근성 축** | 티어표·단가표·계정 행 버튼은 순수 텍스트 `<button>`이지만 전역 `:focus-visible` 규칙(`index.css`)이 걸려 있어 실제 키보드 Tab으로 도달하면 `outline: 2px solid var(--color-primary)`가 뜬다(실측 확인 — 처음에 `.focus()`로 테스트했을 때 outline이 안 잡혀 "포커스 링이 없다"로 오판할 뻔했는데, 프로그래밍 방식 focus는 `:focus-visible`을 신뢰성 있게 트리거하지 않는다는 브라우저 스펙 특성 때문이었다. 실제 키보드 Tab으로 재확인 후 정정) · disabled 버튼(K2 마지막 슈퍼어드민, K6 자기 자신)의 `title` 속성이 DOM에 그대로 존재(스크린 리더가 title/aria로 읽는 표준 경로) 확인 · `ModelChangeDialog`의 재캘리브레이션 체크박스는 `<label>`이 텍스트를 감싸고 있어 문장 클릭만으로 체크 토글됨(연결 확인) · 새로 추가한 확인 모달 5개 전부 Base UI `AlertDialog` 기본 동작으로 열릴 때 포커스가 모달 안으로 들어오고, `Esc`는 (Dialog 안에 중첩된 경우도) 확인 모달만 닫고 밑에 있던 원래 폼은 유지되며, 전체가 닫히면 포커스가 트리거 버튼으로 돌아옴 — 전부 렌더로 실측, 수정 불필요(기본 동작이 이미 맞음). |
