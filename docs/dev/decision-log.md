## D1 · 개발 착수: `feature/setup` 브랜치 + `docs/` 재편(plan/screen · handbook)

- **배경:** 목업(화면정의 v8) 단계가 끝나고 프론트엔드 개발이 시작됨. 목업 작업은 `planning` 브랜치에 쌓였고 기본 브랜치 `main`은 아직 Vite 스타터(hello-world). 산출물이 `docs/` 루트에 평평하게 섞여 있어(화면정의 + 방법론 + 구버전 v7 + 프로세스 문서) 개발 브랜치에 그대로 들고 가면 스펙과 잡문서가 구분되지 않음.
- **선택지:** (a) `planning`에서 그대로 개발 계속 (b) `main`에서 `feature/setup` 분기 후 필요한 문서만 이관 (c) 문서는 `planning`에만 두고 개발 브랜치는 순수 코드.
- **판단:** (b). `main`에서 `feature/setup`을 파고, **개발 레퍼런스가 되는 문서만** 이관하며 동시에 폴더를 재편한다.
  - `docs/plan/screen/definition/` — 화면정의 명세 전부(SC-\*, 번호문서, `_parking-lot`) + `_source/`(design-tokens · component-contract). **평면 유지**.
  - `docs/plan/screen/wireframe/` — 와이어프레임 HTML 23개.
  - `docs/handbook/` — 팀 협업 규약.
  - **제외:** 구버전 `docs/screens/`(v7) · `docs/superpowers/`(스펙 제작 프로세스 문서) · 루트 PNG 48장(작업 중 스크린샷) · 기획 단계 방법론·회고 문서. 전부 `planning` 브랜치에 보존.
- **근거·출처:** ① 명세서를 평면으로 유지한 이유 = SC↔번호문서↔`_source` 상호링크 34건이 전부 **같은 폴더 상대링크**라, 하위 폴더로 쪼개면 전량 깨짐(이관 전 grep 검증). ② 와이어를 별도 폴더로 뺀 것은 안전 = 마크다운 링크로 참조되는 곳이 0건(코드스팬 언급뿐). ③ 방법론·회고 문서를 뺀 이유 = 제품 스펙이 아니라 기획 단계 산출물이라 개발 브랜치에 두면 신입이 스펙으로 오독함.
- **경로 갱신 원칙:** **실제 파일을 가리키는 포인터만** 새 경로로 치환. **당시 결정의 기록은 원문 보존** — 화면정의 로그 D4의 "`docs/screen-def-v8/` 신규, 예전 `docs/screens/` 미참조"는 그대로 둔다. 히스토리를 새 경로로 덮어쓰면 결정 기록이 위조되므로.
- **목적·효과:** 개발자가 `docs/plan/screen/`만 보면 "무엇을 만드는가"가, `docs/handbook/`만 보면 "어떻게 일하는가"가 나온다.
- **후속:** 목업 배포(gh-pages, `team-iz.github.io/Frontend/`)와 `planning` 브랜치는 목업 아카이브로 유지하다 폐기. 폐기 전 태그로 박제 권장.

## D2 · 팀 Git 규약: 문서에 적을 것과 기계가 막을 것을 분리

- **배경:** 팀이 정한 Git/PR 규약 원문을 어디에 넣을지(md냐 커밋 시 실행되는 스킬이냐) 질문받음. 원문은 커밋 형식·체크리스트·브랜치 전략·PR 규칙·이슈 기준·충돌·커뮤니케이션이 한 덩어리로 섞여 있었음.
- **선택지:** (a) 원문 그대로 md 한 장 (b) 원문 그대로 AI 작업규약에 삽입 (c) **강제 수단별로 쪼개 배치**.
- **판단:** (c). 규칙을 주제가 아니라 **"무엇이 이걸 강제하는가"**로 나눈다.
  - **기계** — `.env` 금지=`.gitignore` · 커밋 메시지 형식=`commit-msg` 훅 · `console.log`=oxlint · 빌드=GitHub Actions · 직접 push=브랜치 보호 · PR 형식=템플릿
  - **핸드북 `docs/handbook/git-convention.md`** — 사람 판단 영역만(브랜치 전략·작업 흐름·이슈 등록 기준·충돌 예절·리뷰 SLA).
- **근거:** ① 원문 체크리스트 6개 중 5개가 기계로 검증 가능 — "console.log 제거" 체크박스보다 린트 룰 한 줄이 정확하고, 사람이 체크하는 항목은 바쁠 때 가장 먼저 생략된다. ② 원문이 같은 규칙을 **3번 중복** 기재했고 이미 드리프트 시작(`1인 승인` vs `1인 리뷰`, 체크박스 누락 2건) — 규약이 3개면 지켜지는 건 0개라 단일 원천으로 통합.
- **폐기:** "로컬에서 정상 동작 확인" 체크 항목 — 검증 기준이 없어 체크박스로 무의미.
- **발견한 충돌:** 규약 전체가 `develop` 통합 브랜치를 전제하는데 레포에 `develop`가 없었음 → 생성 + 브랜치 보호를 세팅 범위에 편입.
- **목적·효과:** 사람은 판단이 필요한 것만 읽고, 나머지는 커밋·PR 시점에 자동으로 막힌다.

## D3 · 규약 자동화: git 네이티브 훅 + 브랜치별 이슈 번호 자동 부착

- **배경:** [[D2]]에서 "문서에 적으면 무시된다 → 기계가 막아야 한다"고 판단한 것의 구현. 추가로 "커밋마다 이슈 번호를 사람이 타이핑해야 하나"라는 문제 제기.
- **선택지(훅 설치):** (a) husky 도입 (b) **git 네이티브 `core.hooksPath`** (c) 각자 `.git/hooks`에 수동 복사.
- **판단:** (b). `.githooks/`를 레포에 커밋하고 `core.hooksPath`로 가리킨다. husky는 이 정도 검사에 npm 의존성 하나를 더 얹는 것이라 불필요. `package.json`의 `prepare` 스크립트가 `npm install` 시 자동 설정하므로 팀원은 클론 후 별도 조치가 없다. (c)는 버전 관리가 안 되어 사람마다 규칙이 갈린다.
- **선택지(이슈 번호):** (a) 매번 손으로 입력 (b) 브랜치명에 번호를 넣어 파싱(`feature/3-setup`) (c) **`git config branch.<name>.issue`에 1회 등록 → `prepare-commit-msg`가 자동 부착**.
- **판단:** (c). (b)는 규약의 브랜치 네이밍(`feature/login-api`)을 바꿔야 하고, (a)는 누락이 반복된다. (c)는 브랜치 생성 시 한 번만 등록하면 이후 커밋 전부에 `(#N)`이 붙고, 이미 번호가 있으면 존중한다.
- **차단 범위:** 되돌리기 비싼 것만 막는다 — `main`·`develop` 직접 커밋, `.env` 스테이징(`.env.example`류는 허용), **AI 공동저자 trailer**(`Co-Authored-By`·`Generated with`·🤖 — 커밋 저자는 사람). 이슈 미연결은 **경고만** 하고 통과시킨다(오타·포맷팅은 이슈 없이 커밋하는 것이 규약 §3).
- **길이 규칙 해석:** 50자 상한은 **`(#N)`을 제외한 설명** 기준. 훅이 자동 부착하는 메타데이터까지 세면 사용자가 쓴 적 없는 글자로 커밋이 거부되기 때문.
- **검증:** `.githooks/test-hooks.sh` 자체 검사 18케이스(정상 7 · 위반 11) **전량 통과**. 이슈 자동 부착·중복 방지·`.env` 차단은 실제 실행으로 확인.
- **한계(명시):** 로컬 훅은 `--no-verify`로 우회된다. **최종 방어선은 GitHub 브랜치 보호 규칙**이며 이는 레포 설정 사항이라 훅으로 대체 불가.
- **AI 서명 소급 안 함:** 기존 히스토리에 5건 이상 유입됐으나 이미 push된 커밋의 재작성 비용이 크고 다른 브랜치·gh-pages까지 물려 있어 앞으로만 차단.

## D4 · default 브랜치를 `develop`으로 변경

- **배경:** 규약은 "모든 기능은 develop으로 머지"인데 GitHub default가 `main`이었음.
- **판단:** default = `develop`.
- **근거:** ① **`closes #N` 자동 닫힘은 default 브랜치로 머지될 때만 작동한다.** default가 main이면 feature→develop 머지로 이슈가 안 닫혀 승격 전까지 계속 열려 있음 — 규약과 GitHub 동작이 어긋남. ② New PR 기본 base가 develop이 되어 실수로 main에 PR을 넣는 사고가 준다. ③ `main`의 역할이 "프로덕션 릴리스 전용"으로 명확해진다.
- **필수 동반 조치:** default를 옮겼으므로 **`main`·`develop` 둘 다** 브랜치 보호를 건다. 안 그러면 develop이 무방비가 된다.
- **연결:** `docs/handbook/issue-and-branch-online.md` §4·부록.

## D5 · 세팅 1차: 되돌리기 비싼 것부터 (strict · 포매터 · alias · CI)

- **배경:** "팀 협업을 위해 세팅 단계에서 뭘 해야 하나" 질문. 목적은 도구를 채우는 게 아니라 **자유도를 미리 줄이는 것** — 4명이 4가지 방언으로 쓰기 시작하면 되돌릴 수 없다. 판단 기준은 하나: **"나중에 하면 비싼가"**(Type-1/Type-2, 화면정의 로그 D5와 동일 프레임).
- **한 것 (Type-1 — 코드 쌓이기 전에만 쌈):**
  - **`strict: true`**(app·node 양쪽). 지금 켜서 **에러 0건**, 코드가 쌓인 뒤면 수백 건. 실측 확인 후 적용.
  - **Prettier** — 없으면 매 PR이 공백 diff 전쟁이 되어 리뷰가 로직을 못 본다. 설정은 **기존 코드 스타일에 맞춤**(`semi:false`·`singleQuote`) — 포매터 도입으로 생기는 리포맷 diff를 최소화하기 위함.
  - **`@/` path alias**(vite `resolve.alias` + tsconfig `paths` 쌍) — `../../../` 방지. tsc·vite 양쪽에서 실제 import로 해석 검증.
  - **`.editorconfig`** — prettier를 안 돌리는 에디터·비JS 파일 대비.
- **한 것 (Type-2지만 매일 아픈 것):** CI(GitHub Actions) · Node 22 고정(`.nvmrc`+`engines`) · README를 Vite 템플릿 원문에서 팀 온보딩용으로 교체 · PR 템플릿.
- **포매터 적용 범위 — 마크다운 전면 제외:** prettier가 표 셀을 **글자 수 기준**으로 패딩하는데 한글은 표시 폭이 2배라, 스펙 문서 30여 개의 표가 오히려 어긋난다(README에서 실제로 재현·확인). 렌더 결과는 어차피 같으므로 **`**/*.md` 전체 제외**. 포매터는 코드·설정에만 건다.
- **`baseUrl` 제거:** TypeScript 6에서 deprecated(TS5101). `paths`만으로 tsconfig 위치 기준 해석되므로 `ignoreDeprecations`로 덮지 않고 제거하는 쪽을 택함.
- **CI 3단계(format:check · lint · build):** `build`가 `tsc -b && vite build`라 타입 검사를 포함 → typecheck를 따로 돌리지 않는다(중복 제거). **로컬에서 CI와 동일 명령을 전수 실행해 3단계 전부 종료코드 0 확인** 후 커밋.
- **안 한 것 (명시):**
  - **`.env.example`** — 환경변수가 아직 0개. 빈 파일은 "나중을 위한 스캐폴딩"이므로 MSW/API가 붙는 단계에서 첫 변수와 함께 만든다.
  - **Storybook** — 컴포넌트 소비자가 여러 팀이 될 때. 3~4명 규모에 와이어프레임이 이미 스펙 역할을 하므로 유지비만 남는다.
  - **Vitest·E2E** — 테스트할 로직이 아직 없다. 첫 실제 로직(RBAC 게이트·기수 스코프 전파)에서 도입.
  - **폴더 레이어 경계(ui/common/features)** — 빈 디렉터리를 미리 파는 건 스캐폴딩. 실제 컴포넌트가 생기는 디자인 시스템 작업에서 규칙과 함께 확정.
- **이슈 분리:** `#3 [Chore] Project Settings` = `src/`를 건드리지 않는 레포·협업 인프라까지. 디자인 시스템(토큰→Tailwind `@theme`·컴포넌트 3계층·variant 어휘·a11y·RBAC 프리미티브)은 **첫 실제 코드**라 리뷰 포인트가 완전히 달라 별도 이슈로 분리(규약 §4 "1 PR = 1 기능", 파일 10개 이내).
- **연결:** [[D1]] 개발 착수 · [[D2]] 규약 배치 원칙 · [[D3]] 훅 자동화 · `docs/plan/screen/definition/07-frontend-setup-plan.md` 0단계.

## D6 · 리뷰 승인을 강제하지 않는다 (의도적 이탈)

- **배경:** ruleset을 점검하다 규약(§2·§4 "최소 1인 리뷰")과 실제 설정(`required_approving_review_count: 0`)이 어긋난 것을 발견. 규약대로 1로 켤지 물음.
- **판단:** **켜지 않는다. 대신 문서에서 "1인 리뷰" 문구를 걷어내고 이탈임을 명시한다.**
- **근거:** 프론트 인원이 **2명**이라 승인 필수는 곧 "매 PR이 상대 1명에게 병목"이다. 지금은 일정이 빠듯해 그 대기 비용이 리뷰로 얻는 것보다 크다는 판단.
- **대신 하는 것:** 리뷰가 필요한 변경(공용 기반·설계 결정·남의 영역)은 **머지 전에 말로 요청**한다. 규칙이 아니라 판단으로 가져간다.
- **되돌리는 조건:** 인원이 늘거나 일정에 여유가 생기면 승인 1인을 다시 켠다.
- **왜 문구를 지웠나:** 지켜지지 않는 규약을 문서에 남겨두면 **나머지 규약의 신뢰도까지 같이 떨어진다**([[D2]] "규약이 3개면 지켜지는 건 0개"와 같은 이유). 정석이 아님을 아는 상태로 내린 결정이라는 사실 자체를 기록해 둔다 — 몰라서 빠진 것과 알고 뺀 것은 다르다.
- **함께 확인된 것:** ruleset에 `required_status_checks`가 없어 **CI가 빨개도 머지되던 상태**였다. 이건 이탈이 아니라 누락이므로 `verify` 체크를 필수로 걸었다.

## D7 · `.gitattributes`로 줄바꿈을 저장소 차원에서 고정

- **배경:** "`.gitattributes`가 없어 Windows·Mac 사용자가 같은 파일을 저장만 해도 전체가 바뀐 것처럼 보인다"는 지적을 받고 검증.
- **검증 결과:** 지적은 타당하다. 다만 현재 추적 파일 중 **CRLF는 0개**(전부 LF)이고 `core.autocrlf`는 미설정 상태였다.
- **판단:** 지금 넣는다. `* text=auto eol=lf` + 바이너리 확장자 명시.
- **근거:** ① `core.autocrlf`는 **사람마다 다른 로컬 설정**이라 신뢰할 수 없다 — Windows Git 설치 옵션에 따라 갈린다. 저장소 차원 보증은 `.gitattributes`뿐. ② 이미 넣은 `.editorconfig`·`.vscode`의 `eol=lf`는 **에디터** 설정이라 git의 체크아웃/커밋 변환은 막지 못한다. ③ **타이밍:** 지금은 정규화할 파일이 0개라 비용이 파일 1개지만, Windows 팀원이 CRLF를 커밋한 뒤에는 **전 파일을 건드리는 정규화 커밋**이 필요해진다 — 정확히 지적이 우려한 "왜 파일 전체를 고쳤지?" 상황이 된다.
- **검증:** `git add --renormalize .` 결과 변경 0건(공짜 시점 확인). `git check-attr`로 텍스트 파일은 `text=auto eol=lf`, PNG는 `binary set`으로 변환 차단됨을 확인.

## D8 · 이슈·PR 제목은 `[Tag] Title Case`, 커밋은 소문자 명령형

- **배경:** 이슈 제목 컨벤션 요청 — `[Chore] Project Settings`처럼 **의미 있는 단어는 대문자로 시작**하고, 관사·등위접속사·짧은 전치사 같은 무의미한 단어는 소문자.
- **판단:** 요청대로 Title Case. **더해서 PR 제목도 같은 규칙으로 통일**한다(기존 규약은 `[feat] add login page UI` 소문자였음).
- **근거:** 이슈와 PR은 **둘 다 GitHub UI에서 사람이 읽는 제목**이라 다른 규칙을 쓸 이유가 없었다. 반면 커밋 메시지는 소문자 명령형을 유지한다 — git 전통이고 훅이 이미 그렇게 검사하며, 로그를 기계로 훑는 대상이라 성격이 다르다. 경계를 "누가 읽는가"로 그었다.
- **어휘:** 태그는 커밋 type과 동일 — `[Feat]` `[Fix]` `[Refactor]` `[Style]` `[Docs]` `[Chore]` `[Remove]`.
- **강제 수단:** **훅으로 막을 수 없다**(제목은 GitHub 쪽). 이슈 제목을 검사하는 Action은 2명 팀에 잔소리 비용이 더 크다고 보고 만들지 않았다. 대신 **이슈 템플릿의 `title:` 기본값**(`[Fix] `·`[Feat] `)으로 형태를 미리 보여주는 방식을 택했다 — 빈칸보다 강하고 봇 코멘트보다 조용하다.
- **적용:** 템플릿 2개 기본 제목, PR 템플릿 주석, 규약 §3·§4, 이미 올라간 PR #4 제목.
- **부수 발견:** 이 레포는 옛 Projects(classic)가 붙어 있어 `gh pr edit`·`gh issue view`가 GraphQL 에러를 낸다. 제목 수정은 REST(`gh api -X PATCH`)로 우회했다.

## D9 · 디자인 토큰: 1레이어(의미론) + 가드, 컴포넌트는 미룸

- **배경:** 참고용으로 사내 다른 프로젝트(React Native 기반)의 디자인 시스템을 검토. 2레이어(원시 팔레트 → 시맨틱)를 쓸지, 컴포넌트를 먼저 만들지 판단 요청.
- **핵심 비대칭(사용자 지적):** 그 시스템은 **화면 5개를 만든 뒤 추출한 결과물**이다("값은 실화면의 실측 사용 빈도에서 도출"). 우리는 화면이 0개다. 같은 산출물을 시작점으로 복제하면 **추측을 시스템처럼 포장**하게 된다. → 베낄 것은 그들의 *산출물*이 아니라 *방법*(만들고 → 재고 → 뽑고 → 왜인지 적는다).

### 판단 기준
**"화면을 만들어봐야 알 수 있는가?"** — 그렇다면 지금 정하지 않는다. 색은 컴포넌트 구조와 독립적이므로(Button을 어떻게 쪼개든 primary는 `#3a4db8`) 토큰은 지금 확정, 컴포넌트 API는 미룸.

### 레이어 = 1개 (원시 팔레트 층 없음)
검토한 측면과 우선순위: ① 가역성 ② 테마 확장 ③ 디자인 소스 정합 ④ 강제 가능성 ⑤ 인지 부하 ⑥ SOLID ⑦ 변경 전파.

- **① 가역성이 결정적 — 한 방향 문이 아니다.** `@theme` 안에서 `--color-primary: var(--color-blue-600)` 형태의 참조가 동작함을 **빌드로 확인**했다. 나중에 원시 층을 끼워도 컴포넌트(`bg-primary`)는 변경 0건. 되돌릴 수 있으면 "지금 필요한 만큼만" 짓는 게 옳다.
- **② 테마 확장 요구 없음** — 플랫폼 콘솔 설정 탭은 상태·AI예산·보존기간·공개범위뿐이고 **기관별 브랜딩 항목이 없다**. 다크 모드도 스펙에 없다(교육생 세션의 다크 코드패널은 컴포넌트 색이지 테마가 아님). 2레이어의 최강 논거가 해당 없음.
- **③ 디자인 소스 정합** — 우리 SSOT는 역할당 값이 1개로 저작됐다. 원시 팔레트를 만들면 **디자인에 없는 구조를 발명**하는 것. 그쪽은 반대로 디자인 원본에 번호 스케일이 있어 2레이어가 원본을 반영한 것이다.
- **④ 강제 가능성** — 2레이어는 "컴포넌트는 시맨틱만 참조" 규율이 있어야 성립하는데, **참고 프로젝트조차 "가능하면 시맨틱을 먼저"라는 연성 규칙**이라 이미 새고 있다. 강제 못 하는 레이어는 무너지고, 무너진 2레이어는 1레이어보다 나쁘다(개념 2개·규율 0).
- **⑥ SOLID** — DIP(구체 대신 추상 의존) 이득은 컴포넌트가 hex 대신 `bg-primary`를 쓰는 시점에 **이미 달성**된다. 원시 층의 추가 이득은 SRP/OCP인데, 그건 **팔레트가 의미와 독립적으로 변할 때**만 값어치가 있다 — 전담 디자이너가 팔레트를 따로 관리하지 않는 우리 구조에선 발생하지 않는다.
- **전환 트리거를 `index.css` 주석에 명시:** ①다크모드·기관 브랜딩 요구 ②같은 계열 명도 단계 5개 초과(현재 최대 primary 4) ③디자이너의 독립 팔레트 관리.

### 이름 = 역할 기준 (실측)
`text-text-2` 같은 중복을 없애고 역할을 드러냄. 와이어 측정: `--c-text-3` **614회**(47%가 xs·11px 동반 → 캡션·메타), `--c-text-2` **280회**(19% → 보조 본문). → `fg` / `fg-muted` / `fg-subtle`, `bg` → `canvas`. **SSOT 문서도 같이 갱신**했다(코드와 문서가 갈리는 것보다 낫다).

### 간격 의도 레이어는 만들지 않음
참고 프로젝트의 간격 의도 레이어(화면 패딩·요소 간격에 이름을 붙인 것)는 실화면 빈도에서 도출된 것. 우리 와이어는 **지배적 패딩값이 없다**(sp-3/4/5/6 = 27·19·11·3회) → 만들면 존재하지 않는 일관성을 발명하게 된다. Tailwind 기본 스케일을 그대로 쓰고 **컨테이너 폭만** 토큰화(`--container-page`, 와이어 10회 일관).

### 가드 = 코드로 (참고 프로젝트에서 가져온 것)
그 프로젝트의 토큰 검사 스크립트는 **컴포넌트 29개에 하드코딩 hex 0건**이라는 결과로 실효성이 입증됐다. 이걸 본떠 `scripts/check-design.mjs`를 만들되 **bash가 아니라 Node**로 썼다 — `.gitattributes`로 Windows 호환을 챙겨놓고 bash 스크립트를 두면 앞뒤가 안 맞는다.
- 검사 ①하드코딩 hex(토큰 정의 파일만 예외) ②대비 AA 16쌍.
- **가드가 즉시 결함을 잡았다:** `fg-subtle #6b7280`은 흰 배경에서 4.83:1로 통과하지만 **실제 페이지 배경(`canvas` #f4f5f7)에서 4.43:1로 미달**이었다. 수동 검산이 놓친 것을 잡아 `#686f7d`(4.63:1)로 교정. 가드를 만든 이유가 그대로 증명됨.
- CI 3단계 → 4단계(design 추가). 위반 시 종료코드 1, 정상 0을 실제로 확인.

### 컴포넌트를 지금 만들지 않음
3번 반복되기 전엔 추출하지 않는다. 첫 화면에서 뽑은 Button은 두 번째 화면에서 반드시 틀린다. 순서를 이렇게 잡았다:
```
① 토큰 + 가드(이 결정)  → ② 화면 1개를 추상화 없이 끝까지 → ③ 두 번째 화면(중복 노출)
→ ④ 추출  ← 여기서부터 2명 병렬
```
②의 첫 화면은 **교육생 리스트** — 173줄로 가장 단순한데 반복 패턴(표·툴바·페이저·배지·빈상태)을 다 품어 추출 수확이 가장 크다. **병렬 시점이 "공용 컴포넌트 완성 후"가 아니라 "④ 추출 후"로 바뀐다.**

### 그 외 버린 것
TS 객체 토큰(RN은 CSS가 없어 불가피했던 것 — 우리가 하면 토큰이 두 곳에 생겨 drift), `AppText` 강제 래퍼(웹은 CSS 상속이 함), 학습용 장문 주석, 컴포넌트 29개 선제작.

## D10 · 디자인 시스템 카탈로그 페이지 — 그리고 그것이 드러낸 결함 3건

- **배경:** "만든 것을 한 화면에서 다 보고 싶다"는 요청. Storybook은 [[D9]]에서 규모에 안 맞아 제외했다.
- **형태를 두 번 바꿨다.** 처음에 앱 라우트(`/dev/design-system`)로 만들었으나, **정적 HTML이어야 한다**는 지적을 받고 생성물로 바꿨다. 이유가 타당했다 — ① 앱 코드는 검수 후 커밋해야 하는데 문서는 먼저 공유하고 싶었고, ② 팀원이 문서를 보려고 개발 서버를 띄워야 하는 것은 문턱이 높다. 지금은 `npm run doc:design`이 `docs/dev/design-system.html`을 만들고, 브라우저로 바로 열린다(외부 자원 참조 0건 확인).
- **핵심 판단 — 토큰 값을 문서에 적지 않는다.** 값을 하드코딩하면 토큰이 바뀔 때 문서가 조용히 거짓말을 하게 된다. 생성 시점에 `src/index.css`에서 읽어 이름·값 모두 `@theme` 하나에서만 나오게 했다. 가드가 하드코딩 hex를 막는 것과 같은 원칙이다.
- **드리프트를 CI가 막는다.** `--check`는 생성 결과가 커밋된 파일과 다르면 실패한다. 토큰만 고치고 문서를 다시 만들지 않는 것은 반드시 일어나므로 사람에게 맡기지 않는다(토큰 한 글자를 바꿔 종료 코드 1을 실측).
- **만들면서 결함 3건이 드러났다.** 카탈로그가 없었으면 전부 조용히 남았을 것들이다.

### ① Tailwind가 토큰을 `@layer` 안에 넣는다
최상위 `cssRules`만 훑으면 토큰이 **0개** 잡힌다. `:root, :host` 규칙이 `CSSLayerBlockRule` 안에 있어서다. 중첩 규칙까지 내려가도록 고쳤다. 빌드는 통과하므로 렌더해보기 전에는 알 수 없는 종류의 결함이었다.

### ② 문서에 적은 예시 코드가 빌드 CSS에 실렸다
카탈로그에 `--color-blue-600`이 떠서 추적하니, 값이 내가 쓴 hex가 아니라 **Tailwind 기본 팔레트의 oklch 값**이었다. 원인은 `docs/dev/decision-log.md`에 남긴 원시 팔레트 예시 한 줄 — Tailwind v4는 기본적으로 **프로젝트 전체**를 훑어 클래스 후보를 찾으므로 문서의 텍스트까지 스캔 대상이 된다.
- **조치:** 문서를 고치지 않고 **스캔 범위를 좁혔다**(`@import 'tailwindcss' source(none)` + `@source '.'`). 문서는 앞으로도 늘어나므로 원인 쪽을 막는 것이 맞다.
- **효과:** 빌드 CSS 19,666 → **17,265 bytes**. 문서에서 끌려오던 것이 그만큼 있었다.
- 주석을 고치다 같은 함정에 두 번 빠졌다("기본 팔레트 이름을 적지 말 것"이라고 쓰면서 그 이름을 적었다). 스캐너는 주석·문서를 가리지 않는다.

### ③ 정의했는데 방출되지 않는 토큰이 있었다
`success`·`neutral-soft`·`primary-border` 등 5개가 아직 어느 화면도 쓰지 않아 CSS에 실리지 않았다. 카탈로그가 "있는 토큰"이 아니라 "쓰인 토큰"만 보여주면, 새로 합류한 사람이 `success`를 못 찾고 임의 색을 만든다.
- **조치:** `@theme static`으로 전량 방출. 비용은 **175 bytes**로, 발견 가능성이 그 값어치보다 크다.

- **부수 효과:** 문서가 세는 색 개수와 가드가 세는 개수가 일치해 서로를 교차 검증한다. 분류에 안 잡힌 토큰은 "그 외"로 떨어져 눈에 띈다.
- **참고:** ①③은 실행 중 스타일시트를 파싱하던 시절의 결함이다. 정적 생성으로 바꾸면서 `@layer` 문제는 사라졌고(CSS 원본을 직접 읽는다), 미방출 토큰 문제도 사라졌다(`@theme static`은 유지 — 유틸리티 클래스 자체는 여전히 사용된 것만 생성된다). 그러나 ②(문서가 CSS를 오염시킴)는 형태와 무관하게 남는 문제였고 그대로 유효하다.

## D11 · 문서를 협업 자료로 — 정보를 세 층으로 나눈다

- **배경:** 팀원이 이 페이지를 보고 코드를 짤 것이므로 "어떤 경우에 쓰는지"와 "왜 그렇게 정했는지"가 필요하다. 다만 다 펼치면 훑어보기가 안 되고, 다 숨기면 아무도 근거를 안 읽는다.
- **판단 — 읽는 목적이 다르면 층을 나눈다.**

| 층 | 무엇 | 언제 읽나 | 수단 |
|---|---|---|---|
| 1 | 토큰 이름·값 | 무엇이 있는지 훑을 때 | 항상 보임 |
| 2 | 언제 쓰나 + 실제 예 | 코딩하다 잠깐 확인할 때 | 호버·포커스 |
| 3 | 왜 이렇게 정했나 | 합류했거나 규칙을 바꾸려 할 때 | 클릭(`<details>`) |

- **2층을 호버로 한 이유:** 코딩 중 확인은 빈도가 높고 짧다. 클릭이면 흐름이 끊긴다. 단 **호버 전용은 접근성 실패**이므로 카드를 `tabIndex=0`으로 두고 `group-focus`에도 같은 규칙을 걸었다(키보드로 Tab 이동 시 동일하게 열림을 실측 확인). 팝오버는 절대 위치로 겹쳐 띄운다 — 카드가 커지면 격자가 흔들린다.
- **3층을 `<details>`로 한 이유:** 네이티브라 키보드·스크린리더가 기본 동작하고, 접혀 있어도 내용이 문서에 있어 검색·인쇄에 걸린다. 상태 관리 코드도, JavaScript도 필요 없다 — 정적 HTML로 옮기면서 이 선택이 더 값어치를 했다.
- **설명을 `scripts/design-doc-content.mjs`로 분리:** 값은 `@theme`에서 읽고, 설명은 이 파일에서만 온다. **값을 두 곳에 적으면 한쪽이 반드시 낡는다**는 [[D10]]의 원칙을 설명에도 적용했다.
- **문서 구멍이 드러나게 했다:** 설명이 없는 토큰은 팝오버가 없어 눈에 띈다. 현재 우리가 정의한 31개는 전부 설명이 있고, 없는 것은 Tailwind 기본 `white` 하나다.
- **값이 조정된 토큰(4개)에 표시(✎)를 붙였다.** SSOT와 다른 값을 쓰는 이유를 카드에서 바로 알 수 있어야, 팀원이 SSOT 문서를 보고 "왜 다르지"라고 혼란스러워하지 않는다.

### 가드에 예외 표시를 추가했다

문서는 **"이렇게 쓰지 마라"를 보여주려고 그 나쁜 예를 적어야 한다.** 실제로 카탈로그의 금지 예시와 옛 SSOT 값 인용이 가드에 걸렸다.

- **판단:** 예시를 흐리게 쓰는 대신 줄 단위 예외 표시(`design-token-allow`)를 뒀다. 문서에서 반복될 상황이고, 예외 수단이 없으면 사람들이 **규칙 자체를 약화시키는 쪽**으로 간다.
- **표시가 눈에 보이고 grep으로 셀 수 있게** 했다 — 현재 5건(금지 예시 2, 옛 값 인용 3). 이 수가 늘어나면 규칙이 현실과 안 맞는다는 신호다.

## D13 · 프리미티브를 전부 Base UI 위에 — 손수 구현 폐기

- **배경:** shadcn CLI(`base-nova` 스타일)로 뽑은 Base UI 포트와 손수 만든 버전을 나란히 두고 비교했다. 가르려던 것은 "Base UI로 우리 디자인을 그대로 재현할 수 있는가"와 "손수 만든 게 나은 지점은 어딘가".
- **1차 판단(기각):** APG 명세가 있는 위젯만 Base UI로 — Dialog·Tabs. Button·Badge·Card는 포커스·포털·키보드 관리가 필요 없어 이득이 없다고 봤다. 실제로 Base UI 프리미티브 위에 같은 cva를 얹었더니 픽셀 단위로 동일했다.
- **최종 판단(뒤집음):** **여섯 개 전부 Base UI 위에.** 손수 버전은 폐기했다.
  - 지금 안 쓰인다고 앞으로도 안 쓰이는 게 아니다 — Button에 아이콘·로딩이 붙거나 "버튼처럼 보이는 링크"가 필요해지는 건 시간 문제다. Base UI Button의 `render`(다른 요소로 렌더)·`focusableWhenDisabled`(비활성도 탭으로 닿게)는 그때 새 컴포넌트 없이 확장된다. Badge도 `useRender`로 같은 이점.
  - **"지금 필요 없다"(YAGNI)보다 "기반을 하나로 통일해 나중에 갈아끼우지 않는다"를 우선했다** — 프리미티브 레벨이라 화면 결정보다 되돌리기 비용이 크다.
  - 픽셀까지 같았다는 실측은 여전히 유효하다. "이득이 없다"가 아니라 "당장의 이득은 없지만 나중 확장 비용이 더 크다"로 결론이 바뀐 것이다.
- **CLI 결과물을 그대로 커밋하지 않는다 — 3단계를 거친다.** ① cva를 우리 토큰으로 교체(`rounded-lg/xl`은 우리 스케일에 없는 값이다) ② 안 쓰는 variant·size 전량 삭제 ③ 파일명·export 정규화. 안 거치면 "variant를 임의로 늘리지 않는다"는 자체 규율이 CLI 한 번에 무너진다.
- **export 규약:** 서브컴포넌트가 없는 단일 요소(Button·Badge)는 `export default` + named 둘 다. 컴파운드(Card·Dialog·Table·Tabs)는 named만 — 서브컴포넌트가 여럿이라 default가 애초에 불가능하다.
- **문서와 대조해 기본값에서 되돌린 것 2건.** Button의 `border border-transparent`(문서의 `.btn`은 `border: 0`이고 ghost만 1px), Badge의 `h-5` 고정 높이(`.bdg`는 높이를 정하지 않는다 — 고정하면 글자가 커질 때 잘린다). **"Base UI 위에"가 "shadcn 기본값대로"를 뜻하지는 않는다.**
- **shadcn 토큰층이 우리 토큰을 덮고 있었다.** `@theme static` 뒤에 `@theme inline`이 붙으면서 같은 이름을 뒤엣것이 이겼다. 빌드 산출물로 실측하니 `bg-primary`가 `#3a4db8`이 아니라 거의 검정, `rounded-md`가 10px이 아니라 8px, body 배경이 canvas가 아니라 흰색이었다. 겹치는 이름을 `@theme inline`에서 빼고 `:root`의 shadcn 변수를 전부 `var()`로 우리 토큰에 연결했다 — **값을 두 곳에 적으면 한쪽이 반드시 낡는다**는 [[D10]]의 원칙을 토큰 이름에도 적용한 것이다.
  > CSS 커스텀 프로퍼티 충돌은 **타입 검사도 린트도 못 잡는다.** 빌드 산출물을 열어보기 전까지 아무도 모른다.
- **미착수:** 아이콘 전용 버튼 사이즈(Dialog 닫기 버튼이 `size="sm"` + `p-1.5`로 정사각형을 흉내내는 중 — 실제 공백이지만 사용처가 한 곳뿐이라 둘째가 생길 때), 기수/프로젝트 전환 팝업(Select가 아니라 Menu Button 패턴이라 별개).

## D14 · 중복 프리미티브를 지금 통합하지 않는다 — 세 번째 등장까지

- **배경:** 인증 화면이 합류하면서 같은 역할의 조각이 두 벌이 됐다.

  | 인증 쪽 | 공용 쪽 | 겹치는 것 |
  |---|---|---|
  | `features/auth/components/PrimaryButton` | `components/ui/Button` | 주 액션 버튼 |
  | `features/auth/components/BrandPanel` + `AuthForm` | (셸 없음) | 인증 화면 2단 레이아웃 |
  | `features/auth/components/TextField` · `PasswordField` | (없음) | 입력 필드 |

- **판단: 지금 통합하지 않는다.** 사용처가 인증 화면 3개뿐이라, 지금 올리면 **인증 화면 사정에 맞춘 것이 공용이 된다.** 이건 `frontend-architecture.md`가 경계한 그 함정이다 — "처음부터 공용으로 만들면 한 곳의 사정에 맞춘 것이 공용이 된다."
- **다시 볼 시점:** 같은 조각이 **두 번째 도메인에서 필요해질 때**(세 번째 등장). 그때는 두 도메인이 실제로 공유하는 부분이 무엇인지 눈으로 보인다. 지금은 추측해야 한다.
  > 한 번은 만들고, 두 번은 기록하고, **세 번째에 올린다.** 두 번째에 올리면 공통점이 아니라 우연의 일치를 공용으로 만든다.
- **이슈로 두지 않고 여기 적는 이유:** "언제 끝난 것인가"를 판정할 수 없기 때문이다. 완료 조건을 쓸 수 없는 것은 이슈가 아니라 결정이다. 이슈로 두면 아무도 못 닫는 채 목록에 남아, 진짜 열린 작업이 안 보이게 된다.
- **중복이 생긴 진짜 원인은 규칙 부재가 아니다.** 규칙(`빈도 5회 이상만 공용으로`)은 이미 있었고 문서에도 적혀 있었다. 두 사람이 각자 만든 이유는 **만들기 전에 볼 곳을 몰랐기** 때문이다. 2인 팀에서 이걸 막는 것은 린터가 아니라 화면 착수 전 **"이 화면에 뭐가 필요한가"를 맞춰보는 5분**이다 — "이 두 파일이 같은 것"은 기계가 판정할 수 없다.

## D15 · 레이어 경계 린트가 절반만 지켜지고 있었다

- **배경:** 인증 화면을 계층 구조로 옮기며 import 방식을 정하다가, 규칙을 실제로 돌려보고 발견했다.
- **결함:** `@/features/*/*` 는 glob의 `*`가 `/`를 넘지 않아 **딱 두 단계만** 잡는다.

  | import | 고치기 전 | 후 |
  |---|---|---|
  | `@/features/{남}/AuthContext` | 막힘 | 막힘 |
  | `@/features/{남}/components/TextField` | **통과** | 막힘 |

  하필 통과하던 쪽이 **남의 도메인 컴포넌트 가져다 쓰기** — 교차 참조의 제일 흔한 형태다. 규칙은 있는데 정작 막아야 할 것을 안 막고 있었다.
- **고침:** 패턴에 `@/features/*/**` 를 더했다. feature가 늘어도 이 줄은 그대로다.
- **feature 안은 상대경로로 참조한다.** 이 규칙이 자기 자신도 막기 때문이기도 하지만, 그것과 별개로 폴더째 옮길 때 내부 import를 다시 쓰지 않아도 된다. 실제로 인증 화면을 옮기며 절대경로로 쓰인 import를 13개 파일에서 다시 썼다. `@/` 로 시작하면 그것만으로 "내 모듈 밖"이 드러나는 이점도 있다.
  > **규칙이 있다는 것과 규칙이 작동한다는 것은 다르다.** 검사 규칙도 코드다 — 통과하는 것만 보지 말고, **막아야 할 것을 넣어서 실제로 막히는지** 확인해야 한다. 이 결함은 규칙을 도입한 날부터 있었지만, 아무도 위반 코드를 넣어본 적이 없어 드러나지 않았다.

## D16 · v1 화면·셸을 지우지 않고 격리한다 — `git mv`로 보관

- **배경:** v2 화면정의서(25화면, `docs/plan/v2/`)가 확정되면서 기존 화면·셸(`src/features`, `src/shells`)이 전부 v1 구조(SC-xxx 기준) 위에 있다는 게 드러났다. 셸·URL 체계가 통째로 바뀌므로 기존 화면 위에 새 구조를 얹을 수 없다.
- **선택지:** (a) 기존 코드를 지우고 새로 짠다 (b) 별도 브랜치에 보관하고 develop에서는 지운다 (c) **같은 트리 안에서 `-v1` 접미사로 격리하고, 뼈대가 서면 화면을 하나씩 이식한다**.

- **근거:** 지우면(a) 실제 동작하는 v1 화면(로그인·커리큘럼·교육생 명부 등, 팀원이 이미 완성한 것)이 통째로 사라진다 — v2 뼈대가 서기 전까지 참고할 원본도, 이식할 원본도 없어진다. 별도 브랜치(b)는 두 브랜치를 오가며 대조해야 해서 실제로는 더 불편하다.

- **목적·효과:** `src/features-v1`가 점점 비어가는 것 자체가 이식 진행률이 된다. 화면을 옮기고 나면 그 폴더만 지운다.

## D17 · 역할별 셸 4개를 `ConsoleShell(role)` 하나로 — 짜고 나서 SOLID·YAGNI 위반을 발견

- **배경:** v2는 역할 4개(슈퍼어드민·오퍼레이터·매니저·교육생)마다 메뉴·스코프가 다르다(`docs/plan/v2/17-ia-menu-tree.md`). 처음엔 v1의 `ManagerShell` 패턴을 그대로 늘려 `SuperAdminShell`·`OperatorShell`·`ManagerShell`·`TraineeShell` 4개 파일을 만들었다 — 각자 공용 프레임에 자기 역할의 사이드바 배열만 주입하는 얇은 래퍼.
- **문제 제기(사용자):** "통일된 거 하려고 ConsoleShell 만든 거 아니야? 넷 다 내용만 다를 텐데 왜 뷰를 하나하나 들어가서 고쳐야 돼?" — 스코프 라벨 하나 바꾸는 데도 파일 4개를 돌아다녀야 했다.
- **판단:** 4개 파일을 지우고 `ConsoleShell`이 `role: Role` 하나를 받아 사이드바(`SIDEBAR_BY_ROLE[role]`)·스코프(`COHORT_SCOPED_ROLES.includes(role)`) 둘 다 내부에서 결정하게 합쳤다. 역할별 래퍼는 "어떤 사이드바를 넣을까"만 다른 얇은 함수였다 — 동작이 아니라 **파라미터**만 다른데 파일을 따로 둔 것.
- **근거:** 이건 개방-폐쇄나 단일 책임과 무관한, 그냥 파라미터화 누락이었다(SOLID). "역할별로 다른 컴포넌트가 필요할 수도 있으니 미리 나눠 둔다"는 근거도 없었다(YAGNI) — 넷 다 지금도 앞으로도 프레임은 완전히 같다.
- **재발 방지:** 이 세션에서 "코드 짜기 전에 기존 구조 파악 + 계획부터"를 원칙으로 명시적으로 받았다. 여러 유사 파일을 만들기 전에 "이게 진짜 행동이 다른가, 파라미터만 다른가"를 먼저 묻는다.

## D18 · 손으로 만들지 않는다 — 있는 컴포넌트·토큰부터 확인

- **배경:** `ConsoleShell`의 상단바(`Header`)를 처음 만들 때 브랜드 로고·기수 선택기·사용자 아바타를 전부 `<div>`/`<span>`/`<button>`으로 손으로 그렸다. 나브 구분선 색도 임의 클래스(`border-nav-active`)를 새로 붙였다.

## D19 · 셸 프레임 버그 2건 — 스크롤과 반응형 폭

- **배경:** `ConsoleShell` 초안이 렌더는 됐지만 실사용 조건에서 두 가지가 깨져 있었다.
- **① 고정 높이(진짜 버그):** `min-h-svh`(최소 높이)를 썼더니, 콘텐츠가 길어지면 문서 전체가 늘어나 헤더·사이드바까지 스크롤에 밀려 올라갔다. 목업은 `.app{height:var(--screen-h)}` + `.content{overflow:hidden}` — 콘텐츠 영역 **안에서만** 스크롤되는 구조다. `h-svh`(고정 높이) + `overflow-hidden`으로 바꾸고, 3000px짜리 테스트 콘텐츠를 넣어 헤더·사이드바가 고정된 채 본문만 스크롤되는 것을 스크린샷으로 확인했다.
- **② 반응형 폭(재현 환경 문제였다):** 사용자가 "헤더 width가 고정 아니냐"고 반복 지적. 코드상 `<header>`는 이미 `flex`/`w-full` 계열이라 뷰포트 폭을 따라가야 했는데, 확인해보니 **재시작 전 죽은 dev 서버 포트(5174)에 열린 탭**을 보고 있었던 것으로 드러났다 — 살아있는 포트(5173)에서는 1100~1920px 전 구간에서 헤더 폭 = 뷰포트 폭이 실측(`getBoundingClientRect`)으로 일치했다. 그래도 `<header>`에 `w-full`을 명시로 박아 애매함 자체를 없앴다.
  > ②는 코드 값이 아니라 **사용자가 실제로 보고 있는 화면을 먼저 재현**하고 나서야 원인이 갈렸다. 코드만 계속 고치는 쪽으로 갔으면 시간을 낭비했을 것이다.

## D20 · 라우팅 방식을 세 번 갈아엎었다 — 도메인 파일 → 화면 파일 겸용 → 화면별 sibling 파일

- **배경:** v1 라우팅 관례(§4, 도메인마다 `routes.tsx` 하나 + `app/routes.tsx`가 손으로 import)를 v2 화면 25개로 그대로 확장하려 했다.
- **1차 — 도메인당 `routes.tsx`.** `app/routes.tsx`가 18개 도메인을 손으로 import + spread하게 됐다. "import가 너무 많다"는 지적에 `import.meta.glob('/src/features/**/routes.tsx')`로 폴더를 훑도록 바꿔, 새 도메인 추가 시 루트 파일이 안 바뀌게 했다.
- **2차 — 화면 파일이 `route`를 겸해서 export.** "폴더마다 routes.tsx를 계속 남겨야 하냐"는 재지적에, `routes.tsx` 자체를 없애고 `{X}Screen.tsx`가 컴포넌트와 `route` export를 같이 갖게 했다. 폴더 하나에 화면이 2개면(면담 목록+브리프 등) 파일을 나눠 가져야 하는 문제는 풀렸지만, 대신 `react/only-export-components` 경고가 화면 25개 전부에서 떴다 — React Fast Refresh가 그 파일에 상태 보존 핫리로드를 못 해 준다.
- **판정 질문(사용자):** "그런 상태가 뭔데, 예를 들어줘." → 폼 입력값·70분 세션 타이머·에디터 내용처럼 개발 중 저장할 때마다 날아가는 구체 사례로 답했다. 비용이 실제로 있다는 데 동의한 뒤 분리를 결정했다.
- **3차(최종) — 화면 파일 옆에 `{X}Screen.route.tsx`를 따로 둔다.** 컴포넌트 파일은 컴포넌트만 export(Fast Refresh 정상), 라우트는 화면마다 독립된 sibling 파일(공유 파일 없음 — 충돌 재발 안 함). `app/routes.tsx`는 glob 패턴만 `*.route.tsx`로 바꿔 계속 자동 수집한다.
- **기각한 대안 — 역할 폴더 단위로 한 번 더 모으기:** "그게 성능상 낫냐"는 질문에 추측으로 답하지 않고 확인했다 — `eager: true`라 glob 단계 수와 무관하게 25개 화면이 전부 같은 번들에 정적으로 들어간다(빌드 산출물의 JS 청크가 1개인 것으로 확인). 중간 집계 파일을 두면 그 파일을 여러 화면 담당자가 같이 고쳐야 해서, 애초에 화면마다 파일을 쪼갠 이유(작업 겹침 방지)가 다시 깨진다. 성능 이득 0 + 충돌 재발이라 기각했다.
  > **파일 구조를 "성능 때문"이라는 이유로 합치기 전에, 무엇이 실제로 정적 번들되는지부터 확인한다.** `eager: true` 하나가 이 질문의 답을 완전히 바꾼다 — 확인 없이 짐작으로 구조를 결정하지 않는다.

## D21 · 셸을 목업과 토큰 단위로 대조 — `--sp-N`의 N은 Tailwind의 N이 아니다

- **배경:** 오퍼레이터 화면 착수 전에 셸을 점검하다가, `01-design-checklist.md`의 「반영 완료」 표가 `ConsoleShell.tsx`에 본문 폭 상한(`mx-auto max-w-7xl`)이 있다고 적어 뒀는데 **실제 코드에는 없었다**(`grep`로 확인). 같은 표의 `TraineeShell.tsx` 행도 존재하지 않는 파일을 가리키고 있었다. 문서의 "반영 완료"를 믿고 화면을 그리기 시작했으면 25화면이 1920에서 조용히 H8을 어겼다.
- **고친 것 3건:**

  | | 목업 | 코드(전) | 코드(후) |
  |---|---|---|---|
  | 본문 폭 상한 | `.content > *{max-width:--w-app}` 1280 | **없음** | `<div class="mx-auto max-w-7xl">` |
  | 본문 좌우 여백 | `.content{padding:--sp-6}` **32px** | `p-6` **24px** | `p-8` 32px |
  | 나브 그룹 구분선 간격 | `.nav .grp{margin-top:--sp-2}` **8px** | `mt-3 pt-3` **12px** | `mt-2 pt-2` 8px |

- **★ 근본 원인 — 목업 간격 토큰의 번호가 Tailwind 번호와 다르다.**

  | 목업 | px | Tailwind 클래스 | 같은 번호를 쓰면 |
  |---|---|---|---|
  | `--sp-1` ~ `--sp-4` | 4·8·12·16 | `1`~`4` | 일치 |
  | **`--sp-5`** | **24** | **`6`** | `p-5`는 20px — **4px 부족** |
  | **`--sp-6`** | **32** | **`8`** | `p-6`은 24px — **8px 부족** |
  | **`--sp-8`** | **48** | **`12`** | `p-8`은 32px — **16px 부족** |

  **오퍼레이터 목업 5장에서만 이 구간이 78회 쓰인다**(sp-5 52 · sp-6 14 · sp-8 12). 목업의 숫자를 그대로 Tailwind 클래스 번호로 옮기는 순간 전부 좁아진다. `p-6` 사고가 정확히 이것이었다.

- **대조해서 이상 없던 것:** `--fs-*`(12·13·14·16·20·26)와 `--r-*`(6·10·14)는 `index.css`의 `--text-*`·`--radius-*`와 **값이 전부 같다.** 타이포·라운드는 목업 이름을 그대로 믿어도 된다 — **어긋나는 축은 간격 하나뿐**이다.

- **검증:** 1920에서 목업(`zoom` 환산)과 앱을 나란히 실측 — 나브 184 / 패딩 32 / 본문 1280 / 좌우 여백 226~228 대 228로 일치. 1440·1512·1728에서도 가로 스크롤 없음.

- **혼선 하나를 같이 기록한다 — 목업은 반응형이 아니다.** `.viewport{width:1920px; zoom:.6625}`라 **창을 어떻게 놓든 항상 1920 레이아웃을 축소해 보여준다.** 실제 앱은 창 폭을 따라가므로 1550px 창에서는 좌우 여백이 43px(패딩 32 + 남는 11)이 정상이고, 목업의 226px와 다른 것이 **버그가 아니다.** 목업과 눈으로 비교할 때는 브라우저를 1920으로 맞추거나 축소해서 본다.

- **재발 방지:** 목업 값을 코드로 옮길 때는 **토큰 이름이 아니라 px 값**을 기준으로 옮긴다. 그리고 문서의 「반영 완료」류 표는 **믿지 말고 `grep`으로 확인한다** — 이 표가 실제로 틀려 있었다.

## D22 · 표 컬럼 폭 — 목업 px을 베끼지 않고 측정해서 시스템으로 만든다

- **배경:** OP-03 프로젝트 목록을 그리려고 목업 컬럼 폭(`.c-nm 112` 등)을 옮기려다, 그 값들이 **실제로는 적용조차 안 되고 있다**는 것을 렌더 실측으로 발견했다.

  | | 선언 | **실제 렌더** |
  |---|---|---|
  | `operator/projects` — 6열 **전부** 폭 지정 | 112·64·180·230·124·108 (합 818) | **175·100·281·359·194·169** |
  | `manager/trainees` — 흡수 열 1개 비움 | 150·124·92·112·(없음)·124 | **선언대로** |

  `table-layout:fixed`는 **모든 열에 폭을 주면 남는 폭을 전 열에 비례 분배한다.** 체크리스트가 이미 *"마지막 열에만 폭을 주지 않는다"* 고 적어 뒀는데 이 목업이 그것을 어겼다 — 462px가 흩어져 선언값이 전부 무의미해졌다. **이미 구현된 MG-05는 규칙을 지키고 있다.**

- **또 하나 — 같은 뜻의 열이 목업마다 다르다.** `.c-nm`(주 식별자)이 **112 / 150 / 264** 세 종류였다. 체크리스트의 *"같은 뜻의 열은 어느 표에서나 같은 폭"* 이 목업에서 안 지켜지고 있었다.

- **기존 `--col-*` 11개도 시스템이 아니었다.** 8px 격자(업계 표준 8pt grid) 위에 있는 것이 **11개 중 4개**뿐이다(`chk 40 · act 96 · period 168 · name 200`). 나머지(92·108·110·116·124·132·196)는 눈대중으로 나온 값이라 근거를 댈 수 없다.

- **판단: 목업 px을 베끼지 않는다. 실제 콘텐츠를 재서 정하고, 새 CSS 토큰은 만들지 않는다.**

  실측(앱 실제 폰트, 셀 좌우 패딩 32px 포함) → 8배수 올림:

  | 뜻 | 최장 내용 | 필요폭 | 채택 | Tailwind |
  |---|---|---|---|---|
  | 짧은 라벨 | `미프` | 56 | **56** | `w-14` |
  | 상태 배지 | `준비 중` + 점 | 90 | **96** | `w-24` |
  | 날짜 | `07-21 18:00` + `5일 남음` | 104 | **128** | `w-32` |
  | 주 식별자 | `미프 5차` + 하위설명 | 160 | **160** | `w-40` |
  | 부 식별자 | `Kubernetes 기초 v1` | 136 | **160** | `w-40` |
  | **흡수 열** | 칩 3개 / `⚠ 미확정 · 후보 8건에서 3건`(176) | — | **미지정** | — |

- **왜 새 토큰을 안 만드나:** Tailwind 폭 유틸리티가 **이미 8px 격자 시스템**이다. 우리에게 없던 것은 값이 아니라 *"어떤 뜻에 어떤 폭"* 이라는 **매핑**이고, 그것은 CSS 변수가 아니라 이 표가 담는다. 토큰을 새로 정의하면 Tailwind 스케일과 `--col-*` 두 벌을 유지하게 된다.

- **경계:** **레이아웃 수치는 우리가 정하고, 문구·상태 이름·케이스 표는 목업이 계약이다.** 00-index가 *"목업이 단일 원천"* 이라고 한 것은 **케이스 표**를 가리킨 것이지 px을 가리킨 것이 아니다. 문구는 계정 열거 방지 같은 보안 규칙이 실려 있어 바꾸면 규칙이 깨진다(D21과 같은 결).

## D23 · 여러 세션이 한 폴더를 공유해 작업이 두 번 사라졌다 — 격리로 풀고, 훅은 보조로 둔다

- **배경:** 터미널 두 개(OP-04 · OP-06)가 같은 레포 폴더에서 동시에 작업하다가, 한쪽의 git 명령이 **다른 쪽의 미커밋 파일을 두 번 날렸다.** 두 번째에는 OP-06 화면 13개가 사라졌다.

### 원인 — reflog에 그대로 남아 있다

추측이 아니라 `.git`의 기록으로 갈렸다.

```
HEAD reflog   2cf9676 → 2cf9676  22:58  reset: moving to HEAD
              2cf9676 → 2cf9676  23:17  reset: moving to HEAD
stash reflog  23:10  WIP on feature/op-03-project-list          ← untracked까지 치움(부모 3개)
.git/AUTO_MERGE  23:17                                          ← 머지하다 끊은 흔적
```

**커밋 해시가 안 움직이고(`2cf9676 → 2cf9676`) 워킹트리만 버려진 것**이 reset 계열이 돌았다는 뜻이다. 그 stash 하나에는 **두 사람 작업이 같이 들어가 있었다** — `admin/` 36개 + `projects/` 6개. 한쪽이 자기 작업을 정리하려던 명령이 남의 폴더까지 쓸어 담은 것이다.

> **reflog 문구만으로 어느 명령인지는 안 갈린다.** 임시 저장소에서 확인해 보니
> `git reset --hard`와 `git merge --abort`가 **똑같이 `reset: moving to HEAD`를 남긴다.**
> 23:17 것은 `.git/AUTO_MERGE`와 시각이 같아 머지 중단 쪽이고, 22:58 것은 그 흔적이 없다 —
> **다른 파일과 대조해야 갈린다.** 처음엔 둘 다 `reset --hard`로 단정했다가 검증에서 고쳤다.

### 왜 이런 일이 가능한가 — 세션 격리가 애초에 없다

터미널·에디터·AI 세션을 여럿 띄워도 **디렉터리 한 벌, `.git` 한 벌을 물리적으로 같이 쓴다.** git에는 "이 세션이 만든 파일"이라는 개념이 없어서, 파괴적 명령은 **경로를 안 주면 워킹트리 전체**에 걸린다.

| git이 아는 저장 지점 | 보호받나 |
|---|---|
| 커밋 | ⭕ reflog가 지킨다 |
| index(`git add`) | 🔺 `clean`엔 안 지워짐 · 되돌리기엔 날아가되 **dangling blob으로 건진다** |
| stash | ⭕ (단 버리면 끝) |
| **untracked 새 파일** | ❌ **git이 존재를 모른다** |

사라진 것은 전부 마지막 칸이었다. **새 화면을 만드는 작업은 구조적으로 가장 약한 상태로 오래 머문다** — 파일을 20개 만들 때까지 커밋할 것이 없기 때문이다.

### 조치 ① 규약 — `git-convention.md` §5

**폴더 분리(`git worktree`)를 동시 작업의 기본으로 올렸다.** 원래 §5는 worktree를 *"정말 필요하면"* 이라는 최후 수단으로 적어 뒀는데 순서가 반대다 — 금지 목록은 실수를 **줄이고**, 격리는 사고를 **불가능하게** 한다.

`.git`을 공유하므로 커밋·브랜치·stash가 한 곳에 모이고, 별도 clone과 달리 서로의 브랜치가 보인다. **이 레포는 이미 목업 작업에 worktree를 쓰고 있어서**(`git worktree list`) 새로 배울 것도 없었다.

### 조치 ② 훅 — 만들었지만 🔺로 표기했다

git에는 `pre-stash`·`pre-reset` 훅이 없다. 그래서 Claude Code의 `PreToolUse`로 명령 실행 **전에** 문자열을 검사하는 `.claude/guard-worktree.sh`를 뒀다.

**만들고 나서 실제로 돌려 봤고, 그 결과를 표에 정직하게 적었다**([[D15]] — *"규칙이 있다는 것과 규칙이 작동한다는 것은 다르다"*).

| 검증 결과 | |
|---|---|
| 의도한 7개 | **전부 차단됨** ⭕ |
| **같은 파괴력인데 통과** | stash 버리기(`drop`·`clear`) · 강제 체크아웃(`-f`) · `checkout <브랜치> -- <경로>` · `reset --merge` · `rm -rf <소스폴더>` · `git -C <경로>` 우회 |
| **우회가 쉽다** | 공백을 둘 넣거나 따옴표를 끼우면 통과 |
| **오탐** | 명령문에 **단어가 들어가기만 해도** 막는다 — 문서를 `grep`하는 것, 금지 문구를 파일에 쓰는 것이 전부 걸렸다. **이 D23을 작성하는 명령 자체가 세 번 막혀서 다른 도구로 우회해야 했다** |

특히 stash 버리기가 안 막히는 것이 아프다 — **이번 사고에서 stash가 유일한 복구처였다.**

- **미커밋 결함(발견 즉시 기록):** `settings.json`은 추적되는데 `guard-worktree.sh`는 **untracked였다.** 둘이 따라온다 — ① 가드 자신이 자기가 막으려는 `clean` 명령의 삭제 대상이다 ② settings.json만 push되면 팀원 쪽엔 스크립트가 없어 `sh`가 **127**을 반환하는데, 차단은 **2**일 때만 걸리므로 **조용히 전부 통과한다.** 훅이 있다고 믿는 상태가 훅이 없는 상태보다 위험하다.

### 결론 — 계층을 뒤집지 않는다

```
1  폴더 분리(worktree)   사고를 불가능하게 한다        ← 진짜 방어선
2  규약(§5)              사람이 판단한다
3  훅                    AI 세션의 실수를 알린다        ← 방어선이 아니다
4  백업 · git add        사고가 나도 복구된다
```

**훅을 정교하게 만들어도 "폴더를 공유한다"는 전제는 안 바뀐다.** 이번에 작업이 살아난 것도 훅이 아니라 4번이었다 — 세션 스크래치패드 백업과, stash에 36개가 남아 있었던 것.

- **연결:** `docs/handbook/git-convention.md` §5·§6 · [[D2]] 규약을 강제 수단별로 배치 · [[D15]] 검사 규칙도 코드다.

## D24 · `반 · 명단`을 두 탭으로 나눴다 — 정의서와 다르게 정한 것

- **배경:** OP-06 정의서 §3이 *"**`반`과 `명단`을 한 탭으로 합친다.** 반을 만드는 것과 명단을 넣는 것은 한 흐름인데 탭이 갈리면 계속 오간다 — 반 하나를 추가하고 바로 그 반에 사람을 넣는 것이 실제 동선이다"* 라고 정해 뒀고, 그대로 구현했다.
- **판단:** **나눈다.** `/operator/admin/classes`(반) · `/operator/admin/roster`(명단).

### 왜 — 구현이 그 근거를 먼저 깨뜨렸다

정의서의 근거는 **"같이 보인다"** 였다. 그런데 만들어 보니 두 표가 한 뷰포트에 안 들어갔다 — 반 10행 + 명단 25행. 그래서 합친 상태를 유지하려고 **반 표에 내부 스크롤**(`maxHeight="19rem"`, 6행만 보임)을 넣었다.

**그 순간 합친 이유가 사라졌다.** 6행만 보이는 표는 "같이 보이는" 것이 아니고, 명단을 보다 반을 확인하려면 위로 올라가 스크롤을 또 해야 한다. 탭을 누르는 것보다 비싸다.

| | 한 탭 | 두 탭 |
|---|---|---|
| 반 표 | **6행만**(내부 스크롤) | **10반 전부** — 스크롤 0 |
| 반 → 명단 이동 | 페이지 스크롤 | 탭 클릭 1회 |
| 명단에서 체크 하나 | 반 표까지 리렌더 | 무관 |

**정의서가 틀렸다기보다, 데이터 규모가 정의 시점의 가정을 넘었다.** 10반 250명은 정의서 자신이 정한 스코프(17번)인데, 두 표를 한 화면에 담는다는 판단은 그 수를 실제로 그려 보기 전에 내려진 것이다.

- **동선은 잃지 않는다.** 탭이 나란히 있어서 반을 만든 뒤 명단으로 가는 것은 클릭 한 번이다. 정의서가 걱정한 *"계속 오간다"* 는 **탭이 서로 먼 곳에 있을 때** 생기는 비용이고, 인접 탭에는 해당하지 않는다.
- **배정 모드의 복귀 지점을 `roster`로 바꿨다.** 배정은 명단에서 시작하는 작업이라 끝나고 반 탭으로 돌아가면 방금 한 일의 결과가 안 보인다.
- **뒤늦게 메운 것 — 반 → 명단 링크.** 목업 케이스 표는 `GET /admin/classes`가 *"반별 인원 · 담당 매니저 · **명단**"* 을 준다고 했는데, 탭을 가르면서 **반에서 그 반 명단으로 가는 길이 사라졌다**(탭을 눌러도 250명 전체가 나온다). 인원 수를 링크로 만들어 `?class=`로 좁혀 연다 — 그 수가 곧 그 명단이라 누를 것이 이미 거기 있었다.
- **부수 효과 — 조회가 하나 늘었다.** 한 탭일 때는 부모가 반 목록을 한 번 조회해 두 섹션이 같이 썼는데, 탭이 갈리면서 명단 탭도 필터 드롭다운용으로 따로 부른다. **탭을 둘 다 여는 경우에만** 늘고, 각 탭은 자기가 그릴 것만 부른다 — 화면이 독립이면 조회도 독립인 것이 맞다.
- **함께 걷어낸 것:** 반 표의 `maxHeight`. 자를 이유가 없어졌다(02-layout §6은 *진짜 길어지는* 목록에만 내부 스크롤을 준다).
- **정의서를 고치지 않았다.** 화면 정의는 기획 산출물이고 이 결정은 구현 판단이라, 근거를 여기 남기고 코드 주석이 이 항목을 가리킨다 — 정의서를 조용히 고치면 *"원래 그렇게 정했다"* 가 되어 판단한 사실이 사라진다([[D1]] 경로 갱신 원칙과 같은 결).

## D25 · 감사 값(누가·언제)을 표 열로 세우지 않고 **바꾸는 자리**에 뒀다

- **배경:** 탭별 검토 중 *"기수나 반이나 편집자·편집일자 같은 게 보여야 하지 않나"* 라는 질문이 나왔다. 확인해 보니 `_/api/types.ts`에 **감사 필드가 하나도 없었다** — `createdAt`·`updatedBy` 어느 것도 없다. 그런데 OP-06 정의서 §3·§4는 *"담당 반 배정이 **기간형 이력**이라 6기 A반 담당이 누구였는지가 그 계정에 붙어 있다"* 고 이미 요구하고 있었다. **기획이 요구한 것을 계약이 표현하지 못하는 상태**였다.
- **판단:** 필드는 더한다(`ClassRoom.assignedAt` · `assignedBy`). 다만 **모든 표에 `편집자`·`편집일자` 두 열을 붙이지는 않는다.**

### 왜 — 감사 값은 "언제나 보이는 값"이 아니라 "물을 때 보는 값"이다

탭 검토 기준 ②는 *"그 열을 지우면 이 탭의 질문에 답을 못 하나"* 로 열을 고른다. 반 탭의 질문은 **어느 반에 담당이 없나 · 정원 여유가 있나**이고, `누가 마지막에 고쳤나`는 그 질문에 답하지 않는다. 여섯 탭 전부에 두 열을 붙이면 **정작 스캔해야 하는 값이 밀려난다.**

그래서 셋으로 갈랐다.

| 값 | 어디에 | 왜 |
|---|---|---|
| **담당 시작일**(`assignedAt`) | 반 표의 열 하나 | 담당은 **기수 중간에도 바뀐다** — 목록에서 실제로 눈에 걸리는 것이 *"D반이 6월에 손이 바뀌었네"* 다 |
| **배정한 사람**(`assignedBy`) | 담당 배정 모달 | 한 칸에 값 하나(E11). 이름은 **바꾸려고 연 자리**에서 필요하다 |
| 생성자·생성일 전반 | **안 만들었다** | 기획에 없고, 지금 화면 어디도 그것으로 판단하지 않는다(YAGNI). 이력 엔드포인트가 생기면 그때 그쪽으로 |

- **`⚠ 백엔드와 확인` 을 타입에 박아 뒀다**(mock-first §4) — 기획 문서에 필드로 적힌 적이 없다. 조용히 넣지도, 조용히 빼지도 않는다.

### 같이 찾은 결함 — 모달이 담당을 **지우고 있었다**

`담당 변경`을 눌러 열면 아무것도 선택돼 있지 않았다(`useState(null)`). 그 상태로 `저장`을 누르면 `managerId = null`이 나가 **담당이 해제된다.** 바꾸러 들어온 사람이 지우게 되는 자리였고, 확인 모달도 없다.

- 현재 담당을 **처음 선택으로** 넣었다. `저장`은 `picked === current`면 눌리지 않는다 — 안 바꾼 것은 저장할 것이 없다.
- `담당 비우기`는 **담당이 있을 때만** 나온다. 이제 그 버튼을 눌러야만 해제된다.
- 모달 제목 아래에 `현재 박지현 · 2026-03-02부터 · 김오퍼레이터 배정`을 적는다 — 검토 기준 ⑩의 *"지금 값이 보이나"*.
- **매니저 쪽 문은 그대로 비워 둔다.** 한 사람이 여러 반을 맡을 수 있어(`classNames: string[]`) "지금 고른 것"이 하나로 정해지지 않는다.

- **연결:** [[D24]] 반·명단 분리 · [[D22]] 목업과 우리 것의 경계 · `scratchpad/tab-review-criteria.md` ⑨·⑩

## D26 · 명단 탭 — 헤더 수가 필터를 따라 움직이고 있었다

탭 ③ 검토에서 찾은 것 여섯. 넷은 결함이고 둘은 빠진 것이다.

### 결함 — 필터 결과를 모집단인 척 썼다

`RosterPage.total`은 **필터를 적용한 수**인데 헤더와 빈 화면이 그것을 모집단으로 썼다. 검색어가 안 걸리면 이렇게 나온다.

```
명단 0명   7기 · 미배정 3
"zzz"와 맞는 사람이 없습니다
7기 0명에서 찾았습니다.      ← 0명 중에서 찾을 수는 없다
```

**반 탭은 같은 문제를 이미 풀어 뒀다** — 헤더용 수를 `getAdminCounts`로 따로 받는다. 명단은 그 규칙을 안 따르고 있었다. `RosterPage.cohortTotal`(필터 전 기수 전체)을 더해 헤더와 빈 화면이 그것을 쓰게 했다. **푸터만 `total`을 쓴다** — 거기가 필터 결과를 말하는 자리다.

### 결함 — 직접 입력이 CSV보다 무르게 검사하고 있었다

CSV는 `parseRosterCsv`가 줄 번호와 파일 안 중복을 잡는데, 직접 입력은 `checkEmail`을 한 줄씩 돌리고 있었다. 그래서 둘을 놓쳤다.

| | 쳤을 때 | 화면이 한 말 | 사실 |
|---|---|---|---|
| 1행 비움 + 2행 오타 | | `1번째 줄 오류` | 1번째 칸은 멀쩡한 빈 칸 |
| 같은 주소 두 줄 | | `✓ 유효 2명` | 서버는 1명만 등록 |

`rules.ts`에 `checkRosterRows(rows, domain)` 하나를 두고 **빈 행을 포함한 입력칸 전체**를 받게 했다 — 번호가 칸과 맞아야 해서 거르지 않고 받는다. `npm run check:admin`에 세 줄을 더해 두 경우가 다시 생기면 잡힌다.

- **라벨도 같이 고쳤다** — `파일 안에서 중복` → `같은 주소가 두 번 있음`. 직접 입력에는 파일이 없다.

### 결함 — 취소하고 다시 열면 지난 판정이 떠 있었다

`reset()`이 **성공했을 때만** 돌았다. 특히 `이미 등록된 이메일 n명`은 **서버가 그 시점에 센 수**라, 그 사이 명단이 바뀌면 틀린 수를 보여준다. 닫는 길 하나(`close`)가 비우는 일까지 하게 묶었다 — 성공도 취소도 같은 문으로 나간다.

> 마지막에 쓴 입력 방식(CSV ↔ 직접)은 **안 비운다.** 그건 지난 판정이 아니라 취향이고, 두 번째 등록도 대개 같은 방식이다.

### 빠진 것 — `미배정`으로 좁힐 수 없었다

헤더가 `미배정 3`으로 경고하는데 **그것으로 거르는 길이 없었다.** 배정 모드에 가면 볼 수 있지만 그것은 *작업*이지 *조회*가 아니다. 같은 축(어느 반이냐)이라 필터를 새로 만들지 않고 `소속 반` 드롭다운에 값으로 넣었다 — 쿼리에서만 갈린다(`scope` ↔ `classId`).

### 빠진 것 — 정렬 키가 행에 없었다

`최근 등록순`으로 정렬해 놓고 **등록일이 어디에도 없었다**(E2 — 기수 탭의 `기간` → `시작 ~ 종료`와 같은 자리). `Trainee.registeredAt`을 더해 열로 세웠다. 중도 합류를 가려내는 값이기도 하다 — 개강일이 아닌 사람이 곧 그 사람이다.

### 안 고친 것

| | 왜 |
|---|---|
| **직전 기수 열** | 재수강생을 어느 반에 넣을지 판단하는 값인데, 그 판단은 **배정 모드**에서 한다. 거기 이미 있다 |
| **교육생 제외·삭제** | 정의서 §5 액션에 없다(`생성·초대·배정·정지`의 정지는 매니저 것) |
| **쪽당 25명** | [[D24]]로 *"반 표와 같이 담는다"* 는 근거가 사라져 실측을 다시 했다 — 1512×900에 9행이라 맞추면 **28쪽**이 되어 페이저가 목록보다 길어진다. 250은 페이지로 훑을 수가 아니라 검색·필터로 좁힐 수다. 죽은 근거를 그대로 두지 않고 주석을 고쳐 적었다 |

- **연결:** [[D25]] 감사 값은 바꾸는 자리에 · [[D24]] 반·명단 분리

## D27 · 배정 모드 — 고를 때마다 표가 밀리고 있었다

### 결함 — 선택 바가 표를 58px 아래로 밀었다

벌크바를 **표 바로 위**에 조건부로 그렸다(목업 `#bulk`). 첫 체크에 표 전체가 아래로 밀린다 — 실측 58px.

**여러 명을 연달아 고르는 화면에서 이건 오조작이다.** 첫 사람을 체크하는 순간 아래 행이 전부 한 줄 높이만큼 내려오므로, 커서를 안 옮기고 두 번째를 누르면 **조준한 사람이 아니라 그 윗사람**이 체크된다. 250명을 스무 번 나눠 넣는 화면에서 스무 번 일어난다.

**위에서 자라는 요소는 아래 있는 것을 전부 민다.** 자리를 잡는 방식이 둘로 갈렸다.

| | 어디에 | 왜 |
|---|---|---|
| **배정 모드** | 모드 **바닥 고정 바** | `h-svh flex-col`의 마지막 칸이라 줄어드는 것은 `main` 높이뿐이고 내용은 위에 붙어 있다. 커밋 액션이 늘 같은 자리에 있는 것이 반복 작업에서 이득이다 |
| **명단 탭** | 툴바와 **같은 칸에 겹침** | 셸 안이라 바닥에 붙일 자리가 없다. 자리를 늘 비워 두면(`invisible`) 표가 44px 내려가 열 번째 줄과 푸터가 접힌 아래로 넘어갔다 |

명단 탭은 둘을 같은 그리드 칸(`col/row-start-1`)에 넣어 **칸 높이를 둘 중 큰 쪽으로 고정**했다 — 실측 두 층 모두 36px, 같은 top, 이동 0px. **필터가 가려지는 것은 손해가 아니다**: 필터를 바꾸면 `narrow()`가 선택을 비우므로 고른 상태에서는 어차피 못 쓰는 컨트롤이었고, `선택 해제`가 같은 줄에 있다.

### 결함 — 버튼 이름이 사용법 문장이었다

`왼쪽에서 반을 고르세요`가 **버튼 위에** 적혀 있었다. 누를 수 있는 일이 아니라 안내다(E10). 게다가 좌 레일 머리글이 이미 같은 말을 하고 있었다(D1). 버튼은 `반에 넣기` → `A반에 넣기`로 **할 일 이름**만 두고, 안내는 레일 한 곳에 남겼다.

### 정의서와 다르게 정한 것 — 순서 강제를 뺐다

§3의 상태 표는 `① 진입(0명 선택) → 레일 **흐림** + 먼저 교육생을 고르세요`다. 즉 **교육생 → 반** 순서를 강제한다.

**반대 순서로 일하는 사람이 있다.** 모드 헤더가 스스로 `A반 채우는 중`이라고 말하는 것이 그 머릿속이다 — *"A반을 채운다"* 를 먼저 정하고 사람을 담는다. 흐림은 그 사람에게 **아무 이유 없이 막힌 벽**이다.

- 순서를 강제해서 막을 사고가 없다 — 넣기 버튼은 **둘 다 정해져야** 켜지고, 그 전까지 잘못될 수 있는 것이 없다.
- 흐림을 걷어내니 상태 하나가 사라졌다(`idle`). 레일 머리글도 `채울 반을 고르세요` 하나로 고정된다.
- C1(*못 하는 일을 흐리게 두지 않는다*)과도 이제 어긋나지 않는다. 예전 주석은 *"권한이 아니라 순서라 다르다"* 고 변호했는데, **막을 이유가 없으면 그 변호도 필요 없다.**

### 쪽당 인원 25 → 10

[[D26]]에서 25의 근거가 [[D24]]로 이미 죽어 있었음을 적었고, 여기서 실제로 바꿨다. 1512×900 실측으로 9~10행이 들어가 02-layout §6(*한 쪽이 뷰포트에 들어가는 행 수로 자른다*)에 맞는다.

> 처음엔 페이저가 36px 모자라 접힌 아래로 넘어갔는데, [[D28]]에서 이메일을 이름 밑에서 제 열로 빼면서 **행이 57px → 53px**이 되어 해결됐다 — 열 줄과 페이저가 다 들어온다(마지막 행 바닥 846px · 페이저 바닥 891px).

- **연결:** [[D26]] 명단 탭 검토 · [[D24]] 반·명단 분리

## D28 · 배정 모드 — 좌우를 뒤집고, 넣기 버튼을 반 옆으로 옮겼다

### 이메일을 이름 밑에서 제 열로 뺐다 (명단·배정 모드·앞으로 매니저도)

한 칸에 이름과 이메일을 쌓고 있었다(`이름` / 작은 글씨 `이메일`). 셋이 걸린다.

| | |
|---|---|
| **한 칸에 값 하나**(E11) | 두 값이 한 칸에 있으면 정렬·복사·훑기 어느 것도 열 단위로 안 된다 |
| **이메일로 훑을 수가 없다** | 세로로 안 맞으니 눈이 매 줄마다 이름을 건너뛰어야 한다. 계정 문제를 볼 때 실제로 훑는 것이 그 열이다 |
| **행이 두 줄이 된다** | 한 화면에 들어가는 사람이 절반이 된다 |

**부수 효과가 컸다** — 행 높이가 57px → 53px이 되면서 명단 탭의 `10행 + 페이저`가 한 뷰포트에 다 들어왔다([[D26]]의 미해결 항목이 여기서 풀렸다). 열 폭은 실측: `교육생 128 · 이메일 224`, 잘림 없음.

### 좌우를 뒤집었다 — 정의서 §3의 `좌 반 레일 · 우 명단`을 바꿨다

**일의 순서와 눈의 순서가 반대였다.** 하는 일은 `누구를(명단) → 어디에(반) → 넣기`인데 명단이 오른쪽, 반이 왼쪽이라 **오른쪽에서 고르고 왼쪽으로 되돌아왔다가** 다시 화면 바닥으로 내려가야 했다. 지금은 **왼쪽에서 오른쪽으로 한 번**에 끝난다.

LTR에서 **내용은 왼쪽, 조작 패널은 오른쪽**이 일반적인 배치이기도 하다(편집기의 인스펙터, 메일의 수신함↔작성 패널). 명단은 훑는 내용이고 반 패널은 조작이다.

### 넣기 버튼을 화면 바닥에서 반 패널 안으로

[[D27]]에서 표가 밀리는 것을 고치려고 버튼을 **모드 바닥 가로 바**로 내렸는데, 실사용 평가가 *"너무 아래라 잘 안 보인다 · 그냥 빈 것 같다"* 였다. 재보니 근거가 있다.

- 폭 1200px짜리 바에 컨트롤이 셋뿐 — **대부분이 빈 공간**이라 바 자체가 구분선처럼 읽혔다.
- 버튼이 **y=880**. 눈이 머무는 곳(표 중앙·반 목록)에서 300px 넘게 떨어져 있었다.

**버튼은 그것이 무엇에 대한 것인지 바로 옆에 있어야 한다.** `A반에 넣기`는 A반 밑에 있을 때 읽힌다. 반 패널 안, 목록 바로 아래로 옮기니 **y=508**이 됐다.

| | 전 | 후 |
|---|---|---|
| 넣기 버튼 | y=880 (바닥 가로 바) | **y=508** (반 패널 안) |
| 고른 수 · 선택 해제 | 바닥 바 | **명단 툴바** — 고른 대상이 거기 있으므로 |
| 표 밀림 | 0px | 0px (유지) |

- **반 패널을 `sticky`로 붙였다** — 명단을 훑어도 넣을 곳과 넣기가 따라온다. 반 열 개라 패널이 뷰포트보다 짧아 자체 스크롤이 필요 없다.
- **미리보기를 한 번만 그린다.** 목록 행의 `22 → 24 / 25`와 버튼 위 문구가 같은 값이었다(D1). 목록은 **고를 때 필요한 것**(지금 인원·정원)만 말하고, `22 → 24 / 25 · 1자리 남음`은 **누르기 직전 한 자리**에 둔다.
- **못 누를 때 무엇이 빠졌는지 버튼 밑에 적는다** — `왼쪽에서 교육생을 고르세요` / `넣을 반을 고르세요`. 버튼 이름에 사용법을 쓰지 않는 대신(E10) 이 줄이 그 일을 한다. 비활성 버튼만 두면 왜 안 눌리는지 알 수 없다.
- **`채울 반을 고르세요`가 안 보인다는 지적도 여기서 풀린다** — 흐린 본문 한 줄이 버튼들 위에 떠 있었다. 지금은 테두리·배경이 있는 **패널의 제목**이라 덩어리로 먼저 읽힌다.

- **연결:** [[D27]] 표 밀림 · [[D26]] 명단 탭 검토

## D29 · 배정 플로우를 도메인부터 다시 봤다 — 목업을 베낀 자리 둘, 계약이 못 하던 일 하나

*"로직이 겉핥기"* 라는 지적을 받고 명단 → 배정 모드 전체를 다시 훑었다. 화면 문제가 아니라 **도메인 문제**가 셋 나왔다.

### ① 되돌리기가 되돌리지 않았다 — 계약이 그럴 수 없었다

`undoAssign`은 **무조건 `미배정`으로** 보냈다.

```
B반 사람을 A반으로 옮김 → 되돌리기 → 미배정   ← B반이 아니다
```

계약이 원인이다. `AssignResult`가 `traineeIds`만 들고 있어서 **옮기기 전 소속이 어디에도 없었다** — 되돌릴 정보 자체가 없는데 버튼은 `되돌리기`라고 쓰여 있었다. `즉시 실행 + 되돌리기`(§3)가 확인 모달을 안 세우는 근거인데, 그 되돌리기가 데이터를 지우고 있었다.

`AssignResult.moved: MovedTrainee[]`로 바꿔 **사람마다 `fromClassId`·`fromClassName`을 들고 온다.** 되돌리기는 그 자리로 돌려놓는다. 배너도 어디서 왔는지 적는다(`옮겨온 사람 B반 → 강건우`) — 어디로 돌아가는지 모르면 되돌리기를 못 누른다.

> 이름에 조사를 붙이지 않는다. `강건우은`처럼 받침 유무를 틀리게 되고(은/는·이/가), 이름은 규칙으로 처리할 값이 아니다.

### ② 옮기면 반 인원 합이 부풀었다

`assignClass`가 **받는 반만 더하고 떠나온 반에서 빼지 않았다.** 배정 모드는 `범위=전체`로 옮기기를 지원하는데(반 통폐합, §3) 짝이 안 맞았다.

| | 전 | 후 |
|---|---|---|
| B반 사람 1명을 F반으로 | B 25 · F 23 → **합 248** | B **24** · F 23 → 합 247 |

같은 반에 다시 넣는 것은 **아무 일도 아닌 것으로** 처리한다 — 세면 인원이 부풀고 되돌릴 것도 없는 되돌리기가 남는다.

### ③ 전원 배정이 끝나면 사람을 옮길 수 없었다

`finished = scope === 'UNASSIGNED' && unassigned === 0`이 **표 전체를 완료 화면으로 대체**한다. 그런데 명단의 `반 변경`도 이 모드로 온다 — 미배정이 0인 기수에서 누르면 **`모두 반에 들어갔습니다`만 뜨고 아무것도 못 했다.** 기수 중반 이후에는 반 이동이 불가능했다는 뜻이다.

**문이 둘이고 하는 일이 다르다는 것을 화면이 몰랐다.** 이제 안다.

| | 채우기 | 옮기기 |
|---|---|---|
| 들어오는 길 | `미배정 배정하기 →` | 명단에서 고르고 `반 배정 →` · 행의 `반 변경` |
| 초기 범위 | `미배정만` | **`전체`** — 골라 온 사람이 이미 반에 있을 수 있다 |
| 완료 상태 | 미배정 0이면 끝 | **없다** — 옮기러 왔지 채우러 온 게 아니다 |

범위가 `미배정만`으로 고정이던 동안, 배정된 사람을 골라 오면 `1명 선택`이라고 써 있는데 **그 사람이 표에 없었다.**

### ④ 넣은 뒤 고른 반이 풀렸다

이 화면이 전제하는 일이 *"A반을 25명까지 채운다"* 인데(헤더도 `A반 채우는 중`) 넣을 때마다 반 선택이 초기화됐다. 스무 번 넣으면 스무 번 더 누른다. **고른 반을 남긴다** — 바꿀 때는 다른 반을 누르면 한 번에 바뀐다.

### ⑤ 목업에 있지만 뺀 열 둘

| | 왜 뺐나 |
|---|---|
| 명단 `소속 반`의 **`· 3팀`** | 팀은 **프로젝트마다 재편성되는 회차의 속성**이다(00-index `학생 → 팀`, 01-design-checklist). **매니저용 명단(MG-05)은 같은 이유로 팀 열을 이미 뺐다** — OP-06만 목업을 베껴 규칙을 어기고 있었다. 한 기수에 회차가 여럿이면 회차 이름 없는 `3팀`은 무엇도 안 가리킨다. 게다가 `반`과 한 칸에 있어 두 축이 한 값처럼 읽혔다(E11) |
| 배정 모드 **`직전 기수`** | **이 부트캠프에 재수강생이 없다**(기획 확인 2026-08-04). 열의 존재 이유 자체가 없었다 — 목업에 있다고 그대로 옮긴 자리다. 값이 있는 척하려고 목 데이터도 31명에 한 명씩 지어내고 있었다 |

`Trainee`에서 `team`·`previousCohort` 필드도 지웠다 — 화면이 안 읽는 필드를 계약에 두면 백엔드가 만들어야 할 것으로 읽힌다.

- **연결:** [[D28]] 좌우 배치 · [[D27]] 표 밀림 · [[D26]] 명단 탭

## D30 · 기획 확인 8건 (2026-08-04) — 지어내던 자리를 답으로 바꿨다

탭별 검토에서 *"기획에 없어서 화면이 정하고 있던 것"* 을 모아 한 번에 물었다. **답이 곧 규칙이고, 아래를 근거 없이 되돌리지 않는다.**

| | 물은 것 | 답 |
|---|---|---|
| ① | 중도 이탈자 | **비활성 처리 + 사유·일자** — 명단에는 남고 계정만 막힌다 |
| ② | 반 수정·삭제 | **기수 시작일이 지나면 잠근다.** 그 전에는 정원·이름 수정과 삭제 가능 |
| ③ | 담당 이력 노출 | **지금 구간만** — `assignedAt`/`assignedBy` 두 필드로 확정 |
| ④ | 기수 스위처 | **나중에** — 탭별 검토를 먼저 끝낸다 |
| ⑤ | 한 반에 매니저 여럿 | **아니다. 1반 1매니저** |
| ⑥ | 명단 오등록 수정 | **이름만.** 이메일은 계정의 신분이라 못 고친다 |
| ⑦ | 비용 `계약 예산` 출처 | **계약에 박힌 값** — 서버가 내려주고 화면은 읽기만 |
| ⑧ | 재수강생 | **없다** — `previousCohort`는 존재 이유가 없었다([[D29]]) |

### 이 답들이 코드에 남기는 것

- **`Trainee.statusNote`가 생긴다**(①). 매니저의 `정지 · 퇴사 2026-05-02`와 같은 모양이다 — MG-05가 *"초대 대기·비활성 행은 흐리게 + **사유·일자**를 쓰되 액션을 두지 않는다. 초대·정지는 **오퍼레이터 소관**"* 이라고 이미 요구하고 있었는데, 그 액션이 어느 오퍼레이터 화면에도 없었다.
- **반 편집이 날짜에 걸린다**(②). `오늘 < 기수.startAt`이면 열리고 아니면 닫힌다 — **날짜 하나로 갈려 예외가 없다.** 잠긴 뒤에도 담당 매니저 변경과 반 배정은 그대로 된다(그건 운영 중에 계속 일어나는 일이다).
- **이메일은 못 고친다**(⑥). 오타 주소는 **비활성 처리 후 재등록**이 정해진 길이다 — 초대가 이미 그 주소로 나갔으므로 주소를 바꾸면 다른 사람이 된다.
- **⑤가 `needsManager`의 전제를 확정한다.** `managerId === null` 하나로 판정하는 것이 맞다([[D26]] rules.ts).

> ④는 **미룬 것이지 아닌 것이 아니다.** `_/cohortScope.ts`의 `COHORT_ID = '7'` 상수가 그 자리를 표시하고 있다.

- **연결:** [[D29]] 배정 플로우 · [[D25]] 감사 값

## D31 · D30의 답 셋을 구현했다 (①·②·⑥)

### ① 중도 이탈 — 비활성 처리

`Trainee.statusNote` + `setTraineeStatus(id, status, reason)`. 매니저의 `정지 · 퇴사 2026-05-02`와 같은 모양이다.

- **사유가 필수다.** 없으면 저장이 안 되고 서버도 같은 규칙을 검증한다 — MG-05가 *"사유·일자를 쓴다"* 고 요구하는데 사유를 안 받으면 매니저 화면에 쓸 것이 없다.
- **일자는 서버가 찍는다.** 화면이 만들면 사용자 시계에 따라 달라진다.
- **사유를 목록으로 만들지 않았다.** 기획에 이탈 사유 분류가 없다(mock-first §5). 정해지면 그때 드롭다운이 된다.
- **상태가 다르면 버튼이 다르다**(C1) — 비활성 행에는 `반 변경`이 사라지고 `다시 활성`만 남는다. 되살리면 사유는 지운다(지난 기록은 지금 상태가 아니다).

> ⚠ **선택지 설명에 쓴 것을 하나 정정한다.** 물을 때 *"반 인원에서 빠진다"* 고 적었는데 **틀렸다.** MG-05 헤더가 `25명 · 활성 23 · 초대 대기 1 · 비활성 1`이라 **비활성이 반 인원 안에 세어져 있다** — 반에서 빼면 담당 매니저가 그만둔 학생을 아예 못 본다. **반을 유지하는 쪽으로 구현했다.**

### ② 반 수정·삭제 — 개강 전에만

`rules.canEditClasses(cohortStartAt, today)` **한 줄이 전부다.** 날짜 하나로 갈려 예외가 없고, `npm run check:admin`이 경계 셋을 지킨다(전날 열림 · **당일 잠김** · 이후 잠김).

- 반 탭이 `getCohort(COHORT_ID)`로 시작일을 받는다. 목록을 통째로 받아 찾지 않는다.
- **잠긴 뒤에도 담당 변경은 남는다** — 매니저 퇴사·교체는 운영 중에 계속 일어나는 일이라 잠금 규칙이 다르다.
- **왜 버튼이 없는지 헤더 한 줄이 답한다**(`· 개강 후에는 반 구성을 바꿀 수 없습니다`). 버튼을 흐리게 두지 않으니(C1) 그 자리를 설명이 대신한다 — 안 그러면 *"고치는 데가 어디지"* 를 찾아 헤맨다.
- **이름을 바꾸면 명단의 `소속 반`도 같이 바뀐다**(D1 — 한 사실은 한 곳에서).
- **삭제하면 그 반 사람들은 미배정으로 돌아간다.** 명단에서 지우는 것이 아니다 — 실측: F반 22명 삭제 → 미배정 3 → **25**, 명단 250명 그대로.

### ⑥ 이름 수정 — 이메일은 못 고친다

모달에 **입력칸이 하나뿐이고**(실측 확인) 이메일은 읽기로만 보여준다. 고칠 수 있는 것처럼 보이면 안 되지만, 무엇을 고치는 중인지 알려면 화면에 있어야 한다.

> 오타 주소의 정해진 길은 **비활성 처리 후 재등록**이다 — ①이 없었으면 ⑥의 답이 성립하지 않는다. 두 답이 짝이다.

### 검증에서 얻은 것

- **`browser_navigate`는 전체 새로고침이라 목 상태가 초기화된다.** 삭제 결과를 다른 탭에서 확인하려다 값이 되돌아가 잠깐 헷갈렸다 — **탭 클릭(클라이언트 이동)으로 확인해야** 같은 세션이다.
- 목의 모든 기수가 이미 시작해서 **개강 전 상태에 닿을 수 없었다.** `MOCK_NOW`를 잠깐 `2026-02-20`으로 돌려 열린 상태를 확인하고 되돌렸다 — 데이터를 지어내 UI를 억지로 띄우지 않는다.
- ⚠ **행 액션이 셋이 됐다**(반 변경 · 이름 수정 · 비활성). 매니저 탭은 더 많다 — **넘침 메뉴로 접을지는 거기서 정한다.** `DropdownMenu`가 디자인 시스템에 있는데 레포에서 아직 아무도 안 쓰므로, 첫 사용처는 액션이 가장 많은 자리에서 고르는 것이 맞다.

## D32 · 표에서 두 줄 쌓기를 걷어내고 `비고` 열로 (+ 정지가 반을 안 놓던 버그)

### 규칙 — **한 칸에 두 줄을 쌓지 않는다. 값이 더 있으면 열을 만든다**

`이름`/작은 글씨 `이메일`, `상태 배지`/작은 글씨 `사유·일자`처럼 쌓아 두고 있었다. 셋이 걸린다.

| | |
|---|---|
| **행 높이가 갈린다** | 값이 있는 행만 두 줄이 되어 표가 들쭉날쭉했다 — 매니저 탭 실측 **57 ↔ 60px** |
| **그 값으로 훑을 수가 없다** | 세로로 안 맞으니 눈이 매 줄마다 위 줄을 건너뛰어야 한다 |
| **한 칸에 값 하나**(E11) | 정렬·복사·잘림 처리가 열 단위로 안 걸린다 |

명단·매니저 둘 다 **이메일 열**과 **비고 열**로 갈랐다. 비고는 대부분 비지만 — **드문 값이야말로 제자리가 있어야 눈에 걸린다.**

> **버튼이 없는 행도 같은 높이여야 한다.** 액션을 지우고 나니 그 행만 43px이 됐다(다른 행 53px). 높이를 버튼이 아니라 **칸이** 정하게 `h-[30px]` 상자를 뒀다 — 두 탭 모두 실측 53px 균일.

### 명단에서 걷어낸 것

| | 왜 |
|---|---|
| **행마다 `반 변경`** | 반 이동은 여러 명을 한 번에 하는 일이라 벌크바의 `반 배정 →`이 맡는다 — 행마다 두면 250행에 버튼이 250개 생기고 정작 훑을 값이 밀린다 |
| **`이름 수정`** | 필요 없다는 판단(D30-⑥ 철회). `updateTraineeName`과 모달 파일까지 지웠다 — 화면이 안 쓰는 API를 계약에 두면 백엔드가 만들어야 할 것으로 읽는다 |
| **`다시 활성`** | **비활성은 되돌리지 않는다**(기획 확인). `setTraineeStatus(id, status, reason)`를 **`deactivateTrainee(id, reason)`** 으로 좁혔다 — 되돌릴 수 없으면 인자로도 그것을 표현하지 않는다. 모달 문구도 *"되돌릴 수 있습니다"* → **"다시 활성으로 되돌릴 수 없습니다"** 로 바꿨다(빨간 글씨) |
| `미배정 배정하기 →` | → **`반 배정하기 →`** |

### 매니저 탭 — 정지가 담당 반을 놓지 않고 있었다

**확인 모달은 *"담당 반에서 빠집니다"* 라고 약속하는데 코드는 상태만 바꿨다.** 실측으로 재현했다.

```
박지현(7기 A반) 정지 →  매니저 행: 7기 · A반 · 담당 인원 25  (그대로)
                      반 탭:   A반 · 박지현              (그대로)
                      담당 없음 경고: 1                  (안 늘어남)
```

**퇴사한 사람이 반을 붙들고 있는데 아무 데도 신호가 없다.** `담당 없음` 경고와 OP-01 `조치 필요`가 막으려던 바로 그 상황(*"그 반 학생의 면담·독촉을 아무도 처리하지 않는다"*)을 **정지 기능이 만들고 있었다.**

- `releaseClasses(managerId)`를 두고 **정지·초대 취소가 같이 쓴다.** 고친 뒤 실측: `담당 없음 1 → 2`, A반 액션이 `담당 변경 → 담당 배정`.
- **초대 취소도 같은 병이었다.** 초대할 때 반을 맡길 수 있는데(선택) 계정만 지워서 **반에 없는 사람의 id가 남았다.**
- **초대 대기 매니저가 반을 맡으면 한 행이 서로 다른 말을 했다.** `managerName`이 null이라 화면은 빨간 `담당 없음`을 띄우는데 `needsManager`는 id가 있어 false다(D1). 이름이 생길 때까지 **주소가 그 자리를 대신한다.**
- **확인 문구가 이제 사실과 맞는다** — 어느 반이 비는지 이름을 대고(`A반이(가) 담당 없음이 됩니다`), *"다시 활성화해도 담당 반은 자동으로 돌아오지 않습니다"* 를 적는다. 그 사이 다른 사람이 맡았을 수 있어 되돌리는 것은 배정이지 상태가 아니다.

- **연결:** [[D31]] D30 구현 · [[D29]] 이메일 열 분리 · [[D26]] 명단 탭

## D33 · 매니저 탭 — 순서를 아무도 정하지 않고 있었다

표 구조와 정지 버그는 [[D32]]에서 고쳤고, 남은 축(필터·정렬·뷰포트·모달)을 봤다.

### ① 정렬이 정의된 적이 없다

`listManagers`가 **걸러낸 배열을 그대로** 돌려주고 있었다. 지금 순서가 그럴듯해 보이는 것은 목 배열에 적힌 차례가 우연히 `활성 → 초대 대기 → 정지`였기 때문이고, **실제 서버로 바꾸면 순서가 달라진다.** 초대한 사람이 목록 맨 끝에 붙는 것도 같은 이유였다(`MANAGERS.push`).

**이름순으로 고정했다.** 정렬 옵션은 두지 않는다 — 사람을 찾는 목록이라 이름순이 유일하게 자연스럽다(반 목록을 `A반 · B반 …`으로 고정한 것과 같은 판단). 가입 전이라 이름이 없으면 이메일로 줄 세운다.

> api-boundary §1-② — 정렬은 서버의 자리다. 목이 배열이라 "안 정해도 도는" 상태였고, 그래서 **빠졌다는 것 자체가 안 보였다.**

### ② `담당 없는 반` 경고가 기수를 안 가렸다

`CLASSES.filter(needsManager)` — 기관 전체 반을 훑는다. 지난 기수의 반이 섞이면 **이미 끝난 기수에 담당을 붙이라는 경고**가 뜬다. 조치할 수 없는 신호다.

**진행 중인 기수(`Cohort.current`) 것만** 센다. 매니저 필터(`q.cohortId`)를 쓰지 않은 이유가 있다 — 그것으로 세면 8기로 걸러 보는 동안 7기 경고가 사라진다. 헤더 수가 필터와 무관해야 하는 것과 같은 규칙이다.

> 목에 7기 반만 있어서 화면에는 안 드러났다. **데이터가 한 벌뿐이라 안 보이던 결함**이다.

### ③ 초대 모달이 취소 후 값을 남겼다

명단 추가 모달과 **같은 결함**이었다([[D26]]-③). 주소를 치다 취소하고 다시 열면 그 값이 그대로 있어서, 오타를 고치려고 닫은 사람이 같은 오타를 다시 보낸다. 닫는 길 하나(`close`)가 비우는 일까지 하게 묶었다.

> 같은 결함이 두 모달에 있었다는 것은 **모달을 하나씩 검토해야 한다**는 뜻이다. 한 곳을 고쳤다고 같은 종류가 사라지지 않는다.

### ④ 뷰포트 — 고치려다 근거가 틀린 것을 확인했다

표 푸터가 접힌 아래로 **17px** 넘친다(페이저 바닥 917 · 뷰포트 900). 원인이 경고 두 줄(65px)이라 보고 설명을 한 문장으로 줄였다.

**높이가 65px 그대로였다.** 제목 한 줄 + 설명 한 줄이라 애초에 두 줄이었고, 문장을 빼도 줄 수가 안 줄었다. **문장 수가 아니라 줄 수가 높이를 정한다.**

뺐던 문장을 되돌렸다 — 두 화면이 같은 사실을 가리킨다는 것은 적어 둘 값이 있고(D1), 줄이려던 목적도 달성 못 했으니 남길 이유만 남았다.

**넘침은 그대로 두기로 했다.** 표는 마지막 행까지 다 보이고(바닥 872 < 900), 넘치는 것은 페이저 줄뿐이다. 이 화면의 페이저는 페이지가 하나라 `1`만 그려지는 장식이고(E7), 셸이 `overflow-auto`라 데이터가 잘려 사라지지도 않는다. 없애려면 경고를 빼거나 행을 줄여야 하는데 **둘 다 더 나쁘다.**

### 안 고친 것

| | 왜 |
|---|---|
| **`담당 없음` 매니저 필터** | 9행에 필터가 이미 셋이다(검토 기준 ④ — 10행짜리에 필터 셋은 과하다). 반을 안 맡은 사람은 `담당 반` 열에 `미배정`으로 이미 보인다 |
| **페이지 나눔** | 기관당 매니저가 반 수(6~10)를 크게 넘지 않는다. 넘으면 명단과 같은 모양(`page`·`size`)을 더한다 |

- **연결:** [[D32]] 매니저 표 구조·정지 버그 · [[D26]] 명단 탭

## D34 · 매니저 배정 — 라디오로 골랐는데 추가되고 있었다

[[D33]] 뒤에 남은 축(배정 모델·데이터 연관성)을 봤다. **화면 문제가 아니라 모델 문제**가 셋 나왔다.

### ① 컨트롤 모양과 동작이 반대였다

한 모달이 두 방향을 다 처리했다 — 반 쪽은 `이 반을 누가`, 매니저 쪽은 `이 사람이 어느 반을`. **둘 다 라디오였고 저장도 `setClassManager` 하나였다.** 그런데 그 함수는 *반 하나에 담당 하나*를 쓰므로, 매니저 쪽에서 부르면 기존 담당은 그대로 두고 하나가 더 붙는다.

```
이도윤 7기 · B반, D반 (50명)  →  라디오로 F반 하나 선택  →  B반, D반, F반 (72명)
```

라디오는 **"이것 하나로 정한다"**는 약속이다(E10). 관계가 1:N인데 1:1 컨트롤을 쓴 것이다.

| | 관계 | 컨트롤 | 저장 |
|---|---|---|---|
| 반 쪽 | **1:1** — 한 반에 매니저 하나(D30-⑤) | 라디오 | `setClassManager(classId, managerId)` |
| 매니저 쪽 | **1:N** — `classNames: string[]` | **체크박스** | **`setManagerClasses(managerId, classIds[])`** |

`setManagerClasses`는 **PUT**이다 — 넘긴 목록이 곧 결과다. 그래야 체크를 풀어 담당을 뺄 수 있다(매니저 쪽에서 반을 빼는 길이 **아예 없었다**). 여러 번 나눠 부르면 중간에 실패했을 때 절반만 반영된다.

> **본인이 맡은 반에도 `교체됩니다`가 떴다.** `warn={!needsManager(room)}`이 담당 유무만 보고 *그 담당이 본인인지*를 안 가렸다 — 자기를 자기로 교체한다는 말이었다.

실측: `B반, D반` → D반 체크 해제 + F반 체크 → **`B반, F반`(47명)**, 빠진 D반이 곧바로 `담당 없음` 경고에 잡힘.

### ② 계약이 기수 하나만 표현할 수 있었다

```ts
assignment: { cohortName: string; classNames: string[] } | null   // 기수가 하나뿐
```

배정이 **기간형 이력**이라(정의서 §3) 한 사람이 `6기 A반` + `7기 B반`을 동시에 갖는다. 목에 6기를 가진 사람이 정지 하나뿐이라 화면에 안 드러났을 뿐이다. `assignments: ManagerAssignment[]`로 바꿨다.

`null`을 없앤 이유 — 없음과 빈 목록이 같은 사실이라 두 표현을 두면 화면이 둘 다 검사해야 한다.

### ③ 가입 전 매니저가 반을 맡을 수 있었다 (기획 확인)

초대 모달이 담당 반을 같이 받았다. **가입 전에는 로그인을 못 해 그 반의 면담·독촉을 처리할 수 없는데**, 반에는 담당 id가 박혀 `담당 없음` 경고에 안 잡힌다 — 경고가 막으려던 상황(아무도 안 보는 반)을 **초대 기능이 만들고 있었다.**

**기획 답: 가입이 끝난 매니저만 배정 가능.** `InviteManagerRequest`에서 `classId`를 빼고 모달의 칸도 들어냈다. 없는 칸은 눈에 안 띄므로 **왜 없는지를 폼 안에서 밝힌다**(권한 칸을 설명한 것과 같은 이유).

부수 효과 — 초대 취소 확인 문구에서 반 이야기가 사라졌다. 맡겨 둔 반이 있을 수 없어졌기 때문이다.

### ④ 표 — 기수와 담당 반을 갈랐다 (→ **D35에서 되돌림**)

`7기 · B반, D반`이 한 칸에 있어서 `기수` · `담당 반` 두 열로 나눴다. **이 판단이 틀렸다** — 겸임에서 짝이 깨진다. 근거와 대안은 [[D35]].

### ⑤ 액션 — 활성 안에서 갈리지 않았다

담당이 있는 사람과 없는 사람이 같은 `반 배정`을 봤다. 반 탭이 `담당 배정`/`담당 변경`으로 가르는 것과 같은 규칙을 적용했다.

| 상태 | 액션 |
|---|---|
| 활성 · 담당 없음 | **반 배정** · 정지 |
| 활성 · 담당 있음 | **담당 변경** · 정지 |
| 초대 대기 | 재발송 · 취소 (배정 버튼 없음 — ③) |
| 정지 | 재활성 |

### ⑥ 초대 시각·초대자를 더했다

초대 대기 행은 최근 접속도 담당 반도 비어서 **볼 것이 아무것도 없었다.** `재발송`을 눌러야 할지 판단할 근거가 없다 — 어제 보낸 건지 3주 전 건지 모른다. `invitedAt`·`invitedBy`를 더해 `비고` 열에 `2026-07-24 초대 · 김오퍼레이터`로 쓴다. 반의 `assignedAt`/`assignedBy`(D25)와 같은 모양이다.

### ⑦ 정렬 — 둘만 둔다

정의서가 이 탭을 *"초대 · 반 배정 · 정지"*로 정의한다. 거기서 나오는 순서는 둘뿐이다.

| 옵션 | 근거 |
|---|---|
| **이름순**(기본) | 사람을 찾는 목록의 자연 순서 |
| **담당 인원순** | 한 사람에게 몰리는 것이 조치 대상. `headcount`가 이미 계약에 있고, 배정 모달도 같은 이유로 각자의 담당을 보여준다 |

**안 만든 것** — 최근 접속순(보이지만 할 조치가 없다), 상태순(*무엇이 급한가*를 화면이 정하는 셈이라 E8. 상태 필터가 이미 그 일을 한다).

### 남은 것 — 헤더 기수 스위처

화면에 기수 컨트롤이 **둘**이다. 헤더의 `기수 7기`(전역, 그런데 `COHORT_ID='7'` 상수라 아무 일도 안 한다)와 툴바의 `기수 · 전체`(진짜 필터)가 **서로 다른 말을 한다**.

정의서 §3이 *"반·명단·비용은 선택 기수, 매니저와 교안은 기관 전체"*라 해서 **6탭 중 3탭에만** 의미가 있다. 고치는 방법은 **범위가 있는 탭에서만 렌더**하는 것이고, 탭 레지스트리(`adminTabs.ts`)에 `scoped` 한 칸을 더하면 헤더가 화면을 몰라도 된다.

**이번 변경에 넣지 않았다** — `shells/`는 매니저·교육생 화면도 쓰므로 다른 사람 작업에 영향이 간다. 별도 PR로 간다.

- **연결:** [[D33]] 매니저 탭 검토 · [[D32]] 표 구조 · [[D30]] 기획 확인

## D35 · 겸임을 표에 어떻게 보여주나 — 쪼개면 짝이 깨지는 값

[[D34]]-④에서 `7기 · B반, D반` 한 칸을 `기수` · `담당 반` 두 열로 갈랐다. **그 판단이 틀렸다.**

### 무엇이 깨졌나

한 매니저에게 8기 겸임을 넣고 렌더해 봤다.

```
기수:     7기 · 8기
담당 반:  E반, G반, A반      ← A반이 8기 것인 줄 알 수 없다
```

**쪼개는 순간 관계가 사라졌다.** `담당`은 `(기수, 반들)`의 목록이지 서로 독립인 두 값이 아니다 — 이름과 이메일을 가른 것([[D32]])과 **종류가 다르다.** 저쪽은 쪼개도 각자 온전하고, 이쪽은 쪼개면 짝이 없어진다.

> **E11(한 칸에 값 하나)을 잘못 적용했다.** 여기서 "값 하나"는 `담당` 전체다. 규칙이 막으려는 것은 *무관한 두 값을 겹쳐 쓰는 것*이지 *구조를 가진 값 하나를 온전히 쓰는 것*이 아니다.

### 네 방법을 놓고 골랐다

| | 방법 | 짝 유지 | 한 줄 | 표에서 보임 | 정렬·선택 |
|---|---|---|---|---|---|
| A | 두 열로 분리 (D34) | ❌ | ⭕ | ⭕ | 기수만 |
| B | **한 열에 기수 라벨 + 반** | ⭕ | ⭕ | ⭕ | ⭕ |
| C | 기수마다 행을 나눔 | ⭕ | ⭕ | ⭕ | ❌ **행이 매니저가 아니게 된다** — 목록의 단위가 무너지고 선택·정렬이 깨진다 |
| D | 개수(`3개 반`)만 + 상세는 모달 | ⭕ | ⭕ | ❌ **표에서 누가 어느 반인지 못 본다** — 이 목록의 질문이 그것이다 |

**B를 골랐다.**

```
담당
7기 E반·G반   8기 A반
```

- **기수는 흐리게, 반은 진하게** — 묶음 하나가 눈에 한 덩어리로 들어와야 `8기 A반`이 따로 읽힌다
- **묶음 사이 12px**(실측) — 쉼표로 잇는 것보다 경계가 분명하다
- **한 줄 유지**(`whitespace-nowrap` + `truncate`) — 행 높이가 안 흔들린다([[D32]]에서 세운 규칙)
- 넘치면 자른다. **전체는 `담당 변경` 모달에 있고 합계는 옆 칸(`담당 인원`)에 있다** — 표에서 잘려도 답을 얻을 길이 둘 남는다

열이 하나 줄어 9열 → 8열이 됐고, `담당` 폭이 224px로 늘었다(실측 — 겸임 2묶음이 안 잘린다).

### 기수 필터와의 짝은 유지된다

두 열로 나눈 이유 중 하나가 *"툴바 기수 필터와 짝이 맞는다"*였는데, **합쳐도 값 안에 기수가 보이므로** 그 설명은 그대로다.

- **연결:** [[D34]] 매니저 배정 모델 · [[D32]] 한 칸에 두 줄 금지

## D36 · 담당이 역대 누적되고 있었다 — 목록은 "지금", 이력은 "수"

[[D35]]에서 겸임을 한 칸에 묶었다. 그다음 질문이 나왔다 — **5·6·7기를 연달아 맡은 사람은?**

### 재현

종료된 6기 반 하나를 이도윤에게 붙이고 목록을 갱신했다.

```
담당:      7기 B반·D반  6기 A반      ← 기수마다 묶음이 늘어난다
담당 인원:  73                      ← 7기 50 + 6기 23
```

**지금 50명을 보는 사람이 73명으로 표시된다.** 그리고 묶음은 기수를 맡을 때마다 늘어난다 — 10기수를 맡으면 열 묶음이다.

> 더 나쁜 것은 **정렬의 근거가 무너진다**는 점이다. [[D34]]-⑦에서 `담당 인원순`을 넣은 이유가 *"한 사람에게 몰리는 것이 조치 대상"* 이었는데, 역대 누적으로 정렬하면 **부하가 아니라 근속**을 재게 된다.

### 이 목록이 답하는 것은 "지금"이다

정의서가 매니저 탭을 *"초대 · 반 배정 · 정지"* 로 정의한다 — **전부 지금 할 수 있는 조치**다. 끝난 기수의 담당은 조치 대상이 아니다.

| 값 | 범위 |
|---|---|
| `assignments` | **진행 중인 기수(RUNNING)의 담당만** ← [[D37]]에서 *조회 범위*로 다시 잡음 |
| `headcount` | 그 반들의 인원 합 |
| **`pastCohorts`** | 끝난 기수 중 담당했던 **기수 수**(이름이 아니라 수) |

**끝이 생긴다.** 진행 중인 기수는 1~2개(기수 전환기에만 2개)라 묶음이 그 수를 못 넘는다.

```
7기 B반·D반                 (지난 기수 없음)
미배정  지난 1기수            (지금은 안 맡음 · 기록은 있음)
```

**이름을 다 늘어놓지 않으면서 "이 계정에 기록이 있다"는 신호는 남긴다** — 퇴사자를 지우지 않고 정지로 남기는 이유(OP-06 §3)가 화면에도 보여야 한다.

### 같이 나온 것 — 정지가 지난 기수 기록을 지우고 있었다

[[D32]]에서 만든 `releaseClasses`가 **그 사람의 반을 전부** 풀었다. 끝난 기수 반까지 풀리므로 **정지 한 번에 `6기 A반 담당이 누구였나`가 사라진다** — 정의서가 지우지 말라고 한 바로 그 기록이다.

**진행 중인 기수만 푼다.** 실측으로 확인했다 — 최상현을 재활성했다가 다시 정지해도 `지난 1기수`가 살아 있다.

### 목 데이터도 원천을 하나로 맞췄다

최상현의 6기 담당이 `MANAGERS`에 손으로 적혀 있었다. **6기 반 둘을 `CLASSES`에 넣고 거기서 파생되게** 했다 — 목 파일 자신의 규칙(*"반 정의에서 채운다"*)이고, 그래야 위의 "정지가 이력을 지우는가"를 화면으로 확인할 수 있다. 6기는 `CLOSED`라 반 탭·담당 없음 경고 어디에도 안 나온다.

- **연결:** [[D35]] 겸임 표시 · [[D34]] 배정 모델 · [[D32]] 정지 시 담당 해제

## D37 · 기수 필터를 걸면 그 기수를 볼 수 있어야 한다

[[D36]]에서 `assignments`를 **진행 중인 기수만** 담게 잘랐다. 그러자 기수 필터가 죽었다.

```
기수 · 6기로 걸러 봄  →  결과 0명
```

6기를 맡았던 사람이 셋인데 목록이 비었다. **필터가 고를 수 있는 값을 데이터가 안 갖고 있었다** — 저장 단계에서 미리 잘라 버렸기 때문이다.

### 자르는 자리를 옮겼다 — 저장이 아니라 조회

| | 갖고 있는 것 | 자르는 곳 |
|---|---|---|
| 전 | 진행 중 기수만 | **저장**(`syncManagerAssignments`) |
| 후 | **모든 기수** | **조회**(`listManagers`) — 질의에 맞춰 |

실제 서버가 하는 일과 같다. 저장소는 사실을 다 갖고, 조회가 *지금 보고 있는 것*에 맞춰 좁힌다.

```
기수 필터 없음 → 진행 중 기수 담당 + 나머지는 `지난 N기수` 수로
기수 필터 있음 → 그 기수 담당 (끝난 기수여도 그대로)
```

**`headcount`도 같은 범위로 센다.** 담당과 인원이 다른 범위를 말하면 행이 거짓말을 한다.

실측 — 5·6·7기를 연달아 맡은 이도윤 한 행이 범위마다 이렇게 바뀐다.

| 보는 범위 | 담당 | 담당 인원 |
|---|---|---|
| 전체 | `7기 B반·D반` + `지난 2기수` | 50 |
| 6기 | `6기 C반` | 25 |
| 5기 | `5기 A반` | 25 |

`pastCohorts`는 **필터를 걸면 0**이다 — 그때는 그 기수가 곧 답이라 나머지를 셀 이유가 없다.

### 목 데이터를 제대로 만들었다

이 결함이 안 보였던 이유는 **끝난 기수 데이터가 거의 없어서**였다. 5기를 더하고 지난 기수 반 여섯을 넣어, 연차가 다른 매니저가 실제로 생기게 했다.

| 매니저 | 담당 이력 |
|---|---|
| 이도윤 | 5 · 6 · 7기 (3기수) |
| 박지현 · 최유진 | 2기수 |
| 최상현(퇴사) | 6기만 — 지금 담당 없음 |

**그리고 손으로 적던 것을 없앴다.** `assignments`·`headcount`·`pastCohorts` 셋 다 반(`CLASSES`)에서 나오는 값이라 손으로 적으면 반을 고칠 때 어긋난다. 목록에는 빈 값으로 두고 첫 조회 때 한 번 파생시킨다 — 이 파일의 규칙(*"반 정의에서 채운다"*)을 매니저에도 적용한 것이다.

> 이 규칙을 안 지켰던 탓에 [[D36]]까지 **손으로 적은 값과 반 데이터가 어긋난 채**였고, 목록을 갱신해야만 진짜 값이 보였다.

- **연결:** [[D36]] 역대 누적 · [[D35]] 겸임 표시 · [[D34]] 배정 모델


## D38 · 매니저도 기수에 붙인다 — 한 표가 두 일을 하려다 꼬였던 것

### 무엇이 꼬였나

매니저 탭이 **두 가지 일**을 한 표로 하고 있었다.

| 일 | 질문 | 대상 | 기수와의 관계 |
|---|---|---|---|
| **계정 관리** | 이 계정이 정상인가 | 초대 대기·정지 포함 전원 | 무관 |
| **담당 배정** | 이 기수 반을 누가 맡나 | 그 기수 담당자 | 기수마다 답이 다르다 |

둘이 **대상도 시간축도 달라서**, 기수 필터를 걸 때마다 계정 관리 대상이 사라졌다 — 실측으로 7기를 고르면 9명 중 7명만 남고 **초대 대기·정지가 증발**했다. [[D35]]~[[D37]]에서 겸임 표시·역대 누적·필터 범위를 연달아 고친 것이 전부 이 꼬임의 증상이었다.

### 판단 — 반이 기수에 붙듯 매니저도 붙인다

정의서 §3은 *"매니저는 기수를 옮겨 다니므로 기관 전체"* 라 했다. **그 전제를 바꾼다**(기획 결정).

**소속을 담당 반이 아니라 `cohortIds`로 잡는 것**이 핵심이다. 담당으로 판정하면 초대 대기(아직 반 없음)·정지(퇴사)가 어느 기수에도 안 잡힌다.

```
소속 = 담당 반이 있는 기수 ∪ 초대받은 기수
```

초대가 **기수를 받는다**(`InviteManagerRequest.cohortId`). 반은 여전히 안 받는다 — 가입 전엔 로그인을 못 해 반을 볼 수 없다는 규칙([[D34]]-③)은 그대로고, **기수는 반이 아니므로** 정할 수 있다.

### 이걸로 같이 풀린 것

| | |
|---|---|
| **기수 컨트롤이 둘이던 것** | 툴바 필터를 없앴다. 상단 스위처가 그 일을 한다 — 둘이 서로 다른 값을 가리키고 있었다(헤더 7기 / 툴바 전체) |
| **겸임 표시**([[D35]]) | 한 기수만 보므로 묶음이 하나다. 표시 방식은 그대로 두었다 — 기수 전환기에 둘이 될 수 있다 |
| **역대 누적**([[D36]]) | 범위가 곧 기수라 인원이 그 기수 것이다 |
| **헤더 수와 목록 불일치** | `counts`도 기수 범위에서 센다. 기수는 필터가 아니라 **화면의 범위**다 |

### 기수 상태가 액션을 정한다 (`rules.assignPolicy`)

| 기수 | 담당 변경 | 왜 |
|---|---|---|
| **시작 전** | 그냥 됨 | 아직 아무 일도 안 일어났다(반 편집이 열리는 것과 같은 시점 — [[D30]]-②) |
| **진행 중** | **확인 후** | 되돌릴 수 있지만 **학생이 이미 그 사람을 보고 있다** |
| **종료** | **불가** | 이력이다. 액션을 안 그리고 *무엇을 보고 있는지*를 배너로 알린다 |

`canEditClasses`(반 편집)와 **일부러 다른 함수**다. 반은 개강 후 못 고치지만 담당 변경은 운영 중에도 일어난다(매니저 퇴사·교체) — 같은 함수로 묶으면 그 차이가 사라진다. `check:admin`이 경계 넷을 지킨다.

### 사고 — 작업 트리 되돌리기 명령으로 커밋 안 된 작업을 날렸다

편집 하나를 되돌리려고 파일 하나에 되돌리기 명령을 썼다가 **그 파일의 D33~D37 작업이 전부 사라졌다**(마지막 커밋 상태로 되돌아감). 백업이 없었다.

- **가드 훅이 못 막았다.** 훅은 `--` 형태와 `.` 형태를 잡는데 **경로를 바로 주는 형태가 패턴에 빠져 있었다.** 훅을 고칠 것.
- **피해가 한 파일에 그친 이유** — 계약·API·목·모달은 다른 파일이라 무사했고, decision-log에 변경 근거가 절마다 적혀 있어 복구가 기계적이었다. **기록이 백업 노릇을 했다.**
- 근본 원인은 **커밋을 안 하고 오래 끌었던 것**이다. D32~D37이 전부 미커밋이었다.

- **연결:** [[D37]] 조회 범위 · [[D34]] 배정 모델 · [[D30]]-② 반 편집 잠금


## D39 · 비용 탭 — 제목은 7기인데 다른 기수 반을 세고 있었다

### ① 반 표에 다른 기수가 섞였다 (16행)

7기는 10반인데 표가 **16행**이었다. `getCost`가 인자를 버리고 있었다.

```ts
export function getCost(cohortId: string) {
  void cohortId                    // ← 버린다
  return delay({ classes: CLASS_COST })   // 전체 반
}
```

[[D37]]에서 지난 기수 반을 목에 넣자 드러났다. **제목은 `7기 · 이번 달`이라 써 놓고 5·6기 반을 같이 보여줬다.**

목도 같이 고쳤다 — `CLASS_COST`가 전체 반을 훑고 세션 기록이 없으면 `[0, 0]`을 넣고 있었다. **사용량이 0인 것과 그 기수 것이 아닌 것은 다른 사실**이라, 기록이 있는 반만 담게 했다.

### ② 두 기수가 상시 공존했다

요약 카드에 `7기 $268 · 8기 $144`가 늘 나란히 있었다. **부트캠프는 한 번에 한 기수를 돌린다** — 목이 8기를 `2026-06-01 ~ 09-30`으로 잡아 7기와 통째로 겹쳐 놓은 것이 원인이었다.

**다만 완전히 안 겹치지는 않는다.** 7기 종료 직전에 8기가 시작하는 **전환기**가 실재하고, 그 달 청구서에는 두 기수가 같이 찍힌다([[D38]]에서 매니저 담당을 진행 중 기수 복수로 잡은 것과 같은 사정).

| | 방법 | 판단 |
|---|---|---|
| ⓐ | 요약도 선택 기수 하나만 | ❌ 정의서가 `기관 총량 + 기수/반`이라 총량을 못 뺀다 |
| ⓑ | **총량 + 그달에 실제로 돈 기수만** | ⭕ 평시 하나 · 전환기 둘. **데이터가 사실을 말하게 한다** |
| ⓒ | 기수 카드 제거 | ❌ *"어디로 갔나"* 를 못 본다 |

ⓑ를 골랐고 **고친 것은 목 데이터다** — 8기를 9월 시작으로 옮기니 화면이 저절로 하나가 됐다. 그리고 `CohortCost.period`를 더해 **카드가 왜 이 기수가 여기 있는지 스스로 말하게** 했다(전환기에 둘이 뜰 때 필요하다).

### ③ "비싼 데"를 찾을 수 없었다

이 화면의 질문은 셋이다 — *얼마 나왔나 · 어디로 갔나 · **비싼 데가 있나***. 셋째를 전혀 못 했다: 정렬이 없어 10행을 눈으로 훑어야 하고, **반마다 인원이 달라 총액이 큰 반이 비싼 반도 아니다.**

**`1인당` 열 + 정렬 셋**(반 이름순 · 비용 많은 순 · 1인당 많은 순)을 넣었다. 요약 카드는 기수별 1인당을 이미 보여주는데 **표에는 없어서 같은 판단 기준이 한 단계 아래에서 사라져 있었다.**

> **`세션당`은 안 만들었다.** OP-01이 *"세션당 LLM 비용 산식이 어느 문서에도 정의된 적 없다"* 고 명시한다 — 화면이 `비용 ÷ 세션`을 만들면 그 산식을 발명하는 것이다(E8). `1인당`은 다르다: 인원은 우리가 아는 값이고 요약이 이미 쓰는 계산이다.

**정렬은 서버가 한다**(api-boundary §1-②) — 목이 배열이라 화면에서 돌려도 되지만 그러면 연동이 재작성이 된다.

### ④⑤ 요약 문구 — 판단 근거가 빠져 있었다

| | 전 | 후 |
|---|---|---|
| 예산 | `예산 $600 대비 69%` | **`월 계약 예산`** — 월인지 총액인지, 기관인지 기수인지 없었다(바로 아래 기수 카드와 한 상자라 기수 예산으로 읽혔다) |
| 증감 | `전월 대비 +12%` | **`지난달 $239 → +12%`** — `+12%`가 $400→$412인지 $50→$56인지에 따라 할 일이 다르다 |

`previousTotal`이 null이면(첫 달) 증감을 아예 안 그린다 — **없는 비교를 만들지 않는다**(F3).

### ⑦ 3열 고정 격자가 데이터 개수에 안 맞았다

`grid-cols-3`에 [총량][기수][기수]를 넣고 있었다. **기수가 하나면 칸이 비고 셋이면 넘친다** — 개수가 데이터에 달린 것을 고정 격자에 넣으면 깨진다. 총량만 폭을 고정하고(이 화면의 기준값이라 자리가 움직이면 안 된다) 기수는 흐르게 뒀다.

### 목 숫자가 서로 안 맞던 것

고치고 보니 **반 합계 $276 ≠ 기수 총액 $268**이었다. 화면이 두 수를 같이 보여주므로 어긋나면 바로 드러난다 — 합이 맞게 맞췄다.

**그리고 F반을 `22명 · 세션 64`로 바꿨다.** 모든 반이 25명이면 1인당이 총액에 비례해서 **두 정렬이 같은 답을 낸다** — 그러면 1인당 열이 왜 있는지 화면에서 안 보인다. 지금은 갈린다.

| 정렬 | 1위 |
|---|---|
| 비용 많은 순 | C반(25명) $29 |
| **1인당 많은 순** | **F반(22명) $27 · 1인당 $1.23** |

- **연결:** [[D38]] 기수 스코프 · [[D37]] 지난 기수 데이터 · [[D30]]-⑦ 예산은 계약값


## D40 · 비용 — 1인당을 버리고 월별·회차를 넣었다

[[D39]]에서 `1인당` 열을 넣었다. **그 판단이 틀렸다.**

### ① 1인당은 구조적으로 상수다

기획을 다시 보니 근거가 둘 있었다.

> `측정 규칙  문항 3 · 단계 4 · 힌트 2 · 세션 70분` — **전 기수 공통 · 읽기 전용** (OP-04)
> `7기 전체 · 10반 250명이 **같은 회차**를 한다` (OP-03)

**학생 1명이 쓰는 세션 규격이 고정이고 모든 반이 같은 회차를 한다.** 그러면 1인당 비용은 반마다 같아질 수밖에 없다 — 실측으로도 $1.12~$1.23이라 정렬해 봐야 총액순과 같은 순서가 나왔다.

> D39에서 이 열을 살리려고 **F반을 22명으로 바꿔 억지로 차이를 냈다.** 데이터를 비틀어야 차이가 나는 지표는 지표가 아니다 — 그게 신호였는데 그때는 "목이 단조롭다"로 읽었다.

**`세션 많은 순`으로 대체했다.** 비용은 세션에서 나오고, 재시험·미제출이 반마다 다르면 세션이 갈린다 — **그것이 유일하게 조치 가능한 차이**다.

### ② 이번 달만 보면 판단할 수 없다

기수는 7개월인데 화면은 이번 달 한 점만 봤다. 그래서 못 답하는 것이 셋이었다 — 지금까지 얼마 썼나 · 어느 달에 튀었나 · **예산이 버티나**.

정의서가 이 탭을 `선택 기수`로 정의하므로(§3) **기수가 범위이고 이번 달은 그 안의 한 점**이다.

| | 전 | 후 |
|---|---|---|
| 요약 기준 | 이번 달 $268 | **기수 누적 $1,147** |
| 예산 비율 | 월 예산 대비 | **계약 예산(기수 전체) 대비 48%** |
| 기간 감각 | 없음 | **남은 2개월** |

예산을 월 기준으로 두면 늘 작게 나와 안심하게 된다. **남은 기간과 소진율은 짝이다** — `48%`만으로는 판단이 안 되고 *"2개월 남았는데 48%"* 여야 읽힌다. **예측은 안 만든다**(*"이 추세면 초과"* 는 화면이 만드는 판정이라 E8) — 재료만 주고 판단은 사람이 한다.

### ③ 금액에 "그달에 뭘 했나"를 붙였다 — 이 변경의 핵심

`$268`을 보고 할 수 있는 판단이 없었다. 많은지 적은지 기준이 없기 때문이다.

기획에 답이 있었다 — **비용은 세션에서 나오고, 세션은 회차에서 나온다.**

```
2026. 07   미프 4차 · 빅프 1차              673   $268
2026. 06   미프 3차                        601   $239
2026. 05   마감된 회차 없음 · 재시험·재응시    422   $168
2026. 04   미프 1차 · 미프 2차              631   $251
2026. 03   오리엔테이션 진단                 555   $221
```

**회차가 둘인 달이 비싼 것은 정상이고, 회차가 없는데 비싼 달이 조치 대상이다.** 5월이 그 자리를 보여준다 — 마감된 회차가 없는데 $168이 나왔고 그것은 재시험·재응시다.

- 회차 이름은 **문자열만** 받는다(`MonthlyCost.projectNames`) — 프로젝트 도메인 객체를 들이면 레이어 규칙을 넘는다([[D15]]). 교안의 `linkedProjectNames`가 같은 방식이다.
- 회차 없는 달에 `—`를 안 쓴다 — **없음과 0은 다르다**(F3). 무엇이 있었는지 쓴다.
- **차트를 안 만든다.** 점이 5~12개라 표로 충분하고, 무엇보다 **차트는 회차 이름을 못 담는다** — 이 블록의 값이 거기 있다.

### ④ 제목이 범위를 잘못 말하고 있었다

`2026년 07월 · 기관 전체`라 적혀 있었는데 요약도 표도 **선택 기수** 것이다. `7기 · 2026년 07월 기준`으로 고쳤다.

### 화면 순서 — 질문의 순서

표가 둘이 되어 한 화면에 안 들어간다(실측 395px 넘침). **월별을 위, 반별을 아래**로 뒀다 — 월별이 이 화면의 새 축이고, 반별은 *이번 달 어디가 많이 썼나*라는 한 단계 아래 질문이다. 스크롤하는 순서가 질문의 순서다.

- **연결:** [[D39]] 비용 탭 1차 검토 · [[D30]]-⑦ 예산은 계약값


## D41 · 반별에 누적을 나란히 — 월별 매트릭스는 안 만든다

[[D40]]에서 월별 표를 만들자 반별이 **이번 달 한 점**만 남았다. 반별도 기간을 봐야 한다.

### 매트릭스가 아닌 이유

`반 × 월` 격자를 먼저 검토했다.

| | 매트릭스 | 누적 열 |
|---|---|---|
| 열 수 | 기수 7개월이면 **10열**, 12개월이면 **15열** | 6열 |
| 읽는 부담 | 50~120개 셀 | 10행 × 2값 |
| 셀 하나의 크기 | `$25`~`$30` — **훑어도 차이가 안 보인다** | 누적은 폭이 벌어져 보인다 |

**기간이 늘수록 열이 늘어나는 표는 넘친다.** 게다가 셀 하나가 $25~30이라 격자를 채워 놔도 어디가 비싼지 안 읽힌다.

### 이번 달 + 누적을 나란히

한 달치 편차는 실측 **$25~29(폭 $4)** 라 우연히 갈린 것인지 계속 그런 것인지 모른다. **누적하면 폭이 $20 넘게 벌어진다.**

```
반    담당      교육생  세션  이번 달  기수 누적
F반   담당 없음   22     64    $27     $138   ← 이번 달은 중간, 누적 1위
C반   최유진     25     71    $29     $128
```

**두 값이 다른 질문에 답한다.**

| 열 | 질문 | 조치 |
|---|---|---|
| 이번 달 | 지금 어디가 많이 쓰나 | 즉시 |
| **기수 누적** | **계속 많이 쓰는 곳이 어디냐** | 구조적 |

요약의 `지난달 $239 → 이번 달 $268`과 같은 짝이다 — **한 점이 아니라 변화를 보여준다.**

정렬에 `누적 많은 순`을 더했다. 실측으로 **이번 달 순서와 다른 답이 나온다**(이번 달 1위 C반 / 누적 1위 F반) — 두 열이 따로 필요한 이유가 화면에서 보인다.

### 목 데이터 — 네 합계를 맞췄다

화면이 총계와 내역을 같이 보여주므로 어긋나면 바로 드러난다.

| | |
|---|---|
| 반별 이번 달 합 268 | = `COST.total` |
| 반별 누적 합 1147 | = `COST.cohortTotal` |
| 반별 이번 달 세션 합 668 | = `monthly[0].sessions` |
| 반별 누적 세션 합 2877 | = `monthly` 세션 합 |

넷째를 맞추다 `monthly[0].sessions`가 673으로 적혀 있던 것을 발견해 668로 고쳤다.

**F반을 `이번 달 중간 · 누적 1위`로 뒀다** — 이번 달만 보면 안 보이는 반이 있어야 누적 열의 값이 드러난다. 22명인데 재시험이 계속 많았던 반이라는 설정이다.

> [[D40]]에서 *"데이터를 비틀어야 차이가 나는 지표는 지표가 아니다"* 라고 적고 1인당을 뺐다. 이번은 반대다 — **비틀지 않아도 차이가 나는 값**을 목이 표현하지 못하고 있었다(모든 반이 균일했다). 지표가 문제인지 목이 문제인지를 가르는 것이 판단의 자리다.

- **연결:** [[D40]] 월별·회차 · [[D39]] 비용 탭 1차


## D42 · 지난달 반별을 볼 길이 없었다 — 월별에서 반별로 내려간다 (→ **D43에서 대체**)

[[D41]]에서 반별에 `이번 달`과 `기수 누적`을 뒀다. **그 사이 달들은 볼 방법이 없었다** — *"6월에 어느 반이 많이 썼나"* 에 답을 못 한다.

### 드릴다운 — 물음이 이어지므로 표도 이어진다

월별 표의 **월을 누르면 아래 반별이 그달로 바뀐다.**

```
월별   2026. 06  미프 3차   601  $239   ← 누른다
반별   7기 · 2026년 06월 (선택)
       A반  박지현  25  62  $25  $118
       …                    합 $239 ← 월별 총액과 같다
```

이 화면의 물음이 실제로 이 순서다 — **언제 튀었나(월별) → 그달에 어디가 썼나(반별)**. 표 둘을 이어 붙이면 두 번째 물음에 답할 자리가 생긴다.

| | 방법 | 판단 |
|---|---|---|
| A | **월 클릭 → 반별 전환** | ⭕ 열이 안 늘고, 물음의 순서와 같다 |
| B | 반별에 월 드롭다운 | ❌ 컨트롤이 하나 더 늘고, **월별 표를 보고 고르는 것**이 자연스럽다 |
| C | 반 × 월 매트릭스 | ❌ [[D41]]에서 버렸다 — 열이 10~15개가 되고 셀이 $25~30이라 안 읽힌다 |

**셀 전체가 아니라 버튼이다.** 키보드로 닿고, 누를 수 있다는 것이 모양에 보인다 — 행 클릭만 두면 둘 다 안 된다. 고른 달은 행 강조 + 제목 `(선택)` + **열 이름**(`06월`)에 나타난다. 열 이름을 `이번 달`로 두면 6월을 보면서 7월로 읽는다.

### 목 — 50칸을 손으로 적지 않는다

반 10개 × 월 5개 = 50칸이다. 손으로 적으면 **월 총액과 어긋나는 순간을 아무도 못 잡는다.**

**누적을 가중치로 두고 서버가 나눈다.** `CLASS_TOTAL`(반별 기수 누적)이 원천이고, 각 달은 그 비율로 배분된다.

- 합이 **항상** 월 총액과 맞는다 — 실측으로 다섯 달 전부 일치(세션·비용 둘 다)
- 반별 성향이 달마다 유지된다 — F반은 어느 달에 가도 상위다
- 반올림 오차는 **가중치가 가장 큰 반이 흡수**한다. 작은 반에 몰면 그 반 숫자가 튄다

> 목이 배열을 갖고 있던 것을 계산으로 바꾼 것이라, 실제 서버로 갈 때는 이 함수가 통째로 사라진다(DB가 월별 사용량을 그대로 갖는다). **목이 커질수록 계산으로 두는 편이 안전하다** — 손으로 적은 값은 서로 어긋나고, 어긋난 것을 화면이 보여준다.

- **연결:** [[D41]] 누적 열 · [[D40]] 월별·회차


## D43 · 반별을 월 매트릭스로 — 내가 두 번 틀린 자리

[[D41]]에서 매트릭스를 버리고, [[D42]]에서 드릴다운을 넣었다. **둘 다 틀렸다.**

### 무엇이 틀렸나

| | 판단 | 실제 |
|---|---|---|
| [[D41]] | 매트릭스는 **열이 10~15개**라 넘친다 | **교육생·세션을 같이 세어서** 나온 수다. [[D40]]에서 1인당을 뺀 뒤 그 둘은 이 표의 질문에 답하지 않는다 |
| [[D42]] | 월별 행을 눌러 반별을 바꾼다 | **누를 수 있다는 것이 화면에 안 보인다.** 게다가 한 번에 한 달이라 **두 달을 나란히 못 본다** — 앞 달 숫자를 외워야 한다 |

빼고 다시 재니 **696px**다(반 64 + 담당 96 + 월 7칸 448 + 누적 88). 셸 내용 폭이 약 1130px이라 여유가 434px 남는다. **처음부터 들어갔던 것이다.**

### 매트릭스

```
반    담당      3월   4월   5월   6월   7월    누적
A반   박지현    $23   $26   $17   $25   $28    $118
C반   최유진    $25   $28   $19   $27   $30    $128
F반   담당 없음  $27   $30   $20   $29   $27    $138
```

**한 행이 한 반의 궤적이다.** 왼쪽에서 오른쪽으로 시간이 흐르고 끝의 `누적`이 결론이다 — 어느 반이 어느 달에 튀었는지가 눈으로 잡힌다. 월별 표는 최근이 위(내림차순)지만 **매트릭스는 오래된 것이 왼쪽**이다: 추이는 왼→오른쪽으로 읽는다.

- **`담당`은 남겼다** — 비싼 반을 찾은 다음 할 일이 *누구에게 묻나* 다
- **이번 달 열만 진하게** — 나머지는 지난 것이라 배경으로 물러난다
- **달마다 정렬을 안 만든다** — 월이 열로 펼쳐졌으므로 눈으로 훑는 일이고, 일곱 개짜리 드롭다운은 매트릭스가 이미 하는 일이다. `반 이름순`·`누적 많은 순` 둘만 남겼다
- 아직 안 지난 달은 열이 없다 — 기수가 9월까지여도 7월이면 다섯 칸이다

실측 — **각 월 열의 합이 월별 표와 일치**(221 · 251 · 168 · 239 · 268), 누적 합 1147, 가로 스크롤 없음.

### 배운 것

**"열이 넘친다"는 판단을 셈 없이 했다.** D41에서 `10~15열`이라 쓸 때 실제로 폭을 재지 않았고, 지금 표에 있는 열을 그대로 세었다 — **매트릭스로 가면 빠질 열을 안 뺐다.** 화면 구조를 바꾸는 판단은 *바꾼 뒤의 모습*으로 재야 한다.

D42의 드릴다운은 더 나쁜 종류였다. **동작은 했고 검증도 통과했다**(다섯 달 전부 합계 일치). 그런데 *"누를 수 있다는 것을 사용자가 아는가"* 는 그 검증에 없었다 — 기능이 도는 것과 발견되는 것은 다른 문제다.

- **연결:** [[D42]] 드릴다운(대체됨) · [[D41]] 누적 열 · [[D40]] 1인당 제거


## D44 · 비용 탭 뷰 보완 — 흡수 열을 또 틀렸다

### ①② 마지막 열에 폭을 안 줘서 행을 못 읽었다

| 표 | 흡수 열이던 것 | 폭 |
|---|---|---|
| 반별 | `누적` | **751px** |
| 월별 | `회차` | **927px** |

표 열 폭 표준이 *"마지막 칸이 남는 폭을 흡수한다"* 인데, **그 전제는 마지막이 액션이거나 서술 열**일 때다. 둘 다 마지막이 **값**이라 앞 숫자와 사이가 벌어져 한 행을 가로로 따라 읽을 수 없었다.

> **이 파일에 이미 같은 실수를 잡은 주석이 있다** — *"규칙 문장만 따라 `비용`을 비우면 `세션`과 `비용` 사이에 700px가 벌어진다(실제로 그렇게 만들었다가 렌더에서 잡았다)"*. **적어 놓고 또 했다.** 열을 새로 만들 때마다 흡수 열이 어디로 갔는지 다시 봐야 한다.

흡수를 **식별 열**로 옮겼다(반별 → `담당`, 월별 → `월`). 이름이 왼쪽에 붙고 **숫자들이 오른쪽에 모여 나란히** 읽힌다. 실측 — 7월과 누적 사이 **0px**, 가로 스크롤 없음.

### ③ 숫자만으로는 이상치가 안 보였다

[[D43]]에서 *"어느 반이 어느 달에 튀었는지가 눈으로 잡힌다"* 고 썼는데 **안 잡혔다.** 실측한 편차가 이렇다.

| | 범위 | 폭 |
|---|---|---|
| 월별 칸 | $14~$30 | **$6~9** |
| 누적 | $97~$138 | $41 |

**$6 차이를 50개 숫자 속에서 찾는 것은 불가능하다.**

**칸에 배경 농도를 입혔다**(4단계). 텍스트는 그대로 두고 배경만 바꾸면 행을 훑을 때 진한 칸이 먼저 보인다.

```
F반   33333   $138      ← 모든 달에서 상위
E반   1....   $102
J반   .....    $97
```

- ⚠ **기준을 화면이 만들지 않는다**(E8). `$28 넘으면 빨강` 같은 임계값이 아니라 **그 달의 최소~최대 사이 어디쯤인지**만 칠한다 — 기준은 데이터가 정한다
- **경고색을 안 쓴다** — primary 계열이다. 비싼 것이 잘못된 것은 아니다
- 폭이 0이면(전부 같으면) 안 칠한다 — 차이가 없는데 강약을 만들지 않는다

### ④ 원인을 반별로 볼 수 없었다

[[D43]]에서 반별 `세션`을 뺐다. 그런데 이 화면은 *비용은 세션에서 나온다* 고 계속 말해 왔다 — *"F반이 왜 누적 1위지"* 의 답이 세션인데 그 열이 없었다. `누적 세션` 열을 더했다(①을 고치니 폭이 남았다).

### ⑦ 푸터가 페이징을 암시했다

`1–10 / 10개`는 **나뉜 것이 있을 때** 쓰는 표기인데 10반이 전부다. 푸터를 뺐다 — 제목의 `10개`로 충분하고, E7(*페이지가 하나면 페이저를 그리지 않는다*)의 연장이다.

### ⑥ 결함이 아니었던 것 — `x`

접근성 트리에 `x`가 잡혀 결함으로 보고했다. 파고드니 **Base UI가 `progressbar` 안에 넣는 1×1px 자리표시자**였다(`role="presentation"` + `visuallyHidden`, `ProgressRoot.js:65`). 화면에도 스크린 리더에도 안 나온다.

- 처음엔 *"내가 `aria-label`을 넘겨서 생겼다"* 고 진단했는데 **틀렸다** — 그 속성을 안 넘기는 슈퍼어드민 화면에도 똑같이 있었다.
- **`innerText`로 본 것이 오판의 원인이다.** 시각적으로 숨긴 요소도 그 값에는 잡힌다 — 화면에 보이는지는 **크기와 계산된 스타일**로 재야 한다.

`aria-labelledby`로 아래 설명 문단을 가리키는 것은 남겼다 — 같은 문장을 `aria-label`로 또 쓰면 한 사실이 두 곳에 생긴다(D1).

### 안 고친 것 — 세로 스크롤 (판단)

세 블록이 세로로 쌓여 **395px 넘친다**(요약 346 → 월별 650 → 반별 1218). 월별과 반별을 같이 못 보는데, 둘을 비교하는 것이 이 화면의 일이다. 서브탭으로 묶는 안을 냈으나 **지금 구성을 유지하기로 했다**(사용자 판단) — 3블록이면 견딜 만하다.

> ⚠ 기수가 12개월이면 월별이 12행이 되어 더 길어진다. 그때 다시 볼 자리다.

- **연결:** [[D43]] 매트릭스 · [[D39]] 흡수 열 첫 사례
