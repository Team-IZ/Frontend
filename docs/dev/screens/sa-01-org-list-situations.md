# SA-01 기관 목록 — 상황 전수

> `docs/dev/screenhardening.md` 1단계 결과물. 대상 파일: `OrgListScreen.tsx` ·
> `OrgCreateDialog.tsx` · `OrgMetrics.tsx` · `labels.ts`.
> 연동은 완료 상태(2026-08-10 전수 조사 기준, 슈퍼어드민 3/3). 여기서는 값이 **오기 전·
> 안 올 때·이상하게 올 때** 화면이 무엇을 하는지만 본다.

## 조회 흐름

```
useFindOrganizations({query})   GET /organizations          ─┐
useFindPlatformSummary()        GET /organizations/summary   ─┘ 서로 안 기다린다 — 독립 병렬

OrgCreateDialog(모달이 열렸을 때만):
  checkNameAvailability({query})  이름 입력마다, 400ms 디바운스, react-query 아닌 직접 호출
  useCreateOrganization()         제출 시 1회 — 성공하면 organization 접두 쿼리 전부 무효화
                                   (목록·요약이 각자 갱신을 부르지 않는 이유)
```

목록과 요약 카드는 **서로 다른 쿼리라 따로 끝난다** — 하나가 먼저 오고 하나가 늦게 올 수 있다.
이 자체가 축 B다.

## 축

### 축 A. 목록 조회 상태

| | |
|---|---|
| A1 | pending(첫 로딩) — `TableFrame` 안에 스켈레톤 5행 |
| A2 | isError |
| A3 | success, `total === 0` 이고 필터 없음 → "아직 등록된 기관이 없습니다"(플랫폼 전체가 빈 것) |
| A4 | success, `rows.length === 0` 이고 필터/검색 있음 → "조건에 맞는 기관이 없습니다" |
| A5 | success, `rows.length > 0` |

A3·A4는 같은 "0건"인데 문구·액션이 다르다(`hasFilter`로 분기) — **검색어 때문에 0건인데
"아직 없다"고 하면 거짓말**이라고 코드 주석이 직접 밝혀 둔 지점.

### 축 B. 요약 카드(summary) 조회 상태 — 목록과 독립

| | |
|---|---|
| B1 | pending — `summary.data &&` 조건이라 **카드 자리 자체가 없다**(스켈레톤 없음) |
| B2 | success |
| B3 | isError — `isError`를 아예 안 읽는다. 실패해도 그냥 안 뜬다, 재시도 버튼도 없다 |

조합 후보: 목록은 이미 떴는데(A5) 요약은 아직(B1) → **표가 먼저 자리 잡고 카드 4개가 위에서
불쑥 나타나며 표를 밀어낸다**(레이아웃 시프트 후보, 4단계에서 CLS로 확인). 반대로 요약이
먼저 오고(B2) 목록이 스켈레톤(A1)인 조합도 가능.

### 축 C. 검색 · 상태 필터

| | |
|---|---|
| C1 | 검색어 없음 · 상태 전체(ALL) |
| C2 | 검색어만 |
| C3 | 상태 필터만(활성 또는 정지) |
| C4 | 검색어 + 상태 필터 |

`DELETION_PENDING`·`DELETED`는 필터 옵션에 없다(의도적 — labels.ts 주석) → 그 상태의 기관은
**필터로 좁혀 찾을 수 없고 우연히 페이지를 넘기다 만난다**는 뜻. 상황으로 남긴다.

### 축 D. 정렬

| | |
|---|---|
| D1 | 이름 asc/desc |
| D2 | 생성일 asc/desc(기본값) |

기수 수·교육생 수·비용 3열은 정렬 버튼이 없다(서버가 배치 집계라 전역 정렬 불가 — 의도).

모양으로 안 보이는지**를 렌더로 확인해야 하는 지점.

## 조합 수

데이터 로드 축만(A × C × D × E, B·F·G는 각자 별도 트랙): 대표값으로 잡아도
`3(성공/실패/로딩) × 6(검색×필터) × 4(정렬) × 3(페이지 위치)` ≈ **216**. 여기에 B(3)를 곱하면
600대. G(8)는 행 단위라 곱하지 않고 "그 상태를 가진 기관이 실제로 있는가"로 따로 확인.
F(12)는 모달을 열어야 진입하는 별개 플로우. **전부 못 본다** — 2단계에서 실제로 갈리는
지점(A×B 조합, G8, F5)만 추린다.

## 2단계 · 실측(curl 기반, 2026-08-12)

이 세션은 Bash·Chrome 확장을 함께 쓸 수 있어 screenhardening.md 2~6단계를 직접 진행했다.
브라우저 자동화(claude-in-chrome)는 세션 도중 연결이 끊겨 있어 **curl로 되는 것부터** 먼저
실측했다. 렌더 확인·CLS·플로우 캡처는 확장 연결 후 이어서 채운다.

### 경계 데이터 — 실제 조회 결과(15개 기관 전수)

| 축 | 실제 있음? |
|---|---|
| 오퍼레이터 미배정(G2) | ✅ 파이널랩(ACTIVE, `operatorUnassigned: true`) |
| 정지(G3) | ✅ 블루아카데미·코딩부스트(둘 다 오퍼레이터 배정됨) |
| 삭제 대기(G4)·삭제됨(G6) | ❌ 없음 |
| G8(정지+미배정 동시) | ❌ 없음(정지 2건 모두 배정 상태) |

DELETION_PENDING·G8은 실제로 없어 **재현이 필요한 상태**다. 사용자와 상의해 백엔드 데이터를
직접 건드리지 않고(파기(purge) API가 스웨거상 "사용 불가"라 만든 기관을 완전히 못 지운다는
것 확인 — 건드리면 되돌릴 수 없는 흔적이 남는다) **브라우저 라우트 가로채기로 시뮬레이션**하기로
결정. 확장 연결 후 진행.

### API 실측 — TTFB (3회 반복, `curl -w`)

| 엔드포인트 | run1 | run2 | run3 |
|---|---|---|---|
| `GET /organizations?size=20` | 2.26s | 1.69s | 1.58s |
| `GET /organizations/summary` | 1.83s | 1.79s | 1.88s |
| `GET /organizations/name-availability` | 0.95s | 1.02s | 0.94s |

- **크기·필터에 안 붙는다** — `size=1`도 1.89s, `status=SUSPENDED` 필터도 1.81s로 거의
  그대로. 15개뿐인 목록에 1.6~2.3초는 응답 크기(12.7KB)로 설명 안 되고, `time_connect`가
  50~130ms인 걸 보면 네트워크도 아니다 — **서버 계산 비용**으로 보인다(OP-01 `/projects`와
  같은 패턴).
- **목록·요약은 실제로 병렬이다** — 별도 타이머로 각각 재보니 850ms/2298ms처럼 서로 다른
  시간에 끝났다(둘 다 0ms에서 시작). 처음에 두 요청을 동시에 쐈을 때 합계에 가까운 총
  시간이 나와 "직렬 아닌가" 의심했으나, 각 요청을 자기 시작 시각 기준으로 다시 재니
  병렬이 맞았다 — **의심을 실측으로 재확인**(느낌으로 결론 내지 않는다).
- ④ 문서에 답이 있나 — `docs/dev/backend/`·`docs/dev/decision-log.md`에 이 지연 관련 기재
  없음(grep 확인, 0건). ⑥ 아직 요청서로 보내지 않음 — §6 "화면 하나마다 보내지 않는다"에
  따라 다른 화면 실측과 묶어 한 번에 정리 예정.

### 코드 리뷰로 확정된 것(①우리 코드, 렌더 없이 판정 가능)

- **F5 · 고침, 렌더 재현은 도구 한계로 미완** — `OrgCreateDialog.tsx` `checkNameAvailability`
  실패 시 `.catch(() => setNameCheck('idle'))`로 무조건 `idle`로 되돌리던 것을, "아직 입력
  안 함"과 구분되는 `unknown` 상태로 분리했다("중복 확인에 실패했습니다. 제출 시 다시
  확인합니다." 문구, `canSubmit`은 그대로 통과 — 최종 판정은 여전히 제출 409가 한다).
  브라우저에서 `window.fetch`를 패치해 실패를 강제해 봤지만 **격리된 JS 컨텍스트라 페이지의
  실제 `fetch`엔 안 먹었다**(같은 방식으로 CLS `PerformanceObserver`는 성공 — 이건 브라우저
  레벨 API라 컨텍스트를 안 타지만, `fetch` 몽키패치는 앱이 이미 참조를 잡고 있어 늦다).
  코드 리뷰·타입체크·빌드로는 정답이 명확해 고침은 유지하되, **실패 문구가 실제로 뜨는지는
  다음 세션에서 실제 네트워크 차단(DevTools 오프라인 토글 등)으로 재확인 필요**.
- **접근성(행 키보드 진입) · ✅ 고침·렌더 확인 완료** — `OrgListScreen.tsx`의
  `<TableRow onClick=...>`에 `role="button"` `tabIndex={0}` `onKeyDown`(Enter·Space →
  같은 네비게이션)을 추가했다. Tab으로 포커스 진입·Enter로 상세 진입 실제 확인.
  **추가로 렌더에서만 보이는 결함을 하나 더 잡았다** — 전역 `:focus-visible` 아웃라인
  (`outline: 2px solid var(--color-primary); outline-offset: 2px`)이 테이블 행에서는
  다음 행에 아래쪽이 가려져 **윗변 얇은 선 한 줄만 보였다**(행이 경계 없이 맞붙어 있고
  `outline-offset`이 다음 행의 페인트 순서에 덮인 것으로 추정). `outline-none` +
  `focus-visible:ring-2 focus-visible:ring-inset focus-visible:ring-ring`로 교체해
  포커스 링이 행 안쪽에 완전히 그려지도록 고쳤다(Item.tsx·Textarea.tsx가 이미 쓰는
  "outline-none은 대체 링과 함께"라는 기존 관례를 그대로 따름). 고친 뒤 렌더로 재확인 완료.
- **인증·세션(축 검증) 통과** — `RequireRole.tsx`가 `SUPER_ADMIN`이 아니면 로그인 여부와
  무관하게 `initialScreenFor(role)`로 리다이렉트하는 것을 코드로 확인. 서버 401/403과
  별개로 프론트 방어선이 실제로 있다 — 문제 없음, 렌더 확인 불필요.
- **summary 실패 시 무대응(B3) 확정, 아직 미수정** — `OrgListScreen.tsx`는 `summary.data &&`만
  보고 `summary.isError`를 아예 안 읽는다. 실패해도 카드 4개가 자리 없이 사라질 뿐 재시도
  수단이 없다 — 코드로 확정. 렌더 확인 전이라(어떤 실패 UI가 적절한지 시각적 판단이
  필요) 이번 커밋에서는 보류.
- **G8 배지·배경 불일치는 재현 못 함** — `orgStatusBadge`(labels.ts) 우선순위는 의도적
  설계(정지 > 미배정)이지만, 행 배경(`bg-warning-soft`)은 `operatorUnassigned` 하나만 보고
  켜져 배지와 다른 말을 할 수 있다는 것은 코드로 보인다. 실제 데이터엔 그 조합이 없고(2단계
  경계 데이터 표), `fetch` 라우트 가로채기도 격리 컨텍스트 문제로 안 먹혀 **아직 눈으로
  못 봤다**. 다음 세션 후보: ① 실제로 정지+미배정 조합 기관이 생기면 그때 확인 ②
  DevTools Network 탭에서 수동으로 응답 오버라이드(Local Overrides) ③ 사용자 승인 하에
  실제 기관 하나를 짧게 SUSPENDED로 바꿨다 되돌리기(사용자가 앞서 라우트 가로채기 쪽을
  택해 이번엔 보류).

### 실제 렌더에서만 잡힌 것 (2단계 핵심 — 코드 리뷰로는 안 보였다)

- **🔴 최우선 · ✅ 고침 — `isPlatformEmpty`가 로딩 중을 "없음"으로 오판.** 새로고침 직후
  실제로 15개 기관이 있는데도 2~3초간 **"아직 등록된 기관이 없습니다" + `[+ 기관 생성]`**이
  떴다(스켈레톤 대신). 원인: `isPlatformEmpty = !hasFilter && total === 0`가 `isPending`을
  안 봐서, `data`가 아직 없어 `total`이 구조상 0인 로딩 중에도 참이 됐다. 렌더 삼항연산자
  순서상 `isError → isPlatformEmpty → (필터 UI + isPending 분기)`라 `isPlatformEmpty`가
  `isPending` 분기보다 **먼저** 걸려 스켈레톤 자체가 안 그려졌다. `isPending`을 조건에
  추가해 고침, 재현 스크린샷으로 고침 전/후 확인함. **최우선("거짓말을 하나")으로 처리** —
  기존 기관을 다 지우라고 잘못 권하는 CTA까지 같이 떴던 것이 특히 심각.
- **실제 503 두 번 관측** — `GET /organizations`가 새로고침 두 번 중 한 번꼴로 503을
  반환했다(`/organizations/summary`는 그때마다 200). 기존 `isError` 처리("기관 목록을
  불러오지 못했습니다" + 다시 시도)가 정확히 의도대로 작동하는 것을 실측으로 확인 —
  **이 부분은 이미 맞게 짜여 있었다.** 다만 반복 빈도(테스트 트래픽 짧은 시간에 4~5회 중
  2회)로 보아 이 백엔드 엔드포인트가 유난히 불안정하다 — TTFB 실측(1.6~2.3s, 위 표)과
  함께 백엔드 요청서 후보로 묶어 둔다(⑥, 아직 미발송 — §6).
- **SPA 내비게이션에서 캐시 데이터가 실패한 백그라운드 재조회에 지워짐** — 플랫폼 관리
  화면에서 사이드바로 "기관"을 클릭하면 t=0ms에 **캐시된 정상 목록이 즉시 보였다가**,
  약 1초 뒤 React Query의 마운트 시 백그라운드 재조회가 503을 맞아 **정상 데이터를 밀어내고
  실패 화면으로 바뀌었다.** 이건 위 503 이슈가 노출시킨 것이지, 캐시 자체의 결함은 아니다
  — 다만 "이미 보여준 정상 데이터를 실패한 background refetch가 지워도 되는가"는 별개의
  설계 질문으로 남긴다(예: `placeholderData: keepPreviousData` 류로 이전 성공 데이터를
  유지하며 조용히 재시도하는 편이 사용자에게 덜 놀랍다 — 이번 범위에서는 코드 변경 안 함,
  다음 논의 후보로만 기록).
- **CLS 실측** — `PerformanceObserver`로 측정한 layout-shift 누적 0.0550(임계 0.1 미만,
  "양호" 구간이지만 무시할 정도는 아님). 두 번의 시프트 중 큰 쪽(0.052)이 **t=5527ms**에
  발생 — situations 문서가 예측한 "표가 먼저 자리 잡고 요약 카드 4개가 나중에 밀고 들어와
  표를 아래로 미는" B1+A5 조합이 실제로 일어난다는 뜻. 이번 측정은 위 503 재시도까지 겹쳐
  전체 로드가 느렸던 케이스라(5초대) 정상 컨디션에서 재측정하면 수치가 더 낮아질 수 있다
  — 재현 조건 명시.

## 4단계 · 2차 라운드 — 실제로 눌러 확인 (2026-08-12, 이슈 #185)

이 세션은 Chrome 확장(claude-in-chrome)이 살아 있었지만, **네이티브 DevTools가 같은 탭에
동시에 붙지 못해**(둘 다 CDP로 탭에 attach — 하나만 허용됨) F12가 반응하지 않았다.
`window.fetch` 오버라이드를 메인월드에 스크립트 주입까지 해서 시도했지만 **API 클라이언트가
페이지 로드 시점에 이미 `fetch` 참조를 붙잡아 둔 뒤라 늦게 붙인 오버라이드가 안 먹혔다**
(격리 컨텍스트 문제가 아니라 **참조 캡처 타이밍** 문제였다 — 이전 세션 결론을 한 겹 더
정확하게 만든 것). 최종적으로 **Playwright(Node, 완전히 별도 프로세스)를 새로 띄워 사용자가
직접 로그인하고, `page.route()`로 실제 응답을 가로채는 방식**으로 뚫었다 — 같은 탭에 두
CDP 클라이언트가 못 붙는 문제와 무관한 계층이라 라우트 가로채기가 정상 동작했다. **다음
화면부터는 claude-in-chrome이 막히면 바로 이 방법으로 넘어간다.**

### E1–E6 · 페이지네이션 실클릭 — ✅ 전부 정상, 버그 없음

실제 조직이 15개뿐이라(PAGE_SIZE=20) 항상 1쪽이었던 문제를, `page.route()`로 `/organizations`
응답을 200개로 부풀려(실제 15개를 실제로 조회한 뒤 그 데이터를 복제 — 백엔드는 손대지 않음)
진짜 10쪽짜리 목록을 만들어 확인했다.

- E1(1쪽, `totalPages===1`) — 실측 그대로(15개, Prev/Next 안 그려짐). 정상.
- E2(1쪽 Prev 비활성) — `aria-disabled="true"` 확인 + **강제 클릭까지 실제로 시도** →
  범위 표시(`1–20/200개`)가 안 바뀜. 정상.
- E3(중간 쪽) — 5쪽 클릭 → 정상 이동.
- E4(마지막 쪽 Next 비활성) — 다음을 반복 클릭해 10쪽 도달, `다음` 버튼이 실제로
  안 눌림(Playwright가 "element is not enabled"로 클릭 자체를 거부). 정상.
- E5(생략 `…`) — 총 10쪽에서 `…` 렌더 확인(`getPageRange` 로직대로 한쪽만 접힘). 정상.
- E6(필터 변경 시 1쪽 강제 리셋) — **10쪽에 가 있는 상태**에서 상태 필터를 활성으로
  바꾸니 범위가 `1–20/200개`로 리셋됨(스크린샷·범위 텍스트 둘 다 확인). 정상.

### D축 · 정렬 불가 헤더 — ✅ 정상, 버그 없음

`getComputedStyle`로 직접 확인: 기관명·생성일(정렬 가능)은 내부에 `<button>`이 있고
`cursor: pointer`. 기수·교육생·이번 달 AI 비용(정렬 불가)은 버튼 자체가 없고 `<th>`
직접 텍스트라 `cursor: auto` — 클릭 가능한 모양으로 안 보인다. 의도대로.

### C1–C4 · 검색어+상태필터 조합 — ✅ 정상, 버그 없음

실제 타이핑·클릭으로 확인. 검색어만(없는 이름) → `"OO"와 맞는 기관이 없습니다`(A4).
상태필터만(정지) → 2건. 검색어+필터 매치("블루"+정지) → 1건. 검색어+필터 불일치
("리부트"+정지, 리부트는 활성) → 0건이지만 문구는 여전히 검색어 기준 A4(`"리부트"와
맞는 기관이 없습니다`) — "아직 없다"로 잘못 말하지 않음. 정상.

### F10 · checking 중 제출 — ✅ 정상, 버그 없음

디바운스 창(400ms) 안에서 실제로 값을 바꾸고 그 직후 제출 버튼을 스크립트로 폴링해
"확인하는 중…" 문구가 뜬 순간 버튼을 클릭 — `disabled` 속성이 이미 `true`라 클릭이
아무 효과도 없었다(모달 안 닫힘, 요청 안 나감). `canSubmit`의 `nameCheck !== 'checking'`
가드가 실제로 작동.

### F11 · 모달 닫고 재오픈 — ✅ 정상, 버그 없음

이름 입력 → checking 진입(100ms, 400ms 타이머 살아있는 상태) → 취소 버튼으로 닫기 →
재오픈. 재오픈 시 이름 입력칸이 빈 값, 안내문이 기본 문구("다른 기관과 겹치지 않는
이름이어야 합니다")로 완전히 리셋됨 — 이전 이름의 검사 결과(확인 중/사용 가능 등)가
새지 않음. 코드 추적으로도 확인: `open` 이펙트가 매번 `nameCheck`를 `idle`로 강제
리셋하고, `name`이 그때 함께 초기화되며 디바운스 이펙트의 클린업이 이전 타이머를 취소한다.

### SA-02 갔다가 뒤로가기 — 🔴 실제 버그 발견 · ✅ 고침

**재현**: 검색어("테크") 입력 → SA-02 상세로 진입 → 브라우저 뒤로가기 → **검색어·상태
필터가 초기화됨**(빈 칸, "상태·전체"로 되돌아감). `OrgListScreen`이 라우트 전환마다
언마운트/리마운트되는데 검색어·필터·정렬·쪽 번호가 전부 `useState`뿐이라 복원할 곳이
없었다 — situations.md 1차에서 "적어만 두고" 안 눌러봤던 항목이 실제로 터졌다.

**고침**: `useSearchParams`로 전환해 **확정된(디바운스 끝난) 조건만** URL에
`replace: true`로 반영(`?q=&status=&sortKey=&sortDir=&page=`, 기본값은 파라미터
생략). 브라우저가 뒤로가기에서 URL을 그대로 복원해 주므로 마운트 시 URL에서 초기값을
읽기만 하면 된다. 타이핑 중간값이 아니라 `searchQuery`(디바운스 후 값)를 넣어 히스토리를
어지르지 않는다.

**검증**: 고침 전/후 렌더 스크린샷으로 재현·재확인. 고친 뒤: 검색어 "테크" 입력 →
URL이 `?q=테크`로 바뀜 → 상세 진입 → 뒤로가기 → URL이 `?q=테크`로 복원되고 화면도
검색어·필터링된 결과가 그대로 뜸. 상태 필터도 동일하게 확인(`?status=SUSPENDED`).

파일: `OrgListScreen.tsx` — `search`·`statusFilter`·`sort`·`page` 초기값을
`searchParams`에서 읽고, 확정값이 바뀔 때마다 URL에 반영하는 `useEffect` 추가.

### G8 · 정지+미배정 동시 — 🔴 실제 버그 발견 · ✅ 고침

**실제로는 이 조합의 기관이 없어**(경계 데이터 표) `page.route()`로 정지 기관 둘의
`operatorUnassigned`를 `true`로 만들어 재현(백엔드 데이터는 안 건드림 — 실제 15개
응답을 받아 그 필드만 수정해 돌려줌).

**재현된 것**: 배지는 우선순위대로 회색 "정지"만 뜨는데, **행 배경은 `bg-warning-soft`
(`rgb(251,243,230)`, 실측)로 주황 계열**이 켜지고, 이름 옆에 주황 "신규" 배지, 오퍼레이터
칸에 주황 "미배정" 텍스트까지 같이 떴다 — 회색 배지 하나와 주황 신호 셋이 동시에 다른
말을 하는 상태. situations.md가 예측했던 그대로.

**고침**: `orgStatusBadge`(labels.ts)의 우선순위(삭제됨 > 삭제 대기 > 정지 > 미배정 >
예산초과 > 활성)를 행 강조 로직에도 맞췄다. `const unassigned = org.operatorUnassigned`
→ `const unassigned = !dimmed && org.operatorUnassigned`(`dimmed = status !== 'ACTIVE'`).
정지·삭제대기·삭제됨 상태에서는 애초에 "미배정" 신호가 표에 안 뜬다 — 우선순위상 더 급한
배지가 이미 있으니까. 오퍼레이터 칸도 자동으로 실제 배정 목록(`formatOperators`)을
보여주게 됨(원래 미배정 텍스트로 가려져 있던 정보).

**검증**: 고침 전 `background-color: rgb(251, 243, 230)` → 고침 후
`rgba(0, 0, 0, 0)`(투명, 다른 행과 동일). 스크린샷으로 "신규" 배지·주황 텍스트도 사라진
것 확인.

### DELETION_PENDING · DELETED · G5 — ✅ 정상, 버그 없음(재현 확인)

같은 라우트 가로채기 방식으로 실제 15개 중 몇 건의 `status`·`deletedAt`을 바꿔 재현.

- 삭제 대기 + `deletedAt` 있음 → 배지 `삭제 대기 · 2026-09-29 파기`
  (`deletedAt: 2026-07-01` + `dataRetentionDays: 90` = 파기일 계산 정확).
- G5(삭제 대기인데 `deletedAt` 없음) → `삭제 대기`만, 파기일 없이. 크래시 없음.
- `DELETED` → `삭제됨`(neutral 배지). 정상.

### F5 · checkNameAvailability 네트워크 실패 — ✅ 정상, 버그 없음(1차 고침 렌더 확인 완료)

1차 세션에서 "격리 컨텍스트라 fetch 몽키패치가 안 먹혀 렌더 미확인"으로 남겼던 것을,
Playwright `page.route(url, r => r.abort('internetdisconnected'))`로 **진짜 네트워크
실패**를 만들어 확인했다. 이름 입력 → 요청이 실제로 끊김 → 안내문
`"중복 확인에 실패했습니다. 제출 시 다시 확인합니다."` 정확히 렌더됨(1차 세션에서 만든
`unknown` 상태). 제출 버튼은 도메인 칸이 비어 있어 비활성 상태(별개 이유) — 정상.

### 200% 확대 — ✅ 정상, 버그 없음

`documentElement.style.zoom = 2`로 확대 후 확인: 문서 레벨 가로 스크롤 없음(헤더·사이드바·
카드 안 겹침, 안 깨짐). 표 자체는 내부 컨테이너가 가로 스크롤을 가짐(`scrollWidth 772` vs
`clientWidth 455`) — 이건 팀 레이아웃 표준이 원하는 "표는 자기 컨테이너 안에서 스크롤"
그대로라 의도된 동작.

### 다크 모드 — 스코프 정정(테스트 대상 아님)

`src/index.css`에 **"다크 모드는 명세에 없다"고 명시돼 있고 `.dark` 블록 자체가
없다**(shadcn init 기본 다크 블록도 일부러 지운 상태 — 코드 주석 참조). `bg-warning-soft`의
다크 모드 대비는 애초에 물을 대상이 없다 — situations.md 1차가 이 항목을 다크 모드까지
포함해 적어 둔 것은 스코프 착오였다. **라이트 모드 대비만** 대신 실측: `bg-warning-soft`
위 "미배정" 텍스트(`#96631a`) 대비 `4.65:1` — WCAG AA(4.5:1) 통과. 기관명 텍스트는
`15.67:1`.
