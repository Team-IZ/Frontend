# 화면 정의서 작성 방법론 설계

## 배경

다음 4개 기획 문서를 근거로 화면 정의서(Screen Definition Doc)를 작성한다.

- `기능명세서_v8.xlsx` (시트 `04_기능명세(v8)`, FR 67개, P0 27 / P1 17 / P2 23)
- `요구사항정의서 (1).xlsx`
- `서비스플로우_v3.png` (역할×폐루프 단위 흐름도)
- `기술스택_선정서_v1 (1).md` (프론트: Vite 8 + React 19 + TS + shadcn/Base UI + TanStack Query/Table + Recharts, 모노레포 `manager-web` / `trainee-web` 분리)

리포지토리(`IZ-frontend`)는 `components.json` 기준 shadcn `base-nova` 스타일 + Base UI(Radix 아님)로 초기 스캐폴딩되어 있고, `src/components/ui`에 button/card/dialog/table/tabs/select/input/label/avatar/badge 10종만 존재하는 백지 상태다.

## 핵심 발견 — 방법론을 결정한 근거

기능명세서 v8의 `화면 흐름` 컬럼에 모든 FR이 이미 화면 ID(`SC-A01`, `SC-M01` 등)로 태깅되어 있고, 화면 간 전이(`SC-A02 → SC-A01`)까지 기록되어 있다. 또한 FR마다 예외 `case`가 6~10개씩 있어 이것이 곧 화면의 상태(로딩/빈상태/에러/권한없음) 정의 소스가 된다. 따라서 화면을 처음부터 상상해서 정의하지 않고, **기능명세에서 화면을 역추출하는 방식**을 택한다. 이렇게 하면 기능명세와 화면정의서 간 불일치가 구조적으로 발생하지 않는다.

## 방법론: 기능명세 역추출형 화면 인벤토리

1. 기능명세서 `화면 흐름` 컬럼을 파싱해 화면ID → FR 목록 역매핑 (완료: `fr_screen_map.csv` 스크래치 산출물 기준, 총 20개 화면 확인 — `SC-A01~03`, `SC-M01~12`(단 M05/M10/M12는 P1/P2 전용), `SC-S01`, `SC-T01/02/04/05` — v8 변경으로 `SC-T03`은 제외됨)
2. MVP단계(P0/P1/P2) 기준으로 작업 배치 확정. P0 FR을 하나라도 포함하는 화면 = 16개.
3. 화면정의서 표준 템플릿 확정 (아래)
4. IA/내비게이션 구조는 서비스플로우 v3 다이어그램의 역할×흐름을 뼈대로 사용
5. 화면별 정의서 작성 (배치 순서대로)
6. 화면별 저해상도 와이어프레임(Artifact HTML) 제작 — 기존 shadcn/Base UI 컴포넌트 재고에 맞춰, 없는 컴포넌트(차트, 히트맵, 스트리밍 세션 UI)는 별도 표시
7. 기능명세 case 전수가 화면 어딘가에 반영됐는지 체크리스트로 역추적

## 산출물 형태

화면 1개 = 마크다운 정의서 1개 + Artifact 와이어프레임(HTML) 1개.

### 화면정의서 템플릿

```
화면ID / 화면명 / 역할(권한) / 진입경로 / 연계 FR ID
목적 (1~2문장)
주요 데이터·컴포넌트
상태별 UI: 정상 / 로딩 / 빈상태 / 에러 / 권한없음 / (화면별 추가 상태 — FR의 case에서 추출)
인터랙션 (클릭 시 이동, 필터, 편집 등)
사용 컴포넌트 매핑 (기존 src/components/ui 중 무엇을 쓰는지, 신규 필요한 것은 무엇인지)
```

## 사용 도구/스킬

- `impeccable` 스킬 — 화면별 레이아웃·정보밀도·접근성 검토, 특히 대시보드/히트맵류
- `shadcn` 스킬 — `base-nova` + Base UI 레지스트리 일관성 유지하며 컴포넌트 추가
- `Artifact` 도구 — 화면별 브라우저 와이어프레임 렌더링
- `dataviz` 스킬 — ENG-02 시계열, DASH-14/15 히트맵 등 시각화 화면

- 와이어프레임: Artifact로 발행, 정의서 내 링크로 연결
