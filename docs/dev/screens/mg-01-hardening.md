### 1. 브리프 90초 무응답 — `?state=`를 안 넘겼다

사용자 보고("5차에서 브리프 열기를 눌렀더니 답변이 안 왔다")로 시작했다.

브리프 화면은 `?state=`로 **「`GET`할지 `POST`로 만들지」**를 가른다. 없으면 있다고
보고 `GET`하는데, **없는 브리프의 404는 브라우저에서 무응답**이라(30차 R1) 90초를
기다렸다 실패로 떨어진다. MG-03 목록은 넘기고 있었는데 MG-01만 빠져 있었다.

**5차는 대기 4건이 전부 `NONE`이라 매번 그렇게 됐다.**

```
briefState=NONE → GET 404 0.6초(서버 직접) / 브라우저에서는 무응답
2차 {FAILED 2, NONE 3}   3차 {DRAFT 1, FAILED 1, NONE 5}
4차 {NONE 6, FAILED 1, CONFIRMED 1}   5차 {NONE 4}   6차 {NONE 1}
```

고친 뒤 **0.67초**에 「아직 브리프가 없습니다 · [브리프 만들기]」로 간다.

> ⚠ 처음에 **`FAILED`를 막아 뒀다가 되돌렸다.** 실측하면 `FAILED`는 오히려 200으로
> 내용이 오고 `NONE`이 404다. **반대로 알고 막고 있었다** — 게다가 브리프 화면은
> `NONE`·`FAILED` 둘 다 [브리프 만들기]로 받아 주므로 막으면 만들 길까지 막는다.

### 2·3. `PLANNED` 프로젝트

`class-progress`에 `keepPreviousData`가 붙어 있어 「11」을 골라도 **14초 뒤까지
미프 6차의 `제출 21/26`**이 붙어 있었다. 프로젝트마다 대상이 다른 값이라 옛 값은
위로가 아니라 거짓말이다 — 이 조회만 뺐다.

그러자 이번엔 화면이 통째로 스켈레톤이 되면서 **프로젝트 선택기까지 사라졌다.**
이 조회가 실제로 매달리는데(18초 무응답) 되돌아갈 컨트롤이 없으면 새로고침
말고는 길이 없다. `runPending`을 따로 내보내 **select는 남기고 숫자 자리만** 비운다.

### 4. 밴드가 조용히 빠졌다

명부가 5~6초라 도착 전에 목록을 완성된 것처럼 그렸다 — **2차가 8건 → 7건**으로
보였고 「응시 못 한 사람」 밴드가 통째로 없었다. 넷이 다 올 때까지 목록 자리를
스켈레톤으로 둔다(`itemsPending`).

> **부분을 전부인 척 보여주는 것이 비어 보이는 것보다 나쁘다.**

### 5. 머리가 옛 건수를 말했다

컨트롤 전수에서 잡았다 — `PLANNED`로 바꾸면 본문은 스켈레톤인데 머리는 직전
프로젝트의 「2건」을 계속 말했다. 목록 조회들이 옛 값을 들고 있어서다.
아직 오는 중이면 **개수를 안 적는다**(규칙 D).

### 6. 무효 행에만 반이 없었다 — **요청서로 갈 뻔했다**

다른 행은 `C반`이 붙는데 무효 행만 이름뿐이었다. signals가 `classroomId`만 주고
`className`을 안 줘서인데, **담당 반 목록은 이미 받아 두고 있다**(`cohortScope`가
기수를 정하는 순간 미리 받는다). 판정 ①에서 끝났다 — 콜도 안 늘었다.

부수 효과로 **[면담 목록에서 확인]의 반 필터도 고쳐졌다** — `className`이 `null`이라
쿼리에 안 실려 면담 목록이 「반 · 전체」로 열리고 있었다.

### 7. 반 필터에 **이름을 보내고 있었다** — 5명이 전부 그 반인데 0행

무효 응시 행의 [면담 목록에서 확인]을 누르면 회차·반이 미리 걸린 면담 목록이
열려야 한다. 회차는 맞았는데 **반이 이름(`C반`)으로 나갔다.** 목록 화면의
`?class=`는 **그대로 `classId`로 서버에 나간다**(`InterviewListScreen.tsx:130`).

```
고치기 전  ?round=…&class=C반   → 필터는 「반 C반」으로 보이는데 **행 0**
고친 뒤    ?round=…&class={UUID} → 행 5 ✅
```

목의 판단 기록이 **정확히 이 경우를 경고하고 있었다** — 「걸어 둔 필터가 실제로
그 사람이 뜨는 회차·반과 다르면 "빈 목록"이라는 오히려 더 나쁜 결과가 된다」.
목에서는 `roundId`만 맞춰 두고 반은 이름을 쓰고 있었는데, 목 데이터에서는
반 필터가 이름으로도 걸려서 안 드러났다.

**필터를 미리 거는 링크는 「보이는 값」이 아니라 「나가는 값」으로 만든다.**

### 8. 프로젝트 스코프를 주소로 옮겼다 — 규칙 J

세션 메모리(`viewState.ts`)에 있었다. 규칙 J대로 `?project=`로 옮기고 그 파일을
지웠다. 원래 세션 메모리를 만든 이유가 **「브리프를 열었다 뒤로가기로 돌아오면
보던 회차가 리셋된다」**였는데, 주소에 두면 그 문제가 저절로 없어진다 —
게다가 딥링크·새로고침까지 따라온다.

`replace: true`를 쓴다 — 프로젝트를 바꾼 것은 다른 화면으로 간 것이 아니라 같은
화면의 범위를 바꾼 것이라, 뒤로가기가 바꾼 횟수만큼 걸리면 안 된다.

> 같은 패턴이 `heatmap/viewState.ts`에도 있다 — 이 화면 범위 밖이라 안 건드렸다.

### 10. 주소의 프로젝트가 **없는 것이면 멈춰 있었다**

규칙 J가 「URL 값이 목록에 없으면 기본값으로 떨어진다」고 경고하는데, 8번에서
주소로 옮기면서 그 판정을 안 넣었다.

```
/manager/dashboard?project=00000000-0000-0000-0000-000000000000

고치기 전  선택기에 「00000000-0000-0000-0000-000000000000」이 그대로 뜨고
           본문은 끝없이 스켈레톤 — 없는 id의 class-progress가 무응답이라
           영원히 안 끝난다
고친 뒤    진행 중 프로젝트로 떨어진다 ✅
```

⚠ **목록이 아직 없을 때는 판정을 미룬다** — 빈 목록으로 지우면 프로젝트가
도착하기 전에 주소 값이 날아간다.

## 2단계 · 응답을 가로채 이상 상황을 만든다 — 결함 넷

정상 데이터로는 안 나오는 상태를 만들었다. **조회 다섯을 각각** 500으로, 명부는 403도.

```js
const hit = (re) => (u) => re.test(new URL(u).pathname)   // 경로로만 가른다
await p.route(hit(/\/trainees$/), r => r.fulfill({ status: 500, … }))
```

> ⚠ **경로로만 가른다.** 전에 `**/sections**` 같은 글롭을 썼다가 앱 자산까지 잡아
> 페이지가 통째로 죽었다. `new URL(u).pathname`을 정규식으로 본다.

### 11. 🔴 조회 하나가 죽으면 **화면 전체가 에러**였다

signals 하나만 500인데 **멀쩡한 22건이 통째로 사라졌다.**

`async-states` §3-5가 정확히 이 경우를 규정한다 — 「**그 줄만** 유형 3 톤으로 표시한다.
전체를 실패 화면으로 덮으면 멀쩡한 데이터까지 못 본다」.

**목이 이미 이 구조였다.** `mockData.ts`의 `bandTwoFailed`가 「확인이 필요한 것 밴드만
로드 실패」를 위한 자리였는데, 연동하며 없애고 어댑터 주석에 **「하나라도 실패하면
실패다」라고 반대로 적어 뒀다.**

축과 행을 갈랐다.

```
축   projects · class-progress   죽으면 프로젝트를 못 고르고 회차를 모른다 → 전체 실패
행   trainees   → 밴드 1          죽어도 나머지 밴드는 그린다 → 그 자리에만 실패 줄
     signals    → 밴드 2
     interviews → 밴드 3
```

밴드 4(미제출·분석 실패)는 원천이 곧 축이라 여기 안 온다.

### 12. 🔴 실패 문구가 **원인을 안 보고 있었다**(규칙 I)

밴드 실패 줄을 처음에 이렇게 하드코딩했다.

```
「{밴드 이름}을(를) 불러오지 못했습니다」 + [다시 시도]   ← 무조건
```

**403 `MANAGER_SCOPE_NOT_FOUND`에도 「다시 시도」가 그려졌다.** 담당 밖 자원이라
다시 눌러도 같은 답인데, 규칙 I가 막으려던 바로 그 화면이다.

`failedBands`가 `true`가 아니라 **그 조회의 에러를 그대로** 담게 하고, 화면이
`errorCopy`에 넘겨 문구·톤·재시도 여부를 받는다. 덤으로 조사 문제(`사람을(를)`)도
사라졌다 — `errorCopy`가 `withParticle`로 이미 붙인다.

### 13. 🟠 실패 화면인데 **머리가 개수를 말했다**

진행 줄이 500인데 머리는 「대시보드 **1건**」이었다. `count`가 `shell()` 안에 있어
실패 분기에서도 그려진다 — `!inbox.isError`를 조건에 넣었다.

> ⚠ **이 수정은 한 번 조용히 실패했다.** `python replace`로 한 줄짜리 형태를 찾았는데
> prettier가 이미 여러 줄로 접어 둔 뒤라 매치가 안 됐고, **아무 일도 안 일어난 채
> typecheck는 통과**했다. 다음부터 치환은 `assert`로 확인한다.

### 14. 🟠 문구가 깨져 있었다 — 「불러오기하지 못했습니다」

`errorCopy(err, { subject, action })`의 `action`은 **어간**을 받아 `${action}하지`로
붙는다(「삭제」→「삭제하지」). 「불러오기」를 넘겨서 「불러오기하지」가 됐다.
빼면 기본이 「불러오지 못했습니다」다.

## 값의 빈 구석 — **7종 전부, 결함 없음**

실데이터에 없어서 가로채기로 만들었다.

```js
for (const c of d.items)  { c.riskSummary = null; c.briefState = null; c.className = null }
d.submissionDueAt = null
for (const t of c.failedTeams) { t.failureReason = null; t.representativeName = null }
for (const a of pr.actionItems) if (a.type === 'UNSUBMITTED_TEAMS') a.teams = []
```

| 비운 값 | 화면 |
|---|---|
| `riskSummary: null` | 「면담 대기」 기본 문구 ✅ |
| `briefState: null` | [브리프 열기] — `?state=` 없이 가고 브리프 화면이 404를 받아 [만들기]로 잇는다 ✅ |
| `className: null` | 이름만 · 반 자리가 **빈 채로 남지 않는다** ✅ |
| `failureReason: null` | 「저장소를 확인하고 다시 제출해야 합니다」 ✅ |
| `representativeName: null` | 「이름 제출 · 」 앞부분이 통째로 빠진다 ✅ |
| `submissionDueAt: null` | **제출 마감 줄이 사라진다** — `· ` 구분자만 남지 않는다 ✅ |
| `teams: []` | 「C반 · 1팀이 아직 제출하지 않았습니다」로 접힌다 ✅ |

## 접근성 · 키보드 — 결함 하나

### 정상

```
Tab 순서   프로젝트 select → 교육생 이름 → [브리프] → [프로젝트에서 보기]
포커스 링   전부 outline 2px — 없는 것 0개
```

`:focus-visible` 전역 규칙(`index.css`)이 그대로 먹는다.

> ⚠ **`.focus()`로 재면 안 잡힌다** — `:focus-visible`은 입력 방식 휴리스틱을 타서
> 스크립트 포커스에 항상 매치되지 않는다. **`keyboard.press('Tab')`**으로 잰다
> (D34에서 같은 함정에 걸렸던 기록이 있다).

### 15. 🔴 목록에 **시맨틱이 하나도 없었다**

```
전   div(밴드 라벨) + div(행) + div(행) …   →  role=list 0 · listitem 0
후   section aria-label="면담 대기 1건"
       h2 밴드 이름
       ul > li × N                          →  role=list 2 · listitem 2 ✅
```

인박스는 **목록**인데 스크린리더에는 `div` 더미였다 — 「몇 건 중 몇 번째」를 못 읽고
밴드 경계도 안 읽힌다. 밴드 이름에 **건수를 넣었다**: 시각 사용자는 행을 세어 알지만
스크린리더 사용자는 그렇지 못하다.

> ⚠ 첫 측정에서 `section 0 · ul 0 · li 0`이 나와 **수정이 안 먹은 줄 알았다** —
> 화면이 덜 뜬 상태였다(본문 길이 211자). 「행이 하나라도 있나」로 기다린 뒤 다시
> 재서 확인했다. 13번과 같은 함정이라 **측정 스크립트를 먼저 의심**했다.

부분 실패(11번) 수정 때 붙인 의존성 6개가 **조용히 안 들어갔다**(13번과 같은 유형 ·
prettier가 접어 둔 형태를 못 찾았다). `assert`로 확인해 다시 넣었다.

**넘치지 않고 세로로 늘어난다.** 실데이터의 `riskSummary`는 「개념 3건 전부 2단 이하 ·

못 읽는데, 인박스는 그 사유를 보고 누구부터 처리할지 정하는 화면이다).

## 시간·타이밍 — 결함 없음

`formatDateTime`이 `getHours()`(로컬)를 쓰므로 UTC→KST 변환이 자동이고 자정도 함께 넘어간다.

```
서버 2026-03-23T14:59:00Z  →  화면 03-23 23:59   ✅
서버 2026-03-23T15:00:00Z  →  로컬 03-24 00:00   ✅ 날짜가 같이 넘어간다
```

상대 표현(「오늘」·「어제」)이 이 화면에 없다 — 목의 `checkedLabel`이 그것이었는데
체크 버튼과 함께 걷어냈다. 렌더할 때마다 값이 바뀌는 자리가 없다.

> ⚠ **연도가 없다**(`03-23 23:59`). 지금 9기는 같은 해 안이라 안 드러나지만, 기수가
> 해를 넘기면 「03-23」이 언제인지 모른다. **전 화면 공통 포맷**이라 이 화면에서만
> 바꾸면 일관성이 깨진다 — 화면 범위 밖으로 남긴다.
