# TR-03 검증 세션 (코드 분석) — 확정 규칙

> **출처:** 2026-08-11 백엔드 논의 + 2026-08-12 사용자 확인(예시·시간·재시험 규칙).
> **이 문서가 최신이다.** `docs/plan/v1/definition/SC-T04-verification-session.md`(정의서)는
> L1~L3 3단·SURFACE/PARTIAL/DEFENDED를 쓰는데 아래 규칙이 그것을 대체한다.
>
> 화면 구현(`src/features/trainee/session/`)은 **아직 옛 모델**이라 아래와 여러 곳이 다르다(3절).

## 1. 보고된 결함

> **답변을 엉터리로 써도 힌트가 나오지 않고, 다음 질문으로 넘어가는 오류.**

우리 목도 같은 증상을 그대로 재현한다 — `session/api.ts`의 `submitAnswer()`가 답변 내용을
보지 않고 `script.ts`에 박힌 턴 인덱스로 결과를 정한다. **판정에 점수가 실려 와야** 사라진다.

## 2. 확정 모델

### 2-1. 구조 — 세션 1 : 개념 3 : 단계 4 : 시도 3

```
세션(sessionId)
 └ 개념(문제) 3개 고정          예) REST 설계 · 예외처리 · DTO 분리
    └ 단계 4개 (L1~L4)          질문 하나가 단계 하나
       └ 시도 최대 3회           답변 + 힌트1 후 답변 + 힌트2 후 답변
```

| 단계 | 무엇을 묻나 |
|---|---|
| 1단 | 코드이해 |
| 2단 | 설계논리 |
| 3단 | 대안비교 |
| 4단 | 반례대응 |

**최대 36 답변**(3 × 4 × 3)이 나온다. 이 규모가 시간 설계의 근거다(2-4).

### 2-2. 채점과 힌트 — 한 단계 안에서 도는 고리

```
질문(L4) → 답변① 1점  미달 → 힌트1
         → 답변② 1점  미달 → 힌트2
         → 답변③ 2점  미달 → 이 개념 종료, 다음 개념으로
                    3점↑ → L4 통과
```

- **점수 0~5점 · 3점 미만이면 실패**
- **힌트는 점수 3점 미만일 때 제공 · 질문당 최대 2개**
- **힌트 2개를 다 쓰고도 3점 미만이면 그 단계에서 종료** → 다음 개념

> **힌트 2개 = 재시도 기회 2개다.** 그래서 한 단계의 최대 시도가 3회이고, 예시의
> *"L4에서 1점, 1점, 2점"* 이 점수 세 개인 이유가 이것이다.

**힌트가 나오는 길은 둘이다.**

| | 언제 | 지금 코드 |
|---|---|---|
| ① 학생이 요청 | [다시 설명해 주세요] 버튼 | ⭕ 있다 (`REQUEST_HINT`) |
| ② 점수 미달로 지급 | 채점 결과 3점 미만 | ❌ 없다 — 새로 붙는다 |

버튼은 **그대로 남는다.** 남은 개수는 두 경로의 합산이며 **서버가 세 준다** — 화면이 세면
지급분이 빠진다(지금 `currentHintUsed`가 버튼만 센다).

### 2-3. 도달 단계 — 마지막으로 통과한 단계

**0~4단, 5단계다.** 스펙에도 백엔드가 🔴로 적어 뒀다 — *"도달 단계는 4단이 아니라 5단(0~4)."*

| | 통과 | 실패한 단계 | 도달 |
|---|---|---|---|
| A문제 | L3까지 | L4 | **3단** |
| B문제 | L2까지 | L3 | **2단** |
| C문제 | L1까지 | L2 | **1단** |
| — | 없음 | L1 | **0단** |

> ⚠️ **"2단에서 종료되면 1단으로 취급"은 별도 보정 규칙이 아니다.** 위 표의 C가 그것이고,
> **도달 단계 = 마지막으로 통과한 단계**라는 정의에서 자동으로 나온다. 보정 로직을 따로
> 만들면 안 된다.

**`0단`과 `문항 없음`은 다르다.** 서버가 엄격히 가른다.

| | 뜻 |
|---|---|
| `0단` | **물었는데 못함** (L1 실패) |
| `문항 없음`(unasked) | **묻지 못함** — 확정된 개념이 그 학생 코드에 없어 문항이 안 만들어짐 |

*"코드에 이 개념이 없어 묻지 못했습니다 — **못한 것이 아닙니다**"* 가 매니저 화면이 이미 쓰는
문구다. **교육생 리포트에도 이 자리를 만든다**(확인받음).

### 2-4. 시간 — 세션 60분 · 문제당 20분

| | 값 |
|---|---|
| 세션 전체 | **1시간** |
| 문제(개념) 하나 | **20분** |

예시의 *"L3에서 2점, 2점, 시간초과로 실패"* 가 **문제당 20분 초과**다 — 시간초과도 그 시도의
실패로 처리되고, 그 시점의 마지막 통과 단계가 도달 단계가 된다.

> 3 × 20분 = 60분이라 두 상한이 정확히 맞물린다. **문제당 남은 시간이 다음 문제로 이월되는지는
> 미확정** — 이월 없이 각 20분 독립으로 보고, 세션 60분은 안전망으로 둔다(5절에서 물었다).

### 2-5. 재시험(다시 보기)

> **2026-08-12 사용자 확인으로 전부 확정됐다.** `14-verification-design.md` §11과
> 갈리던 넷(대상·문항·힌트·창 기산점)의 답이 아래다 — 그 문서가 옛 것이다.

| | |
|---|---|
| 대상 | **불합격 개념만** = 도달 **2단 미만**(0·1단) ✅확정 — 14번의 「2단 이하」가 아니다 |
| 문항 | **같은 문항** ✅확정 |
| 범위 | 그 개념을 **L1부터 4단계 전부** 다시 |
| 힌트 | **없음 — 자력만** ✅확정 (아래 5절 열린 질문 해소) |
| 창 | **리포트 발행 후 3일 또는 다음 회차 제출일 중 빠른 쪽** ✅확정 — 고정값, 설정하지 않는다 |
| 횟수 | **1회만** |
| 결과 | 원점수를 **바꾸지 않는다** — 기록에만 남는다 |
| 리포트 | **재시험 결과도 교육생이 볼 수 있어야 한다** |
| 문항 없음 개념 | **재시험 대상 아님** — 표시만 한다 |

**창의 기산점이 리포트 발행인 이유**(2026-08-12 판단):

- 재시험은 **리포트가 있어야 성립한다** — 대상(0·1단)이 채점 결과에서 나오고 학생은
  리포트의 교안 위치를 보고 공부한다. 14번이 3일을 둔 근거 자체가 *"리포트를 읽고
  교안을 다시 보는 최소 시간"* 이다.
- 제출 마감 기준이면 **창이 역전된다** — 응시 창이 개인별(코드 분석 완료 +24h)이라
  마감 직전 제출자는 분석·응시에만 하루 이상 쓴다. 제출 마감 +3일로 자르면 응시가
  끝나기 전에 재시험 창이 닫히는 학생이 나온다.
- TR-04와 맞물린다 — `SUMMARY`는 재시험 전 임시 상태이고 재시험 후 `FULL`이 된다.
  리포트가 먼저 존재해야 이 전이가 성립한다.

**대가** — 리포트 발행일이 확정 날짜가 아니라(전원 응시 완료를 기다린다) 화면이
「며칠에 닫힌다」를 못 쓴다. **상대 표현으로 쓴다**(「리포트 발행 후 3일」) — 없는
날짜를 지어내지 않는다. OP-04 개요 타임라인이 그렇게 그린다.

**길이는 설정값이 아니다**(2026-08-12 확정). 오퍼레이터·매니저 누구도 안 바꾼다.
검토했다가 뺀 안 둘 — ⓐ 기수별 설정: 실효 구간이 좁다(9기 실측 마감 간격이 3·11·24·38일이라
컷이 먼저 걸리거나 길이가 무의미하다) + 오퍼레이터가 회차마다 판단할 거리만 는다.
ⓑ 주말 흡수용 5일: 연속 5일이면 평일 3일이 보장돼 「영업일 3일」의 싼 구현이 되지만,
**3일로 못 박는 쪽을 골랐다** — 재시험은 판정에 반영되지 않아(14번 §11) 창 길이가
성적을 좌우하지 않는다.

> ⚠ **`14-verification-design.md` §11의 「자동 지정 + 매니저가 발송 버튼을 누른다」는
> 기능 범위 밖이다**(2026-08-12 확인). 독촉·발송 기능이 없으므로 창은 **리포트 발행에서
> 자동으로 열린다.** 그 줄을 근거로 설계하지 말 것.

예시로: A(3단)·B(2단)는 대상이 아니고 **C(1단)만 재시험**, C를 L1부터 다시 본다.

> ⚠️ **지금 구현·목업은 정반대다.** `TransitionScreen`이 *"지난번에 막혔던 질문 하나씩만 봐요 ·
> 더 깊은 질문으로 이어지지 않아요"* 라고 하고 `RETRY_SCRIPT`도 그렇게 짜여 있다.
> **막혔던 질문 하나가 아니라 그 개념 전부를 처음부터** 다시 본다.

> **서버 집계는 원점수를 쓴다.** 위험자(`3건 중 2단 이하 2개 이상`)·집단 미달·기수 비교가
> 전부 첫 응시 기준이다.

## 3. 지금 코드와의 차이

| | 지금 (`src/features/trainee/session/`) | 바뀌어야 하는 것 |
|---|---|---|
| 개념 수 | `script.ts` 3문제 | ⭕ **맞다** |
| 단계 | `LadderLevel = 1\|2\|3\|4` | **`0` 추가** (`--color-reach-0`은 이미 있다) |
| 단계당 질문 | 개념당 턴 2~3개, 단계와 1:1이 아님 | **단계 = 질문 1개**, 개념당 최대 4단계 |
| 시도 | 한 턴에 **1회 제출** | **최대 3회** (힌트 사이에 낀다) |
| 점수 | **없다** | 시도마다 **0~5점** |
| 힌트 트리거 | `REQUEST_HINT` 하나뿐 | 버튼 유지 + **제출 응답이 힌트를 싣고 온다** |
| 힌트 카운트 | 화면이 센다 | **서버가 센 값**을 쓴다 |
| 종료 판정 | `hintExhaustedOutcome`이 목에 박힘 | **점수로 판정** |
| 도달 단계 | 없음(리포트에만) | 세션이 개념마다 확정해 넘긴다 |
| 문항 없음 | **없다** | 개념이 3개 미만으로 올 수 있다 |
| 시간 | 70분 하드캡 · 60분 예고 | **세션 60분 + 문제당 20분** — 문제당 카운트다운 필요 |
| 재시험 범위 | 막혔던 질문 하나씩 | **그 개념 L1부터 전부** |
| 재시험 횟수 | 제한 없음 | **1회만** |

**상태 머신(`sessionReducer.ts`)은 뼈대가 남는다.** `INTRO → IN_PROBLEM ⇄ WAITING_NEXT →
TRANSITION → ENDED`는 그대로 쓰고, 바뀌는 것은 ① `APPLY_SUBMIT_RESULT`가 `score`와 지급된
힌트를 함께 받는 것 ② 같은 질문에 다시 답하는 경로(지금은 답하면 무조건 다음으로 간다)
③ 문제당 타이머 추가다.

**`ComposeBar`의 버튼은 남지만 `N번 남음`이 서버 값이어야 한다** — 지급으로 2개를 다 쓴
학생에게 "2번 남음"이라고 표시되면 안 된다.

## 4. 막힘 — 붙일 API가 없다

세션 엔드포인트가 스펙에 **하나도 없다**(2026-08-12 `api:pull`, 96개 전수 확인).
문제 조회·답변 제출·채점·힌트가 전부 없다. 위 규칙은 **목 안에서만** 반영할 수 있다.

계약 제안은 [16차 요청서 R3](../backend/backend-api-requests-16.md)으로 보냈다.

## 5. 남은 확인

- **문제당 20분이 이월되는가** — 15분에 끝내면 남은 5분이 다음 문제로 가나, 아니면 각 20분 독립인가
- **시간초과가 시도 하나의 실패인가 그 개념의 종료인가** — 예시의 B는 3번째 시도가 시간초과라
  둘이 같은 결과였지만, 1번째 시도에서 시간초과면 갈린다
- ~~**재시험에도 힌트가 있는가**~~ — ✅ **없다. 자력만**(2026-08-12 확인). 지금 화면이
  이미 그렇다(`mode === 'FIRST'` 조건) — 그대로 둔다
- **재시험 중 시간 규칙** — 개념 1개만 보면 20분인가
