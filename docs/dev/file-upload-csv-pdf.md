## 1. 명단 CSV — 넓어졌습니다

### 무엇이 문제였나

백엔드가 **29차 회신에서 CSV 파서를 넓혀 배포**했는데, **화면이 여전히 옛 규칙으로 막고
있었습니다.** 서버는 받는 파일을 화면이 거절하고 있었던 것입니다.

가장 흔한 경우가 막혀 있었습니다 — **윈도우 엑셀에서 「CSV(쉼표로 분리)」로 저장하면
CP949**입니다.

```
번호,이메일,소속,이름   (CP949)
  서버  200 ✅
  화면  ✗ "UTF-8이 아님 — 엑셀에서 「CSV UTF-8」로 다시 저장해 주세요"
```

### 지금 규칙

**`이름`·`이메일` 열이 있기만 하면 됩니다.**

| | |
|---|---|
| 인코딩 | UTF-8 · **CP949**(엑셀 기본 저장) |
| 열 순서 | **상관없음** |
| 다른 열 | **있어도 됨**(`번호`·`소속` 등은 무시) |
| 머리글 공백 | `이름, 이메일`처럼 쉼표 뒤 공백 OK |
| 막는 것 | 두 열 중 하나라도 **없음** · 이름 칸이 **빈 행** |
| 인원 | 한 번에 **1000명**까지 |
| `.xlsx` | **안 받습니다** — 「엑셀은 CSV로 저장해 주세요」 |

### 화면과 서버가 같은 판정을 하는지 — 6종 전부 확인

같은 파일을 화면과 서버 `preview`에 각각 넣어 비교했습니다.

| 파일 | 화면 | 서버 |
|---|---|---|
| `이름,이메일` UTF-8 | ✓ 유효 1명 | `registrableCount: 1` |
| `번호,이메일,소속,이름` **CP949** | ✓ 유효 2명 | `registrableCount: 2` |
| `이메일,이름` (순서 바뀜) | ✓ 유효 1명 | `registrableCount: 1` |
| `이름, 이메일` (공백) | ✓ 유효 1명 | `registrableCount: 1` |
| 이름 열 없음 | ✗ 파일 오류 | `400 CSV_FORMAT_INVALID` |
| 이름 빈칸 | ✗ 2행 | `400 TRAINEE_NAME_INVALID` |

**6/6 일치** — 화면이 통과시킨 것은 서버도 받고, 막은 것은 서버도 막습니다.

### 만진 곳

| 파일 | 무엇 |
|---|---|
| `admin/_/rules.ts` | 머리글을 **이름으로 찾음**(순서·개수 무관) · 칸 `trim()` |
| `admin/_/components/RosterCsvField.tsx` | UTF-8 실패 시 **CP949로 읽음**(둘 다 `fatal`) · 안내 문구 |
| `admin/_/labels.ts` | 실패 문구 2개 |
| `scripts/check-admin-rules.mts` | **가드가 옛 규칙을 지키고 있어서** 같이 고침 + 케이스 2개 |

> **정규화는 안 합니다.** 미리보기만 화면이 읽고, 서버로는 **고른 파일이 원본 그대로**
> 갑니다. 우리가 UTF-8로 다시 인코딩해 보낼 필요가 없습니다.

## 2. 교안 PDF — 4.5MB가 천장입니다

### 왜 4.5MB인가 (6MB가 아니라)

백엔드 앞에 **AWS Lambda Function URL**이 있고, 그 플랫폼 한도가 **요청 6,291,456바이트**
입니다. Lambda가 바이너리 본문을 **base64로 감싸서**(×4/3) 넘기므로 실을 수 있는 바이트는
그 **3/4**입니다.

```
6,291,456 × 3/4 = 4,718,592 B = 4.5 MiB
```

여기서 multipart 경계·헤더·파일명 몫을 더 뺍니다. **이분 탐색 실측**:

```
4,715,625 B  →  통과
4,717,187 B  →  413
```

약 3KB가 부대 비용이고, **4KB는 그보다 넉넉하게 잡은 값**입니다. 파일명 길이도 재
봤는데(5B vs 93B) 이 근처에서 결과를 안 바꿨습니다 — 즉 이 여유는 계산으로 딱 맞춘 것이
아니라 **경계에 붙지 않으려고 일부러 남긴 것**입니다.

대가는 4.5MB 바로 아래 **1.5KB쯤 되는 구간이 화면에서만 막히는 것**입니다(서버는 받습니다).
4.5MB 중 0.03%라 무시했습니다 — 반대쪽 대가(경계를 넘겨 잡아 **사용자가 413을 보는 것**)가
훨씬 나쁩니다.

화면 상한은 계산값이고, 사람에게 보이는 「4.5MB」도 **같은 상수에서 나옵니다** — 손으로
적지 않아 어긋날 수 없습니다.

> 스펙도 같은 말을 합니다 — *"본문이 base64로 부풀어(×4/3) 실질 4.5MB에서 막히는 것이라
> **앱이 손댈 수 있는 층이 아니고**, presigned S3로 그 층을 비켜가는 것이 답이다."*

### 이 실패는 스펙에 없습니다

`POST /curricula`의 응답 목록은 `201 · 400 · 401 · 403 · 409 · 503`입니다 — **413이 없습니다.**
**앱 코드에 닿기 전에 잘리기 때문**이고, 그래서 응답 몸통도 우리 `{code, message}`가 아니라
AWS 형식입니다.

```json
{"Message": "Request must be smaller than 6291456 bytes for the InvokeFunction operation"}
```

`code`가 없으니 `errorCopy`가 가를 수 없습니다 — **상태 코드(413)로 직접 가릅니다.**

### 화면이 지금 하는 일

```
전:  8MB 등록 → 413 → "등록하지 못했습니다. PDF 파일인지 확인해 주세요."
후:  8MB 고름 → "이 파일은 8.0MB로 4.5MB를 넘습니다 — 나눠서 올리거나 용량을 줄여 주세요."
                등록 버튼 잠김 · 요청 0건
```

전에는 **멀쩡한 PDF를 의심하게 만들어**, 사람이 파일을 다시 저장하거나 다른 파일을 찾는
헛일을 하게 했습니다. 진짜 할 일은 「쪼개기·압축」입니다.

**상한은 평소에 안 씁니다** — 넘겼을 때만 **자기 파일 크기와 함께** 말합니다. 얼마인지
알아야 얼마나 줄일지 판단할 수 있습니다.

> ⚠ **서버 413도 계속 처리합니다.** 화면 검사는 *"어차피 실패할 요청을 안 보낸다"* 는 것이지
> 마지막 방어선이 아닙니다 — 파일명이 길면 경계 근처에서 서버까지 갑니다.

### 실제 파일로 확인

로컬 `~/Downloads`의 「교안」 PDF 7개 중 둘을 화면에서 눌렀습니다.

| 파일 | 크기 | 결과 |
|---|---|---|
| `AI_BackEnd_교안.pdf` | **6.88MB** | 🚫 차단 · 요청 **0건** |
| `AI_미니프로젝트 5·6차_교안.pdf` | 2.08MB | ✅ 201 등록 |

나머지 4개(1.91~2.37MB)도 통과 크기이고, **`AI_클라우드 현대화 이해 서비스_교안.pdf`
(8.50MB)는 차단 대상**입니다.

### 만진 곳

| 파일 | 무엇 |
|---|---|
| `api/uploadLimits.ts` **(신규)** | 상한 계산 · `tooLargeToUpload()` · 표시 문구 |
| `curricula/components/RegisterCurriculumDialog.tsx` | 고른 순간 차단 · 413 문구 · 아래 버그들 |
| `scripts/check-admin-rules.mts` | 상한이 실측 경계 안에 있는지 CI가 검산 |

> **상한을 `api/` 아래에 둔 이유** — 이것은 **교안의 규칙이 아니라 전송 경로의 한계**입니다.
> PDF든 CSV든 ZIP이든 같은 문을 지납니다. 교육생 코드 제출(ZIP)도 나중에 같은 벽을 만납니다.

## 3. 눌러 보고 나온 버그 — 6건

전부 **코드만 봐서는 안 나오고 화면을 직접 눌러야** 나온 것들입니다.

| | 무엇 | 왜 나빴나 |
|---|---|---|
| 🔴 1 | 4.5MB 초과 → *"PDF 파일인지 확인해 주세요"* | 멀쩡한 파일을 의심하게 만든다 |
| 🔴 2 | 제목 중복(409) → **같은 문구** | 고칠 곳이 제목인데 파일을 보게 한다 |
| 🔴 3 | 제목을 **고치는 중에도** 빨간 표시가 남음 | 고쳐도 안 된다는 뜻으로 읽힌다 |
| 🔴 4 | CSV 실패 배너가 **직접 입력 탭까지** 따라감 | 그 탭엔 아무것도 안 넣었는데 실패가 떠 있다 |
| 🔴 5 | 그 배너가 **닫았다 열어도** 남음 | 빈 화면에 실패 문구만 남는다 |
| 🔴 6 | 등록 직후 *"분석을 시작하지 못했습니다"* | **뒤 목록은 이미 「분석 중」** — 아래 참고 |

### 6번이 특히 위험했습니다

**서버가 등록과 동시에 분석을 시작하게 바뀌었습니다**(실측: `201` 직후
`analysisStatus: PENDING`). 우리가 이어 붙인 `POST /analyses`가 `409
CURRICULUM_ANALYSIS_IN_PROGRESS`로 튕기는데, 화면이 그걸 **실패로 읽었습니다.**

```
화면:  "분석을 시작하지 못했습니다. 목록에서 다시 분석을 눌러 주세요."
목록:  분석 중                ← 이미 돌고 있다
```

시킨 대로 「다시 분석」을 누르면 **`?force=true`가 나가 돌고 있는 분석을 버리고 처음부터
다시** 돌립니다. **없는 문제를 알리고, 그 해결책이 실제로 해를 끼치는 자리**였습니다.

→ 그 409만 **성공으로 칩니다.** 호출 자체는 남겼습니다 — **스펙은 아직 옛 동작**
(*"등록 직후엔 분석이 안 된 상태다"*)이라, 자동 시작이 없는 경로가 남아 있어도 우리가 채웁니다.

### 3·4·5번은 같은 종류입니다

**입력이 바뀌었는데 그 입력에 대한 답이 안 지워지는 것.** 제목을 고치면·탭을 옮기면·
다이얼로그를 닫으면 앞선 판정은 무효입니다.

`AddRosterDialog`의 `reset()`이 다른 건 다 지우면서 **`previewFailure`만 빠뜨렸고**,
탭 전환도 `preview`만 지우고 있었습니다.

## 4. 아직 못 하는 것

| | 무엇 | 누가 |
|---|---|---|
| 🟠 | **4.5MB 초과 PDF** — 정답은 **presigned S3**(스펙 명시 · 계약 변경) | 백엔드 |
| 🟠 | 원본 우회는 **로컬에서 8MB 성공**했지만 **Vercel 한도를 아무도 안 쟀다** | 프리뷰 배포 필요 |
| 🟡 | 분석 자체가 이 환경에서 자주 실패한다(교안 17개 중 실패 다수) · **사유가 응답에 없다** | 백엔드(10차 요청) |

### 원본 우회가 왜 가능해졌나 (참고)

15차에 포기했던 이유는 **우회할 곳이 없어서**였습니다 — Lambda는 6MB, 그런데 App Runner
원본도 3MB에서 413이었습니다. **그 벽이 사라졌습니다.**

```
                15차          지금
Lambda 프록시    6MB 벽        6MB 벽 (그대로)
App Runner 원본  3MB에서 413   8MB → 201 ✅
```

로컬에서 vite에 원본용 프록시 경로를 하나 더 두니 **8MB가 201로 올라갔습니다.**
다만 **막는 것 둘**이 남습니다.

- **Vercel rewrite 자체 한도를 안 쟀습니다** — 로컬만 보고 고치면 배포에서 또 413
- **App Runner는 잠듭니다** — 잠들면 404만 주고 스스로 못 깨어나서, 원본에 쏘기 전에
  프록시로 깨우는 단계가 필요합니다(백엔드가 AI 쪽에 쓴 그 패턴)

## 5. 참고로 알아 둘 것

**교안 제목은 지워도 계속 점유됩니다.** 유니크 인덱스가 부분 인덱스가 아니라 전역이라
논리 삭제한 것과도 부딪힙니다(스펙 명시). *"아까 지웠는데 왜 중복이라고 하지"* 가 나옵니다 —
그래서 화면 문구에 그 사실을 같이 적었습니다.

> 같은 제목의 교안이 이미 있습니다
> 교안명을 바꿔 주세요 — **지운 교안도 제목을 계속 차지합니다.**

**`trainees/preview`는 아무것도 만들지 않습니다.** 한때 응답이 `registeredCount`라 「등록
됐다」로 읽혔는데(우리도 그걸 보고 기수 명단을 뒤졌습니다), 31차 요청으로 **`registrableCount`**
로 바뀌고 스키마도 갈렸습니다.
