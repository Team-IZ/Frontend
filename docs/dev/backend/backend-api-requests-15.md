## 1. 🔴 R1 — 기수의 「이번 회차」를 물을 API가 없습니다

### 요청

```
GET /api/v0/cohorts/{cohortId}/projects/current
```

**그 기수에서 지금 굴러가는 회차 하나**를 돌려주세요. 응답은 프로젝트 상세
(`GET /projects/{projectId}`)와 같은 모양이면 충분합니다 — `projectId` · `name` ·
`sequenceNo` · `status` · `startDate` · `endDate`.

없으면(회차 0개) `404`가 아니라 **본문 없이 비어 있음**을 알 수 있으면 좋겠습니다 —
회차를 아직 안 만든 기수는 실패가 아니라 정상 상태입니다.

### 왜 필요한가

지금 OP-01 대시보드는 이렇게 하고 있습니다.

```
GET /cohorts/{id}/projects   →  회차 7개 전량 + 집계   (4.6초 · 2.4KB)
      ↓ 그중 1개만 골라서
GET /projects/{pid}/class-progress                     (1.7초)
```

**7개 중 6개를 버립니다.** 그리고 목록 응답의 `conceptCandidateCount`(교안 섹션을 읽어야
나오는 값)를 대시보드는 **쓰지도 않습니다.**

### 목록 조회가 왜 느린가 — 실측

```
엔드포인트                    연결(TCP+TLS)   TTFB     크기
GET /cohorts                       72ms      1.53s    1.0 KB
GET /cohorts/{id}/projects         79ms      4.62s    2.4 KB   ← 이것
GET /cohorts/{id}/analytics/actions        204ms      2.13s    1.5 KB
GET /cohorts/{id}/analytics/risk-trainees  127ms      2.18s   21.4 KB
GET /projects/{projectId}                   —         2.11s    1.8 KB
```

**네트워크가 아닙니다.** 연결은 80ms이고 전송은 0.2ms입니다(`4.621018` → `4.621255`).
21KB짜리 `risk-trainees`가 2.2초인 것을 보면 크기 문제도 아닙니다 — **2.4KB를 만드는 데
4.6초**입니다.

회차 수에 비례하지도, 필터로 줄지도 않습니다.

```
9기  회차 7개   5.28s  4.90s  4.85s      전체(7개)             4.85s
10기 회차 6개   4.22s  4.44s  4.48s      ?status=RUNNING(1개)  4.48s  ← 1건인데 같습니다
8기  회차 6개   4.00s  3.87s  4.82s      ?size=1               5.03s  ← 무시되고 7건이 옵니다
7기  회차 6개   4.03s  4.29s  4.70s
```

요청과 무관하게 **일정하게 4~5초**라, 매번 고정된 무거운 집계를 도는 것으로 보입니다.
반면 **단건 상세(`GET /projects/{projectId}`)는 2.1초**입니다 — 목록보다 2.5초 빠릅니다.

### 왜 화면이 혼자 못 푸는가

스웨거 **82개 경로를 전수로 확인**했습니다(실서버 `/v3/api-docs`, 로컬 스펙과 동일).
「기수의 현재 회차」를 주는 것은 없고, 근접한 둘은 이렇습니다.

| | 문제 |
|---|---|
| `GET /cohorts/{id}/projects` | 4.6초 · 전량 + 안 쓰는 집계 |
| `GET /projects/{projectId}` | 2.1초로 빠르지만 **`projectId`를 이미 알아야** 합니다 |

`risk-trainees`가 `rounds[].projectId`를 주어서 회차를 특정할 수 있을 것 같았는데,
**두 값이 없어 못 씁니다.**

| 없는 것 | 왜 필요한가 |
|---|---|
| 프로젝트 `status` | 어느 것이 진행 중인지 모릅니다 |
| `startDate` | 화면이 「제출 시작 08-03」을 씁니다 |

`GET /cohorts/{cohortId}`(기수 상세)에도 회차 정보는 없습니다.

### 왜 「필드 추가」가 아니라 「신설」인가

`rounds[]`에 `status`·`startDate` 두 필드를 넣는 것이 더 작은 변경입니다. 그런데 그러면
**「이번 회차가 무엇인가」를 프론트가 계속 판정**하게 됩니다 — 지금 화면이 들고 있는 규칙은
이렇습니다.

```
진행 중(RUNNING) → 없으면 가장 이른 예정(PLANNED) → 그것도 없으면 마지막 회차
```

이건 **저희가 지어낸 규칙**이고 어디에도 합의된 적이 없습니다. 서버 정렬이 바뀌면 조용히
다른 회차가 뜨고, 같은 판단이 필요한 화면이 늘면 규칙이 두 곳으로 갈립니다.

「지금 어느 회차인가」는 화면 취향이 아니라 **도메인 사실**이라 서버가 판정하는 것이
맞다고 봅니다(저희 `api-boundary` 원칙도 *"판정·정렬·집계는 서버"* 입니다).

### 효과

| | 지금 | 신설 후 |
|---|---|---|
| 이번 회차 블록 | **8.8초** | **3.9초** (`current` 2.1초 + `class-progress` 1.7초) |
| 버리는 데이터 | 회차 6개 + 안 쓰는 집계 | 없음 |
| 회차 선택 규칙 | 프론트 | 서버 |

### 신설이 어렵다면 — 대안

`rounds[]`에 **`status`와 `startDate` 두 필드만** 추가해 주셔도 대시보드는 `/projects`를
뺄 수 있습니다(회차 블록 3.9초). 선택 규칙은 프론트에 남지만 성능 문제는 같이 풀립니다.

### 참고 — 목록 조회 자체도 느립니다

OP-03 프로젝트 목록은 이 조회가 **화면 자체**라 첫 진입이 5초입니다. `current`가 생겨도
그쪽은 그대로이므로, 여유가 되면 **`conceptCandidateCount`가 목록에 꼭 필요한 값인지**
봐 주세요 — 목록 화면은 이 값을 배지 하나에만 쓰고, 상세에서 다시 조회합니다.

## 2. 🔴 R2 — 교안 PDF 등록이 막혀 있습니다

### 관측

`POST /api/v0/curricula`(multipart)가 **크기와 무관하게 전부 413**입니다(2026-08-12 실측,
운영 계정 토큰).

```
1MB → 413    2MB → 413    5MB → 413    9MB → 413    11MB → 413
```

응답이 원인을 말해 줍니다.

```
HTTP/1.1 100 Continue
HTTP/1.1 413 Payload Too Large
server: envoy          ← App Runner 라우터가 직접 답합니다
content-length: 0      ← 본문이 없습니다 = 앱까지 안 갔습니다
```

**앱이 답한 것이 아닙니다.** 스프링이 크기 제한으로 막았다면 JSON 본문이 오는데
(`{"status":413,...}`) 본문이 0바이트이고 `server: envoy`입니다.

참고로 **16바이트짜리 더미 PDF는 500**이 났습니다(`{"status":500,...}` JSON) — 그건 앱까지
도달했다는 뜻이라, 실제 파일 크기가 조금만 커져도 envoy에서 잘린다는 것을 보여줍니다.

### 프록시 전환과 별개입니다

`.env.local`을 프록시로 바꾼 뒤에도 같습니다.

| 보낸 곳 | 3MB | 8MB |
|---|---|---|
| 프록시(`lambda-url`) | 413 | 413 · `Request must be smaller than 6291456 bytes` |
| 원본(`awsapprunner`) | **413** | 413 |

프록시의 **6MB는 Lambda Function URL 플랫폼 한계**라 이해하고 있습니다(AI 서비스 PR에서
확인하신 그 제한입니다). **문제는 원본도 3MB에서 413**이라는 것입니다 — 6MB와 무관한
별개 벽입니다.

### 왜 지금 물어보나

AI 서비스 쪽에서 **「무거운 것은 프록시를 건너뛰고 원본으로 직접」** 패턴을 적용하셨다고
들었습니다(warmup은 프록시, PDF는 origin). 프론트도 같은 패턴을 쓰려고 했는데,
**원본이 안 받아서 우회할 곳이 없습니다.**

### 요청

| 물어보는 것 |
|---|
| ① App Runner / envoy에 **요청 본문 크기 제한**이 걸려 있나요 |
| ② 있다면 상한이 얼마이고, 올릴 수 있나요 |
| ③ `POST /api/v0/curricula`가 지금 **실제로 동작하는 경로**가 있나요(운영에서 교안을 어떻게 올리고 계신가요) |

### 같이 확인 부탁드립니다 — 교육생 코드 제출(ZIP)

`POST /api/v0/analyses`는 아직 Backend 클라이언트가 없다고 하셨는데, **화면은 이미
「최대 50MB」를 사용자에게 약속하고 있습니다**(`ZIP_HELP`). 지금 구조로는 프록시 6MB는
물론 원본도 못 갑니다.

만드실 때 **presigned S3 업로드**를 검토해 주시면 좋겠습니다 — 브라우저가 S3로 직접 올리고
서버는 키만 받는 방식이면 프록시·envoy 한계를 둘 다 비켜갑니다. AI PR 논의에 나왔던 그
방식입니다.

### 재현

```bash
TOKEN=... # operator 로그인 토큰
python3 -c "open('/tmp/t.pdf','wb').write(b'%PDF-1.4\n'+b'0'*(3*1024*1024))"
curl -i -X POST 'https://mmbvymzj5k.ap-northeast-1.awsapprunner.com/api/v0/curricula?title=t' \
  -H "Authorization: Bearer $TOKEN" -F "file=@/tmp/t.pdf"
```

## 3. 🔴 R3 — 프록시가 동시 요청의 프리플라이트를 502로 죽입니다

### 증상

대시보드(OP-01)에서 **「이번 회차」와 「반 비교」 블록이 랜덤하게** *"불러오지 못했습니다"*
가 됩니다. 새로고침하면 다른 블록이 죽거나 정상이 되기도 합니다.

### 원인 — 프리플라이트(`OPTIONS`)가 502입니다

브라우저는 `Authorization` 헤더가 붙은 요청 앞에 **CORS 프리플라이트**를 먼저 보냅니다.
화면이 조회 셋을 동시에 쏘면 **프리플라이트 셋도 동시에** 나가는데, 프록시가 그중 둘을
502로 죽입니다.

```bash
# 프리플라이트 3개를 동시에 (3회 반복)
for EP in analytics/risk-trainees analytics/actions projects; do
  curl -s -o /dev/null -D - -X OPTIONS "$PROXY/api/v0/cohorts/$COHORT/$EP" \
    -H 'Origin: http://localhost:5174' \
    -H 'Access-Control-Request-Method: GET' \
    -H 'Access-Control-Request-Headers: authorization' &
done; wait
```

```
1회차   502 / 502 / 200
2회차   502 / 502 / 200
3회차   502 / 502 / 200
```

**프리플라이트가 502면 브라우저는 본 요청을 아예 보내지 않습니다.**

```
✗실패 .../cohorts/{id}/projects — net::ERR_FAILED
```

### 프록시 층 문제인 것이 확실합니다

| | 결과 |
|---|---|
| 프록시로 동시 3개(GET) | **10회 중 9회 502** |
| **원본으로 같은 동시 3개** | **5/5 성공** |
| App Runner 로그 | 그 시각 **에러 없음 · 서비스 `RUNNING`** |

App Runner에 요청이 **도달조차 하지 않습니다.** 502 응답 헤더에
`x-amzn-Remapped-connection: close`가 붙습니다.

### 요청

| 물어보는 것 |
|---|
| ① 프록시 Lambda에 **예약 동시성(reserved concurrency)** 이 걸려 있나요 — 1이면 동시 호출이 스로틀됩니다 |
| ② `OPTIONS`(프리플라이트)를 **Lambda까지 태우지 않고 프록시에서 바로 응답**할 수 있나요 |
| ③ 502를 낼 때 Lambda 로그에 무엇이 남나요 |

**②가 가장 효과적일 것 같습니다.** 프리플라이트는 본문도 인증도 없는 정형 응답이라
Lambda를 거칠 이유가 없고, 그것만 걷어내도 **동시 호출 수가 절반**이 됩니다.

### 프론트가 지금 하고 있는 것 — 증상 완화

`net::ERR_FAILED`(=`status: 0`)도 재시도 대상에 넣고 **흔들림(jitter)** 을 줬습니다.

```ts
retry: (count, error) =>
  isApiError(error) && (error.status >= 500 || error.isNetwork) && count < 3,
retryDelay: (count) => 400 * 2 ** count + Math.random() * 400,
```

흔들림이 없으면 **동시에 죽은 요청들이 같은 순간에 재시도해 또 겹칩니다.** 이 값으로
실측 4/4 정상이지만, **실패할 때마다 최대 4초가 더 붙습니다** — 근본 해결은 프록시 쪽입니다.

> 10차 요청서에도 *"프록시가 병렬 요청에서 502"* 기록이 있습니다. **같은 문제가 재발했고**,
> 이번에는 원인이 프리플라이트라는 것까지 좁혔습니다.

## 4. 🔴 Q1 — 인원이 API마다 다릅니다

### 관측

같은 9기(`f7011ddf-8b38-437e-9917-97725f258d78`)를 **네 곳**에 물었습니다(2026-08-11 실측).

| API | 필드 | 값 |
|---|---|---|
| `GET /cohorts/{id}` | `traineeCount` | **208** |
| `GET /projects/{pid}/class-progress` | `summary.targetTraineeCount` | **208** |
| `GET /cohorts/{id}/analytics/risk-trainees` | `cohortSummary.traineeCount` | **196** |
| `GET /cohorts/{id}/trainees` | `cohortTotal` | **224** |

**208이 둘이라 그게 기준선으로 보입니다.** `risk-trainees`가 `withdrawnCount: 12`를 같이
주고 `196 + 12 = 208`이라, 196은 **중도 이탈 제외**로 설명이 됩니다.

**남는 것은 224입니다** — 208과 **16명** 차이입니다.

### 왜 문제인가

**한 화면 안에서 두 값이 같이 보입니다.**

```
대시보드 머리글    대시보드 › 9기 › 196명 · 9반
      바로 아래    제출  0/208
```

사용자는 이 화면에서 *"이 기수는 몇 명인가"* 를 묻는데 **화면이 두 가지로 답합니다.**
운영 관리 · 명단으로 넘어가면 또 다른 답(224명)이 나옵니다.

### 요청

**각 값의 정의를 알려 주세요.** 통일해 달라는 것이 **아닙니다** — 뜻이 다르면 다 맞고,
화면이 라벨로 구분해 쓰면 됩니다(`대상 208명` · `등록 196명` 처럼).

| 물어보는 것 |
|---|
| ① `208`(기수 상세 · 회차 대상)이 기준선이 맞나요 |
| ② `196`(위험 분석)은 **이탈 12명 제외**가 맞나요 |
| ③ `224`(명단)는 무엇을 더 포함하나요 — 초대 대기? 비활성? |
| ④ **224 − 208 = 16명**은 어떤 상태인가요 |
