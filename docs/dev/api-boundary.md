# API 경계 — 무엇이 서버 것이고 무엇이 화면 것인가

> **이 문서가 답하는 것:** 값 하나를 만났을 때 **어디에 두어야 하는가**, 그리고 연동할 때
> **무엇이 지워지고 무엇이 남는가**.
>
> 옆 문서와의 경계 — [api-layer-decisions.md](api-layer-decisions.md)는 *왜 이 구조인가*,
> [api-codegen.md](api-codegen.md)는 *생성기가 어떻게 만드나*, 여기는 **누구 소관인가**.
>
> **화면을 새로 시작할 때는** [mock-first-screens.md](mock-first-screens.md)를 먼저 본다.

---

## 0. 판정 — 다섯 갈래가 두 자리로 줄었다

예전에는 다섯 갈래를 손으로 나눠 적었다. **스펙이 생기면서 앞 셋이 생성물로 통째로 옮겨갔다.**

| 갈래 | 무엇 | 어디에 | 연동 시 |
|---|---|---|---|
| **① 서버 데이터** | 서버가 그대로 주는 값 | **생성물** `src/api/{태그}/` | 재생성. 손댈 것 없음 |
| **② 서버 판정** | 서버가 **계산해서** 줘야 하는 값 | 〃 | **화면이 계산 중이면 옮긴다** ← 이 문서의 핵심 |
| **③ 계약** | 이름·값을 맞춰야 하는 것(enum·에러코드) | 〃 (`errorCodes.ts`·공유 enum) | **스펙이 원본.** 손으로 안 적는다 |
| **④ 기획 상수** | 양쪽이 같이 아는 규칙 값 | **손** `features/…/rules.ts` | 남는다 |
| **⑤ 화면 것** | 표시·입력·정렬 UI | **손** `features/…/labels.ts`·화면 | 남는다 |

> ### 판정 기준 한 줄 — **스펙에서 유도되는가.**
> 유도되면 생성물, 아니면 손. 애매하면 *"백엔드가 이 값을 바꾸면 우리가 따라가야 하나"* 를 묻는다.

**실제로 이 기준으로 되돌린 적이 있다.** `GENERIC_CODES`(무엇을 분기에 못 쓸 코드로 볼 것인가)를
생성물에 넣었다가 `_contract`로 되돌렸다 — 스펙에서 나온 값이 아니라 **우리 정책**이기 때문이다.
생성물에 두면 스펙에서 나온 것처럼 보여 거짓말이 된다.

## 1. 지금 배치

```
src/api/
├─ _contract/          ★ 손 — 통신 계약. 백엔드가 바뀌어도 시그니처가 남는다
│  ├─ client.ts           전송 · 401 재발급 · signal
│  ├─ errors.ts           ApiError · isGenericCode ← ④에 가까운 우리 정책
│  ├─ authBridge.ts       토큰 주입 빈칸
│  ├─ options.ts          훅 옵션 모양
│  └─ page.ts             목록 봉투 정규화(toPage)
├─ schema.d.ts         ① 생성 — 스펙 원본 타입
├─ errorCodes.ts       ③ 생성 — 에러 코드 유니온
├─ PENDING.md          생성 — 아직 못 쓰는 API
└─ {태그}/             ①②③ 생성 — 타입 · 호출 함수 · 쿼리 키 · 훅

src/features/{역할}/{도메인}/
├─ api.ts              ★ 손 — 화면이 의존하는 유일한 곳. 생성물 or 목을 고른다
├─ rules.ts            ④ 기획 상수
├─ labels.ts           ⑤ 표시 라벨
├─ mockData.ts         목 — 연동 시 **파일째 삭제**
└─ {X}Screen.tsx       ⑤ 그리기만
```

**`api.ts`가 이 구조의 잠금장치다.** 화면은 생성물도 목도 직접 모른다.
스펙 커버리지가 절반이라(프로젝트·교안·세션·리포트·면담이 아직 없다) **한 화면 안에서도
어떤 조회는 실서버, 어떤 조회는 목**일 수 있는데, 그 사실이 화면에 새지 않는다.

## 2. ★ 서버 판정 — 화면이 하면 안 되는 것

**이 문서에서 가장 자주 틀리는 자리다.** 목이 배열이라 화면에서 도는 게 되지만,
실제 API는 그 결과를 준다. 그대로 두면 **연동이 재작성**이 된다.

| 화면이 하면 안 되는 것 | 왜 |
|---|---|
| 전량을 받아 `filter` | **쿼리 파라미터**가 된다 |
| 배열 `sort` | 페이지가 나뉘면 **현재 페이지 안에서만** 맞다 |
| 상태별 집계 `reduce` | 전체 모집단 기준이라 **페이지가 나뉘면 못 센다** |
| 연관 목록에서 개수 합산 | 그 목록 전량을 받아야 셀 수 있다 → 서버가 **숫자로** 준다 |
| 파생 배지를 조합으로 유추 | 규칙이 두 곳에 생긴다 |

### 실제 스펙이 이미 그렇게 되어 있다

`GET /api/v0/organizations`의 설명이 못을 박아 뒀다.

> *"이름 검색·상태 필터·정렬을 **모두 서버가 처리**하므로 화면은 파라미터만 넘기면 된다
> (클라이언트에서 다시 거르지 않는다)."*

```
?query= &status= &sort= &page= &size=
→ { content, page, size, totalElements, totalPages }
```

**파생 배지도 서버가 준다.** `operatorUnassigned`·`budgetExceeded`가 그 예이고,
스펙에 *"저장 상태가 아니므로 status는 그대로 ACTIVE다"* 라고 성격까지 적혀 있다.
화면이 `operators.length === 0`으로 유추하면 **같은 규칙이 두 곳에 생긴다.**

### 목 단계에서도 후자로 맞춘다

```ts
// ✗ 화면이 전량을 받아 거른다 — 연동 시 재작성
const rows = useMemo(() => ALL.filter(...).sort(...), [filters])

// ⭕ 조건을 넘기고 결과를 받는다 — 목이든 실서버든 화면 코드가 같다
const { data } = useFindOrganizations({ query: filters })
```

**목 안에서는 그 로직을 그대로 쓴다** — 지우는 게 아니라 **서버 자리(`api.ts` 안쪽)로 옮기는 것**이다.

### ⚠️ 지금 서버가 못 주는 것 하나 — 상태별 내역

표 헤더의 `준비 중 2 · 진행 중 1 · 종료 1`은 **필터와 무관한 전체 모집단** 기준이라
목록 한 페이지로는 못 만든다. 그런데 `OrganizationListResponse`에 `counts`가 없다.

→ **프로젝트·명단 API가 나올 때 같이 요청한다**(5절). 그전까지 그 내역이 필요한 화면은
목으로 두고, **`items.length`로 대충 세지 않는다** — 페이지가 나뉘는 순간 조용히 틀린다.

## 3. 연동할 때 무엇이 지워지나

| 지워짐 | 남음 |
|---|---|
| `mockData.ts` — **파일째** | **화면 전부** |
| `api.ts` 안의 Mock 블록 | `api.ts` **시그니처** |
| 목 전용 상수(고정 기준일 등) | `rules.ts` · `labels.ts` · 필터·모달 UI 상태 |

**표식을 남긴다 — 검색 한 번으로 지울 것이 다 나와야 한다.**

```ts
// mockData.ts 머리
// ⚠️ Mock 전용 — 백엔드 연동 시 이 파일을 통째로 삭제하세요.

// api.ts 각 함수 안
// ===== Mock 버전 (현재 활성) =====
...
// return findOrganizations({ query })   ← 실제 버전을 주석으로 같이 둔다
```

> **목 전용 값도 경계를 통해 나간다.** 화면이 `mockData`를 직접 import하면 목을 지우는 순간
> 화면이 깨진다. 날짜처럼 목에서 고정해야 하는 값도 `api.ts`가 준다.

## 4. 기획에 없는 값을 만나면

**화면이 기준을 만들지 않는다**(점검표 E8). 임계값·색 구간·단위·조건 필터가 전부 포함된다.
그런데 화면을 그리려면 정해야만 하는 경우가 있다. 그때는 **숨기지 말고 표시한다.**

```ts
/*
  ⚠ 이 숫자는 기획에 없다 — 프론트가 정한 값이다.
  목록의 유일한 경고가 "마감 임박 + 준비 중" 조합인데 임박의 정의가 어느 문서에도 없다.
  일주일을 고른 이유는 "다음 주 회차를 이번 주에 준비한다"는 것뿐이다.
  기획에서 값이 나오면 여기만 바꾼다.
*/
export const DUE_SOON_DAYS = 7
```

**그리고 PR 본문과 이슈에 질문으로 남긴다.** 코드에만 적으면 아무도 안 본다.

> `DUE_SOON_DAYS`는 **아직 미결이다.** 프로젝트 API가 나올 때 함께 정한다 —
> 서버가 `dueSoon: boolean`을 주는 편이 나은지도 그때 판단한다(기준이 없으면 서버도 못 정한다).

## 5. 백엔드와 남은 합의

**대부분 해소됐다.** 1·2·3차 요청서로 정리했고 반영률이 100%다.

| | 상태 |
|---|---|
| ~~id 형식~~ | ✅ **UUID** |
| ~~날짜 타임존~~ | ✅ **ISO-8601 UTC** |
| ~~`status` 판정 주체~~ | ✅ **서버.** 공유 enum으로 |
| ~~에러 코드 체계~~ | ✅ **60종.** `examples` 키에서 기계 추출 |
| **목록 응답의 `counts`** | 🟡 없다. 상태별 내역을 못 만든다(2절) |
| **`totalElements`가 필터 적용 후인가** | 🟡 미확인. 표 푸터·헤더 숫자가 갈린다 |
| `CONCEPT_COUNT = 3` 서버 검증 | ⏳ **프로젝트 API가 아직 없다.** 클라 검증만 있으면 우회된다 |
| `DUE_SOON_DAYS` | ⏳ 기획 결정 대기 |

**막힘 3건은 [3차 요청서](backend-api-requests-3.md)에 있다** — 쿠키 `SameSite` · 배포 도메인 Origin · `GET /me`.

## 6. 새 도메인을 붙일 때 — 순서

```
1  npm run api:pull && npm run api:check      스펙이 생성을 감당하나 (error 0)
2  npm run api:gen                            해당 태그가 available인가 · PENDING.md 확인
3  features/…/api.ts 에 위임 함수를 쓴다       ← 화면이 보는 것은 여기까지
4  화면은 어댑터만 부른다                       생성물도 목도 모른다
```

**3번에서 목록이면 `toPage()`를 통과시킨다.** 봉투가 다섯 가지라 표 컴포넌트가 한 모양만
받게 하려는 것이고, 정규화를 **생성 함수가 아니라 여기서** 하는 이유는 봉투에 같이 실려 오는
값(`activeCount` 등)이 사라지지 않게 하기 위해서다.

```ts
// features/superadmin/orgs/api.ts
export async function listOrgs(query: OrgQuery) {
  const res = await findOrganizations({ query })
  return { ...toPage(res.content ? res : { content: [] }), raw: res }
}
```

**아직 스펙에 없는 도메인은 3번만 목으로 쓴다.** 화면은 차이를 모른다 — 그게 이 경계의 목적이다.
