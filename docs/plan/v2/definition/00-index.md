## 각 문서가 답하는 것

```
1  한 줄       이 화면이 하는 일 하나
2  진입·이탈    어디서 오고 어디로 나가나
3  뷰           구조 스케치
4  데이터       무엇을 읽나 · 무엇을 쓰나
5  액션         버튼을 누르면 무엇이 일어나나
6  상태         빈 · 로딩 · 오류 · 부분 실패
7  안 하는 것    다른 화면 소관인 것 (중복 방지)
```

**7번이 v2에서 새로 들어간 칸이다.** v1이 겪은 문제가 **같은 데이터를 여러 화면이 각자 그린 것**이었다(개입 상세 ↔ 교육생 상세). 정의 단계에서 못을 박는다.

## 케이스는 어디에 있나 — 목업이 단일 원천

**케이스(예외·상태) 표는 목업에 둔다.** 정의서에도 같은 표를 두지 않는다 — **정의서는 안 읽힌다.**
사람들이 여는 것은 목업 URL이고, 백엔드도 그것으로 개발한다. 사본을 만들면 화면을 고칠 때 하나만 고쳐지고 그때부터 어느 쪽이 맞는지 아무도 모른다.

### 목업 안의 두 자리

| | 담는 것 |
|---|---|
| **케이스 계약 상태**(`#cases`) | **전량 표** — 번호 · 상태 · 에러코드 · 문구 · 다음 행동 · 목업 해시. 사이드바 첫 항목이라 한 번에 열린다. 표의 `목업` 열은 그 상태로 가는 링크다 |
| **상태별 화면** | **시각적으로 다른 것만** 그린다 |

### 페이지를 만드는 기준 — "화면이 달라지는가" 하나

| 케이스 | 페이지(`.rpage`) | 계약 표 |
|---|---|---|
| **화면이 다르다** | **만든다** | 행 있음 |
| **서버는 구분하지만 화면이 같다** | 안 만든다 | **행은 나눈다** |
| **화면에 안 나타난다** (라우팅 · 이탈) | 안 만든다 | 행 있음 |

**표의 행 수와 그림 장수는 다르다.** AU-01 예 — `토큰 발급 실패 · 롤백 · 쿠키 실패`는 **표 3행 / 그림 1장**(`#sysfail`)이다. 서버는 셋을 구분해 처리·기록하지만 사용자가 할 수 있는 일은 재시도 하나뿐이라 **그림 3장은 같은 그림**이다. `성공`은 화면을 벗어나므로 **표 1행 / 그림 0장**.

**백엔드 케이스를 빼먹는 것이 아니다.** 그림이 없는 케이스도 표에는 전부 있다 — 빠지면 구현할 때 그 분기를 아무도 모른다.

### 정의서 §6에 남는 것

**"왜 그렇게 정했나"만.** 표로 설명이 안 되는 판단 — 잠금을 안 쓰는 이유 · 감추는 것과 알려주는 것 · 알림 위치 근거 · v1에서 버린 것.

### 케이스 표에 무엇을 적나

```
# · 상태 이름 · 에러코드 · 화면 표현(문구 그대로) · 다음 행동 · 목업 해시
```

**문구는 계약값이다.** `이메일 또는 비밀번호가 올바르지 않습니다`처럼 그대로 적는다 — 요약해 두면 구현할 때 각자 다르게 쓰고, 계정 열거 방지 같은 보안 규칙이 문구에 실려 있어서 바꾸면 규칙이 깨진다.

**에러코드는 프론트 타입과 같은 값을 쓴다**(`src/features/auth/authTypes.ts`). 문서와 코드가 다른 이름을 쓰면 연동할 때 매핑표가 하나 더 생긴다.

### v1에서 가져올 때

**v1 케이스를 그대로 복사하지 않는다.** v1은 기능명세서 case를 1:1로 옮긴 것이고, v2에서 **전제가 바뀐 것이 있다.** 화면마다 §「v1 대조 — 검수 결과」 표에 `그대로 / 고침 / 버림`과 이유를 남긴다.

| 실제 예 | |
|---|---|
| **버림** | AU-01 `계정 잠금`(v1 case2·3) — 명단에 전원 이메일이 있어 **잠금이 남을 막는 수단**이 되고 해제 화면이 없다 → 지연으로 대체 |
| **고침** | AU-01 `미인증`(이메일 인증) → `미활성`(초대 활성화). v2는 인증 메일 단계가 없다(AU-02 §1) — 그대로 뒀으면 **없는 기능을 명세**하게 된다 |
| **그대로** | AUTH-03 예외 전량 매핑 구조 · 계정 열거 방지 문구 규칙 |

## 전역 규칙

**전체 목록은 [01 점검표](01-design-checklist.md)에 있다.** 아래는 그중 배치에 관한 것만 다시 적은 것이다.

### 표 배치 — 3단 고정

```
헤더    제목 + 총개수 (좌)                        [+ 추가] (우)
툴바    검색 · 필터 · 정렬                (전부 좌)
────────────────────────────────────────────────────────
본문
────────────────────────────────────────────────────────
푸터    1–25 / 138 (좌)          [< 1 2 3 >] (중앙)
```

### 상세 — 세로 스택 금지

블록이 5~6개로 늘면 스크롤이 아니라 **탭(3~4개, 항목이 독립일 때)** 또는 **마스터-디테일(좌 목차 → 우 한 섹션)**로 담는다. **목차는 앵커 스크롤이 아니라 섹션 전환**이다.

### 프로젝트는 기수 단위다 — 반 지정이 없다

**v1은 프로젝트가 반 하위**였다(`v1/.../02-domain-hierarchy.md` — *"반에서 진행"*).
v2에서 기수 하위로 올라갔고 **반을 지정하지 않는다.**

검증 개념 3건이 프로젝트 단위로 고정되므로(14번 4-3) **같은 회차를 하는 모든 반·팀·개인이
같은 3건으로 평가**된다. 이 전제 위에 서 있는 화면이 넷이다.

| 화면 | 무엇이 깨지나 |
|---|---|
| **MG-02 히트맵** | `행 10반 × 열(회차×개념)` 격자 — 열이 반마다 달라지면 표가 안 만들어진다 |
| **OP-01 반 비교** | 막대 모집단이 달라져 나란히 못 놓인다 |
| **OP-02 분석** | 회차별 위험자 비율이 같은 판정 기준(9-2)을 공유한다 |
| **9-6 집단 미달** | *"반 절반 이상"* 이 여러 반이 같은 개념을 했다는 전제다 |

**배정은 세 군데로 갈린다.**

| | 어디 | 언제 |
|---|---|---|
| 학생 → 반 | **OP-06 `반·명단`** | 기수 세팅 시 1회 |
| 학생 → 팀 | **MG-08 `팀`** | **프로젝트마다** 재편성 |
| ~~프로젝트 → 반~~ | **없다** | |

> **재개 조건:** 트랙 축이 확정되거나 롤링 입학이 도입되면. 상세는
> [OP-03](OP-03-project-list.md) 3-1.

### 숫자 점수는 어디에도 없다

0~5 루브릭은 내부 값이다. 화면에는 **도달 단계(0~4단) · 힌트 횟수 · 축별 서술**만 나온다. 학생·매니저·오퍼레이터 전부 같다([14](../14-verification-design.md) 10-3).

### 배지

**처리하면 줄어드는 수에만** 단다. 위험 인원처럼 그 회차 내내 안 줄어드는 수는 배지가 아니다.

### 스코프 표기

지금 보는 범위만 쓴다(`A·B·C반 138명`). **남의 권한 범위는 화면에 쓰지 않는다.**

### 역할 게이팅 없음

흐린 버튼·잠긴 액션을 만들지 않는다. 할 수 있는 일이 다르면 **화면이 다르다**([17](../17-ia-menu-tree.md) 5절).

## 작업 순서

정의는 전부 쓰고, 목업은 [15번 차수](../15-mockup-rework-plan.md)를 따른다 — **데이터가 만들어지는 순서**다.

| 단계 | 화면 | 왜 이 순서인가 |
|---|---|---|
| **1** | OP-03 · OP-04 프로젝트 | **개념 3건이 모든 문항의 출발점** |
| **2** | TR-01 · TR-02 홈 · 제출 | 제출이 없으면 세션이 없다 |
| **3** | TR-03 검증 세션 | **제품의 핵심.** 나머지 화면의 데이터 원천 |
| **4** | TR-04 내 리포트 · MG-08 프로젝트 상세 | 세션 결과의 첫 소비처 |
| **5** | MG-02 히트맵 · MG-06 교육생 상세 | 누적 조회. 4가 정해져야 그린다 |
| **6** | MG-03 · MG-04 면담 | 브리프가 2~5의 값을 읽는다 |
| **7** | MG-01 · OP-01 대시보드 | 다른 화면의 상태를 모으는 화면 |
| **8** | MG-05 · MG-07 · MG-09 · OP-02 · OP-05 | 나머지 조회 |
| **9** | OP-06 운영 관리 · SA-01~03 | 세팅·콘솔 |
| **10** | AU-01~03 | v1 이식 · 기계적 |

**대시보드가 7단계인 이유:** 두 대시보드 모두 다른 화면의 상태를 모아 보여준다. 모을 것이 정해지기 전에 그리면 v1처럼 **정의 없는 KPI 칸**이 남는다.
