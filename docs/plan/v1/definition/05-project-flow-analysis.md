# 프로젝트 중심 생성·측정 플로우 분석 (체크포인트 의존성)

> 작성 2026-07-15. 계기: "프로젝트가 체크포인트보다 상위 개념인데, 현재 사이드바·화면 플로우가 의존 순서를 뒤집어 놨다"는 지적.
> 결론 제안 = D77(01-decision-log.md). 이 문서는 근거·데이터플로우.

---

## 0. 핵심 명제

**체크포인트는 파생물이다.** 체크포인트(측정 이벤트)는 "누가(제출 단위) · 무엇을(레포 코드) · 어떤 초점(포커스)"이 **확정된 뒤에만** 의미 있는 값을 가진다. 그런데 현재 IA는 `측정 계획(체크포인트)`을 `프로젝트`와 **동렬 사이드바 항목**으로 두어, 마치 독립적으로 세울 수 있는 것처럼 보이게 한다. 이건 데이터 의존성의 역전이다.

증거(현재 M03): 체크포인트 표에 "응시 진행 **48/48**"이 박혀 있다. 이 `/48`(분모)은 **제출 단위가 개인 48명으로 이미 확정됐다**고 가정한 값이다. 하지만 팀 프로젝트라면 분모는 48이 아니라 **N팀**이고, 그 N은 팀 편성 전에는 존재하지 않는다. 즉 측정 계획 화면이 **아직 존재하지 않는 값**을 표시하고 있다.

## 1. 의존 구조 — 선형이 아니라 다이아몬드 (레포∥체크포인트는 병렬)

⚠️ 초판은 ①→②→③레포→④체크포인트로 **선형**으로 그렸으나 오류. 레포와 체크포인트는 **직교 축**(레포=측정 대상/누구의, 체크포인트=측정 계기/언제)이라 순차 종속이 아니다. 관계는 **스냅샷을 통한 M:N** — 한 레포는 모든 체크포인트에서, 한 체크포인트는 모든 단위 레포를 측정.

```
        ① 프로젝트 생성 (유형 개인/팀 결정)
             │
        ② 단위 확정 (팀 편성 or 개인) = 분모 N
            ╱          ╲
   ③ 레포 연결      ④ 체크포인트 계획      ← 병렬(서로 안 막음)
   (단위별·상시)     (측정일·추출정책·질문수·포커스)
            ╲          ╱
        ⑤ 측정 실행 = 스냅샷(레포 × 체크포인트)   ← 여기서만 수렴
```

**각 의존의 강제성(정확히):**
- ①→②: 유형 '개인'이면 ② 스킵(단위=학생, 이미 존재). '팀'이면 ②가 단위를 만든다.
- ②→③: 레포는 **단위에 매달린다**. 팀이면 팀 확정 후, 개인이면 ① 직후 가능.
- ①→④: **체크포인트 계획은 프로젝트만 있으면 선다.** 레포 불필요(커리큘럼 결정). 단 "응시 X/N"의 분모 N은 ②에서 상속.
- ③∥④: **레포 연결과 체크포인트 계획은 서로를 막지 않는다.** 병렬.
- (③,④)→⑤: 각 체크포인트 **실행 시점**에 그 단위 레포 스냅샷이 있어야 측정. 레포 준비는 **체크포인트별 JIT 조건**(미연결 unit은 그 체크포인트 응시 불가), 전역 선행조건 아님.

**두 개의 "커버리지"를 구분(초판이 뭉갠 것):**
- **레포 커버리지(③):** 레포 연결한 unit / 전체 unit = 준비 상태(예: 3/4팀 레포 연결).
- **응시 커버리지(⑤, 체크포인트별):** 그 체크포인트에 응시한 unit / 전체 unit(예: 체크포인트2에 3/4팀 응시).
- 전자가 후자를 게이트하지만 **값이 다르다.** 현재 M03의 "48/48"은 후자(응시)인데 분모를 개인으로 가정한 것이 문제.

## 2. 단계별 데이터 플로우 — 무엇이 들어와 어떻게 처리·표시·사용되나

| 단계 | 들어오는 값(입력) | 처리 | 산출·표시 | 사용처 | 담당 |
|---|---|---|---|---|---|
| **① 프로젝트** | 프로젝트명, **유형(개인/팀)**, 대상(기수·반), 기간, 요구사항/결정지점, 검증포커스(자동제안+편집), 회차 수 | Project 엔티티 생성, 유형 분기 확정, 포커스 시드 | 프로젝트 목록에 신규 행(상태=준비), 유형 배지 | 하위 전 단계의 컨테이너 | 총괄 |

**"이 시점엔 아직 모르는 값" (표시하면 안 되는 것):**
- ① 시점: 팀·레포·응시대상 수 전부 미정 → 프로젝트 목록에 "응시율" 표시 금지.
- ② 이전: 분모 N 없음 → "3/4" 류 진행률 표시 불가(현재 M03이 위반).
- ③ 이전: 레포 커버리지 없음 → 추출·측정 관련 값 전부 미정.

## 3. 사용자가 든 두 예시의 정확한 해소

**(a) "4팀 중 3팀만 냈다 = 3/4"**
- **분모 4** = ② 팀 편성에서 태어남(팀이 4개로 확정되는 순간).
- **분자 3** = ③ 레포 연결(또는 ⑤ 제출)에서 채워짐.
- 따라서 "3/4"는 **②가 끝나야 분모가, ③/⑤가 진행돼야 분자가** 생긴다. ④측정계획이 이 값을 "가정"하면 안 되고, **②·③에서 확정된 값을 물려받아** 표시해야 한다.

**(b) "문제 3개 낼지 4개 낼지"**
- 질문수(예산 N)는 ④에서 회차별로 정하지만, **그 결정의 전제**가 ①유형(개인/팀은 질문 설계가 다름)·②단위다. 팀 프로젝트면 "팀 공동 코드 vs 본인 커밋"(추출범위)에 따라 질문 수·성격이 갈린다. 즉 질문수는 ④의 값이되 **①②의 확정을 근거로** 정해진다. 구조 미확정 상태에서 질문수부터 정하면 근거가 없다.

## 4. 교정된 IA — 체크포인트를 프로젝트 하위로

**현재(잘못):** 사이드바에 `프로젝트`와 `측정 계획`이 **동렬 형제**. 팀·레포는 M13에 섞여 있고, 측정계획은 프로젝트와 무관하게 독립돼 보임.

**제안: 측정 계획(체크포인트)을 프로젝트 워크스페이스의 하위 단계로.** 운영 관리를 4탭(의존 순서)으로 만든 것과 동형.

```
프로젝트 [총괄]
  └─ 프로젝트 선택 → 워크스페이스 탭 (의존 순서대로):
       [개요] 유형·대상·요구사항·포커스
       [팀·레포] 팀 편성(D75 골라담기) → 단위 확정 → 레포 커버리지
       [측정 계획] 체크포인트 (①만 있으면 계획 가능 · 레포는 실행 시 JIT · 응시 분모는 단위에서 상속)
       [결과] 체크포인트 리포트·성장추이
```

**사이드바 상위 순서 (준비 → 실행 → 분석):**
1. 대시보드
2. **운영 관리**(기수·반·명단·매니저) [총괄] — 조직 구조
3. **프로젝트**(생성·팀·레포·측정계획·결과) [총괄] — 커리큘럼·측정 구조
4. 교육생 / 위험·분석 / 개입 / 리포트 [담당] — 실행·모니터링
5. 교안

- **기수-전체 체크포인트 타임라인**(모든 프로젝트의 체크포인트를 누적 순서로)은 리포트/대시보드에서 별도로 제공 — 개별 프로젝트 안에선 그 프로젝트의 회차만, 전체 조망은 리포트에서.
- 게이트(교정): 측정 계획 **계획**은 프로젝트만 있으면 가능(레포 게이트 아님). 다만 **응시 X/N의 분모 N**은 단위(②)가 있어야 뜬다 — 단위 미확정이면 스케줄은 짜되 "응시 대상 미확정"으로 표기(지금의 가짜 48/48 금지). 레포는 **체크포인트별 실행 시점 JIT**(미연결 unit은 그 체크포인트 응시 불가로 표시).

## 6. 관련 결정·피드백 연결
- **D76**(회차/체크포인트 3층 모델) — 이 분석의 전제.
- **FB-F5**(프로젝트·측정계획 생성=총괄) — 이 플로우의 ①④ 담당 확정.
- **FB-F6**(검증포커스 자동+수동) — ①의 입력.
- **FB-F4**(팀 배정 시 이해도·가능여부) — ②의 표시.
- **FB-Y1**(레포 연결 일관성) — ③의 컴포넌트.
- **FB-M02a**(팀 매핑 골라담기) — ②의 인터랙션(D75 재사용).
- **D75**(명단 기반 배정) — ②가 그 패턴의 형제(반 배정 = 팀 배정).

→ 이 항목들이 사실상 **하나의 플로우**(프로젝트→팀→레포→체크포인트)로 수렴. 개별이 아니라 이 순서로 묶어 재설계하는 게 맞음.
